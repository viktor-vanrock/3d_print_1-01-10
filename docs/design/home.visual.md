## 1. Композиция — три зоны, один скролл

```
┌─────────────────────────────────────────────┐
│ HomeHeader (закреплено, не в счёт «двух      │  ← header.capsule.md, без изменений
│ блоков» — это хром страницы, не контент)     │
├─────────────────────────────────────────────┤
│                                               │
│   Hero (строка ввода)          .homeSearchHero
│                                               │
├─────────────────────────────────────────────┤
│                                               │
│   Полки ИЛИ результаты поиска  ← ОДНО МЕСТО, │
│   (взаимоисключимо)              не сумма    │
│                                               │
└─────────────────────────────────────────────┘
```

**Инвариант:** `<main className="homeContent">` держит ровно два прямых секционных
ребёнка — `<HeroSearch />` и `<Showcase />` (переименование `NeuroSearch`/`PopularGallery`
ниже, §7). `Showcase` сам решает, рендерить полки или результаты — снаружи это один
слот, компонент никогда не растёт в третий `<section>`. Всё, что сегодня стоит между
ними (`PersonaCtaRow`, `ContinueCard`, `CompatModule`, `ActivationChecklist`) —
удаляется по адресам §8.

**Постоянный контракт — `FirstRunFlow` (MF-437).** На первую сессию
(`state === "first_run"`) третьим/последним ребёнком `.homeContent` рендерится
`FirstRunFlow` (персона/принтер/филамент/чек-лист как терминальный шаг) — это
решение оператора от 2026-07-04 (см. комментарий в `firstrun.tsx`), зафиксированное
UX как постоянное в [MF-921](mention://issue/c6354907-1bfc-41e3-949b-dfd11e8bf8d0)
(вариант (b): легализация, не переезд в отдельный гейт-шаг — см.
`home.scenario.md §5–§6`). Инвариант «ровно два ребёнка» на состояние `first_run`
не распространяется — это норма, не дефект приёмки, и реализации на главной не
требует: код уже так рендерит (`home.tsx:144`), MF-918 его не трогала.
«Мягкость» блока (позиция ниже полок, не гейт до ценности) держат правила из
`home.scenario.md §6`: один шаг за раз, «Пропустить» равноправно с ответом,
дисмисс персистится навсегда.

Ширина контента — текущий `--content-max` (не `--content-max-wide`; header.capsule.md
уже зафиксировал, что wide-шапка Дома не тянет за собой широкий контент, «без потери
воздуха» — не пересматриваем).

## 2. Hero: анатомия по контролам

Каркас `.homeSearchHero` остаётся. Меняется состав и подписи.

```
        Нейропоиск · Kandinsky 3D              ← Eyebrow: см. фикс ниже
        ┌─────────────────────────────┐
        │  Что напечатаем?          × │        ← .homeGhostInput + новая .homeInputClear
        └─────────────────────────────┘
        Сгенерировать: «кот в шлеме» →          ← новая строка-подпись (см. §2.3)
        ( 🎤 )        ( ✨ )                     ← без скрепки (см. §2.4)
   [котик в шлеме] [ваза с узором] [органайзер]…  ← .homeSearchChips, без изменений
```

### 2.1 Eyebrow — врущая надпись уходит

`<Eyebrow>Нейропоиск · Kandinsky 3D</Eyebrow>` (`home.tsx:203`) переименовать в
**«Опишите словами · найдём или сгенерируем»** — статична, не завязана на состояние
поля (никаких «Поиск…»/«Генерация…» здесь, это не статус-строка, а объяснение
формата один раз при входе на экран). `aria-label` инпута — `"Найти модель"` (не
«Поиск модели» — минимальная синонимичная правка, только чтобы не расходиться с
надписью искры ниже).

### 2.2 Кнопка очистки — новый контрол

`.homeInputClear` — маленькая круглая «×», 24–28px, приглушённое стекло (не
акцентный цвет — это не действие-решение, а отмена), внутри правого края
`.homeGhostInput` (инпут получает `padding-right` под неё). Видима только когда
`query.length > 0` — `data-visible` тем же паттерном, что `data-armed` у send-кнопки.
Тач-таргет полной кнопки — 48×48px (сама «×» визуально меньше, хит-зона больше,
стандартный приём иконки в поле). `aria-label="Очистить"`.

### 2.3 Подпись-обещание искры — новый элемент

Строка под инпутом, **одна на весь hero**, три состояния:

| Состояние поля | Текст | Стиль |
|---|---|---|
| Пусто | *(не рендерится)* | — |
| Есть текст, идёт/прошёл поиск | «Сгенерировать: «{query}» →» | приглушённый текст (`--text-dim`), акцентная стрелка `--accent`; сама строка кликабельна — тот же `handleSend()`, что и искра (дублирующий, не альтернативный, путь к тому же действию) |
| Есть текст, результаты показаны, под ними | «Не то? Сгенерируем «{query}» →» | тот же стиль, но рендерится **под последней плиткой результатов**, не под инпутом (см. §4 «Нашлось») — это разные DOM-места одной мысли, не дубль на экране одновременно |

Обрезка длинных запросов — `text-overflow: ellipsis`, `max-width` по колонке инпута
(не растягивает hero вширь).

### 2.4 Голос и фото — скрепка снимается, микрофон остаётся приглушённым

- **Микрофон** (`.homeGhostButton`, `MicIcon`) — визуально остаётся ровно как
  сегодня (круглая ghost-кнопка слева от искры), но пока голос не реализован
  (GAP-VOICE, §11 сценария) — **не рендерить саму кнопку**, оставить только её
  место пустым (не резервировать заметный пробел — hero центрируется по двум
  оставшимся кнопкам: искра одна, без микрофона по левую руку). Как только
  голос будет готов, кнопка возвращается на то же место слева от искры.
- **Скрепка** (`ClipIcon`, «Прикрепить фото») — удаляется из разметки целиком
  (не `display:none`, не disabled — код-referens тоже уходит, вернётся вместе с
  MF-12 на то же место справа от искры).
- Итог на релиз MF-803: единственная кнопка в `.homeSearchActions` — искра.
  Раскладка `.homeSearchActions` (`home.css:498`) при одной кнопке остаётся
  центрированной, не «съезжает» влево — Front проверяет на пустом экране.

### 2.5 Искра — подпись честная

`aria-label="Найти или сгенерировать"` (`home.tsx:219`) → `aria-label="Сгенерировать"`
(пока пусто — не нажимается, см. `data-armed`) либо динамический
`` `Сгенерировать: «${query}»` `` (совпадает с текстом подписи §2.3 — на скринридере
и на экране должно звучать одинаково, это один и тот же контракт кнопки).

### 2.6 «Все результаты →»

Под сеткой найденных (максимум 8, §4 «Нашлось») — текстовая ссылка-строка,
не кнопка: `Eyebrow`-стиль без uppercase, обычный текст + стрелка, ведёт на
`/project?q=…` (тот же `marketPath` + `q`). Не путать с подписью искры (§2.3) —
это две отдельные строки, «Все результаты» первой (сразу под сеткой), подпись
искры — второй (см. очерёдность в §4).

## 3. Полки — реестр вместо одной галереи

`PopularGallery` (`home.tsx:258`) заменяется на `Showcase`, рендерящий **массив
именованных полок**, каждая — тот же каркас, что уже есть (`.homeGalleryHead` +
`.homeGallery`/`ModelTileGrid`), просто несколько раз подряд:

```
Популярно сейчас · Печатают чаще всего        ← Eyebrow (текущий стиль, без изменений)
[ 🧊 ][ 🧊 ][ 🧊 ][ 🧊 ][ 🧊 ][ 🧊 ][ 🧊 ][ 🧊 ]  → .homeGallery, горизонтальный скролл на mobile/tablet

Сделано из других моделей · Ремиксы через Кандинского
[ 🧊 ][ 🧊 ][ 🧊 ][ 🧊 ][ 🧊 ]

Новое в каталоге
[ 🧊 ][ 🧊 ][ 🧊 ][ 🧊 ][ 🧊 ][ 🧊 ]
```

- Вертикальный зазор между полками — тот же ритм, что сегодня между
  `.homeGalleryHead` и следующим модулем (`gap` секции), не сжимать при
  нескольких полках подряд — каждая полка визуально самостоятельна.
  «Новое в каталоге» — **всегда последняя** полка на экране (§4 сценария),
  без верхнего разделителя/линии между полками — просто следующий Eyebrow.
- **Полка `<4` моделей не рендерится вообще** — ни секции, ни Eyebrow, ни
  пустого места. `Showcase` фильтрует полки ДО рендера, не показывает
  скелет/заглушку для несостоявшейся полки.
- Ranking/состав полок — реализация Front/Data по реестру сценария §4
  (`home.scenario.md`); визуально каждая полка — идентичный каркас, разница
  только в Eyebrow-тексте и наборе моделей. Дизайн не вводит второй вид
  карточки-полки.
- **Реестр на релиз (GAP-SHELVES, §11 сценария):** до API-реестра полок рендерятся
  ровно две — «Популярно сейчас» (`sort: popular`) и «Новое в каталоге»
  (`sort: new`), в этом порядке. Это не временная заглушка с своим видом —
  тот же компонент полки, просто короче список; когда реестр появится,
  добавление «С чего начать»/«Апгрейды…»/«Функциональное»/«Ремиксы» не меняет
  визуал ни на пиксель, только количество полок.
- **Горизонтальный скролл внутри полки** (уже есть — `.homeGallery` скроллится
  на узких экранах, `home.css:637/643`) не должен красть жест смены раздела —
  ссылка на существующий разбор [touch.nav.md §2](touch.nav.md), приоритет
  как у `HeroCarouselView`: жест, стартующий внутри `.homeGallery`, остаётся
  внутри неё.

### 3.1 Плитка — без изменений

`ModelTileButton`/`ModelTileGrid` (`modeltile.tsx`) переиспользуются как есть —
тот же слоистый стек (глянец/фото/тень). Никакого нового вида карточки для полок.

`PopularGallery`. Переключение — замена содержимого этого слота, не смена секции.

| Состояние | Что рисуем | Ссылки |
|---|---|---|
| **Пусто в поле** | Полки (реестр §3). Искра приглушена (`data-armed` отсутствует, текущее поведение). Подпись-обещание (§2.3) не рендерится. | — |
| **Ищу** (250мс дебаунс уже истёк, запрос в полёте) | Полки **не исчезают мгновенно** — на их месте появляется сетка **скелетов** такой же геометрии, что `ModelTileGrid` (8 плейсхолдеров: та же рамка/радиус/размер тайла, залитая приглушённым стеклом + `modelShimmer`-подобное мерцание, тот же keyframe что уже используется у карточек каталога — не новый). | **Не нашлось** | Полки **не возвращаются** (это не «пусто в поле» — здесь есть намерение) и не рендерится второй `EmptyState`-модуль: одна строка по центру области полок — «В каталоге такого нет — сгенерируем?» + искра рядом (той же формы, что hero-искра, но меньшего/равного размера — дизайн-решение Front по факту компоновки, разрешено переиспользовать `.homeSendButton` уменьшенной версией или полноразмерной, лишь бы не вводить третий вид кнопки). ## 5. Полки и персона — визуал не меняется от порядка

Персона решает **какие Eyebrow-заголовки и в каком порядке**, не рисует ничего
поверх карточек (без бейджей персоны на тайлах, без цветовой дифференциации полок
по персоне — рамка §4 сценария явно это запрещает). Единственное визуальное
отличие персонализированного дома от гостевого/дефолтного — состав и заголовки
полок; сама сетка тайлов идентична.

## 6. Первый визит — одна коучмарка у искры

Переиспользуется существующий `Coachmark` (`ui.tsx`, уже используется в
`home.tsx:138` для другого триггера — паттерн общий). Новый текст:

> **«Опишите словами. Найдём — покажем. Не найдём — сгенерируем.»**

Позиционирование — **у искры** (`.homeSendButton`), не у поля целиком: коучмарка
объясняет судьбу нажатия, значит стоит рядом с тем, что нажимают. Не двигает
раскладку (`position: absolute`/поповер-паттерн, как остальные коучмарки).

**Это ЕДИНСТВЕННАЯ коучмарка на главной.** `link_printer`/`compat_badge`
(`coachmarks.ts`) — снимаются из главного экрана вообще: их условия срабатывания
(`!has_printer`, `has_printer && !catalog_visited`) переезжают на экраны, где
привязка принтера/бейдж совместимости реально видны (раздел «Принтеры», карточка
модели/каталог — адрес переезда §7 сценария, реализация — отдельные карточки на
тех разделах, не эта). `useActiveCoachmark`/`COACHMARK_SPECS` на главной сужаются
до одной записи с новым текстом выше и новым условием: показывать **всем**
(гостю тоже — `localStorage`, не только `home_dismissed_prompts` авторизованного
— сценарий §6 требует обоих путей хранения), не только `returning`-состоянию.

Дисмисс — **четыре независимых триггера**, любой первый гасит навсегда:
первый символ в поле · тап «Понятно» · 8 секунд без взаимодействия · любой
скролл страницы. Существующий `Coachmark` компонент, вероятно, поддерживает
только явный `onDismiss` — остальные три триггера (символ/таймер/скролл)
вызывают тот же `dismiss()` из `home.tsx`, это событийная проводка, не новый
визуал кнопки «Понятно».

## 8. Что снимается и куда переезжает (визуальная сторона адресов §7 сценария)

Функциональные адреса — в `home.scenario.md §7`, здесь — что это значит для

## 10. Пульт (ТВ) — фокус и «назад»

**Вынесено из MF-918/MF-803 в [MF-923](mention://issue/6deb5a5b-a7e3-4534-9e45-2f44d3ba5a16).**
В кодовой базе не было ни одного примитива, отличающего «пульт/D-pad» от
«мышь/тач» — слепой `autofocus` на первую плитку без такого детекта ломает
обычный вход мышью/тачем (нежданный скролл-джамп, лишний focus-ring на
десктопе/тач). Решение по детекту — [tv.10foot.md §9](tv.10foot.md), новый
раздел; реализация примитива + разводка по этому §10 — отдельная карточка
MF-923, не блокирует релиз hero-поиска/полок. Раздел ниже остаётся контрактом
на будущее — MF-923 реализует его как есть.

- **Вход на экран:** фокус на первой плитке первой полки (`Showcase`), НЕ на
  `.homeGhostInput`. Focus-ring — [tv.10foot.md §3](tv.10foot.md) (2–3px
  мятное кольцо + glow, ярче состояния покоя).
- **Порядок:** `↑` с первой плитки первой полки → чипы-подсказки (`←/→` между
  ними) → `↑` ещё раз → поле ввода → `→` с поля → искра (единственный
  primary, получает толстый focus-ring по правилу «primary фокусируется явно»,
  tv.10foot.md §3). `↓` с последней плитки последней полки → фокус уходит на
  меню шапки (не тупик — tv.10foot.md §3 «D-pad ловит намерение»).
- **«Назад»:** из `/generate` → Дом с сохранённым запросом в поле (не сброс).
  С Дома при непустом поле → очистка поля (эквивалент тапа «×», §2.2) —
  только повторное «назад» на уже пустом поле выходит из раздела/приложения.
- **Свайп внутри полки** (`touch.nav.md §2`) не участвует в ТВ-навигации —
  пульт не свайпает, это чисто тач-ветка того же требования «не красть
  жест».

## 11. Границы и что НЕ входит в этот файл

- Разметка иконок (Mic/Clip/Spark и т.п.) — существующие компоненты
  `home.tsx`, переиспользуются как есть за вычетом Clip (§2.4).
  Новых SVG-иконок эта карточка не вводит, кроме `×` очистки (§2.2 — простая
  line-иконка 2px, тот же язык, что остальные — components.md § «Иконки»).
- Точные пиксельные отступы — Front выводит из существующих `metrics.md`
  токенов и текущей вёрстки `home.css`, не из этого файла (здесь — контракт
  поведения и состава, не тех-дизайн).
- Моушен/звук новых элементов (скелет-переход, «×», подпись-обещание,
  коучмарк-дисмисс по скроллу/таймеру) — раскладка по существующим токенам
  зафиксирована в [motion.md §9](motion.md) / [sound.md §3](sound.md)
  (обновлено этой же карточкой) — новых Motion/Sound-карточек заводить не
  нужно, это применение уже описанных примитивов (`.reveal`, `modelShimmer`,
  `tick`), не новая хореография калибра hero-send-кнопки.
- Гостевая главная без `AuthGate` — визуал состояний гостя описан выше (§4),
  но не включается физически, пока GAP-GUEST не решён CTO (см. `frame.md`,
  отдельная карточка).
