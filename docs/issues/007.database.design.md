## Суть

Первичная задача перед реальной разработкой: спроектировать схему хранения данных — какие сущности, в каком хранилище, как связаны. Не эпик (нет внешнего ресёрча/API-интеграций), но требует решений до того, как писать код в `apps/api`.

## Что уже решено (входные ограничения, не пересматривать без причины)

- **PostgreSQL** — основная БД, владелец схемы `apps/api` (`docs/architecture/readme.md`).
- **pgvector** — для нейропоиска (`docs/issues/003.neural.search.md` / `docs/epics/neural.search.md`), НЕ отдельная vector DB.
- **S3 (cloud.ru), бакеты `3mf`/`auth`** — файлы/бинарники НЕ в Postgres (`docs/infra/readme.md`). Postgres хранит метаданные и путь/ключ до объекта в S3, не сам файл.
- **PostgreSQL job tables** — очередь фоновых задач для `apps/mesh`; отдельный broker/cache в текущем runtime не используется.
- Пользователь появляется через 3 провайдера авторизации (`docs/issues/002.auth.triple.md`) — Сбер ID / PlagID / возможно GigaID — схема `users` должна с самого начала поддерживать multi-provider (не «email как PK»), см. эпик.
