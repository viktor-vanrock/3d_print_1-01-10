# VERSIONING

## Формат

Формат — `YY.RELEASE.MINOR`.

Пример: `26.1.1` — 2026 год, релиз №1, первая сборка этого релиза.

- **YY** — две цифры года. Проставляется в момент, когда РЕЛИЗ вырезается (не пересчитывается задним числом у старых релизов).
- **RELEASE** — номер релиза. Увеличивается **только явным решением Валерия** («когда я говорю что релиз»). **Счётчик сквозной (монотонный)** — не сбрасывается с началом нового года, год живёт отдельным полем `YY`.
- **MINOR** — минорное обновление. Увеличивается автоматически на каждый шип в рамках текущего релиза. Начинается с **1** при вырезании нового релиза (не с 0 — см. пример `26.1.1`).

Источник истины — [`version.json`](version.json) в корне репозитория (не `package.json` — сервисы полиглотные, единая версия продукта не может жить в JS-специфичном файле). Git-тег — `v{YY}.{RELEASE}.{MINOR}`, например `v26.1.1`.

## Кто что бампает и когда

| Событие | Что происходит | Кто/что триггерит |
|---|---|---|
| Push в `dev` | `scripts/version.mjs bump` (MINOR+1) → коммит `chore(release): … [skip ci]` + тег, прямо в `dev` | Автоматически, CI (`.gitverse/workflows/release.yaml`) |
| «Режем релиз» | Свод миноров в `changelog.md` → `scripts/version.mjs release` (RELEASE+1, MINOR=1, YY=текущий) → тег `v{YY}.{RELEASE}.1` | **Решает оператор** → CTO курирует заметки → **Git режет** по runbook'у (ниже). `workflow_dispatch action=release` — запасной ручной путь оператора |
| Деплой в **dev** | Таймер `portal.deploy-dev` на VDS тянет `origin/dev` раз в минуту | Автоматически, systemd-таймер (см. `CONTRIBUTING.md` § «Модель веток») |
| Деплой в **production** | Таймер `portal.deploy.timer` на VDS тянет `origin/main` каждую минуту, собирает и перезапускает `portal.api`; `main` двигается только промоушеном `dev→main` (Lead/директора) | Автоматически по факту промоушена (см. `CONTRIBUTING.md` § «Промоушен в main») |

MINOR бампается на каждый push в `dev` (реальный рабочий ствол — CONTRIBUTING.md, модель двух веток). `main`/продакшн обновляется реже, осознанным промоушеном — версия туда просто едет вместе с промоутнутыми коммитами, отдельного бампа при промоушене нет.

**История (MF-1792, 2026-07-17):** до перехода на модель двух веток (2026-07-08) бамп триггерился на push в `main` — тогда `main` был активным стволом. После перехода на dev/main реальная интеграция ушла в `dev`, а `main` стал обновляться редко ручным промоушеном; триггер на `main` из-за этого молчал 6 дней (668 неучтённых коммитов), пока футер портала не соврал версию. Перенесено на push в `dev`.

## Как пользоваться руками

```bash
node scripts/version.mjs bump      # минорное обновление
node scripts/version.mjs release   # новый релиз
```

Оба варианта пишут `version.json` и печатают итоговую строку версии.

## Changelog

`changelog.md` (корень репо) ведётся по [Keep a Changelog](https://keepachangelog.com/ru/) по секциям `## [YY.RELEASE.MINOR] — YYYY-MM-DD`. Черновик секции генерит **`scripts/changelog.mjs <range> --version X.Y.Z`**: группирует Conventional Commits (`feat`→Added, `fix`→Fixed, `perf`/`refactor`→Changed, неконвенциональные→Прочее, `docs`/`chore`/`ci`/`test`→сворачивает во «Внутреннее» счётчиками), тянет `MF-N` ссылки, оставляет плейсхолдер строки-итога. Владелец файла — роль **Git**, нарратив курирует **CTO** (строка-итог голосом оператора).

Фиксируем **релизы и заметные изменения**, а не каждый MINOR-бамп (их сотни, полная история — в git). При нарезке релиза секция сводит работу накопленных миноров под новый `RELEASE.1`.

Между релизами `## [Unreleased]` наполняется **автоматически**: `.gitverse/workflows/release.yaml` на каждый push в dev тем же `chore(release)`-коммитом, что и version bump, вызывает `scripts/changelog-unreleased.mjs` — он берёт `feat`/`fix`/`perf`/`refactor`-коммиты этого push'а (диапазон с предыдущего `chore(release)`-коммита) и подсыпает пункты в нужные подсекции (`Added`/`Fixed`/`Changed`), дедуплицируя по тексту пункта/MF-ссылке против того, что уже вписано вручную автором PR. (MF-908, 2026-07-18: раньше это было ручной обязанностью роли Git — «держать тёплым» — и не исполнялось несколько проходов подряд, застой доходил до 322 миноров без заметок; автор PR по-прежнему может вписать пункт в свой коммит вручную, скрипт его не задвоит.)

## Кто режет релиз — владельцы

Разделение «решение / нарратив / исполнение» (уточнено оператором 2026-07-09):

- **Оператор (Валерий) — РЕШАЕТ**, когда режется релиз («когда я говорю что релиз» / «переходим на новую версию»). RELEASE не бампается на автомате.
- **CTO — релиз-менеджер**: по команде оператора определяет scope (что из накопленного входит) и **курирует заметки голосом оператора**. Git руками не трогает.
- **Git — релиз-инженер**: исполняет нарезку по runbook'у ниже. Владеет `scripts/changelog.mjs`, `scripts/version.mjs`, `changelog.md`.

## Runbook нарезки (роль Git)

Один заход по команде «режем релиз»:

```bash
git fetch origin main dev --tags
# база релиза = origin/main (прод); невыкаченную работу dev с CTO: промоутить или в след. релиз
NEXT=$(node scripts/version.mjs peek release)               # напр. 26.3.1 (файл НЕ пишется)
LAST=$(git tag --list 'v*.*.1' --sort=-v:refname | head -1) # старт прошлого релиза, напр. v26.2.1
git checkout -B dev origin/main
node scripts/changelog.mjs "$LAST..HEAD" --version "$NEXT" > /tmp/sec.md
#  → причесать /tmp/sec.md (строка-итог с CTO), вписать в changelog.md ВМЕСТО [Unreleased],
#    завести сверху новый пустой «## [Unreleased]»
node scripts/version.mjs release                            # version.json → $NEXT
git add changelog.md version.json
git commit -m "chore(release): v$NEXT [skip ci]"            # [skip ci] — чтобы CI не бампнул MINOR
git tag "v$NEXT"
git push origin HEAD:main && git push origin "v$NEXT"
git push origin HEAD:dev    # если dev был == main; иначе merge тега в dev (НЕ форсить)
release-announce "🚀 v$NEXT — <итог>"                       # Telegram-анонс
```

**Тег релиза — единственный санкционированный ручной тег**, и только через этот runbook. MINOR-теги по-прежнему ставит только CI (`release.yaml`). Релиз-коммит `chore(release): … [skip ci]` — третий санкционированный писатель `main` (наряду с промоушеном `dev→main` и CI); пишет одинаково в `main` и `dev`, дивергенции не создаёт.

**GitVerse Releases API** (`POST /releases`) на этом инстансе недоступен (проверено — 400/404; публичный API отдаёт `/pulls`, `/issues`, не releases/tags/actions). Источник заметок = `changelog.md` в репо + git-тег + Telegram-анонс, не «релиз-страница» GitVerse.
