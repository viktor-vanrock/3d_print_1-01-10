# Активация: первый запуск и онбординг (product-слой)

**Продуктовая логика first-run/activation по факту реализации MF-436 в `dev`.** Этот документ описывает
то, что **реально работает** в коде — цели шагов онбординга, условия перехода между состояниями и
бизнес-правила. Не философия «как хотелось бы»; когда описание эпика шире реализации, здесь зафиксирован
именно shipped-контракт, а расхождения помечены явно.

Происхождение (эпик MF-435 «профиль активации главной», в рамках кабинета MF-15):
- **Фаза 1 (MF-436)** — стейт-машина и API: дом читает/пишет состояние **только** через API, без
  localStorage-состояния флоу.
- **Фаза 2 (MF-437)** — first-run флоу: персона → принтер → филамент/soft-track → чек-лист.
- **Фаза 3 (MF-438)** — события воронки + inferred-персона.

**Где живёт код:**
- API и стейт-машина — `apps/api/src/profile/activation.ts`, схема — таблица `user_activation`
  (`apps/api/db/schema.sql`).
- Клиент состояния — `apps/web/src/home/activation.ts` (хук `useActivation`, `resolveTier`).
- First-run флоу — `apps/web/src/home/firstrun.tsx` (`computeFirstRunStep`, `FirstRunFlow`).
- Чек-лист — `apps/web/src/home/checklist.tsx`; inferred-персона — `apps/web/src/home/inferpersona.ts`.
- Оркестрация на главной — `apps/web/src/home/home.tsx`; персона-дом returning-состояния —
  `apps/web/src/home/personahome.tsx`.
- Экран выбора @-хендла (отдельный, до дома) — `apps/web/src/auth/onboarding.tsx`.
- События — клиент `apps/web/src/home/track.ts`, allowlist на бэке — `ACTIVATION_EVENT_NAMES`.

## 1. Модель состояния (что персистится)

Всё состояние активации живёт в одной строке `user_activation` на пользователя (PK `user_id`, каскадное
удаление вместе с юзером). Дом ничего не хранит в localStorage — единственный источник истины это API.

| Поле | Тип | Смысл (product) |
| --- | --- | --- |
| `state` | `first_run` \| `returning` (default `first_run`) | Стадия жизненного цикла пользователя на главной. |
| `has_printer` | bool (default `false`) | Есть ли у пользователя хотя бы один привязанный принтер. Ведётся автоматически при add/delete принтера. |
| `first_run_completed_at` | timestamp \| null | Когда онбординг завершён (проставляется вместе с переходом в `returning` через `first_run_completed`). |
| `primary_persona` | `novice` \| `maker` \| `author` \| `builder` \| `pro` \| null | Кто пользователь по задаче. `null` = ещё не определились / «просто посмотреть». |
| `persona_source` | `declared` \| `inferred` \| null | Как персона получена: тап по плитке (`declared`) или достроена по поведению (`inferred`). |
| `home_tier` | `auto` \| `home` \| `farm` \| `business` (default `auto`) | Масштаб парка → раскладка дома. `auto` = вычисляется по числу принтеров. |
| `sessions_seen` | int (default `0`) | Грубый счётчик заходов, инкремент на каждом `GET /me/activation`. Триггер авто-перехода в `returning`. |
| `activation_checklist` | jsonb `{ключ: bool}` | Отметки выполненных шагов чек-листа (`catalog_visited`, `model_uploaded`, `profile_visited`, …). |
| `home_dismissed_prompts` | jsonb `{ключ: bool\|string}` | Гейты «не показывать повторно» для шагов флоу и одноразовых подсказок; сюда же пишется `printer_answer` (`yes`/`no`/`skip`). |

Строка создаётся **лениво** при первом `GET /me/activation` (upsert), там же считается сессия — отдельного
эндпоинта «начало сессии» нет, N сессий — намеренно грубая метрика.

---

## 2. Стейт-машина: `first_run` → `returning`

Два состояния. Обратного перехода `returning → first_run` в продуктовом потоке нет (поле можно выставить
руками через PATCH, но флоу его не инициирует). Переход в `returning` вызывают **три** пути (замысел
MF-436: «чек-лист завершён/закрыт ИЛИ ага-действие ИЛИ прошло N сессий»); в shipped-коде конкретные
писатели перехода такие:

1. **N сессий (авто, сервер).** На `GET /me/activation`, если `state = first_run` и
   `sessions_seen ≥ RETURNING_AFTER_SESSIONS` (**= 5**), сервер сам переводит в `returning`. Пользователь
   ничего не делал — просто зашёл 5-й раз.
2. **Чек-лист пройден (клиент).** Когда все шаги чек-листа `done` и `state = first_run`, дом шлёт
   `PATCH /me/activation {first_run_completed: true}` → сервер ставит `first_run_completed_at = now()` и
   `state = returning`. Событие воронки — `first_run_completed {trigger: "checklist_all_done"}`.
3. **Пользователь пропустил онбординг (клиент).** Кнопка «Пропустить» на карточке персоны шлёт тот же
   `first_run_completed: true`. Событие — `first_run_completed {trigger: "persona_skip"}`.

**«Ага»-действие (привязка принтера) и переход.** Гипотеза активации завязана на привязку принтера, но
сам по себе `POST /me/printers` **не** флипает `state` — он выставляет `has_printer = true`. В `returning`
привязка принтера приводит через закрытие шага «Привяжите принтер» в чек-листе (путь №2), а не отдельным
переходом. Это сознательный shipped-контракт, не баг: единственные писатели `state = returning` —
серверный счётчик сессий и клиентский `first_run_completed`.

`PATCH /me/activation` также принимает `state` напрямую (`first_run`/`returning`) — служебный путь, флоу
им не пользуется.

## 3. Персоны

Enum из пяти значений (проверяется CHECK-констрейнтом БД и allowlist API): `novice`, `maker`, `author`,
`builder`, `pro`. Персона меняет **порядок** CTA и модулей дома, но не состав («мягкая
переприоритизация», критерий приёмки эпика) — она не отбирает доступ и не прячет разделы.

**Плитки выбора (declared).** Карточка персоны (`PersonaCard`) — не отдельный экран-опросник, а мягкий
блок **после** поиска и галереи (фидбек владельца: «главная встречает делом, онбординг — ниже и
пропускаем»). Тап пишет `primary_persona` с `persona_source = declared`. Плиток **четыре**:

| Плитка | persona | Подпись |
| --- | --- | --- |
| «У меня есть принтер» | `novice` | «Хочу печатать» |
| «Выкладываю модели» | `author` | «Я автор» |
| «Собираю принтер» | `builder` | «DIY / Voron» |
| «Печатаю на заказ» | `pro` | «Мастер / ферма» |

`maker` **не** предлагается плиткой — это значение только для inferred-персоны (см. §4).

**Источник персоны:** `declared` (явный тап) весомее `inferred` (достроено по поведению). Declared-персону
система никогда не переписывает автоматически.

---

## 4. Inferred-персона (Фаза 3, returning-состояние)

Когда пользователь пропустил/смазал развилку персоны, дом достраивает её по первым действиям. Правило
(`inferPersona`, по убыванию уверенности):

1. **3+ принтера в парке** → `pro` (сильный сигнал масштаба).
2. **Загрузил первую модель** (`activation_checklist.model_uploaded`) → `author`.
3. **Есть принтер И листал каталог** (`has_printer` && `catalog_visited`) → `maker`.
4. иначе → `null` (не навязываем).

Достройка применяется **только** если `primary_persona` пуст или уже был `inferred` — declared-персону не
трогаем, inferred даём уточняться. Отдельного события воронки на inferred нет (`persona_declared`
зарезервирован за явным тапом): inferred проявляется в самих CTA/модулях, не в метрике.

---

## 5. Тир дома (`home_tier`)

Раскладку главной определяет масштаб парка. `resolveTier`:

- если `home_tier ≠ auto` — берём выставленное значение (ручной выбор);
- иначе `auto`: **≥ 3 принтера → `farm`**, иначе **`home`**.

`business` к v1 включается **только ручным выбором** — заказов/выплат ещё нет, авто-детектить нечего. Тир
проброшен в `data-tier` на корне дома и переключает модули/плотность, а не доступ.

## 6. First-run флоу (пошаговый онбординг)

Флоу рендерится на главной, только пока `state = first_run` и есть сессия (гостю не показывается).
Показывается **ровно один шаг за раз** (бюджет анти-перегруза). Текущий шаг — чистая функция от
персистентного состояния (`computeFirstRunStep`), поэтому переживает reload: вопрос не задаётся заново на
каждый заход. Правила выбора шага:

1. Нет `primary_persona` → **`persona`** (карточка персоны). Цель: понять задачу пользователя, чтобы
   переприоритизировать дом. Можно «Пропустить» (→ сразу `returning`).
2. Нет ответа `printer_answer` → **`printer_question`** («У вас уже есть 3D-принтер?» — Да / Пока нет /
   Пропустить). Ответ (в т.ч. «Пропустить») сразу пишется в `home_dismissed_prompts.printer_answer`, иначе
   при перезагрузке вопрос вернётся на каждый заход.
3. Ответ **`yes`**:
   - нет принтера и picker ещё не закрыт → **`picker`** (привязка принтера);
   - иначе не пройден филамент → **`filament`** (опц. «ваш пластик»);
   - иначе → **`checklist`**.
4. Ответ **`no`/`skip`**:
   - не пройден soft-track → **`soft_track`** (мягкий трек «нет принтера»);
   - иначе → **`checklist`**.

Все ветки сходятся к чек-листу; выход в `returning` — через прохождение чек-листа, пропуск персоны или 5
сессий (§2).

### Цели шагов
- **Персона** — задать контекст (что переприоритизировать).
- **Развилка «есть принтер?»** — one-branch паттерн: три тапа, ничего не блокирует.
- **Picker (привязка принтера)** — довести до «ага»-действия. Источники привязки: коннектор, популярные,
  поиск, каталог, ручной ввод, IP (LAN). Ручной ввод не блокируется (см. §9).
- **Филамент** — опциональный шаг «ваш пластик», всегда **каталожная** привязка (ручного ввода в этой фазе
  нет).
- **Soft-track «нет принтера»** — три двери, ни одна не ведёт в пустой экран: «Посмотреть, что печатают»
  (витрина/каталог), «Подобрать первый принтер» (picker как живая витрина-заглушка), «Продолжить без
  принтера» (поиск и лента уже доступны гостю).

## 7. Чек-лист активации под персону

Финальный шаг флоу и «якорь» первых шагов. Первый пункт — **«Аккаунт создан»** — всегда уже выполнен и не
кликабелен: прогресс стартует не с 0, а с ~20% (эффект Зейгарник). Состав шагов зависит от персоны:

- **`author`:** Аккаунт создан · Загрузите первую модель · Заполните профиль · Найдите вдохновение в
  каталоге.
- **прочие (`novice`/`maker`/`builder`/`pro`):** Аккаунт создан · Привяжите принтер (`builder`: «Привяжите
  вашу сборку») · Откройте модель для печати (`builder`: «Сравните станки в каталоге») · Укажите филамент.

Отметки шагов пишутся в `activation_checklist` (`model_uploaded`, `catalog_visited`, `profile_visited`);
«Привяжите принтер» закрывается по `has_printer`, «Укажите филамент» — по наличию филамента. Прохождение
**всех** шагов → переход в `returning` (§2, путь №2). Чек-лист можно свернуть («Понятно»/dismiss —
`home_dismissed_prompts.checklist`); свёрнутый или полностью пройденный чек-лист не показывается.

**Границы намеренно уже описания эпика:** шаги, ведущие в ещё не существующие разделы web (выложить в Make,
сравнить принтеры отдельной страницей, привязать выплаты), **не** включены — чтобы не давать шаг «в
никуда». Как только раздел появляется, сюда добавляется шаг с реальной ссылкой.

## 8. «Ага»-момент (гипотеза активации)

Гипотеза эпика: пользователь активирован, когда **привязал принтер и открыл первую совместимую модель**. В
returning-доме модуль «Совместимо с вашим <принтером>» ловит первое открытие совместимой модели и один раз
за аккаунт пишет событие `aha_reached` (гейт `home_dismissed_prompts.aha_reached`). Это метрика гипотезы,
а не отдельный переход состояния.

## 9. Бизнес-правила и инварианты

- **`has_printer` ведётся автоматически.** `POST /me/printers` → `true`; удаление **последнего** принтера
  → `false`.
- **Ровно один основной принтер.** Первый привязанный принтер становится `is_primary = true`; выставление
  нового основного снимает флаг со всех остальных (инвариант держат и POST, и PATCH).
- **Ручной ввод принтера = сигнал спроса.** `link_source = manual` → `verified = false`: конкретной модели
  ещё нет в каноническом каталоге принтеров, факт логируется как сигнал спроса для ресёрчеров. Привязка из
  каталога/коннектора → `verified = true`.
- **Привязка из каталога** (`link_source = catalog`) пишет `catalog_printer_id` (FK на каталог
  `printers`), отдельно от legacy `printer_id`; метрика «каталог → мой парк» считается по нему.
- **Филамент — только каталожная запись** (нет ручного ввода/`verified`/`link_source` в этой фазе).
- **Уведомления первого запуска.** В `first_run` дом показывает системное «Добро пожаловать»; при
  отсутствии принтера — предупреждение «Привяжите принтер».

## 10. События воронки активации

Пишутся через `POST /me/activation/events` — тонкий фасад над общим `emitEvent` с тем же fail-closed
consent-гейтом и серверным `anon_id`-merge, что и остальные продуктовые события. Имя события — из
**заужённого** allowlist `ACTIVATION_EVENT_NAMES` (клиент не может писать произвольное имя таксономии).
Аналитика best-effort: потеря одного события не роняет и не тормозит экран. События воронки:

`first_run_start` · `home_view` · `persona_declared` · `printer_question_answered` · `printer_picker_open`
· `printer_linked` · `printer_not_found_manual` · `soft_track_chosen` · `checklist_step_done` ·
`home_cta_click` · `aha_reached` · `first_run_completed` · `state_changed` — плюс сопутствующие
поведенческие (`home_hero_submit`, `nav_item_click`, `gallery_tile_click`, `profile_view`,
`generation_outcome`, `home_hint_chip_click`).

## 11. Экран выбора @-хендла (до дома)

Технически отдельный слой от активации, но часть первого пути пользователя: до входа в приложение AuthGate
показывает экран выбора @-хендла (`apps/web/src/auth/onboarding.tsx`), пока `handle_confirmed = false`.
При первом входе логин уже сгенерирован автоматически — пользователь оставляет его или меняет; отправка
формы шлёт `PATCH /me {username}`, бэкенд сам ставит `handle_confirmed = true`. После этого пользователь
попадает на главную, где начинается first-run флоу активации, описанный выше.
