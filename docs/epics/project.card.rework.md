## 3. Решения (6 новых механик)

### 3.1 Полноэкранный режим вьюера

**Решение:** CSS-оверлей на весь вьюпорт (`position: fixed; inset: 0`, z-index поверх шапки) как основной механизм — Fullscreen API (`element.requestFullscreen()`) как **прогрессивное улучшение** поверх него, не единственный путь. Почему не полагаться только на Fullscreen API: на iOS Safari `requestFullscreen` для произвольных DOM-элементов не работает надёжно (только для `<video>`) — CSS-оверлей работает везде одинаково, Fullscreen API просто убирает браузерный хром там, где браузер это позволяет.

- Кнопка «Развернуть» (line-глиф, ≥48px) в углу canvas рядом с существующим «⟲ сброс» (`marketplace.full.md` §12.2). Открывает оверлей: canvas растягивается на весь вьюпорт студийным фоном, панель действий (голос/скачать/поделиться) сворачивается в компактный плавающий ряд снизу или прячется за тапом — на реализацию Front, не блокирует приёмку.
- Выход: явная кнопка «✕» + `Escape` (и `fullscreenchange`, если реальный Fullscreen API сработал).
- Ресайз: переиспользовать существующий resize-listener `modelscene.ts` (обновление `camera.aspect`/`updateProjectionMatrix`), просто триггерить его и на вход/выход из оверлея, а не только на `window.resize`.
- Слабое устройство/только постер (нет GLB): фуллскрин всё равно доступен (крупно посмотреть фото), просто без орбиты — так же, как сегодня постер работает без интерактива.
- Владелец: Front (реализация) + Design (лёгкая дельта хрома — где именно живут свёрнутые кнопки в фуллскрине).

### 3.2 Автоориентация «дном к полу»

Сегодня `modelscene.ts::fitAndAdd()` только центрирует bbox и подгоняет масштаб под фиксированный радиус камеры — ориентация модели остаётся такой, как её экспортировал mesh-пайплайн из исходного файла (случайная относительно «правильного» вида). Это касается **только презентации** (вьюер + webp-постер), не самого печатного файла — слайсер всё равно делает свой auto-orient/поддержки независимо, канонический 3MF/исходник не трогаем.

**Решение:** вычисление ориентации переезжает в mesh-пайплайн (Python, `apps/mesh`), не во фронт — по двум причинам: (1) webp-постер уже рендерится сервером с фиксированным ракурсом 3/4 (`model.preview.md`), этому рендеру в любом случае нужна «правильная» ориентация модели ДО съёмки кадра; (2) вычислять эвристику на каждом клиентском рендере одного и того же GLB — трата CPU много раз ради одного и того же результата.

- **Алгоритм (рекомендация, финал — Mesh, спайк в фазе 1):** «физически устойчивые позы» по выпуклой оболочке — для каждой грани convex hull моделируем, как объект лёг бы на неё, считаем итоговую высоту bbox и площадь контакта; выбираем позу с наибольшей контактной площадью / наименьшей высотой (типичная эвристика auto-orient слайсеров). Если в пайплайне уже используется `trimesh` (Python, обычная зависимость для STL/3MF) — у него есть готовый `compute_stable_poses()`, ровно эта задача «из коробки»; если библиотеки нет — сделать свою упрощённую версию по той же логике. Точный выбор — на Mesh, не блокирует остальные стадии.
- **Детерминизм:** симметричные модели (шар/куб) дают несколько равнозначных поз — фиксировать выбор детерминированно (например, по наименьшему индексу грани), чтобы повторная генерация не «прыгала».
- **Где хранится:** результат **запекается прямо в GLB** (трансформ корневого узла сцены) и учитывается в камере при рендере webp — **без новых колонок БД и без нового API-контракта**. Вьюер просто рисует сцену, как она авторизована файлом.
- **Кнопка «⟲ Сброс»** (уже существует, `marketplace.full.md` §12.2) меняет смысл: сегодня возвращает к захардкоженному углу — теперь возвращает к авторизованной (детектированной) ориентации модели. Упрощение кода Front, не усложнение.
- **Бэкафилл:** уже готовые (`ready`) модели нуждаются в перегенерации `preview`/`thumbnail` с новой логикой — та же схема бэкафилл-джобы, что паттерн MF-521 (идемпотентно, без даунтайма).
- **Граница честности:** это эстетическая эвристика для показа/фото, не гарантия печатаемости/поддержек — orbit по-прежнему свободный, юзер может крутить как хочет; авто-ориентация только задаёт стартовый вид.

### 3.3 Отступ вьюера от верхних блоков сайта

Явный acceptance-критерий (Design аудит + Front фикс, если разрыв подтверждён): герой-вьюер и парящая правая колонка страницы `/project/:id` не должны примыкать вплотную к `HomeHeader`/`wide`-шапке — безопасный отступ сверху, тот же принцип, что уже описан для wide-режима (`projects.page.md` Р1), просто явно проверяется на этой странице. Мелкий пункт, включён в критерии приёмки §6, не отдельная механика.

### 3.4 Статистика: публичная (по принтерам) + владельческая (детальная)

- **Публичная («Напечатали», уже частично построено):** `MakeStatsPanel` расширяется с «топ-1 комбо станок×филамент» до **полного списка** — каждый станок, на котором есть хотя бы один make, с числом печатей, отсортированный по убыванию (это и есть буквально «на каких принтерах и сколько раз печатали» из запроса). Источник данных не меняется — те же само-репорт `makes.machine_id`, никакой новой телеметрии. Пункт каталога станка — опционально ссылка в его карточку (задел на MF-32).
- **Владельческая («Статистика», сегодня EmptyState-заглушка):** активируем реальными данными. Ключевое решение — **закрываем открытый вопрос `marketplace.v2.md` §6.3 про `views_count`**: по факту событие `model_view` уже реально эмитится в проде (`analytics.events.md`, 6 из 11 событий live с 2026-07-09) — раз данные есть, вопрос решён **да**, считаем просмотры. Владелец видит: голоса, скачивания, **просмотры**, комментарии, makes — те же 4+1 плиток, что уже спроектированы (`marketplace.v2.md` §6.2, приглушённо/разгорается по «яркость=важность» при свежей активности), плюс тот же полный per-machine список, что и в публичном блоке (без дублирования кода — общий компонент).
- Ничего не «изобретаем заново» — обе части это активация уже спроектированных, наполовину построенных механик.

### 3.5 Meta-карточка (визуальный блок метаданных)

Технические метаданные (формат/габариты/размер/дата загрузки) сегодня — `SpecRow`, плоский приглушённый список строк (`marketplace.v2.md` §2.2 п.7). **Решение:** оформить тем же данными отдельным лёгким визуальным примитивом `MetaCard` (сетка глиф+подпись+значение на стекле, в духе `StatTile` статистики §3.4) — не новые данные, а новая подача существующих. Ничего не меняется в контракте API. Design фиксирует композицию (может остаться как компактная карточка под описанием либо влиться в правую парящую колонку — на реализацию).

### 3.6 LICENSE.md и доп. документы проекта

Два раздельных, но связанных решения — расширение уже принятой конвенции репозитория (`project.git.md` §10.2), не новая подсистема:

1. **Лицензия — первоклассный объект.** Автор выбирает лицензию из короткого курируемого списка (аналог GitHub license picker: CC0, CC-BY, CC-BY-SA, «Все права защищены» как честный дефолт для авторов, не думавших о лицензии) в форме редактирования проекта → бэкенд коммитит `LICENSE.md` в корень репо по шаблону (тот же git-модуль `apps/api/src/git/repo.ts`, что уже коммитит README). На странице — компактная пилюля «Лицензия: <название>» рядом с автором/meta-карточкой (не отдельный тяжёлый блок), тап открывает полный текст (переиспользуем существующий markdown-рендер). Новая роль в реестре Data (`project.git.md` §10.2): `license` → путь `LICENSE.md` (корень, вне craft-папок) → git.
2. **Доп. документы — общий бакет, не файловый менеджер.** Новая роль `doc_file` (generic supplementary doc: markdown/txt/pdf) → путь `docs/` (уже существующая папка репо, сегодня там только `description_image`) → отображается в блоке «Файлы проекта» новой группой «Документы» (та же логика §3.1/§3.2 `projects.md` — группа появляется, только когда есть хотя бы один файл роли `doc_file`). Это закрывает буквальный запрос «положить и другие `.md`-файлы, как на гите» без превращения страницы в файловый браузер репозитория.

### 3.7 OG/share-превью ссылки (найдено этим ресёрчем, не в исходном запросе — включаю т.к. дёшево и достраивает уже принятую кнопку «Поделиться»)

## 5. Критерии приёмки (приёмка эпика — CTO)

1. Вьюер имеет рабочий полноэкранный режим (десктоп + мобильный CSS-фолбэк), явный выход (✕/Esc), без регресса постер→GLB флоу.
2. Новые и бэкафилленные модели по умолчанию ориентированы устойчивой плоской гранью вниз и в GLB-вьюере, и на webp-постере; «Сброс вида» возвращает именно к этой ориентации, не к захардкоженному углу.
3. Страница модели держит видимый безопасный отступ вьюера/правой колонки от шапки сайта — подтверждено скринами `vmatrix` на 3 брейкпоинтах.
4. Вкладка «Статистика» владельца показывает реальные просмотры/скачивания/голоса/комментарии/makes — больше не EmptyState-заглушка.
5. Публичный блок «Напечатали» показывает полный список станков с числом печатей на каждом (не только топ-1 комбо).
6. Автор может прикрепить лицензию из курируемого списка (видна пилюлькой, лежит `LICENSE.md` в корне репо, открывается/скачивается) и произвольные доп.-документы (роль `doc_file`, группа «Документы» в блоке файлов).
7. Дерево файлов / README / история коммитов рендерятся на странице из реальных git-эндпоинтов (`/tree` `/readme` `/history`) — разрыв MF-522 закрыт.
8. Шаринг ссылки на проект даёт непустое превью (заголовок/описание/фото) минимум в Telegram — проверено вручную.
9. «Отправить в печать» остаётся ровно disabled-заглушкой, как решено раньше — эпик её не трогает.
10. Инструкция по сборке не входит в приёмку этого эпика (сознательно вне рамок, §2).

## 6. Открытые вопросы

1. **Точный алгоритм автоориентации** (`trimesh.compute_stable_poses` vs свой convex-hull эвристик) — решает Mesh на спайке стейджа 1, не блокирует остальные зоны.
2. **Список лицензий** в picker'е — предлагает Design на стейдже 1 (дефолт-рекомендация: CC0 / CC-BY / CC-BY-SA / «Все права защищены»), не блокирует.
3. **Механизм OG head-инъекции** (nginx include vs мини-мидлварь в apps/api) — решают Back+Ops на стейдже 2, не блокирует Front.
4. **Срок эпика.** Провизорный дедлайн — **2026-07-24** (2 недели, обоснование: большая часть архитектуры уже построена, это достройка+полировка, не редизайн с нуля). Финал собирает Lead из оценок стейджей; молчание оператора — согласие, возражения — правим.
