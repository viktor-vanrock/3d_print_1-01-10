## Зачем этот эпик

Оператор (2026-07-11) директивно внёс в v1 то, что роадмап раньше исключал → возникло расхождение
источника истины и профильных эпиков, из-за которого девайс/слайс-работа стопорилась. Эпик снимает
расхождение и официально фиксирует состав как **часть v1**.

## Решение по 4 пунктам оператора (кратко; полностью — в MF-1075)

1. **Облачный слайсинг — MVP в v1** (было v2). `apps/mesh`-воркер: очередь слайсинга (CPU вне HTTP)
   + таблица `slice_cache` (`slice_key = hash(model_hash, profile_hash, config_fingerprint)` → g-code
   в S3 + подпись). Кэш **только per-account**, БЕЗ глобального дедупа/P2P (v3+).
2. **Локальные принтеры — v1, подтверждено.** `managed-local`: браузер→Moonraker напрямую по LAN
   (сервер IP не трогает, anti-SSRF). Moonraker-резолвер — приоритет №1 перед Bambu/Prusa/OctoPrint.
3. **Свой агент/веб (замена Fluidd) — v1, пилот немедленно.** Спека `printer.support.md`. 🔴 OS-образы
   собирает ОПЕРАТОР вручную, репо образов — отдельные (не монорепо). Пилот Ender-3 V3 (KE) +
   FLSun V400, цель 13–14.07.2026.
4. **Бэк-платформа — аддитивно поверх существующих таблиц** (не плодим сущности):
   - `user_api_keys` — обобщение `printer_connections.api_key_enc` (scope slicing/printer/public_api,
     ротация, rate-limit); одна модель ключей на всё.
   - Привязка принтер↔юзер — уже есть (`user_printers`, `device_shares` роли owner/operator/viewer/
     guest), не меняем.
   - Слепок принтера — `config_fingerprint` (аддитивно): agent-тип — агент читает Klipper-конфиг;
     managed/connector — из БД + декларация юзера «сток/модифицирован» (уровень «заявлено», не
     «проверено» — честно фиксируем).
   - Хранение нарезанных столов = `slice_cache` (g-code в S3, индекс в Postgres).
   - P2P/торрент — **НЕ в v1**, v3+ (`data.fragmentation.md §8`); v1 закладывает фундамент
     (fingerprint + подписи + slice_key), чтобы P2P встал позже без переделки схемы.

## Что НЕ входит (явно)
Глобальный публичный слайс-кэш и P2P-обмен (v3+); полная верификация fingerprint без агента
(остаётся «заявлено»); Bambu-MQTT/PrusaLink/managed-cloud (v2); организации/фермы/ratio (v2/v3);
тяжёлый AI и деньги (вне v1). Data-plane работает отдельным NestJS relay process; load,
event-loop delay, memory, backpressure и recovery остаются обязательными release gates.

## Активные workstream'ы (дети MF-1075 — единственная декомпозиция)

| Карточка | Зона | Суть | Статус-якорь |
|---|---|---|---|
| Data | Data | схема `slice_cache` + `user_api_keys` + `config_fingerprint` (аддитивные миграции) | stage 1, разблокирует остальное |
| Fullstack/Back | Back+Mesh | mesh-воркер очереди слайсинга + slice-кэш; relay/agent enroll | зависит от Data-схемы |
| Front/Design | Front+Design | UI локальных принтеров + статус пилота прошивки | параллельно |

Пилот прошивки (13–14.07) — отдельный stage 1, не блокирует остальное. Все стыки — через
`packages/contracts` (`service.map.md §3`).

## Definition of Done (закрывает CTO)
`slice_cache`/`user_api_keys`/`config_fingerprint` в схеме на dev; облачный слайсинг выдаёт плейт под
связку и сохраняет per-account; managed-local показывает живой Klipper по LAN; enroll+агент+визуал
на одной пилот-модели (двусторонняя связь); публичный API управляет по ключу; P2P-поля заложены.
Роадмап и service.map отражают девайс-контур/слайсинг как v1.
