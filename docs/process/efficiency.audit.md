# Аудит эффективности флота — методика и снапшот

Источник данных — Multica Postgres (dev-vm, `multica` db). Все запросы читают
`agent_task_queue` (жизненный цикл задачи), `task_usage` (токены по
provider/model), `issue`/`project` (карточка → направление), `activity_log`,
`comment`, `autopilot_run`. Раз в аудит — окно последних N часов
(`created_at >= now() - interval 'N hours'`).

## 3. Ключевые метрики и формулы

```
-- A. Статусы задач и throughput (task_ledger)
SELECT t.id, a.name agent_name, ar.provider, a.model, t.status,
  (t.autopilot_run_id IS NOT NULL) via_autopilot,
  (t.retry_of_task_id IS NOT NULL) is_retry,
  t.originator_source, t.trigger_summary, t.failure_reason,
  t.created_at, t.started_at, t.completed_at,
  i.id issue_id, i.title, i.status issue_status, i.priority,
  p.title project_title,
  u.input_tokens, u.output_tokens, u.cache_read_tokens, u.cache_write_tokens
FROM agent_task_queue t
JOIN agent a ON a.id=t.agent_id JOIN agent_runtime ar ON ar.id=a.runtime_id
LEFT JOIN issue i ON i.id=t.issue_id LEFT JOIN project p ON p.id=i.project_id
LEFT JOIN (SELECT task_id, SUM(input_tokens) input_tokens, SUM(output_tokens) output_tokens,
       SUM(cache_read_tokens) cache_read_tokens, SUM(cache_write_tokens) cache_write_tokens
     FROM task_usage GROUP BY task_id) u ON u.task_id=t.id
WHERE t.created_at >= now() - interval '{N} hours';

-- B. Усвоение по provider/model/agent/project/status (usage_by_agent) —
--    ГРУППИРОВКА ПО task_usage.created_at (не task.created_at!) — так cost
--    попадает в окно, когда он реально «сжигается», а не когда задача
--    была создана.
SELECT u.provider, u.model, a.name agent_name, p.title project_title,
  t.status task_status, (t.autopilot_run_id IS NOT NULL) via_autopilot,
  SUM(u.input_tokens) input_tokens, SUM(u.output_tokens) output_tokens,
  SUM(u.cache_read_tokens) cache_read_tokens, SUM(u.cache_write_tokens) cache_write_tokens,
  COUNT(DISTINCT u.task_id) n_tasks
FROM task_usage u JOIN agent_task_queue t ON t.id=u.task_id
JOIN agent a ON a.id=t.agent_id
LEFT JOIN issue i ON i.id=t.issue_id LEFT JOIN project p ON p.id=i.project_id
WHERE u.created_at >= now() - interval '{N} hours'
GROUP BY 1,2,3,4,5,6;
```

**Формулы производных метрик:**

- `% ресурсов на направление X` = `Σ(input+output X) / Σ(input+output всего)` — прямо из `project_title`, не требует ролевой таксономии.
- `% бюрократии` = `Σ(input+output, agent∈bureaucracy) / Σ(input+output всего)`.
- `Мусор (сожжённые токены без результата)` = задачи со `status IN (failed,cancelled)` **и** `input_tokens+output_tokens > 500` (порог отсекает queue-churn — см. ниже). Без порога попадают сотни queue-cancel с нулевым потреблением, которые не тратили ресурс.
- `Queue-churn (снято до старта)` = `status='cancelled' AND started_at IS NULL` — НЕ путать с «мусором»: это переброшенные/переиграные mention-директивы (новый триггер на ту же (issue,agent) пару отменяет старую очередь по `idx_one_pending_task_per_issue_agent`), реального токена не стоит, но стоит **авторства комментария**, который его создал. Если >30% задач в окне — это сигнал, что каденс указаний опережает пропускную способность очереди per-issue, а не что агенты ленятся.
- `Housekeeping churn` = `(status_changed+due_date_changed+assignee_changed+title_changed+description_updated+priority_changed события за окно) / task_completed за окно` — событий процессной возни на 1 реально закрытую задачу.
- `Продуктовый выход` = коммиты `git log origin/dev --since --until` за то же окно, разбитые по conventional-commit префиксу: `fix|feat` = продукт, `docs(process|quota|board)` = мета/оркестрация, остальное — по месту. Явно считать отдельно от `Σ(feature-bucket tokens)`, чтобы не путать «потрачено на фичи» с «выпущено фич».
- `Реальный $ / сутки` = `Σ($ opencode за окно) * (24/N)`.
- `Теневая $ Claude / сутки` = аналогично, для сравнения относительного веса, не бюджета.

## 5. Что мониторить дальше (кандидаты в трекер)

1. `% bureaucracy` по токенам — целевой коридор, алярм если >40% вне
   ночей-перестроек.
2. `n_tasks(Board Clerk)+n_tasks(Duty Officer)` за час — алярм на частоту,
   не на длину ответа (симптом уже пофикшен диетой, причина — нет).
3. `cancelled_before_start / total` — не алярмить сам факт (churn — это
   ОК), алярмить если >50% ИЛИ если один и тот же (issue,agent) отменяется
   3+ раза подряд (реальный признак мечущихся указаний).
4. `fix+feat commits / (bureaucracy+leadership tokens)` — отношение
   продукта к мета-весу; отслеживать по дням, не по 4-часовым окнам (шум
   высокий на коротком окне).

## 6. Квота как ресурс: калибровка «токены ↔ % лимита» (снапшот 2026-07-17)

Операторский запрос: перевести «сколько токенов потратила задача/направление»
в «сколько % 5-часового/недельного лимита провайдера это на самом деле
съело» — то, что раньше было чёрным ящиком (только текущий `%` в Главном,
без единиц измерения токенов). Метод — эмпирическая калибровка, не
теоретический расчёт: провайдеры не публикуют «токенов на 1% лимита»,
поэтому коэффициент выводится из совместного ряда `~/.quota/history.jsonl`
(`{ts, provider, u5, u7}`, тик ~15 мин) и `task_usage` (токены по provider
за то же время).

**Метод:** для последовательных сэмплов `(i, i+1)` одного провайдера —
`Δu = u[i+1] - u[i]`, `Δt = ts[i+1] - ts[i]`. Пара отбрасывается при `Δu≤0`
(сброс/нет изменения) или `Δt>2400с` (провал гварда). Для годных пар —
`ratio = Σtokens(provider, ts[i]..ts[i+1]) / (Δu×100)` = токенов на 1 п.п.
Плюс «макро»-сверка: тот же расчёт на первом↔последнем сэмпле всего файла
(длинный `Δu`, меньше шума тика/лага записи БД).

**⚠️ Главная оговорка (не игнорировать при использовании чисел ниже):**
история на дату расчёта — **1.04 суток** (98 сэмплов×3 провайдера,
2026-07-16 17:35 → 2026-07-17 18:31 UTC). Недельный (`u7`) коэффициент —
экстраполяция на <15% недельного цикла, пересчитать через 7 суток истории.

**Результаты (2026-07-17):**

| Провайдер | ток/1пп 5ч | ток/1пп недели (point) | ток/1пп недели (macro) | Уверенность |
|---|---|---|---|---|
| Claude | ~33 454 (mean, n=31, stddev 69 634; медиана 0 — см. ниже) | ~60 505 (n=11, шумно) | **~219 248** (n=1, самый длинный Δ) | средняя |
| Codex | **не вычисляется** | n=2, недостаточно (порог 5) | ~173 286 (n=1) | низкая |
| Grok | нет usage-строк вообще | — | — | некалибруем |

**Находка не про математику, а про инфраструктуру:** у Codex `u5` (5ч)
зафиксирован на `0.0` все 98 сэмплов подряд за 24.94ч, при этом за это же
окно потрачено ~16.1M токенов Codex — не шум малой выборки, а **нулевая
дисперсия при большом трафике**. Подтверждение — `codex.json`:
`"resets_at_u5": null` (у Claude есть значение). **quota-guard физически не
инструментирует 5ч-окно Codex** — это дыра в самом гварде, не в данной
калибровке; чинить нужно там, не здесь.

**Медиана Claude-5ч = 0 — тоже методологическая находка, не баг:** 20 из 31
годных интервалов имеют `tokens=0` при `Δu5>0` — квота тикает, а
usage-строка ещё не закоммичена в `task_usage` (лаг записи vs лаг
счётчика). На 11 интервалах с ненулевым расходом: mean 94 279 / медиана
67 678, разброс ×145 (1 982…288 345) — калибровка на 5ч-окне грязная даже
без нулей, использовать как порядок величины, не точное число.

**Перевод в $:** раз ratio — это токены (input+output вместе, без разбивки
на направление), перевод в теневые $ — по прайсу §2 отдельно на реальном
input:output-сплите конкретной задачи/агента: `$ ≈ tok_in/1e6×price_in +
tok_out/1e6×price_out`. Общего блендового $-числа здесь намеренно не даю —
конкретный сплит не измерялся в этом прогоне (см. принцип §2: не выдумываем
цифру без данных).

направлений (`project.status NOT IN ('completed','cancelled')`) — лид через
