# HYPERPC — локальные LLM для поисковых агентов

Отдельная (не наша VDS) машина под Windows с 3 GPU, доступна по Tailscale
(`100.74.48.83`) — предоставлена под разработку поисковых агентов флота:
(1) умный поиск по сайту/проектам portal.ru, (2) мониторинг новостей/брендов,
(3) сбор данных по принтерам (документация, календарь релизов), плюс задел на
эмбеддинг постов/портала и классификацию 3D-моделей «по форме» (может пересекаться
с эпиком «AI-интеллект» → «нейропоиск по моделям», «диагностика по фото» на доске —
связь никто явно не подтвердил, не считать фактом).

Все порты — **без авторизации**, это ок только потому что всё закрыто периметром
Tailscale. Не пробрасывать наружу как есть.

### Слот 1 — скорость, контекст, переключаемый reasoning

⚠️ **Первые замеры (~16 ток/с) были нечестными** — сделаны на тривиальных
ответах в 2-4 токена, не показательны для реальной нагрузки. Ниже — честные
цифры админа машины после свопа на Ada, замеренные на 177-300 токенах вывода
(достаточная выборка, чтобы усреднить стартовый latency):

**Итоговая таблица скоростей по всем 4 сервисам (2026-07-20, после свопа GPU):**

| Сервис | Карта | Генерация | Промпт-процессинг |
|---|---|---|---|
| Qwen3.6-35B-A3B (слот 1) | Ada 48GB | ~151 ток/с | ~122 ток/с |
| gemma-4-e4b (слот 2) | 3090 #1 | ~136 ток/с | ~65 ток/с |
| TRELLIS2 low (512px, 8 шагов, ~100k граней) | 3090 #2 | ~40с/модель | — |
| TRELLIS2 medium (1024_cascade, 12 шагов, ~300k граней) | 3090 #2 | ~177с/модель | — |
| Embedding (Qwen3-VL-2B, слот 4) | 3090 #2 | ~7 текстов/с (батчем) | — |

Qwen3.6 на Ada (~151 ток/с) оказался быстрее, чем ожидалось по сравнению с
прежней оценкой (~16 ток/с) — разница объясняется как минимум частично тем, что
до свопа модель на 3090 была «забита под завязку, без запаса VRAM» (см. выше),
что похоже на CPU/host-спиллинг части весов, а не только нечестностью первого
замера. **Контекст на один запрос: 32768** (не 131072!) — сервер поднят с `-c 131072
  -np 4`, то есть общий бюджет контекста поделён на 4 параллельных слота
  (`n_slots=4, n_ctx_slot=32768` в логе загрузки). Нужен полный 128K на один
  запрос — `-np 1` даст это, но без параллельной обработки нескольких клиентов.
  Родной архитектурный потолок модели — 262144 (`n_ctx_train`), то есть при
  желании можно расширить общий пул сверх текущих 131072, не только
  перераспределить его.
- **Reasoning ПЕРЕКЛЮЧАЕТСЯ** (в отличие от прежней gemma-31B) — но только
  правильным полем. Проверено лично, разница критичная:
  - `{"enable_thinking": false}` **плоским полем верхнего уровня — НЕ работает**,
    модель молча продолжает думать (reasoning_content как обычно, поле просто
    игнорируется).
  - `{"chat_template_kwargs": {"enable_thinking": false}}` — **работает**:
    `reasoning_content: null`, ответ мгновенный (4 токена на "столица Франции?"
    вместо obычных сотен).
  Используйте вторую форму. Без неё — закладывайте `max_tokens` с запасом
  (500-1000+), как раньше приходилось для gemma-31B.

### Слот 4 — эмбеддинг + реранкер (свой контракт)

```
POST /embed
  {"inputs": ["текст" | "url_картинки" | {"text": "...", "image": "..."}], "prompt": "опц. инструкция"}
  → {"embeddings": [[...]], "dim": 2048}

POST /rerank
  {"query": "...", "documents": [...], "top_k": 10}
  → {"results": [{"index": N, "score": 0.xx}, ...]}   # отсортировано по score

GET /health → {"status": "ok", "device": "cuda"}
```

Единое пространство эмбеддингов для текста, картинок, документов-как-картинок (без
OCR) и видео — 30+ языков, проверено на русском. `documents`/`query` в `/rerank`
принимают те же три формы, что `inputs` в `/embed`.

**3D-меши (STL/3MF/OBJ/PLY):** отдельной 3D-модели эмбеддинга (Uni3D) не
завели — рендерить несколько ракурсов на своей стороне (`trimesh`, дёшево по CPU) →
слать картинки в `/embed`. Заодно обходит Windows-риск сборки DeepSpeed/custom CUDA.

## Грабли

1. **Не сажать одну модель на несколько GPU разом** — падает `GGML_ASSERT(n_inputs <
   GGML_SCHED_MAX_SPLIT_INPUTS)` (известный баг llama.cpp). Каждый процесс жёстко на
   одной карте (`CUDA_VISIBLE_DEVICES`/`--cuda-device`).
2. Все 4 сервиса — автозапуск через Windows Task Scheduler (`ONLOGON`, автологин),
   переживают перезагрузку. Если после ребута не отвечает — на машине, вручную,
   Task Scheduler → `Run` соответствующей задачи (`LaunchLMStudio`,
   `LaunchSlot2Llama`, `LaunchSlot3ComfyUI`, слот 4 — своё имя).
3. **Если сами качаете что-то новое с HuggingFace на этой машине — сначала `pip
   uninstall hf-xet`** — эта библиотека стабильно вешает загрузку больших файлов в
   этой сети/окружении. Не баг вашего кода, если что-то долго не двигается — известный
   паттерн, характерный и для HF, и для LM Studio на этой сети.
4. LM Studio `POST /api/v1/models/load` с новым `context_length` **создаёт НОВЫЙ
   instance** (суффикс `:2`), не заменяет текущий — обе версии остаются загружены
   одновременно (двойной расход VRAM), пока не выгрузишь явно `POST
   /api/v1/models/unload {"instance_id": "..."}` первую. (Актуально только пока
   какой-то слот на LM Studio — сейчас оба текстовых слота на raw `llama-server`,
   но если что-то снова перенесут на LM Studio, грабля та же.)
5. **ComfyUI кэширует ноды по хэшу входов** — повторная отправка того же
   `/prompt`-payload (тот же seed/картинка) не пересчитывает граф заново, а
   мгновенно отдаёт готовый результат из кэша прошлого прогона. Если бенчмаркаете
   TRELLIS2/любой workflow — **меняйте seed на каждом замере**, иначе получите
   фиктивную цифру вида «0.07с» вместо реальной (админ машины поймал это лично,
   см. таблицу скоростей выше — там уже честные цифры со сменой seed).
6. **Windows Task Scheduler + `Stop-Process -Force` + немедленный `schtasks /Run`
   подряд — гонка состояний.** VRAM/файловый лок от только что убитого процесса
   ещё не успевает освободиться, новый `llama-server` падает МГНОВЕННО и МОЛЧА —
   задача Task Scheduler при этом честно отчитывается кодом `0` (успех), лог не
   создаётся вообще, выглядит как «всё ок», но порт не отвечает. Чинится паузой
   ~15-20с между убийством старого процесса и запуском нового — тогда процесс
   стартует и остаётся жить, статус задачи корректно уходит в
   `SCHED_S_TASK_RUNNING` (как у остальных слотов). Если после ручного рестарта
   какого-то слота порт молчит, а Task Scheduler показывает «выполнено успешно» —
   это оно, не спешить с повторным перезапуском, подождать.

## Как это подключено к флоту (Multica)

Второй, полностью изолированный OpenCode-раннтайм — **не смешан** с существующим
OpenCode-раннтаймом на `worker`, который бьётся в OpenRouter-баланс (см.
[quota.control.md](quota.control.md) § v6.4, тот раннтайм жёг ~95% баланса).

- Linux-юзер `ocsearch` на `worker` (`useradd -m`) — свой `$HOME` даёт естественную
  изоляцию `~/.config/opencode`, `~/.local/share/opencode/auth.json` (0 credentials —
  никакого OpenRouter-ключа), `~/.multica/`. Бинари `opencode`/`multica` общие с
  `plag` (симлинк на общий бинарь), но конфиг резолвится от `$HOME` вызывающего
  юзера, не от пути бинаря.
- `~/.config/opencode/opencode.jsonc` — два custom-провайдера (`@ai-sdk/openai-compatible`),
  оба слота живые, конфиг синхронизирован с переездом слота 1 на порт `1236`/Qwen:
  - `hyperpc-slot1` — `qwen3.6-35b-a3b` (`id` — полный Windows-путь модели, порт
    `1236`), `tool_call: true`, `reasoning: true` (модель ПОДДЕРЖИВАЕТ выключение
    reasoning per-request через `chat_template_kwargs.enable_thinking: false`, но
    сам `reasoning: true` в конфиге — это capability-флаг для OpenCode, не
    переключатель; он просто говорит OpenCode ожидать `reasoning_content` в ответе,
    когда thinking включён), `limit: {context: 32768, output: 8192}` — 32768, не
    131072, потому что это предел НА ОДИН запрос при `-np 4` (см. выше).
  - `hyperpc-slot2` — `gemma-4-e4b`, `tool_call: false`, `id` — полный Windows-путь
    модели, `limit: {context: 65536, output: 4096}`.
  - Дефолт (`"model"` верхнего уровня) пока НЕ переключён на slot1: он надёжнее для
    tool calling, но по умолчанию (thinking on) ощутимо медленнее/дороже по
    токенам и не годится универсальным дефолтом без ведома конкретной задачи.
    Явный выбор providers (`hyperpc-slot1/...` для задач с tool calling/JSON —
    по возможности с `chat_template_kwargs.enable_thinking:false` в теле запроса,
    `hyperpc-slot2/...` для текстовых/長контекстных без инструментов) остаётся за
    тем, кто настраивает конкретного поискового агента — не общий дефолт всего
    раннтайма.
- Второй Multica-демон — **не второй процесс на порту** (единственный control-port
  демона на хост общий, попытка второго процесса падает `address already in use`
  независимо от Linux-юзера/`--daemon-id`), а тот же `multica.real`, запущенный с
  top-level флагом **`--profile ocsearch`** (`multica --profile ocsearch daemon
  start ...`) — изолирует config/daemon-state/control-port под
  `~/.multica/profiles/ocsearch/`. Тот же механизм, что использовался в отменённом
  эксперименте «демоны-лейны» — рабочий, просто операционно неудобный для ОСНОВНОГО
  флота при большом числе демонов; для одного доп. изолированного раннтайма — ровно
  то, что нужно. systemd `multica-daemon-ocsearch.service` на `worker`, `User=ocsearch`.
- `multica login --token` почему-то отвергает валидный PAT даже уже работающего с
  ним демона (не выяснено почему) — обходной путь: скопировать `~/.multica/config.json`
  (или `~/.multica/profiles/<name>/config.json`) напрямую с рабочим токеном.

**Открытый блокер:** у юзера `ocsearch` нет git-credentials на `gitverse.ru` — демон
не может склонировать репо под task-workdir (`could not read Username for
'https://gitverse.ru'`), назначенные карточки зависают до старта. Решение
(переиспользовать существующий credential vs завести отдельный dedicated token) —
за оператором, не принято.

Runtime зарегистрирован в Multica как **«Opencode (worker-ocsearch)»**; тестовый
агент — **«OC Local Test»**. Реальные поисковые агенты (по трём направлениям из
шапки этого файла) — отдельная, ещё не начатая работа поверх этой инфраструктуры.

**Третий, отдельный OpenCode-раннтайм (MF-2045)** живёт на `dev-3mf`
(не `worker`), контейнером, а не Linux-юзером — обслуживает продуктовый
assistant (`apps/giga`/`apps/api`), не поисковых агентов флота. См.
[opencode.assistant.runtime.md](../infra/opencode.assistant.runtime.md) — не
путать три раннтайма между собой при следующих правках этого файла.

## Периметр и наблюдаемость — живой аудит (MF-2002, Ops, 2026-07-20)

Проверено живьём с `dev-3mf` (реальный прод-VDS, есть прямой Tailscale-доступ в
тот же tailnet, что и `100.74.48.83`):

- **Публичной экспозиции нет.** `deploy/nginx.3mf.tech.conf` и живые vhost'ы на
  VDS не проксируют ни один из портов HYPERPC (`1236`/`1235`/`8188`/`8189`) —
  `grep` по конфигу и по `/etc/nginx/sites-enabled` пуст. `apps/web/src` и
  `apps/api/src` не содержат ни одного упоминания `100.74.48.83` или этих портов
  — сегодня ни один продуктовый сервис (и тем более браузер) не знает об этом
  адресе вообще, обращаться неоткуда.
- **`apps/search` и `apps/giga` пока не интегрированы с HYPERPC.** `apps/search`
  — только `pyproject.toml`/`readme.md` (скелет, код по картам C1, см. эпик
  `neural.search.md`), `apps/giga` (`config.py` и весь `src/giga`) не содержит
  ни `HYPERPC`, ни `100.74.48.83`, ни портов слотов. Проверять/закрывать env
  этих приложений под HYPERPC пока буквально нечего — конфигурации, которую
  можно было бы утечь или неверно захардкодить, не существует. Единственный
  сегодняшний потребитель — изолированный OpenCode-раннтайм юзера `ocsearch` на
  `worker` (см. выше, «Как это подключено к флоту») — отдельная, не
  product-код-путь машина/лейн, недоступная и неаудируемая из этой сессии (нет
  SSH/учётки на `worker` в рамках этой задачи).
- **Расхождение `:1234`/`:1236` уже закрыто, не блокер.** Живая проверка:
  `curl` на `1236` → `200` (текущий raw `llama-server`, слот 1), `curl` на
  `1234` → `connection refused` (старый LM Studio-инстанс, вытеснен, порт
  закрыт). История и причина миграции задокументированы в шапке этого файла
  (коммит `0492e5f5`, тем же днём). Дополнительно проверены `1235`/`8188`/`8189`
  — все 4 слота живые, `200`.
- **UFW на `dev-3mf` подтверждён активным** (`default deny incoming` + разрешены
  только `22/80/443` и весь трафик с `tailscale0`) — соответствует состоянию,
  зафиксированному после MF-855 в `docs/infra/readme.md`. Это ограничивает, кто
  может достучаться ДО `dev-3mf`, но не имеет отношения к тому, кто в tailnet
  может достучаться до самого HYPERPC — это отдельный периметр (см. блокер ниже).
- **🚧 Блокер — Tailscale ACL identity-ограничение НЕ проверено и не может быть
  проверено/применено из этой сессии.** У установленной здесь версии `tailscale`
  (1.98.8) нет CLI-подкоманды `acl`; на VDS не найдено ни API-ключа, ни
  OAuth-client credential для Tailscale API (`~/.config/tailscale`, домашний
  каталог, `/etc/default/tailscaled` — проверено, ничего нет). Политика ACL
  тайлнета редактируется только через веб-консоль `login.tailscale.com`
  (PlagID/оператор), недоступную агенту. Живьём подтверждено обратное —
  `dev-3mf` СЕЙЧАС достаёт до всех 4 портов HYPERPC без ограничений; остаётся
  открытым, действует ли на тайлнете какая-то явная ACL, сужающая круг identities
  до конкретных нод (`dev-3mf`, `worker`), или доступ фактически open-by-default
  для всех участников тайлнета (ноутбук, телефон и т.д.) — то же самое
  верно и в обратную сторону: не проверено, кто ещё в tailnet технически может
  достучаться до `100.74.48.83`. **Адресат: оператор (`@plag`)** — только у него
  есть доступ к консоли `login.tailscale.com`; нужно явное подтверждение (или
  создание) ACL-правила, ограничивающего доступ к тегу/IP HYPERPC конкретными
  node identities, и разово прислать результат сюда или в `docs/infra/readme.md`.
- **🚧 Блокер — Windows firewall на HYPERPC не проверен по тем же причинам, что
  уже задокументированы выше** («нет SSH/файлового доступа к самой машине»,
  только HTTP через Tailscale) — не новая находка, статус не изменился с
  предыдущей версии документа. **Адресат: админ машины HYPERPC** (см. «Внешний
  handoff от админа машины» выше) — верификация firewall-правил и сведение с
  `hyperpc-ai/HANDOFF.md` возможны только с его стороны.
- **Health probe / timeout / circuit breaker / retry-storm policy — пока
  проектный вопрос, не Ops-хардненинг.** Готового клиента к HYPERPC из
  продуктового кода нет (см. пункт про `apps/search`/`apps/giga` выше) — писать
  алертинг/circuit breaker для несуществующего вызывающего кода означало бы
  спекулятивный код без потребителя. Референс-паттерн уже есть в репозитории и
  им стоит руководствоваться, когда интеграция появится: `apps/giga/src/giga/
  gigachat_client.py` — явный `timeout=30s`, `max_retries=3`,
  `retry_backoff_factor=0.5s`, retry только на `429/500/502/503/504` (не на
  таймаут соединения и не на `200` с невалидным телом — эти классы нужно
  различать отдельно в алертинге). Со стороны HYPERPC уже задокументирован
  сценарий retry storm — Task Scheduler race (граблях №6 выше): `Stop-Process
  -Force` + мгновенный `schtasks /Run` роняет процесс молча с кодом `0`,
  чинится паузой 15-20с — это операционная мера на стороне админа машины, а не
  что-то, что закрывается кодом клиента.
