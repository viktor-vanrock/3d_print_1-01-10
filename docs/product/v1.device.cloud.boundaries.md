# Матрица границ v1/v2/v3 — девайс-контур и слайсинг

Единая сводная таблица allowed/forbidden по девайс-контуру и слайсингу, чтобы не заводить
параллельные (и расходящиеся) формулировки версии в разных доках. Эта таблица не источник
решения — она **сверяет** уже принятые решения; при конфликте с исходником ниже правит
исходник, а эта таблица обновляется следом.

Источники истины (не дублируем содержание, только сводим):
- Директива и даты — [`roadmap.md` § «Пересмотр скоупа v1 — 2026-07-11»](roadmap.md#пересмотр-скоупа-v1--директива-оператора-2026-07-11-cto)
  и решение [MF-1075](mention://issue/7c29c98a-04f5-43c0-8f6d-adbad265dfa2).
- Операционный канон — [`v1.command.md`](v1.command.md).
- Полная спека решения — [`../epics/v1.device.cloud.md`](../epics/v1.device.cloud.md).
- Серверный слой/протоколы — [`../architecture/printer.server.md` § 4 «Этапы»](../architecture/printer.server.md#4-этапы-ложатся-на-версии).
- Фрагментация/дедуп/P2P — [`../architecture/data.fragmentation.md` § 8-9](../architecture/data.fragmentation.md#8-этапы-ложатся-на-версии).
- Уровни поддержки принтеров/custom-агент — [`../epics/printer.support.md`](../epics/printer.support.md).

## Правило поддержания

Любая карточка, меняющая версию пункта этой таблицы, обязана сначала обновить исходник
(`roadmap.md` / `v1.device.cloud.md` / профильный architecture-док), затем эту таблицу —
в одном delivery-потоке. Docs при аудите сверяет только соответствие, не придумывает версию
самостоятельно.
