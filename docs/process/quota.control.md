> Действует с 2026-07-16. Подписочные системы (Claude, Codex, Grok) имеют

> контур. Специализация систем — по решению оператора (см. таблицу).

## Blackout-сценарий (все подписки выжжены, деньги есть на OpenCode)

При PAUSED провайдера guard дополнительно **отводит его автопилоты**:
инцидентные (автодеплой упал, CI упал, site keeper) → Duty Officer;
доска (бесхозные, паспорт, сроки, не движется) → Board Clerk;
остальные active → пауза. На подъёме всё возвращается из снимка.
Итог: новые таски в погашенных агентов НЕ кидаются, прод не остаётся без рук,
доска не зарастает. При blackout 3/3 Sentinel эскалирует напрямую оператору
(tg-say), после отката первой системы — сводка CTO.

## Ярусы интеллекта (умных не трогаем по мелочам)

- **opus (CTO)** — только эпик-закрытия, архитектура, конфликты лидов, портфель.
  mct=1. Административное CTO обязан делегировать вниз, не решая сам.
- **sonnet high** — лиды проектов: решения в своей зоне, closer in_review.
- **sonnet medium** — исполнители бэка и HQ-аналитика (Forecast, Board Curator,
  AgentOps, Platform Guardian, Growth, Docs).
- **haiku (Project)** — вся механика доски: паспорт, бесхозные, сроки-пинги,
  «карточка не движется». Рутинные автопилоты доски и GitVerse-вотчеры PR
  назначены на haiku/дешёвые (Project, Git), НЕ на opus/лидов.
- Правило маршрутизации: карточка/автопилот сначала целится в САМЫЙ ДЕШЁВЫЙ
  ярус, который справится; эскалация вверх — только с причиной.

## Дозирование и умный роутер (v5)

Штатно: исполнители max_concurrent_tasks=1, лиды=2. quota-guard — бесплатный
скрипт (curl+SQL+CLI, ноль LLM-токенов), интервал СЛУЧАЙНЫЙ 10–25 минут
(RandomizedDelaySec). Каждый прогон ведёт:

- **history.jsonl** — u5/u7 по провайдерам → скорость горения;
- **task-stats.json** (утилита `task-stats`) — трекер задач из БД Multica:
  по агенту/провайдеру n задач, p50/p80 длительности, средние токены на задачу.

**Резерв оператора 20–30%: жёсткий стоп на 75%** использования лимита.

- **Край** (>=60% ИЛИ формула: минут до 75% <= p80-длительность задачи
  провайдера + 10 мин): guard будит Sentinel ОДИН раз — карточка «роутер: реши
  что доделываем» (usage, скорость, p80, ETA сброса, in_progress). Sentinel
  по-агентно: успеет доделать — работает; нет — mct=0 + «сверни, коммить как
  есть». Смысл формулы: роутер срабатывает ровно за одну «среднюю задачу» до
  стопа — агенты успевают финишировать штатно.
- **Жёсткий стоп 75%** — guard гасит всех + отводит автопилоты (Blackout).
- **Подъём <65%** — восстановление снимка + Sentinel возобновляет свёрнутое.
- Остыли <50% без паузы — тихий сброс флага роутера (0 токенов).

## Планирование по времени на доске (velocity-модель, MF-1719)

Источники: `~/.quota/task-stats.json` (n / p50 / p80-длительность рана / средние
токены — по агенту и по провайдеру, обновляется guard-ом каждые 10–25 мин,
0 LLM-токенов) и сама доска (`issue list`, `issue children`). Оператор модели —
Forecast; формулы ниже — контракт, по которому Forecast считает еженедельную
витрину и любой другой агент может пересчитать вручную.

### 1. Пропускная способность провайдера (fleet-wide, задач/сутки)

Агенты одного провайдера делят ОДНУ подписку и общий кап параллельности
(см. «Параллельность по провайдерам» выше: Claude≈2, Codex≈1, Grok≈1,
OpenCode≈1 одновременных задач по всему флоту, не на агента). Поэтому
пропускная способность считается на уровне провайдера, а не агента:

```
cap_provider(P50) = concurrency(provider) × uptime_fraction × 1440 / p50(provider)
cap_provider(P80) = concurrency(provider) × uptime_fraction × 1440 / p80(provider)
```

`uptime_fraction = 0.75` — резерв оператора 20–30% и жёсткий стоп на 75%
(см. «Дозирование и умный роутер» выше) означают, что в среднем провайдер
доступен для новых задач ~75% календарного времени; `p50`/`p80(provider)` —
из `task-stats.json → providers.<name>`. Пример на срезе 2026-07-17:

| Провайдер | p50, мин | p80, мин | concurrency | cap P50, задач/сутки | cap P80, задач/сутки |
|---|---|---|---|---|---|
| Claude | 3.2 | 8.8 | 2 | 675 | 245 |
| Codex | 3.3 | 7.0 | 1 | 327 | 154 |
| Grok | 0.9 | 1.0 | 1 | 1200 | 1080 |
| OpenCode | 1.0 | 2.1 | 1 | 1080 | 514 |

Grok/OpenCode выборки (n=2, n=99, малая история активных продуктовых
агентов) — доверять числу меньше, чем Claude/Codex; отмечать в витрине как
«мало истории», не молчать.

### 2. Velocity агента

Внутри провайдера общий кап делится между агентами пропорционально их
исторической доле задач (`n` агента / `n` всех агентов этого провайдера в
`task-stats.json`) — это proxy того, какую долю общего слота агент реально
получает при текущем миксе работы:

```
share(agent)       = n(agent) / Σ n(agent′) по всем agent′ того же провайдера
velocity_P50(agent) = cap_provider(P50) × share(agent)
velocity_P80(agent) = cap_provider(P80) × share(agent)
```

Если агента нет в `task-stats.agents` (мало истории, < ~3 задач) — velocity
не считается, помечать «нет данных», не подставлять 0 и не выдумывать число.

### 3. Прогноз эпика (P50/P80 дата завершения)

Для каждого агента, у которого есть открытые (не `done`/`cancelled`)
delivery-карты внутри эпика:

```
дней_P50(agent) = очередь(agent, эпик) / velocity_P50(agent)
дней_P80(agent) = очередь(agent, эпик) / velocity_P80(agent)
```

Дата эпика = максимум по всем вовлечённым агентам (эпик закрыт, когда
закрыт самый медленный участник):

```
дата_P50(эпик) = сегодня + max(дней_P50(agent))
дата_P80(эпик) = сегодня + max(дней_P80(agent))
```

Сверка: `дата_P80(эпик) > due_date` → флаг «под риском» в витрине.

**Наблюдение среза 2026-07-17:** при текущем правиле «волна — 2–4 карточки»
(`board.projects.md` п.7) открытая очередь почти всегда мала (1–6 карт на
агента на эпик), поэтому per-эпик P50/P80 почти всегда «сегодня» — velocity
provider-уровня с запасом перекрывает такую очередь. Реальный сигнал риска
не на уровне эпика, а на уровне агента по ВСЕЙ доске сразу — см. §4.

### 4. Дефицит ресурса (агрегат по агенту, не по эпику)

Очередь агента — это открытые карты (`todo`+`in_progress`+`blocked`, БЕЗ
`in_review` — это отдельная очередь ревьюера, не исполнителя) по ВСЕЙ доске,
не только внутри одного эпика: агент выполняет их из одного и того же
квотного пула. Ближайший `due_date` среди этих карт — ориентир срочности:

```
дефицит(agent) = очередь(agent) − velocity_P50(agent) × дни_до_ближайшего_due(agent)
```

`дефицит > 0` → агенту физически не хватает пропускной способности до
ближайшего срока при текущей нагрузке → сигнал CTO о перераспределении
(снять менее ценное с агента или сдвинуть срок, НЕ добавлять карточки).
Срез 2026-07-17 (демонстрация, полные числа — в комментарии MF-1719):
`FLSun` (очередь 3, due завтра, дефицит +2.0) и `Bridge` (очередь 14, due
завтра, дефицит +1.7) — под риском; у большинства агентов дефицита нет,
запас кратный (Back, Fullstack, Data, Docs — сотни задач/сутки capacity
против очереди в единицы-десятки).

### 5. Витрина

Еженедельный коммент в эпик (или сводный в «Оперирование») формата:

```
Прогноз по velocity-модели (task-stats на <дата>):
- P50 <дата>, P80 <дата> (due <дата>) [флаг ⚠️ если P80 > due]
- Дефицит: <агент> (очередь N, capacity до due M, дефицит +K) — сигнал CTO
- Провайдеры с малой историей (Grok/OpenCode) — доверять с оговоркой
```

Считает Forecast по запросу или еженедельно; формулы выше — стабильный
контракт, конкретные числа устаревают в течение дней (task-stats пересчитывается
каждые 10–25 мин) — не кэшировать значения velocity дольше одной витрины.

## Механика контроля лимитов

**Слой 1 — quota-guard (детерминированный).** `/usr/local/bin/quota-guard` на
dev, systemd-таймер каждые 10 минут:

- Пробы: codex — реальный usage API подписки (u5/u7 из auth-токена);
  claude/grok — v1 реактивно (rate-limit ошибки в логе демона ⇒ u5=1.0 с
  кулдауном 60 мин; точные пробы — TODO-карточка Ops).
- Состояние: `~/.quota/<provider>.json`, снимок `~/.quota/mct-snapshot.json`.
- **Гашение при ≥90%** (зазор 10%): всем агентам провайдера
  `max_concurrent_tasks=0` (прежние значения — в снимок).
- **Подъём при <85%**: восстановление mct из снимка.
- На каждой транзиции: `tg-say` + карточка в «Оперирование» на Quota Sentinel.

**Слой 2 — Quota Sentinel (агентный, OpenCode gemini-3.5-flash).** Будится
карточкой от гварда, делает то, что скриптом не сделать:

- комментирует in_progress карты погашенного провайдера («система на лимите,
  продолжит ~HH:MM»);
- urgent-карты критического пути предлагает лиду проекта перекинуть на другой
  раннтайм;
- при возобновлении перезапускает брошенные задачи и снимает пометки;
- эскалация: 2+ систем выжжены одновременно → urgent-карточка CTO.


## Параллельность по провайдерам (3 демона, мягкие капы; 2026-07-16)

Целевые капы оператора: **Claude≈2, Codex≈1, Grok≈1, OpenCode≈1** одновременных задач.
У платформы нет per-provider капа (только кап демона на машину + mct агента), поэтому
после эксперимента с демонами-лейнами (отменён оператором: слишком много демонов)
принята схема «3 демона на 3 машины, провайдеры сгруппированы по машинам»:

| Демон | cap | Раннтаймы с агентами | Ожидаемый профиль |
|---|---|---|---|
| dev | **3** | Claude (dev) ×32, Codex (dev) ×10 | ~2 Claude + ~1 Codex |
| worker | **2** | Grok (worker) ×7, Opencode (worker) ×3, Claude (worker) ×1 (Release) | ~1 Grok + ~1 OO |
| Mac | **1** | Grok (Mac) ×1 (Polygon) | полигон, редкие |

Капы МЯГКИЕ: внутри машины провайдеры делят слоты (теоретически dev может занять
3 Claude или 2 Codex). Жёсткость не требуется: mct=1 у исполнителей, quota-guard
стопит провайдера по бюджету, а худший случай короткоживущий. Строгий вариант
(демоны-лейны с MULTICA_DAEMON_ID + --profile) описан в git-истории этого файла —
возвращаться к нему только решением оператора.


## v6: OO — генеральный диспетчер (2026-07-16, директива оператора)

Капы демонов мягкие (dev=4, worker=2, mac=1) — реальное управление у OpenCode-контура
через ДВА рычага: **очередь** и **токены**. quota-guard (бесплатный, тик 10–25 мин)
собирает `~/.quota/fleet-state.json` (running/queued по провайдерам, failed за час,
висящие running >3ч, возраст очереди) и будит платных диспетчеров только по делу:

- **Quota Sentinel** — диспетчер ТОКЕНОВ: целевые средние 2×Claude/1×Codex/1×Grok,
  рычаг mct агентов; будится guard-ом у края лимита (роутер-карточка).
- **Duty Officer** — диспетчер ОЧЕРЕДИ: будится guard-ом при аномалиях (failed>0,
  queued >45 мин, running >3ч, затор >6); перезапуски mention-комментом, перекидка
  нагрузки, эскалации. Кулдаун пробуждения 60 мин.
- **Board Clerk** — паспорта карточек (пассив).

Мандаты вшиты в промпты агентов. Пауза провайдера guard-ом (5h-лимит) — штатный
режим: OO не чинит её, а не даёт очереди копиться у остальных. Приоритет №1
(тек.): дизайн-фиксы — Codex-контур гасится последним.

### Синергия OO ↔ автопилоты (v6.1)

Duty Officer получает работу из ДВУХ источников: события (автопилоты Multica,
webhook) и метрики (quota-guard). Автопилоты на OO: «Доска: карточка не движется»
(канал реанимации тасков), «Доска: ревью-очередь» (пинки лидов-closer-ов),
«Dev: site keeper», «CI: прогон упал», «GitVerse: автодеплой упал» — все на Duty;
«целостность паспорта», «бесхозная карточка», «ревизия сроков» — на Board Clerk.
Guard дополнительно ловит ПРОСТОЙ: 0 running/queued при живых todo → Duty раздаёт
работу mention-комментами (дизайн первым). Инвариант контура: работа не простаивает.

## v6.3: ПРОСТОЙ/НЕДОЗАГРУЗКА считают только todo с активным эпиком (2026-07-19)

Наивный `count(status='todo')` был неточным сигналом: живая доска почти никогда не
пустеет буквально, но это не всегда значит «есть готовая работа». На проверке нашлось
два класса шума, оба реально существовали на доске: (1) todo-сироты под уже
`done`/`cancelled` эпиком — эпик закрыт, а один дочерний пункт забыт в todo;
(2) служебные ops-алерты без продуктового эпика (например «квота: codex ПОГАШЕН») —
карточка сама себе `parent_issue_id=null`, «эпик» только по формальному признаку, а не
по смыслу. Guard будил Duty Officer каждый час (кулдаун `DUTY_COOLDOWN_S`) даже когда
ни одного настоящего эпика с работой не было — оператор поймал это по логу
Telegram-канала (3 срабатывания подряд ночью 2026-07-18→19 при пустом фронте работ).

Фикс — `count_ready_todo()` в `/usr/local/bin/quota-guard`: считает todo-карточки,
чей эпик (верхний предок по `parent_issue_id`, сам себе если предка нет) в статусе
`todo`/`in_progress` и **не из проекта «Оперирование»** (тот же признак, которым
`multica-event-router.py` уже отличал легитимный «у эпика нет родителя» от малформед —
см. v6.2 выше; здесь тот же принцип применён ко второму, независимому потребителю).
Проверено на живых данных 2026-07-19: из 18 todo-карточек наивный счётчик видел все
18, `count_ready_todo()` — 14 (3 сироты + 1 ops-алерт отсеяны). **Если активных эпиков
с готовой работой нет вообще — guard теперь молчит, а не будит диспетчеров впустую.**

Тот же SQL-контракт задействован в `/epic-readiness` (`multica_fleet_exporter.py`,
127.0.0.1:9101) для видимости на дашборде `control.tasks.3mf.tech/fleet` — секция
«Диспетчеры и управление» показывает готовую работу и «сирот» рядом с самими
диспетчерами, чтобы было видно, ПОЧЕМУ guard молчит или будит.

Явный признак эпика на доске — лейбл **`эпик`** (создан 2026-07-19, применяется на все
top-level карточки вне проекта «Оперирование» — конвенция и владелец лейбла описаны в
[board.projects.md § «Паспорт карточки»](board.projects.md)). Источник истины для
guard/exporter остаётся структурным (`parent_issue_id is null` + проект ≠
Оперирование) — лейбл витрина поверх него, не замена: если разойдутся (новый эпик без
лейбла), подсчёт всё равно верный, лейбл просто временно не синхронизирован.

## v6.4: Duty Officer посажен на скамейку — guard и автопилоты его не будят (2026-07-19)

Тем же вечером выяснилось, что v6.3 адресовал ТОЧНОСТЬ сигнала «ПРОСТОЙ», но не его
СТОИМОСТЬ: даже честный сигнал (14 реальных готовых карточек) ловится гвардом ~раз в
час (`DUTY_COOLDOWN_S`), а каждый ответ Duty Officer на него — полноценная агентная
сессия с git-чекаутом и ревью нескольких карточек, а не лёгкая проверка. Проверено на
живых данных: ~21 запуск/24ч, ~1.9М cache-read токенов на запуск, Duty Officer — 95%
всего трафика провайдера `opencode` (8.9М input + 39.6М cache-read против 467К у Quota
Sentinel). Реальный OpenRouter usage_daily: $6.58→$11.04 за неполные 4 часа ≈
**$1.1-1.2/час устойчиво, ~$27/сутки** при таком ритме.

Оператор поставил Duty Officer на паузу (`multica agent update --max-concurrent-tasks
0`) и попросил приглушить и автопилоты, и этот канал — работу ему теперь назначают
точечно, вручную. Сделано:
- Все 5 автопилотов, назначенных на Duty Officer (`Dev: site keeper`, `CI: прогон
  упал → Test`, `GitVerse: автодеплой упал`, `Доска: карточка не движется`, `Доска:
  ревью-очередь`) — `paused` (были поставлены на паузу раньше в тот же день, отдельным
  поручением; на момент v6.4 просто перепроверены — ни один не откатился).
- **`duty_benched()`** в `/usr/local/bin/quota-guard`: перед `wake_duty()` гвард
  читает `agent.max_concurrent_tasks` Duty Officer прямо из БД — если `0`, карточка не
  создаётся вообще (никакого «раздай работу», никакого severe-stall force-bypass —
  полная тишина, как и просил оператор). Источник истины — САМ `mct`, не отдельный
  флаг: как только оператор вручную вернёт `mct` выше нуля, guard тут же возобновит
  будить его без правки кода — самовосстанавливающийся выключатель, не двойной
  источник правды.

Это НЕ redesign частоты/стоимости триггера (оператор явно сказал, что хочет
продумать это сам) — только полная остановка автоматических назначений на
конкретного, сейчас отключённого агента. 40 карточек «диспетчер: аномалии
очереди — разбор HH:MM:SS» остались висеть в `in_review` под ним, никем не
закрываются — отдельная, не тронутая находка.

## v6.2: частота автопилотов доски — «только по особым причинам» (2026-07-17)

Аудит эффективности (`efficiency.audit.md`) показал: 62.4% токенов флота за
4ч ушло в bucket bureaucracy, 88% из них — Duty Officer + Board Clerk (147
автопилот-запусков за 4ч: «целостность паспорта» ×110, «ревизия сроков»
×33). Причина не в длине ответа (диета уже стояла), а в ЧАСТОТЕ: событие
`issue_changed` пересчитывало malformed/overdue на КАЖДУЮ правку поля
(due_date/priority/assignee/title/description), не только на реальный
переход статуса, а условие «нет `parent_issue_id`» ложно бьёт по каждому
эпику (у эпика по определению нет родителя — это не дефект).

Правки в `~/event-router/multica-event-router.py` (директива оператора —
режем автостарты в разы, только по особым причинам):

- **malformed**: убрано `not parent_issue_id`; считается только на
  `issue_created` или реальный переход `old_status != status`, закрытые
  карточки (`done`/`cancelled`) не проверяются; порог батча `threshold`
  15 → **80**.
- **overdue**: тот же гейт на реальный переход, не на любую правку поля у
  уже просроченной карточки; порог 15 → **50**.
- **fire()** теперь реально уважает `endpoints.<name>.status: "paused"` в
  `~/.config/multica-event-router.json` (раньше поле было декоративным) —
  ручной рубильник конкретного автопилота без редеплоя кода.

Ожидаемый эффект: на порядок меньше запусков «целостность паспорта»/
«ревизия сроков» при том же реальном объёме проблем — батч копится дольше
и фильтрует рутинный шум (title/priority/assignee edits), а не только
подряд идущие статус-переходы.

## v6.3: код > бюрократия — крупные задачи, автономия разработчиков (2026-07-17)

Директива оператора по итогам аудита: реальный код должен занимать бОльшую
часть токенов флота, а не координация. Патчи в промптах 22 агентов
(`agent.instructions`, психика не меняется — меняется размер работы):

- **Волна — 2–4 крупных delivery-карточки**, не 4–8: функциональные лиды
  (Data/Fleet/Fullstack/QA/Design) и владельцы паспортов всех 12 проектов.
  Одна карточка = весь связанный блок (несколько эндпоинтов/экранов одного
  контракта), а не один файл/компонент/тест — см. правило 7 в
  `board.projects.md`.
- **Лид после первой волны — НЕ микро-менеджмент.** Роль смещена на сверку
  с docs и переговоры с другими лидами напрямую; reassign/redirect —
  только при реальном блокере, не для рутинной ре-приоритизации. Следующая
  волна — только когда предыдущая реально дошла до dev, не превентивно.
  (Аудит показал: массовая ре-приоритизация «цели на 48ч» одним залпом
  отменила 139 ещё не стартовавших задач за 2 минуты — это churn очереди,
  а не потерянная работа, но сигнал, что каденс редиректов опережал
  пропускную способность.)
- **Разработчикам — автономия.** Back/Front: снято «делай только
  атомарные изменения» + эскапхэтч «попроси Lead разрезать» — теперь
  доводят карточку целиком (несколько эндпоинтов/таблиц/экранов одного
  результата за заход) и режут объём сами; к Lead — только за другим
  владельцем контура или архитектурным конфликтом.

## Правила

1. Рубильник — только `max_concurrent_tasks`, НЕ `systemctl stop` демона:
   демон машины обслуживает несколько провайдеров, стопить его — гасить
   невиновных. (Старый `codex-guard-worker` отключён поэтому.)
2. Sentinel никогда не гасит opencode (сам себя) и не создаёт продуктовых карт.
3. Зазор 10% — чтобы у оператора и срочных ручных задач всегда оставался запас.
4. Бюджет OpenCode мониторит оператор (OpenRouter dashboard); Sentinel обязан
   быть лаконичным — каждое его слово стоит денег.
