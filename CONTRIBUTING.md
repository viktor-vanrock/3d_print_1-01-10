# CONTRIBUTING

Правила разработки в монорепо portal.ru. Архитектура/локальный запуск — `docs/architecture/readme.md`. Версии/релизы — `docs/process/versioning.md`.

> **Работа ведётся на доске задач `tasks.3mf.tech` (Multica).** Любое задание = карточка на доске со статусом. Как — `docs/process/multica.md`; правила и оформление карточек — `docs/process/tasks.multica.md`; памятка входа для агентов — `CLAUDE.md`. См. § «Задания» ниже.

## Ветвление

Модель — **trunk-based на ДВУХ долгоживущих ветках, и только на них** (правило оператора, 2026-07-08). Отдельные ветки под задачу НЕ создаём — ни `feature/`, ни `fix/`, ни `docs/`, ни `agent/*`, ни «ветку под обнову». За пределы `main`/`dev` не выходим.

- **`dev`** — общий рабочий ствол. Сюда коммитят все (люди и агенты). Пуш в `dev` автоматически деплоится на **dev.3mf.tech** (systemd-таймер `portal.deploy-dev` поллит `origin/dev` раз в минуту) — живой стенд для проверки. `dev` держим всегда зелёным/деплоящимся: сломал — чинишь forward сразу, не «прячешься» в отдельную ветку (её нет).
- **`main`** — production trunk, деплоится на **3mf.tech** (polling каждую минуту, рестарт `portal.api` при изменениях в `apps/api/`). В `main` попадает ТОЛЬКО: (1) **промоушеном `dev → main`** (fast-forward) после проверки фичи живьём на dev.3mf.tech — право у Lead и директоров; (2) авто-коммитами CI (`chore(release): …` от `release.yaml`). Прямой push произвольной работы, ручные правки, ветки-в-обход — запрещены.

**Цикл работы:**

```
git config user.name "<Роль>"                             # self-stamp (демон ставит всем общий lead)
# НЕ переключайся на локальную ветку dev — работай на своей ветке воркдира
# (демон уже дал уникальную agent/<роль>/<hash> в task-workdir; она локальная и никогда
# не пушится — правило «две ветки» про origin, локальный scratch-ref им не нарушается).
# …правки, коммиты (Conventional Commits), мелко и часто…
git fetch origin dev && git rebase origin/dev              # синк со свежим общим dev
git push origin HEAD:dev                                   # публикация в общий dev
# проверка на https://dev.3mf.tech (webcheck) → зелено →
git fetch origin dev && git push origin origin/dev:main    # промоушен на прод (ff; Lead/директор)
```

**Никогда `git checkout -B dev origin/dev` (и никакая другая форма локального переключения на
ветку `dev`) в task-workdir.** Один bare-репо расшарен на десятки параллельных worktree
(один на запуск агента); `git` блокирует чекаут одной и той же ветки в двух worktree
одновременно, но **только для голого `git checkout <branch>`/`git switch <branch>`** —
`checkout -B` (force create-or-reset) эту защиту не проверяет и тихо переключает HEAD, даже
если `dev` уже занята в 40 других worktree. Итог: десятки worktree делят один и тот же
`refs/heads/dev`, но у каждого свой протухший index/working tree — `git status` в них
показывает фантомные `M`/`D` по файлам, которые агент не трогал (просто кто-то другой сдвинул
общий `dev` первым). Реальный инцидент и разбор — карточка MF-746 на доске, механика — в
`docs/process/git.hygiene.md` § 1. Работай на своей ветке (`HEAD`), синкайся `fetch && rebase`,
публикуй `push origin HEAD:dev` — результат тот же линейный `dev`, без разделяемого чекаута.

`push origin/dev:main` отклонён как non-ff (в `main` уехал коммит версии от CI) → `git fetch
origin main dev`, повтори промоушен на свежих ссылках; **никогда** `--force`, **никогда**
rebase общего `dev`.

**dev-only ≠ ветка, а ENV.** Всё, что должно жить только на dev (открытый вход без авторизации, сиды, тестовые данные), — в env-файле на VDS (`portal.api-dev.env`, вне git), НЕ в коде ветки `dev`: `dev → main` неизбежен, любой dev-only код рано или поздно уедет в прод.

**Ретрофит (2026-07-08):** старые пространства имён (`feature/*`, `fix/*`, `docs/*`, `agent/*`, ветка `test`) — легаси, вычищаются (`docs/process/git.hygiene.md`); на `origin` остаются только `main` и `dev`.

**⚠️ Защита `main` не настроена** (`protected: false`; branch protection нет в публичном API GitVerse — [док](https://gitverse.ru/docs/developers/public-api/repositories), не баг). Держится процессом (промоушен-дверь выше). Появится UI/API-защита — вопрос к CTO.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/ru/): `<тип>(<область>): <описание>`.

Типы: `feat` · `fix` · `docs` · `refactor` · `test` · `chore` · `ci` · `perf` · `design` · `deploy` · `infra` · `analytics` · `process`. Область — имя приложения (`web`/`api`/`mesh`/`giga`), пакета/сервиса (`device-agent`/`relay`/`scout`) или `repo` для общего.

```
feat(mesh): добавить конвертацию STL → 3MF
fix(api): починить 500 на /health при пустом body
docs(repo): расширить коммит-конвенцию
infra(relay): обновить systemd-конфиг
```

Зачем: `changelog.md` собирается из коммитов при бампе версии, тип коммита понятен без чтения диффа.

## Промоушен в `main` (вместо per-feature PR)

Per-feature PR в модели двух веток НЕ используется — работа непрерывно интегрируется в `dev`. Выкатка на прод:

1. Фича проверена **живой на dev.3mf.tech** (webcheck-скрин в карточку) + `dev.3mf.tech` в целом зелёный + вердикт QA.
2. Промоушен `dev → main` (fast-forward): `git push origin dev:main`. Право — Lead и директора вертикалей; делается **часто**, чтобы `main` шёл впритык за `dev` (не большим батчем).
3. Пуш в `main` = автодеплой на 3mf.tech (~2 мин). Версию `release.yaml` бампает отдельно, на каждый push в `dev` (MF-1792, `docs/process/versioning.md`) — промоушен в `main` версию не трогает и никуда её не синкает, она просто едет вместе с промоутнутыми коммитами.

Что заменяет approve на PR: живой стенд **dev.3mf.tech** (реальное поведение важнее диффа), вердикт QA, вето Lead/директора. Секреты не в коде (`SECURITY.md`) и границы `web→api→{mesh,giga}` (`docs/architecture/readme.md`) — на совести коммитящего и директора вертикали; CI (`ci.yaml`) гоняет lint/typecheck/test/build.

**Единственные писатели `main`:** промоушен `dev→main` (после проверки на dev.3mf.tech) и релиз-стамп роли Git (нарезка релиза, `chore(release): … [skip ci]` + тег — `docs/process/versioning.md`). CI (`release.yaml`) с MF-1792 (2026-07-17) бампает версию на `dev`, `main` не пишет. Всё прочее в `main` — нарушение (детектит роль Git, см. `docs/process/git.hygiene.md` § «Защита main»). Правило merge-двери MF-528 (squash-PR в main) заменено этой промоушен-дверью 2026-07-08.

## Задания — `issues/*.md`, обычные и большие (эпики)

**Задачи трекаются в git, не в GitVerse Issues** — у публичного API GitVerse эндпоинтов для issues нет вообще (только веб-UI, см. `docs/infra/readme.md` § «GitVerse Public API»), а вести реальную работу через UI, недоступный мне напрямую, неудобно. Решение 2026-07-03, «пока что» — пересмотреть, если у GitVerse появится API или команда вырастет настолько, что нужны уведомления/богатый трекер.

**Формат** (`docs/issues/readme.md` — доска со всеми задачами, обновлять при каждом изменении статуса):
- Файл `docs/issues/<NNN>.<slug>.md` — номер (3 цифры, сквозной счётчик, следующий — `docs/issues/readme.md`+1) + короткий slug через точки.
- Обязательные поля вверху: `**Статус:**` (`open`/`in-progress`/`done`/`blocked`), `**Тип:**` (`epic`/`infra`/`bug`/`feature`), `**Создано:**`.
- Тело: суть (несколько предложений), чеклист фаз/шагов, открытые вопросы (если есть).

**Большая задача (эпик)** — многонедельная инициатива, требующая своего ресёрча/дизайна до начала кода (напр. смена формата хранения, новый способ авторизации, нейропоиск). Отличается от обычной задачи объёмом и тем, что решение нужно ПРОРАБОТАТЬ, а не просто описать:

1. **Полная спека — отдельно:** `docs/epics/<name>.md` (проблема/цель, ресёрч с источниками, архитектура/варианты с trade-off’ами, **открытые вопросы, требующие решения** — явно помечены, разбивка на фазы, критерии приёмки). **Для любого UI-эпика критерии приёмки обязаны включать перформанс+анимации+звук** (`docs/design/motion.md`/`sound.md`) — это не отдельная фича, а сквозной критерий готовности любого фронт-экрана (`docs/product/roadmap.md` § «Перформанс и „дорогое“ ощущение»), эпик без этого пункта в критериях приёмки не полон.
2. **Файл в `issues/`** — короткий, со ссылкой на спеку (`**Спека:** [docs/epics/<name>.md](../epics/<name>.md)`), не дублирует полный текст — спека меняется отдельно (PR-ревьюится), issue-файл остаётся указателем + треком статуса.
3. **Реализация — отдельными `issues/*.md`**, каждый ссылается на эпик по номеру. Эпик — `done`, когда все дочерние закрыты.
4. Открытые вопросы из спеки — либо решаются до старта кода (Валерий отвечает в PR/комментарии к коммиту), либо явно фиксируются как «решаем по ходу, дефолт — Х» с обоснованием (не блокировать работу неопределённостью, если есть безопасный дефолт).

GitVerse Issues (веб-UI, шаблоны `.gitverse/ISSUE_TEMPLATE/*.yaml`) остаются рабочими как **вторичный** канал — например, для быстрого репорта от будущего внешнего подрядчика без доступа на запись в репо.

**Живая операционная доска — отдельно от `docs/issues/`.** `docs/issues/`+`docs/epics/` — это спеки и крупные инициативы (версионируются, ревьюятся в PR). Повседневная работа и то, что ассистент делает по поручению Валерия, ведётся на доске Multica (`tasks.3mf.tech`, воркспейс `3mf`, префикс `MF`) — см. [`docs/process/tasks.multica.md`](docs/process/tasks.multica.md). Поручение ассистенту = карточка на доске со статусом, а не только «тихое» действие.

## Тестирование и локальная БД: КРИТИЧНО

⚠️ **Для локальных и QA-тестов используй ТОЛЬКО изолированную БД `portal_qa_test`, НЕ `DATABASE_URL` из `portal.api.env` или `.pgpass`.** Это касается в первую очередь запусков на prod-VDS (где живит боевая БД), но правило универсально: локальные миграции и тесты никогда не должны трогать боевую схему.

**Почему это критично:** `.env.example` в репо показывает `DATABASE_URL=postgres://portal:portal@localhost:5432/portal` — это образец для локальной машины. Но на prod-VDS это **реальный боевой DATABASE_URL**, и `.pgpass` на той же машине хранит валидный пароль ровно для этой учётки. Агент или разработчик, видя `.env.example`, могут случайно принять боевую БД за тестовую и прогнать на ней миграции или тесты, что повредит данные.

**Что делать:**

- **Локально (на своей машине):** `docker compose up -d` в `apps/api/` создаёт контейнер Postgres со схемой `portal`, роль `portal`, пароль `portal` — этот именно для вас. Используйте его для `pnpm test` и миграций. `.env.example` верен.
- **На prod-VDS (боевой VDS, если нужно там тестировать):** используй роль `qa_tester` и БД `portal_qa_test`. Креды и схема — уже настроены Ops. Переопределите `DATABASE_URL=postgres://qa_tester:…@localhost:5432/portal_qa_test` перед `pnpm test` или миграциями.

**Как узнать, где вы:** `echo $DATABASE_URL` или `grep DATABASE_URL ~/.pgpass | head -1` — если в строке слово `portal_qa_test`, вы на правильной БД. Если без суффикса `_qa_test` — СТОП, не запускайте тесты/миграции.

Инцидент ([MF-698](mention://issue/3f93634c-0789-4b16-9ccd-ca96b7d80e24)): QA-агент прогнал миграцию на боевой БД, вовремя остановился, данных не потеряно, но риск повторения остаётся.

**Итерируешь файл миграции (правишь `db/migrations/*.sql` после того, как уже разок прогнал `dbmate up`)** — гоняй `dbmate up`/`down` только на throwaway `sandbox-db create`, никогда на общей dev-БД. На общей БД версия попадает в `schema_migrations` уже на первом прогоне; если файл потом ещё раз поменяется, закоммиченный `db/schema.sql` (pg_dump с этой машины) зафиксирует версию как applied без DDL, который ей на самом деле соответствует — ровно тот класс инцидентов, что закрыт в [MF-836](mention://issue/0602ef70-77fa-4980-b396-4870cc65f48c) (MF-33/409, MF-466, MF-748).

## Нейминг (обязательно)

**Файлы и папки: lowercase, слова разделяются точкой. Никаких `-` и `_`.**
Пример: `release.process.md`, не `release-process.md` и не `release_process.md`. Ветки: `feature/stl.converter`, не `feature/stl-converter`.

**Исключения — только там, где имя жёстко задано инструментом** (иначе инструмент файл не узнает):

| Файл/паттерн | Почему нельзя иначе |
|---|---|
| `CLAUDE.md`, `AGENTS.md` | ИИ-инструменты (Claude Code и др.) читают ровно эти имена автоматически |
| `CODEOWNERS`, `PULL_REQUEST_TEMPLATE.md`, `ISSUE_TEMPLATE/` (в `.gitverse/`) | GitVerse ищет ровно эти имена |
| `CODE_OF_CONDUCT.md`, `LICENSE.md`, `SECURITY.md`, `CONTRIBUTING.md`, `README.md` | GitHub/GitVerse community-файлы — распознаются только по точному имени |
| `.gitignore`, `.editorconfig`, `.npmrc` | Конвенция самого инструмента (точка в начале обязательна) |
| `package.json`, `pnpm-workspace.yaml`, `turbo.json`, `pyproject.toml`, `compose.yaml` | Имя жёстко зашито в npm/pnpm/Turborepo/Python build/Docker Compose |
| ENV-переменные (`DATABASE_URL`, `GITHUB_OUTPUT`) | POSIX требует `UPPER_SNAKE_CASE` — точки и дефисы в именах переменных окружения синтаксически невалидны |
| Python-модули/пакеты (`test_main.py`) | PEP 8 + автообнаружение pytest (`test_*.py`) требуют `_`, точка в имени модуля означает вложенность пакета, а не разделитель слов |
| Классы CSS-фреймворков (если появится Tailwind) | Не наши идентификаторы — конвенция самого фреймворка |
| Имя React-компонента **внутри кода** (`export function App()`) | `eslint-plugin-react-hooks` определяет по регистру ИМЕНИ ФУНКЦИИ, легитимный ли это компонент (иначе `rules-of-hooks` не даёт вызывать хуки) — это не про имя файла |

**Правило про файлы ≠ правило про идентификаторы кода.** Файл — `app.tsx` (lowercase, наше правило). Экспортируемый компонент внутри — `App` (PascalCase, этого требует статический анализ `eslint-plugin-react-hooks`). Это два разных пространства имён, не конфликт.

## Документация: читай, ведёшь, синхронизируешь

**Главное правило:** док = источник истины. Протухший док — баг. Чтобы держать доки актуальными, действует правило: **перед началом работы читаешь профильные доки, по ходу ведёшь/обновляешь свой `.md`**.

Детально — `docs/readme.md` § «Куда класть новое» → «Правило: перед фичей читаешь док и ведёшь свой». Кратко:

- **Перед началом:** работа на `web` → читай `docs/design/readme.md` + тематические файлы. На `api` → `docs/architecture/readme.md` + спеки эпиков. На инфре → `docs/infra/readme.md`.
- **По ходу:** новый компонент/паттерн/подход → заводишь/обновляешь `.md` с ссылкой из папки-readme.
- **На готовность фичи (merge в dev):** её док уже синхронен — никаких отложенных обновлений.
- **Исключение:** рефакторинг/багфикс без изменения контракта или поведения — док не трогаем.

Если неизвестно, чинится ли докумет при этой правке — лучше обнови, чем оставь старым. Сомневаешься — пингуй владельца (карта владения — `docs/readme.md`).
