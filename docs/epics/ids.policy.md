# Политика внешних ID и необнаружимости (MF-39 фаза 3, рядом с MF-21)

**Статус:** зафиксировано (Data), 2026-07-10
**Контекст:** [MF-39](mention://issue/c5978c31-226d-4f0d-9201-1337dfc248c1) «Антипиратство и необнаружимость», шаг «зафиксировать политику ID и совместимость подписанных ссылок» из [MF-425](mention://issue/82f1c2e1-637b-4033-8c11-908e006c812f) (Фаза 3). Ссылка per спеку — рядом с `formats.policy.md` (MF-21).

## Что уже верно (аудит кода, 2026-07-10)

Проверено `apps/api/src/db/schema.ts`: **все 25+ таблиц** используют `id uuid primary key default gen_random_uuid()` (UUIDv4, криптослучайный). Ни одной `serial`/`bigserial`/autoincrement-числовой PK нет нигде в схеме. Это уже зафиксировано как конвенция в `docs/epics/domain.model.md` § «Принципы» п.6 и было явным решением ещё для `users` в `docs/issues/007.database.design.md` (2026-07-03): «`id` — `gen_random_uuid()` (UUID v4, НЕ v7/ULID — не должен быть сортируем по времени/палить темп регистраций)».

Вывод: **МF-423 (Фаза 1, «развести внутренний PK и внешний public_id») по факту уже выполнена схемой с первого дня** — здесь нет отдельной колонки `public_id`, потому что сам PK уже некогда не был числовым/перечислимым. Дополнительная миграция «числовой PK → public_id» **не нужна**, потому что мигрировать нечего.

Роутер уже частично соблюдает контракт: `apps/api/src/db/uuid.ts` (`isUuid()`) используется в `models/detail.ts`, `models/download.ts` и других ручках `models/:id/...` — невалидный/неполный UUID отклоняется 404 ДО похода в БД (не 500 от `::uuid`-каста, MF-712/713). Это правильный паттерн, его надо тиражировать на любую новую сущность с публичным ID.

## Политика (закрепляется этим документом)

1. **Любая публичная сущность** (модели, заказы, ремиксы, файлы, комменты, идеи, посты, треды и т.д.) — PK `uuid default gen_random_uuid()`. Никогда `serial`/`bigserial`/`identity` в качестве PK, который может попасть в API-ответ или URL.
2. **UUIDv7/ULID запрещены** для сущностей, где важна необнаружимость роста (модели, заказы, юзеры) — они раскрывают timestamp создания. Разрешены только для внутренних, не публикуемых наружу структур (если вообще понадобятся).
3. **Отдельного `public_id`-хелпера (encode/decode, FPE/Feistel, Sqids) не требуется** — честный `gen_random_uuid()` уже даёт то же свойство («неперечислимо, невосстановимо без БД»), которое MF-39 рекомендует как единственный надёжный вариант. Sqids/Hashids поверх PK по-прежнему запрещены для чувствительных сущностей (если где-то возникнет — вето Data при ревью).
4. **Роутер:** любая ручка с сущностью в пути обязана валидировать формат ID (`isUuid()` или аналог) до похода в БД и отвечать 404 на невалидный формат — не 500, не 400 с деталями. Это тестируется CI-линтом «нет числовых ID в путях роутера» (реализация — Back/Test, вне территории Data; критерий приёмки описан здесь).
5. **Пагинация и агрегаты** (offset/total count) — вне территории Data по коду, но БД-слой не должен поощрять `count(*)` по всей таблице в публичных ответах; курсор — по `(created_at, id)` opaque-токену, не по числовому смещению.

## Migration-window: не требуется

В текущей схеме нет ни одной таблицы с легаси-числовым ID моделей (или другой публичной сущности) для миграции — `models.id` был `uuid` с момента проектирования (MF-453, 2026-07-05). Deep-link `?item=`, упомянутый в MF-39 как риск («миграция существующих числовых ID моделей... с сохранением deep-link `?item=`»), ссылается на черновой демо-документ `3dmake/DEMO.md`, которого нет в этом репозитории — в текущем `apps/web` такого параметра/маршрута не найдено (проверено grep по `apps/web/src`, `docs/`). Если демо-флоу вернётся отдельной задачей, заводить `?item=`→`?item=<uuid>` сразу без промежуточного числового ID.

**Если когда-либо появится сущность с унаследованным числовым ID** (импорт из внешней системы и т.п.): expand→migrate→contract — (1) добавить `uuid`-колонку `default gen_random_uuid()` рядом, (2) прогнать бэкофилл, (3) переключить сериализаторы/роутер на неё, (4) отдельной миграцией дропнуть старую числовую колонку после окна совместимости. Общий паттерн уже принят для схемы (см. `apps/api/src/db/migration-plan.models-to-projects.md` как пример готового плана переименования).

## Открытая проблема: публичный offload файлов конфликтует с целью MF-39 (важно, не решается на этой карточке)

`apps/api/src/storage/s3.ts` (`modelPublicUrl`/`isPublicOffloadEnabled`, `withResponseOverrides`) + [MF-709](mention://issue/4068497e-7fcd-42c8-8537-4cb4b3a6639a) и [MF-715](mention://issue/f986cfcb-1cdf-4f89-83da-a1939ec30266) (оба **done**, 2026-07-09/10, CTO-approved, эпик MF-703 «offload egress») переключают отдачу файлов `3mf`/`generations` с прокси-стрима API (сессия+статус+403/404-маскировка) на **прямой анонимный публичный URL** `https://<domain>.s3.cloud.ru/<bucket>/<key>` — БЕЗ проверки сессии, БЕЗ rate-limit, БЕЗ форензик-журнала, БЕЗ TTL, если офлоад включён (`S3_PUBLIC_ENDPOINT`/`S3_PUBLIC_URL_STYLE` заданы).

S3-ключ детерминирован (`models/{model_id}/{role}.{ext}`, см. `modelObjectKey()`), а `model_id` (UUID) не секрет — он есть в любом публичном URL карточки модели. Значит **любой, кто открыл страницу модели, может собрать прямую ссылку на файл и скачать его в обход всех защит, которые MF-39 фазы 1–2 должны построить** (rate-limit/challenge, форензик-журнал скачивания, короткоживущие подписанные ссылки).

Это прямой конфликт с «Готово когда» пп. 2–4 эпика MF-39 (приватный бакет/подписанные ссылки/форензик на каждое скачивание). Не вето на MF-709/715 задним числом (уже done, CTO одобрил ради v1-цели снять egress с VDS) — но MF-39 (v2, дедлайн 31.12.2026) **не может закрыть свои критерии, пока публичный offload остаётся включённым для канонических 3MF-файлов в исходном виде**. Варианты на выбор Lead/CTO при старте фаз 1–2 MF-39:
- (a) вернуть отдачу канонического 3MF на прокси-стрим API (потерять часть egress-экономии MF-709 для этого пути, оставить offload только для превью/thumbnail, которые не являются «выкачкой»);
- (b) держать offload, но переключить бакет `3mf` на подписанные query-string URL с коротким TTL (cloud.ru поддерживает presigned для anonymous-read бакетов так же, как AWS S3 — тогда egress не через VDS, а защита сохраняется);
- (c) явно принять риск как продуктовый trade-off v1-vs-v2 (записать решение здесь после вердикта).

**ВЕРДИКТ CTO (2026-07-10): вариант (b).** Offload остаётся (не откатываем egress-выигрыш
MF-709/715), но protected-роли (`source`, `canonical_3mf`, `cnc_program`, `drawing`, `gerber`,
`code_archive`, `aux`) уходят на приватный prefix `protected/models/{model_id}/{role}.{ext}` бакета
`3mf` и отдаются только presigned GET с коротким TTL; `preview`/`thumbnail`/`description_image`
остаются публичны на `public/models/{model_id}/...` без изменений. Bucket-policy сторона (перенос
уже загруженных объектов + policy только на `public/*`) реализована в
[MF-754](mention://issue/286ade1a-2ece-4e6a-8d73-ee038a963631) (Ops, 2026-07-10) — подробности и
живая проверка в `docs/infra/readme.md` § «Bucket-policy hardening». Presigned-код и переключение
`modelObjectKey()`/`upload.ts`/`apps/mesh` на новый prefix — [MF-755](mention://issue/63dc7e9e-5e55-4758-82cf-8ee01d447303)
(Fullstack) — сделано: новые загрузки пишутся под `protected/`/`public/` сразу, `download.ts`
отдаёт presigned GET для protected-ролей, существующие строки `model_files.s3_key` переведены
на новый prefix миграцией `20260710320000_model_files_protected_prefix.sql`.

Ничего не меняю в `s3.ts`/download-коде в рамках этой карточки — код на прод-VDS и стриминг файлов вне территории Data (`apps/api/src/db`), решение затрагивает Ops (bucket policy) и Fullstack/Back (download-код), плюс сам конфликт эпиков — уровень Lead/CTO.

## Совместимость подписанных ссылок с v1 «отправить на принтер» / MF-26 (NAT)

Текущая архитектура **не использует presigned S3 URL** в принципе — `s3.ts` явно документирует причину (MinIO живёт на loopback на VDS, presigned-ссылка недостижима из браузера), поэтому контроль доступа к файлам реализован на уровне API (`readSession` + `status='ready'`/владелец + 404-маскировка в `models/download.ts`), а не подписью URL. Итог для MF-39/MF-26: любой флоу «отправить на принтер» (включая печать через NAT, MF-26) должен ходить через существующий сессионный API-эндпоинт `/models/:id/download.3mf` (или его аналог для конкретного флоу), а не ожидать presigned-URL-паттерн из исходного текста эпика MF-39 — тот пункт эпика устарел относительно уже принятого архитектурного решения. Если офлоад (см. риск выше) когда-то станет единственным путём отдачи, флоу «отправить на принтер» обязан сохранить форензик-запись на стороне API до выдачи ссылки, иначе печать по прямому URL останется бесследной.
