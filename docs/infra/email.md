# Email (SMTP) — общая инфраструктура для всех сервисов проекта

Единый почтовый ящик `auth@3mf.tech` (Timeweb) шлёт письма для **двух независимых сервисов** сейчас:
`apps/api` (email-OTP для входа на `3mf.tech`) и self-hosted Multica (`tasks.3mf.tech`, коды входа на доску).
Этот файл — единственный источник правды по email-инфраструктуре: если заводишь **третий** сервис, которому
нужна отправка писем — читай этот файл целиком, ничего дополнительно настраивать в DNS/на Timeweb не надо
(см. «Как подключить новый сервис» ниже).

## Провайдер и почему именно он

**SMTP через Timeweb**, не западный ESP (Resend/SendGrid/Mailgun и т.п.) — осознанный выбор 2026-07-06.
Причина: основная целевая аудитория email-логина — корпоративная почта `@sberbank.ru`/`@sberdevices.ru`
(см. `docs/epics/auth.triple.md` § «Метод 1»), а домен `3mf.tech` и так на DNS/хостинге Timeweb (тот же держит MX) —
минимум трения, никакой сторонней регистрации. Компромисс: Timeweb — обычный shared-хостинг email, не
специализированный ESP с гарантиями доставляемости; на практике это не бесплатно (см. «Доставляемость» ниже).

## Ящик и креды

- Ящик `auth@3mf.tech` заведён **Валерием вручную в панели Timeweb** — я туда доступа не имею (только DNS
  Timeweb, не Cloudflare — тоже не мой доступ, все правки DNS делает Валерий по моим инструкциям).
- SMTP: `smtp.timeweb.ru:465` (implicit TLS — порт 465 форсирует TLS независимо от прочих настроек).
  IMAP (для диагностики/чтения ящика, не для отправки): `imap.timeweb.ru:993`.
- **Креды хранятся в двух местах на VDS `176.123.160.18`** (НЕ в git, нигде):
  - `~/portal.api.env` (для `apps/api`, systemd `portal.api.service`, `EnvironmentFile=`) — переменные
    `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`/`SMTP_FROM` (все = `auth@3mf.tech`, кроме host/port/pass).
  - `~/tasks.multica/.env` (для self-hosted Multica, `docker compose`) — **другие имена той же сути**:
    `SMTP_HOST`/`SMTP_PORT`/`SMTP_USERNAME`/`SMTP_PASSWORD`/`SMTP_EHLO_NAME` + **обязательно**
    `RESEND_FROM_EMAIL=auth@3mf.tech` (эта переменная задаёт `From:` для ОБОИХ путей — и Resend, и SMTP;
    без неё письма уйдут от дефолтного `noreply@multica.ai`, несовпадение с доменом реального ящика — сразу
    подозрительно для антиспама получателя).
  - Оба файла `chmod 600`, доступны только пользователю `plag`.

## DNS-записи (уже в проде, DNS Timeweb, не Cloudflare)

Всё уже настроено и опубликовано, ничего добавлять не нужно, если новый сервис шлёт от того же `auth@3mf.tech`:

| Тип | Хост | Значение |
|-----|------|----------|
| TXT (SPF) | `3mf.tech` | `v=spf1 include:_spf.timeweb.ru ~all` |
| TXT (DKIM) | `dkim._domainkey.3mf.tech` | `v=DKIM1; k=rsa; p=<ключ, см. запись в DNS>` — селектор `dkim`, приватный ключ хранится и подписывает письма **на стороне Timeweb автоматически** (мы приватный ключ не видели и не храним) |
| TXT (DMARC) | `_dmarc.3mf.tech` | `v=DMARC1; p=none;` (мягкий режим — только мониторинг, ничего не блокирует; `rua=` для отчётов не задан — можно добавить `rua=mailto:auth@3mf.tech` при желании) |

Проверено вручную (2026-07-06): SPF-цепочка (`_spf.timeweb.ru → _spf1.timeweb.ru`, IP `176.57.223.12`
покрыт диапазоном `176.57.222.0/23`) и DKIM (реальный `DKIM-Signature: ... d=3mf.tech; s=dkim` в заголовках
письма, увиден через self-send + IMAP-чтение сырых заголовков) — оба реально работают, не просто «запись в DNS
есть, а толку нет».

## Доставляемость — что подтверждено, что нет (важно!)

**Технически всё настроено правильно** (SPF passes + DKIM реально подписывает + DMARC опубликован) — но это
**не гарантирует доставку везде**. Результаты тестов 2026-07-06:

- ✅ **iCloud** (`plagness@icloud.com`) — доставляется надёжно, подтверждено многократно.
- ❌ **Protonmail** (`plagness@protonmail.com`) — **тихо роняется**, без спама, без bounce, без DSN, несмотря
  на явный запрос DSN (`notify:['SUCCESS','FAILURE','DELAY']`) и полностью корректные SPF/DKIM/DMARC.
  Timeweb принимает письмо в очередь по-настоящему (реальный Exim queue id), но результат на стороне
  Protonmail не проверяем — это classic «accept-then-silently-drop» поведение известных строгих спам-фильтров
  по отношению к новым доменам без истории отправок. **Не техническая дыра у нас — политика получателя.**
  Дальше не гонять — не входит в целевую аудиторию продукта.
- ❓ **Gmail** (`nabiyarov.fanzil@gmail.com`, в `ALLOWED_EMAILS` Multica) — **не тестировалось**, нет доступа
  к ящику для проверки. Если он попробует войти и код не придёт — разбираться так же (self-send + IMAP-чтение
  заголовков на `auth@3mf.tech`, контрольное письмо на альтернативный ящик для сравнения).
- ❓ **`@sberbank.ru`/`@sberdevices.ru`** (реальная целевая аудитория) — **не тестировалось, нет доступа ни к
  одному реальному ящику на момент написания (2026-07-06)**. Это единственная проверка, которая реально имеет
  значение для приёмки — Protonmail не показатель (другой профиль фильтрации, консьюмерский privacy-сервис,
  не корп-шлюз). Как появится реальный тестовый адрес — прогнать тот же метод диагностики (ниже).

### Метод диагностики (если снова «не доходит»)

1. **Полный SMTP-дебаг** — `nodemailer` с `logger:true, debug:true` + `dsn:{ret:'FULL', notify:['SUCCESS','FAILURE','DELAY']}`, смотреть весь протокольный обмен (не только финальный `250 OK`).
2. **Self-send** — письмо самому себе на `auth@3mf.tech`, прочитать сырые заголовки через IMAP (`imaplib`,
   `imap.timeweb.ru:993`, те же креды) — подтверждает, что DKIM реально подписывает именно это сообщение.
3. **Контрольный адрес** — параллельно отправить на заведомо рабочий ящик (сейчас — iCloud) для сравнения:
   если контрольный дошёл, а целевой нет — проблема на стороне получателя, не у нас.
4. **IMAP-инспекция `auth@3mf.tech`** — папки `INBOX`/`Spam`/`Delayed`/`Trash`/`Sent` через `imaplib`
   (`Sent` для raw-SMTP отправки всегда 0 — это нормально, SMTP-протокол не пишет в IMAP Sent, это делает
   только сам почтовый клиент/веб-морда, не наш код).
5. **RBL-проверка IP** (`176.57.223.12`) — **публичные резолверы (8.8.8.8 и т.п.) не годятся для Spamhaus**
   (он специально блокирует запросы не со своих серверов, возвращает `127.255.255.254` = «используй наш DNS»,
   это не «плохой IP», а отказ отвечать). Проверено вручную: SpamCop/Barracuda чистые. Веб-чекеры
   (mxtoolbox/talos/check.spamhaus.org) блокируют автоматический доступ (403) — при реальной необходимости
   открывать глазами в браузере, не через WebFetch.

## Как подключить новый (третий) сервис к этой же почте

1. Если сервис шлёт **от того же `auth@3mf.tech`** — просто взять креды из `~/portal.api.env` (или завести
   аналогичный `.env` на своей VDS/окружении) и переиспользовать тот же SMTP-транспорт. Ничего в DNS менять
   не нужно — SPF/DKIM/DMARC уже покрывают этот адрес.
2. Если сервису нужен **другой локальный адрес** (например `notify@3mf.tech` или `no-reply@3mf.tech`) —
   сначала завести реальный ящик в панели Timeweb под этим адресом (как заводили `auth@3mf.tech`), DKIM/SPF/DMARC
   для домена `3mf.tech` в целом уже покрывают любой адрес `@3mf.tech` — но нужно проверить, разрешает ли
   Timeweb отправлять `From:` не совпадающий с аутентифицированным SMTP-логином (обычно нет — большинство
   провайдеров форсят `From = SMTP_USER` ради анти-спуфинга) — то есть либо новый ящик = новый SMTP-логин,
   либо остаётся `auth@3mf.tech` с другим `Reply-To`.
3. Код — копировать паттерн `apps/api/src/email/send.ts` (nodemailer, no-op-with-warning без кредов, тот же
   принцип что `storage/s3.ts`): не падать, если SMTP не настроен, просто предупреждать в лог. Это специально
   для дев/тестовых окружений, где креды не нужны.
4. **Секреты — только в `.env` на сервере, никогда в git.** См. `SECURITY.md` § «Секреты».

## Кто чем управляет (два разных механизма allowlist, не путать)

- **`apps/api` (3mf.tech)** — домен-гейт `EMAIL_DOMAINS = ['sberbank.ru', 'sberdevices.ru']` **захардкожен**
  в `apps/api/src/auth/email.ts` (не через env) — вход по email доступен **любому** адресу в этих двух
  доменах, без предварительного индивидуального разрешения (в отличие от Multica ниже). Это **полностью
  независимый путь входа, без Telegram/PlagID вообще** — готов и задеплоен с 2026-07-03, реальная отправка
  включена 2026-07-06.
- **Multica (`tasks.3mf.tech`)** — два раздельных механизма в `~/tasks.multica/.env`:
  - `ALLOWED_EMAILS` — точечный список конкретных адресов (сейчас `plagness@icloud.com,nabiyarov.fanzil@gmail.com`).
  - `ALLOWED_EMAIL_DOMAINS` — доменный allowlist (добавлено 2026-07-06: `sberbank.ru,sberdevices.ru`) — любой
    адрес в этих доменах тоже пускается, без ручного добавления в `ALLOWED_EMAILS`.
  - **⚠️ Но перед этим email-экраном на `tasks.3mf.tech` всегда стоит отдельный Telegram-гейт**
    (`gate/server.js` + nginx `auth_request`, см. `docs/process/tasks.multica.md`) — сберовец с доменным доступом всё
    равно не попадёт на саму форму email+код, пока не пройдёт Telegram (или не получит `has3mf` через
    доступ к 3mf.tech — см. `project.tasks.multica` в памяти ассистента). **Открытый вопрос, не решён**:
    нужен ли обход Telegram-гейта специально для `sberbank.ru`/`sberdevices.ru`, чтобы «только по email»
    работало и на доске тоже, не только на главном сайте — решение зависит от того, кто именно должен попадать
    на доску (сотрудники Сбера как полноценные участники разработки, а не только тестовая аудитория продукта).

## ⚠️ Грабля: exit-node ломает SMTP к Timeweb (2026-07-08)
VDS ходит наружу через Tailscale exit-node (Финляндия, обход гео-блока Anthropic — см. `readme.md` § «Исходящий трафик»). Timeweb SMTP (`smtp.timeweb.ru:465`, российский сервер) через финский IP **недостижим** — коды верификации/OTP не отправляются («ошибка отправки кода»). Затрагивает ВСЮ почту с VDS: и Multica-логин, и apps/api.
**Фикс:** SMTP-трафик к Timeweb идёт напрямую через WAN (мимо exit-node) — `ip rule to <Timeweb-подсети> lookup wanout priority 90` (ВЫШЕ tailscale-правила 5270). Подсети `176.57.223.0/24` (smtp.timeweb.ru) + `178.248.239.0/24` (mail.timeweb.com) — /24 чтобы пережить ротацию IP. Персистентно в `/usr/local/sbin/wan-policy-routing.sh` (юнит `wan-policy-routing.service`, применяется на буте).
**Проверка:** `openssl s_client -connect smtp.timeweb.ru:465` должен дать `220 … ESMTP` и `Hello … [176.123.160.18]` (российский IP, НЕ финский). Если `Hello` с чужим IP или таймаут — правило слетело, переприменить скрипт.
