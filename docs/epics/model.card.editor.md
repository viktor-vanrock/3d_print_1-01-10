## 1. Проблема

Постановки фаз MF-9 (04.07) написаны через контейнер `projects` / `project_files` / `project_models`
(1 проект → N 3D-моделей, доп-файлы, картинки описания). Принятые позже архитектурные решения
(запрос Валерия MF-480, 06.07) фиксируют обратное: «проект = эволюция `models`, параллельную
таблицу `projects` не заводить» (`projects.foundation.md` §2 п.1; `docs/design/projects.md` §1.2 —
одна витрина; план миграции `models`→`projects` — отложен, с явными триггерами). Пока конфликт
не решён, контракт API фаз 1–2 не существует ни в одной форме: MF-339 стоит, MF-341 в `blocked`.

Формулировки `project_*` в карточках MF-339..341 — это текст постановок, через приёмку
архитектуры они не проходили. Принятые доки — проходили. Конфликт решается в пользу того,
что принято, если требования MF-9 в принятой модели выразимы. Проверяем ниже — выразимы.

## 2. Факты (ресёрч)

- **Live-схема** (`apps/api/src/db/schema.ts`): `models` (per-карточку: `status` конвейера,
  `source_format`, `craft`, `description`, `bbox`) + `model_files` (`role`:
  `source`/`canonical_3mf`/`preview`/`thumbnail` + проектные роли MF-482). Сегодня — один
  `source` на карточку: mesh-воркер (`apps/mesh/src/mesh/worker.py`) очередится по
  `models.status='pending'`, берёт единственный `role='source'`, ключи S3
  `models/{id}/{role}.{ext}` — один файл на роль.
- **Вся живая витрина** (каталог, страница модели, теги, голоса, миниатюры — MF-462/464/469)
  построена над `models`. Вторая контентная сущность рядом = либо дублировать всё это,
  либо строить мост/merge-view — и то и другое дороже расширения.
- **Требования MF-9 по существу:** (а) доп-файлы любых форматов; (б) картинки описания;
  (в) черновик/публикация; (г) N 3D-моделей в одной публикации, превью и статус каждой.
  (а)–(в) уже уложены в `models`+`model_files` ревизией постановок Lead от 06.07 (роли
  `aux`/`description_image`, поле публикации на `models`). Открытым оставалось только (г).
- **Принятый принцип** (`projects.foundation.md` §2 п.2): «мульти-артефактность живёт на
  уровне файлов» — реестр `model_files.role` уже расширен под ЧПУ/лазер/платы/код (MF-482).

## 3. Варианты

- **A. Контейнер (буква постановок MF-9):** новые таблицы `projects` / `project_files` /
  `project_models`; `models` остаётся про конвертацию одного файла.
  *За:* мульти-модель «из коробки», конвейер mesh не трогаем.
  *Против:* вторая контентная сущность параллельно `models` — две витрины или мост
  (каталог/теги/голоса/страница — всё на `models`); прямо противоречит трём принятым докам
  и самой формулировке Валерия в MF-480 (фундамент «Проектов» = эволюция магазина, а не
  вторая система рядом); обнуляет дешёвый план переименования `models`→`projects`;
  это ровно та параллельная супер-сущность, от которой предостерегает `domain.model.md`.
- **B0. Одна сущность, жёстко одна 3D-модель на карточку:** конвейер не трогаем, «список
  моделей» из MF-9 вычеркнуть.
  *За:* дешевле всех, ноль миграций.
  *Против:* режет прямое требование эпика — реальный проект печати это несколько
  частей/STL; пере-решать придётся при первом же мульти-парт проекте, т.е. скоро.
- **B. Одна сущность, мульти-модель на уровне файлов — ПРИНЯТО:** карточка («проект») =
  строка `models`; N 3D-артефактов = N строк `model_files` c `role='source'`; статус
  конвертации и связка preview/thumbnail — **per-file**; `models.status`/`source_format`
  перестают быть per-артефакт (агрегат карточки или ретирование — решает Data); схема
  ключей S3 получает файловую компоненту; очередь mesh-воркера переезжает с
  `models.status` на файлы.
  *За:* закрывает MF-9 целиком; не создаёт второй сущности; консистентен с принятым
  «мульти-артефактность на уровне файлов»; сохраняет план переименования и одну витрину.
  *Против:* трогает конвейер mesh и требует per-file DDL — цена одной миграции и правки
  воркера, платится один раз.

## 4. Решение (обязательное для фаз 1–3)

Принят **вариант B**. Следствия для контракта:

1. `project_*`-таблиц не существует ни в каком виде. API-неймспейс остаётся `/models`
   (публичные пути не переименовываем — см. migration-plan §4). UI-термин MVP — «модель»
   (`docs/design/projects.md` §1, решение за Валерием по триггеру второго ремесла).
2. **Контракт `GET /models/:id` — списочный по 3D-артефактам с первого дня:** массив
   объектов `{file_id, source_format, статус конвертации, preview/thumbnail}` + файлы по
   ролям (`aux`, `description_image`). Даже если первая поставка ограничит N=1, форма
   ответа — список: фронт (фаза 3) не переделывается при снятии ограничения.
3. Статус конвертации — per-file. Черновик/публикация — отдельное поле публикации на
   `models`, с конвейерным статусом не смешивать (уже зафиксировано в MF-340).
4. Зоны: точный DDL (где живёт per-file статус, судьба `models.status`/`source_format`/`bbox`,
   ключи S3, очередь воркера) — вердикт **Data**; декомпозиция и порядок шагов, в т.ч.
   допустимость cap N=1 в первой поставке с отдельным шагом «мульти-модель», — **Lead**.

## 5. Критерии приёмки (моя приёмка эпика MF-9)

- Критерии «Готово когда» фаз MF-339..341 выполнены.
- `project_*`-таблиц не заведено; контракт карточки — списочный (п.4.2).
- Конвейерный статус и авторская публикация разведены.

## 6. Условия пересмотра

Вернуться к контейнеру (**поверх** `models`, не вместо) — только если понадобится композиция
ЧЕРЕЗ публикации: «проект» агрегирует самостоятельно живущие артефакты с отдельными
жизненными циклами (репозиторий GitVerse + несколько независимо опубликованных карточек).
Триггеры: второе живое ремесло с реальными смешанными проектами, либо явное продуктовое
решение Валерия. Переименование `models`→`projects` — строго по триггерам migration-plan.
