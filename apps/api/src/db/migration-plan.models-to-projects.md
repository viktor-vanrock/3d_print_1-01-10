# План миграции `models` → `projects` (документ, выполнение отложено)

**Статус:** план, не выполнять сейчас. Заведён по MF-482 / `docs/epics/projects.foundation.md` §2, п.1:
«Проект = эволюция `models`, не новая супер-сущность... Переименование `models` → `projects`
в БД — НЕ сейчас (принцип `domain.model.md` "не переименовывать до второго ремесла")».

Этот документ фиксирует, чем триггерится переименование, что оно ломает и как катить его
без даунтайма, — чтобы решение принималось не с нуля, когда придёт время.

## 1. Когда триггерить

Все три условия должны быть выполнены одновременно (решает Валерий/Architect, не DB-агент):

1. **Второе живое ремесло с реальными данными** — не просто `craft` в check-констрейнте
   (это уже есть, MF-482), а реальные строки `models` с `craft != '3d_printing'` от живых
   пользователей. До этого «Проект» = «модель для 3D-печати», переименование бессмысленно.
2. **Терминология UI подтверждена** — `docs/design/projects.md` (стадия 1 MF-480, Systems designer)
   даёт рекомендацию «Модели» vs «Проекты», Architect/Валерий утверждают. Открытый вопрос
   в `docs/epics/projects.foundation.md` §6.1: дефолт — после появления второго ремесла, т.е.
   совпадает с условием 1.
3. **Решён вопрос «один раздел или два»** (§6.2 того же эпика) — если «Проекты» окажутся
   отдельным разделом рядом с магазином, а не тем же самым, переименование таблицы вообще
   может не понадобиться (два UI-раздела над одной таблицей — обычная вещь), и весь план
   ниже становится неактуальным. Проверить это решение первым, до старта миграции.

## 2. Что ломается (объём изменений)

БД — единственный источник схемы, которым владеет `apps/api` (никто, кроме него, в Postgres
не пишет, см. `docs/architecture/readme.md` — `mesh`/`giga` только через API). Значит, ломается не
межсервисный контракт, а **внутренняя связность одного сервиса**: SQL в `schema.ts`, запросы
в `apps/api/src/models/*`, и, отдельным решением, публичные API-роуты.

| Объект | Было | Станет | Замечание |
|---|---|---|---|
| Таблица | `models` | `projects` | `ALTER TABLE ... RENAME TO` — метаданная операция, без переписи таблицы, без блокировки на чтение/запись дольше, чем доля секунды, независимо от объёма данных |
| Таблица | `model_files` | `project_files` | то же |
| Колонка | `model_files.model_id` | `project_files.project_id` | `ALTER TABLE ... RENAME COLUMN` — тоже метаданная операция |
| Таблица | `model_tags` | `project_tags` | + колонка `model_id` → `project_id` |
| Таблица | `model_votes` | `project_votes` | + колонка `model_id` → `project_id` |
| Индексы | `models_owner_idx`, `models_status_pending_idx`, `models_created_at_idx`, `models_popularity_idx`, `model_files_model_idx`, `model_tags_tag_idx` | переименовать в `projects_*`/`project_*` | косметика, не блокирует функциональность — можно сделать отдельным шагом после переименования таблиц, не обязательно синхронно |
| Ограничения (constraint names) | `models_source_format_check`, `model_files_role_check`, ... | автопереименовываются вместе с таблицей (Postgres переносит `tablename_check`-имена при `RENAME TO`, если имя не задано явно — те, что заведены явным `ADD CONSTRAINT <name>` как в MF-482, потребуют отдельного `RENAME CONSTRAINT`) | проверить по факту на момент миграции |
| Код | `apps/api/src/db/schema.ts`, `apps/api/src/models/*.ts` (upload/list/detail/asset) | переименовать таблицы/колонки во всех SQL-запросах | зона TypeScript-агента, не DB — координировать, не выполнять со стороны DB в одиночку |
| API-роуты | `POST /models`, `GET /models`, `GET /models/:id` | решение НЕ принято — переименование путей ломает существующие ссылки (SEO каталога, возможные внешние закладки на `3mf.tech/models/:id`) | отдельный вопрос от Architect/Валерия, шире, чем DB-миграция; можно оставить `/models` как публичный путь даже после переименования таблицы в БД — синхронизация не обязательна |

## 3. Как катить без даунтайма

Схема — за одним сервисом (`apps/api`), Postgres — за одним VDS (`ru-4gb-16018`,
`docs/infra/readme.md`), в проде — единственный инстанс API (не multi-instance rolling deploy на
момент написания). Это упрощает план: не нужен classic expand/contract с
compatibility-view на две версии кода одновременно, но nужно жёсткое совпадение по
времени между накаткой миграции и деплоем новой версии кода — они не могут быть
рассинхронизированы дольше, чем время одного запроса (иначе живой процесс упадёт на
запросах к переименованным таблицам).

1. **Подготовка (без риска, за любое время до окна):**
   - Подготовить новую версию `schema.ts`/`apps/api/src/models/*` с новыми именами —
     PR готов и провалидирован (тесты, staging/локальная БД), но не смёржен/не задеплоен.
   - Подготовить SQL-скрипт переименования отдельно от `SCHEMA_SQL` (не как часть
     идемпотентного DDL — переименование не должно повторяться при каждом рестарте
     сервера; выполнить один раз вручную или разовым скриптом, см. `issues/007` — вопрос
     инструмента миграций всё ещё открыт, к моменту этой миграции решить его).
2. **Окно миграции (короткое, секунды — переименования не переписывают таблицу):**
   - Остановить `apps/api` (или перевести в maintenance-режим, если к тому моменту есть
     health-check/балансировщик перед ним).
   - Выполнить SQL переименования (таблицы → колонки → индексы → явные constraint-имена).
   - Задеплоить новую версию `apps/api`, которая уже ссылается на `projects`/`project_files`.
   - Поднять сервис, проверить smoke (создание/чтение проекта, аплоад файла).
3. **Откат** — пока новый код ещё не принял живой трафик, откат дешёвый: `RENAME TO`
   в обратную сторону + поднять предыдущую версию `apps/api`. После того как новая
   версия отработала на реальных данных (новые строки/файлы уже пишутся под новыми
   именами), откат эквивалентен по стоимости прямой миграции — нельзя просто вернуть
   старые имена, если в `projects` уже успели попасть строки, которых не было в момент
   бэкапа `models`.
4. **После миграции (не обязательно синхронно с п.2):**
   - Переименовать индексы (`projects_owner_idx` и т.д.) — косметика, отдельным PR.
   - Обновить `docs/epics/domain.model.md`/`docs/epics/3mf.storage.md`/`docs/issues/007.database.design.md`
     — исторические DDL-примеры в них перестанут совпадать с live-схемой, пометить как
     «исторический снимок на момент MF-336/462», не переписывать задним числом.

## 4. Явно не в этом плане

- Переименование API-путей (`/models` → `/projects`) — отдельное решение Architect/Валерия,
  может не понадобиться вовсе (см. §1, условие 3).
- Переименование `user_printers` → `user_machines` — отдельный триггер (второй вид станка,
  не второй craft), см. `docs/epics/domain.model.md` «Чего не делать сейчас».
- Сам инструмент миграций — если к моменту триггера `docs/issues/007.database.design.md` всё
  ещё не решён, выбор инструмента для этой конкретной миграции решать заранее, не в разгар
  окна простоя.
