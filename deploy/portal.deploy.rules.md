# Правила prod-каталога `/home/plag/portal.ru`

Документ фиксирует инварианты, нарушение которых может заморозить прод
(инцидент MF-543 → профилактика MF-545).

## Один писатель

`/home/plag/portal.ru` принадлежит **исключительно** таймеру `portal.deploy.timer`.
Никакой другой процесс, агент или человек не выполняет `git checkout`, `git switch`,
`git reset`, `git pull` и любые другие команды, меняющие рабочее дерево или
указатель ветки в этом каталоге.

**Правило**: агентские ветки и worktree создаются ТОЛЬКО в отдельном каталоге.
Для разработки уже есть `/home/plag/portal.ru-dev` (ветка `dev`) — использовать его.
Создавать новые рабочие копии можно в любом другом месте (`~/portal.ru-<имя>`),
но не в `~/portal.ru`.

**Почему**: `portal.deploy.sh` требует, чтобы рабочая копия была на ветке `main`.
Переключение на другую ветку (или detached HEAD при `git checkout <tag>`) блокирует
каждый последующий тик таймера до ручного вмешательства Ops. При таймере 1 тик/мин
и неотловленной ошибке прод остаётся на старой версии бессрочно.

## Что делает `portal.deploy.sh` при нарушении (MF-545)

Скрипт реализует **самовосстановление**:

1. При старте проверяет `git branch --show-current`.
2. Если ветка не `main` — логирует WARNING в journalctl и принудительно делает
   `git checkout -f main`.
3. Затем приводит к `origin/main` через `git reset --hard origin/main` вместо
   прежнего `git pull --ff-only` — переживает diverged-состояние.

Это страховка, а не разрешение нарушения правила. При срабатывании guard'а
нарушение должно быть расследовано по journalctl:

```bash
journalctl -u portal.deploy --since "1 hour ago" | grep WARN
```

## Алерт на залипание (MF-545)

Если `portal.deploy.sh` падает **3 и более тиков подряд**:

- КРИТИЧЕСКОЕ событие записывается в journalctl (уровень `err`, тег `portal.deploy`).
- Уведомление отправляется в Telegram-мост (`/home/plag/tg-bridge/queue`).

Ops реагирует немедленно (`journalctl -u portal.deploy -f`, `systemctl status portal.deploy`).
Прод заморожен на версии до первого сбоя — откат не нужен, новые коммиты просто не катятся.

Сбросить счётчик можно вручную: `rm /tmp/portal.deploy.fail_count`
(после устранения причины; следующий успешный тик тоже сбрасывает его автоматически).

## Ветка `main` залочена чужим worktree (MF-942)

Отдельный от «чужая ветка в `~/portal.ru`» failure mode: guard делает
`git checkout -f main`, но это падает с `fatal: 'main' is already used by
worktree at '<путь>'`, если ветку `main` в этот момент держит ДРУГОЙ git
worktree — например, task-workdir агентской сессии, которая уже завершилась,
но её worktree не был вычищен (`git worktree remove`) вовремя.

Self-heal-гард это не чинит сам (`checkout -f` не снимает чужой lock), таймер
падает каждый тик, пока лок не освободится. Разрешается это либо (а) отложенным
cleanup-проходом платформы Multica по завершённым task-workdir'ам (наблюдалось
в MF-942 — лок снялся сам между тиками, без ручного вмешательства), либо
(б) вручную: убедиться, что worktree осиротел (сессия завершена, нет живого
процесса с cwd в этом каталоге, `.gc_meta.json` показывает `completed_at`
в прошлом), и снять лок через `git worktree remove --force <путь>` из
`~/portal.ru`. НЕ трогать `~/portal.ru` руками в обход таймера (см. «Один
писатель» выше) — освобождать сторонний worktree можно, сам `~/portal.ru`
только читать (`git worktree list`, `git reflog`) для диагностики.

## CD-заглушки в `.gitverse/workflows/`

`release.yaml` (job `deploy-staging`) и `deploy.yaml` (job `deploy`) **не трогают**
`~/portal.ru`. Git-операции (`git checkout`, `git fetch --tags`) удалены из обоих
stub-job'ов в рамках MF-545. Раннер с меткой `deploy` не зарегистрирован — job'ы
всё равно не исполняются, но код-мина снята.

Когда появится реальный staging-контур — реальные шаги деплоя добавляются в эти job'ы
**без** `cd ~/portal.ru`: для staging нужна отдельная рабочая копия, не прод-каталог.
