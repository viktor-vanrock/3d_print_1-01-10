# MF-1335: dev-чеклист восстановления после сорванного enroll

Короткий runbook для `managed-bridge`/`custom` в dev. Основание: [printer.server.md §2.3](../architecture/printer.server.md#23-enroll--identity), [printer.support.md § «Контракт кода и credential»](../epics/printer.support.md#контракт-кода-и-credential-mf-1214) и [printer.wizard.md §4.1](../design/printer.wizard.md#41-credential-отклонён-или-отозван-безопасное-восстановление-mf-1294-d).

## Граница воздействия

- Только dev, тестовые `JWT_SECRET` и `AGENT_JWT_SECRET`; production, реальные credentials и физический принтер не используются.
- Сценарий не вызывает `start`, `pause`, `resume`, `cancel`, G-code, upload или firmware reset. До подтверждённого live-сигнала устройство остаётся `offline`, команды disabled.
- Код и credential не копируются в логи, комментарии, URL, `localStorage` или артефакты. В evidence допустимы только HTTP-статус, безопасный `error`, `device_id`/`agent_id` в обезличенном виде, claims без токена и наличие audit-записи.

## Воспроизводимый прогон

1. В dev выдать одноразовый код: `POST /me/devices/enroll-codes` → `201`; сохранить только локальный признак «код выдан» и `expires_at` (не сам код). Убедиться, что срок не больше 15 минут.
2. Начать обмен `POST /devices/agent/enroll` и оборвать его до успешного ответа. Зафиксировать статус/безопасный код ошибки и отсутствие live-сигнала. Не повторять старый credential.
3. Проверить состояние через API/БД: нет частично созданной связки, plaintext-кода, credential или токена в ответах/логах; audit содержит только безопасные поля. Если обмен атомарно завершился — использовать созданный `device_id`, иначе начать новый код.
4. Для истёкшего, повторно использованного или конкурентно повторённого кода ожидать `401 {"error":"invalid_or_expired_code"}`. Повтор не должен создавать второе устройство или сжигать новый код.
5. Для `invalid_token`/`unknown_agent`/`revoked` оставить устройство `offline`; UI показывает «Связь с агентом отклонена»/«Доступ агента отозван» и единственный владелецский CTA «Подключить заново».
6. Выпустить новый код и выполнить новый обмен. После подтверждённого `connect` и live heartbeat проверить, что сохранён тот же `user_printer.id`, статус стал live, а команды разблокировались только после этого сигнала.
7. При необходимости проверить отзыв: `POST /me/devices/:deviceId/revoke` → `200 {"ok":true}`, повторный revoke → `409 already_revoked`; следующий `session/open` со старым credential → `401 revoked`. Значение credential не выводить.

## Матрица ожидаемых результатов

| Сценарий | Ожидаемый результат | Запрещено считать успехом |
|---|---|---|
| свежий код | enroll `201`, одна agent/device/audit-связка | код или JWT в evidence |
| обрыв/ошибка подписи | транзакция откатана; код не становится частично использованным | ручная запись credentials или повтор старого JWT |
| timeout/повтор/replay | `401 invalid_or_expired_code`, новых связок нет | `200`, второе устройство или раскрытие причины внутреннего сбоя |
| отозванный credential | следующий connect `401 revoked`, устройство `offline` | мгновенное утверждение live по открытому WS |
| новый обмен | тот же парк/`user_printer.id`, live только после heartbeat | запуск печати, upload или прошивки |

## Evidence-шаблон

Заполнять после dev-прогона, без секретных значений: дата и commit; endpoint + статус; безопасный `error`; количество созданных связок до/после; наличие audit; проверка логов на `code`, `Bearer`, JWT и credential; итоговый Fleet-статус. Если соседние проверки не приложили evidence, это фиксируется как незаполненный внешний вход, а не подменяется предположением.
