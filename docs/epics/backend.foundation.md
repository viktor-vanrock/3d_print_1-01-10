## Решения CTO

### 1. Go в стек не входит

Оператор упомянул Go. Вердикт: **в v1 (и до явного нового факта) Go не вводим.** Стек зафиксирован `docs/architecture/readme.md`: TypeScript/Fastify (публичный API, владелец схемы) + Python (гео-обработка, ИИ, воркеры). Все разрывы v1 закрываются этими двумя.

- Варианты: (а) Go-сервис под парсеры/нагрузку — отклонено: третий рантайм = третий CI-контур, третий деплой-юнит, ни одной задачи v1, где Go даёт решающее преимущество; (б) статус-кво — принято.
- Что нас переубедит: профилирование покажет, что Node-API упирается в CPU на телеметрии сотен тысяч устройств — это территория v3 (привязка живых принтеров), не v1.

### 2. Миграции: dbmate, идемпотентный DDL замораживается

Ключевой техдолг слоя данных (`docs/issues/007.database.design.md`): схема живёт идемпотентным `SCHEMA_SQL` в `apps/api/src/db/schema.ts:1`, применяется на старте сервера, — это ломается на первом же деструктивном изменении (rename/drop/split), не даёт порядка, отката и истории.

Вердикт: **плоские SQL-миграции через dbmate** (дефолт; Data вправе переубедить фактами в своём вердикте — тогда решение фиксируется там же).

- Почему dbmate, а не node-pg-migrate/drizzle: единственный бинарь без рантайм-зависимостей; чистый SQL — в культуре проекта (ORM нет, `pg`/`psycopg` напрямую); язык-агностичен — Python-сервисы (mesh/giga, будущий scout) читают ту же схему, JS-DSL им чужой; `db/schema.sql`-дамп даёт ревьюируемый снапшот.
- Переход: `SCHEMA_SQL` замораживается как baseline-миграция `0001_baseline.sql`; `migrate()` в `apps/api/src/db/client.ts` живёт один релиз для совместимости, затем сервер перестаёт трогать DDL; `deploy/portal.deploy.sh` получает шаг миграции ДО рестарта api. Новые таблицы этого эпика — уже только миграциями.
- Что нас переубедит: если Data покажет, что бинарь dbmate неустановим/неподдерживаем на VDS — fallback node-pg-migrate (запуск из api-пакета, тоже plain SQL).

### 3. Парсер-контур: новый Python-сервис `apps/scout`

Флагман v1 — «агенты парсят интернет, добавляют новые принтеры с характеристиками и датой выхода» (`docs/product/roadmap.md` MF-32). Схема под это задеплоена 2026-07-06 (`machine_candidates`, `release_events`, провенанс в `machines.field_provenance`), но сам контур не существует: кандидатов никто не пишет, канон никто не пополняет, календарь пуст.

Вердикт: **четвёртое приложение `apps/scout`** — Python 3.12, uv, по образу mesh/giga: FastAPI `/health` (внутренний, без публичного порта) + воркер-поллер (Postgres `SKIP LOCKED`) + systemd-юнит + таймер расписания.

- Границы записи: scout пишет в staging (`machine_candidates`, будущий `material_candidates`) и в `release_events`; промоушен в канон `machines` — резолвер-стадия того же воркера по конвейеру blocking→matching→merge из `domain.model.md` § MF-32: `confidence ≥ порога` — авто-merge с записью провенанса, ниже — `status='pending'` на ручной аппрув.
- Источники фазы 1: официальные страницы вендоров (whitelist в конфиге, уважение robots.txt), открытые данные слайсер-профилей (Orca/Prusa — бутстрап ≥300 моделей), SpoolmanDB для филамента. Скрейпинг соц-сетей/маркетплейсов — вне v1.
- Метрика (из `docs/product/vision.md`): свежесть — дни от анонса производителя до карточки; считается из `release_events.announced_at` против `machines.created_at`, отдельная таблица под метрику не нужна.
- Варианты: (а) кроны внутри api (Node) — отклонено: экосистема скрейпинга/парсинга в Python сильнее, и падение парсера не должно жить в одном процессе с публичным API; (б) расширить giga — отклонено: giga = ИИ-слой, парсеры не должны зависеть от GigaChat и его квот; (в) отдельный сервис — принято.
- Что нас переубедит: если к концу фазы 1 окажется, что 90% данных приходит из структурированных каталогов (не HTML), контур можно упростить до пары CLI-скриптов на таймере — сервисная обвязка не догма.

### 4. Каталожный API живёт в `apps/api`

Таблицы каталога есть — эндпоинтов нет ни одного: роутеры покрывают только auth/profile/models/tags. Витрине v1 (каталоги принтеров и филаментов, карточки, календарь новинок — MF-11, MF-31, MF-32) читать нечем.

Вердикт: публичные read-эндпоинты в `apps/api` (владелец схемы, единственная публичная поверхность — по архитектуре): `GET /machines` (фильтры: vendor/kind/integration/q + пагинация), `GET /machines/:id`, `GET /vendors`, `GET /materials` (+ `:id`, фильтры vendor/type/kind), `GET /releases` (календарный фид: диапазон дат, статус). Плюс ЛК: «мои филаменты» из roadmap — таблица `user_materials` (user_id, material_id, variant_id nullable, note; имя без «filament» — ядро не знает про 3D-печать) и `POST/DELETE /me/materials` по образцу `/me/printers` (`apps/api/src/profile/activation.ts`). Write-эндпоинтов каталога в v1 нет — канон пишет только scout и ручная модерация.

### 5. Комьюнити-фундамент: полиморфные `comments`, `forum_topics`, карма-леджер

v1 требует обсуждения проектов (MF-464) и форума-лайт (MF-35); vision требует «репутационное ядро в фундаменте форума, а не прикручивается потом». Сегодня в схеме нет ни комментариев, ни форума, ни кармы.

Вердикт, форма (точный DDL — вердикт Data):
- **`comments`** — одна таблица на все обсуждения, полиморфная пара `(subject_type, subject_id)` с check `subject_type in ('model','forum_topic')` (принцип 4 `domain.model.md`), `parent_id` self-FK под ветвление, `status` (active/hidden/deleted), денорм `comments_count` на предмете.
- **`forum_topics`** — лайт, без `communities` (те — v2): id, author_id, title, body, status, счётчики. Тема = предмет комментариев, отдельной таблицы постов нет.
- **`karma_events`** — append-only леджер: user_id (кому), actor_id, delta, reason (text+check), source полиморфно. Формула агрегации кармы — сознательно НЕ сейчас (открытый вопрос `domain.model.md`); v1 пишет события и показывает сырую сумму. Леджер с первого дня — чтобы историю не пришлось реконструировать.
- Существующая `idea_comments` (`ideas.page.md`) не трогается; унификация — осознанный будущий рефакторинг, не блокер.
- Что нас переубедит: если Design-спека форума потребует сущностей сверх «тема+ветка комментариев» (разделы, теги тем) — расширяем справочником, не переделкой ядра.

### 6. Хвосты, включаемые в эпик (решения уже есть, нет исполнения)

- **Почта.** `email_otp` работает, но код пишет OTP в лог (`apps/api/src/auth/email.ts`), провайдер не подключён. Ops выбирает/заводит SMTP по `docs/infra/email.md`, Back подключает транспорт (nodemailer уже в зависимостях). Без этого вход по email — фикция.
- **Приём файлов.** Долг Back по `formats.policy.md`: `apps/api/src/models/upload.ts` доверяет расширению — нужны magic-байты, decompression-защита, таксономия ошибок (MF-375/MF-501). Это фундамент безопасности загрузки, тянем в эпик.
- **Мульти-меш.** DDL `model_meshes` ждёт вердикта Data (MF-339, `projects.foundation.md` § 2.7) — закрыть вердиктом в рамках данных этого эпика (реализация — по своей дорожке проектов).
- **FK `user_printers.printer_id`** — `VALIDATE CONSTRAINT` после проверки Ops (протокол уже описан в `domain.model.md`).
