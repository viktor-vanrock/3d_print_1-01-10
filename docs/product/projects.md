# Проект: публичный результат и личная сборка

Этот документ фиксирует продуктовый канон сущности «Проект» и дополняет
[vision.md](vision.md), [philosophy.md](philosophy.md) и
[roadmap.md](roadmap.md). Дизайн публичной страницы развивается в
[../design/projects.md](../design/projects.md), существующий гайд сборки — в
[../design/assembly.guide.md](../design/assembly.guide.md), git-субстрат — в
[../epics/project.git.md](../epics/project.git.md), а единый переносимый язык
проекта и сценарии Git/STL/3MF — в
[project.as.code.md](project.as.code.md).

## Тезис: один проект, два уровня

Проект — не карточка файла и не одноразовый чек-лист. У него два связанных,
но принципиально разных уровня:

1. **Публичный project landing** отвечает на вопрос «что это, получится ли у
   меня и какой вариант выбрать?». Это каноническое, индексируемое и
   распространяемое знание о результате.
2. **Личная build session** отвечает на вопрос «что мне делать следующим,
   чтобы собрать выбранный вариант?». Это приватное, изменяемое состояние
   конкретного пользователя после выбора конфигурации.

Оба уровня используют один проект и одни исходные артефакты, но не смешивают
ответственность. Публичная страница не превращается в персональную панель
прогресса, а личные отметки не меняют проект автора.

### Публичный проект должен воспроизводиться из Git

Полноценный проект — это не набор данных, который существует только внутри
форм портала. Его структура, конфигурации, детали, соединения, сборочные сцены
и шаги описываются в версионируемом `portal.project.yaml` рядом с исходниками.
Веб-редактор является визуальным способом менять тот же документ и обязан
сохранять смысловой round-trip: изменения из Git видны в редакторе, изменения
из редактора возвращаются в Git обычным коммитом.

Для простой публикации это не добавляет обязательной ручной работы:

- пачка STL автоматически становится минимальным print-only проектом;
- 3MF сохраняет объекты, единицы и трансформации и становится
  многодетальным print-only проектом;
- Git-репозиторий с манифестом открывает конфигурации, BOM, код, электронику,
  сборочные сцены и полную build session.

Лендинг адаптируется к фактической сложности, а не к способу загрузки:
простая модель не получает пустые блоки «Код» и «Пайка», сложная робототехника
не сплющивается до карточки одного STL.

## 1. Публичный project landing

Публичная страница должна позволить принять осознанное решение до начала
сборки. На ней показываются:

- **результат:** что получится, для чего это нужно, фото, видео, 3D-превью,
  автор, лицензия, версия и происхождение/форк;
- **конфигурации:** реальные варианты результата и различия между ними,
  рекомендуемый вариант и основания рекомендации;
- **требования:** время, уровень навыка, станки и принтеры, инструменты,
  материалы, компоненты, код/прошивка и требования безопасности;
- **совместимость:** с каким принтером, материалом, платой, прошивкой или
  станком вариант проверен; неизвестное показывается как неизвестное, а не
  как молчаливое «подходит»;
- **состав проекта:** BOM, инструкция, исходники, файлы для производства,
  код и репозиторий, история изменений;
- **опыт сообщества:** Makes, отзывы, обсуждения и посты связанного саба.

Главное действие — **«Собрать»**. Оно сначала открывает выбор конфигурации и
показывает итоговый набор требований. Читать проект и сравнивать
конфигурации можно без входа; создать сохраняемую build session можно после
авторизации.

### Конфигурация — явная версия способа сборки

Конфигурация — не фильтр UI и не произвольный набор галочек. Это
версионируемый вариант проекта, который связывает:

- ожидаемый результат;
- совместимые машины, материалы, платы и прошивки;
- конкретные артефакты и BOM;
- требования и предупреждения;
- шаблон фаз и шагов сборки.

Например, один проект может иметь конфигурации «PLA + Ender-3», «ABS +
закрытая камера» и «плата v2 + прошивка 1.4». Начатая сборка фиксирует
ревизию проекта и ревизию конфигурации. Обновление проекта не должно молча
менять инструкции под руками: переход на новую ревизию — отдельное
осознанное действие.

## 2. Личная build session

Build session создаётся после выбора конфигурации и принадлежит пользователю.
По умолчанию она приватна, возобновляется на другом устройстве и хранит
фактический путь сборки, а не только позицию чтения инструкции.

Полный словарь фаз фиксируется сразу:

1. `print` — подготовить и изготовить печатные детали;
2. `assembly` — собрать механическую часть;
3. `flash` — загрузить код или прошивку;
4. `solder` — собрать электрическую часть;
5. `check` — проверить результат и безопасность.

Проект показывает только применимые фазы. Отсутствующая фаза не рисуется
дизейбленной. Фазы и шаги могут иметь зависимости: модель данных не должна
сводить любой проект к одному жёсткому линейному списку, даже если первый UI
показывает простой последовательный маршрут.

### Что видит и делает пользователь

Build session в каждый момент должна отвечать на три вопроса: **где я,
почему не могу идти дальше и какое одно действие сейчас главное**.

Для текущего шага показываются инструкция, необходимые входы, зависимости,
предупреждения и ожидаемый результат. Возможные действия:

- открыть или скачать нужный файл;
- подготовить/запустить печать, а позже — отправить задание на устройство;
- выполнить сборку, прошивку, пайку или проверку;
- отметить действие выполненным, повторить его или пропустить, если это
  разрешено конфигурацией;
- приложить заметку, фото или измерение;
- зафиксировать проблему и причину блокировки;
- поставить сборку на паузу, продолжить или завершить без результата.

Минимальный словарь состояний шага:
`not_started`, `ready`, `in_progress`, `blocked`, `done`, `skipped`,
`failed`. Процент и состояние фазы вычисляются из шагов и обязательных
зависимостей, а не хранятся вторым изменяемым счётчиком. `blocked` всегда
имеет понятную причину и следующий путь выхода.

Публичный просмотр гайда может помнить только позицию чтения. Это не build
session, не доказательство выполненного шага и не основание считать проект
собранным.

## 3. Завершение: Make, отзыв, пост и профиль

Когда все обязательные фазы завершены, build session предлагает оформить
результат:

1. создать **Make** с фотографиями, фактической конфигурацией и отклонениями
   от инструкции;
2. оставить отдельный отзыв: получилось ли, что было сложно, что следует
   исправить;
3. опубликовать пост в связанном сабе/ленте или сохранить результат
   приватным;
4. добавить проект в раздел профиля **«Собрано»**.

«Собрано» не смешивается с «Мои проекты»: первое — подтверждённый путь
билдера, второе — авторство/владение проектом. Публикация не должна быть
принудительной. Make, отзыв и пост — связанные, но отдельные сущности:
пользователь может сделать только Make, Make + отзыв, либо ещё и пост.

Публичный Make ссылается на проект, ревизию конфигурации и фактически
использованные материалы/оборудование. Он пополняет доказательную базу
совместимости, но не переписывает авторские требования автоматически.

## 4. Данные и API: принципы

Физические имена таблиц и маршрутов фиксируются профильными контрактами;
этот документ задаёт границы сущностей.

- **Project/revision** — публичный канон результата и git-ревизия
  артефактов. Существующий индекс `models` может оставаться индексом проекта;
  новая параллельная супер-сущность ради названия не нужна.
- **Configuration/revision** — версионируемый набор требований,
  совместимости, артефактов, BOM и шаблона фаз.
- **Phase/step template** — авторская инструкция, не пользовательский
  прогресс.
- **Build session + step state** — приватный снимок выбранных ревизий,
  состояние действий, заметки и evidence конкретного пользователя.
- **Make/review/post** — явно опубликованные результаты и социальные
  проекции завершённой сборки.

Обязательные свойства контрактов:

1. **API-first.** Публичный landing, конфигурации, создание/чтение session,
   изменение шага, завершение и публикация доступны через версионированный
   API; web — его первый клиент, а не привилегированный обход.
2. **Раздельные read/command-контракты.** Публичный landing можно кэшировать
   как проекцию; команды session требуют авторизации владельца.
3. **Revision pinning.** Session хранит точные ревизии проекта и
   конфигурации. Миграция на новый вариант явная и проверяет совместимость
   уже выполненных шагов.
4. **Идемпотентность и конкуренция.** Создание session, завершение и
   публикация принимают idempotency key; изменение шага защищено версией
   состояния/optimistic concurrency.
5. **Одна истина прогресса.** Итоговый статус и процент выводятся из
   обязательных шагов. Отдельные счётчики не могут расходиться с ними.
6. **Совместимость как claim.** У утверждения есть источник: автор,
   производитель, подтверждённый Make, агент или вычисление, а также степень
   доверия. `unknown` — допустимое и видимое состояние.
7. **Приватность по умолчанию.** Заметки, незавершённые фото и проблемы
   session закрыты. В публичный слой данные попадают только явной командой
   публикации.
8. **Артефакты не дублируются.** Исходники и история остаются в git,
   производные превью — в объектном хранилище, операционное состояние — в
   БД. Session ссылается на стабильные id и хэши, а не копирует файлы.

Минимальная поверхность API концептуально состоит из публичного чтения
landing/configurations и команд `create session`, `apply step action`,
`complete session`, `publish Make/review/post`. Конкретные URL и payload
утверждаются отдельным API-контрактом до реализации UI.

## 5. Поставка: MVP и будущее

Полная модель фиксируется сейчас, но поставляется по roadmap, без скрытого
перетаскивания V3 в v1.

| Версия поставки | Что входит |
|---|---|
| **v1** | Публичный landing проекта: результат, файлы/git-история, один default-вариант или простые конфигурации, структурированные требования и честная совместимость, публичный гайд. Закладываются стабильные id/revision и API-границы. Полноценная личная session, Make и соцпубликация не являются критерием v1. |
| **v2** | Личная build session для печатных проектов: сохранение прогресса, ручные действия фаз `print`/`assembly`/`check`, возобновление, ассистент сборки. Завершение создаёт Make/отзыв и запись «Собрано» в профиле. |
| **v3** | Публикация результата в саб/соцленту и петля обсуждения, рекомендации на базе Makes, более богатые роли и доступы. |
| **v4–v5 / эпоха V3** | Полная мультистаночная модель: применимые `flash`/`solder`, ЧПУ/лазер/электроника, действия на подключённых устройствах, код и GitVerse, совместная разработка и ветвящиеся конфигурации. |

Фазовый словарь, revision pinning и разделение публичного/личного должны
появиться в контрактах до богатого UI. Иначе быстрый линейный чек-лист станет
второй моделью проекта, которую придётся ломать при переходе к робо-руке.

## 6. Связь автора и потребителя

У проекта три связанные, но разные поверхности:

1. **Author Studio** — рабочая версия, конфигурации, BOM, шаги, история и
   релизы. Это поверхность автора и соавторов.
2. **Public landing** — результат, реальные Makes, варианты, совместимость,
   ожидаемая стоимость/сложность и выбор «Хочу сделать».
3. **Build session** — личный прогресс потребителя, закупки, команды
   подключённым устройствам, evidence и финальная публикация.

Author Studio публикует не страницу как набор вручную расставленных блоков,
а ревизию project graph. Landing и session — две проекции одной ревизии.
Поэтому изменение модели или кода может пройти обычный branch/review/release
цикл, а пользователь, который уже собирает старую версию, не оказывается
посреди другой инструкции.

Для SO‑ARM100 целевой happy path автора:

```text
GitHub main@SHA
  → разбор STL + STEP + BOM + Simulation + README
  → конфигурации follower / leader+follower
  → комплект печати, покупок и инструментов
  → print → assembly → flash → check
  → рабочий commit в portal/dev
  → release/tag
  → public landing
  → новая build session пользователя
```

Покупные позиции описываются требованиями и каталогом, а не одной ссылкой
на магазин. Portal может показать аналоги на российских маркетплейсах и
проверить их характеристики; автор подтверждает соответствие. Цена и
наличие всегда имеют дату актуальности и не входят в immutable project
manifest как вечные свойства компонента.
