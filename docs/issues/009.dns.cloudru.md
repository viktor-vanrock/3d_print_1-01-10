# 009 · Передать NS `3mf.tech`/`api.3mf.tech` под управление cloud.ru + сертификат оттуда

**Статус:** done — **но не по своей причине**, см. ниже. NS-перенос можно не продолжать.
**Тип:** infra
**Создано:** 2026-07-03, закрыто 2026-07-03

## Что произошло по факту

Валерий запустил передачу NS `3mf.tech` на cloud.ru (2026-07-03), но **`dig NS 3mf.tech` в момент закрытия задачи всё ещё показывал NS Timeweb** — перенос не успел распространиться. При этом внешний HTTP/HTTPS к VDS **заработал сам** (проверено `curl` снаружи, независимо от VDS) — то есть причиной блокировки 80/443, описанной в `docs/issues/008.vds.runtime.md`, была, похоже, **не отсутствующая NS-делегация**, а сама security group в консоли cloud.ru — просто применение правила заняло дольше обычного (несколько часов/десятков минут между «✅ created» в панели и реальным эффектом на трафике).

Разгаданное «TCP handshake отвечает, хотя на ВМ никто не слушал» (наблюдалось раньше на порту 443) было, вероятно, тоже следствием неприменившегося ещё правила — как только security group реально заработала, эффект пропал.

## Итог

- **TLS выпущен обычным `certbot --nginx`** (Let's Encrypt, HTTP-01 challenge через порт 80) — не через панель cloud.ru, она не понадобилась.
- Перенос NS на cloud.ru можно смело отменить/остановить, если ещё не завершился — он не был необходим. Если уже завершится сам — ничего страшного, домен продолжит работать, просто через другой DNS-провайдер.
- `https://3mf.tech`/`https://api.3mf.tech` подтверждены снаружи 200, полный e2e-тест (email OTP → verify → сессия) прошёл по реальному HTTPS.

## Вывод на будущее

Записан в `docs/issues/008.vds.runtime.md` — если в будущем снова похожий симптом (правило в security group «есть», трафик не идёт) — сначала просто подождать (у cloud.ru применение правил не мгновенное), не бросаться искать скрытый L7-прокси/Anti-DDoS.
