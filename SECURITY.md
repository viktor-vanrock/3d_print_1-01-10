## Секреты

- **Ничего секретное не коммитится**: ключи S3 (`3mf`/`auth` бакеты, cloud.ru), токены GigaChat, `DATABASE_URL`, JWT-секреты и т.п. — только `.env` (в `.gitignore`) локально и на VDS, либо GitVerse Actions Secrets для CI (`Settings → Actions → Secrets`).
- Пример конфигурации — `.env.example` (корень репо, `apps/web/.env.example`) — имена переменных без значений.
- **Секреты авторизации (`apps/api`, добавлено 2026-07-03, см. `docs/epics/auth.triple.md` § «Модель данных»):** `JWT_SECRET` (сессия портала), `AUTH_HMAC_KEY` (слепой индекс идентификаторов), `AUTH_ENCRYPTION_KEY` (шифрование сырых claims в S3 `auth`, base64 32 байта), `PLAGID_EXTERNAL_TOKEN_SECRET` — **тот же секрет**, что `EXTERNAL_TOKEN_SECRET` у воркера `auth.plag.space` (`wrangler secret put EXTERNAL_TOKEN_SECRET` в `garage/auth`) — это общий секрет обмена между двумя системами, не совпадает ни с одним из остальных четырёх.
- **SMTP для email OTP (`apps/api/src/email/send.ts`, добавлено 2026-07-06):** `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`/`SMTP_FROM` — почтовый ящик на 3mf.tech через Timeweb (тот же хостинг, что держит MX домена). Без этих переменных код OTP просто пишется в лог (`journalctl -u portal.api.service`) — поведение по умолчанию для дев/теста, не падает.
- **SberID (`apps/api/src/auth/sberid.ts`, добавлено 2026-07-06, MF-356):** `SBERID_CLIENT_ID`/`SBERID_CLIENT_SECRET` — партнёрские креды Сбер ID, заводит Валерий (портал Сбер ID, оферта ЭДО, см. `docs/epics/auth.triple.md` § «Метод 3»). Пока не заданы — эндпоинты `/auth/sberid/*` отвечают `501` (сам OAuth2/OIDC-флоу ещё не реализован, наличие переменных в env пока не переключает поведение).
- Self-hosted раннер на VDS (см. `docs/architecture/readme.md`) имеет доступ к продовым секретам по факту размещения — деплой-джобы **не** триггерятся на `pull_request` от форков/непроверенных веток (только `push`/`workflow_dispatch` на `main`/теги), см. `.gitverse/workflows/deploy.yaml`.
- **Startup Superadmin (`apps/api/src/modules/auth`, обновлено 2026-09-26):** `ADMIN_USERNAME` + `ADMIN_PASSWORD` создают или безопасно связывают ровно один аккаунт с singleton marker. UUID генерируется один раз внутри locked transaction; после binding marker, а не username, является стабильной identity и не даёт runtime bypass. Existing installation связывается только при совпадении password credential и точного исторического grant provenance. Account, credential, marker, catalog grants и audit коммитятся одной транзакцией. Совпадающий password даёт no-op restart; изменённый password атомарно ротируется и инвалидирует browser sessions. Production-пароль — минимум 12 символов, development — 8.
- **Исторический Admin-allowlist (MF-511):** `ADMIN_USERNAMES` обслуживал удалённый `POST /models/:id/featured` и больше не является источником runtime-авторизации. Административный доступ определяется только permissions; legacy-флаг `users.is_staff` удалён.
- **GigaChat (`apps/giga`, добавлено 2026-07-09, MF-352):** `GIGACHAT_CREDENTIALS` — Authorization key (base64) из личного кабинета GigaChat API, используется ветками генерации (openscad/kzd/hueforge/trellis, `src/giga/gigachat_client.py`) для чат-запросов и встроенной генерации изображений. Не задан — конкретная генерация уходит в `status=error`, воркер и HTTP-часть не падают (тот же паттерн, что S3/DATABASE_URL выше).
- **ComfyUI/TRELLIS.2 (`apps/giga`, добавлено 2026-07-20, MF-2001):** `COMFYUI_URL` — адрес ComfyUI на HYPERPC (слот 3, порт 8188, `docs/process/hyperpc.local.llm.md`), используется только веткой `trellis` (`src/giga/branches/{trellis,comfyui_client}.py`) для сборки 3D-меша из GigaChat-референс-картинки. Не секрет по значению (Tailscale-only адрес, бесполезен вне тейлнета — см. правило про IP VDS ниже), но заводится тем же путём, что остальной конфиг — только `.env`/VDS/GitVerse Actions Secrets, не хардкодится. Не задан — конкретная генерация уходит в `status=error`, воркер не падает (тот же паттерн, что `GIGACHAT_CREDENTIALS`). `COMFYUI_TIMEOUT_SECONDS`/`COMFYUI_MAX_RETRIES`/`COMFYUI_RETRY_BACKOFF_SECONDS`/`COMFYUI_POLL_INTERVAL_SECONDS`/`COMFYUI_POLL_TIMEOUT_SECONDS`/`COMFYUI_EXPORT_TZ_OFFSET_HOURS` — опциональны, у всех рабочие дефолты в коде (последний — калиброванное живым smoke-test'ом смещение часового пояса машины HYPERPC от UTC, MSK/+3 на момент проверки, см. докстринг `comfyui_client.py`).
- **Лимиты/модерация генераций (`apps/api/src/generations/*`, добавлено 2026-07-09, MF-657):** `GENERATION_QUOTA_HOURLY`/`GENERATION_QUOTA_DAILY` — не секреты, per-user квоты на `POST /generations` (дефолт 10/час, 30/сутки, `contract.ts`). `GENERATION_BLOCKED_WORDS` — не секрет, comma-list дополнительных запрещённых слов к встроенному MVP-фильтру промптов (`moderation.ts`), позволяет Ops расширять список без деплоя. `GENERATION_STALE_TIMEOUT_MINUTES` — не секрет, через сколько минут без обновления `queued`/`running`-job лениво переводится в `status=error` (`stale.ts`), защита от зависшего воркера `apps/giga`. Ни одна не задана → используются дефолты в коде, поведение не меняется.
- **Веб-пуш VAPID (`apps/api/src/push/*`, добавлено 2026-07-10, MF-434):** `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` — пара ключей W3C Web Push (сгенерировать один раз через `npx web-push generate-vapid-keys`, не менять после первого релиза — смена ключа делает все существующие подписки браузеров мёртвыми, юзерам придётся переподписаться). `VAPID_SUBJECT` — не секрет, контактный `mailto:`/`https:` (дефолт `mailto:ops@3mf.tech`). Не заданы — `/push/vapid-public-key` отдаёт `null`, рассылка `sendPush()` молча no-op с warn в лог, HTTP не падает (тот же паттерн, что SMTP выше).
- **Ключ шифрования бэкапов (`deploy/portal.backup.sh`, добавлено 2026-07-09, MF-717):** `/home/plag/.portal-backup.key` — только на VDS, chmod 600, НЕ в git. Пароль для симметричного GPG (AES256), которым шифруются env-файлы (`portal.api.env`/`portal.mesh.env`) внутри ежесуточного бэкапа (раньше — плейсхолдер: файлы просто копировались с суффиксом `.enc` без реального шифрования, MF-717). Расшифровка — `deploy/portal.restore-env.sh <файл.gpg> <выходной путь>`. Потеря этого файла = бэкапы env необратимо нечитаемы, поэтому он сам входит в контур бэкапа VDS (не в `/srv/backups`, отдельно).
- **Креды агента устройства (`apps/api/src/modules/devices`, эпик MF-26 «Парк устройств»):** `AGENT_JWT_SECRET` подписывает долгоживущий enrollment credential, который агент получает после одноразового `POST /devices/agent/enroll`. Credential остаётся локальным входом для agent-owned API flows и не является WSS identity: relay v1 принимает gateway только по индивидуальному mTLS-сертификату. Отдельный секрет от `JWT_SECRET` намеренно разделяет браузерную и device границы доверия. Обязателен для enroll; исходное значение не логируется и не пересылается в relay hello.
- **Relay control-plane (`apps/api/src/modules/relayInternal`, `apps/relay`):** `RELAY_SERVICE_TOKEN` — отдельный service-to-service секрет только для canonical `/internal/relay/v1/*`, заголовок `x-relay-service-token`. Gateway certificate, agent credential и browser token этим секретом не являются. API guard сравнивает значение timing-safe и возвращает безопасную versioned ошибку; relay не стартует без значения длиной 32..512. Устаревшие `RELAY_INTERNAL_TOKEN`, `RELAY_API_TOKEN`, `API_INTERNAL_URL`, заголовок `x-relay-internal-token` и unversioned `/internal/relay/*` запрещены и не являются активным fallback.

[docs](https://yookassa.ru/docs/payment-solution/payouts/overview) и [testing basics](https://yookassa.ru/developers/payouts/testing-and-going-live/testing/basics)), выданы оператором для интеграции оплаты в ₽ (Мир/СБП/ЮMoney) и выплат авторам, эпик MF-17 фаза 2. Продовые креды (боевой магазин) заводятся отдельно перед реальным запуском. ⚠️ Переменная переименована из `YOOKASSA_SECRET_KEY` (эта запись изначально называла её так же, как Payments API строкой ниже — два разных секрета под одним именем не заводятся в `.env.example`, см. MF-364 фаза 2 шаг 3): в `.env.example` это `YOOKASSA_PAYOUTS_SECRET_KEY`, задел под будущую автоматизацию Payouts API — пока `POST /payouts` эти креды не читает, обработка заявки ручная (staff, `PATCH /payouts/:id`).
- **ЮKassa Payments API — приём оплаты (`apps/api/src/billing/*`, MF-364/MF-1025, добавлено 2026-07-17):** `YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY` — креды тестового магазина для СОЗДАНИЯ платежа (`POST /v3/payments`) и подтверждающего запроса статуса из вебхука (Basic auth shopId:secretKey). ⚠️ Это **другой продукт** ЮKassa, чем Payouts API строкой выше — `YOOKASSA_AGENT_ID`/`YOOKASSA_PAYOUTS_SECRET_KEY` из MF-1024 НЕ подходят для приёма оплаты, их нельзя переиспользовать. На момент этой карточки shop_id для Payments API не выдан — Ops/оператору нужно завести отдельный тестовый магазин на yookassa.ru. Без переменных `POST /purchases` отвечает `503` (платёж не создать без провайдера, не soft-fail — в отличие от push/email). Только `.env` на VDS, не в git.
- **Подпись `slice-trust.v1` (`apps/mesh/src/mesh/slice_trust_signing.py`, добавлено 2026-07-20, MF-1992):** `MESH_SLICE_TRUST_PRIVATE_KEY_PATH` — путь к PEM-файлу с приватным Ed25519-ключом (`openssl genpkey -algorithm ed25519 -out mesh-slice-trust.pem`), `MESH_SLICE_TRUST_KEY_ID` — версионированный идентификатор активного ключа (например `mesh-slice-trust-2026-07`). Оба обязательны для воркера `mesh-slice-worker` (`portal.mesh-slice-worker(-dev).service`) — без них он простаивает по ВСЕЙ очереди слайсинга, не только Orca/U1 (`process_one_slice_job` требует обязательный `slice-trust.v1` для каждой job, не деградирует до legacy-fallback). Сам PEM-файл — только на VDS, chmod 600, НЕ в git, НЕ в `.env` (путь к файлу — не секрет, но лежит рядом с остальными env-файлами воркера, `~/portal.mesh(-dev).env`). `MESH_SLICE_TRUST_PUBLIC_KEYS_PATH` — опционально, путь к JSON-реестру `{key_id: base64(raw 32 bytes public key)}` не-секретных публичных ключей retired-ключей: нужен только при ротации, чтобы уже закэшированные `slice_cache_entries` с подписью старого `key_id` оставались проверяемыми (публичный ключ активного `key_id` всегда выводится из приватного ключа, реестр не может его подменить). Ротация: сгенерировать новый PEM с новым `key_id`, добавить публичный ключ ПРЕЖНЕГО `key_id` в реестр, переключить `MESH_SLICE_TRUST_PRIVATE_KEY_PATH`/`MESH_SLICE_TRUST_KEY_ID` на новый ключ, перезапустить воркер.
- Ротация: при утечке/увольнении — немедленно перевыпустить ключ в cloud.ru + обновить секрет в GitVerse Actions + на VDS.

## Сетевые границы

`mesh` и `giga` — внутренние сервисы, не имеют публичного домена/порта наружу. Единственная публичная поверхность — `api` (и статика `web`). Подробности — `docs/architecture/readme.md`.

`apps/relay` — отдельный compiled NestJS data-plane. Публичная gateway-граница — raw WSS с TLS 1.3 и обязательным индивидуальным client certificate; L4 proxy только передаёт TLS в relay. Отдельный loopback HTTP listener отдаёт `/health`, `/ready`, `/metrics` и не публикуется на gateway-порту. `/internal/relay/v1/*` на API — приватный service-token контур и не проксируется как публичный API. См. `apps/relay/readme.md`.

## Что не публикуем в репозитории

Даже в приватном репо — без необходимости не светим: реальные email/личные контакты (используем `@`-упоминания на gitverse.ru), публичный IP VDS (используем Tailscale-имя `ru-4gb-16018` — бесполезно вне тейлнета), сырые ключи/токены (см. «Секреты» выше). Это не про секретность самих фактов, а про минимизацию поверхности на случай утечки доступа к репо.

## Зависимости

- Лок-файлы (`pnpm-lock.yaml`, `apps/*/uv.lock`) коммитятся — воспроизводимые сборки.
- `pnpm audit` (Node) и `uv run pip-audit` (Python) — часть CI (`.gitverse/workflows/ci.yaml`), high/critical — блокирует merge.
- Обновление зависимостей — вручную по мере необходимости; авто-PR-бот (Dependabot-аналог) не настроен (см. «Открытые вопросы»).

## Персональные данные

Продукт — публичный сервис для физлиц на российском рынке → попадает под 152-ФЗ («О персональных данных»). Хранение/обработка ПДн пользователей требует юридической проработки (согласия, локализация хранения в РФ — уже закрыто выбором cloud.ru, политика конфиденциальности) до появления реальной регистрации пользователей.

## Открытые вопросы (до публичного запуска)

Не блокируют разработку и внутренний доступ, но должны быть закрыты **до открытия регистрации реальных пользователей**:

- 🔴 **Юридическая проработка ПДн (152-ФЗ)** — согласия, политика конфиденциальности, право на забвение. Это флаг, не юрконсультация: свериться с юристом перед запуском регистрации. Блокирует реальную регистрацию.
- 🟠 **Выделенный security-контакт** — вместо личного `@plag` завести общий адрес (напр. `security@…`), когда появится команда.
- 🟠 **Авто-обновление зависимостей** — настроить Dependabot-аналог при росте команды.
- 🟢 **Юрлицо в копирайте** — при регистрации ООО/ИП под проект обновить `LICENSE.md` (сейчас копирайт личный).
