# Агентские аккаунты — co-authorship + кабинет API-ключей

Статус: спека к MF-2028 (+ Ф1 MF-2029 / Ф2 MF-2030 / Ф3 MF-2031), заведена 2026-07-21.
**Ф1-Ф3 реализованы и живут на dev.3mf.tech с 2026-07-21** — см. § «Живое состояние
2026-07-21» в конце файла для фактического финального устройства (search-механизм,
паблики, найденные по пути баги, автоматика).

Разработчики и (позже) обычные пользователи регистрируют свой ИИ-агент как
соавтора контента на портале: агент пишет посты в ленту и предлагает
правки/новые карточки в каталог принтеров **от имени владельца**, с видимым
двойным авторством (человек + агент). Тестовый прогон — на аккаунте `plagx`,
раннтайм агента — существующий OpenCode на HYPERPC (`ocsearch`,
[hyperpc.local.llm.md](../process/hyperpc.local.llm.md)).

Это закрывает открытый TODO из [agents.and.humans.md](../product/agents.and.humans.md)
§ «Что это требует от модели данных и UX» — там раздел был концептуальным
заделом без реализации; здесь — конкретная схема и API.

## 0. Что уже существует и переиспользуется

Прежде чем читать дальше: в кодовой базе уже есть три прецедента, из которых
этот эпик строится почти целиком композицией, а не изобретением заново.

1. **Identity агента, отдельного от человека** — `apps/api/src/devices/agentSession.ts`.
   `AgentCredentialClaims{agentId, ownerId, deviceId, role}`, подписано **отдельным**
   секретом `AGENT_JWT_SECRET` (не тем же, что человеческие cookie — комментарий
   в файле прямо объясняет почему: «агентские креды — другая граница доверия»),
   дискриминатор `typ:"agent"` не даёт спутать с человеческой сессией. **Уточнение
   при реализации Ф1 (2026-07-21):** для content_agents НЕ заводили отдельного JWT —
   research/feed_ingest уже показывают более простой, тоже проверенный паттерн
   (`user_api_keys.key_hash`, plain bearer-токен, без JWT вообще) — `agent_content`
   пошёл по нему (см. п.4 ниже), JWT-подход остаётся только у device-агентов.
2. **Двойная аутентификация (cookie ИЛИ bearer-ключ)** —
   `apps/api/src/printers/research.route.ts::researchUserId()` уже принимает и
   session, и `Authorization: Bearer mf_research_…`, резолвя единый `userId`
   независимо от способа. Новый `postAuthorContext()` — тот же приём.
3. **Модерируемая community-очередь для принтеров** —
   `apps/api/src/printers/reports.route.ts` (`printer_reports`,
   `source='community'`, `confidence='low'`, `approve`/`reject` ролью
   `researcher`) — уже устроена ИМЕННО для «обычный пользователь предлагает
   правку, канон не трогается напрямую». Агентские предложения идут в ту же
   таблицу, не создают четвёртый параллельный контур.
4. **Аддитивная миграция нового scope** —
   `apps/api/db/migrations/20260718220000_feed_ingest_scope.sql` — образец,
   как `feed_ingest` был добавлен в `user_api_keys` без затрагивания
   существующих scope. `agent_content` добавляется тем же способом.

Не путать с **researcher-контуром** (`role='researcher'`,
`docs/epics/printers.research.md`, MF-1574) — это отдельный, куда более
доверенный внутренний контур (3 сервис-аккаунта Ресёрчеров, пишут в канон
напрямую, без очереди). Обычный пользователь и его агент в этот контур не
попадают ни при каких условиях этого эпика.

## 1. Модель данных

### `content_agents` (новая таблица)

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | uuid pk | |
| `owner_user_id` | uuid → users | человек-владелец |
| `name` | text | отображаемое имя агента (свой «профиль», не спрятан) |
| `avatar_s3_key` | text null | своя аватарка — нужна для двойной подписи в UI |
| `bio` | text null | опционально: «что за агент» (напр. «локальная модель на HYPERPC») |
| `runtime_label` | text null | свободный текст-прозрачность (напр. `opencode/hyperpc-slot1+2`) — принцип «вклад агента виден» из agents.and.humans.md применён и к тому, ЧТО именно исполняет агента |
| `status` | text check(active/revoked) | |
| `created_at`, `revoked_at` | timestamptz | |

Один пользователь может завести несколько агентов (не 1:1) — схема не
блокирует, хотя бета обкатывается на одном.

### `user_api_keys` — новый scope `agent_content`

Аддитивно расширяются существующие CHECK-констрейнты (тем же способом, что
`research`/`feed_ingest`):

- `user_api_keys_scope_check` → добавить `'agent_content'` в список.
- `user_api_keys_provider_scope_check` → `agent_content` в группу
  «`provider IS NULL`» (как public_api/research/feed_ingest, не как printer).
- `user_api_keys_secret_shape_check` → `agent_content` в группу `key_hash`
  (не `secret_enc`) — минтед-ключ, юзер видит plaintext один раз.
- `user_api_keys_scopes_check` → `agent_content` жёстко `scopes=['write']`
  (как research/feed_ingest — это ключ действия, не read/control-тиеринг).
- Новая nullable колонка `agent_id uuid → content_agents(id)`, заполняется
  только когда `scope='agent_content'` — резолвит, какой именно агент стоит
  за ключом (в отличие от research/feed_ingest, где ключ = весь
  сервис-аккаунт, здесь один человек может иметь несколько агентов/ключей).
- Префикс `mf_agent_` (по аналогии `mf_research_`/`mf_feedingest_`).

### «Ключ доступа к принтеру» — новой схемы НЕ требует

Оператор подтвердил (2026-07-21): это уже существующий `user_api_keys.scope='printer'`
(`secret_enc`, `provider` обязателен) — та же механика, что у реального
девайс-энролла (`apps/api/src/devices/enroll.ts` + `agentSession.ts`):
credential кладётся на устройство (или в контекст агента, который работает с
конкретным принтером), при revoke устройство/агент обязаны
переавторизоваться. Работа этого эпика по «ключу принтера» — **только**
self-service UI в кабинете (список/revoke существующих ключей пользователя),
без новых миграций. Если понадобится минтить `printer`-ключ вне физического
enroll-флоу (например, чтобы дать агенту read-контекст чужого — точнее,
СВОЕГО — принтера без переустановки прошивки) — это отдельное расследование
`devices/enroll.ts`, не в объёме Ф1-Ф3, фиксируется как открытый вопрос ниже.

### Co-authorship: `feed_posts.co_author_agent_id`

```sql
alter table feed_posts add column co_author_agent_id uuid references content_agents(id);
```

`author_id` **не меняется** — остаётся человеком-владельцем. Это осознанное
решение: вся существующая логика (ACL комьюнити, rate-limit, ранжирование,
голоса, `is_edited`) продолжает работать без единой правки, потому что она
завязана на `author_id`. `co_author_agent_id` — чисто атрибуция для UI:
рендерится как двойная подпись «plagx + 🤖 <имя агента>» (решено оператором
2026-07-21 — не «от лица агента» и не тихий бейдж, а полноценное совместное
авторство, по аналогии с GitHub `Co-authored-by`).

### Co-authorship для `printer_reports`

Аналогично: новая nullable `co_author_agent_id` (или переиспользование
`reporters uuid[]` с параллельным `agent_ids uuid[]` — решает Ф1-исполнитель
по факту миграции, схема `printer_reports` уже держит массив репортеров, так
что естественнее массив агентов той же формы). `field_provenance.filled_by`
при агентском вкладе — `"community:<user_id> (agent:<agent_id>)"`, `source`
и `confidence` остаются `community`/`low` (агент не поднимает доверие выше
человека-репортёра — это тоже сознательное решение: агент вносит контент **с
доверием своего владельца**, не выше).

## 2. API

### Управление агентом и ключами (человек, session-only)

- `POST /me/agents` — создать агента. **Гейт беты**: `AGENT_ACCOUNTS_BETA_USERNAMES`
  (env allowlist, no-op-закрыто если не задан — тот же паттерн, что
  `ADMIN_USERNAMES` у `POST /models/:id/featured`). Сейчас: `plagx`.
- `GET /me/agents`, `POST /me/agents/:id/revoke`.
- `POST /me/agents/:id/keys` — минт `agent_content`-ключа для этого агента
  (одноразовый показ plaintext, по образцу `keys.route.ts`).
- `GET /me/user-api-keys` (существующий) — расширить листинг, чтобы показывал
  и `printer`-ключи (self-service revoke), и новые `agent_content`-ключи с
  привязанным именем агента.

### Создание контента (agent_content-ключ ИЛИ session)

- `POST /feed/posts` — `postAuthorContext()` вместо чистого `readSession`:
  session → `author_id=session.id`, `co_author_agent_id=null` (как сегодня);
  Bearer `mf_agent_…` → резолвит `content_agents` → `ownerId`, требует ту же
  community-membership проверку, что и сегодня для `ownerId`, ставит
  `author_id=ownerId`, `co_author_agent_id=agentId`. Публикуется сразу
  (`status='visible'`) — **не** как `feed_ingest` (draft по умолчанию):
  здесь за постом стоит явно названный, подотчётный человек, а не анонимный
  сервис-аккаунт, поэтому тот же уровень доверия, что у обычного поста
  человека.
- `POST /printers/:id/report` — тот же двойной auth, `agent_id` пишется в
  `printer_reports`, provenance помечается как описано выше. Гейт по
  роли/скоупу НЕ добавляется сверх обычной community-проверки — принтер-контент
  и так идёт через модерацию `researcher`, дополнительный барьер не нужен.

### RACI и инварианты

Любое изменение `user_api_keys` подчиняется
[api-keys.raci.md](../process/api-keys.raci.md) — Product/Trust остаётся
accountable, `agent_content` не читает `api_keys` (legacy-контур) и не
смешивает scopes. Ф1-исполнитель обязан прогнать миграцию вперёд-назад на
throwaway DB (метод MF-1076) и приложить SQL-evidence перед merge.

## 3. Локальный news pipeline на HYPERPC

> **Важно:** первоначальная схема этого раздела, в которой Finisher сам получал
> `AGENT_CONTENT_KEY` и вызывал write-API, выведена из эксплуатации. Канонический
> контур и границы ролей описаны в
> [feed.news.pipeline.md](../architecture/feed.news.pipeline.md). Ни одна модель,
> включая локальную и Grok, не получает publish-секрет или write-инструмент.

Существующий раннтайм `ocsearch` (docs/process/hyperpc.local.llm.md) уже
сконфигурирован под 2 нужных провайдера — используем как есть, без нового
Linux-юзера/профиля:

- **Researcher** — `hyperpc-slot2/gemma-4-e4b` (порт 1235, большой контекст
  65536, без надёжного tool-calling). Роль: прочитать источник/тему и
  подготовить структурированные находки со ссылками и цитатами — быстро,
  без необходимости структурированных инструмент-вызовов.
- **Composer** — `hyperpc-slot1/qwen3.6-35b-a3b` (порт 1236, надёжный
  structured output). Роль: взять проверенные находки Researcher, оформить
  rich-черновик и вернуть только `news-composition.v2`.
- **Grok moderator** — независимая редакторская проверка `accept | revise |
  reject` и advisory-only предложения по API. Grok не исправляет контракт и
  не публикует материал автоматически.
- **Host publisher** — единственный детерминированный процесс с
  `feed_ingest`-секретом. Он повторно проверяет v2-артефакты, evidence и
  решение модератора, после чего отдельно создаёт draft и публикует его.

Блокер git-credentials у `ocsearch` (см. `hyperpc.local.llm.md` § «Не
доделано») не обходится передачей модели продуктового секрета: product worker
живёт в репозитории, вызывает локальные inference endpoints и сохраняет
версионированные артефакты. Write-граница остаётся только на host publisher.

## 4. Дорожная карта — что значит «широко» (v2/v3)

По просьбе оператора — явно фиксируем, куда это растёт, чтобы бета не
казалась случайной точкой, а масштаб решения был виден заранее.

**v1 (этот эпик, MF-2028):**
- Создание постов и предложений в каталог принтеров через API-ключ, двойная
  подпись, всегда с человеком-владельцем в основе.
- Кабинет: список агентов + список/revoke двух типов ключей. Ничего сверх
  этого (без редактирования чужого контента, без profile-правок, без загрузки
  моделей через агента).
- Бета закрыта allowlist'ом (`plagx`).

**v2 (следующая итерация, отдельные карточки заводятся по факту готовности v1):**
- Расширение write-охвата: агент может редактировать/удалять СВОИ posted-посты,
  загружать модели/генерации от имени владельца (переиспользуя уже готовый
  `generations`-контур), self-service минт `printer`-ключа вне физического
  enroll-флоу (см. открытый вопрос ниже).
- Доверие к агентским printer-правкам перестаёт быть плоским `confidence=low`
  для всех — реализуется тиринг по репутации владельца (см.
  [trust.md](../product/trust.md) — уже существующая, но пока не применённая
  к агентскому контенту модель доверия).
- Открытие беты за пределы allowlist'а — сначала разработчикам, потом шире.
- Rich-редактор ленты (MF-2032, отдельный эпик — темы/embed-реестр/3D) — не
  зависит от MF-2028, но естественно стыкуется: агент тоже пишет через тот же
  редакторский контракт.

**v3 (горизонт, не карточки, а направление):**
- Полная параллель с org/brand-аккаунтами из [accounts.md](../product/accounts.md)
  — агент, зарегистрированный НЕ отдельным человеком, а организацией/брендом.
- Публичный «реестр агентов» — сторонний разработчик регистрирует агента,
  который могут подключить себе другие пользователи (маркетплейс агентов),
  не только «свой агент под себя».
- Автоматизированный модерационный ассистент поверх `printer_reports`-очереди
  (агент-модератор, отдельная роль от агента-контрибьютора).
- **Явная граница, которая НЕ переносится ни на одну версию без отдельного
  продуктового решения**: финансовые действия (заказы/выплаты) через
  API-ключ агента не даются — это касается людей и организаций напрямую,
  вне зависимости от того, насколько широким становится остальной охват.

## 5. Открытые вопросы (не блокируют Ф1-Ф3)

1. Нужен ли self-service минт `printer`-ключа вне физического enroll-флоу
   (для агента, читающего telemetry СВОЕГО уже подключённого принтера)? Не
   решается здесь — расследование `devices/enroll.ts` при появлении реального
   сценария.
2. `printer_reports.agent_id` — массив (как `reporters`) или одиночная
   колонка? Решает Ф1-исполнитель по факту миграции, не архитектурный вопрос.
3. Доля доверия агентского printer-контента (`confidence`) относительно
   человеческого — зафиксировано как РАВНОЕ (`low`, как у любого community-
   отчёта) на v1; тиринг — v2, см. выше.

**🔴 Инцидент 2026-07-21: `post-publisher` галлюцинировал успешную публикацию

(`c6c7d97d-3630-433d-834a-69b563d588a6`).

1. `post-publisher.md` — жёсткое правило: `status: success` только если в

   лог + `exit 1`. **БД, а не текстовый отчёт модели, теперь источник
   истины о том, состоялась ли публикация** — тот же принцип, что и везде

подтверждены независимым SELECT. Итого все 3 бренда подтверждены рабочими
под верифицированным конвейером — задача «запустить процесс живьём на
новых брендах» закрыта по-настоящему, не только на словах модели.

Остаётся открытым: скрипт ловит «публикации не было», но не ловит

БД. Не сделано, следующий кандидат на усиление при следующем инциденте.

## Живое состояние 2026-07-21 (продолжение №2): иерархия сабов, запрет постов без community (MF-2037/MF-2038)

Продуктовое уточнение оператора: пост никогда не публикуется «себе на страницу», только в саб;
пост в machine-сабе ("QIDI Q2") виден и в нём, и в его vendor-сабе ("QIDI") — направление
одностороннее, vendor-пост в machine-саб не протекает. Разбор показал, что ВСЕ 9 постов первого
дня конвейера ушли без `community_id` — не редкий сбой, а системная поломка.

**Первопричина**: анти-бригадинг гейт (`feed/gate.ts`, MF-1859) считал официальные каталожные
vendor/machine-сабы «новыми» наравне с пользовательскими custom-клубами и требовал репутацию,
которой у plagx не было. `post-publisher.md` содержал инструкцию при 403 REPUTATION_TOO_LOW
ретраить без `community_id` — этот "штатный fallback" и был багом, не решением.

**Фикс (4 файла бэкенда + 1 фронтенда, все задеплоены и проверены живьём):**
- `feed/gate.ts` — vendor/machine полностью исключены из гейта (единственные на subject,
  лениво создаются системой, unique index не даёт дубль — не «своя» тусовка, которую можно
  забригадить).
- `feed/list.ts` — `GET /communities/:id/feed` разворачивает vendor-саб в его machine-сабы
  (переиспользован join уже существовавший для scope=subscribed, просто не применялся к явной
  ленте одного саба).
- `community/feed.ts` — попутно найденный pre-existing баг: эндпоинт не вызывал
  `hydrateFeedPosts`, автор рендерился как «[удалённый пользователь]».
- `feedscreen.tsx` — сайдбар «Мои сабы» вёл официальные сабы на пустую страницу тредов
  (`/community/:slug`, Q&A-функция MF-931), а не на `/feed?community=...`, где реально лежат
  посты — без этого фикса роллап был бы технически исправен, но невидим в UI.
- `post-publisher.md` — фоллбэк без community_id заменён жёстким правилом: нет подходящего
  community_id → не публиковать вообще, `status: failure` с объяснением.

**Backfill**: 8 реальных постов переставлены на верный community_id по контенту (4 общих
Creality-поста → vendor; 2 QIDI Q2-поста → machine; Snapmaker U1-обзор → machine, новость о
раунде финансирования компании → vendor). 2 тестовых поста сессии удалены.

**Проверено живьём** (не только юнит-тестами): гейт больше не блокирует официальные сабы;
`GET /communities/{QIDI}/feed` отдаёт и QIDI, и QIDI Q2 посты, обратное — только свои; автор
резолвится корректно; клик по сабу в сайдбаре ведёт в ленту; свежий прогон конвейера после фикса
проставил community_id с первого раза без фоллбэка (подтверждено SELECT, не отчётом LLM).

Карточка `MF-2038` (done) — полный отчёт с деталями верификации.

## Живое состояние 2026-07-21 (продолжение №3): конвейер простаивал на 15 из 18 брендов (MF-2040/MF-2041)

Оператор заметил: «последний пост был 3ч назад». Разбор показал ДВЕ независимые причины,
обе исправлены и задеплоены.

**Причина 1 — узкая ротация.** `/home/plag/pipeline-brands.json` на worker (vds) содержал только
3 бренда (Creality/QIDI/Snapmaker) — тот же исходный список с самого начала конвейера, никогда не
расширенный вслед за 18-брендовым каталогом (MF-2039). При этом `creality-content-pipeline.sh`
обрабатывал РОВНО 1 бренд за системд-прогон (таймер раз в 6ч) — даже расширив список, полный
круг занял бы 4.5 суток.

**Причина 2 (настоящий блокер новых брендов) — `403 NOT_A_MEMBER`.** `POST /feed/posts`
(`feed/create.ts`, MF-1926 п.1) требует членства автора в целевом сабе. Официальные vendor/machine
сабы создаются `ensureCatalogCommunity()` без человека-владельца — вступать в них некому. Владелец
ключа `agent_content` (plagx) состоял в Creality/QIDI/Snapmaker (кто-то вступил вручную на заре
конвейера), но получал 403 на все 15 новых брендов. Живой лог зафиксировал: `research-reporter`
честно написал новость, `post-publisher` вызвал реальный `curl`, сервер ответил 403 — агент НЕ
придумал успех, корректно отчитался `status: failure`.

**Фикс (`apps/api/src/feed/create.ts`)**: членство не требуется, когда пост co-authored агентом
(`author.coAuthorAgentId !== null`) И саб официальный (`kind IN ('vendor','machine')`). Обычная
публикация человека в официальный саб без вступления по-прежнему 403 — сужение точное, не общее
ослабление гейта. Симметрично с исключением из анти-бригадинг гейта (MF-2036/MF-2038) — тот же
принцип: официальные каталожные сабы системные, не «чужой клуб».

**Расширение конвейера (`creality-content-pipeline.sh` на vds)**: переведён на пакетную обработку
— `BATCH_SIZE` (дефолт 5) брендов за один системд-прогон, каждый бренд изолирован (`process_brand`
возвращает статус, не валит остальной батч). `pipeline-brands.json` расширен до всех 18 брендов
каталога. При 4 прогонах/сутки (таймер `03,09,15,21`) и BATCH_SIZE=5 весь каталог освежается за
сутки. `TimeoutStartSec` поднят 600→3600.

**Проверено живьём**: ручные батчи после фикса дали 24 поста агента (было 9) — покрытие всех 18
брендов, кроме 3 (ANYCUBIC/Prusa Research/Zortrax), где `research-reporter`/`post-publisher`
корректно отказались публиковать (не нашли валидный URL источника или получили обрезанный
черновик) — честный отказ, не системная поломка, само-исцелится на следующих плановых прогонах.

Карточка `MF-2041` (закрыла заодно устаревший `MF-2036`, оставшийся `todo` после его же фикса
в MF-2038 — доска не была обновлена) — полный отчёт с деталями.
