# Эпик: Уровни поддержки принтеров + кастомная прошивка на базе портала

**Директива оператора (2026-07-10). Приоритет v1.** Это стратегическое ядро продукта: от
«каталога принтеров» — к «принтерам, которыми управляешь из портала», вплоть до «принтеров под
нашей кастомной прошивкой с двусторонней связью». Data-moat + замок пользователя в экосистему.

Связь: БД принтеров — [printers.research.md](printers.research.md) (наполнение Ресёрчерами);
девайс-контур API — [domain.model.md](domain.model.md), MF-26/MF-390..392 (перенесены на v1).

## Три уровня поддержки (support_level у каждого принтера)

Каждая карточка принтера в БД получает поле **`support_level`** — фасет каталога и обещание портала:

### 1. `list` — Просто в каталоге
Принтер есть в БД с характеристиками (стол/хотэнд/AMS/цена…), но управления нет. Дефолт для всех
запарсенных Ресёрчерами. Ценность: сравнение, выбор, сообщество вокруг модели.

### 2. `managed` — Управление БЕЗ вмешательства в прошивку
Принтером можно управлять из портала, НЕ трогая его прошивку — через то, что уже стоит:
- **Klipper+Moonraker** (Ender-3 V3/KE, FLSun V400/T1/SR, любой Klipper-принтер) — портал говорит
  с **Moonraker HTTP/WebSocket API** (стандарт): статус печати, старт/пауза/стоп, отправка G-code,
  телеметрия, вебка. Пользователь вводит IP (или enroll по коду) — принтер в парке.
- Родные облака/LAN-режимы вендоров — по мере реверса, ниже приоритет Klipper.
Требование к пользователю: принтер в его сети, Moonraker доступен. Мы НЕ меняем прошивку — только
подключаемся к API. Это большинство современных Klipper-принтеров «из коробки».

### 3. `custom` — Наша кастомная прошивка (флагман)
На принтер ставится **наша сборка**: Klipper (движок печати остаётся) **+ наш ВИЗУАЛ** (морда
портала на экране/в вебе вместо Mainsail/Fluidd) **+ наш АГЕНТ** (сервис-туннель к нашему серверу).
«Агент» — общее имя для этой связки. Даёт **двустороннюю связь**:
- **принтер → портал**: с экрана/морды принтера пользователь заходит в свой портал-аккаунт, видит
  свои проекты/очередь/сообщество, шлёт печать из облака.
- **портал → принтер**: продвинутое удалённое управление (макросы, обновления, диагностика,
  мониторинг парка) через наш агент-туннель (работает за NAT/CGNAT, outbound-only, см. MF-26 relay).
Способы доставки прошивки (три, на выбор пользователя):
- **(а) Веб-перепрошивка** — прямо из портала заливаем образ/конфиг на принтер (для моделей с
  доступным флешем: Moonraker update manager / SD-swap / recovery). Самый простой UX.
- **(б) Готовая флешка/образ** — пользователь пишет готовый SD/eMMC-образ (Klipper+Moonraker+наш
  визуал+агент, преднастроенный под модель) и вставляет.
- **(в) Git-проект принтера** — репозиторий на модель (конфиги Klipper, printer.cfg, макросы,
  инструкция, ссылка на образ) — продвинутый пользователь клонирует и накатывает сам. Шаблон-скелет
  под новую модель (MF-934) — [../../printer.firmware.template](../../printer.firmware.template).

**🔴 КТО СОБИРАЕТ ОБРАЗ/OS: ОПЕРАТОР (Валерий) ВРУЧНУЮ со своего компа — агенты сквада OS-образы
НЕ делают.** Готовые образы/OS живут в **ОТДЕЛЬНЫХ git-репозиториях** (по репо на модель), НЕ в
монорепо portal.ru. Агенты делают: наш визуал (морду), агент-туннель, портальный API/UI/каталог
прошивок, скелет git-репо принтера и инструкции, кнопки/страницы доставки — но саму сборку
OS-образа производит оператор. В карточке модели агент лишь ССЫЛАЕТСЯ на репо/образ (GitVerse-URL),
который дал оператор.

**Прошивка пока ПРИВАТНАЯ** (не публичный релиз) — образы/репо закрыты, доступ по мере готовности.
Публичный релиз прошивки — позже (заложить флаг `firmware_public` / этап). UI на custom пока
показывает «поддерживается, доступ по запросу», не открытую кнопку скачивания.

**Статус «поддерживаемый»** (`support_level=custom`, флаг `firmware_ready`) выставляется, КОГДА
образ для модели собран оператором, испытан на железе и репо привязан. До этого модель — `list`
или `managed`.

## Неподдерживаемые принтеры — «Сделай сам» + прошивки сообщества

Официально поддержаны не все модели (образ делает оператор — их будет ограниченно). Для остальных
даём пользователю САМОМУ адаптироваться — это ключевой рычаг охвата без ручной работы оператора:

- **Публичный API портала** — документированный API управления/интеграции принтера (тот же, что
  использует наш агент): пользователь пишет СВОЙ коннектор/интеграцию под свой принтер по нашему API.
  Даём спеку API + примеры. Это работает даже без нашей прошивки (поверх любого Moonraker/родного API).
  Дока v0 (read+basic-command, MF-888): [../api.public.md](../api.public.md).
- **«Сделать самому»** — когда прошивка станет публичной: пользователь берёт нашу открытую прошивку/
  конфиги и адаптирует под свою модель сам (форк git-репо принтера-образца, правка printer.cfg/визуала).
- **Прошивки от сообщества** — каталог community-сборок: пользователи публикуют свои адаптации на
  **GitVerse**, портал показывает их списком со ССЫЛКАМИ на репозитории (community_firmware: model,
  автор, git-URL, «не проверено нами»). Модерация/бейдж доверия — позже.

**Кнопки/UI (заложить во Front):** на карточке неподдерживаемого принтера — **«Сделать самому»**
(→ дока публичного API + инструкция адаптации) и **«Прошивки сообщества»** (→ список GitVerse-репо
под эту/похожую модель). На поддерживаемом — «Управлять»/«Поставить прошивку» (доступ по запросу, пока
приватно).

## Сценарий «добавить принтер» — честный поток (UX, MF-890)

Канонический словарь шести состояний уже подключённого контура и правила
fail-closed: [спецификация состояний подключения](../design/printer-connection-states.md).

Ведёт UX. Реализуют Design (визуал мастера) и Front (страница принтера MF-892). Принцип
переиспользуемый вынесен в [../product/ux.md §6](../product/ux.md). Опирается на реальный
существующий флоу `apps/web/src/home/printerpicker.tsx` (MF-437) — сейчас он умеет ТОЛЬКО
«заявить» (каталог/ручной ввод → `user_printers`, без управления). Мы его достраиваем до
честного выбора уровня, а не строим с нуля.

### 🔴 Осевой принцип честности (из [printer.server.md §1](../architecture/printer.server.md), NAT)
Мастер **не обещает того, чего сеть не может дать**. «Ввести IP» — это НЕ «управляй из
любой точки»: браузер юзера говорит с Moonraker напрямую, и это работает, **только пока
браузер в той же сети, что принтер**. Удалённое управление = либо облако вендора, либо наш
агент/мост в сети юзера. Мастер проговаривает это ДО привязки, а не после — иначе юзер
привяжет «по IP», уйдёт из дома и решит, что мы сломались.

### Точки входа
1. **Онбординг / чек-лист активации** (`PrinterPicker`, home) — первый контакт. Сейчас
   ведёт только в «заявить»; добавляем предложение «а хотите ещё и управлять?» после привязки.
2. **ЛК / «Мой парк»** — канонический дом мастера: primary-кнопка «+ Добавить принтер».
   Принтер живёт в парке, поэтому мастер запускается отсюда (роут `/park/add`, не оверлей —
   [ux.md §2](../product/ux.md): на это дают ссылку, сюда возвращает «назад»).
3. **Каталог `/printers` → карточка модели** (MF-892): «У меня такой» — префилл бренда/модели
   в мастер + подсветка уровня, доступного этой модели.

#### Диплинк из каталога и гостевой возврат (MF-1126)

Действие «У меня такой»/«Добавить принтер» ведёт на `/park/add` с referrer и моделью в
контексте. Гостю показываем: **«Чтобы добавить принтер, войдите или зарегистрируйтесь»** с
действиями **«Войти»** и **«Продолжить как гость»**. До логина сохраняем referrer, выбранную
модель и шаг. Успешный вход возвращает на тот же `/park/add` и шаг; отмена/назад — в каталог,
не на пустой экран. Гость может выбрать модель и проверить LAN, но перед сохранением в парк
входит; после входа поля и результат проверки не сбрасываются.

### Путь — два вопроса подряд, не один
Мастер спрашивает по очереди **ЧТО за принтер** (уже умеет `PrinterPicker`), затем **ЧТО ты
с ним хочешь делать** — и человеческим языком, не «выбери протокол»:

| Выбор юзера (его словами) | Уровень | Что происходит | Честная подпись |
|---|---|---|---|
| «Просто отметить, что он у меня есть» | `list` | добавляем в парк, управления нет (текущее поведение) | сравнение/сообщество/сигнал спроса |
| «Управлять, пока я дома» | `managed-local` | ввод IP → **браузер↔Moonraker напрямую**, сервер только рисует UI; клиентская проба доступности | «Работает только в вашей сети — вне дома принтер офлайн» |
| «Управлять из любой точки — через облако производителя» | `managed-cloud` | привязка аккаунта вендора (Bambu/Prusa), опрос через их облако | «Идёт через облако <вендор>, прошивку не трогаем» (v2) |
| «Управлять из любой точки — через наш мост» | `managed-bridge` | лёгкий агент в сети юзера, enroll-код, outbound-туннель, БЕЗ смены прошивки | «Ставим маленький сервис рядом с принтером, работает за NAT» |
| «Полный портал прямо на принтере» | `custom` | наш визуал+агент, двусторонняя связь; доставка (а/б/в) | если `firmware_ready` — «Поставить прошивку»; иначе «Доступ по запросу» |

### Контролы (что · зачем · куда ведёт)
- **Плитки уровня** — по каждой: что даёт · **чем ограничен** (главное!) · что после. Недоступные
  для модели уровни не прячем, а показываем приглушённо с причиной (см. §5 ниже, «не молчим»).
- **Поле IP + «Проверить»** (managed-local) — проба идёт **из браузера, не с сервера** (это же и
  защита от SSRF: сервер не ходит по чужим адресам). Успех → в парк с бейджем `managed-local`.
- **«Повторить проверку»** — повторяет запрос на том же адресе, не очищая модель/IP и не создавая
  новую запись. Во время запроса кнопка заблокирована; каждая попытка показывает исход. После
  третьей неудачи остаются **«Повторить проверку»** и **«Скопировать данные для поддержки»**
  (модель, адрес, время/код ошибки, без токенов), чтобы не зациклить пользователя.
- **«Установить агент»** (bridge/custom) — выдаёт enroll-код + короткую инструкцию (MF-887/390).
  Пока код не активирован — принтер в парке в состоянии «ждём агента».
- **«Поставить прошивку»** (custom) — НЕ однотапная кнопка: прошивка приватна, деструктивна и
  рискованна → «Доступ по запросу» + предупреждение (см. крайние случаи).

### Гейтинг уровней по модели (сердце честности — читаем схему MF-884)
Какие плитки загораются для конкретной модели — из полей `connector_type` / `firmware_ready` /
`firmware_public`:
- `list` — всегда.
- `managed-local` — если `connector_type ∈ {moonraker, prusa-link, octoprint}` (есть открытый
  локальный API). Подпись «только дома».
- `managed-cloud` — если `connector_type ∈ {bambu, prusa-connect, vendor-cloud}`.
- `managed-bridge` — если наш агент умеет обернуть локальный API модели (v1 — moonraker).
- `custom` — если `firmware_ready=true`; иначе плитка заблокирована «скоро»; `firmware_public=false`
  → «доступ по запросу», без открытой скачки.
- **Ни один managed/custom не подходит** (`connector_type=none`, Marlin типа Ender-3 V3 SE) →
  остаётся `list` + два выхода наружу (ниже).

### Экраны для неподдержанных — «Сделать самому» и «Прошивки сообщества»
Точки входа: карточка неподдержанной модели (MF-892) и «тупик» мастера, когда managed/custom
не светятся.
- **«Сделать самому»** → дока публичного API (MF-888/896) + инструкция адаптации. Смысл: юзер
  пишет свой коннектор по нашему API поверх любого Moonraker — охват без ручной работы оператора.
- **«Прошивки сообщества»** → список `community_firmware` (MF-889): GitVerse-репо под эту/похожую
  модель, каждая с бейджем «не проверено нами» (`verified=false`). Ссылка наружу, не установка.

### Состояния (в терминах юзера)
- **Первый раз / парк пуст** — мастер приглашает, объясняет уровни спокойно, без стены текста.
- **Грузится** — проба IP / ожидание enroll / привязка вендор-аккаунта.
- **Ошибка** — «принтер не отвечает по этому адресу; вы точно в той же сети и Moonraker включён?»
  → тут же предложить `bridge` («хотите управлять и вне дома? поставьте наш агент»). Enroll-код
  истёк → «сгенерировать новый». Вендор-авторизация не прошла → назад к привязке.
- **NAT/недоступен из интернета** — не называем это просто «офлайн» и не предлагаем проброс порта.
  Показываем: **«Не удалось подключиться из интернета. Порт наружу открывать не нужно: подключите
  устройство к той же локальной сети и повторите проверку»**. Действия: **«Повторить проверку»**
  (шаг 2), **«Изменить данные»** (шаг 1 с сохранёнными полями), **«Назад в каталог»**. Доступ
  вне дома — отдельный `managed-bridge` с агентом, не обещание работы LAN-IP через NAT.
- **Нет прав / гость** — по тапу промпт входа (переиспускаем логин-флоу, [ux.md §1.2](../product/ux.md)),
  не молчаливый отказ.
- **Успех** — принтер в парке с верным бейджем уровня + следующий шаг («Открыть управление» /
  «Отправить печать»).

### Pass/fail для Front и QA (MF-1126)

- **Pass:** гость из `/catalog` попадает на `/park/add`; referrer и модель сохраняются; отмена
  логина возвращает в каталог, успешный вход — на тот же шаг.
- **Pass:** успешная LAN-проверка/enroll приводят в парк или деталь с одной записью; retry не
  создаёт дубль.
- **Pass:** loading блокирует повторный тап, поля не очищаются, каждая попытка показывает исход;
  после трёх ошибок доступно копирование данных поддержки.
- **Pass:** NAT-ошибка содержит LAN-only объяснение и три действия восстановления; UI не предлагает
  открывать порт и не утверждает, что LAN-IP доступен через интернет.
- **Fail:** потеря модели/IP/шага при логине или retry, «офлайн» без причины, бесконечный retry,
  дубль устройства или возврат после отмены на пустой мастер.

### Связи
Онбординг `PrinterPicker` → мастер уровня → парк (бейдж) → управление (managed: браузер↔Moonraker
или через агент; custom: морда MF-891) · каталог MF-892 «У меня такой» → мастер · тупик →
«Сделать самому»/«Прошивки сообщества» · «не нашли модель» = ручной ввод (сигнал спроса, уже есть).
Бейджи уровня — общий словарь с каталогом (визуал бейджей — MF-891, страница — MF-892).

### Крайние случаи / где заабьюзят
- **«По IP», потом ушёл из дома** → в парке принтер честно «доступен только в вашей сети», когда
  браузер не в LAN. Ожидание задано бейджем заранее — не сюрприз.
- **IP на произвольный адрес** → проба и запросы идут ИЗ браузера, сервер по чужим адресам не
  ходит (нет SSRF) — это и есть причина, почему local = браузер-напрямую.
- **enroll-код утёк** → одноразовый, индивидуальные креды на устройство, отзыв на устройство
  (MF-887). Дубликат физического принтера → дедуп по идентити устройства (агент) / варнинг на
  совпадении IP+модель.
- **Прошивка custom деструктивна** → «Поставить прошивку» за «доступ по запросу» + явное
  предупреждение, не однотапно. Marlin-модели (Ender-3 V3 SE) → мастер честно «прошивка не идёт»,
  только `list` + выходы наружу.

## Архитектура «агента» (custom-уровень)

### Приёмка команд через реконнект (MF-1178)

Пилот использует неизменённый frame/ack-контракт MF-844. Проверяются offline-доставка без двойного
исполнения после reconnect, role/token binding, capability allowlist, срок токена и защита
`nonce`/`sequence` от replay. `cancel`/`stop` имеют приоритет. ACK/error публикуются с
`correlation_id`, после ACK сверяется состояние Moonraker, а нормализованный результат для QA и
аудита не содержит токенов или payload-секретов. Реализация и тесты relay: SHA
`9c46be9bbd45b7483a2519fda5e34873f9ae3a9a`, Relay, 12.07.2026.

### Приёмка команд через реконнект (MF-1178)

Для пилота safe-command delivery используется неизменённый frame/ack-контракт MF-844. Приёмка
проверяет полный маршрут `API → queue → relay → agent → Moonraker`: офлайн-команда переживает
реконнект, но подтверждённая команда не исполняется повторно. Перед исполнением обязательны
привязка роли и токена к устройству, capability allowlist, непогашенный срок токена и защита
`nonce`/`sequence` от replay; viewer без права команды и просроченный токен отклоняются.

`cancel`/`stop` имеют приоритет над обычными командами. ACK/error публикуются с `correlation_id`,
а после ACK выполняется авторитетная сверка состояния с Moonraker. Наружу отдаётся нормализованный
результат для QA и аудита без токена и секретов payload: `command_id`, `correlation_id`, итоговое
состояние и безопасный `error_code` при ошибке. Реализация и тесты зафиксированы в relay, SHA
`9c46be9bbd45b7483a2519fda5e34873f9ae3a9a`, автор Relay, 12.07.2026; контракт MF-844 не менялся.

```
┌─ Принтер (Klipper-железо) ──────────────┐        ┌─ Наш сервер (портал) ─┐
│ Klipper (движок) ── Moonraker (API)     │        │  relay-приёмник       │
│        ▲                    ▲            │        │  (WS-туннель, MF-26)  │
│        │                    │            │        │  портал-аккаунт,      │
│   наш ВИЗУАЛ (морда)   наш АГЕНТ ────────┼──WSS──▶│  очередь, парк, соц   │

│                         Moonraker-драйвер)        │                       │
└─────────────────────────────────────────┘        └───────────────────────┘
```
- **Klipper** не трогаем как движок — он остаётся (проверенная кинематика/термика). Мы поверх.
- **Наш визуал** — форк KlipperScreen (экран принтера) и/или веб-морда (форк Mainsail/Fluidd или
  своя) в стилистике портала. Точка входа пользователя в экосистему прямо с принтера.
- **Наш агент** — systemd-сервис на принтере: enroll (одноразовый код → индивидуальные креды,
  MF-390), outbound WSS-туннель к relay (работает за NAT), драйвер поверх Moonraker (телеметрия/
  команды/файлы/камера, MF-391), деградация без сети. Слабое ARM-железо → лёгкий бинарь/скрипт.
- **Безопасность**: устройство — недоверенная среда; enroll с индивидуальным ключом, отзыв на
  устройство, канал только outbound (MF-423..425).

### Контракт кода и credential (MF-1214)

Подробный эксплуатационный контракт и dev-проверка находятся в
[архитектуре серверного слоя §2.3](../architecture/printer.server.md#23-enroll--identity). Для
пилота важно зафиксировать: enroll-код одноразовый, хранится только как SHA-256 и живёт не более
15 минут; success — `POST /devices/agent/enroll` с `201`, повторное использование или истечение —
детерминированный `401 invalid_or_expired_code`. Обмен атомарен, поэтому сбой подписи credential не
сжигает код.

После обмена агент получает JWT `typ=agent` с TTL 400 дней (около 13 месяцев). Credential нельзя
писать в логи; `AGENT_JWT_SECRET` — только dev/test-секрет в окружении, production-секреты в
документации и проверках не используются. Отзыв доступен владельцу на конкретное устройство,
помечает `agents.revoked_at`, переводит устройство в `offline`, а на следующем подключении/реконнекте
даёт тот же нормализованный `401 {"error":"invalid_token"}`, что и любой неверный или неизвестный
credential. Уже открытая сессия не рвётся мгновенно; отзыв не инициирует команду или печать и не
затрагивает другие устройства владельца. Ротация выполняется через revoke → новый enroll-код → новый
обмен. Фактический обработчик и тесты: [`relayInternal.ts`](../../apps/api/src/devices/relayInternal.ts),
[`relayInternal.test.ts`](../../apps/api/src/devices/relayInternal.test.ts).

## Разбивка по слоям (для CTO/Lead при нарезке — стейджи по зависимости)

- **stage 1 — Data**: `support_level` (list/managed/custom) + `firmware_ready` + `firmware_public`
  + `connector_type` в схеме; `firmware_repo` (GitVerse-URL образа, даёт оператор); таблица
  `community_firmware` (model, автор, git_url, verified); user_printers.link_source (manual/ip/agent).
- **stage 2 — Back**: Moonraker-коннектор (managed: статус/старт/стоп/G-code по IP+enroll);
  relay-приёмник агента (custom, MF-26); enroll-контур (MF-390); **публичный API управления/интеграции
  принтера** (для «сделай сам») + его дока.
- **stage 2 — Design/UX**: сценарий «добавить принтер» (заявить/по IP/наш агент); визуал морды
  принтера (KlipperScreen-форк + веб-морда портала); UI уровней в каталоге; экраны «Сделать самому»
  и «Прошивки сообщества».
- **stage 3 — Front**: страница принтера с бейджем support_level; на поддержанном — «Управлять»/
  «Поставить прошивку» (доступ по запросу, пока приватно); на неподдержанном — **«Сделать самому»**
  (→ дока публичного API) и **«Прошивки сообщества»** (→ список GitVerse-репо); фасет каталога по уровню.
- **Прошивка-трек**: 🔴 образ/OS собирает ОПЕРАТОР вручную (не агенты), образы в ОТДЕЛЬНЫХ git-репо.
  Агенты делают: визуал (морду), агент-туннель, публичный API, каталог прошивок, скелет git-репо
  принтера + инструкции, страницы доставки. В карточке модели — только ССЫЛКА на репо/образ оператора.
