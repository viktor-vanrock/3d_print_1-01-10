# RACI: центр доверия для API-ключей и ownership

Статус: handoff-контракт для code-карт v1, 2026-07-13. Документ не меняет
схему, API или поведение приложения.

## Границы решения

В работе существуют два разных контура, которые нельзя смешивать:

- `user_api_keys` — канонические ключи пользователя для scopes `slicing`,
  `printer`, `public_api`. Здесь живут ownership, ротация через
  `rotated_from_id`, статус и зашифрованные vendor-секреты.
- `api_keys` — legacy-контур публичного API v0. Его `owner_id`, `key_hash`,
  scopes `read/control` и аудит остаются отдельным контрактом до специального
  решения о миграции. Новые изменения `user_api_keys` не являются миграцией
  `api_keys` и наоборот.

Владелец ключа определяется связью с пользователем; владение принтером —
`user_printers.user_id`. `device_shares` добавляет доступ, но не передаёт
ownership. Проверка разрешений должна различать владельца, делегированную роль
и отсутствие доступа.

## Матрица RACI

Обозначения: **R** выполняет работу, **A** принимает решение и отвечает за
результат, **C** консультирует, **I** получает handoff/evidence.

| Артефакт / решение | Product/Trust | Data/DB | Back/API | Security/QA | UX | Dev Delivery |
|---|---:|---:|---:|---:|---:|---:|
| Каноническая модель `user_api_keys` и scopes | A | R | C | C | I | I |
| Legacy `api_keys` и граница совместимости v0 | A | C | R | C | I | I |
| Ownership `user ↔ printer` и роли `device_shares` | A | R | C | C | C | I |
| Authorization / denial и отсутствие утечки существования | A | C | R | R | C | I |
| Revoke/rotate: атомарность и race-сценарии | A | C | R | R | I | I |
| Audit trail и redaction секретов | A | R | R | A | I | I |
| UX: создание, одноразовый показ, revoke/rotate, denial | C | I | C | C | A/R | I |
| Миграции, API-контракт и тестовые evidence | I | R | R | C | I | A |
| Delivery handoff и проверка lineage | I | C | C | C | I | A/R |

Роли в таблице — функциональные владельцы потока; конкретный исполнитель
назначается в соответствующей code-карте. Если в одной карте появляются два
кандидата на **A**, Lead должен выбрать одного владельца до начала реализации.

## Непереговорные инварианты

1. Запрос к одному контуру не читает таблицу другого по умолчанию. Любая
   миграция или dual-read оформляется отдельным решением с планом прекращения.
2. `key_hash`/зашифрованный секрет не выдаётся в списках, логах, ошибках,
   audit-экспорте и UX после одноразового показа. Наружу допускается только
   безопасный `key_prefix` и редактированные метаданные.
3. Revoke и rotate должны быть атомарны относительно конкурентных запросов:
   после успешного revoke старый credential не проходит authorization; rotate
   сохраняет audit-связь и не создаёт два действующих результата из одного
   исходного ключа.
4. Отказ не раскрывает, существует ли чужой ключ или принадлежит ли принтер
   другому пользователю. Проверка ownership выполняется до действия, а
   denial фиксируется с минимально необходимыми redacted-данными.
5. Любой новый публичный ответ сохраняет действующий HTTP-контракт, если
   отдельная карта явно не согласовала его расширение.

## Handoff в Dev Delivery

Владелец каждой code-карты прикладывает ссылку на этот документ и указывает:

- какой контур меняется: `user_api_keys` или legacy `api_keys`;
- назначенных **A/R** и консультируемые роли;
- SQL/тестовое evidence для ownership, denial, race revoke/rotate и redaction;
- обратную совместимость API и точный способ отката.

Dev Delivery принимает карту только после проверки этих четырёх пунктов и
публикует в handoff фактические commit/CI/deploy evidence. Этот документ не
является разрешением на миграцию legacy-контура.
