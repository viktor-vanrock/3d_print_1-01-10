# Эпик: Всплывашки — уведомления, тосты, модалки, алерты печати

Issue-указатель: **MF-440** (доска `tasks.3mf.tech`). Дочерние фазы: **MF-441** (примитивы/слой) → **MF-442** (алерты печати ↔ MF-26) → **MF-443** (центр уведомлений/звук/интеграции). Стадии строго последовательны: MF-443 стоит на контрактах MF-441 и модели серьёзности MF-442.

Дизайн-каноны: [docs/design/status.alerts.md](../design/status.alerts.md) («яркость=важность»), [docs/design/motion.md](../design/motion.md) (reduce-motion, `setTimeout` а не rAF), [docs/design/readme.md](../design/readme.md) §Философия п.3-4-7. Примитивы — из библиотеки [MF-40] (`apps/web/src/ui/`). Токены — `apps/web/src/theme/tokens.css`.

Это **архитектурная спека**: она фиксирует общие контракты (типы, публичный API, слои, файлы), чтобы три фазы собирались из готовых примитивов, а не копипастились между экранами. Реализатор (агент TypeScript) следует ей пофазно.

---

## 1. Цель архитектуры

Один слой поверх контента, вызываемый из любого экрана четырьмя функциями — `toast()`, `confirm()/modal()`, `sheet()`, `alert()` — плюс центр уведомлений (колокол+лента) и звук по семантике. Провайдер один, стор один, портал один. Экраны не держат свой `useState` для оверлеев и не копируют разметку тостов/модалок.

Принцип «яркость=важность» — не косметика, а типовой контракт: `severity` — единственная ось, по которой система решает цвет, пульс, звук, приоритет очереди и роль для скринридера.

---

## 2. Ядро: единый тип серьёзности (общий контракт всех фаз)

Всё в системе кодируется одной осью. Заводится в MF-441, потребляется в MF-442/443.

```ts
// apps/web/src/overlay/severity.ts
export type Severity = "info" | "success" | "warn" | "critical";
```

Маппинг серьёзности на поведение (единая таблица — источник правды, а не разрозненные `if`):

| severity | токен цвета        | пульс | звук по умолч. | роль a11y | приоритет очереди |
|----------|--------------------|-------|----------------|-----------|-------------------|
| info     | `--text-dim`       | нет   | нет            | status    | 0                 |
| success  | `--accent`         | нет   | success        | status    | 1                 |
| warn     | `--accent-warn` (янтарь) | нет | warn        | status    | 2                 |
| critical | `--accent-danger` (коралл) | да | critical  | alert     | 3                 |

Правило «яркость=важность» и `urgCol()` из демо (≤10 мин → critical/коралл, ≤30 → warn/янтарь) реализуются в MF-442 как чистая функция `severityFromPrinter(status, ageMs)` поверх этого типа, **не** как новая параллельная шкала.

## 3. Слои и z-index (заводятся в MF-441, фиксируются здесь навсегда)

Текущее занято: капсула-поповер `20`, аватар-редактор оверлей/модал `50`. Резервируем непрерывный диапазон для системы оверлеев **выше** контента, но модалка над тостом, критичный алерт — над всем:

| Слой                       | z-index | Компонент                        |
|----------------------------|---------|----------------------------------|
| Контент/страница           | 1       | `.homeContent` и т.п.            |
| Поповеры капсулы           | 20      | `.homePopover` (как есть)        |
| **Тосты (очередь)**        | **60**  | `OverlayToaster`                 |
| **Правые панели/шиты**     | **65**  | `OverlaySheet`                   |
| **Модалки/confirm**        | **70**  | `OverlayModal`                   |
| **Алерт-хост печати**      | **75**  | `AlertHost` (critical — поверх)  |

Аватар-редактор (`50`) остаётся ниже системного слоя — при системном critical-алерте алерт видно поверх редактора (это желаемо). Значения — CSS-переменные `--z-toast/--z-sheet/--z-modal/--z-alert` в `tokens.css`, чтобы не хардкодить числа по компонентам.

## 4. Публичный API (императивный фасад + провайдер)

Один провайдер наверху дерева (`app.tsx`, рядом с `ThemeProvider`), один портал в `document.body`. Экраны зовут императивно через хук — без прокидывания пропсов.

```ts
// apps/web/src/overlay/index.ts — единственная точка импорта для экранов
export function useOverlay(): {
  toast(opts: ToastOptions): ToastHandle;
  confirm(opts: ConfirmOptions): Promise<boolean>;   // деструктив/да-нет
  modal(opts: ModalOptions): ModalHandle;            // произвольный контент
  sheet(opts: SheetOptions): SheetHandle;            // правая панель
  alert(opts: AlertOptions): AlertHandle;            // алерт печати (MF-442)
  notifications: NotificationApi;                    // центр (MF-443)
};
```

### Типы (черновой контракт — уточняется по фазам, но оси не меняются)

```ts
interface ToastOptions {
  severity?: Severity;          // дефолт info
  title: string;
  message?: string;
  duration?: number | "sticky"; // дефолт по severity: info/success 4с, warn 8с, critical sticky
  action?: { label: string; onAction: () => void }; // undo/перейти
}
interface ToastHandle { dismiss(): void; update(patch: Partial<ToastOptions>): void; }

interface ConfirmOptions {
  severity?: Severity;          // деструктив → critical (коралл-кнопка)
  title: string; message?: string;
  confirmLabel?: string; cancelLabel?: string;
  destructive?: boolean;
}

interface AlertOptions {
  severity: "warn" | "critical";
  printerId: string;            // дедуп-ключ: один алерт на принтер
  what: string;                 // «обрыв филамента» / «засор» / «термранэвей» / «отвал» / «офлайн»
  why?: string;                 // человекочитаемая причина, если известна
  actions: Array<{ label: string; onAction(): void }>; // [Пауза][Стоп][Разобраться→деталь]
}
```

`confirm()` возвращает `Promise<boolean>` — вызывающий пишет `if (await confirm(...))`, никакого колбэк-ада. Очередь: ≤1 модалка, ≤2 тоста одновременно; лишнее — в очередь по `severity`-приоритету (critical вытесняет info вперёд, но не удаляет).

## 5. Стор (единый, без внешних либ)

В проекте нет zustand/redux и заводить их не нужно — хватит `useReducer` + Context в провайдере. Один редьюсер держит: очередь тостов, стек модалок (глубина 1), открытый шит, карту алертов `Map<printerId, Alert>` (дедуп), ленту уведомлений, `muted`, счётчик непрочитанных.

Персист (localStorage, ключи в неймспейсе `portal.overlay.*`): `muted`, прочитанные id уведомлений. Токены/паттерн — как `portal.theme` в `theme.tsx`.

## 6. Раскладка по фазам (что в какой issue)

### MF-441 — Примитивы и слой (фундамент, идёт первым)
Файлы: `apps/web/src/overlay/{severity.ts, provider.tsx, store.ts, portal.tsx, toaster.tsx, modal.tsx, sheet.tsx}` + `overlay.css`; CSS-переменные `--z-*` и severity в `tokens.css`.
- Провайдер + портал + `useOverlay()` фасад (пока `alert`/`notifications` — заглушки-`noop`, вводятся в 442/443).
- `toast()` (все severity, автоскрытие, действие/undo, очередь ≤2), `confirm()/modal()` (фокус-трап, Esc/фон, затемнение, тач ≥48px, `role` по severity), `sheet()`.
- Severity-токены + пульс/glow keyframes с деградацией под `prefers-reduced-motion`/`Save-Data`. Триггеры появления — `setTimeout`, не rAF (грабля из [motion.md](../design/motion.md)).
- Готово: стресс 10 вызовов не ломает раскладку; успех-тост исчезает сам, ошибка держится до действия; модалка проходит фокус-инспектор и 375px без горизонт-скролла; critical заметен цветом+иконкой при reduce-motion.

### MF-442 — Алерты печати ↔ телеметрия MF-26 (ядро)
Файлы: `apps/web/src/overlay/alert/{severity-from-printer.ts, alerthost.tsx, reasons.ts}`.
- `severityFromPrinter(status, ageMs)` (правило `urgCol`), эскалация warn→critical по времени без реакции.
- `AlertHost` на слое 75: дедуп по `printerId`, автозакрытие при восстановлении, приглушённая сводка «печатают N» когда всё ок (0 attention-элементов). Каталог причин `reasons.ts` (обрыв/засор/термранэвей/адгезия/офлайн → человекочитаемое «почему»).
- Источник статусов MF-26: **открытый вопрос** — есть ли поток телеметрии к v1 или мок/ручные статусы (см. §8). Реализовать за интерфейсом `PrinterStatusSource`, чтобы мок и реальный поток были взаимозаменяемы.

### MF-443 — Центр уведомлений, звук, интеграции (эта задача, стоит на 441/442)
Файлы: `apps/web/src/overlay/notifications/{store слот, center.tsx, bell.tsx}` + `apps/web/src/overlay/sound.ts`.
- **Колокол+центр:** заменить хардкод в `home/homeheader.tsx` (`homeCapsuleBadge` "2" и статичные `NotificationRow`) на данные из стора. Бейдж = счётчик непрочитанных, открытие центра гасит, группы **печать / сообщения (MF-38) / система**, персист прочитанного, глубокая ссылка на источник (алерт печати → деталь принтера).
- **Звук:** `sound.ts` на WebAudio — `success/error/push/critical` синтезом (как демо), `mute`-тумблер в капсуле (рядом с колоколом). У новых пользователей звук выключен; сохранённый выбор тумблера не сбрасывается. Звук привязан к `severity` события, не зовётся напрямую экранами.
- **Интеграции:** гостевой пуш (MF-28) → `toast({severity:'info', action:'Открыть'})` владельцу; прогресс загрузок (MF-9) → `toast` с `update()` по прогрессу; деструктив везде → `confirm({destructive:true})`.
- Готово: событие поднимает бейдж и открытие гасит; звук играет по семантике после включения тумблером; гость→пуш-тост, загрузка→прогресс-тост, удаление→модалка.

## 7. Правила переиспользования (чтобы не плодить тех-долг)

- Экраны импортируют **только** `useOverlay()` из `overlay/index.ts`. Никаких прямых `createPortal`, локальных `useState('modalOpen')`, самописных тостов на экранах.
- Визуальные примитивы (карточка/кнопка/пилюля/иконка) — из `ui/` (MF-40). Слой оверлеев даёт **поведение** (портал, очередь, фокус-трап, оркестрация), а не новый визуал.
- Цвет/пульс/звук/роль выводятся из `severity`, а не задаются точечно на месте вызова.
- Существующий `avatareditor.tsx` (свой `createPortal`) — кандидат на миграцию в `modal()` **после** MF-441, отдельной мелкой задачей; в рамках эпика не трогаем, чтобы не расширять scope.

## 8. Открытые вопросы (нужны решения владельца перед MF-442/443)

1. **Источник статусов принтера к v1 (MF-26):** живой поток (ws/поллинг) или мок/ручные статусы как в демо? Влияет на `PrinterStatusSource`. По умолчанию проектируем за интерфейсом + мок.
2. **Порог «агрессивности» critical:** нужна ли опция «понятно, не напоминать N минут», чтобы не раздражать, но не проспать поломку.
3. **Область алерт-оверлея:** только дом/цех/деталь принтера или глобально на всех экранах (с приоритетом видимости)?
4. **Пуш вне вкладки** (Web Push/PWA, MF-42) — в этом эпике или отдельно? Решено: отдельно (MF-434, Фаза 3 эпика MF-42) — свой VAPID web-push транспорт на `api` (`apps/api/src/push/*`), здесь остаётся только in-app. Типы `like`/`comment` уже отправляются реально (`models/vote.ts`, `ideas/comments.ts`); `remix`/`sale`/`printer_status`/`new_order` заведены в схеме, но ждут своих источников событий (makes-роут, MF-17, MF-16/26 телеметрия).

## 9. Как выглядит результат эпика

Единый слой всплывашек: тосты/модалки/панели вызываются из любого экрана одним хуком; алерты печати по «яркость=важность» (норма — приглушённая сводка, поломка — янтарно/коралловый пульс+звук с причиной и действиями); центр уведомлений с колоколом+бейджем; звук по семантике с mute. Новый экран собирается из готовых примитивов — без копипаста разметки оверлеев.
