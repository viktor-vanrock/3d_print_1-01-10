# Мастер «добавить принтер» — визуал (MF-900)

← [docs/design/readme.md](readme.md) · сценарий/копирайт — [epics/printer.support.md § «Сценарий»](../epics/printer.support.md) (UX, MF-890) · принцип честности — [product/ux.md §6](../product/ux.md) · граница за NAT — [architecture/printer.server.md §1](../architecture/printer.server.md) · бейджи `support_level` в каталоге — отдельно в [MF-891](mention://issue/dedb31bb-2e55-4d04-b226-72fde8bde805), здесь только переиспользуем словарь тонов, не заводим второй.

**Что это.** Визуальная раскладка/состояния/хореография мастера `/park/add` и двух экранов-выходов для неподдержанных моделей. **Что не это** — сценарий, порядок вопросов и копирайт-логику уже дал UX (MF-890, таблица «Выбор юзера → уровень» в эпике); этот файл их ОДЕВАЕТ, не переизобретает. ## 0. Где живёт

- Роут `/park/add`, не оверлей — [ux.md §2](../product/ux.md): диплинк/шара/кнопка «назад» должны работать (юзер может прислать ссылку другу «вот как я подключал»), и юзер должен вернуться туда же, откуда пришёл.
- Точки входа (см. эпик §«Точки входа»): онбординг `PrinterPicker` (soft-предложение «а хотите ещё управлять?» после привязки) · ЛК/«Мой парк» (primary-кнопка «+ Добавить принтер») · каталог `/printers` → карточка модели (MF-892) «У меня такой» — префилл бренда/модели, шаг 1 пропускается визуально.
- Схема-опора (Data, MF-884, уже в dev): `printers.support_level` (`list/managed/custom`), `connector_type` (`moonraker/bambu-mqtt/prusa-link/octoprint/vendor-cloud/none/null`), `firmware_ready`/`firmware_public` (bool), `user_printers.link_source` (`manual/popular/search/connector/agent/ip`). Гейтинг плиток (§3.3 ниже) читает эти поля буквально — не выдумывает пятый.

## 1. Композиция (общая для обоих шагов)

- Одна колонка, `Card` по центру вьюпорта, `max-width` ≈ 560–620px (как формы логина), симметричные отступы — [layout.md](layout.md).
- Шапка мастера: круглая icon-кнопка «назад» (к парку) слева + прогресс **визуальный**, не только текст — переиспользуем заливку `.uiChecklistBarFill` (уже есть, `ui.tsx` `Checklist`) на 50%/100%, подпись рядом «Шаг 1 из 2»/«Шаг 2 из 2».
- **Один зелёный CTA видим одновременно** (принцип #2, readme.md) — на шаге 2 это ровно та развёрнутая под-панель уровня, что сейчас активна; остальные плитки не спорят с ней яркостью.

## 2. Шаг 1 — «Какой у вас принтер»

Переиспользуем `apps/web/src/home/printerpicker.tsx` (MF-437) **визуально как есть** — популярные чипы → поиск → «не нашли, ручной ввод». Дельта под мастер:

- Обернуть в шаг-контейнер (прогресс-бар сверху из §1); отдельной кнопки «Далее» нет — тап по чипу/результату поиска/сохранению ручной формы сразу переводит на шаг 2 (текущее поведение `onLinked`, просто теперь ведёт не «в парк», а «на шаг 2»).
- Ссылка «Позже» (`onSkip`) — только для onboarding-варианта того же компонента; в `/park/add` её нет (юзер уже сознательно открыл мастер, «позже» здесь = просто уйти с роута).
- После перехода на шаг 2 — модель остаётся на виду: маленький чип-бейдж над плитками («Ender-3 V3 KE» + line-иконка карандаша «изменить», тап возвращает на шаг 1 без потери прогресса).
- Префилл с карточки модели (MF-892, «У меня такой») — шаг 1 пропускается, мастер открывается сразу на шаге 2 с чипом модели уже проставленным.

## 3. Шаг 2 — «Что вы хотите делать» (плитки уровня, сердце спеки)

### 3.1 Компонент: строка-плитка уровня — расширение `ActionCard`, не новый компонент с нуля

`ActionCard` (`ui/ui.tsx`, `.uiActionCard` в `ui.css`) уже даёт ровно нужную форму: полноширинная строка, радиус `--card-radius` (28px), заголовок+подпись слева, круглая иконка-аффорданс справа, кликабельна целиком, свой градиент+обводка. Front добавляет только:

- `data-selected` (как в `SelectionTile`/`Chip`) — заливка промотирует к `--accent` **морфом**, не мгновенно (тот же паттерн, что тумблер/сегмент-выбор, [motion.md §7](motion.md)); правая иконка меняется со стрелки/шеврона на галочку (тот же svg, что `StatusPill done`).
- `data-disabled` — плитка НЕ прячется (принцип §6 ux.md), а приглушается: `opacity: .45`, курсор `not-allowed`, иконка справа — line-«замок»/тире вместо стрелки, тап неактивен (но текст читаем полностью, включая причину — см. §3.3).
- Второй ряд подписи: `sub` у `ActionCard` уже `ReactNode` — передаём фрагмент из двух строк: **что даёт** (обычная `.uiActionCardSub`, opacity .66) и **чем ограничено** (та же подпись, но со смысловым line-иконка-«инфо» перед текстом — не эмодзи, не восклицательный коралл: это факт, не ошибка).
- **Группа из пяти строк живёт ВНУТРИ одной внешней `Card`** (шаг 2 — сам `Card` с зерном), плитки — плоские разделённые строки без собственного зерна/своей обводки-карточки — пять наложенных друг на друга «стеклянных» карточек с зерном шумят визуально; зерно и обводка — на уровне контейнера шага, не строки. Выделение все ещё читается за счёт заливки/иконки/чекмарки при `data-selected`.
- Радио-семантика: выбор одной плитки снимает выделение с других (`role="radiogroup"` на обёртке, `aria-checked` на строке) — это ОДИН орган выбора ([ux.md §3](../product/ux.md)), не пять независимых тумблеров.

### 3.2 Пять плиток — заголовок / что даёт / чем ограничено (копирайт сверяется с UX-таблицей эпика, здесь — под тач-бюджет строки)

| Плитка | Заголовок | Что даёт | Чем ограничено |
|---|---|---|---|
| `list` | Просто отметить | В парке для сравнения, каталог сообщества | Управления нет |
| `managed-local` | Смотреть live state, пока дома | Live state через прямой запрос браузера к Moonraker; команды и upload в этом пути не входят | Работает только в вашей сети — сервер не ходит в LAN и не проксирует принтер |
| `managed-cloud` | Управлять из любой точки, через вендора | Опрос через облако производителя, прошивку не трогаем | (v1) Скоро — облако вендора едет в v2, пока недоступно |
| `managed-bridge` | Управлять из любой точки, через наш агент | Маленький сервис рядом с принтером, работает за NAT | Нужно установить агент (несколько минут) |
| `custom` | Полный портал на принтере | Наш визуал+агент на экране принтера, двусторонняя связь | Приватная прошивка — доступ по запросу (или «скоро», если `firmware_ready=false`) |

### 3.3 Гейтинг — приглушение с причиной, **два разных источника, не путать текстом**

Одна и та же визуальная обработка (§3.1 `data-disabled`), но подпись-причина называет источник честно — юзер должен понимать, ждать ли это вообще:

1. **Не подходит МОДЕЛИ** (`connector_type`/`firmware_ready` этой конкретной карточки принтера) → «**Недоступно этой модели**: …» — например `connector_type=none` (Marlin, Ender-3 V3 SE) → и `managed-*`, и `custom` гаснут разом с одной причиной «прошивка Marlin, наш агент и кастом-сборка сюда не встают».
2. **Ещё не сделали МЫ** (дорожная карта v1/v2, не свойство железа) → «**Скоро**: …» — `managed-cloud` в v1 (только Moonraker-адаптер готов, см. [printer.server.md §4](../architecture/printer.server.md)), или `custom` при `firmware_ready=false` (оператор ещё не собрал образ под эту модель).

Конкретно по гейтингу (буквально из полей, эпик §«Гейтинг уровней по модели»):
- `list` — всегда светится.
- `managed-local` — светится, если `connector_type ∈ {moonraker, prusa-link, octoprint}`.
- `managed-cloud` — в v1 приглушена ГЛОБАЛЬНО «скоро» независимо от модели (адаптер не готов); в v2 гейтится по `connector_type ∈ {bambu-mqtt, vendor-cloud}`.
- `managed-bridge` — светится, если наш агент умеет обернуть протокол модели (v1 = `moonraker`, как и `managed-local`).
- `custom` — светится (не серая), если `firmware_ready=true` для модели; иначе «скоро». Внутри светящейся — если `firmware_public=false` (сейчас всегда), кнопка ведёт не на открытую скачку, а на «доступ по запросу» (§3.4).
- Если `managed-*`/`custom` не светится НИ ОДИН — под плитками сразу видны (не за скроллом, не на отдельном «тупиковом» экране) два выхода §5.

### 3.4 Что происходит после тапа по плитке (раскрытие — инлайн внутри шага 2, НЕ шаг 3)

- **`list`** — сразу CTA primary «Добавить в парк», без доп. полей.
- **`managed-local`** — разворачивается панель: `Input` IP + `Button` «Проверить» (см. состояния §4).
- **`managed-cloud`** — в v1 не разворачивается (задизейблена §3.3).
- **`managed-bridge`** — разворачивается панель «Установить агент» → показ enroll-кода (см. §4).
- **`custom`** — если `firmware_ready`: разворачивается панель предупреждения + CTA «Запросить доступ» (НЕ однотапная кнопка — прошивка деструктивна, эпик §«Контролы»); если не `firmware_ready`: задизейблена «скоро».

## 4. Состояния (по каждому исходу таблицы UX эпика)

- **Проверка IP — идёт.** Кнопка «Проверить» морфит в кольцо-прогресс — тот же паттерн, что send-кнопка AI-поиска ([motion.md §3](motion.md)), не новый примитив.
- **Проверка IP — успех.** Hero-иконка-галочка дорисовывается (`stroke-dashoffset`, [motion.md §4](motion.md)), `StatusPill tone="ok" done` «Принтер найден», следом CTA primary «Добавить в парк».
- **Проверка IP — ошибка.** Приглушённый shake на группу инпут+кнопка + цвет-пульс к `--accent-warn` ([motion.md §4](motion.md)), текст ошибки **под инпутом** (не тост — должен остаться читаемым, пока юзер не поправит): «принтер не отвечает по этому адресу — вы точно в той же сети и Moonraker включён?». Сразу же вторичная ghost-кнопка-подсказка «Управлять и вне дома? Поставить агент» — ссылка на `managed-bridge`, не второй primary (иначе два равных CTA, против принципа #2).
- **Enroll-код (bridge/custom).** Код — крупный моноширинный текст в «hero-панели метрики» (components.md: залитая мятным карточка, тёмное крупное число/код) + короткая инструкция 1-2-3 (нумерованные кружки, dim). Статус ожидания — `StatusPill tone="dim"` «ждём агента…» (НЕ `pulse` — pulse зарезервирован под warn/critical, [status.alerts.md](status.alerts.md); здесь просто нейтральное ожидание, троеточие/спиннер, не тревога). Код истёк → баннер + ghost CTA «Сгенерировать новый».
- **Гость / нет прав.** Тап по `managed-*`/`custom` без сессии → login-overlay (переиспуск, [ux.md §1.2](../product/ux.md)) — не молчаливый disabled и не отдельная страница.
- **Успех (любой уровень).** Принтер в парке с верным бейджем (словарь MF-891) + следующий шаг («Открыть управление» для managed/custom, просто «Готово» → парк для `list`).

### 4.1 Credential отклонён или отозван — безопасное восстановление (MF-1294-D)

Этот сценарий относится только к `managed-bridge`/`custom` и к уже созданному
устройству в парке. Источник факта — нормализованный Fleet-статус
`invalid_token`, `unknown_agent` или `revoked` после следующего
connect/reconnect; UI не выводит HTTP-ответ, credential, JWT, сертификат или
сырое диагностическое сообщение. Контракт причины и момент отзыва —
[printer.server.md §2.3](../architecture/printer.server.md#23-enroll--identity).

| Факт от Fleet | Что видит пользователь | Безопасное состояние и действие |
|---|---|---|
| `invalid_token` или `unknown_agent` | `StatusPill tone="warn"` «Связь с агентом отклонена» и текст «Подключение этого устройства не подтверждено. Управление недоступно.» | Карточка устройства остаётся в парке; последний снимок телеметрии остаётся помеченным временем, а не выдаётся за live. Все команды, включая печать, паузу и стоп, disabled с видимой причиной. Единственный primary CTA владельца — «Подключить заново». |
| `revoked` | `StatusPill tone="warn"` «Доступ агента отозван» и текст «Для этого устройства нужна повторная авторизация.» | То же `offline`-состояние, без попытки отключить другое устройство. CTA владельца — «Подключить заново»; повторный отзыв не предлагается. |
| Пользователь начал recovery | Под текущим устройством открывается существующая enrollment-панель: «Создаём новый код…» → «Ждём агента…». | Запрашивается новый одноразовый код, затем агент выполняет новый обмен. Старый credential никогда не повторяется и не отображается. Новый enroll-код допустим только в этой одноразовой панели, не записывается в URL/local storage/лог и после закрытия, перезагрузки или истечения заново не показывается. |
| Fleet подтвердил новый connect и живой кадр | `StatusPill tone="ok"` «Агент на связи», в evidence «Восстановлено». | Тот же `user_printer.id` остаётся в парке; команды становятся активны лишь после подтверждённого API live-сигнала, не после генерации кода. |
| Recovery не подтвердился или код истёк | Явная причина рядом с панелью: «Код истёк» либо «Нет связи с порталом». | Устройство по-прежнему `offline`; доступно только «Сгенерировать новый» или «Повторить». Ни печать, ни upload, ни прошивка, ни физический reset этим сценарием не запускаются. |

`role="alert"`/`aria-live="assertive"` объявляет отказ и истечение кода;
первичный CTA и текст причины остаются доступны с клавиатуры, тач-цели не
меньше 48px. Причина всегда передаётся текстом и `StatusPill`, не только
цветом. Для пользователя без права владельца recovery-CTA не показывается:
остаётся текст «Обратитесь к владельцу устройства». В evidence и тестовых
fixture запрещены любые значения credential, Bearer, JWT, сертификата и
enroll-кода; допустимы только безопасный код причины и подтверждённый статус.

### 4.2 Единая карта состояний: `/park/add` → LAN/enroll → первая печать (MF-1489)

Это контракт **копии и наблюдаемого UI**, а не новый визуальный паттерн:
используем уже описанные `ActionCard`, inline-панель, `StatusPill` и карточку
операции. «Первая печать» начинается только после успешной привязки и живёт
на `/printer/:id`; её детальный автомат —
[printer.offline-command-states.md §4](printer.offline-command-states.md#4-g-code-выбор-проверка-передача-и-старт).
Для live-доказательств и `last_confirmed_at` на этой поверхности действует
каноническая матрица [printer.face.md §2.5](printer.face.md#25-честность-про-офлайн-симметрично-мастеру);
таблица ниже описывает только переходы мастера и не заводит второй словарь
`support_level` или тонов.
Ни один переход ниже не может быть выведен локальным таймером или HTTP-кодом
без факта от LAN/Bridge/Fleet.

| Состояние | Наблюдаемый факт и user outcome | Копия и действие в `/park/add` / LAN / enroll | Копия и действие для первой печати | Recovery | Владелец дефекта при расхождении |
|---|---|---|---|---|---|
| `idle` | Операция ещё не запущена; выбранные модель, уровень и введённый IP остаются видимыми. | «Проверьте подключение принтера» / «Установите агент»; primary — «Проверить» или «Показать код». | «Выберите файл G-code»; печать не обещана. | Пользователь запускает явное действие. | **Front** — потеря выбранного уровня, IP или фокуса. |
| `loading` | Проверка LAN, выпуск кода, ожидание агента, передача или подтверждение запуска ещё не имеют исхода. | «Проверяем подключение…», «Создаём новый код…» или «Ждём агента…»; primary показывает progress и не создаёт второй запрос. | «Загружаем на принтер: {n}%» либо «Запуск в очереди; печать не подтверждена». | «Отмена» только если её поддержал контракт; после deadline — явное «Проверить снова». | **Bridge** — неэмитированный/некорректный lifecycle-факт; **Front** — дублирующий запрос или бесконечный spinner. |
| `success` | Есть ровно тот факт, который подтверждает этап: LAN отвечает; агент подключился; файл получил `file_complete`; печать — только после свежего snapshot `printing`, не после `202` или ACK. | «Принтер найден» → «Добавить в парк»; «Агент на связи» → «Открыть управление». | «Файл загружен на принтер» → «Запустить печать»; затем «Печать началась» только при подтверждённом `printing`. | Продолжить следующий явный шаг, не повторять завершённый автоматически. | **Bridge/Fleet** — ложный или пропущенный факт; **Front** — преждевременный success-copy. |
| `error` | Пришёл безопасный terminal error конкретной операции; контекст и предыдущий безопасный ввод не теряются. | Под полем: «Не удалось проверить подключение: {reason}»; для enroll: «Не удалось подключить агента: {reason}». Никаких raw HTTP, токенов или диагностик. | «Загрузка не завершена: {reason}» либо «Команда не выполнена: {reason}». | Только действие, которое названо причиной: «Повторить», «Выбрать файл заново» или «Разобраться». | **Bridge** — unsafe/неверно классифицированная причина; **Front** — причина скрыта, ввод потерян или действие не соответствует причине. |
| `offline` | LAN/агент/принтер недоступен, но отзыв credential не подтверждён. Старые данные не называются live. | Для `managed-local`: «Принтер не отвечает по этому адресу. Проверьте, что вы в той же сети и Moonraker включён». Для bridge: «Нет связи с агентом» + последнее подтверждённое время, если есть. | «Нет связи с принтером»; upload и remote-команды заблокированы, не поставлены в скрытую очередь. | «Проверить связь»; после `online` перечитать незавершённую операцию. | **Bridge** — неверный offline/liveness-факт; **Front** — stale выдан за live или кнопки остались активны. |
| `expired` | Одноразовый enroll-код истёк или уже использован; это не отказ агента и не сетевой диагноз. | «Код истёк» рядом с панелью; старый код не показывается повторно. | Не применяется к уже стартовавшей печати: управление остаётся недоступным, пока owner не восстановит связь. | Owner: «Сгенерировать новый» и пройти новый enroll; старая карточка устройства сохраняется. | **Bridge** — код принят после expiry/replay либо lifecycle не отдан; **Front** — повторно показан старый код. |
| `revoked` | Bridge/Fleet передал безопасный `revoked`/`credential_rejected`; это не «плохой интернет». | Для текущей привязки: «Доступ агента отозван. Для этого устройства нужна повторная авторизация». | «Доступ агента отозван»; нет upload, печати, auto-retry и попытки продолжить старую операцию. | Только owner видит «Подключить заново» → новый enroll; остальные — «Обратитесь к владельцу устройства». | **Bridge/Fleet** — неразличение revoke и offline; **Front** — предложен обычный retry или раскрыта техническая причина. |
| `retry` | Пользователь явно начинает допустимую повторную попытку после `error`/`offline`; она сохраняет контекст, но не подменяет revoke или success. | «Проверяем подключение снова…»; IP, модель и выбранный тип подключения сохраняются. При LAN-ошибке вторичный путь — «Управлять и вне дома? Поставить агент». | При `next_seq` — «Возобновляем загрузку…» с тем же `transfer_id`; без него — «Выбрать файл заново». Старт печати повторяется только после свежего статуса. | Следовать разрешённому переходу в `loading`; после второго terminal-факта снова показать его причину. | **Front** — сменён тип подключения, потерян контекст или auto-retry; **Bridge** — неидемпотентный повтор/неверный `next_seq`. |

#### 4.2.1 Честная NAT-copy: локальная доступность — не ошибка сервера

`managed-local` выполняет запрос из браузера/локального контура: сервер не
ходит в LAN и не проксирует принтер. Поэтому Front не заменяет локальную
недоступность общим «Ошибка сервера», а Bridge/Fleet не маскирует отказ
credential под LAN-проблему.

| Факт | Разрешённая копия и следующий шаг | Запрещено |
|---|---|---|
| LAN IP не отвечает или браузер больше не в домашней сети | «Этот способ работает только в вашей сети. Проверьте Wi‑Fi и доступность Moonraker.» → «Проверить снова»; вторичный путь — «Управлять и вне дома? Поставить агент». | «Сервер не смог подключиться к вашему принтеру», обещание серверного retry или смена `managed-local` на bridge без тапа. |
| Портал/Bridge недоступен при выпуске кода или ожидании агента | «Нет связи с порталом. Код и подключение агента не подтверждены.» → «Повторить»; состояние принтера остаётся неизвестным. | Текст про домашний Wi‑Fi/LAN, «агент подключён» без connect и показ raw HTTP. |
| Credential отозван/отклонён | «Доступ агента отозван» → только owner «Подключить заново». | «Проверьте Wi‑Fi», обычный retry или повторный показ старого enroll-кода. |

#### 4.2.2 Handoff Front ↔ Bridge

- **Front:** один mapping состояний без локального enum по HTTP; сохраняет
  модель/IP/тип подключения до явной отмены, выводит текст + `StatusPill`,
  `focus-visible`, `aria-live` для отказа/истечения и touch-цели ≥48px. Для
  первой печати использует только нормализованные поля/fixtures из
  [state/copy reference](printer.offline-command-states.md#7-контракт-который-нужен-front).
- **Bridge/Fleet:** в fixture и runtime отдаёт безопасный lifecycle-факт для
  LAN timeout/offline, `pending`/connect, `expired`/replay, `revoked` и
  reconnect; не передаёт IP, serial, enroll-код, credential или raw error.
  `file_complete`, command ACK и snapshot `printing` остаются разными
  фактами.
- **При расхождении:** Front заводит дефект владельцу из таблицы с
  безопасным state, correlation id/временем и viewport; Bridge прикладывает
  redacted fixture/evidence. Оба не исправляют контракт optimistic fallback.

Связанный state/copy reference закрепляет тот же маршрут для экрана первой
печати: [printer.offline-command-states.md §8](printer.offline-command-states.md#8-связь-с-мастером-parkadd-и-граница-nat-mf-1489).

#### 4.2.3 Связь и команда: взаимоисключающая матрица (MF-1498)

Эта матрица закрывает наблюденный в MF-1168 конфликт: после `online` не
остаются одновременно старый баннер «Нет сети» и новое состояние готовности.
На экране устройства есть **ровно один** текущий статус связи. Карточка
команды — отдельная ось: она не заменяет статус связи и не меняет его
локальным таймером. Канонический порядок и поля —
[printer.offline-command-states.md §2.1](printer.offline-command-states.md#21-правило-одного-статуса-и-двух-независимых-осей-mf-1498).

| UI-state | Факт от runtime | Label и причина | Доступное действие | Выход / запрещённая комбинация |
|---|---|---|---|---|
| `online` | `live=true` и свежий snapshot. | `Принтер на связи`; «Обновлено {state_updated_at}». | Доступные роли и capability команды; «Обновить статус». | Только после нового offline/stale-факта. Не показывать offline/reconnecting banner или stale-label одновременно. |
| `offline` | `live=false` или `state="offline"`; причины revoke нет. | `Нет связи с принтером`; «Последняя связь {last_seen_at}». | `Проверить связь`. Все remote-команды и upload disabled с видимой причиной. | `reconnecting` при явной попытке восстановления либо `online` только после свежего snapshot. Не создавать скрытую очередь. |
| `stale` | Runtime пометил snapshot устаревшим либо не пришёл новый `seq` до `stale_after_at`. | `Данные устарели`; «Последнее обновление {state_updated_at}». | `Обновить статус`; значения остаются видимыми с временем. | `reconnecting` или `online` после более нового `seq`. Не называть температуры и прогресс live. |
| `reconnecting` | После `offline`/`stale` runtime начал восстановление, но свежего snapshot ещё нет. | `Восстанавливаем связь…`; старые данные остаются помеченными временем. | После server deadline — `Проверить снова`. | `synced`/`online` только после нового snapshot; `offline` при неудаче. Не оставлять старый offline-banner вторым уведомлением и не крутить бесконечный spinner. |
| `synced` | После reconnect получен snapshot с `seq` новее показанного и актуальным `state_updated_at`. | `Связь восстановлена`; «Данные обновлены». Одноразовое `polite`-сообщение, затем обычный `online`. | `Обновить статус`; после сверки — доступные команды. | Автоматически переходит в `online` после объявления. Нельзя считать синхронизацией только исчезновение баннера или успешный HTTP-ответ. |
| `command_blocked` | Пользователь не отправлял команду: связь `offline`/`stale`/`reconnecting`/`revoked`, нет роли либо capability. | У кнопки: `Команда недоступна: {безопасная причина}`. | Действие из причины: `Проверить связь`, `Подключить заново` только owner либо `Обратиться к владельцу`. | После устранения причины пользователь запускает новую явную команду. Не писать «в очереди» и не выдавать `command_id`. |
| `command_queued` | API **подтвердил** `202` с `command_id` и `status="queued"`. Это возможно для уже принятой операции; Front не создаёт его из offline-состояния. | `{Действие} в очереди; выполнение не подтверждено`. | `Проверить статус`; `Отменить команду` только при подтверждённой API-policy. | `sent`/`ack`/`error`/`timeout` только по runtime-факту. Не менять telemetry, не писать «выполнено» и не показывать как `command_blocked`. |

Для обычного изменения связи используем один `aria-live="polite"`-узел;
ошибка или отзыв — один `role="alert"`. Визуальный тон, иконка и текст
дублируют друг друга; disabled-кнопка не является единственным объяснением.
Контраст и фокус из §4.2.2 и state/copy reference обязательны также для
баннера, карточки очереди и действия recovery.

### 4.3 Ограниченный `safe test job`: отдельная control surface (MF-1539)

Это не обычное управление принтером и не обещание, что удалённая команда
доступна. Панель появляется только для явно переданного runtime-факта
`safe_test_job=true` вместе с allowlist. Она нужна QA/оператору для безопасной
проверки и располагается на `/printer/:id` отдельным блоком **«Проверка test
job»** под статусом связи, а не в мастере добавления. Мастер может привести к
этому экрану, но не создаёт capability и не выводит режим из модели, роли или
успешного HTTP-ответа.

В нормальном состоянии блок использует тот же тёмный `Card` и один яркий
акцент дизайн-системы: primary — только следующее допустимое действие, а
«Проверить статус» остаётся нейтральным. В заголовке всегда видны режим и
источник факта: «Ограниченный test job» + `live` либо `mock`. Не показывать
маркер как «безопасный принтер»: безопасна только конкретно подтверждённая
test job и только её allowlist.

| UI-state | Достаточный факт | Что видит человек | Доступное действие / запрет |
|---|---|---|---|
| `unavailable` | Нет `safe_test_job=true`, allowlist отсутствует/неизвестен или capability не распознана | «Управление test job пока недоступно» и «Нужен подтверждённый safe marker и список разрешённых действий». | Только `Проверить статус`. Никаких оптимистичных controls и скрытой очереди. |
| `available` | Safe marker подтверждён, связь свежая, нужное действие есть в allowlist и допускается текущей ролью/состоянием job | «Доступно для этой test job: {действие}». | `query` всегда называется «Проверить статус»; `pause`/`resume` показываются лишь когда каждый из них разрешён текущим snapshot. |
| `restricted` | Marker и allowlist валидны, но набор намеренно уже обычного управления | «Разрешены только проверка статуса, пауза и продолжение». Ниже статичный список «Запуск, остановка, cancel, G-code и upload не входят в test job». | В DOM нет интерактивных `start`/`stop`/`cancel`, upload и произвольной команды; серый вид кнопки не должен намекать, что их можно разблокировать. |
| `denied` | API/контракт вернул безопасный отказ, например `command_denied`, `safe_test_job_required`, `role_forbidden` или `unknown_command` | `Действие не разрешено для этой test job: {безопасная причина}`. Сохраняются время и request/correlation ID в раскрытых деталях. | Не повторять автоматически; показать `Проверить статус` и действие recovery из причины. Для `start`/`stop` не рисовать кнопку даже после отказа. |
| `stale` / `offline` | Соответствующее нормализованное состояние связи из [state-spec](printer.offline-command-states.md#2-связность-устройства) | `Данные test job устарели` / `Нет связи с test job` + время последнего факта. | Все команды заблокированы с видимой причиной, единственное recovery — `Обновить статус`/`Проверить связь`. Не ставить команду в очередь. |
| `mock-only` | Runtime явно пометил среду `mock_only=true`; это не live-доказательство и не предположение Front | Бейдж «Mock: действия не управляют физическим принтером» и тот же lifecycle command card. | Допускаются только fixture-действия из mock allowlist; результат подписан «Проверка mock». Нельзя заменить этим бейджем live-статус, назвать результат проверкой железа или убрать blocker live-допуска. |

`available` и `restricted` могут быть видны одновременно: первый отвечает на
вопрос «можно ли сделать следующий разрешённый шаг сейчас», второй — «почему
экран не является полным пультом». Любой неизвестный marker, команда, роль,
исход или режим среды всегда ведёт в `unavailable`, а не в `available`.
Front пересекает полученный allowlist с жёстким набором
`{query, pause, resume}`. Если runtime добавил туда `start`, `stop` или
незнакомое значение, это contract mismatch: включается `unavailable`,
создаётся blocker владельцу контракта, но новый control не появляется.
«Проверить статус» в `unavailable` — только уже доступное read-only
обновление snapshot; если для него понадобилась бы удалённая команда, кнопка
также отсутствует.

#### 4.3.1 Последовательность, confirmation и rollback

1. `query` не требует confirmation; он лишь запрашивает новый status и не
   меняет состояние job. До свежего ответа не переключать `stale`/`offline` в
   `available`.
2. Перед `pause` и `resume` открывается модальное confirmation с именем
   test job, точным глаголом и нейтральной кнопкой «Назад». Единственная
   яркая CTA повторяет глагол: «Поставить на паузу» или «Продолжить test job».
   В modal нет подстановки `start`/`stop` и нет общего «Подтвердить».
3. После accept показывается обычная command card из
   [state-spec §3](printer.offline-command-states.md#3-pause-resume-и-cancel-конечный-автомат):
   «в очереди» не означает «пауза выполнена». Изменение основного статуса
   допускается только после отдельного свежего `query`/snapshot.
4. Rollback — не автодействие. После подтверждённого `pause` UI предлагает
   разрешённый `resume` как **следующий** шаг с новой confirmation; после
   `resume` — `query`, подтверждающий возврат к согласованному состоянию.
   Пока outcome неизвестен, показываются «Исход паузы неизвестен» и
   `Проверить статус`; не отправлять вторую или обратную команду вслепую.
   Если rollback не подтверждён, это `denied`/`blocked` feedback, а не успех.

#### 4.3.2 Touch, keyboard и доступность

- Каждая доступная кнопка — реальный `<button>`, минимальная тач-цель 48×48
  CSS px; порядок Tab повторяет визуальный порядок: статус → details →
  `Проверить статус` → разрешённое действие. Confirmation возвращает фокус
  в вызвавшую кнопку при отмене или завершении.
- Причина недоступности написана рядом с блоком и связана с control через
  `aria-describedby`; одно только disabled-состояние, цвет или замок не
  объясняют ограничение. У статичного списка запретов нет ложной button- или
  link-семантики.
- Изменение связи и `query` объявляются одним `aria-live="polite"`; отказ,
  конфликт и timeout — одним `role="alert"`. Не дублировать объявление при
  каждом рендере и не читать raw error, IP, serial, credential либо payload.
- Текст имеет контраст не ниже 4.5:1, иконки/обводка focus — не ниже 3:1;
  видимый `:focus-visible` не заменяется тенью. Информация о `mock-only` и
  `restricted` дублируется текстом и иконкой. Motion confirmation/command
  card уважает `prefers-reduced-motion`.

Полный mapping runtime-полей, command lifecycle и приёмка Front — в
[printer.offline-command-states.md §3.1](printer.offline-command-states.md#31-ограниченный-safe-test-job-mf-1539).

## 5. Два экрана-выхода — «Сделать самому» и «Прошивки сообщества»

Точки входа: тупик мастера (§3.3, когда все `managed-*`/`custom` погашены — эти два выхода показываются сразу под плитками, не спрятаны) и карточка неподдержанной модели (MF-892, кнопки там — зона Front, экраны — здесь). Оба — **реальные роуты** (шарибельно/диплинк, [ux.md §2](../product/ux.md)): предлагаю `/printers/:id/diy` и `/printers/:id/community-firmware` (финальный нейминг — по согласованию Front/UX, не блокирует визуал).

### 5.1 «Сделать самому»

- `Heading` двухтоновый «Сделайте сами» + 2–3 предложения интро: публичный API портала работает даже без нашей прошивки, поверх любого Moonraker/родного API модели.
- Нумерованный список 1-2-3 (крупные dim-кружки с номером): прочитать доку API → написать свой коннектор → протестировать на своём принтере.
- CTA primary «Открыть документацию API» → доку публичного API (MF-888/896).

### 5.2 «Прошивки сообщества»

- Список `ActionCard` variant `secondary` (без стрелки-аффорданса — вместо неё справа `StatusPill tone="dim"` «не проверено нами»): модель/похожая, автор, тап по всей строке уводит на GitVerse-репо (`target="_blank"`, внешняя ссылка, не разворачивается внутри портала).
- **Пусто** (для этой модели пока никто не публиковал) — `EmptyState`: иконка принтера, «Пока никто не опубликовал прошивку под эту модель», secondary CTA во вне («Как опубликовать свою» → инструкция/GitVerse).
- `verified=false` бейдж — нейтрально-серый (`tone="dim"`), НЕ `warn`/`danger`: это факт («не проверено нами»), не ошибка — coral/янтарь здесь читался бы как «что-то не так», а сообщество просто не промодерировано ещё.

| Два экрана-выхода, карточки-строки | [motion.md §1](motion.md) | `tick` |

Единственное, что реально новое, — сама последовательность (плитка→панель→прогресс→успех), а не новый визуальный примитив; Front собирает её из уже специфицированных кусков.

## 7. Готово когда (проверяемо, Front)

- Шаг 1 переиспользует `PrinterPicker` без визуальных изменений формы, только шаг-обвязка (прогресс, без «Далее», без «Позже» в контексте `/park/add`).
- Все 5 плиток отрисованы на `ActionCard`-базе с `data-selected`/`data-disabled`, радио-семантика, зерно только на внешнем `Card` шага, не на строках.
- Приглушение с причиной различает «недоступно этой модели» vs «скоро» текстом (§3.3) — не одна общая надпись «недоступно».
- Состояния IP (idle/loading/success/error) и enroll (код/ожидание/истёк) отрисованы по §4.
- `safe test job` отрисован только при подтверждённых marker и allowlist:
  есть `available/restricted/denied/stale/offline/mock-only/unavailable`,
  `query/pause/resume` не смешаны с `start/stop`, confirmation и feedback
  rollback следуют §4.3.
- Оба экрана-выхода (§5) — реальные роуты, не оверлеи; пустое состояние community-списка отрисовано.
- Хореография — по таблице §6, без изобретения новых motion/sound примитивов.
