## 1. Словарь «Проектов»: финальные RU-формы

**Решение эпика Р1 принято:** публичный раздел называется «Проекты» с этого эпика, витрина одна (не два раздела). Механика — строго план [projects.md](projects.md) §1.3 (мини-словарь форм `entityNoun`, одномоментная замена, ноль перевёрстки, обратимо). Здесь — **финальные строки**; Front подставляет их дословно, без додумывания.

### 1.1 Открытый вопрос §7.1 эпика: таб «Проекты» vs «Маркетплейс» — рекомендация **«Проекты»**

Дефолт эпика — «Проекты»; аргументирую **за дефолт**:

1. **Дух запроса Валерия** — переименование раздела, не косметика подписи. Полу-переименование («заголовки — Проекты, таб — Маркетплейс») оставит расщепление термина в самом заметном месте навигации.
2. **Честный UI теперь совпал с термином.** Раньше «Проект» был обещанием мульти-артефактности, которого не было (аргумент projects.md §1.1 за «Модели»). Этот же эпик (Р2) реально открывает мультиформат — обещание перестаёт быть пустым, «Проекты» стало честным.
3. **Обратимость дешёвая** (projects.md §1.3): термин — флаг/конфиг над мини-словарём, не деплой. Если пользователи путаются (метрики/фидбэк) — откат словом.

**Итог:** таб в капсуле `HomeHeader` = **«Проекты»**. Структура навигации не меняется (один вход в витрину, §1.2 projects.md). Финально — Валерий; если он выберет «Маркетплейс» на табе — меняется одна строка таблицы §1.2, остальное остаётся.

### 1.3 Мини-словарь форм `entityNoun` (финальные значения) + RU-плюрализация

projects.md §1.3 предписал завести `entityNoun` как задел со значением «модель». **Теперь значение — «проект».** «Проект» — мужской род, неодушевлённый; винительный = именительный. Финальная структура:

```
entityNoun = {
  singular:    'проект',          // им.п. ед.ч. — «страница проекта»
  singularAcc: 'проект',          // вин.п. ед.ч. — «Найти проект…», «Добавить проект»
  plural:      'проекты',         // им.п. мн.ч. — таб, «Проекты @username»
  add:         'Добавить проект',
}
```

**RU-плюрализация счётчика** (строка 15 таблицы — «N проектов» на профиле, счётчики). Одной формы мало; Front берёт форму по числу:

```
plural(n): 
  n % 10 === 1 && n % 100 !== 11            → 'проект'     // 1, 21, 31…
  n % 10 in [2,3,4] && !(n % 100 in [12,13,14]) → 'проекта' // 2, 3, 4, 22…
  иначе                                     → 'проектов'   // 0, 5, 11, 12…
```

Примеры: `1 проект`, `2 проекта`, `5 проектов`, `11 проектов`, `21 проект`. Это единственное место, где нужна плюрализация; остальные строки таблицы §1.2 — фиксированные. **URL и API-пути не меняются** (`#/market/...`, `/models`) — словарь отвязан от схемы (projects.md §1.3, эпик Р1).

## 2. Флоу загрузки мультиформата: два класса приёма

Реализация Р2 эпика в UI. Портал принимает не-печатные форматы **сейчас**, честно разделяя два класса — без обещаний конвертации/просмотра, которых нет (принцип честного UI, [../epics/marketplace.md](../epics/marketplace.md) §1.6; инвариант projects.md §3.2 «Скачать как есть»).

### 2.1 Два класса приёма (UI-контракт)

| Класс | Форматы (ориентир) | Что делает портал | Подпись в UI | Статус после загрузки |
|---|---|---|---|---|
| **Конвейерный** | STL, OBJ, 3MF | конвертирует в канонический 3MF, строит превью/вьюер | «Печать · сконвертируем в 3MF» | `processing`→`ready` (как сегодня) |
| **Артефакт «как есть»** | STEP (.step/.stp), DXF, SVG, G-code/NC, Gerber, ZIP-архив кода | хранит и отдаёт **как есть**, ничего не конвертирует | «Артефакт · сохраним как есть» | сразу `ready` (без конвейера) |

- **Точную роль/craft файла присваивает сервер** (Data/Mesh стадии 1 фиксируют реестр ролей и сигнатуры; формат→класс→роль — их контракт). UI **читает** присвоенный класс/роль из ответа и не хардкодит соответствие. До ответа сервера UI показывает класс по расширению как предварительный (быстрый фидбэк), финальный — из ответа.
- **`accept` в пикере расширяется** (подсказка, не защита): `.stl,.obj,.3mf,.step,.stp,.dxf,.svg,.gcode,.nc,.gbr,.zip` (финальный список — из formats.policy v0.2, Mesh). Реальная валидация — magic-байты на сервере (Back, стадия 2); UI на неё полагается, «по расширению» ничего не решает.
- **Подпись кнопки «Добавить проект»** (строка 6 §1.2) перечисляет оба класса честно: «STL · 3MF · STEP · чертежи · G-code · код — до 100 МБ». Не «любой формат» (обещание, которого нет за пределами списка).

### 2.2 Модалка «Добавить проект» — дельта к §3.2 marketplace.md

Раскладка §3.2 marketplace.md (дропзона → поля → отправка) **в силе**; дельта — класс приёма и честная маркировка:

- **Дропзона** — копирайт «Перетащите файл проекта сюда или нажмите, чтобы выбрать»; подпись мелким = список §2.1. Тач-таргет ≥48px, `:active` (не `:hover`).
- **После выбора файла** — строка выбранного файла (имя + размер + `×`-сброс) дополняется **чипом класса** (`Chip`, тон `dim`, [status.alerts.md](status.alerts.md) — классификация, не алерт; глиф из реестра §3.1 projects.md):
  - конвейерный → чип «Печать · сконвертируем в 3MF»;
  - как есть → чип «Артефакт · сохраним как есть» + микроподпись под зоной: **«Файл будет доступен для скачивания как есть. Просмотра во вьюере и конвертации не будет.»**
- **Никогда** не показываем для «как есть» аффордансов «Открыть во вьюере», «Отправить на станок», «Сконвертировать» — их нет (инвариант §5 п.4, projects.md §3.2).
- **Поле «Название»** — предзаполняется именем файла без расширения (как сегодня). **Поле «Описание»** — теперь markdown-редактор (§3).

### 2.3 Прогресс, статусы и тосты — честность по классу

- **Прогресс-бар загрузки** (§3.3 marketplace.md) — общий для обоих классов (`XMLHttpRequest.upload.onprogress`).
- **После 100% аплоада:**
  - конвейерный → карточка появляется в `processing`/`converting`, тост «Проект загружен» / «Идёт конвертация в 3MF» (как сегодня);
  - **как есть → карточка сразу `ready`**, никакого фейкового спиннера «конвертация» (её нет). Тост **«Файл сохранён»** — без обещания конвертации.
- **Статус-пилюля на карточке/странице** для «как есть» не проходит через `processing/converting` — сразу спокойное `ready` (или скрыта, «яркость=важность»). Показывать псевдо-конвертацию для файла, который не конвертируется, — нечестно.

### 2.4 Мульти-артефактный проект: секция «Файлы проекта» в редакторе

«Добавить проект» создаёт проект из **первого** файла (его класс определяет craft — печатный STL или, например, ЧПУ-программа). Чтобы проект стал **мульти-артефактным** (печать + ЧПУ + код) — артефакты добавляются в **редакторе проекта**, переиспользуя ту же загрузку:

- В модалке «Редактировать проект» — секция **«Файлы проекта»** (реестр ролей §3.1 projects.md): текущие артефакты строками, сгруппированы по ролям.
- **«Добавить файл»** — та же дропзона/пикер §2.2 (чип класса, честные подписи). Роль присваивает сервер по формату; если формат маппится на >1 роль (редко) — компактный селектор роли, иначе роль скрыта (auto).
- **«Удалить»** на строке артефакта — коралловая, с подтверждением ([status.alerts.md](status.alerts.md): деструктив всегда коралловый).
- Появление второго артефакта/не-печатного craft «зажигает» уже спроектированный спящий UI (craft-бейдж, блок «Файлы проекта» с группами, крафт-фильтр — projects.md §2/§3/§5) — **без правок вёрстки**, от данных. Это и есть проверка приёмки эпика §6 п.6.
- **Одиночный печатный проект (весь MVP-типовой) выглядит ровно как v2:** одна роль-группа → блок «Файлы проекта» дремлет (projects.md §3.2), primary «Скачать 3MF» + мета «Формат».

### 2.5 Ошибки загрузки — тексты (дополняют таблицу §3.4 marketplace.md)

Через слой всплывашек, тон = семантика ([status.alerts.md](status.alerts.md)):

| Причина | Где | Текст (RU) | Тон |
|---|---|---|---|
| Неподдерживаемый формат | инлайн под зоной + блок «Загрузить» | «Формат не поддерживается. Принимаем STL, 3MF, STEP, DXF/SVG, G-code, Gerber, ZIP-архив.» | danger |
| Подмена содержимого (magic-байты ≠ расширение, `FORMAT_MISMATCH` — Back §6 formats.policy) | инлайн под зоной | «Содержимое файла не совпадает с расширением. Загрузите настоящий {формат}.» | danger |
| Файл больше 100 МБ | инлайн под зоной | «Файл больше 100 МБ. Уменьшите или сожмите.» | danger |
| Битый архив / превышен лимит распаковки (decompression bomb) | инлайн/тост | «Не удалось прочитать архив. Проверьте, что это корректный ZIP.» | danger |

Тексты `FORMAT_MISMATCH`/лимитов согласуются с таксономией ошибок §6 formats.policy (Mesh/Back) — при расхождении финальны серверные коды, UI подставляет RU-текст по коду.

## 3. Описание проекта: markdown-редактор и типографика рендера

Реализация Р3 эпика. Хранение — сырой markdown в `models.description` (колонка `text`, есть). Рендер — на клиенте, безопасное GFM-подмножество, **raw HTML вырезается санитайзером всегда** (XSS через описание невозможен — приёмочное, эпик §6 п.3). Редактор — **textarea + предпросмотр, не WYSIWYG** (Р3).

### 3.1 Редактор описания (в модалках «Добавить»/«Редактировать проект»)

Заменяет простое поле «Описание» (§3.2 marketplace.md). Панель со стеклянной обводкой (`1px solid var(--border)`, radius 22, [components.md](components.md)):

```
┌ Описание ────────────────────────────────────────┐
│ [ Ж  К  ‹›  •  1.  H  🔗  🖼 ]        {312/50 КБ} │  ← тулбар (dim) + счётчик
├──────────────────────────────────────────────────┤
│ ⟦ Редактор ⟧   ⟦ Предпросмотр ⟧                    │  ← две вкладки (сегмент Chip)
├──────────────────────────────────────────────────┤
│ textarea (моноширинно-читаемый markdown-сырец)    │
│ …                                                 │
└──────────────────────────────────────────────────┘
```

- **Две вкладки** (`Chip`-сегмент, как сортировка §1.3 v2): **«Редактор»** (textarea) / **«Предпросмотр»** (рендер). Не WYSIWYG — вкладки, не синхронный split (на широком десктопе split «редактор | предпросмотр» бок-о-бок — **опционально**, не обязателен для MVP). На таче/мобиле — только вкладки.
- **Textarea** — существующий `.marketTextarea` (§0 инвентаря базы), авто-рост, `--font-sans`, комфортный `line-height`. Плейсхолдер: «Опишите проект: как печатать или собирать, настройки, материалы. Поддерживается Markdown — заголовки, списки, таблицы, код, ссылки, картинки.»
- **Тулбар форматирования** (над вкладками, тон `dim`, line-глифы, **без эмодзи** — в макете выше эмодзи-заглушки для читаемости) — кнопки **вставляют markdown-разметку в textarea** (обрамляют выделение / вставляют шаблон), не превращают в rich-text: **Ж** `**жирный**`, **К** `*курсив*`, **‹›** `` `код` ``, **•** маркированный список, **1.** нумерованный, **H** заголовок `## `, **ссылка** `[текст](url)`, **картинка** (см. ниже). Тач-таргеты ≥48px. Тулбар — удобство; ввод markdown руками работает так же. Тулбар **опционален** (при нехватке времени Front режет до textarea + вкладок), картинки — не опциональны (роль `description_image` — часть контракта).
- **Счётчик** «{n}/50 КБ» (`--text-dim`) — мягкий лимит описания (эпик Р3, дефолт 50 КБ); при превышении — блокировка отправки + инлайн «Описание длиннее 50 КБ, сократите».

### 3.2 Загрузка картинок описания (роль `description_image`, MF-9)

- Кнопка **«картинка»** в тулбаре / drop файла в textarea → загрузка через редактор в роль **`description_image`** → в textarea вставляется markdown-ссылка на файл роли `![альт](<url-файла>)` в позиции каретки.
- **Только свои картинки.** Внешние хотлинки (`![](https://чужой-домен/...)`) в рендере **не отображаются как картинки** (приватность/протухание, эпик Р3) — санитайзер рендера показывает их как обычную ссылку или вырезает (§3.4). Аплоад — единственный путь получить картинку в описании.
- **Прогресс** загрузки картинки — инлайн (тот же `.uiChecklistBar`/будущий `ProgressBar`, §3.3 marketplace.md).
- **Лимит** — ≤20 картинок на описание (эпик Р3, дефолт); при превышении — тост «Не больше 20 картинок в описании».

### 3.3 Вкладка «Предпросмотр»

Рендерит GFM-подмножество **тем же рендерером и CSS, что публичная страница** (§3.4) — автор видит ровно то, что увидят люди: парящий текст на студийном фоне, вуаль-контраст под блоком (§2.1 v2). Не отдельная «облегчённая» стилизация — иначе предпросмотр врёт.

### 3.4 Типографика рендера GFM-подмножества (публичная страница проекта)

Описание рендерится в правой парящей колонке (§2.2 п.5 v2), парящим текстом, под блоком — вуаль-контраст для читаемости на ярком студийном фоне. **Allowlist элементов = приёмочный контракт санитайзера** (всё вне списка — вырезается; raw HTML/`<script>`/`<iframe>`/атрибуты-обработчики — всегда режутся):

| Элемент markdown | Рендер в нашем языке |
|---|---|
| **Абзац** | `--font-sans`, `--text`, `line-height ~1.6`, парит; под блоком — вуаль-контраст. |
| **Заголовки h1–h6** | `--font-sans`, вес 600 (**не** Unbounded — чтобы не конкурировать с Unbounded-названием проекта, §2.2 п.2 v2). Кегль ступенями: h1 ~1.4em, h2 ~1.2em, h3 ~1.05em, h4–h6 ~1em bold. Цвет `--text`, верхний отступ для ритма. Без uppercase. |
| **Списки** ul/ol | Стандартные маркеры/номера, отступ; текст `--text`, маркеры `--text-dim`. Вложенность до 2–3 уровней. |
| **Таблицы** (GFM) | Ячейки `1px solid var(--border)`, шапка — `--text-dim` полужирным; на мобиле — контейнер `overflow-x:auto` (широкая таблица скроллится, не ломает раскладку). |
| **Инлайн-код** `` `x` `` | Стеклянный чип: моноширинный (`--font-mono`, GAP §6), фон `--surface`, radius малый, `--text`. |
| **Блок кода** ```` ``` ```` | Тёмная стеклянная панель, `--font-mono`, `overflow-x:auto`; **без подсветки синтаксиса на MVP** (не тянем highlighter — честно; подсветка — задел, не сейчас). Опц. кнопка «Копировать» (`IconButton`). |
| **Ссылки** | Текст `--accent` (мятный), подчёркивание на `:active`. Внешние — `target="_blank" rel="noopener noreferrer nofollow"`. GFM-автолинк допустим. |
| **Картинки** (только `description_image`) | radius ~12, `max-width:100%`, лёгкая тень (парят как облегчённый превью-стек), `loading="lazy"`, `alt` уважается. Внешние URL как картинки **не рендерятся** (§3.2). |
| **Цитата** blockquote | Левый бордюр `--accent` (dim) + текст `--text-dim`, отступ. |
| **Разделитель** hr | Тонкая линия `--border`. |
| **Жирный / курсив** | `font-weight:600` / `italic`, цвет `--text`. |

- **Пустое описание** — «Автор не добавил описание» (`--text-dim`), как §2.2 п.5 v2.
- **Безопасность (приёмочное, эпик §6 п.3):** санитайзер режет любой raw HTML, `javascript:`-URL в ссылках/картинках, атрибуты-обработчики. Выбор библиотеки (напр. `markdown-it` + `DOMPurify`, или `marked`+sanitize) — за Front; **allowlist выше и XSS-непробиваемость — приёмочный контракт**, не деталь реализации.
- **Reduced-motion / Save-Data:** markdown статичен; картинки — `lazy`. Никакой анимации рендера.
- **Нейропоиск** (стадия 3, AI): индексирует описание с очисткой разметки (эпик Р3) — на типографику рендера не влияет, здесь не проектируется.

## 4. Строка репо-линка в блоке «Код» (`repo_url`)

Реализация Р4 эпика: активируем зарезервированное место projects.md §4.2 (глиф + имя репо + «Открыть»). Это **фундамент-ссылка**, не интеграция — никакого OAuth/синка/импорта, ноль упоминаний конкретного хостинга как обязательных (эпик Р4).

### 4.1 Задание в редакторе проекта

- В модалке «Редактировать проект» (и опц. при добавлении) — поле **«Репозиторий»** (необязательное): текстовое поле (`.marketField*`, radius 22–28), плейсхолдер «https://gitverse.ru/user/repo».
- **Валидация:** https-URL (клиентская — мгновенный фидбэк; серверная — Back). Не-URL/не-https → инлайн «Нужна ссылка вида https://…».
- Подпись мелким (`--text-dim`): «Ссылка на репозиторий проекта. Откроется в новой вкладке — без синхронизации.» — честно, что это просто ссылка.
- Пусто → строки в блоке «Код» нет (§4.2).

### 4.2 Показ в блоке «Код» (страница проекта)

Блок «Код» (projects.md §4) — список источников кода. **Дельта к projects.md §4.1:** правило видимости расширяется —

> Блок «Код» появляется, когда у проекта есть **хотя бы один** источник кода: файл роли `code_archive` **или** заданный `repo_url`. (Раньше — только по `code_archive`.)

Репо-линк — **первая строка** списка «Код» (канонический источник; ниже — архивы-снимки):

```
▸ КОД                                        (Eyebrow, парит)
   ⟨repo⟩ gitverse.ru/user/repo      [ Открыть ]   ← источник-ссылка (repo_url)
   ‹/›   firmware.zip · 240 КБ        [ Скачать ]   ← вложение code_archive (как есть)
```

- **Анатомия строки-ссылки:** line-глиф репозитория (отдельный от `‹/›`-архива — напр. ветка/репо-глиф; **без эмодзи**) + **имя репо** (человекочитаемо из URL: `host/path` без схемы, напр. `gitverse.ru/user/repo`, при длинном пути — усечь до `user/repo`) + действие **[ Открыть ]** (стеклянная кнопка, `--accent`-текст но **не** сплошной-зелёный primary — один зелёный на кадр = «Скачать 3MF», инвариант §5 п.5).
- **«Открыть»** → `target="_blank" rel="noopener noreferrer"`, новая вкладка. Никакого клона/pull/звёзд/синка — только переход.
- **Первый класс для GitVerse — на уровне UI, не схемы** (эпик Р4): при host `gitverse.ru` можно показать узнающий глиф/подпись; для прочих хостингов — нейтральный репо-глиф + host. Схема (`repo_url text`) нейтральна к хостингу.
- **Честность:** строка-ссылка не обещает интеграции. Композиция §3.2 projects.md инвариантна к типу источника (файл vs ссылка) — репо-линк встал одной строкой, без перевёрстки (требование «без перевёрстки» закрыто).
- **Мобиль:** строка на всю ширину, действие ≥48px (§3.3 projects.md).

## 5. Инварианты (приёмка Architect / Lead)

Продолжают инварианты projects.md §6; здесь — специфичные для дельты:

1. **Словарь финален и берётся дословно** (§1.2): витрина говорит «Проекты» во всех строках таблицы; URL/API не меняются; счётчик плюрализуется по RU-правилу (§1.3). Таб — «Проекты» (рекомендация §1.1; финально — Валерий).
2. **Два класса приёма честны** (§2): конвейерный конвертируется, «как есть» — хранится и скачивается без вьюера/конвертации/«на станок»; статус «как есть» — сразу `ready`, без фейковой конвертации.
3. **Валидация — по сигнатурам, не по расширению** (§2.1/§2.5): UI полагается на magic-байты сервера; `FORMAT_MISMATCH` даёт честный RU-текст.
4. **Никаких обещаний, которых нет** (§2.2/§2.3): для «как есть» нет «Открыть во вьюере»/«Сконвертировать»/«На станок»; тост не обещает конвертацию.
5. **Один зелёный primary на кадр сохранён** (readme §2): страница проекта — «Скачать 3MF»; «Открыть» репо и скачивания прочих артефактов — нейтральное стекло, не зелёные.
6. **Markdown безопасен** (§3.4): raw HTML/`<script>`/`javascript:` вырезаются всегда; XSS через описание невозможен (приёмочный пробой). Рендер = allowlist §3.4; редактор — textarea+предпросмотр, не WYSIWYG.
7. **Картинки описания — только свои** (§3.2): роль `description_image`, внешние хотлинки как картинки не рендерятся.
8. **Репо — фундамент, не интеграция** (§4): одна строка-ссылка «Открыть», ноль синка/OAuth; блок «Код» появляется по `code_archive` **или** `repo_url`.
9. **Всё от данных, не от флагов** (кроме термина): craft-бейджи/группы/фильтр/блок «Код» зажигаются значениями `craft`/`role`/`repo_url` в выборке (projects.md §6 п.8); термин переключает Валерий явно (§1).
10. **Схема карточки — вердикт MF-9 (вариант B):** артефакты = строки `model_files` с ролями, `project_*`-таблиц нет; эта спека читает per-file роли из ответа, не проектирует DDL.
