# Веб-слайсер: UX-контракт редактора стола и отправки в печать

← [Design](readme.md) · [модель и живой 3D](model.card.v3.md) ·
[парк](park.md) · [страница принтера](printer.page-types.md) ·
[состояния команд и G-code](printer.offline-command-states.md)

**Статус.** UX-спека MF-1093 для эпика MF-1053. Это основание для
визуального этапа Design и реализации MF-1094; файл не является макетом и не
расширяет wire/API-контракт сам по себе.

### Delta 2026-07-19: рабочее пространство вместо формы

Живая реализация разворачивает слайсер в отдельное полноэкранное 3D-пространство:

- стол и модели занимают весь viewport под устойчивым глобальным header;
- справа плавает inspector с режимами «Обычный» и «Про»;
- объекты и копии живут в компактном dock, а не отнимают у стола постоянную
  колонку;
- «Обычный» спрашивает результат — качество, материал и intent поддержек;
  «Про» раскрывает machine/process/filament-профили и точную раскладку;
- клиент может показать только **предварительные** опоры и footprint. Финальные
  supports, toolpaths, время и расход материала появляются только из результата
  Orca-worker и не симулируются Front;
- итог всегда предлагает два независимых пути: скачать G-code либо передать его
  подключённому принтеру. Передача файла и запуск печати подтверждаются отдельно.

Эта delta заменяет старую desktop-композицию из трёх постоянных колонок ниже,
но сохраняет её требования к доступности и точным числовым контролам.

## 0. Задача экрана и границы v1

**Кто:** владелец модели, у которого есть хотя бы один принтер в парке.

**Одна работа экрана:** собрать проверяемый стол под конкретный пользовательский
принтер, подготовить G-code и передать его в существующий Devices-контур.

Поток v1:

```text
модель/файл → принтер и его стол → копии и трансформации → проверка
→ подтверждение материала/профиля → облачный слайс → передача → запуск
```

Границы обещания:

- редактор не подключает принтер и не строит собственный транспорт: источник
  устройств — парк, отправка — только Devices relay/agent;
- размер, форма стола, сопло, кинематика и fingerprint не вводятся заново в
  слайсере; это снимок выбранного `user_printer` и связанного профиля;
- клиентская коллизия даёт быстрый feedback, но окончательный preflight
  подтверждает сервер/Mesh перед созданием G-code;
- `202 queued`, готовый G-code и начавшаяся печать — три разных факта. UI не
  называет команду выполненной до authoritative ACK и свежего snapshot;
- простой режим принимает intent поддержек (`auto|tree|off`) и показывает
  предварительную визуализацию, но authoritative supports/toolpaths приходят
  только из Orca-worker. Painting, seam, modifier meshes, variable layer
  height и ручное редактирование G-code остаются за границей v1 и не прячутся
  за неработающими кнопками.

## 1. Точка входа и восстановление контекста

Основная дверь — действие **«Отправить в печать»** на карточке готовой модели.
Оно открывает редактор с одним источником и одной копией по центру стола.
Дополнительная дверь — загрузка одного или нескольких локальных
`3MF`/`STL`-файлов из самого редактора, если формат принят текущим Mesh-контрактом.

Для project-as-code основная дверь точнее: build session передаёт
`revision + configuration_digest + workflow_step_id + artifact_id`.
Редактор показывает имя файла и шаг над столом, а слайсит именно этот
artifact. Подмена его общей `preview_url` проекта запрещена. Если backend
ещё не умеет резолвить artifact, primary disabled с видимой причиной; UI не
делает вид, что верхнеуровневая модель и выбранная деталь — одно и то же.

При входе система последовательно:

1. проверяет сессию и доступ к модели;
2. загружает парк и выбирает основной совместимый принтер; если основного нет —
   первый совместимый, но выбор явно виден;
3. получает геометрию стола и подходящие process/filament-профили;
4. показывает постер модели, затем заменяет его живой геометрией без скачка
   рабочей области;
5. ставит одну копию в допустимый центр и запускает preflight.

Черновик раскладки переживает reload в рамках той же сессии и восстанавливает
принтер, источники, копии и трансформации. Механизм хранения выбирает
реализация; UI не обещает синхронизацию между устройствами, пока сервер не
хранит layout. При уходе с несохранёнными изменениями — диалог
«Раскладка изменена. Выйти без неё?» с действиями «Остаться» и «Выйти».

Deep-link на существующий результат восстанавливает job по стабильному id.
Готовый артефакт продолжает использовать существующий handoff
`/slice/:sliceId/print`; критический контекст нельзя держать только в query.

### 1.1 Snapmaker U1 как первый живой pilot

U1 проверяет весь поток на реальном локальном устройстве: профиль стола и
сопел, slicing и передачу через relay. UX показывает четыре разных факта:

1. «U1 найден в локальной сети»;
2. «U1 привязан к моему парку»;
3. «G-code подготовлен профилем U1»;
4. «Файл передан» / «печать запущена».

Ни один последующий статус не выводится из предыдущего. Обнаружение доступно
только локальному agent/relay, требует явного подтверждения владельца и не
открывает LAN для VDS. Для первого релиза достаточно честной одной
toolhead-конфигурации; многоцветный/многоголовочный режим включается только
после отдельной верификации.

### 1.2 Safari и локальная сеть

Обычная HTTPS-страница Portal не является надёжным LAN-agent. Даже если Safari
не показывает системный Local Network permission для top-level страницы, web
остается ограничен mixed content, CORS, Private/Local Network Access и
неполной поддержкой LNA в WebKit. Поэтому UI не обещает сканирование mDNS,
Moonraker HTTP/WebSocket или произвольного IP напрямую из браузера.

Поддерживаемый маршрут:

```text
Safari → Portal API → привязанный local helper/relay → Moonraker/Snapmaker U1
```

- helper обнаруживает принтер в том же LAN, читает capabilities и слоты
  материалов, но наружу отдаёт только нормализованный versioned contract;
- ручной IP можно ввести в Portal, однако он передаётся helper для локальной
  проверки — браузер не делает `fetch()` к этому IP;
- привязка helper/device требует одноразового подтверждения владельца,
  account/device scope и отзыва; VDS не получает маршрут в LAN;
- native Safari extension/helper допустим как будущая оболочка, но не создаёт
  второй printer protocol: он использует тот же Devices-контракт;
- загрузка G-code и `start` — две разные команды. Автозапуск после загрузки
  запрещён.

## 2. Информационная архитектура

Экран — рабочий стол, а не дашборд. Главный объект — реальная граница печати;
панели только объясняют и меняют то, что лежит на ней.

```text
┌ global header поверх сцены ──────────────────────────────────────┐
│ контекст шага     [вид сверху] [3D] [reset]  ┌ inspector ──────┐ │
│                                                       Обычный/Про │
│                                                             принтер│
│                         живой стол                    материалы │
│                         модели и supports             качество  │
│                                                       supports  │
│ [Объекты · Деталь A ×3]                   preflight   [Нарезать] │
│                                                └───────────────┘ │
└──────────────────────────────────────────────────────────────────┘
```

- **Global header:** не перемонтируется при входе; back, раздел и пользователь
  остаются на тех же координатах поверх сцены.
- **Context HUD:** имя artifact/шага, revision и краткое состояние принтера.
- **Object dock:** источники и экземпляры. Здесь доступны все действия без
  canvas: выбрать, задать число копий, дублировать и удалить.
- **Центр:** 3D/ортографический стол. По умолчанию перспектива слегка сверху;
  отдельная кнопка «Вид сверху» даёт точное чтение границ.
- **Floating inspector:** принтер, материалы, качество, supports и результат;
  в «Про» — профили Orca и числовые трансформации.
- **Footer inspector:** итог preflight и один primary. Primary остаётся на
  месте disabled с видимой причиной, а не исчезает.

Визуальная подпись будущего макета — **живой контур стола**: прямоугольник,
круг или подтверждённый polygon из профиля. Это инструментальная поверхность,
а не декоративный зелёный hero. Цвета, типографика и плотность берутся из
действующих design tokens; новый визуальный язык в этой UX-спеке не вводится.

## 3. Принтер и геометрия стола

### 3.1 Выбор принтера

Picker показывает только пользовательские устройства, для которых известны:

- `user_printer.id` и принадлежность аккаунту;
- подтверждённые X/Y/Z и форма области печати;
- сопло и совместимый machine/process-профиль;
- возможность передачи G-code через Devices или честное read-only состояние.

Строка: «{brand} {model}» · размер/форма · сопло · состояние связи. Основной
принтер помечен текстом «Основной», не только иконкой. Несовместимое устройство
остаётся видимым в секции «Недоступны» с одной конкретной причиной.

Смена принтера пересчитывает допустимую область и preflight. Если текущая
раскладка не помещается, объекты не двигаются молча: экран сохраняет их
координаты, помечает проблемы и предлагает «Автораскладка». Возврат к прежнему
принтеру восстанавливает его последнюю раскладку в текущем черновике.

### 3.2 Форма — обязательный факт

`x/y/z` недостаточно для FLSun/дельта-принтера: круг диаметром 300 мм и
квадрат 300×300 мм допускают разные раскладки. Нужен versioned `bed_geometry`:

```text
shape: rect | circle | polygon
width_mm / depth_mm / diameter_mm / points_mm
origin: center | front_left | explicit
excluded_zones_mm: optional
```

UI нормализует координаты для человека, но не меняет origin при отправке.
Если форма/origin не подтверждены, показывается состояние
**«Геометрия стола не подтверждена»**, canvas не рисует выдуманную границу,
а primary недоступен. Действие — «Открыть настройки принтера»; ручной размер
редактируется там и затем возвращается как новый профильный факт.

## 4. Модели, копии и трансформации

### 4.1 Источники и экземпляры

Один загруженный mesh — источник; каждая размещённая копия — экземпляр со
своей трансформацией. Изменение количества:

- добавляет новые копии рядом с исходной, затем запускает автораскладку по
  явному действию или автоматически только при первом создании;
- при уменьшении удаляет последние копии после предупреждения, если они были
  вручную перемещены;
- не объединяет одинаковые файлы молча: дубликат источника предлагает
  «Добавить копию существующей модели».

Каждый экземпляр имеет стабильное имя «{модель}, копия N». Выделение в списке
и на столе синхронно. `Esc` снимает выделение; `Delete` удаляет экземпляр,
но не весь источник без отдельного подтверждения.

### 4.2 Перемещение, поворот и масштаб

- pointer/тач drag меняет X/Y; движение ограничивается только визуально —
  пользователь может увидеть выход за границу и вернуть объект;
- ручки поворота меняют только Z в v1; X/Y-orientation приходит из
  подготовленной модели и не маскируется свободной 3D-орбитой;
- масштаб равномерный, вводится процентом. Любое изменение мгновенно
  инвалидирует предыдущий preflight и slice result;
- числовые поля принимают мм/градусы, показывают допустимый диапазон и
  нормализуют значение после blur/Enter;
- undo/redo покрывает перемещение, поворот, масштаб, копирование, удаление,
  смену количества и автораскладку. Смена принтера — одна атомарная операция.

### 4.3 Коллизии и границы

Для каждой копии одновременно вычисляются:

- `inside_bed` — весь footprint внутри реальной геометрии стола;
- `collision_ids[]` — пересечение с другими footprint;
- `height_ok` — Z не превышает объём печати;
- `clearance_ok` — выдержан безопасный зазор выбранного process-профиля.

Проблема кодируется контуром/штриховкой, иконкой и текстом. Только красного
цвета недостаточно. Внизу показывается агрегат: «2 модели пересекаются ·
1 выходит за границу». Тап по проблеме выбирает первый экземпляр; «Следующая»
циклически проходит остальные.

Клиентский результат подписан «Предварительная проверка». Только server
preflight разрешает слайсинг. При расхождении UI сохраняет layout и говорит:
«Сервер нашёл пересечение после точной проверки», а не `invalid geometry`.

## 5. Автораскладка

Кнопка **«Автораскладка»** размещает все экземпляры в текущей форме стола с
зазором выбранного профиля. Она не меняет масштаб, количество, ориентацию
исходной модели или принтер.

Состояния:

```text
idle → arranging → arranged | partially_arranged | failed
```

- `arranged`: все копии помещены; статус «Разложено: {n} из {n}»;
- `partially_arranged`: допустимые копии остаются на столе, остальные — в
  области «Не помещаются», primary заблокирован;
- `failed`: прежняя раскладка восстанавливается; текст
  «Не удалось разместить все копии. Уменьшите количество или масштаб»;
- повторный запуск с тем же входом детерминирован и не тасует стол случайно;
- пока идёт расчёт, ручные трансформации заблокированы, но есть «Отменить»;
  после отмены возвращается ровно предыдущий layout.

## 6. Подтверждение и запуск pipeline

Primary **«Отправить в печать»** доступен, когда server preflight зелёный,
профиль подтверждён, принтер допускает G-code и нет незавершённого действия.
Он открывает confirmation sheet, не отправляет запрос сразу.

Подтверждение содержит:

- принтер и подтверждённую форму/размер стола;
- модели, число экземпляров и итоговые габариты;
- материал/вариант из «Моих филаментов»;
- process-профиль, сопло и intent (`strength|speed|appearance|miniatures`)
  понятными русскими названиями;
- предупреждение об экстраполяции профиля с причиной и confidence;
- текст «Сначала подготовим G-code, затем передадим его принтеру».

Действия: ghost «Назад к столу» и единственный primary
**«Отправить в печать»**. Если выбранный филамент не подтверждён как
заправленный, это предупреждение, а не выдуманный факт; опасная несовместимость
блокирует primary с конкретной причиной.

После подтверждения layout становится immutable snapshot. Возврат к редактированию
создаёт новую ревизию и не меняет уже запущенную job.

## 7. Две независимые оси результата

### 7.1 Слайсинг

| API | Текст UI | Что можно утверждать |
|---|---|---|
| `queued` | «Слайсинг в очереди» | Запрос принят; работа не началась |
| `running` | «Нарезаем модели…» | Воркер обрабатывает job; процент показывается только при server progress |
| `succeeded` | «G-code готов» | Артефакт создан и прошёл slice-trust; ещё не на принтере |
| `failed` | «Не удалось подготовить G-code: {безопасная причина}» | Job завершилась ошибкой; layout сохранён |

Если backend не отдаёт процент, используется неопределённый progress с
этапом и прошедшим временем — не фальшивые «73%». Reload восстанавливает job
по id и продолжает polling/subscription, не создавая дубль.

### 7.2 Передача и запуск

После `succeeded` применяется канон
[printer.offline-command-states.md](printer.offline-command-states.md):

```text
G-code готов → передача файла → file_complete → подтверждение запуска
→ command queued → sent → ack | error | timeout
```

- browser/API accept не равен delivery;
- прогресс файла берётся из `uploaded_bytes / size_bytes` по `transfer_id`;
- разрыв сети сохраняет докачку, а не начинает новый transfer молча;
- `file_complete` говорит «Файл на принтере», но не «Печать началась»;
- запуск требует отдельного confirmation с именем принтера и файла;
- только ACK запуска плюс свежий snapshot `printing` даёт итог
  «Принтер начал печать»;
- timeout говорит «Подтверждение не получено. Состояние принтера неизвестно»;
  автоматический повтор запуска запрещён.

Статус слайсинга остаётся видимым рядом со статусом передачи. Нельзя заменить
оба одной зелёной пилюлей «Отправлено».

После `succeeded` UI показывает два равноправно доступных результата:
primary «Передать на {printer}» и secondary «Скачать G-code». Выбор скачивания
не меняет состояние принтера. Передача не запускает печать автоматически:
после `file_complete` пользователь отдельно подтверждает `start`.

## 8. Состояния экрана и recovery

| Состояние | Что видно | Следующее действие |
|---|---|---|
| loading | устойчивый shell, граница стола skeleton только после известной формы | дождаться; ложного CTA нет |
| model processing | постер и «Модель ещё готовится» | «Вернуться к модели» |
| invalid file | имя файла и безопасная причина | «Выбрать другой файл» |
| no printers | EmptyState «Нет принтера для отправки» | «Добавить принтер» |
| bed unknown | выбранный принтер, но без выдуманного стола | «Открыть настройки принтера» |
| profile loading/error | layout сохраняется, панель профиля loading/error | «Повторить подбор» |
| editing valid | стол, зелёный preflight, один primary | «Отправить в печать» |
| collision/outside/height | проблемные копии и текстовый агрегат | «Автораскладка» или выбрать проблему |
| printer stale/offline | последний подтверждённый профиль с временем; отправка заблокирована | «Проверить связь» |
| permission | контекст не исчезает; login/role explanation | «Войти» либо запросить доступ |
| slice failed | layout + job id + безопасная причина | «Повторить слайсинг», если retryable |
| upload paused | точный сохранённый прогресс | «Возобновить», когда online |
| command timeout | готовый файл и неизвестный outcome | «Проверить статус» |
| success | две оси завершены, свежий printer snapshot | «Открыть принтер» |

Ошибки не живут только в toast. Raw stack, S3 key, LAN endpoint, fingerprint и
credential никогда не попадают в пользовательский текст.

## 9. Keyboard, screen reader и touch

Canvas — визуальное представление, не единственный control. Список экземпляров
и числовые поля дублируют все действия нативными элементами; весь экран не
получает `role="application"`.

- `Tab` идёт: shell → printer → источники/копии → view controls → transform
  fields → preflight → actions. Порядок DOM совпадает с визуальным;
- стрелки при фокусе экземпляра двигают его на 1 мм, `Shift+стрелка` — на
  10 мм; клавиатурный drag не требует удерживать pointer;
- поворот и масштаб доступны через подписанные number inputs/steppers;
- после drag/keyboard commit polite live-region один раз сообщает итоговую
  позицию и проблемы. Во время каждого pointermove announcements нет;
- после автораскладки фокус возвращается на её кнопку, status объявляет
  «Разложено…» или причину. После ошибки фокус можно программно перевести на
  `role="alert"` с `tabindex="-1"`;
- границы/коллизии различаются текстом и паттерном, не только цветом;
- touch targets ≥48×48, primary не перекрывается bottom-nav/safe-area;
- focus-visible ≥2px и 3:1, обычный текст ≥4.5:1, графические границы стола,
  выбранного объекта и проблемы ≥3:1;
- `Escape` закрывает sheet/диалог и возвращает фокус инициатору; focus trap
  не выпускает фокус из открытого modal;
- на реализации каждый fixture проходит `a11y <url>` с 0 critical/serious,
  затем ручной keyboard и VoiceOver/NVDA проход. Axe не заменяет эти проходы.

## 10. Responsive, motion, sound и performance

### Desktop ≥1024

Сцена занимает весь viewport. Inspector плавает справа и может сворачиваться;
object dock не перекрывает модель. Выбранный принтер, preflight и primary
остаются видимыми. Полезная область сцены — минимум 480×480.

### Tablet 641–1023

Canvas сверху, нижний inspector — tabs «Модели / Положение / Проверка».
Primary sticky над системной safe-area. Drag и точные поля равноправны.

### Mobile ≤640

Вид сверху занимает первый экран; inspector открывается bottom-sheet.
Точные X/Y/поворот/масштаб и автораскладка позволяют закончить сценарий без
тонкого drag. Горизонтальная ориентация не обязательна и не показывается как
единственный путь.

### Motion

- direct drag следует pointer 1:1 без spring-lag; hover/press — общие токены;
- автораскладка перемещает уже видимые копии 220–280ms `ease-in-out`, одним
  согласованным layout-переходом, без bounce и stagger;
- новый объект появляется 160–200ms `ease-out`; ошибка использует действующий
  короткий shake только группы проблемы, не всего canvas;
- orbit/idle-анимации на рабочем столе нет: это частый инструментальный экран;
- при `prefers-reduced-motion: reduce` все перестановки мгновенные, progress
  остаётся читаемым текстом, функциональность не меняется.

### Sound

- обычный выбор/поле — общий `tick`, primary — общий `cta`, без нового тембра;
- автораскладка не звучит на каждое перемещение; один `toggle/tick` на запуск;
- успех/ошибка звучат только по общему severity-движку и только на terminal
  server result, не на optimistic client state;
- master mute и reduced-motion default соблюдаются по [sound.md](sound.md).

### Performance

- pointer drag держит визуальный feedback без React-render на каждый пиксель;
  тяжёлый preflight дебаунсится и отменяет устаревший запрос;
- LOD/poster не блокируют выбор принтера и список; большой mesh показывает
  явный этап загрузки;
- целевой interaction latency для drag/rotate — один кадр; автораскладка и
  server preflight не блокируют main thread;
- реализация проверяется на 1, 10 и 50 экземплярах; при 50 список остаётся
  управляемым, а reduced detail не скрывает коллизии.

## 11. Handoff Front/Data/Mesh/Devices

### Уже существующие контракты, которые переиспользуются

- `POST /models/:id/slice` и `GET /slice-jobs/:jobId` — lifecycle
  `queued|running|succeeded|failed`;
- `slice-trust.v1` — привязка account/device/profile/slice key;
- `/slice/:sliceId/print` — текущий экран выбора принтера и command-result;
- Devices command/file lifecycle — источник delivery/ACK, не локальный таймер;
- `GET /slicer-profiles/:printerId/:filamentId` — подбор профиля и честная
  экстраполяция.

### Контрактные разрывы до MF-1094

1. Текущий slice-create принимает одну модель и один `scale`, но не layout,
   несколько источников, экземпляры, X/Y/rotation и server preflight. Нужен
   versioned layout payload/snapshot; Front не должен кодировать его в имя файла.
2. `UserPrinter.build_volume` сейчас типизирован как X/Y/Z без формы/origin.
   Для круглой FLSun-платформы нужен `bed_geometry`; до этого dispatch fail-closed.
3. Нужен детерминированный arrange/preflight result с per-instance codes,
   а не один boolean: `collision`, `outside_bed`, `height_exceeded`,
   `clearance_failed`, `unsupported_geometry`.
4. Нужен стабильный layout/job id для reload и idempotency. Повтор confirmation
   с тем же snapshot не создаёт вторую job/команду.
5. UI нужен безопасный error mapping и server-owned `retryable`; по raw error
   повтор не угадывается.
6. Project-as-code artifact нельзя подменять top-level `model_id`. Нужен
   versioned create-contract с identity
   `revision + configuration_digest + workflow_step_id + artifact_id +
   artifact_sha256`, где сервер сам резолвит pinned source и проверяет hash.
7. Результат job должен отдавать server-owned manifest финального preview:
   toolpaths/supports по слоям, оценки времени/массы и `gcode_url`. До такого
   результата Front подписывает supports как предварительные и не рисует
   выдуманную нарезку.
8. Devices должен отдавать нормализованный inventory слотов/голов и freshness.
   Ручной материал остаётся отдельным user assertion и не маскируется под
   телеметрию принтера.

Минимальный новый payload:

```text
source: revision/configuration_digest/workflow_step_id/artifact_id/artifact_sha256
target: user_printer_id + immutable machine/process/filament profile ids
layout: bed geometry + instances[x_mm,y_mm,rotation_z_deg,scale]
intent: quality + supports(auto|tree|off)
```

В живом Front этот разрыв закрыт fail-closed: точный code-first STL можно
проверить и разложить на столе, скачать как source, но кнопка облачного
слайсинга остаётся disabled до versioned artifact-contract. Подстановка
другой модели ради зелёной кнопки запрещена.

Владение: layout/geometry — Mesh + versioned contract; job/schema — Data/Back;
editor — Web; доставка и authoritative command/file outcome — Devices. Ни одна
часть не импортирует чужой `src`; общий shape живёт в `packages/contracts`.

## 12. Приёмка реализации

- От ready-модели можно выбрать конкретный пользовательский принтер, увидеть
  подтверждённую форму/размер стола, создать ≥2 источников и ≥10 копий.
- Pointer и keyboard позволяют перемещать, вращать и масштабировать копии;
  undo/redo возвращает точное состояние.
- Rect и circle fixtures дают разные корректные границы; неизвестная форма
  блокирует отправку, а не рисуется квадратом.
- Коллизия, выход за границу, превышение Z и нехватка clearance видимы на
  объекте, в списке и в текстовом агрегате; server preflight — финальный gate.
- Автораскладка детерминирована, отменяема и честно возвращает partial/failed.
- Confirmation показывает принтер, материал, профиль, сопло, число копий и
  предупреждение экстраполяции; primary на экране всегда один.
- Слайсинг и доставка показаны двумя осями; reload не дублирует job, transfer
  или start command. `202` не отображается как выполненная печать.
- Offline/stale сохраняет layout и результат, блокирует скрытую отправку и
  предлагает проверку связи; timeout остаётся неизвестным outcome.
- Desktop 1440×900, tablet 834×1194 и mobile 390×844 проходят полный сценарий;
  touch targets ≥48px, keyboard без ловушек, `a11y` — 0 critical/serious.
- `prefers-reduced-motion` и mute работают; motion не превышает 300ms и не
  задерживает данные. Live-проверка Front прикладывает URL/fixtures, webcheck,
  vmatrix, axe и Lighthouse согласно своим карточкам.
