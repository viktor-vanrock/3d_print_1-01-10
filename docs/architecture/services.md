# SERVICES — не монолит: принципы нарезки, границы, зоны команд

Раскрывает канон `docs/product/philosophy.md` § «Мы НЕ … НЕ монолит: сотни
микросервисов, много команд». Здесь — **почему**, **по каким швам режем**,
**как сервисы общаются** и **как это живёт в текущем монорепо**. Текущее
состояние (что есть сейчас) — [readme.md](readme.md); этот файл — принципы
и вектор эволюции поверх него.

## Почему не монолит

Портал растёт не в одну фичу, а в несколько параллельных направлений
одновременно: другие станки (ЧПУ, лазер, токарка — `docs/epics/domain.model.md`),
умный слой (Кандинский, диагностика, семантический поиск), комьюнити/форум,
интеграция с GitVerse (V3). Каждое направление со временем — своя команда со
своим темпом релизов, своим стеком, своей зоной ответственности. Монолит на
одну команду не масштабируется на много команд: общий деплой блокирует
несвязанные релизы, общий кодстайл/рантайм не даёт взять правильный
инструмент под задачу (см. «Почему полиглот» в readme.md — это тот же
принцип, уже применённый к `mesh`/`giga`), общая кодовая база создаёт
конфликты между командами, которые не должны друг друга ждать.

Вывод: сервис = независимый деплой + независимое владение. Это не эстетика,
а прямое следствие «команд будет много» (принцип 4 философии, «агенты и
люди строят вместе» — тоже про множество независимых исполнителей).

## Принципы нарезки

**Режем по домену/вертикали, не по слою.** Сервис — это «каталог станков»,
«конвертация геометрии», «умный слой», а не «весь backend» или «весь
frontend-API». Слоёная нарезка (например, отдельный сервис «валидация» или
отдельный сервис «логирование») создаёт сервисы, которые не могут релизиться
без синхронизации с соседями — это распределённый монолит, худшее из двух
миров.

**Критерий выделения нового сервиса** — сервис оправдан, когда выполняется
хотя бы одно:
- Другой рантайм/экосистема даёт реальное преимущество (`mesh`/`giga` —
  Python ради trimesh/numpy и GigaChat SDK, см. readme.md).
- Нагрузочный профиль расходится настолько, что общий процесс мешает
  масштабировать (тяжёлая CPU-конвертация геометрии не должна блокировать
  HTTP-запросы `api` — отсюда уже сегодня PostgreSQL-очередь с отдельным worker).
- Зона переходит от одной команды к другой (владение, не просто код) —
  когда за направлением закрепляется отдельный директор/вертикаль со своим
  темпом (см. «Как команды делят зоны» ниже), граница команды становится
  границей сервиса.
- Домен становится достаточно самостоятельным, чтобы иметь свой жизненный
  цикл релизов, независимый от остального (например, будущий парсер
  каталога станков, работающий по расписанию, а не по запросу).

**Что осознанно НЕ дробим в v1.** Распределённая система стоит дороже
монолита: сетевые границы вместо вызовов функций, согласованность данных
между сервисами, отдельный деплой/мониторинг/секреты на каждый сервис,
дублирование инфраструктурного кода. В v1 команда одна (агенты + оператор),
инфраструктура — один VDS (readme.md § «Окружения»), поэтому:
- Внутри `api` НЕ выделяем отдельные сервисы на каждый домен (auth,
  проекты, каталог станков и т.п.) — это модули одного процесса с общей
  Postgres-схемой, пока нагрузка/команда не требуют иного.
- Новый вид станка (ЧПУ, лазер) на старте **не** получает отдельный сервис —
  он ложится в существующую доменную модель (`crafts`/`machines`,
  `docs/epics/domain.model.md`) внутри `api`; выделяется в сервис только
  когда у направления появляется свой темп релизов или свой рантайм.
- Не вводим сервис ради будущей нагрузки, которой ещё нет («на всякий
  случай») — издержки распределённости платятся один раз при реальной
  необходимости, не заранее.

Правило по умолчанию: **новый функционал — новый модуль внутри
существующего приложения**; отдельный сервис — осознанное решение по
критерию выше, не стартовая позиция.

## Границы и контракты

**Публичная поверхность — только `api`** (readme.md). Это правило
масштабируется: сколько бы сервисов ни появилось внутри, наружу (`web`,
внешние клиенты) смотрит одна точка входа. Новые внутренние сервисы
получают HTTP наружу только через `api` как reverse-proxy/агрегатор, либо
не получают публичного адреса вообще (как сегодня `mesh`/`giga` — без
публичного домена, readme.md § «Окружения»).

**Сервисы общаются по HTTP внутри приватной сети/докер-сети** (сегодня:
`api` → `{mesh, giga}`). Тяжёлые/асинхронные задачи — через PostgreSQL-backed
очередь, а не синхронным HTTP-вызовом, когда обработка дольше
запрос-ответного цикла. Это же правило действует и для будущих сервисов:
синхронный вызов для быстрых операций, очередь для тяжёлых/фоновых.

**Данные — у владельца схемы.** Каждый сервис владеет своими таблицами;
чтение чужих данных — через API владельца, не прямой SQL в чужую схему.
Сегодня `api` — единственный владелец Postgres-схемы (readme.md § «Данные и
хранилища»); когда домен выделяется в сервис со своим хранилищем, он
уносит свои таблицы и открывает контракт (эндпоинт/событие) взамен прямого
доступа. Пока миграция не сделана — временный прямой доступ к чужим
таблицам недопустим даже «на время».

**Правила на будущее:**
- Новый сервис объявляет контракт (эндпоинты/схема запроса-ответа) до
  первого вызова из другого сервиса — контракт живёт в `docs/architecture/`
  или в самом сервисе, не только в коде.
- Ломающие изменения контракта — версионируются или согласуются с
  вызывающей стороной заранее; сервис не может в одностороннем порядке
  сломать соседа.
- Секреты и доступ к внешним провайдерам (GigaChat, S3, БД) — у сервиса,
  которому они нужны по существу; не расшариваем креды шире необходимого
  (SECURITY.md § «Сетевые границы»).

## Как команды делят зоны

Соответствие «вертикаль команды ↔ сервис/набор сервисов» держит стыки
явными: если у зоны нет отдельного владельца, она либо часть чужой зоны,
либо повод завести директора. Сегодня (`docs/process/squad.multica.md`):

| Вертикаль (директор) | Сервис(ы) | Зона |
|---|---|---|
| Fullstack | `apps/api` (Back), `apps/mesh` (Mesh), `apps/giga` (AI) | backend, геометрия/3MF, умный слой |
| Design | `apps/web` (Front) | UI, дизайн-система, анимация/звук |
| Data | схема Postgres (`db/migrations/`) | доменная модель, вето на любую схему — сквозь все сервисы, которые её используют |

Одна вертикаль может владеть несколькими сервисами (Fullstack — три), пока
её темп это позволяет; когда направление внутри вертикали перерастает
директора (например, `mesh` или `giga` требует собственного постоянного
фокуса), это повод выделить под него отдельную вертикаль/директора — тогда
и код-граница (сервис уже существует), и организационная граница
совпадают. Это симметрично Принципу 3 философии («расширять заложенное») —
не переписываем структуру, а по мере роста добавляем ещё один узел
«директор ↔ сервис».

Кросс-вертикальная работа (сервис одной команды нужен другой) идёт через
директора владеющей вертикали, не напрямую в чужую зону
(`docs/process/squad.multica.md` § «Кросс-вертикаль»).

## Как структура кода это отражает

Монорепо `apps/{web,api,mesh,giga}` — это уже нарезка по домену, не по
слою (readme.md § «Монорепо»): каждая папка — независимо деплоящийся
сервис с собственным рантаймом, а не общий код, поделённый на клиент и
сервер. Это **семя** микросервисной структуры, не временная заглушка,
которую «перепишем на микросервисы» — рост происходит добавлением новых
`apps/*`, а не сменой архитектуры.

**Как в монорепо живёт много сервисов:** `apps/<service>/` — граница
сервиса и граница владения одновременно; `packages/` — код, общий по
техническим причинам (линт/тайпскрипт-конфиг), не бизнес-логика; общая
Postgres-схема сегодня — временное состояние одного владельца (`api`), не
архитектурное решение «сервисы должны делить БД».

**Критерий, когда сервис уезжает из монорепо** (отдельный репозиторий,
отдельный CI/деплой) — применяем тот же критерий выделения сервиса выше, но
на уровень строже: монорепо разделяем только когда общий репозиторий сам
становится издержкой — конфликтующие релизные циклы (сервис должен
деплоиться чаще/реже остальных), разный доступ команд (внешняя команда не
должна видеть остальной код), или размер CI/чекаута уже мешает. До этого
момента отдельная папка в монорепо даёт всё то же независимое владение и
деплой без цены отдельного репозитория (общий CONTRIBUTING.md, общий
нейминг, один PR-процесс). Пример уже был решён руками: `garage/auth`
(PlagID) — отдельный репозиторий, потому что это внешний по отношению к
порталу сервис с собственным жизненным циклом, а не часть портала; это и
есть ориентир «когда рано, когда пора».

## Итог

«Не монолит» — это принцип на вырост, применённый уже сегодня (полиглот
`web/api/mesh/giga`, единая публичная точка входа через `api`,
модуль-на-домен внутри `api`), а не обещание будущего переписывания.
Каждый следующий сервис появляется по критерию выше — осознанно, когда
рантайм/нагрузка/команда это требуют, — и занимает то же место в структуре,
что и `mesh`/`giga` сегодня: своя папка, свой контракт, свой владелец.
