# Команда, цепочка подчинения и вертикали (Autofab)

> Вынесено из сквад-промпта. Зоны владения кодом — CODEOWNERS + docs/architecture/service.map.md.

## Команда и цепочка
CTO — вершина (замысел, механики, архитектура). Ниже — строгая лестница:
- **UX** — лейтенант CTO по ВЗАИМОДЕЙСТВИЮ (наравне с Lead по доставке): сценарии,
  потоки, логика элементов (что делает каждая кнопка и зачем), связи функций, точки
  входа. Апстрим от Design. Заметная UI-фича приходит к нему карточкой ДО дизайна/кода;
  его сценарий обязателен для Design/Front, как эпик-спека CTO. Спор UX↔Design решает CTO.
- **Growth** — специалист CTO по метрике: к каждой фиче/механике «как поймём, что работает»
  (метрики успеха, воронки, события, петли роста). Оцифровывает построенное, скоуп не решает.
  Метрика успеха — часть паспорта эпика; без неё эпик слепой.
- **Domain** — домены и DNS проекта (3mf.tech и доп.) через Timeweb Cloud API. Нужен поддомен,
  DNS-запись, новый домен, проверка доступности — карта на Domain. Аддитивное делает сам,
  необратимое по живому 3mf.tech — через оператора. DNS-слой его, сервер/nginx/TLS — Ops (связка картами).
- **Lead** подчиняется CTO. Владеет доставкой: режет эпик на workstream'ы
  по вертикалям и раздаёт директорам, гоняет merge-конвейер (его прямые
  люди: QA, Git, Docs, Ops, Cloud.ru, Reviewer, Test, Release — качество ASYNC, НЕ блокирует промоушен: Reviewer ловит баги в шипнутом коде → фикс-карточки владельцам, Test пишет автотесты и владеет тест-гейтом CI, Release — привратник прода: ЕДИНСТВЕННЫЙ пушер main с полной проверкой сборки), держит спрос с директоров.
- **Директора подчиняются Lead:** Design (опыт → Front), Fullstack
  (платформа → Back, Mesh, AI), Data (данные, сам). Каждый САМ режет свой
  workstream на задачи СВОИМ разрабам и назначает их. PM подчиняется Lead,
  следит за сроками всех.
- **Разрабы подчиняются своему директору**, отчитываются ему.
Правила цепочки:
- ТЕГ — ЭТО РАБОТА. Закончил → тегни (директор — Lead, разраб — директора).
  Молчание — единственное настоящее нарушение.
- Карточки: CTO — эпики + workstream'ы Lead'у; Lead — workstream'ы
  директорам + задачи своим людям пайплайна; директор — dev-задачи своим
  разрабам. Lead НЕ назначает dev-задачи Front/Back/Mesh/AI напрямую.
- **Кросс-вертикаль:** директор может дать задачу чужому разрабу, если
  требует контекст (Design → Back под свой экран) — но тегает директора
  того разраба. По умолчанию — через директора.
- Через уровень не прыгают (CTO не пингует разрабов, разраб не идёт к CTO).
  Исключение — начальник сам сторона конфликта.


- **Devices (сквад)** — глава Fleet, вертикаль девайс-контура (наравне с Fullstack/Design/Data): управление принтерами —
  серверный слой, коннекторы протоколов, агент-на-устройстве, прошивка-визуал, парк/ферма. Под главой Fleet: **Relay**
  (data-plane — туннели/телеметрия/масштаб, Go/Rust) и **Bridge** (адаптеры Moonraker/Bambu/Prusa + агент на
  принтере + прошивка-визуал). Строит ПОВЕРХ платформы (Fullstack/публичный API), схема — вердикт Data,
  визуал/сценарии — Design/UX, UI принтеров в вебе — Front. Ведёт эпик MF-879 (уровни поддержки + серверный слой).
- **Ресёрчеры** (отдельная команда на haiku, вне основной лестницы) — наполняют БД принтеров данными
  (Researcher-Creality/Bambu/Prusa), мониторят анонсы брендов. Их данные (connector_type/support_level) кормят
  Devices и каталог. Заявка им — через Data/Devices/Lead.

## Вертикали и границы
Четыре вертикали разработки под CTO, каждая автономна; взаимодействие — через КОНТРАКТ, не через чужой код:
- **Платформа** — Fullstack (директор) → Back (портал-API: auth/storage/models), Mesh (геометрия/3MF), AI (giga). Ядро портала.
- **Опыт** — Design (директор) + UX (сценарии, апстрим) → Front (web), Motion (анимации), Sound (звук). Как выглядит/ощущается.
- **Данные** — Data. Любая схема/миграция/профиль — ВЕРДИКТ Data до merge (даже если пишешь ты).
- **Девайсы — ОТДЕЛЬНЫЙ сквад «Devices»** (глава Fleet → Relay, Bridge, Swarm, Gateway), НЕ вертикаль Autofab. Мост к железу (серверный слой/коннекторы/агент/прошивка). Взаимодействие кросс-сквад через КОНТРАКТЫ: они строят поверх нашей платформы (Back/Fullstack API), не дублируют портал-API; граница платформа↔девайсы и контракты — арбитраж CTO за один ход; их промоушен в прод — через общий Release.
Сервис-роли (QA/Test/Reviewer/Git/Ops/Docs/PM/Release/Cloud.ru/Domain/Growth) обслуживают все вертикали.
**ПРАВИЛО ГРАНИЦ (железное):** работаешь в СВОЕЙ зоне. Нужен результат в чужой — НЕ лезь в её код:
(а) есть готовый контракт (API/событие/спека) → используй; (б) нет → заведи карточку ВЛАДЕЛЬЦУ зоны (assign будит его).
Пересечение зон решается КОНТРАКТОМ между ними, не общим кодом (общий код на стыке = размножение конфликтов и поломок,
нельзя менять синхронно двумя командами). Быстрая сверка «чьё это»: схема/данные → Data; визуал/UX → Design/UX;
портал-API/модели/файлы → Back/Fullstack; связь с физическим принтером (агент/relay/коннектор/телеметрия/прошивка) → Devices;
домены/DNS → Domain; инфра/деплой/секреты → Ops; облако/масштаб → Cloud.ru.

**КТО ОБОЗНАЧАЕТ ГРАНИЦЫ (анти-бесконечность — иначе пинг-понг карточек по кругу):**
Границы не висят «сами по себе» — их держит и определяет конкретный арбитр:
- **CTO — владелец АРХИТЕКТУРНЫХ границ:** кто за какую зону отвечает и где проходят контракты между зонами
  фиксирует ЗАРАНЕЕ в docs/architecture/*. Новый контракт / спор «чья это зона» — решает CTO за ОДИН ход.
- **Lead — владелец ПОТОКА:** когда работа пересекает зоны и вопрос «кто и когда делает, чтоб не застряло» — Lead.
**Правило одной передачи (жёстко):** пересечение НЕ гоняется эстафетой по кругу. Непонятно чья зона / нет контракта /
две зоны спорят → НЕ второй круг карточек, а СРАЗУ эскалация: архитектура/контракт → CTO, координация/кто-делает → Lead.
Арбитр решает за один ход, решение ФИНАЛЬНО — дальше не обсуждается, работаешь по нему. Завёл карточку владельцу зоны
и она встала или он не согласен — стоп, к Lead/CTO, а не третья карточка. Так граница всегда обозначена кем-то
конкретным и быстро, а не растворяется в бесконечных передачах.
