# UX-приёмка: offline-команда, очередь и восстановление (MF-1504)

## Граница

Этот сценарий описывает только уже подтверждённые состояния runtime и
дизайн-контракт. Он не вводит новые API-поля, не обещает поддержку физического
принтера и не подменяет результат команды состоянием сети.

## Journey и правила текста

| Шаг | Подтверждённый факт | Что видит пользователь | Безопасное действие | Нельзя считать / делать |
|---|---|---|---|---|
| 1. Попытка remote-команды offline | `live=false` или `state="offline"`; команда ещё не отправлена | У кнопки: «Команда недоступна: нет связи с принтером». Видно время последней связи, если оно есть. | «Проверить связь». | Создавать запрос или `command_id`, писать «в очереди», отключать кнопку без пояснения. |
| 2. Команда заблокирована по stale/reconnecting/role/capability | Runtime передал соответствующую безопасную причину; команды не отправлялись. | «Команда недоступна: {безопасная причина}». | Соответствующее причине действие: «Обновить статус», «Проверить снова», «Подключить заново» только owner или «Обратиться к владельцу». | Смешивать отказ связи с отказом прав; автоматически повторять команду. |
| 3. Ранее принятая команда в очереди | Только API `202 { id, status: "queued" }`; есть `command_id`. | «{Действие} в очереди; выполнение не подтверждено». | «Проверить статус»; «Отменить команду» только при подтверждённой API-policy. | Получать очередь из offline-состояния, объявлять доставку, ACK или исполнение. |
| 4. Восстановление связи | Runtime начал reconnect, но нового snapshot ещё нет. | Единственный статус связи: «Восстанавливаем связь…»; старые данные остаются с временем. | После server deadline — «Проверить снова». | Оставлять рядом старый offline-banner, бесконечно показывать spinner, разблокировать remote-команды. |
| 5. Синхронизация | Получен snapshot с `seq` новее показанного и актуальным `state_updated_at`. | Однократно: «Связь восстановлена; данные обновлены», затем обычное «Принтер на связи». | Сначала перечитать исход всех `queued`/`sent`/`timeout`, затем дать новый явный запуск. | Считать исчезновение баннера, HTTP success или reconnect подтверждением команды. |
| 6. Конечный исход | Runtime передал `ack`, `error`, `timeout` либо подтверждённый `cancelled`. | `ack`: «Принтер подтвердил: {действие}»; `error`: «Команда не выполнена: {причина}»; `timeout`: «Подтверждение не получено. Состояние принтера неизвестно»; `cancelled`: «Команда отменена». | Для `error` — «Повторить» только из allow-list, иначе «Разобраться»; для `timeout` — «Проверить статус». | Автоповторять, менять телеметрию без свежего snapshot или выдавать timeout за failed execution. |

Статус связи и карточка команды — независимые оси: в каждый момент на экране
ровно один статус связи. `online` очищает offline/reconnecting/stale-индикатор;
`synced` возможен только после нового snapshot. Ошибка/отказ сообщается ровно
один раз через `role="alert"`, обычное изменение связи — через один
`aria-live="polite"`; текст, иконка и semantic tone дублируют смысл.

## Приёмочный сценарий

### Предусловия

- Используется simulator/fixture из MF-1497; это не тест физического принтера.
- Есть пользователь с разрешённой remote-командой и команда, которую runtime
  может принять в очередь.
- В журнале проверок сохраняются только безопасные state, `command_id`,
  `correlation_id` (если отдан), время и фактический UI-текст — без секретов и
  raw diagnostics.

### Шаги и ожидаемый результат

1. Передать `offline` и попытаться выполнить remote-команду. Должна появиться
   понятная причина и «Проверить связь»; запроса и `command_id` нет.
2. Передать `stale`, `reconnecting`, а также отказ роли/capability по одному.
   В каждом случае текст и recovery соответствуют именно причине; очередь не
   создаётся.
3. Для уже принятой операции вернуть `202 { id, status: "queued" }`. Карточка
   показывает `queued`, `command_id`, отсутствие подтверждения выполнения и
   только разрешённые действия.
4. Во время `queued` передать reconnect без нового `seq`. Экран показывает
   один status связи и не меняет исход команды.
5. Передать свежий snapshot с большим `seq`. Проверить одноразовое `synced`,
   очистку offline/reconnecting/stale и последующее перечитывание исхода
   сохранённой команды.
6. Отдельными прогонами передать `ack`, `error`, `timeout` и `cancelled`.
   Проверить точный текст и действие recovery; ни один из исходов не заменяет
   свежий snapshot телеметрии.

## Критерии

**PASS:** причина отказа понятна и находится рядом с действием; есть безопасный
следующий шаг; `blocked`, `queued`, `synced` и terminal outcomes различаются;
очередь и восстановление связи не считаются исполнением команды; после нового
snapshot на экране остаётся единственный актуальный статус связи.

**FAIL:** зафиксировать шаг, фактический текст, доступное действие,
`connection_state`, `command_state`, безопасный `command_id`/`correlation_id`
и владельца: UX — неоднозначная формулировка или путь; Design — конфликт
матрицы/копирайта; Front — неверный mapping, дублирование, accessibility или
optimistic UI. Если отсутствует runtime-факт/terminal outcome, владелец —
Fleet/Relay; это blocker, а не повод угадывать поведение.
