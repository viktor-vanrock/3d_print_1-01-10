## Метод 1 — Email, домен-гейт (`@sberbank.ru` / `@sberdevices.ru`)

**Не Сбер ID / OAuth** — уточнение 2026-07-03 отменяет это. Это обычный email-логин (скорее всего OTP-код или magic-link на почту — выбор конкретного механизма ниже), с единственным ограничением: адрес должен быть в домене `sberbank.ru` или `sberdevices.ru`, иначе регистрация отклоняется на этапе ввода. Судя по всему — метод для внутренних пользователей/тестировщиков экосистемы Сбера, не для массовой аудитории.

- **Механизм подтверждения:** рекомендация — one-time code на почту (6 цифр, TTL 10 минут), не magic-link (проще на бэкенде, не требует стабильного deep-link домена на момент MVP). Не решено окончательно — открытый вопрос ниже.
- **Домен-allowlist** — конфигурируемый список (`['sberbank.ru', 'sberdevices.ru']`), не хардкод в SQL/коде — на случай расширения набора корпоративных доменов.
- ~~Прежний ресёрч по Сбер ID оставлен как справочный материал на будущее~~ — **активирован 2026-07-06**: Валерий подтвердил, что нужен именно Сбер ID как отдельный (третий) метод входа. См. Метод 3 ниже — там теперь Сбер ID, не GigaID/`id.ru`.

## Метод 2 — PlagID

Это наша собственная система: `auth.plag.space` (Cloudflare Worker, Hono+D1) — по факту **Telegram OIDC/OAuth 2.0** под капотом (`oauth.telegram.org`), сессия — JWT в cookie `plag_session` на домене `.plag.space`. Уже работает и используется в garage.plag.space, draft.plag.space, plag.space.

**Технический разрыв, который нужно закрыть:** сегодняшний `/login` → `/callback`-флоу в `garage/auth/src/index.ts` **создаёт сессию только через cookie на `.plag.space`** — portal.ru живёт на домене `3mf.tech`, чужом для этого cookie. Простой редирект на `auth.plag.space/login?redirect=https://3mf.tech/...` не даст 3mf.tech получить сессию — cookie туда не долетит (разные домены).

**Готовый прецедент в том же коде:** для Telegram Mini App (draft.plag.space) уже реализован паттерн «выдать JSON с данными сессии вместо cross-domain cookie» — `POST /tg/miniapp {initData}` → `{user, projects, startParam}` + Set-Cookie на **своём** домене. Нужно сделать симметричный эндпоинт для обычного OAuth-редиректа (не Mini App): например, `GET /callback` уже сегодня поддерживает `redirect`-параметр — расширить так, чтобы для доверенных внешних `redirect`-доменов (allowlist, включая `3mf.tech`) он возвращал не просто редирект-с-cookie-на-своём-домене, а **подписанный короткоживущий токен** в query/fragment (`?token=<JWT>`), который `apps/api` (наш Fastify) верифицирует (тот же `JWT_SECRET` — либо новый, вопрос ниже) и уже сам выставляет **свою** сессионную cookie на `.3mf.tech`.

Итого PlagID = «Войти через Telegram/plag.space», реализуется через **небольшое расширение существующего auth-воркера**, а не с нуля.

## Метод 3 — SberID (пересмотрено 2026-07-06, заменяет GigaID/`id.ru`)

**Валерий подтвердил 2026-07-06: третий метод — «SberID», это и есть Сбер ID** (полноценный OAuth 2.0 +
OpenID Connect, `developers.sber.ru/docs/ru/sberid`), не GigaID/`id.ru`. Исследование GigaID/`id.ru` (см.
`<details>` ниже, оставлено для истории) закрыто — тот провайдер так и не подтверждён как публично
доступный для интеграции; SberID, наоборот, задокументирован, бесплатен для подключения и не требует
гипотез. Полный ресёрч по SberID уже был сделан 2026-07-03 (см. `<details>` в Методе 1 выше — Authorization
Code Flow + PKCE, JS/Android/iOS SDK, регистрация организации на портале Сбер ID → оферта ЭДО → `Client
ID`/`Client Secret`, поддержка `support_sberid@sber.ru`) — переносить сюда не дублируем, там всё есть.

**UI-требование (Валерий, 2026-07-06):** на экране входа — Sber-почта (текущий Метод 1, сверху, как уже
реализовано в `login.tsx`), а под ней два равных по значимости метода в один ряд: **SberID слева**, **PlagID
справа** (наш внутренний Telegram-метод, уже там сегодня). Макет — на замену текущего неактивного слота
GigaID (см. `apps/web/src/pages/login.tsx`, кнопка `provider="gigaid"` с `disabled` и подсказкой «id.ru пока
недоступен» — переименовать в SberID и разблокировать, когда появится реальный `Client ID`).

**⚠️ Блокирующая зависимость — не код, а внешняя регистрация:** для старта интеграции нужен реальный
`Client ID`/`Client Secret` от Сбер ID — это **партнёрская регистрация организации на портале Сбер ID +
оферта по ЭДО**, сделать это может только Валерий (аналогично тому, как для PlagID нужна была регистрация
бота в BotFather). До получения кредов `/auth/sberid/*` остаётся заглушкой (501) — реализовать сам
OAuth-флоу (redirect → callback → обмен кода → апсерт `users`/`user_identities` с `provider='sber_id'`,
паттерн один в один с `plagid.ts`) можно сразу, как только появятся креды — код небольшой, основная
неопределённость снята исследованием 2026-07-03.

**Заметки к реализации (собрано при ревизии MF-25, не блокирует, но проверить перед merge callback-кода):**
- **Identifier для `identifier_hash`:** UserInfo Сбера отдаёт телефон как основной claim (email опционален).
  Хешировать стабильный `sub`, если он есть в токене; если `sub` нестабилен между входами — нормализованный
  телефон в E.164. НЕ email (может отсутствовать у SberID в отличие от email-гейта Метода 1).
- **Обязательный аналитический бикон Сбер ID** — часть протокола, не опция: без него Сбер вправе
  приостановить интеграцию. Включить отправку бикона в тот же PR, что и сам OAuth-флоу, не отдельным тикетом.
- **Возможен клиентский сертификат (mTLS) при обмене кода на токены**, а не просто `client_secret` в теле
  запроса — уточнить в документации Сбер ID при получении кредов и заложить в деплой на VDS (не только
  env-переменная, возможно нужен файл сертификата с правами доступа как у `~/portal.api.env`).
- **152-ФЗ / персональные данные:** SberID передаёт ПД (телефон, ФИО). Нужна опубликованная политика
  конфиденциальности и согласие на обработку ПД на 3mf.tech до прод-запуска метода — это отдельная
  под-задача (не техническая), завести при получении кредов, не забыть.
- **Account-linking коллизия:** один и тот же человек может войти сначала через SberID (ключ = `sub`/телефон),
  потом через email-домен-гейт (ключ = email) — модель `user_identities` их сейчас не связывает, получатся
  два независимых `users`-ряда. Явно не решаем сейчас (нет постановки от Валерия), но зафиксировать как
  известное ограничение, а не забытый баг, если всплывёт в проде.

## Модель данных (спроектировано 2026-07-03)

Требование Валерия: **id пользователя не должен палить количество зарегистрированных юзеров** (не sequential/auto-increment), публичный хендл — в формате `@ник` (как Telegram), сырые данные провайдера (email/provider-id) — в S3-бакете `auth`, зашифрованные.

### Postgres — `users` и `user_identities`

```sql
create table users (
  id uuid primary key default gen_random_uuid(), -- pgcrypto, ⚠️ НЕ uuid v7/ULID
  username text not null unique,                  -- "@ник" без "@", хендл
  display_name text,
  avatar_url text,
  status text not null default 'active'           -- active | banned | deleted
    check (status in ('active', 'banned', 'deleted')),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table user_identities (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references users(id) on delete cascade,
  provider text not null check (provider in ('email_corp', 'plag_id', 'sber_id')),
  identifier_hash bytea not null,   -- HMAC-SHA256(lower(email|tg_id|...), AUTH_HMAC_KEY) — слепой индекс
  s3_key text not null,             -- 'identities/<user_id>/<provider>.json.enc' в бакете `auth`
  verified_at timestamptz not null default now(),
  created_at timestamptz not null default now(),
  unique (provider, identifier_hash)
);
```

**Почему `id` не через `uuid_generate_v7()`/ULID:** v7/ULID **специально** содержат таймстемп в старших битах ради сортируемости по индексу — это ровно то, что нужно избежать: имея два ID, снятых с разницей в день, можно оценить темп регистраций, а имея текущий ID — примерную дату создания. `gen_random_uuid()` (UUID v4, полностью случайный) не сортируется по времени и не даёт подобной утечки. Осознанный trade-off: индекс по `id` чуть менее «тёплый» в кэше при вставках, чем с v7 — для нашего масштаба (мейкер-платформа, не high-load) это не критично.

**Как `identifier_hash` защищает соответствие «явно указанный email/tg-id → юзер»:** при логине для найденного email/tg-id считаем `HMAC-SHA256(identifier, AUTH_HMAC_KEY)` и ищем по `(provider, identifier_hash)` — сам identifier (email, telegram id и т.п.) в Postgres не хранится, только его HMAC и ссылка на зашифрованный объект в S3. Postgres-дамп/бэкап сам по себе не раскрывает ни одного реального email.

### S3-бакет `auth` — сырые данные провайдера

Ключ объекта: `identities/<user_id>/<provider>.json.enc` (`user_id` — тот же непоследовательный UUID, не даёт понять порядок/количество по имени объекта).

Содержимое объекта — AES-256-GCM, зашифровано ключом `AUTH_ENCRYPTION_KEY` (**новый секрет, отдельный от `JWT_SECRET` и от `AUTH_HMAC_KEY` выше** — три разных секрета с разным назначением, компрометация одного не раскрывает остальные), только на VDS/GitVerse Actions Secrets:

```json
{
  "provider": "email_corp",
  "identifier": "ivan.petrov@sberbank.ru",
  "raw_claims": { "...": "как есть от провайдера" },
  "verified_at": "2026-07-03T12:00:00Z"
}
```

Расшифровка нужна редко (саппорт/расследование инцидента), не на каждый логин — обычный логин работает через `identifier_hash` в Postgres, к S3 вообще не обращаясь.

**Важная честная оговорка (не оверселлить свойство):** непоследовательный `id` + шифрование не прячут *количество объектов в бакете* от того, у кого есть прямой доступ к S3-бакету `auth` (листинг `s3 ls` покажет реальное число ключей) — это защищено не шифрованием, а тем, что доступ к бакету есть только у `apps/api` через ключи на VDS (см. `SECURITY.md` § «Секреты»), не публичный. Шифрование + непоследовательный ID защищают от другого случая: если один объект/строка утечёт (лог, дебаг, скриншот), по нему нельзя понять, «пользователь номер сколько» это и когда он зарегистрировался.

### `username` — формат `@ник`

Публичный хендл, отдельная колонка от `id`. Валидация: lowercase, `^[a-z0-9](?:[a-z0-9.]{1,30}[a-z0-9])?$` (буквы/цифры/точка, 3–32 символа, уникально без учёта регистра). Это **продуктовый** формат (как у пользователя, `@plag`), не подчиняется файловому правилу «никаких `-`/`_`» из `CONTRIBUTING.md` — то правило про имена файлов/веток в репозитории, не про пользовательские данные; здесь просто выбран простой URL-safe формат для консистентности с остальным plag.space (Telegram-подобные хендлы).

## Приватная бета — allowlist по Telegram ID поверх PlagID (2026-07-06)

PlagID изначально был **открытой регистрацией**: любой Telegram-пользователь, прошедший OIDC на `auth.plag.space`, автоматически получал `users`-ряд и сессию на 3mf.tech (`/auth/plagid/callback` в `plagid.ts` делает `insert ... on conflict do update`, без проверки прав). По запросу Валерия («хочу дать доступ конкретным людям, а в UI auth.plag.space нет для этого места») — вход закрыт allowlist'ом.

**Механизм — переиспользован `draft_access`**, а не заведена новая сущность:
- `garage/auth` (отдельный репозиторий, воркер `auth.plag.space`) — у него уже был `draft_access`/`draft_projects` (userid+slug+role), обслуживающий вкладку «Drafts» для draft.plag.space-проектов, и админ-UI grant/revoke по Telegram ID.
- Заведён искусственный slug `3mf` в `draft_projects` (НЕ настоящий draft.plag.space-проект) — точечно поправлена HTML-админка, чтобы для этого slug ссылка/подпись указывали на `3mf.tech`, а не на дефолтный `draft.plag.space/<slug>`.
- В `createSession` (`garage/auth/src/index.ts`) перед выдачей внешнего короткоживущего токена (`EXTERNAL_TOKEN_SECRET`) для хостов `3mf.tech`/`api.3mf.tech` — проверка `draft_access` по (userid, slug='3mf'); global admin (`isadmin`) проходит без записи в таблице. **Осознанно НЕ распространено на `tasks.3mf.tech`** — у доски Multica свой отдельный гейт (`ALLOWED_TG_IDS`, см. `docs/process/tasks.multica.md`), дублировать не стали.
- `apps/api/src/auth/plagid.ts` (`/auth/plagid/callback`): при отказе (auth.plag.space не выдал `token`) раньше отдавался голый `400 {"error":"missing token"}` — теперь редирект на `WEB_APP_URL/?error=access_denied`, `apps/web/src/pages/login.tsx` показывает баннер с понятным текстом вместо JSON.
- Управление доступом — тот же существующий UI: `auth.plag.space` → вкладка Drafts → проект «3mf.tech (Portal.ru)» → «Дать доступ»/Telegram ID. Ничего нового строить не пришлось.

Задеплоено 2026-07-06 (воркер `auth.plag.space` — `wrangler deploy`; `apps/api`/`apps/web` — через автодеплой `main`, см. `docs/infra/readme.md` § «Деплой `main`»). Проверено через прямой запрос к D1 (`auth`, remote): `draft_access` для slug `3mf` пуст — то есть сейчас доступ есть только у глобального admin, все остальные Telegram-пользователи получат `access_denied`, пока не будут добавлены явно. Полный e2e через реальный Telegram OAuth не проверялся (curl не может пройти интерактивный `oauth.telegram.org`-флоу) — проверка логики через код-ревью + пустую `draft_access` таблицу.

## Критерии приёмки (Фазы 1–2)

- Пользователь может зарегистрироваться/войти через Telegram (PlagID) и получить рабочую сессию на 3mf.tech. **Код готов, не проверено вживую (нет деплоя).**
- Пользователь с почтой в домене `sberbank.ru`/`sberdevices.ru` может войти по коду и получить рабочую сессию; любой другой домен — отклонён на этапе ввода. Не реализовано (Фаза 2).
- Один и тот же человек не создаёт дублирующийся `users`-ряд, входя дважды одним и тем же методом (уникальность по `(provider, identifier_hash)`).
- Ни в Postgres, ни в логах не встречается сырой email/telegram-id в открытом виде — только `identifier_hash` (Postgres) и зашифрованный объект (S3 `auth`).
