# Метрики маркетплейса (MF-731, Фаза 2 эпика MF-41)

← [docs/product/vision.md](vision.md) · см. также [docs/epics/analytics.events.md](../epics/analytics.events.md) (схема `events`, таксономия, порог ClickHouse)

North Star двустороннего маркетплейса — **ликвидность** (доля предложения, находящего спрос), не GMV: GMV легко расти демпингом/раздачей, ликвидность нельзя накрутить без реального совпадения спроса и предложения. Все вьюхи ниже — `apps/api/db/migrations/20260710240000_marketplace_metrics_views.sql`, читают только `models`/`events`/`tags`/`model_tags`/`user_printers` (уже существующие таблицы, MF-608/MF-462/MF-435) — новых таблиц миграция не заводит.

Сегментация — **по роли действия в конкретном событии**, не по типу юзера: один и тот же `user_id` может публиковать модели (роль автора при `upload_publish`) и скачивать чужие (роль покупателя при `model_download`) — метрики ниже никогда не считают одного юзера дважды на обеих сторонах ОДНОЙ и той же метрики (например, автор не входит в demand собственной модели, см. п.4 «внешнее скачивание»).

## 1. Liquidity — `marketplace_liquidity_30d`

Классический match-rate маркетплейса («доля предложения, нашедшего спрос за окно») адаптирован под цифровой товар: скачивание модели — не дефицитный слот (в отличие от такси/аренды), поэтому «нашла спрос» = «получила ≥1 скачивание», без ограничения на «слот занят только одним покупателем».

```
liquidity_rate = published_models_30d_with_download / published_models_30d
```

- **Окно** — `models.created_at >= now() - 30 days`, `status = 'ready'` (опубликована, не черновик/в обработке).
- **Источник скачиваний** — `models.downloads_count` (денормализованный счётчик, консистентно инкрементится API при каждом download, MF-462/MF-709/MF-656), **не** `events.model_download`. Выбор задокументирован: окно и так на `created_at` модели (не старше 30 дней), поэтому `downloads_count` на момент запроса физически не может включать скачивания «из будущего» относительно окна — джойн к `events` дал бы тот же ответ ценой скана потенциально куда большей таблицы (см. `analytics.events.md` § «Порог ClickHouse», `events` растёт на каждый поиск/просмотр/скачивание, `models` — только на публикацию).
- **Проверено на dev (2026-07-10, портал живёт первый день, данных почти нет — ожидаемо)**: `published_models_30d=0` → `liquidity_rate = null` (честный `nullif`, не `0/0`-ошибка).

## 2. Search → download match-rate — `marketplace_search_match_rate_30d`

Доля поисков (`events.first_search`), после которых тот же subject скачал модель (`events.model_download`) **в течение 30 минут** после поиска.

```
search_to_download_match_rate = searches_with_download_30d / searches_30d
```

- **`first_search` эмитится на КАЖДЫЙ непустой поисковый запрос**, не только на буквально первый в жизни юзера (см. комментарий `apps/api/src/models/list.ts` рядом с `emitEvent`) — метрика не завышена «первым поиском», это обычная поисковая конверсия.
- **Subject** — `coalesce(user_id::text, anon_id)`. Сегодня `user_id` присутствует у ОБОИХ событий всегда (весь портал за auth-гейтом, см. `CLAUDE.md` сквада — preHandler закрывает всё кроме `/health`/`/auth/*`), `anon_id` — задел на случай будущего анонимного доступа.
- **Окно 30 минут** — приближение, не пользователя за пультом секундомером: в событии нет прямой связи «этот download — результат ИМЕННО этого search» (нет `search_id` в `props.model_download`), поэтому окно после поиска — прокси «скачивание случилось в той же сессии просмотра». 30 минут выбрано как типичная верхняя граница сессии просмотра каталога (короче, чем сутки/окно ретеншна, длиннее одного клика) — если разрыв конверсии на дашборде окажется нестабильным относительно окна, первое, что стоит проверить, — сузить/расширить окно, не менять формулу.
- **EXPLAIN (2026-07-10, dev)** — `Index Scan using events_name_ts_idx` на обеих ветках (поиск по `event_name`+`created_at`, индекс из baseline MF-429), без seq scan; `Execution Time: 0.124 ms` на текущем объёме (1 событие). При росте `events` к порогу ClickHouse (`analytics.events.md` § «Хранилище») пересчитать план на реальном объёме — коррелированный подзапрос `exists (... d.subject = s.subject ...)` не покрыт индексом по `subject` (это `coalesce`-выражение, не колонка), это первое место, где заведётся выражение-индекс, если план начнёт делать bitmap heap scan большого размера.

## 3. Take-rate / GMV / net revenue — `marketplace_gmv_take_rate`

**В схеме нет таблиц `purchase`/`payout`/`orders`, и ни одна ручка `apps/api` их не создаёт** (эти фичи — деньги — вне скоупа MF-731, см. «Не в скоупе» карточки). Вместо фиктивных данных вьюха честно читает `events` по именам `purchase`/`payout_requested` — они уже приняты констрейнтом `events_event_name_check` (baseline MF-429, `analytics.events.md` § «Таксономия»), просто ни одна ручка их пока не пишет.

```
gmv          = sum(события 'purchase'.props.amount)               -- gross, с покупателя
payouts_total = sum(события 'payout_requested'.props.amount)       -- net, автору после комиссии
net_revenue  = gmv - payouts_total                                  -- удержанная комиссия платформы
take_rate    = net_revenue / gmv
```

Сегодня обе суммы читают 0 строк → `gmv=0`, `payouts_total=0`, `net_revenue=0`, `take_rate=null` (`nullif(gmv,0)`, не деление на 0). **Как только появится реальная ручка покупки/выплаты — вьюха начнёт считать реальные цифры без новой миграции**, при условии, что эмиттер использует контракт `props` ниже (это интерфейс для будущей карточки покупок, саму ручку эта карточка не строит):

| Событие | `props` | Комментарий |
|---|---|---|
| `purchase` | `{model_id, seller_id, amount}` | `amount` — gross RUB, сумма, которую заплатил покупатель (`user_id`/`anon_id` события = покупатель) |
| `payout_requested` | `{model_id, seller_id, amount}` | `amount` — net RUB, сумма, которую получит автор после комиссии платформы |

Если будущая ручка выберет другие имена ключей — вьюха не упадёт (`->>'amount'` на отсутствующий ключ = `null`, `sum()` игнорирует `null`), но молча продолжит показывать 0 вместо реальных цифр. Кто бы ни делал ручку покупок — держать эти два имени ключа или обновить эту вьюху в той же миграции, где заводится `purchase`.

## 4. Time-to-first-sale автора

**`marketplace_time_to_first_sale`** — целевая метрика по формуле эпика: интервал между первой публикацией автора (`upload_publish`, `min(created_at)` по `user_id`) и его первой продажей (`purchase`, `props.seller_id`). Как и GMV/take-rate, сегодня возвращает `avg_days_to_first_sale = null` (0 строк `purchase`) — это ожидаемо, не ошибка.

**`marketplace_time_to_first_download_proxy`** — ⚠️ **PROXY-метрика**, не подмена time-to-first-sale: пока продаж физически нет, публикация → первое скачивание модели автора **внешним юзером** (`e.user_id is distinct from m.owner_id` — автор, скачивающий свою же модель для проверки, не считается «внешним интересом», иначе первая же самопроверка после публикации давала бы `0 дней` для всех и метрика была бы бессмысленной). Обе вьюхи существуют раздельно и не переиспользуют общее имя — на дашборде подписывать вторую явно как «прокси, не продажи».

## 5. Supply/demand баланс по категориям/принтерам — `marketplace_supply_demand_by_printer_tag`

Сопоставляет «моделей под бренд X» (по тегу) vs «печатников с принтером бренда X» (по `user_printers.brand`):

```
models_per_printer_owner = models_count / printer_owners_count
```

- **Эвристика (важно)**: в схеме нет формального поля «модель совместима со станком X» — `apps/api` пока не формализовал это как отдельную колонку (см. `analytics.events.md` § «Усиление гипотезы принтера», тот же открытый вопрос MF-32). Сопоставление здесь идёт **по текстовому совпадению `lower(tags.name) = lower(user_printers.brand)`** — теги свободные, без модерации (MF-462), значит это приближение: автор мог не проставить тег с именем бренда, а мог проставить тег, который бренду не соответствует. Это не тянет на полноценный компат-фильтр — как только MF-32 формализует поле совместимости на `models`/`model_files`, эту вьюху нужно переписать на JOIN по нему, не по имени тега.
- **`full join`** между сторонами намеренный: бренд с держателями принтера, но без единого тега с таким именем, обязан попасть в отчёт с `models_count=0` — именно эта строка и есть сигнал «явного перекоса» (много принтеров этого бренда на руках, ни одной модели под него в каталоге), который просит карточка.
- **Проверено на dev (2026-07-10)**: `tags`/`model_tags` пустые (каталог только запущен), `user_printers` — 4 строки (`Bambu Lab` × 2, `Homebrew` × 2). Вьюха вернула ровно это: обе строки с `models_count=0`, `printer_owners_count=2`, `models_per_printer_owner=0` — рабочий пример максимального перекоса «спрос есть, предложения нет», именно то поведение, которое метрика должна показывать на молодом каталоге.

## Двойной учёт сторон — как исключён

- **Liquidity/match-rate** — считают модели/события, не юзеров; один и тот же юзер, который и публикует, и скачивает, не создаёт двойного счёта, потому что метрика не группирует по юзеру вообще.
- **Time-to-first-download proxy** — явно исключает автора, скачивающего собственную модель (`e.user_id is distinct from m.owner_id`), иначе автор считался бы «своим первым покупателем».
- **Supply/demand по принтерам** — supply считается по моделям (владелец модели неважен), demand — по держателям принтера (`user_printers.user_id` неважен для группировки, считаются владения, не владельцы) — одна и та же персона, будь она автором модели с тегом «bambu lab» и одновременно держателем Bambu Lab, попадает в обе стороны один раз каждая (это и есть корректный «двусторонний» подсчёт, не задвоение — маркетплейс двусторонний по определению, разные роли одного юзера должны считаться в обеих сторонах ровно по разу).
