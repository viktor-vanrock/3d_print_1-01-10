# Мастер-план эпиков — организация по направлениям (для декомпозиции CTO)

**Назначение.** Крупные детальные эпики по ВСЕМ направлениям продукта, с приоритетом, сроком,
скоупом, фазами, владельцем-сквадом, зависимостями и критериями приёмки. Организовано так, чтобы
**CTO разложил каждый эпик на 4–8 крупных delivery-подзадач первой волны (Lead) → связанные шаги чеклистом в описании**
([roadmap.md](product/roadmap.md) «Правила ведения доски»). Источник КОГДА — [roadmap.md](product/roadmap.md);
ЧТО — [features.md](product/features.md); этот файл — организация и нарезка.

## Как читать
- **Приоритет:** `P0` (блокер дедлайна, urgent) · `P1` (high) · `P2` (medium) · `P3` (low/задел).
- **Срок** привязан к версии-поставке: **v1 = 30.09.2026** · **v2 = 31.12.2026** · **v3 = Q1 2027** ·
  v4–v6 = 2027+. Девайс-контур — отдельная ось (оператор грузит СЕЙЧАС, поставка v1), у неё свои
  под-дедлайны.
- **MF** — якорь на существующую карту-эпик (не плодить дубли; если нет — CTO заводит).
- **Deadline-first закон:** данные раньше интеллекта, интеллект раньше денег. Фичи двигаются ВНИЗ
  по версиям, не пересматривая остального (решение CTO при риске срыва).

## Инструкция CTO (общая для всех эпиков ниже)
Для каждого эпика: (1) проверь/заведи карту-эпик в проекте-НАПРАВЛЕНИИ (docs/process/board.projects.md) с лейблом версии; (2) разложи на **крупные
подзадачи по фазам** (Ф1 фундамент → Ф2 основной поток → Ф3 полировка), по одной на владельца-агента;
(3) в каждой подзадаче — скоуп + шаги чеклистом + критерии приёмки + зависимости; (4) проставь
приоритет и due_date подзадачам от дедлайна эпика назад; (5) блокеры — одному владельцу, не плодить
эпики. Версия задаёт лейбл и due_date, НЕ проект. Эпик закрываешь только ты после проверки DoD.
