## Суть

3 способа входа: **email, только домены `@sberbank.ru`/`@sberdevices.ru`** (уточнено 2026-07-03, не Сбер ID OAuth — простой домен-гейт + OTP), **PlagID** (расширение `auth.plag.space`, Telegram OIDC, нужен новый эндпоинт для чужого домена), **SberID** (полноценный OAuth2/OIDC Сбер ID, `developers.sber.ru/docs/ru/sberid` — пересмотрено 2026-07-06, заменяет закрытую тему GigaID/`id.ru`, см. спеку § Метод 3). UI экрана входа (2026-07-06): Sber-email сверху, SberID и PlagID — рядом под ним (SberID слева, PlagID справа).

Модель данных: `users`(непоследовательный UUID v4, `@username`-хендл) + `user_identities`(HMAC-слепой индекс, без сырых email/id) в Postgres, сырые claims провайдера — зашифрованы (AES-256-GCM) в S3-бакете `auth`. Полный разбор — в спеке, раздел «Модель данных».

Управление — тот же админ-таб «Drafts» на `auth.plag.space` (проект `3mf` там теперь виден, с корректной ссылкой на `3mf.tech`, не на `draft.plag.space/3mf`). Отказ до выдачи токена → `apps/api` (`plagid.ts` callback) редиректит на логин с `?error=access_denied` вместо голого 400, `login.tsx` показывает баннер. Задеплоено (воркер `auth.plag.space` + VDS автодеплоем). **Сейчас `draft_access` для slug `3mf` пуст — доступ есть только у глобального admin, остальным нужно выдать вручную через UI.**
- [x] Фаза 2 — Email-домен-гейт (`sberbank.ru`/`sberdevices.ru`): UI (локальная часть + select домена, `EmailLogin.tsx`) + `/auth/email/start`+`/verify` (`email_otp`-таблица, HMAC-хеш кода, TTL 10 мин, cooldown 60с, лимит 5 попыток) готовы, задеплоены, e2e проверены. **Отправка письма НЕ подключена** — email-провайдер (SMTP/API) не выбран, код временно только в логе `journalctl -u portal.api.service` — рабочий канал для внутреннего теста, не для реальных пользователей.
- [x] **Код отправки email готов и включён (2026-07-06).** `apps/api/src/email/send.ts` (nodemailer) вызывается из `/auth/email/start` вместо голого `log.warn`; без `SMTP_HOST`/`PORT`/`USER`/`PASS`/`FROM` в окружении остаётся no-op-with-warning (дев/тест без изменений). Провайдер — SMTP через **Timeweb** (`smtp.timeweb.ru:465`, тот же хостинг, что держит MX 3mf.tech; SPF `v=spf1 include:_spf.timeweb.ru ~all` подтверждён вручную — выбран вместо западных ESP типа Resend ради доставляемости на корп-почту `@sberbank.ru`/`@sberdevices.ru`). Ящик `auth@3mf.tech` заведён Валерием в панели Timeweb, креды — в `~/portal.api.env` на VDS (chmod 600, не в git).
- [x] **DKIM/DMARC добавлены (2026-07-06), Protonmail всё равно не доставляет — диагноз закрыт как политика получателя.** Первый тест (`nodemailer` → `plagness@protonmail.com`) получил `250 OK` от Timeweb, но письмо не дошло (ни инбокс, ни спам; IMAP `auth@3mf.tech` — везде пусто, bounce не было). Диагностика: DSN-тест + контрольное письмо на `plagness@icloud.com` → iCloud получил, Protonmail — нет. Валерий добавил в DNS Timeweb DKIM (`dkim._domainkey.3mf.tech`, селектор `dkim`) и DMARC (`_dmarc.3mf.tech`, `p=none`) — подтверждено вручную (dig) и через self-send + чтение сырых заголовков (`DKIM-Signature: ... d=3mf.tech; s=dkim` реально присутствует и валиден). **Повторный тест на Protonmail ПОСЛЕ публикации записей — снова не доставлено.** Вывод: технически всё настроено правильно (SPF+DKIM+DMARC), Protonmail тихо роняет письма от новых доменов без истории отправок вне зависимости от аутентификации — это политика получателя, не наша конфигурация. **Дальше не гонять** — Protonmail не входит в целевую аудиторию продукта. Полная методика диагностики (self-send, DSN, RBL-проверка, IMAP-инспекция) — вынесена в общий `docs/infra/email.md`, не дублируется здесь.
- [ ] **Реальная проверка на `@sberbank.ru`/`@sberdevices.ru` — единственный тест, который на самом деле имеет значение, ещё не проводился.** Нет доступа ни к одному реальному ящику на момент написания. Корп-шлюз банка — другой профиль фильтрации, чем консьюмерский Protonmail, результат непредсказуем по аналогии. Как появится реальный тестовый адрес — прогнать методику из `docs/infra/email.md`.
