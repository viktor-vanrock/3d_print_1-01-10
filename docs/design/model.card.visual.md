## 1. Отступ героя от верхних блоков — токены (v3 §9)

**Что сейчас** (подтверждаю замер v3 §9): `.homeTopbar` — padding 16px + внутренний ряд `min-height: 52px` ⇒ блок шапки ≈ **84px**. `.homeContent` даёт после него всего `padding-top: 8px`. Шапка **не** `position: fixed` (обычный поток) — но `.modelViewerStage` на десктопе получает `position: sticky; top: 20px` (`model.css:87`), то есть при скролле вьюер сам ловит себя в 20px от **верхнего края вьюпорта**, а не от шапки — тесно и без запаса под будущий верхний блок (баннер/режим), ровно то, о чём просит оператор.

**Токены (`theme/tokens.css`, рядом с `--z-*`, глобальные — переиспользуются любым будущим sticky-под-шапкой элементом):**

```css
--header-safe: 88px;    /* высота капсулы-шапки + дыхание (84px факт + запас) */
--hero-top-gap: 24px;   /* второй отступ: герой карточки не «поднырывает» под шапку */
```

**Применение (только карточка модели, не переписываю `.homeContent` глобально — остальные страницы вне этой карточки):**
1. `.modelViewerStage` (`model.css:87`) — `top: 20px` → `top: var(--header-safe)`.
2. `.modelHero` (`model.css:9`) — добавить `margin-top: var(--hero-top-gap)`.
3. Никаких новых магических чисел — появится баннер/тир-режим сверху, меняется `--header-safe`, не пять файлов.

## 2. Полноэкранный режим 3D-вьюера (v3 §3)

### 2.1 Вход — вторая кнопка в чроме

Рядом с уже существующей `.modelViewerReset` (`modelviewer.tsx:145-154`, круглая glass-кнопка 40×40, `top:14 right:14`, видна только при `state === "active"`) — вторая круглая glass-кнопка **того же размера и формулы** (`modelGlassBtn`, только `padding:0`/40×40, тот же line-стиль, что `RotateIcon`/`ResetIcon` рядом):

- **Глиф** — четыре угла-скобки к центру/от центра (стандартный «expand», line ~2px, без заливки — components.md «Иконки»).
- **Позиция** — левее «Сбросить вид», тот же ряд `top:14`, зазор 8px между кнопками (`right: 14px` у «Сбросить вид», `right: 62px` у «На весь экран» — 40+8+14).
- **Видимость** — только `state === "active"` (как «Сбросить вид»); на постере кнопки нет вовсе (v3: «иначе фулскрин откроет статичную картинку»).
- `aria-label="На весь экран"`.

### 2.2 Композиция в фулскрине

Контейнер вьюера растягивается на весь кадр (реальный `requestFullscreen()` или CSS-фолбэк `position:fixed; inset:0`, §2.4). Фон — тот же studio-градиент, что `.modelViewerStage` (`radial-gradient` по `--tile-hue`, `model.css:77-83`), растянутый на весь вьюпорт — не белая/пустая заливка, никаких вспышек при входе.

**Чром фулскрина** (крупнее обычного — единственный фокус кадра, тач-цели генерозные):
- **Верх-право** (safe-area-aware, `padding: max(14px, env(safe-area-inset-top)) max(14px, env(safe-area-inset-right))`): ряд из двух круглых glass-кнопок 44×44 (крупнее инлайн-чрома 40×40 — единственные интерактивы кадра), зазор 10px: **«Сбросить вид»** (тот же `ResetIcon`) слева от **«×» выхода** (крестик, самый край — ожидаемое место закрытия).
- **Верх-лево**: приглушённая подпись — название модели, `Eyebrow`-трекинг, `--text-dim`, без фона (парит, не карточка) — «чтобы скриншот из фулскрина имел контекст» (v3).
- **Больше в кадре ничего нет** — ни вкладок, ни «Скачать», ни голоса (v3: «кадр = разглядываю, а не действую»).

### 2.3 Переход

- **Вход/выход** — cross-fade + едва заметный scale контейнера (`0.97→1` / обратно), `--dur-slow`/`--ease-out` (motion.md — тот же токен, что модалки/карусель, самый «весомый» переход шкалы).
- **Чром (×/Сбросить вид/подпись)** проявляется с задержкой ~40ms после старта контейнера (тот же приём, что пилюля-навигация ведёт контент, motion.md §2) — не должен «выскакивать» одновременно со сценой.
- `prefers-reduced-motion` → без scale/fade-задержки чрома, мгновенный кросс-фейд (motion.md — токены обнуляются глобально, отдельный `@media` не нужен).

### 2.4 Состояния

- **Ошибка сцены/потеря WebGL** — выходим из фулскрина, `overlay.toast({ severity: "critical", title: "Не удалось показать модель" })`, вьюер переходит в свой обычный `state === "error"` с «Повторить» (уже реализовано, `modelviewer.tsx:136-142`) — фулскрин не оставляет чёрный экран.
- **iOS Safari-фолбэк** (нет `requestFullscreen()` на `<div>`) — визуально **идентичен** реальному фулскрину (тот же CSS-оверлей на всём экране, тот же чром) — пользователь не должен видеть разницу.

## 3. Обсуждение модели (v3 §4)

Переиспользую паттерн карточки комментария из `feed.post.editor.md` §1.6 (уже специфицирован, тот же полиморфный `comments`) — **не рисую новый компонент**, адаптирую под три отличия v3: **один уровень** ответов (не дерево), **без голосов** на комментах, менюшка «⋯» вместо открытых кнопок голоса.

### 3.1 Композер + лента

- Заголовок `Eyebrow` «ОБСУЖДЕНИЕ (N)» — парит, как остальные заголовки блоков (уже так, `modelSocialTabs`).
- Композер сверху — `.marketTextarea` (существующее поле, v2 §4.1), плейсхолдер «Оставьте комментарий…», авто-рост, кнопка «Отправить» — **нейтральное стекло** (не зелёный primary страницы, тот же довод, что `feed.post.editor.md` §1.6 и v2 §4.1: primary уже занят «Скачать»), активна только при непустом тексте.
- Лента — новые сверху, ответы — сразу под своим корнем (без отступа-лестницы: **один уровень** значит ответ визуально не отступает на 24px, как в `feed.post.editor.md` §1.6, а просто идёт следующей строкой под корнем с меньшей тонкой направляющей слева ~12px, чтобы «принадлежность» ответа корню читалась, но не создавала иллюзию второго уровня вложенности).

### 3.2 Карточка комментария

Мини-аватар (32px, [avatar.md](avatar.md)) + `@username` (ссылка `/u/:username`) + относительная дата + **бейдж «автор»** (мелкая нейтральная пилюля рядом с `@username`, тот же формат, что `AgentBadge` — components.md, но текст «автор») у реплик владельца модели + тело (**plain text**, не markdown — отличие от `feed.post.editor.md`, там комменты поддерживают markdown; здесь v2 §4.1 база держит простой многострочный текст, дельта v3 это не пересматривает — не завышаю скоуп).

- **Своя реплика** — тонкая мятная обводка `data-mine` (тот же приём, что `.homeModelTile[data-mine]` у своей плитки каталога, `market.css:73`, и `feed.post.editor.md` §1.6).
- **Без голосовалки** на комментах (v3: «на кадре ровно один голосовой контрол — за модель»).
- **«Ответить»** — только у корневых комментариев (нет у ответов — держит один уровень буквально). Раскрывает тот же `.marketTextarea`-композер инлайн под корнем.
- **«⋯»** (`IconButton`, глиф — три точки) → компактное меню из двух пунктов: **«Удалить»** (свой коммент или владельцу модели любой под своей моделью, `confirm` → soft-delete) и **«Пожаловаться»** (та же дверь `ContextFeedbackDoor`, `ref: {type:'comment', id}` — см. GAP §6.3, форма пункта меню, не пилюля).

### 3.3 Плейсхолдер удалённого

Soft-delete с ответами → на месте корня плейсхолдер: приглушённая строка курсивом «Комментарий удалён» (обычное удаление автором) либо «Комментарий удалён владельцем проекта» (удаление владельцем чужого — v3 §4.4, честность вместо запрета). Ответы под плейсхолдером остаются видимы как обычно — плейсхолдер держит место в треде, не схлопывает его.

### 3.4 Состояния (переиспользую формулировки v2 §4.2 buquально, v3 не меняла тексты)

- **Пусто** — компактный `EmptyState` (не полноэкранный): «Пока никто не обсуждал», подпись «Спросите автора или расскажите, как печаталось» (v3 §4.5), без CTA (композер уже над лентой).
- **Загрузка** — скелетон 2–3 карточек коммента (shimmer, тот же паттерн, что скелетон каталога).
- **Ошибка** — «Не удалось загрузить обсуждение» + «Повторить».
- **Отправляю** — кнопка в состоянии ожидания, текст поля не теряется при ошибке (v3 §4.5).

## 4. Вкладка «Статистика» владельца (v3 §5)

5 плиток `StatTile` (**уже существует**, `ui.tsx:387`, `.uiStatTileGrid` — `repeat(auto-fit, minmax(160px,1fr))`, **готов к 5 без нового CSS**, ровно тот же примитив, что `MakeStatsPanel` уже использует для 3 плиток статистики Make) — приглушены по умолчанию (`tone="dim"`), «яркость=важность»:

| Плитка | `value` | `tone` | Тап |
|---|---|---|---|
| Просмотры | `views_count` | `dim`/`ok` (см. ниже) | — |
| Скачивания | `downloads_count` | `dim`/`ok` | — |
| Голоса | `votes_up − votes_down` (+мелкая разбивка ▲/▼ через `hint`) | `dim`/`ok` | — |
| Комментарии | `count(comments)` | `dim`/`ok` | → вкладка «Обсуждение» (`navigate(modelPath(id, "comments"))`) |
| Напечатали | `count(makes)` | `dim`/`ok` | → вкладка «Напечатали» |

- **Тон** — `tone="dim"` при 0 (свежая метрика, «ещё нет»), `tone="ok"` как только показатель > 0 (существующая семантика `data-tone="ok"` уже даёт лёгкое акцентное свечение обводки, `ui.css:542`) — деградация «яркость=важность» до абсолютной значимости, как и оговорила v3 §5.2 («без данных о последнем визите»). Новый режим не нужен — существующие тоны `StatTile` уже дают ровно требуемое поведение.
- **Кликабельные плитки** («Комментарии»/«Напечатали») — `StatTile` сегодня не принимает `onClick` (только статичный `div`) → **GAP-CSS** (§6.1): обернуть в `button`/добавить `onClick`-проп, не меняя визуал.
- **Состояние «всё по нулям»** — плитки видны тускло, под сеткой подпись `--text-dim`: «Статистика появится, когда проект начнут смотреть и скачивать» (v3 §5.3).
- **Загрузка** — скелетон 5 плиток (тот же shimmer-паттерн).
- Заголовок блока — `Eyebrow` «ВАША СТАТИСТИКА» (уже в v2 §7, не меняю).

## 5. Мета-файлы репо в блоке «Файлы проекта» (координация с Data, MF-826)

**Контекст.** `project.git.md` §10.2 уже резервирует папку `docs/` под «README-картинки + будущие произвольные doc-файлы проекта» — она архитектурно предусмотрена, просто ничего, кроме `description_image`, туда пока не пишет. Data (MF-826) ещё решает конвенцию роли/пути для LICENSE-подобных файлов — этот раздел фиксирует, как оно **выглядит**, вне зависимости от финального имени роли.

### 5.1 Рекомендация Design → Data: класть в `docs/`, не в корень

`RepoTree` (`projectfiles.tsx:206-231`) уже умеет рендерить произвольные файлы внутри craft-папок (глиф+имя+размер, кнопка «Скачать» — если роль резолвится). Если Data заведёт мета-файлы **внутри `docs/`** — визуал уже готов, **новой вёрстки не требуется**, только маппинг `role → "docs"` в `ROLE_TO_FOLDER` (Front). Если вместо этого файл ляжет в **корень репо** (`LICENSE.md` рядом с `README.md`) — `buildRepoTree` сегодня такие файлы **молча теряет** (`projectfiles.tsx:205-232` собирает `root.files`, но функция возвращает только `root.folders` — корневые файлы никуда не попадают, кроме уже отдельно обрабатываемого `README.md`). Чтобы не городить новый визуальный контейнер «файлы в корне» — **рекомендую Data путь внутри `docs/`**, а не в корне: ноль новой вёрстки, ноль нового бага.

### 5.2 Как выглядит строка мета-файла

Та же анатомия строки, что у любого файла роли (`.projectFileRow`: глиф + имя + размер + «Скачать») — **не изобретаю новую форму**. Имя строки — **оригинальное имя файла** (`LICENSE.md`, не метка роли — как и у прочих файлов внутри `RepoTree`, в отличие от роль-групп верхнего уровня, где имя = формат). Глиф — существующий `FileGlyph` (generic-документ), отдельного глифа под «лицензию» не завожу (единственная роль, велика вероятность 1-2 файлов на проект — не стоит нового SVG под редкий кейс, components.md «не заводить впрок»).

### 5.3 ⚠️ GAP: блок «Файлы проекта» может не появиться вовсе

`shouldShowProjectFiles()` (`projectfiles.tsx:60-62`) сегодня требует роль **вне печатной базы** (`source`/`canonical_3mf`), чтобы блок вообще отрисовался (§3.2 `projects.md` — «дремлет при одной роль-группе»). Чисто печатный проект (STL + 3MF) с одним `LICENSE.md` в `docs/` — сегодня этот инвариант **спрячет весь блок**, и добавленный файл не будет виден нигде. Мета-файл — не печатный артефакт, но он должен «будить» блок так же, как ЧПУ/код-роль. Флагирую Front (§6.2): `shouldShowProjectFiles`/эквивалент для git-дерева обязаны учитывать наличие файлов в `docs/`, не только craft-роли вне печатной базы.
