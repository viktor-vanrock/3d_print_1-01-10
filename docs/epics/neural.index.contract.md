Issue-указатель: **MF-525** (ресёрч, доска `tasks.3mf.tech`), родитель — эпик «Проект = git» [MF-514](project.git.md).
**Статус:** ресёрч-задел, не блокирует прототип MF-508. Не реализация — контракт для Data/Back, чтобы субстрат MF-514/MF-497 не пришлось переделывать, когда в v2 придёт [нейропоиск](neural.search.md) (MF-12).
Связанные доки: [project.git.md](project.git.md) (MF-514, git-субстрат), [projects.multiformat.md](projects.multiformat.md) (MF-497, markdown-описания Р3), [projects.page.md](projects.page.md) (MF-508 Р3, живой ILIKE-поиск со сменным бэкендом), [neural.search.md](neural.search.md) (MF-12, что и как эмбеддим).

## 0. Канонический документ проекта для эмбеддинга (MF-1016)

**Владелец контракта:** API/Data. Реализация находится в
`apps/api/src/models/indexText.ts`, тесты — в
`apps/api/src/models/indexText.test.ts`. Каноническая версия исходной реализации:
`0e26e7f114f6e5c67dc3c9de06a22862626c10b`, автор `Back <back@autofab.agent>`,
2026-07-11. Этот SHA фиксирует именно код сборки; последующие изменения обязаны
обновлять этот блок и тесты.

### Входные поля и порядок

Функция получает нормализуемую проекцию одной строки каталога:

| Секция документа | Источник | Правило |
| --- | --- | --- |
| `title` | `models.title` | `trim`, первая секция |
| `description` | `models.description` — кэш README | markdown очищается, пустое значение пропускается |
| `tags` | `model_tags → tags.name` | каждый тег `trim`, пустые пропускаются, порядок уже задан выборкой API |

В схеме `models` отдельной категории нет: категориальные признаки каталога
представлены тем же набором тегов и поэтому входят в секцию `tags`. Поля
`craft`, материал, совместимость с принтером и прочие факты остаются SQL-фильтрами
согласно `neural.search.md`, а не частью эмбеддинг-документа.

После нормализации непустые секции соединяются в порядке `title`, `description`,
`tags`: между секциями ровно две `\n`, внутри описания последовательности из трёх
и более переводов строк схлопываются до двух. Одинаковый набор входных значений
даёт одинаковую строку, что делает переиндексацию идемпотентной.

### Бюджет длины

Лимит задаётся параметром `maxTokens`; значение по умолчанию
`DEFAULT_MAX_INDEX_TOKENS = 3000`. У `apps/api` нет токенайзера провайдера, поэтому
перед `/embed` применяется консервативная оценка 2,5 символа на токен и усечение по
границе пробела. Точный лимит контекста MF-1015 не зафиксировал: его контракт
фиксирует модель `Embeddings`, размерность 1024 и L2-нормализацию, а не бюджет
токенов. При появлении подтверждённого ограничения меняется одна константа или
параметр вызова, а формат документа остаётся прежним.

## 1. Откуда индексатор берёт текст

**Источник истины — git, не БД.** С момента MF-514 `README.md` в bare-репо проекта — это описание (MF-497 Р3 обновлён project.git.md §4: «сырец в БД» → «сырец в README.md репо»). Индексатор v2 читает:

- `README.md` из корня репо проекта (`models.repo_path`), **единственный текстовый источник описания** — конвенция папок MF-517 не выносит описание никуда, кроме корня.
- Ветка/ref: конвенции нескольких веток юзеру не показываем (project.git.md §3.5) — индексатор читает **HEAD дефолтной ветки репо**, второй ref не нужен.
- `models.title` и теги — как и сегодня, из Postgres (это уже структурные поля, не файлы репо).
- Роли `model_files`, размеченные как текстовые/описательные (в реестре ролей MF-482 таких сегодня нет отдельно от README — маппинг роль↔путь фиксирует Data в MF-516/MF-517). Если в будущем появится доп. markdown-роль (например, `docs/` для развёрнутой документации проекта) — это отдельное решение Data, контракт индексатора не меняется: он просто получает больше путей от того же маппинга.

**Что попадает в индекс:** конкатенация `title + description(README, очищенный от markdown-разметки) + tags` — согласно neural.search.md («не заводить отдельные векторы на каждое поле, если нет доказанной необходимости»). Очистка синтаксиса уже прописана в projects.multiformat.md Р3: «AI-слой индексирует описание с очисткой от разметки (не эмбеддить синтаксис)».

**Что игнорируем:**
- Бинарные/производные роли `model_files` (`canonical_3mf`, `preview`, `thumbnail`, `description_image`, `source`, `aux`, `cnc_program`, `gerber`, `code_archive` и т.п.) — не текст, не эмбеддятся.
- Дерево файлов и имена файлов сами по себе — не эмбеддим путь как текст (это факт для фильтра/навигации, не для смыслового поиска).
- История коммитов (сообщения коммитов, дифы) — не продуктовый текст описания, не индексируем.
- Craft/материал/совместимость с принтером — по neural.search.md остаются обычными SQL-колонками-фильтрами, не текстом в эмбеддинге.

## 2. Перечисление и инкрементальное обновление

Единственный писатель в git — `apps/api` (project.git.md §3): каждое действие юзера, меняющее README (создание проекта, правка описания через редактор MF-497), уже проходит через git-модуль как коммит. Значит **API уже знает точный момент и точный проект, у которого изменилось описание** — отдельный сигнал «что-то в каталоге изменилось» индексатору городить не нужно, диффать все репо или коммит-лог не требуется.

Предлагаемая механика:

1. **Событие эмиттит апи-слой, не индексатор.** В точке, где `apps/api` коммитит README (upload/редактор MF-497, фаза 2 MF-519), он же обновляет `models.description`-кэш (уже решено в project.git.md §3.1 как «description-кэш для поиска») **и** ставит проект в очередь на переиндексацию — тем же паттерном, что и конвейер mesh (`models.status='pending'` → воркер разбирает), только для AI-очереди: например `models.index_status` (`pending`/`done`) с полем, которое дальше читает `apps/giga`-воркер. Точное имя колонки/таблицы очереди — решение **Data/Back**, не фиксирую здесь схему за них.
2. **Дебаунс, не эмбеддинг на каждый чих.** Правка описания — живой markdown-редактор, юзер может сохранять черновик много раз подряд; переиндексация не должна дёргать GigaChat Embeddings на каждое сохранение. Индексатор берёт задание не раньше, чем через окно дебаунса после последнего коммита в README конкретного репо (дефолт для обсуждения — секунды-десятки секунд, не привязываю точное число — тюнинг Back/AI на реализации).
3. **Кэш по хэшу контента, не по факту коммита.** Перед вызовом `/embed` индексатор сверяет хэш нормализованного текста (`title+description+tags` после очистки разметки) с последним проиндексированным хэшем (кэш-колонка, например `models.index_text_hash` — имя и владение снова Data). Коммит, не менявший видимый текст (правка форматирования, которая схлопывается очисткой разметки), не тратит вызов API — прямое следствие принципа «эмбеддинг считается один раз на контент, не на запрос».
4. **Каталог целиком не сканируем на устоявшемся потоке.** Обычный путь обновления — событийный (п.1), не периодический обход всех репо. Полный проход по каталогу — отдельная, разовая операция (аналог backfill-джобы project.git.md §3.7): нужна один раз при первом включении индексатора в v2 (проиндексировать существующие карточки) и, отдельно, при смене модели эмбеддингов (см. §3). Это explicit batch-job, не steady-state механизм.

## 3. Что субстрат уже даёт в v1, чтобы v2-индексатор встал без переделки схемы/репо

Уже решено и не требует ничего нового от этого документа:
- `models.repo_path` (MF-516) — индексатору не нужно ничего кроме этого, чтобы найти README проекта.
- Единственная ветка на репо, README всегда в корне (project.git.md §3.5, MF-517) — стабильный путь чтения, не нужен per-проектный конфиг «где искать текст».
- `models.description` как кэш-колонка, которую API поддерживает синхронной с README при каждом коммите (project.git.md §3.1) — v2-индексатору **не обязательно ходить в git на каждый запрос поиска**: он может подписываться на изменение той же кэш-колонки в Postgres (тот же триггер, что уже существует для каталога/поиска сегодня), а не заводить параллельный механизм чтения git.
- Маппинг `model_files.role` ↔ путь (MF-516/MF-517) — если в будущем текстовых ролей станет больше одной (README), индексатор просто читает из того же маппинга; менять контракт не придётся.

Что стоит **держать в уме** при миграциях Data/Back в v1, чтобы v2 не потребовал ре-миграции (задел, не задание — реализуют Data/Back по факту, когда возьмут в работу):
- Кэш-колонка описания (`models.description`) и её будущие соседи (`index_status`, `index_text_hash`, `pgvector`-колонка, версия модели эмбеддинга — например `index_model_version`, нужна, чтобы при смене модели/self-host из neural.search.md знать, какие карточки требуют переэмбеддинга) — это всё аддитивные `ALTER TABLE ADD COLUMN` на уже существующей `models`, без новой сущности и без переноса файлов. Явно фиксирую: `project_*`-таблиц по-прежнему не заводим (вердикт MF-9 не пересматривается этим документом).
- Очередь «репо изменился → переиндексировать» — если Back уже строит очередь/джоб-механизм для чего-то смежного (например, обновление derived-артефактов при коммите — MF-519/MF-520), переиспользовать тот же механизм для AI-очереди дешевле, чем городить второй. Решение о конкретном механизме — Back.

## 4. Стык с живым поиском v1 (ILIKE, MF-508 Р3)

MF-508 Р3 уже проектирует поиск со сменным бэкендом: один и тот же контракт `GET /models?q=...` (сегодня — ILIKE), фронт не меняется при замене бэкенда (marketplace.md §1.2, projects.page.md Р3). Точка, куда встаёт нейропоиск v2 — **этот же параметр `q`, тот же эндпоинт**: `apps/api` меняет внутреннюю реализацию обработчика (ILIKE → гибрид full-text + вектор через `apps/giga /embed`), контракт запроса/ответа для Front не трогается.

Фильтры (craft, материал, совместимость с принтером) — обычные SQL-колонки уже сегодня; единый управляемый store фильтров+запроса на Front (уже заложен MF-508 Р3 «состояние фильтров — единый store, к которому потом получит доступ AI-агент поиска») — та же точка, где в будущем (после этого MVP, отдельное решение) сможет подключиться интент-разбор запроса в фильтры. Этот документ не проектирует интент-разбор — он вне периметра v1/v2-индексации и явно вне границ MF-525.

## 5. Границы (не решаю за смежные зоны)

- Векторную БД/эмбеддинги/pgvector-схему в v1 не строю — только контракт, откуда/когда брать текст. Финальные имена колонок, конкретный механизм очереди, окно дебаунса — решение **Data**/**Back** в фазе реализации (MF-12), не фиксирую их здесь как готовое ТЗ.
- Хостинг эмбеддинг-модели (API GigaChat vs self-host) и бюджет вызовов — решение CTO/Data по факту роста, покрыто в neural.search.md, не пересматриваю.
- Если появится LLM-разбор запроса в фильтры (интент-парсинг, projects.page.md §7.1) — это отдельный контракт с отдельным вниманием к недоверенному входу (пользовательский поисковый запрос идёт в промпт); вне периметра этого документа, фиксирую как будущий триггер, не решаю сейчас.
