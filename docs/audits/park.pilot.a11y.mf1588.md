# Accessibility-аудит «Мой парк» и виджета пилота прошивки (MF-1588)

Контур: MF-1075 → MF-1077 → MF-1588. Основания: [docs/design/park.md](../design/park.md)
§2–3, [docs/design/printer.face.md](../design/printer.face.md) §1, контракт
`firmware-pilot.v1` (MF-1584), приёмочный канон
[docs/design/printer.surface-a11y.md](../design/printer.surface-a11y.md).

Маршруты: `/park` (dev-аккаунт `autofab-agent`, 14 сидированных принтеров — состояния
`no_data` и `stale` наблюдались вживую; `building`/`burn_in`/`ready`/`stopped` проверены
через `apps/web/src/park/parkscreen.test.tsx` fixtures, т.к. dev-данные их не покрывают) и
`/printers/creality.ender-3-v3-ke` (каталог, `CatalogPilotRow`).

**Примечание по времени:** во время аудита на `origin/dev` приземлился и выкатился на
dev.3mf.tech `fix(park): скрыть виджет пилота прошивки на непилотных карточках (MF-1867)`
— до него `PilotRow` игнорировал `PilotInfo.visible` и рисовал «Пилот прошивки: нет данных
о пилоте» на всех 14 карточках, а не только на KE/V400. Этот отчёт описывает состояние
**после** MF-1867 (перепроверено живьём); фикс не отменяет находки ниже — местами делает
находку 2 более заметной (см. её текст).

## Метод

- Живой authenticated-аудит: `@axe-core/playwright` (wcag2a/aa, wcag21a/aa) с корректной
  dev-сессией (`~/.autofab-session-dev`, домен `.dev.3mf.tech`).
- Клавиатурная навигация и фокус: Playwright `Tab`/`Enter` walk + чтение
  `document.activeElement`.
- Доступное имя: `page.locator(...).ariaSnapshot()` (реальное вычисление браузером), не
  `textContent` (тот не отражает то, что слышит скринридер).
- Контраст: пиксельная выборка реального рендера (`pngjs`, кластеризация цветов
  фон/текст → WCAG relative luminance) — понадобилась, т.к. `axe` пометил эти узлы
  `incomplete` (не `pass`/`violation`) из-за `backdrop-filter: blur` и полупрозрачного фона,
  которые автоматика не может честно посчитать.
- Reduced motion: `page.emulateMedia({ reducedMotion: "reduce" })` + чтение вычисленных
  `--dur-*`/`animationName`.
- Код: построчное чтение `apps/web/src/park/{parkscreen,firmwarepilot}.tsx`,
  `apps/web/src/printers/printerdetailscreen.tsx`, `apps/web/src/ui/ui.{tsx,css}`,
  `apps/web/src/park/park.css`, `apps/web/src/printers/printers.css`,
  `apps/web/scripts/a11ycheck.mjs`.

### Известное ограничение инструментария (для будущих прогонов)

Общий CLI `a11y <url>` подписывает запрос к `dev.3mf.tech` **прод**-сессией
(`~/.autofab-session`, `domain: .3mf.tech`), а `dev.3mf.tech` проверяет JWT другим
секретом (см. `webcheck`), поэтому `a11y https://dev.3mf.tech/...` тихо аудирует
разлогиненный рендер — 0 нарушений / ~23 passes независимо от реального контента. Для этого
аудита использовался тот же приём, что `webcheck`: `~/.autofab-session-dev` +
`domain: .dev.3mf.tech`. Рекомендация: поправить `$HOME/autofab-tools/a11y.js`, чтобы он
выбирал cookie/domain по хосту цели так же, как `webcheck`.

## Находки

### 1. [Serious] Контраст «dim»-тона `StatusPill` ниже WCAG 1.4.3 AA в обеих темах

**Маршрут:** `/park` (бейдж уровня «Поддержка уточняется»/«В каталоге» и строка пилота
«Пилот прошивки: …») и `/printers/<slug>` (тот же компонент).
**Селектор:** `.uiStatusPill[data-tone="dim"]` (`apps/web/src/ui/ui.css:487`).

Измерено на реально отрендеренной `/park` (13px, не bold — применяется порог 4.5:1, не
3:1 крупного текста):

| Тема | Пример узла | Итоговый контраст |
|---|---|---|
| dark | пилот-строка «нет данных о пилоте» | **≈3.91:1** |
| dark | пилот-строка «данные устарели» | ≈3.89:1 |
| dark | бейдж «Поддержка уточняется» | ≈3.89:1 |
| light | пилот-строка «нет данных о пилоте» | **≈2.69:1** |
| light | пилот-строка «данные устарели» | ≈2.59:1 |
| light | бейдж «В каталоге» | ≈2.59:1 |

Причина: `ui.css:487` вешает `opacity: 0.66` на **весь** элемент (фон + рамка + точка +
текст), а не только высветляет цвет текста — поверх и без того полупрозрачного фона
(`background: color-mix(in srgb, var(--surface) 60%, transparent)` +
`backdrop-filter: blur(16px)`). Два слоя прозрачности складываются.

Существующий локальный гейт `apps/web/scripts/a11ycheck.mjs` (`CONTRAST_PAIRS`) не ловит
это: он проверяет только сырую пару `--text-dim` на `--bg` (7.12:1 dark / 5.39:1 light —
оба честно проходят 4.5:1) и не моделирует множитель `opacity: 0.66` пилюли. `axe-core`
тоже не ловит — из-за blur/полупрозрачности он помечает эти узлы `incomplete`, не
`violation` (см. § «Метод»). Разница между «токен на бумаге» и «то, что реально
на экране» — вот что не поймано ни одним из двух существующих гейтов.

**Acceptance:** `tone="dim"` не обесцвечивает флэт-opacity весь блок; либо берётся более
тёмный/светлый (для light) сплошной цвет текста, либо opacity применяется только к
декоративным частям (рамка/фон), а текст остаётся на отдельном сплошном канале, дающем
≥4.5:1 к реально составному фону в обеих темах. Плюс: добавить в
`CONTRAST_PAIRS` (`a11ycheck.mjs`) пару, учитывающую фактическую компоновку `dim`-пилюли
(составной фон × opacity), чтобы регресс такого рода ловился автоматически, а не только
ручной пиксельной проверкой.

### 2. [Serious] Живой статус подключения (§2.2 `LiveState.phase`) не рендерится на `/park` — `ConnectionRow` мертвый код

**Селектор:** `apps/web/src/park/parkscreen.tsx:67-86` (`ConnectionRow`) —
ноль точек вызова; `PrinterRow.sub` (строки 130-145) собирает бейдж + область +
`PilotRow`, но никогда не вызывает `ConnectionRow`.

Эффект: ни для одного принтера (кроме двух пилотных моделей, у которых строку замещает
виджет пилота) `/park` не показывает «Печатает»/«На связи»/«На паузе»/«Ошибка»/«Не в
сети» — ни зрячему, ни пользователю ассистивных технологий. Это не баг озвучивания —
самого факта в DOM нет, поэтому недоступно ничего: ни цвет, ни текст, ни доступное имя.
После MF-1867 (см. примечание выше) это особенно заметно: у 12 из 14 сидированных
принтеров `sub` карточки — это ТОЛЬКО бейдж уровня («Поддержка уточняется»), без единой
строки о состоянии подключения; раньше эту пустоту непреднамеренно маскировала утёкшая
пилюля «Пилот прошивки: нет данных о пилоте».

WCAG 4.1.3 Status Messages / 1.3.1 Info and Relationships — заявленная спекой
(park.md §2.2, чеклист §4 «Строка соединения читает `LiveState.phase`…») информация
отсутствует, а не искажена.

**Acceptance:** `PrinterRow.sub` рендерит `<ConnectionRow live={live} />` (или
эквивалент) для принтеров, где виджет пилота не замещает строку — видно на fixtures
`printing`/`ready`/`paused`/`error`/`offline`.

### 3. [Serious] Точечные изменения статуса не объявляются ассистивным технологиям

Единственный `aria-live` на странице — агрегированная сводка `.parkLiveSummary`
(`role`/`aria-live="polite"`, подтверждено тестом). У строки конкретного принтера (после
починки п.2) и у `PilotRow` своего live-region нет: смена состояния одного устройства
(например, «На связи» → «Ошибка») долетает до пользователя скринридера, только если
фокус в этот момент стоит именно на этой строке. Тот же принцип уже
задокументирован для другой поверхности того же эпика —
`docs/design/printer.surface-a11y.md` §1/§3: «тихое изменение факта — один
`role="status"` (`aria-live="polite"`)».

WCAG 4.1.3 Status Messages (AA).

**Acceptance:** обернуть контейнер пилюли статуса каждой строки в `role="status"`
(polite, без второго `alert`) — по образцу требования, уже принятого для
`/printer/:id`.

### 4. [Moderate] Копирайт виджета пилота не реализует §3.2–3.3 park.md — не модельный, не переведённый, не датированный, без честного гейта на `confidence`

**Код:** `apps/web/src/park/firmwarepilot.ts:23-32` (`pilotInfoFor`).
**Тест, фиксирующий именно этот (небазовый) результат как ожидаемый:**
`apps/web/src/park/parkscreen.test.tsx:287-319` — `expect(await screen.findByText(\`Пилот
прошивки: ${stage}\`))` буквально ожидает необработанные ключи контракта (`building`,
`burn_in`, `not_started`, `ready`) вместо русских формулировок таблицы §3.2. Это не
случайный пропуск — поведение протестировано таким, какое есть.

Расхождения со спекой:
- нет названия модели в тексте (спека: «Пилот прошивки Ender-3 V3 KE: …»);
- нет «данные обновлены {дата}» / для `stale` нет обязательной второй строки
  «Последний факт: {стадия}, обновлено {дата}» — сейчас только «Пилот прошивки: данные
  устарели» без второй строки;
- сырой `stage` контракта выводится как есть, а не переводится
  («building» вместо «сборка», «burn_in» вместо «обкатка», «not_started» вместо «не
  начат», «ready» вместо «готово»);
- нет отдельной ветки для `stage="stopped"` (спека требует `tone="warn"`, без pulse,
  текст «остановлено») — сейчас это обычный `tone="dim"` + непереведённое слово;
- `ready` не проверяется на `confidence==="verified"` — по спеке `ready` с другим
  `confidence` обязан показываться как «нет данных о пилоте», сейчас показывается как
  подтверждённый факт независимо от `confidence`.

На `/park` это смягчается тем, что доступное имя всей карточки-кнопки уже включает
название принтера (подтверждено вычисленным `ariaSnapshot`, не только `textContent`) —
т.е. это не «имя отсутствует», а «контент неполный/не по спеке», причём одинаково и для
зрячих, и для скринридера.

На `/printers/<slug>` — иначе: `CatalogPilotRow`
(`apps/web/src/printers/printerdetailscreen.tsx:420-443`) рендерит `info.label` как
собственное доступное имя **отдельной** фокусируемой кнопки-дисклоужера
(`aria-expanded`/`aria-controls`), не встроенной в более крупный именованный контрол.
Здесь это уже настоящая неоднозначность 4.1.2 Name, Role, Value: пользователь
скринридера, переходящий по списку кнопок/ротору, услышит «Пилот прошивки: данные
устарели» без указания модели.

**Acceptance:** `pilotInfoFor()` возвращает модельно-квалифицированный, переведённый,
датированный текст строго по таблицам §3.2/§3.3 (включая `stopped` отдельной веткой и
гейт `confidence` для `ready`); `CatalogPilotRow` включает название модели в доступное имя
кнопки (например, через `aria-label`, композирующий бренд+модель+`info.label`), даже если
рядом визуально есть заголовок модели.

### 5. [Minor] Хит-зона диклоужера пилота в каталоге — 32px, ниже проектного минимума 48px

**Селектор:** `.prnPilotRow` (`apps/web/src/printers/printers.css:1115-1125`,
`min-height: 32px; padding: 0`).

Формально проходит WCAG 2.2 SC 2.5.8 (24px минимум), поэтому не блокирую, но ниже
собственного инварианта продукта — `--touch-target-min: 48px`
(`docs/design/layout.md` § «Тач/киоск-специфика», повторено в `printer.face.md §2.2`), и
`docs/design/printer.surface-a11y.md` §1 прямо называет 48px «проектным минимумом» и явно
отказывается от исключения WCAG 2.5.8 «для киоска и реального touch». Контрол стоит
рядом с другими маленькими интерактивными элементами карточки (compare-toggle) —
риск промаха на touch/kiosk выше среднего.

**Acceptance:** `.prnPilotRow` получает `min-height: var(--touch-target-min)` (или
эквивалентное увеличение хит-зоны паддингом) — как остальные интерактивные примитивы
дизайн-системы.

## Что уже работает (подтверждено, не барьер)

- `ActionCard` — нативный `<button>`; `Tab` проходит все строки `/park` в осмысленном
  порядке (шапка → тема → звук → уведомления → аватар → «Добавить принтер» → каждая
  карточка), у каждой видимый `:focus-visible` (`outline-style: solid`, подтверждено
  живьём).
- `Enter` на карточке без capability открывает `role="dialog" aria-modal="true"`, фокус
  корректно уходит на первое поле формы (подтверждено живьём).
- Тач-таргеты строк `/park` — фактически 620×169px (десктоп), CSS
  `min-height: clamp(88px,16vw,140px)` — с большим запасом выше 48px.
- `prefers-reduced-motion: reduce` глобально обнуляет `--dur-*` и отключает pulse
  `StatusDot` (подтверждено живьём: `animationName` пуст) — барьеров motion не найдено.
- Ни одно состояние (уровень/пилот/соединение) не передаётся только цветом — тон везде
  сопровождается текстом.
- Пустой парк (код-ревью; на dev-аккаунте не воспроизведён — 14 сидированных принтеров)
  — `EmptyState` с иконкой, заголовком, одним предложением и единственным CTA, без
  тупика.

## Итог

3 Serious + 1 Moderate + 1 Minor. Ни один не «критический» в смысле полной
недоступности управления клавиатурой/скринридером — блокировать visual gate не стал.
Заведена назначенная карточка исправления для Front (см. комментарий MF-1588).
