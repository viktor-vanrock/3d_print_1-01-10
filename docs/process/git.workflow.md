# Git-воркфлоу Autofab — ДВЕ ветки (main+dev)

## Приоритетный режим VDS: только `main` и `dev`

На VDS оставлены только две локальные ветки: `main` и `dev`. Рабочие
task-worktree Multica запускаются в **detached HEAD от `origin/dev`**. Это
обязательное исключение из старых формулировок ниже про локальную
`agent/<роль>/<hash>`-ветку: они устарели и больше не применяются.

Почему detached: Git не позволяет безопасно одновременно checkout-ить одну
локальную ветку `dev` в десятках worktree. Detached HEAD даёт каждому агенту
свой индекс и рабочие файлы, но все публикуют результат в один общий ствол.

Перед работой агент синхронизирует основу:

```bash
git fetch origin dev
git rebase origin/dev
```

Публикация — только `git push origin HEAD:refs/heads/dev`. Запрещены обычный

> Вынесено из сквад-промпта (справочник, тащи по нужде). Правило-суть — в промпте.

## Git — ДВЕ ВЕТКИ, И ВСЁ (main + dev)

В репо для агентов существуют РОВНО две ветки. Больше НЕ создаём — ни
feature/, ни fix/, ни docs/, ни agent/*, ни «ветку под обнову». Это
ПЕРЕОПРЕДЕЛЯЕТ любые старые заметки про «ветку feature/… от origin/main»
и «squash-merge».
- **dev** — общий рабочий ствол. Сюда коммитят ВСЕ. Деплоится на
  dev.3mf.tech (таймер тянет origin/dev раз в минуту) — тут тестируем живьём.
- **main** — прод, только проверенное. Тянется на 3mf.tech автодеплоем
  (~2 мин). В main попадает ТОЛЬКО промоушеном dev→main (ниже); напрямую
  в main никто не коммитит и не пушит.

Цикл работы (всегда так):
1. Личность (демон ставит всем общий «lead» — не видно, кто shipped):
   `git config user.name "<Роль>" && git config user.email "<роль>@autofab.agent"`.
2. Стартуй в detached HEAD task-worktree на `origin/dev`, который подготовил демон.
   Не создавай и не checkout-ь локальную `agent/*` или `dev`: один bare-репо
   расшарен на десятки worktree. Синхронизация основы: `git fetch origin dev &&
   git rebase origin/dev`. Публикация результата — только `git push origin
   HEAD:refs/heads/dev`.
3. Работай, коммить мелко и часто. Conventional Commits: тип(область),
   области web/api/mesh/giga/repo.
4. Публикуй в общий dev ТОЛЬКО так: `git fetch origin dev && git rebase origin/dev && git push origin HEAD:dev`.
   🔴 КРИТИЧНО — как пушить: ВСЕГДА `git push origin HEAD:dev` (твой HEAD едет В dev). НИКОГДА не делай
   голый `git push`, ни `git push origin HEAD`, ни `git push -u origin ...`, ни `git push origin <своя-ветка>` —
   это запушит твою рабочую `agent/<роль>/<hash>` воркдир-ветку на origin как ОТДЕЛЬНУЮ ветку и нарушит
   «ровно 2 ветки» (ловили вживую: Front так создал `agent/front/13890317`). На origin существуют РОВНО
   dev и main — больше никаких. Проверь себя перед пушем: `git push origin HEAD:dev` — двоеточие+dev обязательны.
   Увидел свою `agent/*` (или любую свою) ветку на origin (`git ls-remote --heads origin`) — ты ошибся
   командой: перепушь работу в dev (`git push origin HEAD:dev`) и удали лишнюю (`git push origin --delete <имя>`).
   Конфликт при ребейзе — разрули СЕЙЧАС на своей воркдир-ветке.
5. dev.3mf.tech обновится за ≤1 мин → проверь фичу: `webcheck
   https://dev.3mf.tech/<путь>` (залогинен служебной сессией), консоль/сеть
   чистые, скрин в карточку.
6. **dev всегда зелёный.** Уронил dev.3mf.tech своим пушем — чини forward
   НЕМЕДЛЕННО (фикс или revert своего коммита). Красный dev блокирует
   выкатку ВСЕЙ команды — залёт.

Промоушен dev → main (выкатка на прод) — ТОЛЬКО через агента Release:
- **В main пушит ТОЛЬКО Release.** Директора/Lead/разрабы напрямую в main НЕ
  пушат (это ПЕРЕОПРЕДЕЛЯЕТ старое «право у директоров»). main — отдельная
  прод-машина, туда код едет через один проверенный гейт.
- Готово = фича живёт на dev.3mf.tech (это конец твоей зоны). Выкатка в прод — ОТДЕЛЬНОЕ событие по запросу оператора (не рутинный шаг). Если оператор попросил релиз и ты УВЕРЕН: прошла QA, проверена ЖИВОЙ
  на dev.3mf.tech (доказательство лабораторией — vmatrix/lhaudit/a11y/webcheck-
  скрин или цифры), dev.3mf.tech зелёный, **CI/CD зелёный** (тест-гейт Test) →
  **assign карточку на Release** (это его будит) с комментом-передачей:
  «эта версия протестирована, прошла CI/CD, можно в релиз» + чем именно проверял.
  Release — агент ИЗ ДРУГОГО ОТДЕЛА, живёт на main-машине; это ЕДИНСТВЕННЫЙ путь
  кода в прод. Он делает финальный гейт и промоутит dev→main. Красный CI/билд →
  Release вернёт карточку тебе с точной ошибкой; чинишь на dev и снова ему.
- Release промоутит на прод ТОЛЬКО по запросу оператора и ТОЛЬКО проверенные версии (CI зелёный, QA/Reviewer-баги закрыты); сырое/непроверенное НЕ катит. Механику
  ff-пуша, `git push origin dev:main`, non-ff-мерж, version.json и коммит версии
  `[skip ci]` держит Release — сам в main не лезь.
- Пуш в main = юзеры на 3mf.tech через ~2 мин (отдельная прод-машина, автодеплой).

dev-only ≠ ветка, а ENV. Всё, что должно жить только на dev (открытый вход
без авторизации, сиды, тестовые данные), — в env-файле на VDS
(portal.api-dev.env), НЕ в коде ветки dev. Потому что dev→main неизбежен:
любой dev-only КОД рано или поздно уедет в прод. Нужен dev-тумблер — заявка
Ops на env-флаг, не divergent-код. Версии не трогай, релизы режет оператор.

## Совместная работа (масштаб, внешние агенты)
К проекту подключаются внешние разработчики со своими агентами — доска и
git-конвейер общие, правила одни для всех. Поэтому:
- Коммить в общий `dev` мелко и часто; перед пушем `git rebase origin/dev`.
Конфликт с dev — ребейзишься ты, сразу (отдельной ветки, куда спрятаться, нет).
- Не блокируй чужое: вето/ревью/вердикт — за один свой запуск.
- Всё через карточки и валидные теги: устных договорённостей в мире
  десятков параллельных пушей не существует.
