**Это спека, не реализация.** Она фиксирует исполнимую (проверяемую по чек-листу) модель
безопасности для будущего git-import модуля; конкретный TS/Python-код — отдельная карточка
Back поверх этого документа и контракта MF-1964.

## 0. Скоуп

**Делаем:** одноразовый snapshot-импорт внешнего git-репозитория (URL с GitVerse) в изолированный
quarantine-каталог на диске VDS, валидация содержимого без исполнения кода репозитория, при
успехе — контролируемая promotion отфильтрованного снимка в наш внутренний bare-репо проекта
(`docs/infra/git.repos.md`).

**НЕ делаем (совпадает с постановкой карточки, не пересматривается этим доком):** зеркалирование/
двусторонний sync с GitVerse; OAuth/подключение аккаунта GitVerse; произвольный host вне allowlist
§1; исполнение build scripts или `portal.project.yaml`-экшенов импортированного репозитория
(манифест — декларативная модель, канон MF-1963); автоматическая прошивка устройства как следствие
импорта.

**Модель угрозы:** URL репозитория и всё его содержимое (включая `portal.project.yaml`) —
недоверенный вход. Прямой `git fetch` по юзер-URL без обвязки открывает SSRF (fetch внутренних
адресов VDS/облака от лица нашего сервера), path traversal (символьные ссылки, `.git`-в-пути,
абсолютные пути), исполнение кода (hooks, submodule/LFS smudge-команды), archive/decompression
bomb и исчерпание диска/inode — ни один из этих контуров не покрыт существующим git-модулем,
который сегодня доверяет только собственным commit'ам `apps/api` (`docs/architecture/git.module.md`),
не внешнему fetch.

## 1. Allowlist хоста и транспорта (v1)

- **Единственный разрешённый хост v1 — `gitverse.ru`** (точное совпадение, без wildcard
  поддоменов, без второго хоста «на всякий случай»). Любой другой host →
  `IMPORT_HOST_NOT_ALLOWED`. Расширение allowlist — отдельное решение CTO с явной причиной, не
  тихая правка константы.
- **Единственная схема — `https://`.** `http://`, `git://`, `ssh://`, `file://`, а также git
  remote-helper префиксы (`ext::`, `fd::`, `foo::`) отклоняются на этапе разбора URL до любого
  обращения к сети. Дополнительный defense-in-depth на уровне самого git-вызова:
  `-c protocol.ext.allow=never -c protocol.file.allow=never` (§2) — не полагаемся только на
  собственный парсинг URL.
- **Без credentials в URL** (`https://user:pass@host/...`) — отклонить (`IMPORT_URL_HAS_CREDENTIALS`);
  доступ к GitVerse только как к публичному репозиторию, свои креды в URL не пробрасываем.
- **Host — только доменное имя, не IP-литерал.** `https://1.2.3.4/...` отклоняется до resolve
  (`IMPORT_HOST_IS_IP_LITERAL`).
- **DNS-resolve check против приватных/зарезервированных диапазонов** до соединения: `10/8`,
  `172.16/12`, `192.168/16` (RFC1918), `127/8`, `::1` (loopback), `169.254/16`, `fe80::/10`
  (link-local), `fc00::/7` (ULA), `100.64/10` (CGNAT/Tailscale-диапазон нашей же инфры —
  `docs/infra/domain.map.md`), `0.0.0.0/8`, multicast — резолвленный IP в любом из них →
  `IMPORT_HOST_RESOLVES_PRIVATE`. Это защита от DNS rebinding (публичный домен, отвечающий
  приватным IP), не просто проверка литерала в URL.
- **Редиректы v1 — запрещены полностью**, не «один хоп с повторной проверкой»: `-c
  http.followRedirects=false`. Проще и без TOCTOU-окна между проверкой редирект-цели и
  реальным соединением; GitVerse для клонирования по канонiческому URL репозитория редиректов не
  требует. Получен редирект от сервера → фейл `IMPORT_REDIRECT_REJECTED`, не follow.
- `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS=/bin/false`, `-c credential.helper=` (пустое значение —
  отключает любой credential helper) — импорт никогда не должен виснуть на интерактивном
  запросе пароля и никогда не должен подхватить чужие сохранённые креды.

## 2. Обвязка вызова git CLI

Одна команда клонирования на job, без промежуточных интерактивных шагов:

```
GIT_TERMINAL_PROMPT=0 GIT_ASKPASS=/bin/false \
HOME=<job_quarantine_dir>/home XDG_CONFIG_HOME=<job_quarantine_dir>/home \
GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null \
timeout --signal=KILL 120 \
git -c protocol.ext.allow=never -c protocol.file.allow=never \
    -c http.followRedirects=false -c credential.helper= \
    -c core.hooksPath=/srv/git/quarantine/_noop-hooks \
    -c transfer.fsckObjects=true -c fetch.fsckObjects=true \
    clone --bare --no-local --single-branch --branch <ref> \
    --depth 1 --no-tags --filter=blob:none \
    <https-url> <job_quarantine_dir>/repo
```

- `HOME`/`XDG_CONFIG_HOME`/`GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM` изолированы на job — ни один
  чужой `~/.gitconfig`, `includeIf`, глобальный `core.hooksPath` не может просочиться в вызов.
- `core.hooksPath` указывает на **пустой read-only каталог, владелец root, недоступный на запись
  UID'у quarantine-воркера** (§3) — даже если во входном репозитории лежат `.git/hooks/*`
  скрипты, они физически не исполняются (hooksPath их полностью замещает). Дополнительный
  барьер — сам quarantine-mount `noexec` (§3): даже ошибка в hooksPath-логике не даст исполнить
  файл.
- `--depth 1 --no-tags --single-branch --filter=blob:none` — минимизирует объём фетчащегося
  графа и даёт возможность prospective size-check (§5) до скачивания байт блобов.
- `transfer.fsckObjects=true`/`fetch.fsckObjects=true` — git проверяет структурную валидность
  объектов на лету, отклоняет заведомо повреждённые/вредоносные pack'и раньше наших проверок.
- **Submodules:** `git submodule update`/`init` никогда не вызывается — v1 не разворачивает
  `.gitmodules`. Наличие блоба `.gitmodules` ИЛИ любой tree-записи с mode `160000` (gitlink,
  commit-запись — это и есть submodule-ссылка) в полученном дереве → весь импорт отклоняется,
  `IMPORT_SUBMODULE_REJECTED`, promotion не запускается.
- **LFS:** `git-lfs` не установлен в `PATH` quarantine-процесса (изолированный `PATH` без
  lfs-бинаря — smudge-фильтр физически не может быть вызван). Дополнительно: любой блоб,
  начинающийся с LFS pointer-сигнатуры (`version https://git-lfs.github.com/spec/v1`), или
  `.gitattributes` с `filter=lfs` → `IMPORT_LFS_REJECTED` (pointer-файл без реального содержимого
  бесполезен и вводит в заблуждение, если бы прошёл как обычный файл).
- **Symlinks:** любая tree-запись с mode `120000` → `IMPORT_SYMLINK_REJECTED`, весь импорт
  отклоняется целиком (не «пропустить эту запись») — символьная ссылка, тихо пропущенная на
  этапе записи, но резолвящаяся при последующем чтении, — путь наружу из quarantine/target repo
  даже без explicit path traversal в самом имени.

## 3. Quarantine — окружение исполнения (зона Ops)

- **Путь:** `/srv/git/quarantine/<job_id>/` (`job_id` — uuid), **рядом** с `/srv/git/repos/`
  (`docs/infra/git.repos.md`), не внутри него — promotion (§9) это явный контролируемый шаг
  копирования/коммита, никогда не «тот же каталог».
- **UID:** отдельный низкопривилегированный сервисный аккаунт `portal-gitimport`, НЕ `plag`
  (которым сегодня владеет `/srv/git/repos`, БД-креды и запущен `portal.api.service`). Принцип:
  если парсинг git-объектов/zlib/YAML содержит RCE, поражённый UID не имеет доступа к
  `/srv/git/repos`, Postgres, S3-кредам, `~/portal.api.env` — блочит privilege escalation по
  факту компрометации воркера импорта, не полагается только на софт-проверки §1–§2. Воркер
  импорта — отдельный systemd-юнит (`portal.gitimport.service`, `User=portal-gitimport`),
  запрос на импорт от `apps/api` (`plag`) уходит в него через локальную очередь/сокет, не через
  `sudo`/`setuid` из процесса `plag`.
- **Mount:** `/srv/git/quarantine` — отдельный bind-mount/tmpfs с флагами `noexec,nosuid,nodev`.
  Даже если проверки §2/§4 где-то пропустят исполняемый файл или symlink — запуск физически
  заблокирован на уровне монтирования, а не только на уровне приложения.
- **Диск-квота:** общий бюджет каталога `/srv/git/quarantine` — 5 ГБ (покрывает несколько
  параллельных job), per-job soft cap 2 ГБ (`2× MAX_REPO_BYTES` — запас на объекты до
  прореживания/паковки, окончательный лимит — 1 ГБ репозитория, §5). **Inode-квота:** 200 000
  inode на job — защищает от бомбы «много мелких файлов», которая не выбьет байтовый лимит.
  Реализация — XFS project quota (или loop-mounted sparse-файл нужного размера, если раздел не
  XFS) поверх выделенного mount; в любом случае поверх ОС-квоты остаётся приложенческий
  size/object-count чек §5–§6 (пояс и подтяжки, ОС-квота — последний рубеж на случай, если
  приложенческий чек где-то содержит баг).
- **Timeout:** весь `clone` — wall-clock `SIGKILL` на 120с (см. `timeout --signal=KILL 120` в
  §2). Каждый последующий git plumbing-вызов при валидации (`ls-tree`, `cat-file --batch`, …) —
  отдельный лимит 60с на вызов, ни один git-процесс не работает без верхней границы по времени
  (закрывает тот же класс пробела, что MF-1965 фиксирует для `runGit` в проде — переиспользуем
  паттерн, не изобретаем второй).
- **Output cap:** stdout/stderr любого git-вызова в контуре импорта капается на 1 МБ — превышение
  убивает процесс (тот же фикс, что MF-1965 просит для `runGit`, применённый и здесь: `runGit` в
  `apps/api/src/git/gitcli.ts` сегодня не имеет ни timeout, ни output cap — это относится к
  обоим потребителям одинаково).
- **Cleanup:** `<job_quarantine_dir>` удаляется безусловно в `finally` — и при успешной promotion
  (после того как байты уже скопированы в target repo, §9), и при любом отказе/timeout/крэше.
  Дополнительно — sweep при старте `portal.gitimport.service`: любой `/srv/git/quarantine/*`
  старше 1 часа удаляется как orphan от упавшего воркера (тот же класс пробела, что MF-1965
  фиксирует для repo-lock без TTL/PID — здесь применяем ту же профилактику).
- **Бэкап:** `/srv/git/quarantine` **явно исключён** из контура `portal.backup.sh`
  (`docs/infra/git.repos.md` архивирует только `/srv/git/repos/`) — quarantine содержимое
  недоверенное и одноразовое, бэкапить его не только бесполезно, но и означало бы хранить
  потенциально вредоносные байты дольше, чем нужно.

## 4. Канонические правила пути (проверяются на каждой tree-записи до promotion)

Для каждой записи `git ls-tree -r --full-tree -l <sha>`:

- **Только `blob` (mode `100644`/`100755`).** `tree` (обходится рекурсией), `commit`/gitlink
  (`160000`, §2), symlink (`120000`, §2) — уже отклонены выше на уровне всего импорта.
  Исполняемый бит (`100755`) допускается существовать во входных данных, но при promotion (§9)
  всегда снимается — файл в целевом репо всегда неисполняемый; это defense-in-depth поверх
  `noexec`-mount (§3), не первичный контроль.
- **Байты пути:** отклонить путь, содержащий control-символы (`0x00`–`0x1F`, `0x7F`), сегмент
  `..`, ведущий `/` (абсолютный путь), любой сегмент, регистронезависимо равный `.git`,
  `.gitmodules`, `.gitattributes`, `.gitignore` — на ЛЮБОЙ глубине пути (`foo/.git/config`, не
  только в корне) — блокирует попытку протащить вложенный `.git`-каталог как обычный файл.
- **NFC-нормализация:** каждый путь нормализуется в Unicode NFC перед сравнением; если два
  разных tree-пути после нормализации совпадают → весь импорт отклоняется,
  `IMPORT_PATH_COLLISION` — защищает promotion (файлы лягут на файловую систему/инструменты, для
  которых NFC/NFD-варианты одного пути видны по-разному) от перезаписи.
- **Casefold-коллизии:** та же проверка, casefold (lowercase) каждого нормализованного пути —
  `foo/README.md` и `foo/readme.md` коллизируют на регистронезависимой файловой системе/в
  редакторах, хотя git сам регистро-чувствителен и спокойно хранит оба. Тот же код ошибки
  `IMPORT_PATH_COLLISION`.
- **Длина:** отклонить путь длиннее 255 байт на сегмент или 4096 байт суммарно (стандартные
  ext4/XFS лимиты) — не усекать, отклонять весь импорт.

## 5. Лимиты размера с prospective-проверкой

- Переиспользуем существующие константы `apps/api/src/git/limits.ts` — **`MAX_FILE_BYTES` = 100
  МБ, `MAX_REPO_BYTES` = 1 ГБ** — не заводим второй набор чисел под импорт, один источник истины
  для upload и import.
- **Prospective-проверка ДО скачивания содержимого блобов:** клон с `--filter=blob:none` (§2)
  даёт полный граф коммитов/деревьев без байтов блобов. Один проход `git ls-tree -r -l <sha>` (в
  partial-clone `-l` отдаёт заявленный размер блоба из pack-заголовка без его скачивания) —
  суммируем `sizeBytes` по всем принятым (§4 прошедшим) записям; сумма превышает
  `MAX_REPO_BYTES`, либо одна запись превышает `MAX_FILE_BYTES` → отказ (`IMPORT_REPO_TOO_LARGE`
  / `IMPORT_FILE_TOO_LARGE`) **без единого запроса байт блоба** — это и есть prospective-свойство
  из постановки карточки, не пост-фактум чек после полного скачивания.
- Только после успешной prospective-проверки — `git cat-file --batch` по принятым путям тянет
  реальные байты; фактический размер потока пере-проверяется против того же лимита во время
  чтения (заявленный в заголовке размер может не совпадать с реальным у повреждённого/враждебного
  pack'а — не доверяем заголовку, обрываем поток при превышении лимита посреди чтения, не ждём
  EOF).
- **Object-count/depth cap** (независим от байтового лимита — дешёвый по байтам, но дорогой по
  обходу граф-бомба): `git rev-list --objects <sha>` (ограничен `--depth 1` из §2) не более
  50 000 объектов; глубина дерева каталогов не более 32 — превышение любого →
  `IMPORT_OBJECT_COUNT_EXCEEDED`.

## 6. Валидация содержимого (формат/MIME/YAML/архив)

- Каждый принятый блоб повторно проходит **ту же** сигнатурную/magic-byte проверку, что обычный
  upload (`docs/epics/formats.policy.md` § 1.2–1.7, правило «доверяем сигнатуре, не расширению»)
  — git-импортированные байты не получают более мягкую проверку, чем прямой upload. Формат вне
  whitelist не обязательно фейлит весь импорт (репозиторий легитимно может содержать
  произвольные исходники/доки/конфиги) — не прошедший whitelist блоб помечается
  `UNSUPPORTED_FORMAT` и исключается из promotion (виден в листинге импорта как «не перенесено»,
  не пишется в целевой репо); точный список разрешённых для promotion не-конвейерных
  классов/расширений (`.md`, `.yaml`/`.yml`, `.json`, plain-текст под `code_archive`/`project_doc`
  роли) — решение Back на этапе реализации, этот документ фиксирует МЕХАНИЗМ проверки, не
  финальный список расширений.
- **`portal.project.yaml`/любой `.yaml`/`.yml`-блоб** парсится ТОЛЬКО safe-загрузчиком:
  - произвольные YAML-теги (`!...`) вне plain core schema → отказ;
  - **якоря/алиасы (`&`/`*`) отклоняются целиком, не разворачиваются** — это прямая защита от
    billion-laughs/YAML-bomb (комбинаторное разрастание через цепочку алиасов) убирающая класс
    атаки, а не просто ограничивающая коэффициент разрастания;
  - **дублирующиеся ключи на любом уровне mapping → отказ** (`IMPORT_YAML_DUPLICATE_KEY`), не
    «последнее значение побеждает» — тихая семантика дублей исторически используется для
    контрабанды разного смысла разными парсерами одного и того же документа;
  - лимиты, проверяемые загрузчиком потоково (не после полной материализации в память): документ
    ≤ 1 МБ, глубина вложенности ≤ 16, длина любого mapping/sequence ≤ 10 000 элементов.
  - Диагностический код `IMPORT_YAML_ALIAS_REJECTED` — общий класс с MF-1964 (точный path/line/code
    формат диагностики — контракт той карточки, эта спека фиксирует только сам факт отказа и
    причину).
- **Архивы** (`.zip` — роли `code_archive`/Gerber-набор по `formats.policy.md` § 1.1): до
  распаковки читаем только central directory (без extraction) — отказ, если записей > 10 000,
  либо у любой записи отношение uncompressed/compressed > 100 (guard от decompression bomb),
  либо сумма uncompressed по всем записям превышает `MAX_REPO_BYTES` (`IMPORT_ARCHIVE_BOMB`) — тот
  же принцип «читаем метаданные, платим за extraction только после проверки», что и §5 для
  git-объектов. **Zip-slip:** каждое имя записи архива повторно проходит правила пути §4 (никаких
  `..`/абсолютных путей/NUL) до фактической распаковки любого байта.

## 7. Сканирование секретов

- До promotion каждый текстовый блоб, прошедший §6, сканируется лёгким regex+entropy сканером
  (в проекте сегодня нет отдельного secrets-сканера — это требование вводит эту карточку, не
  описание уже существующего): паттерны вида AWS access key (`AKIA[0-9A-Z]{16}`),
  `-----BEGIN ... PRIVATE KEY-----`, JWT-подобные 3-сегментные base64url-строки, `.env`-подобные
  строки `KEY=<высокоэнтропийное значение>`, плюс порог по энтропии Шеннона для строковых
  литералов длиннее 20 символов.
- Совпадение **не редактируется молча** — весь импорт отклоняется (`IMPORT_SECRET_DETECTED`) с
  кодом причины и byte-offset **только в приватном job-логе**; пользовательская ошибка — «похоже
  на секрет, импорт отклонён» без самого совпавшего фрагмента, чтобы не эхонуть секрет обратно
  инициатору импорта (который мог не знать, что секрет там есть, но тем более не должен получить
  его подтверждение через текст ошибки).
- Любой лог, куда мог попасть найденный фрагмент (stderr git-вызова, путь файла), редактируется
  (`[REDACTED]` вместо совпавшего диапазона) до персиста за пределами эфемерного quarantine —
  quarantine-каталог в любом случае уничтожается по §3 независимо от исхода.

## 8. Webhook signature/replay/idempotency (если/когда GitVerse инициирует импорт вебхуком, не только юзер-инициированный pull)

- Идемпотентность — **тот же паттерн**, что уже проверен в проде для платежей
  (`apps/api/src/billing/routes.ts`: `payment_webhook_events(provider, event_id)`, `ON CONFLICT
  DO NOTHING` до любой мутации, `docs/architecture/services.md`/`domain.model.md` § «Провайдер
  оплаты»). Будущая таблица `git_import_webhook_events(provider, event_id)` — тот же UNIQUE-ключ,
  тот же insert-до-мутации порядок, не новый паттерн.
- **HMAC-подпись обязательна** на каждом входящем вебхуке: общий секрет через `.env`
  (`GITVERSE_WEBHOOK_SECRET`, никогда не хардкодится — `SECURITY.md` § «Секреты»), сверка
  константным временем (`crypto.timingSafeEqual`), неподписанный/неверно подписанный запрос →
  `401` до любого обращения к БД.
- **Таймстемп-заголовок** обязателен, окно ±5 минут от серверного времени — вторая независимая
  защита поверх dedup по `event_id`: dedup ловит точный replay того же события, таймстемп ловит
  захваченный-и-переигранный-с-новым-event_id вебхук.
- Вебхук только **ставит job в очередь** (job_id), сам fetch никогда не выполняется inline в HTTP
  handler'е — тот же принцип «импорт живёт в quarantine-воркере, не в потоке запроса», что и
  везде выше в этом документе.

## 9. Promotion: quarantine → внутренний bare-репо

- Единственная функция (например, `promoteQuarantineToRepo(jobId, targetRepoPath)`) —
  единственная точка записи в `/srv/git/repos/*` из контура импорта. Тот же принцип «один
  writer-surface на модуль», что уже есть у `commitFile` в `apps/api/src/git/repo.ts`
  (`docs/architecture/git.module.md`).
- **Предусловие:** promotion запускается только если §1–§7 пройдены ВСЕ (host+redirect,
  hooks/submodule/LFS/symlink отсутствуют, quarantine не упёрся в timeout/квоту, канонические
  пути чисты, лимиты размера/object-count не превышены, формат/YAML/архив-проверки чисты, скан
  секретов чист). Одна проваленная проверка — весь job фейлится, promotion не запускается;
  частичной/best-effort promotion не существует.
- **Сама promotion** идёт под существующим `withRepoLock` (`apps/api/src/git/lock.ts`) на
  ЦЕЛЕВОМ репозитории (не на quarantine-каталоге — тот уже single-job/single-writer по
  конструкции §3), тем же plumbing-путём, что и обычный upload (`read-tree(parent) → hash-object
  -w → update-index → write-tree → commit-tree → update-ref`, см. `git.module.md`), файл за
  файлом через `commitFile`/маппинг роль↔путь (`docs/epics/project.git.md` §10.2), не сырым
  `cp -r`/`git clone` содержимого quarantine прямо в target bare-репо — сырое копирование обошло
  бы per-file size-recheck, который `commitFile` уже делает, и маппинг путей. Один коммит,
  синтетический автор (`git-import@users.3mf.tech`, тот же паттерн, что
  `gitAuthorForUser`/`paths.ts`), сообщение коммита включает исходный URL + резолвленный commit
  SHA источника — аудиторский след.
- **После успеха** — quarantine-каталог уничтожается (§3). **Если сама promotion упала** (диск
  полон, lock timeout) — целевой репо не изменён (последний мутирующий шаг git —
  `update-ref`, до него ничего не наблюдаемо снаружи), job помечается failed для повтора;
  quarantine cleanup выполняется в любом случае.

## 10. Наблюдаемые метрики и алерты

- Counters: `git_import_rejected_total{reason}` — по одному значению label на каждый код причины
  выше (`host_not_allowed`, `redirect_rejected`, `submodule_rejected`, `lfs_rejected`,
  `symlink_rejected`, `path_collision`, `repo_too_large`, `file_too_large`,
  `object_count_exceeded`, `yaml_alias_rejected`, `yaml_duplicate_key`, `archive_bomb`,
  `secret_detected`, `timeout`, `quota_exceeded`); `git_import_promoted_total`.
- Histogram: `git_import_job_duration_seconds` (clone+validate+promote целиком) — верхняя граница
  бакетов задаётся timeout'ом §3 (120с).
- Gauge: `git_import_quarantine_bytes`/`git_import_quarantine_inodes` — заводится в тот же контур,
  что уже мониторит диск (`docs/infra/git.repos.md` § «Мониторинг диска»,
  `portal.disk-monitor.sh`): WARNING на 75%, CRITICAL на 90% quarantine-бюджета (5 ГБ, §3), тот
  же `journalctl`-priority (`warning`/`crit`) — попадает в уже существующую алертинг-поверхность
  Ops, не заводит новую.
- Каждый отказ логируется с `job_id` + код причины + исходный URL (никогда — совпавший фрагмент
  секрета, §7) на уровне `info` — достаточно, чтобы ответить «почему конкретный импорт упал в
  `IMPORT_REPO_TOO_LARGE`» без повторного прогона job.
