# Проекты доски — направления вместо версий

> Действует с 2026-07-16 (директива оператора). Заменяет систему «проект =
> версия v1–v6» (MF-493, 2026-07-06). Версии остались осью СРОКОВ (лейблы
> `v1`…`v6` + due_date), проекты стали осью ВЛАДЕНИЯ (направление + лид-closer).

## Почему переехали

Диагноз старой доски (снято с данных 2026-07-16): 79% живых карт лежало в
проекте v1 → ось проекта не несла информации; недостающую структуру агенты
изобретали внутри эпиков (MF-1075 разросся до 201 живой карты — 36% доски,
деревья до 6 уровней при правиле «ровно 2»); in_review копился до 299 карт,
потому что closer был один глобальный (CTO) на всё.

## Правила

1. **Каждая карта лежит в проекте-направлении.** Выбор проекта = чей лид
   отвечает за результат. Сомневаешься — спроси направленца, не гадай.
2. **Лид проекта = closer**: in_review своего проекта разгребает лид
   (+ автопилот), CTO закрывает только эпики. Лид назначен в паспорте
   проекта (`project get`) и владеет паспортом карт своего проекта.
3. **Версия — это лейбл** `v1`…`v6` + due_date на эпике. Дедлайны версий —
   [roadmap.md](../product/roadmap.md) (v1 = 30.09.2026, v2 = 31.12.2026, v3 = Q1 2027).
   Property «Критический путь» — механизм фокуса (переименован из «Критический путь v1»).
4. **Role×week деревья запрещены** («Fullstack direction W2», «QA lead:
   очередь — 8+ задач»). Роль — это assignee, неделя — это due_date, не
   иерархия. Направленческие меты живут в «Оперировании».
5. **Ровно два уровня**: эпик → delivery-карта. Шаги — чеклист в описании.
6. QA конкретной фичи — в проекте фичи; QA-очереди/процессные меты — в
   «Оперировании».
7. **Волна — 2–4 крупных delivery-карточки, не больше** (директива оператора
   2026-07-17: код должен занимать бо́льшую часть ресурсов флота, не
   координация). Одна карточка объединяет ВСЕ связанные шаги одного
   владельца и одного результата — не дробить на файл/компонент/состояние/
   тест. Новая child-карточка — только при другом владельце, внешней
   зависимости или доказанном блокере, не для удобства планирования: много
   мелких карточек — это накладные расходы (очередь/ревью/паспорт) на
   каждую, а не польза. После первой волны лид не микро-менеджит —
   исполнитель доводит карточку до dev самостоятельно; лид сверяется с
   docs и договаривается с другими лидами напрямую, reassign только по
   реальному блокеру.

## Паспорт карточки (обязателен, вторая линия — Project HQ + автопилот)

- **Название — строго «[Глобальная задача]: [Задача]»**, пример: «Контракт каталога
  принтеров: query/facet/sort и cursor semantics». Номера MF-N в названии запрещены —
  ссылки на карточки живут в описании; глобальная задача называется по смыслу, не по
  номеру. (Директива оператора 2026-07-16; 210 старых названий переименованы.)
- **Проект-направление** — по таблице выше.
- **parent = эпик** (ровно 2 уровня).
- **priority ≠ none.** Приоритет = важность для дедлайна ближайшей версии,
  НЕ «всё urgent»: критический путь → urgent, остальное high/medium/low честно.
- **РЕАЛЬНЫЙ due_date** — раскладывается от дедлайна эпика назад по стейджам.
  Выдуманный/копипастный срок хуже пустого: по срокам живёт автопилот
  «Доска: ревизия сроков». Просрочил — двигай ЗАРАНЕЕ с комментарием-причиной.
- **Лейблы:** версия (`v1`…`v6`) — обязательна. Домен теперь выражает сам
  проект-направление, поэтому домен-лейбл не обязателен; функциональные
  лейблы (`баг`, `техдолг`, `ресёрч`, `сервис`) вешаются по смыслу.
- **Лейбл `эпик`** (2026-07-19) — ставится на верхнеуровневую карточку
  (`parent_issue_id = null`) вне проекта «Оперирование»: делает эпик видимым
  на доске без знания структуры БД. Источник истины остаётся структурным
  (нет родителя + не «Оперирование» — именно так эпики отличают
  `quota-guard`/`/epic-readiness` на дашборде, см.
  [quota.control.md § v6.3](quota.control.md)); лейбл — витрина поверх него,
  ставит его лид проекта при создании эпика (Headquarters «Ревизия доски»
  подхватывает пропуски по факту аудита, не автоматически на каждую карту).
- **Properties** ([issue.properties.md](issue.properties.md)): «Тип результата»
  и «Целевая среда» заполняет лид до назначения; «Критический путь» — только
  Headquarters/CTO.
- **Ресурсы проекта** — у каждого проекта прикреплён git-репозиторий
  (`project resource list`): десять проектов → `portal.ru` (ветка dev),
  «Прошивка UltraPrint» и «Девайсы: коннектор» → также `UltraPrint` (dev).
  Демоны берут рабочий репозиторий отсюда — не хардкодь пути в карточках.

## Структура v1 эпика (правило для новых карт)

При создании карточек в v1 эпике (или любом version-эпике) соблюдай:

- **Проект-направление** — по смыслу карточки (не "v1 project"), выбор
  зависит от роли: Design/Docs → Дизайн-система, Fleet → Девайсы,
  Data → Данные и каталоги, QA → Инфра и поставка, Fullstack → Девайсы, и т. д.
- **Лейбл версии** — обязателен (в примере v1).
- **Parent** — эпик (parent_issue_id = идентификатор эпика, не role/week).
- **Priority** — не none; честный приоритет по дедлайну версии.
- **Due-date** — раскладывается от дедлайна эпика; для direction-карт без
  дедлайна требуй ввода от CTO/лида, не выдумывай сам.
- **Stage** — номер волны (1, 2, 3, …), для фазированной работы.
- **Assignee** — направленец или его делегат; CTO не назначает код напрямую.

Правило действует с 2026-07-17 (нормализация MF-1193 v1 epic tree, MF-1197).
