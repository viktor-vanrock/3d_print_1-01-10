## Задача

Семантический поиск по моделям (title/description/tags), приоритет — русский язык. Уже заявлен как MVP-фича в `docs/product/features.md` («Семантический поиск на русском») — этот документ прорабатывает, КАК именно.

## Модели эмбеддингов для русского языка (2026)

Ключевая метрика сравнения — **ruMTEB** (бенчмарк качества эмбеддингов на русском). Актуальный расклад:

| Модель | Параметры | Контекст | ruMTEB | Лицензия | Особенность |
|---|---|---|---|---|---|
| **GigaEmbeddings** (Сбер, «AI Sage») | ~3B (после прунинга) | 4096 токенов | **69.1** | **MIT** | Заточена под русский, 3–4 ГБ VRAM с квантованием — можно **самим хостить**, не только через платное API |
| **Qwen3-Embedding-8B** (Alibaba) | 8B | 32000 токенов | **70.58** (выше!) | Apache 2.0 | Длинный контекст, мультиязычность |
| **Qwen3-Embedding-4B** | 4B | 32000 | 69.5 | Apache 2.0 | Компромисс размер/качество |
| **Qwen3-Embedding-0.6B** | 0.6B | 32000 | ниже | Apache 2.0 | <1 ГБ VRAM, edge/дёшево |
| multilingual-e5-large (легаси) | — | — | ~65.5 | MIT | Устаrevшая, но рабочая опция без GPU |

Источники: [обзор embedding-моделей для русского 2026](https://vc.ru/ai/2730372-embedddingi-dlya-russkogo-yazyka-v-2026), [GigaChat Embeddings API](https://developers.sber.ru/docs/ru/gigachat/models/embeddings), [GigaChat Embeddings-2](https://developers.sber.ru/docs/ru/gigachat/models/embeddings-2).

**Важная развилка — GigaEmbeddings как API vs self-host:**
- **Через GigaChat API** (`POST /embeddings`, модели `Embeddings`/`EmbeddingsGigaR`) — не надо поднимать GPU, платим за вызовы, привязка к Sber (усиливает нашу же стратегию «Sber-козырь», см. `docs/product/market.md`).
- **Self-host** — тот же GigaEmbeddings опубликован с MIT-лицензией, можно поднять на своей инфраструктуре (нужен GPU-инстанс — cloud.ru это предоставляет). Оба варианта поддерживают **Matryoshka Representation Learning** — можно урезать размерность вектора (например, до 256) почти без потери качества, экономя место в БД.

**Рекомендация:** начать с **API GigaChat Embeddings** (нулевая инфраструктура, быстрее всего запустить MVP, естественно ложится в `apps/giga`, где уже есть SDK `gigachat`), заложить возможность перехода на self-hosted GigaEmbeddings или Qwen3-Embedding при росте объёма/стоимости.

## Хранилище векторов

| Вариант | Плюсы | Минусы | Когда выбрать |
|---|---|---|---|
| **pgvector** (расширение Postgres) | Ноль новой инфраструктуры — эмбеддинги это колонка в уже имеющемся Postgres; бэкапы/мониторинг/доступ — всё как для обычной БД | Чуть ниже recall на очень больших объёмах | **Наш случай** — Postgres уже основная БД (`docs/architecture/readme.md`), объём моделей маркетплейса реалистично далёк от порога в десятки миллионов |
| **Qdrant** (выделенная vector DB) | На больших объёмах — выше throughput, ниже tail latency | Отдельный сервис (Docker/K8s), свой мониторинг, доп. эксплуатационная нагрузка на маленькую команду | Если/когда перерастём Postgres — не сейчас |

При HNSW-индексах на среднем масштабе задержка у pgvector и Qdrant отличается <1мс на p50; на больших объёмах pgvector даёт на порядок выше throughput при сохранении latency, Qdrant — чуть выше recall (~1%) и ниже tail-latency. Источники: [pgvector vs Qdrant, TigerData](https://www.tigerdata.com/blog/pgvector-vs-qdrant), [сравнение векторных БД 2026](https://www.instaclustr.com/education/vector-database/pgvector-vs-qdrant-5-key-differences-and-how-to-choose/).

**Рекомендация: pgvector.** Соответствует принципу «minimal dependencies» проекта (`CLAUDE.md`), не плодит инфраструктуру ради задачи, которую Postgres решает на нашем масштабе полностью.

## Гибридный поиск (важно — не чисто векторный)

Production-практика — **не** заменять полнотекстовый поиск векторным, а комбинировать: ключевые слова (точные совпадения по названию/бренду/материалу) ловит full-text search (Postgres `tsvector`/`pg_trgm`), смысловую близость («что-то как дракон, но попроще») — вектор. Ранжирование — гибридное (сумма/reciprocal rank fusion двух скорингов). Это то, как большинство реальных поисковых систем маркетплейсов работают в 2026, не только теория.

## Что именно эмбеддим

- Title + description + tags — конкатенировать в один текст перед эмбеддингом (не заводить отдельные векторы на каждое поле, если нет доказанной необходимости — усложнение без явной пользы на старте).
- Категория/материал/совместимость с принтером — **не эмбеддить как текст**, держать как обычные фильтруемые колонки (SQL `WHERE`), комбинировать с векторным поиском (сначала фильтр по фактам, потом ранжирование по смыслу внутри отфильтрованного набора — дешевле и точнее, чем пытаться впихнуть всё в эмбеддинг).
- Описания обычно короткие (не книги) — чанкинг, скорее всего, не нужен на старте; если появятся длинные авторские тексты — разобраться отдельно.

## Поиск по фото/геометрии (вторично, не MVP)

Кратко, не в приоритете: технически реалистично через CLIP-подобные модели (эмбеддинг фото и эмбеддинг рендер-превью модели в одном пространстве, косинусное сходство). Не прорабатывается подробно в этом документе — отдельная задача, если понадобится после MVP текстового поиска.

## Архитектура v1 (минимально жизнеспособная)

```
apps/giga (Python/FastAPI, уже есть SDK gigachat):
  POST /embed {text} → вызывает GigaChat Embeddings API → возвращает вектор
  (по мере роста — заменить на self-hosted модель без смены внешнего контракта)

apps/api (Fastify):
  при создании/редактировании модели → зовёт apps/giga /embed → пишет вектор в Postgres (pgvector column)
  GET /search?q=... → full-text (tsvector) + векторный поиск (эмбеддинг запроса через apps/giga) → гибридное ранжирование → результат
```

## Открытые вопросы

1. Бюджет на вызовы GigaChat Embeddings API при заметном объёме моделей/поисков — уточнить тарифы у Сбера при регистрации (см. `docs/epics/auth.triple.md` — та же регистрация организации пригодится и здесь).
2. Порог, при котором переходим на self-hosted (по деньгам или по нагрузке) — не блокирует MVP, фиксируем как будущий триггер решения.

## Фазы

1. **Фаза 1:** `/embed`-эндпоинт в `apps/giga` (GigaChat API), колонка `pgvector` в таблице моделей, простой векторный поиск.
2. **Фаза 2:** гибридизация с full-text search + фильтрами по фактам (материал/принтер/категория).
3. **Фаза 3 (по решению):** self-hosted эмбеддинги при росте объёма/стоимости API.

## Критерии приёмки (Фаза 1–2)

- Поисковый запрос на русском находит релевантные модели даже без точного совпадения слов в названии (напр. «дракон для стола» находит модель «Statuette Дракончик» без слова «стол»).
- Точные совпадения (бренд/название) не теряются на фоне векторного ранжирования — гибридный скоринг подтверждён вручную на наборе тестовых запросов.
