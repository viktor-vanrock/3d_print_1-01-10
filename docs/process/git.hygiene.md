# Git-гигиена: ДВЕ ветки, теги, чистка

Операционный регламент веток и тегов portal.ru — как поддерживается на практике поверх
`CONTRIBUTING.md` § «Ветвление» (источник правил, этот док их не переопределяет). Владелец
контура — роль **Git** (`docs/process/squad.multica.md`), прогоняет регламент каждый свой
запуск.

Снимок состояния — **2026-07-08**. Числа и списки веток устареют — актуализировать
командами § 5, не верить цифрам вслепую.

## 1. Правило: на `origin` живут РОВНО две ветки

**`main` и `dev` — единственные легитимные ветки на `origin`** (модель двух веток, правило
оператора 2026-07-08, `CONTRIBUTING.md`). Всё остальное на `origin` — под удаление.

- **`main`** — прод-транк (деплой на 3mf.tech). Пишется ТОЛЬКО промоушеном `dev→main`
  (fast-forward, после проверки на dev.3mf.tech) и CI (`release.yaml`).
- **`dev`** — общий рабочий ствол (деплой на dev.3mf.tech). Сюда коммитят все — люди и агенты.
- **Легаси-пространства** (`feature/*`, `fix/*`, `chore/*`, `docs/*`, `hotfix/*`, `agent/*`,
  ветка `test`) — наследие старой модели, **вычищаются** (§ 5). Новые НЕ создаём.

**`agent/<роль>/<hash>` — локальные, не пушить, И НЕ УХОДИМ С НЕЁ.** Демон Multica на каждый
запуск делает `multica repo checkout` и создаёт локальную `agent/<роль>/<hash>` в task-workdir
— это и есть рабочая ветка запуска, `agent/*` НЕ пушится, остаётся локальной и умирает с
workdir. Если `agent/*` всё же появилась на `origin` — это случайный пуш старого поведения,
кандидат на удаление (после проверки, что работа уже в `dev`).

**Инцидент MF-746 (2026-07-10): НЕ делай `git checkout -B dev origin/dev` в task-workdir.**
Старое правило требовало первым делом переключаться на локальную ветку `dev` в каждом
task-workdir. Один bare-репо расшарен на десятки worktree одновременно (один на запуск
агента) — `git` блокирует чекаут одной ветки в двух worktree, но **эта защита работает только
для `git checkout <branch>`/`git switch <branch>`**, а `checkout -B` (force create-or-reset)
её не проверяет. Итог, подтверждённый живьём: 41 из 71 активного worktree одновременно держали
локальный `refs/heads/dev` (`git worktree list` → `[dev]` у всех), каждый со своим протухшим
index. Любой из них при новом `git fetch && git checkout -B dev origin/dev` двигал общий ref
для ВСЕХ соседей разом — их `git status` тут же показывал фантомные `M`/`D` по чужим файлам
(в примере: удалённые иконки PWA, миграция БД, CI workflow — ничего из этого агент не
трогал, просто чужой пуш подвинул общий `dev`, а локальный index не обновился). Несколько
агентов, не распознав фантом, спрятали его в `git stash` «на всякий случай» вместо коммита —
если бы вместо этого прошёл `git add -A && commit && push`, в общий `dev` улетели бы чужие
удаления.

**Исправленный процесс** (тот же результат — линейный общий `dev`, без разделяемого чекаута):
работай на своей `agent/<роль>/<hash>` (`HEAD`), синкайся `git fetch origin dev && git rebase
origin/dev`, публикуй `git push origin HEAD:dev`. Ветку `dev` в своём worktree никогда не
чекаутишь. Канонический цикл — `CONTRIBUTING.md` § «Ветвление».

## 2. Политика жизни веток (просто)

- **`main`, `dev`** — вечные, из чистки исключены целиком.
- **Любая другая ветка на `origin`** — кандидат на удаление:
  - её работа уже в `dev`/`main` (`--merged`) → удаляем безусловно, мёртвый вес;
  - есть неслитые коммиты → сначала перенести работу в `dev` (cherry-pick/merge) ИЛИ пинг
    автору/карточке; удалить после. Чужую неслитую работу молча не сносим.

Снимок 2026-07-08: 45+ remote-веток (17 × `agent/*`, десятки `feature/*`/`docs/*`, `test`) —
весь этот хвост под разовую чистку. Новые не появляются: промпты всех агентов переписаны на
общий `dev` (`docs/process/multica.internals.md` § 5, `squad.multica.md`). Задача Git —
довести `origin` до состояния «только `main` + `dev`» и держать его.

## 3. Теги и версии

**Правило: MINOR-теги ставит только `release.yaml` (CI), руками — никогда. RELEASE-тег
(`v{YY}.{RELEASE}.1`) — исключение: его ставит роль Git по релиз-runbook'у** (`version.mjs
release` + `git tag` + push, коммит `chore(release): … [skip ci]` — см.
`docs/process/versioning.md` § «Runbook нарезки»). Это единственный санкционированный ручной
тег. Формат `v{YY}.{RELEASE}.{MINOR}`, источник значений —
`version.json` в корне. Единственный официальный ручной путь — `workflow_dispatch` с
`action=release` (только Валерий/мейнтейнеры), который тоже идёт через тот же job, а не
через голый `git tag`.

Механика (`.gitverse/workflows/release.yaml`, job `version`): бампает `version.json`,
коммитит `chore(release): v<X> [skip ci]`, ставит тег на этот же коммит, пушит и коммит, и
тег в `main`. Двойная защита от цикла: `[skip ci]` в сообщении + условие
`!contains(head_commit.message, '[skip ci]')` в job.

**Как свериться (read-only, безопасно гонять в любой момент):**
```bash
git fetch --tags origin
# версия из файла на кончике main → ожидаемое имя тега
git show origin/main:version.json | node -e \
  "const v=JSON.parse(require('fs').readFileSync(0)); console.log('v'+v.year+'.'+v.release+'.'+v.minor)"
# тег(и), реально стоящие на HEAD main — должно быть ровно совпадение с именем выше
git tag --points-at origin/main
```
Ожидаемо: `git tag --points-at origin/main` даёт ровно один тег `v{year}.{release}.{minor}`,
совпадающий с `version.json` на этом же коммите.

**Что делать при рассинхроне** (тег не соответствует `version.json`, тег есть без релизного
коммита, или коммит `chore(release)` есть, а тега нет): **не чинить руками** — никаких
`git tag -f`, `git tag -d` + пересоздание, `git push --force` по тегам. Это территория
`release.yaml`/CI (Ops), а массовая/деструктивная правка тегов — красная линия для Git-роли
(«ничего необратимого», см. сквад-инструкции). Зафиксировать факт (какой коммит/тег/файл, в
чём именно разъезд) в журнале «Git-гигиена» и пинговать Ops + Lead немедленно — это тот же
уровень тревоги, что и прямой push в `main` (§ 4).

## 4. Защита `main`

Технической защиты нет (`protected: false`; branch protection отсутствует в публичном API
GitVerse — полный список 21 эндпоинта Repositories API проверен). Держится **процессом**:

- **Единственные легитимные писатели `main`:** (1) промоушен `dev→main` (fast-forward, после
  проверки фичи на dev.3mf.tech; право Lead и директоров) — `CONTRIBUTING.md` § «Промоушен»;
  (2) CI-коммиты `release.yaml` — автор `gitverse-actions <actions@3mf.tech>`, сообщение
  `chore(release): … [skip ci]`; (3) релиз-стамп роли Git по релиз-runbook'у (коммит
  `chore(release): v… [skip ci]` + тег + version.json/CHANGELOG — `versioning.md` § «Runbook»).
- Роль Git **детектирует нарушения**: коммит в `main`, который не пришёл ff-промоушеном из
  `dev` и не является CI-релизом → прямой пуш в обход, тревога: немедленный пинг Lead + CTO.
- Включение технической защиты (branch protection в GitVerse UI, если/когда появится) —
  вопрос к CTO. Git-роль это не настраивает, а детектирует нарушения модели.

## 5. Процедура чистки легаси-веток (регламент; исполнение — сервисной карточкой)

Цель — привести `origin` к «только `main` + `dev`». В самой карточке-регламенте удаление НЕ
выполняется — только формируется список кандидатов и кто подтверждает.

**Шаг 1 — кандидаты (read-only):**
```bash
git fetch --all --prune
# всё, кроме main/dev — кандидаты в модели двух веток
git branch -r | grep -vE 'origin/(main|dev)$|HEAD ->'
# слитые в dev или main — безусловно под снос (история уже там)
git branch -r --merged origin/dev  | grep -vE 'origin/(main|dev)$|HEAD ->'
git branch -r --merged origin/main | grep -vE 'origin/(main|dev)$|HEAD ->'
```

**Шаг 2 — неслитые.** Для ветки с коммитами, которых нет ни в `dev`, ни в `main`: найти
карточку Multica (по номеру/имени в коммитах), проверить статус. Ценная работа → перенести в
`dev` (cherry-pick/merge в dev, проверить на dev.3mf.tech), затем удалить ветку. Терминальная
карточка / не найдена → пинг автору в его карточку, два пинга без ответа → эскалация Lead.

**Шаг 3 — подтверждение.** Слитые → в список на удаление без пинга. Массовый снос легаси
(десятки веток разом) — одобряет Lead/CTO как разовую операцию.

**Шаг 4 — исполнение (отдельной сервисной карточкой):** `git push origin --delete <branch>`
по подтверждённому списку. Слитый локально squash-PR не закрывает PR на GitVerse — после
переноса работы закрыть висящие PR (`gitverse-pr-close <PR>`), чтобы не плодили фантом.

**Никогда:** force-push, удаление/правка `main`/`dev`, снос чужой неслитой работы без
пинга или переноса в `dev`, массовое удаление без прохождения шагов 1–2.
