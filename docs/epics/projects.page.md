## 1. Проблема / запрос

Валерий (2026-07-07, MF-508): проработать бывший «Маркетплейс», переименованный в «Проекты». Требования:

1. **Широкий layout** этой страницы: часы уходят к левому краю экрана, капсула (аватар/уведомления/тема) — к правому («от края и до края»); навигация «домой»/«проекты» — по центру сверху. Это отличает страницу от «дома» (дом — лайтовый хаб). Тот же широкий режим будет применяться и к другим страницам, например «принтеры».
2. **Состав страницы:** сверху — большие карточки 16:9, листаются по очереди справа налево, — галерея лучших проектов, которые мы рекомендуем; ниже — каталог всех работ; слева — меню с настройками и фильтрами; где-то умело расположить нейропоиск, который на лету меняет содержание страницы и имеет доступ к фильтрам.
3. **Приоритет для пользователя:** 1) топ проектов, 2) продвинутый поиск, 3) каталог и фильтры.
4. **Концепция проекта:** проект — не столько про печать, сколько про самоделку (пример «часы»: 3mf, плата и её файл, проект на ГитВёрсе, пошаговая инструкция сборки). Думать о проекте как о расширенном git: README.md как стартовое описание, структура папок, форки, комментарии. В v1 — только 3D-печать, но логику закладывать. Файлы — коннект с аккаунтом ГитВёрса и хранение там; пока тестово у нас, либо наше хранилище потом дублируется на ГитВёрс.

## 3. Решения (с вариантами)

### Р1. Широкий layout — режим системы, не приватная вёрстка страницы

Вводим **wide-режим лейаута** как параметр дизайн-системы: часы — к левому краю вьюпорта, капсула — к правому, по центру сверху — навигация (`домой` / `проекты`; расширяемо для будущих табов). Контент страницы использует увеличенный `max-width`. Дом остаётся в текущем «лайтовом» режиме.

- Владелец — Design: дельта поверх `layout.md` + `header.capsule.md` (режимы шапки), с явным контрактом «какая страница какой режим включает». Страница «принтеры» в эпик не входит — но режим обязан быть переиспользуемым (критерий приёмки: включение режима на новой странице не требует перевёрстки шапки).
- Отклонено: (а) отдельная шапка для страницы «Проекты» — дублирование компонента, расползание стилей; (б) сделать wide-режим глобальным для всех страниц сразу — противоречит «дом = лайтовый хаб» из запроса.

### Р2. Hero-галерея рекомендуемых — кураторская, не алгоритмическая

Сверху витрины — карусель больших карточек 16:9, автолистание справа налево, пауза при взаимодействии. Наполнение в v1 — **кураторский выбор** (отбирает оператор/команда), механика хранения флага/списка «featured» — за Data (минимальная: пометка на `models`, например `featured_at timestamptz nullable`; точную DDL решает Data в фазе 1).

- Отклонено: (а) алгоритмическая подборка по метрикам — в v1 нет ни объёма данных, ни аналитики (роадмап: аналитика — v2), пустой алгоритм даст случайную витрину; (б) ручной JSON-конфиг вне БД — не редактируется без деплоя.
- Карточка hero использует существующие превью-ассеты (webp/GLB-контур marketplace.md §1.13–15); отдельный «баннерный» арт не заводим, пока нет спроса.

### Р3. Поиск: продвинутый UX сейчас, нейро-бэкенд — подключаемый

По приоритету запроса поиск — второй по важности элемент страницы (между hero и каталогом). Делаем **живой поиск**: ввод на лету обновляет выдачу каталога (debounce), поисковый слой может выставлять фильтры панели (единый state поиск+фильтры). Бэкенд v1 — существующий `GET /models?q=` (ILIKE); контракт marketplace.md §1.2 сохраняется, семантический бэкенд MF-12 подключается в v2 без смены UI.

- «Нейропоиск, меняющий фильтры» (интент-разбор запроса → фильтры) — это AI-слой v2 (apps/giga); в v1 закладываем архитектуру: состояние фильтров — единый управляемый store, к которому потом получит доступ AI-агент поиска. Открытый вопрос оператору — §7.1 (тянуть ли нейро-бэкенд в v1 вопреки роадмапу; дефолт — нет).
- Отклонено: строить в v1 отдельную «страницу результатов поиска» — живой каталог и есть выдача (принцип «страница = одна задача» не нарушается: задача страницы — найти проект).

### Р4. «Проект как расширенный git» — концептуальная модель, разложенная по существующим контурам

> **Пересмотрено (CTO, 2026-07-07, решение Валерия в MF-508):** git — не метафора, а субстрат хранения. Действующее решение — [project.git.md](project.git.md) (bare-репозитории за API, миграция, базовый форк в v1). Таблица ниже остаётся верной по UI-контурам; строки «хранение» и «форки» — см. новый эпик.

Направление фиксируем как продуктовую рамку (обновление к vision): целевая сущность — проект-самоделка с артефактами разных ремёсел и «git-подобной» анатомией. Реализация в v1 — БЕЗ новой схемы и без переезда хранения:

| Git-метафора | Наш контур v1 | Где решено |
|---|---|---|
| README.md | markdown-описание проекта | MF-497 Р3 |
| Структура папок | роли `model_files` + блок «Файлы проекта» (группировка по ролям; представление «дерево» — на усмотрение Design) | MF-482, design/projects.md §3 |
| Коммиты/версии | вне v1 (версионирование публикаций — отдельный эпик по спросу) | — |

| Репозиторий | `models.repo_url` — линк, без синка | MF-497 Р4 |

- **Хранение на GitVerse** («коннект к акку и хранение там / дублирование») — НЕ в v1: договорённость с GitVerse не закрыта, API-контракта нет. Храним у себя (S3, 3mf.storage.md) — это и есть «пока тестово у нас» из запроса. Дублирование на GitVerse — отдельный эпик, когда договорённость закрыта (условие пересмотра MF-497 §8). `repo_url` и IA блока «Код» спроектированы так, что интеграция встаёт без перевёрстки.
- Отклонено: (а) завести `project_*`-схему «под git-структуру» — прямо запрещено вердиктом MF-9; (б) реальный git-бэкенд (bare-репозитории) под каждый проект в v1 — тяжёлая инфраструктура без пользователя, при этом UI-анатомия (README/файлы/обсуждение) достижима на текущей схеме.
- Пошаговые инструкции сборки — упомянуты Валерием как «огромный эпик с кучей подзадач»: в этот эпик НЕ входят, отдельная спека по отдельному решению.

### Р5. Маршрут витрины — публичный path `/project` (решение Валерия, 2026-07-07)

Цель, названная оператором: **рабочий прототип на `https://3mf.tech/project`**. Витрина «Проекты» переезжает с hash-маршрута `#/market` на path-маршруты `/project` (каталог) и `/project/:id` (карточка проекта); старые hash-ссылки редиректятся. Serving (nginx отдаёт SPA на `/project*`) — зона Ops; роутинг и редиректы — карточка MF-524 (Fullstack). Решение хэш-роутера marketplace.md §1.1 для витрины уточнено этим пунктом; прочие разделы (`#/u/:username` и т.д.) не трогаем — переезд всего приложения на path-роутинг отдельным решением по факту.

## 6. Критерии приёмки (приёмка эпика — CTO)

1. На странице «Проекты» (`https://3mf.tech`): часы у левого края, капсула у правого, навигация центрирована сверху; «дом» остался в прежнем лайтовом режиме.
2. Wide-режим — переиспользуемый механизм дизайн-системы (включение на тестовой/новой странице не требует правок шапки), зафиксирован в docs/design.
3. Hero-карусель: карточки 16:9, автолистание справа налево, наполнение управляется featured-механикой из БД (без деплоя).

5. Иерархия страницы соответствует приоритету запроса: hero → поиск → каталог+фильтры.
6. Никаких `project_*`-таблиц; словарь/терминология не разъехались с MF-497.
