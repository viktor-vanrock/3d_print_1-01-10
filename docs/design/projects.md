**Что это.** Стадия 1 (дизайн) эпика «Проекты» (MF-481). Проектирует, как «проектность» портала проявляется в витрине **уже сейчас, на печати**, не ломаясь при появлении второго ремесла. Это **дельта поверх** `marketplace.v2.md`: добавляет craft-бейджи, IA страницы проекта (артефакты по ролям + блок «Код») и терминологию — не переписывает раскладку каталога и «парящую» страницу модели (они остаются как в v2).

**Уровень продукта.** Эта спека описывает **публичный project landing**:
канонический результат, файлы и вход в сборку. Личная build session после
выбора конфигурации — отдельный приватный уровень и не должна жить в
состоянии этой страницы. Канон двух уровней, конфигураций и завершения через
Make — [docs/product/projects.md](../product/projects.md).

**Зона.** Только дизайн-спека. Реализует TypeScript-агент на стадии 2 эпика. Схему (`models.craft`, check'и ролей/форматов) готовит DB-агент стадии 1 параллельно — этот файл фиксирует, что витрина **читает** из данных, не проектируя DDL.

**Правило работы (наследуется от v2).** Только существующие токены ([theme/tokens.css](../apps/web/src/theme/tokens.css)) и примитивы UI-кита ([ui/ui.tsx](../apps/web/src/ui/ui.tsx), MF-40) + слой всплывашек (`overlay/`, MF-440). Где системы не хватает — помечено **GAP** (сводка §7). Все тексты — **RU**.

**Границы (НЕ проектируем, §5 эпика).** Конвертеры/вьюеры ЧПУ/лазера/Gerber; реальную GitVerse-интеграцию (только задел-место); переименование таблиц БД; справочник `crafts` таблицей; коммерцию/сообщества. Печать — единственное живое ремесло MVP; всё остальное — **задел раскладки**, не активный UI.

## 1. Терминология витрины: «Модели» vs «Проекты» — рекомендация

Открытый вопрос §6.1 эпика: **когда публичный раздел «Модели» становится «Проектами»?** Решение принимает Валерий; дизайн даёт обоснованную рекомендацию и план перехода без перевёрстки.

### 1.1 Рекомендация: **«Модели» сейчас → «Проекты» после второго живого ремесла**

**Держим слово «Модели» в UI на MVP.** Обоснование:

1. **Честный UI (принцип [marketplace.md](../epics/marketplace.md) §1.6, эпик §2 п.4):** портал не обещает того, чего нет. Сегодня в витрине — только 3D-печать (STL/STEP/3MF). «Проект» подразумевает мульти-артефактность (печать + ЧПУ + плата + код); называть «проектом» одиночный STL-файл — обещание, за которым нет продукта. «Модель» точно описывает то, что есть.
2. **Пользовательская модель мира.** Аудитория первой фазы — 3D-печатники; «модель» — их родной термин (каталоги Printables/Thingiverse/MakerWorld оперируют «моделями/things»). «Проект» на старте создаст лишнюю когнитивную нагрузку («а где остальные части проекта?»).
3. **Схема уже развязывает термин от UI (эпик §2 п.1).** `models` в БД не переименовывается до второго ремесла; терминология UI — **отдельный слой**, меняется без миграции. Значит спешить незачем: смена ярлыка — дешёвая операция «потом», а ранний ребрендинг — дорогая расплата доверием.

**Триггер переключения — появление второго *живого* ремесла**, не второго check-значения в БД. «Живое» = у ремесла есть реальный конвейер/просмотр и хотя бы одна публикация с не-печатным артефактом (эпик §2 п.4: наличие роли в check ≠ пункт в UI). До этого момента «Проекты» в интерфейсе не показываем даже как пустой раздел (домен: «пустые сущности впрок протухают»).

### 1.2 Один раздел или два (§6.2 эпика): **одна витрина**

Рекомендация — **магазин и есть витрина проектов**, не отдельный раздел «Проекты» рядом. Обоснование:

- Философия readme §2 — «одна главная мысль на экран/в навигации». Два параллельных раздела с пересекающимся контентом («Модели» и «Проекты», где проект — надмножество модели) — это два входа в одну сущность, классическая «скомканность» IA (запрос Валерия §9.5 v2 — наоборот, *разносить* задачи, а не *двоить* одну).
- Технически проект = эволюция `models` (эпик §2 п.1), не новая таблица. Одна сущность → одна витрина, один каталог, один маршрут `#/market`. Смена термина «Модели»→«Проекты» — это переименование **той же** вкладки, не добавление второй.
- Craft-фильтр (§5.1) внутри одной витрины разводит ремёсла лучше, чем отдельные разделы: пользователь фильтрует «показать только ЧПУ» в том же каталоге, а не прыгает между вкладками.

**Итог для навигации:** таб `Маркетплейс` в `HomeHeader` (капсула) остаётся единственным входом в витрину. При переключении термина меняется его подпись и заголовки — не структура навигации.

#> **Обновление (MF-498, эпик MF-497):** переключение принято Валерием — витрина говорит «Проекты» с этого эпика. **Финальные RU-строки словаря — в [projects.multiformat.md](projects.multiformat.md) §1** (Front берёт их дословно); там же таб-рекомендация «Проекты» (§7.1 эпика). Таблица §1.3 ниже — исходная механика, актуальные значения — в дельте.

## 1.3 План переключения (когда Валерий скажет «пора»)

Смена — **одномоментная замена словаря**, не редизайн. Централизуется в одном месте, чтобы переключалась флагом, а не правкой по всему коду.

**Что меняется (полный список строк UI):**

| Место | Сейчас | После переключения |
|---|---|---|
| Таб в шапке (капсула) | «Маркетплейс» | «Маркетплейс» (нейтрально — можно оставить) или «Проекты» |
| Заголовок каталога (`Heading hero`, §1.1 v2) | «**Маркетплейс** моделей» | «**Маркетплейс** проектов» |
| Плейсхолдер поиска (§1.2 v2) | «Найти модель…» | «Найти проект…» |
| Кнопка добавления (§1.3 v2) | «Добавить модель» | «Добавить проект» |
| Пустые состояния (§2.4 базы) | «Здесь появятся ваши модели» | «…ваши проекты» |
| Страница сущности — заголовок вкладки, «by @автор» | «модель» в подписях | «проект» |
| Профиль автора (§7 базы) | «модели @username» | «проекты @username» |

**Механика перехода (рекомендация реализации, не блокирует дизайн):**

- Ввести один модуль словаря витрины (напр. `entityNoun` в `apps/web`: `{ singular: 'модель'/'проект', plural, accusative, add: 'Добавить модель'/'Добавить проект' }` — RU-склонения нужны, поэтому не одна строка, а мини-словарь форм). Все UI-строки берут ярлык оттуда, а не хардкодят «модель».
- Переключение — смена одного значения (в идеале — фича-флаг/конфиг, не деплой-релиз кода). Это делает переход **обратимым** и дешёвым: если рано — вернули.
- **Ноль изменений раскладки/данных.** URL `#/market/model/:id` можно оставить (внутренний путь, не показывается) — не ломаем deep-links; при желании позже добавить алиас `#/market/project/:id` (GAP-NAV, не сейчас).

**Дизайн держит дефолт «Модели» до явного «да» от Валерия.** Мини-словарь форм — задел стадии 2 (завести структуру, значение = «модель»), чтобы переключение потом не было «найти-заменить по всему фронту».

## 2. Craft-бейджи: маркировка ремесла

Задача: показать, **к какому ремеслу** относится публикация — на карточке каталога и на странице модели — так, чтобы система масштабировалась с `3d_printing` на `cnc`, `laser`, `electronics`, `software` без перевёрстки. Источник данных — `models.craft` (уже live в схеме, slug справочника `crafts`, [domain.model.md](../epics/domain.model.md) § Ремёсла).

### 2.1 Ключевое решение: бейдж скрыт, пока ремесло одно

**Пока все публикации — `3d_printing` (весь MVP), craft-бейдж НЕ показываем.** Обоснование:

- Философия readme §2/§4 — «одна мысль на кадр», «без перегруза». Бейдж «3D-печать» на **каждой** карточке, когда других ремёсел нет, — чистый шум: он ничего не различает (всё одинаковое), только засоряет плитку.
- Тот же честный паттерн, что теги/фильтры в v2 (§1.3 v2: «пока тегов в БД нет — блок скрыт целиком»). Бейдж-различитель включается, когда есть **что различать**.

**Правило видимости (фиксирую как инвариант):**

> Craft-бейдж рендерится на карточке/странице **тогда и только тогда**, когда в видимой выборке присутствует **больше одного** значения `craft` (или, проще для реализации, когда `craft !== '3d_printing'` — т.е. появилась хоть одна не-печатная публикация). Пока витрина моно-ремесленная — бейджей нет. Это автоматический переключатель от данных, не ручной флаг.

Это делает бейдж **готовым, но невидимым**: код стадии 2 рисует `CraftBadge` всегда, а сам компонент возвращает `null` при моно-ремесле. Появление второго ремесла «зажигает» бейджи по всей витрине без правок вёрстки.

### 2.2 Компонент `CraftBadge` (новый примитив, GAP-CSS §7)

Малый чип-бейдж «глиф + короткая метка», семейство `StatusPill`/`Chip` ([components.md](components.md): пилюли `border-radius: 999`, line-глифы, без эмодзи). Не новый визуальный язык — вариант существующей пилюли.

**Реестр ремёсел (slug → метка / глиф / тон).** Единая таблица-словарь в коде (`craftRegistry`), по образцу того, как v2 разводит статусы. Slugs — строго из [domain.model.md](../epics/domain.model.md) § Ремёсла:

| slug | RU-метка | line-глиф (ориентир) | тон (токен) |
|---|---|---|---|
| `3d_printing` | Печать | куб/слои (уже есть `CubeIcon`) | `dim` (нейтральный) |
| `cnc` | ЧПУ | фреза/спираль | `dim` |
| `laser` | Лазер | луч/искра | `dim` |
| `electronics` | Электроника | плата/чип | `dim` |
| `software` | Код | `< >`/терминал | `dim` |
| `woodworking` | Дерево | доска/стружка | `dim` |
| `metalworking` | Металл | токарный резец | `dim` |

- **Тон — приглушённый (`dim`) для всех.** Craft — **классификация, не статус срочности** (принцип «яркость=важность», [status.alerts.md](status.alerts.md)): ремесло — фон-информация, не алерт. Бейдж не должен конкурировать за яркость с зелёным primary (readme §2). Не раскрашиваем ремёсла в разные яркие цвета (демо-акценты циан/сталь мы осознанно не берём, readme «приоритет источников»); различитель — **глиф + метка**, а не цвет-код. (Если позже понадобится цветовая разводка ремёсел — это отдельное решение палитры, не MVP; оставляем задел `tone` в реестре.)
- **Неизвестный slug** (появился craft, которого нет в реестре) — деградация: бейдж с меткой = сам slug (или «Другое») + нейтральный глиф-точка, тон `dim`. Не падаем, не прячем молча (сигнал «завести метку»).
- **Только метка / только глиф** — компактный режим для тесных мест (плитка каталога): на карточке допустим **глиф без текста** (иконка ремесла в углу превью), на странице модели — полный «глиф + метка». Точный порог — на реализацию.

### 2.3 Craft-бейдж на карточке каталога (⟵ дополняет §2.3 marketplace.full.md)

Анатомия плитки §2.3 базы **не меняется**; craft-бейдж — **новый необязательный элемент**, появляется только при мульти-ремесле (§2.1):

- **Место** — в углу превью (`.homeModelThumb`), поверх слоёного стека, как статусная наложка (§2.3 п.5 базы), но в **другом углу**, чтобы не спорить со `StatusPill` обработки. Компактный режим: **глиф ремесла** (без текста — на плитке тесно), tooltip/aria = полная метка.
- **Приглушённо** (`dim`, полупрозрачное стекло), не перетягивает внимание с превью-героя.
- Пока моно-ремесло — бейджа на плитке нет (§2.1). Карточки печати выглядят ровно как в v2.

**Взаимодействие с craft-фильтром (§5.1):** тап по бейджу — опционально ведёт в каталог с фильтром этого ремесла (`#/market?craft=cnc`), как тап по тегу (§2.3 базы). Не обязателен для MVP-задела (фильтр сам появляется при мульти-ремесле).

### 2.4 Craft-бейдж на «парящей» странице модели (⟵ дополняет §2.2 marketplace.v2.md)

На странице модели место больше — полный бейдж «глиф + метка». Вписывается в **парящую** правую колонку (§2.2 v2), приглушённо, без карточки-подложки:

- **Место** — в строке `Eyebrow` (§2.2 п.1 v2: «STL → 3MF · статус»). Дополняем: **craft-бейдж + формат-источник + статус-пилюля** в одном парящем ряду сверху правой колонки. Порядок чтения: «какое это ремесло → в каком формате → в каком статусе».
- Пример строки (мульти-ремесло): `[⬦ Печать]  STL → 3MF  · [готово]` — бейдж слева, приглушённый, парит (uppercase-трекинг Eyebrow).
- Моно-ремесло — бейджа нет, строка = как в v2 («STL → 3MF · статус»).
- **Смешанный проект** (когда появится): primary-craft (`models.craft`) — основной бейдж в Eyebrow; вторичные ремёсла (выведенные из ролей файлов, эпик §2 п.3) — **не** отдельными бейджами в шапке, а **через группы блока «Файлы проекта»** (§3): наличие группы `cnc_program` уже говорит «тут есть ЧПУ-часть». Не дублируем ремесло дважды (бейдж + группа) — бейдж = primary, группы файлов = состав. Это держит шапку чистой (readme §2).

## 3. IA страницы проекта: блок «Файлы проекта» (артефакты по ролям)

> **Дельта эпика «Проект = git» (MF-514) — см. [projects.page.md](projects.page.md) §9–11.** После пере-решения «git = субстрат, не метафора» (CTO 2026-07-07) файлы проекта живут в настоящем bare-репозитории, а не в S3. Группы-по-роли этого раздела теперь **проецируются на реальные папки репо** (`print/ pcb/ code/ docs/ …`, конвенция — projects.page.md §9); добавлены рендер дерева файлов и истории коммитов (projects.page.md §11). Роли/группировка/принцип «дремлет при одной роли» ниже — **в силе**; git-дельта их уточняет (источник = дерево репо), не переписывает.

Ядро «проектности» витрины. Сегодня у печатной модели файлы — `source` (STL/STEP) + `canonical_3mf` + `preview`. Проект — та же страница, но блок файлов **сгруппирован по ролям**, и группы масштабируются на ремёсла (`cnc_program`, `drawing`, `gerber`, `code_archive` — реестр ролей задан эпиком §2 п.2). Это **новый блок** на «парящей» странице модели (§2 v2), не ломающий её раскладку.

### 3.1 Реестр ролей файлов (slug → группа / метка / действие)

Роли `model_files.role` (check-констрейнт, расширяется по ремёслам, эпик §2 п.2). UI группирует файлы по **семантической роли**, а не по расширению. Словарь-реестр (`fileRoleRegistry`, GAP §7), по образцу `craftRegistry`:

| role slug | RU-метка группы | Что это | Ремесло | Действие в UI |
|---|---|---|---|---|
| `source` | Исходник | Авторский файл (STL/STEP/DXF/SVG…) | любое | Скачать |
| `canonical_3mf` | Готово к печати (3MF) | Сжатый канонический 3MF после конвертации | `3d_printing` | **Скачать 3MF** (primary, §3.4 v2) |
| `preview` | — (не в списке файлов) | GLB для вьюера — **не** файл-артефакт, а ассет сцены | — | (вьюер «покрутить», §12 базы) |
| `thumbnail` | — (не в списке) | webp-постер — ассет каталога, не артефакт | — | (превью-стек, [model.preview.md](model.preview.md)) |
| `cnc_program` | Программа ЧПУ | G-code / NC-файл для станка | `cnc` | Скачать (как есть, §3.4) |
| `drawing` | Чертёж / раскрой | DXF / SVG (лазер / фреза / чертёж) | `laser`/`cnc` | Скачать |
| `gerber` | Плата (Gerber) | Gerber-набор печатной платы | `electronics` | Скачать |
| `code_archive` | Код | Архив кода / прошивка / конфиги | `software` | Скачать (см. блок «Код» §4) |

**Важно (эпик §2 п.4, честный UI):** `preview`/`thumbnail` — **не** файлы-артефакты в списке «Файлы проекта», это ассеты презентации (вьюер/превью-стек, [model.preview.md](model.preview.md)). В блоке файлов показываем **только скачиваемые артефакты** ремесла — то, ради чего пришли: исходник, готовый 3MF, G-code, чертёж, Gerber, код. Не путать «файлы для скачивания» с «ассетами для показа».

### 3.2 Композиция блока «Файлы проекта» (⟵ дополняет §2.2 marketplace.v2.md)

Полноширинная (или в правой колонке — на реализацию) секция страницы модели, **под** блоком действий/описания (§2.2 v2), в «парящей» стилистике: заголовок парит, сами файлы-строки — приглушённое стекло (артефакт кликабелен → лёгкое стекло-аффорданс уместно, как кнопки §2.1 v2).

**Моно-артефактный случай (весь MVP-печать) — блок не разворачивается в «группы».** Когда у модели только `source` + `canonical_3mf`, это **не** «проект из многих частей» — рисовать заголовок «Файлы проекта» с одной группой = перегруз. Дизайн-правило:

> Пока у публикации **одна** содержательная роль-группа (типичная печатная модель: исходник + готовый 3MF) — файлы живут **в существующих действиях** (primary «Скачать 3MF» §3.4 v2 + строка тех.метаданных «Формат» §2.2 п.7 v2). Отдельный блок «Файлы проекта» **не рисуем**. Он появляется, когда ролей-групп **больше одной** (проект реально мульти-артефактный: печать + ЧПУ, или + код).

Это тот же принцип, что §2.1 (бейдж скрыт при моно-ремесле): **структура готова, но показывается только когда есть что структурировать.** Печатная витрина MVP выглядит ровно как v2 — блок «Файлы проекта» дремлет до второго артефакта.

**Развёрнутый блок (мульти-артефактный проект, задел):**

```
┌─────────────────────────────────────────────────┐
│ ФАЙЛЫ ПРОЕКТА                          (Eyebrow) │  ← парит
├─────────────────────────────────────────────────┤
│ ▸ Готово к печати                                │  ← группа-роль (метка из реестра §3.1)
│    ⬦ model.3mf   · 2.4 МБ   [ Скачать 3MF ]      │  ← primary внутри группы
│ ▸ Исходник                                       │
│    ⬦ model.stl   · 8.1 МБ   [ Скачать ]          │
│ ▸ Программа ЧПУ                                   │  ← появляется при cnc-артефакте
│    ⬦ part.nc     · 120 КБ   [ Скачать ]          │
│ ▸ Код                          (блок §4)         │  ← вложения code_archive + задел-линк
└─────────────────────────────────────────────────┘
```

- **Группа** — `Eyebrow`-подзаголовок (метка роли из реестра §3.1) + список файлов группы. Порядок групп — по «полезности для потребителя»: сначала «Готово к печати/использованию» (то, что качают чаще), потом «Исходник», потом ремесло-специфичные, «Код» — последним (§4).
- **Строка файла** — глиф-роль + имя файла + размер (`size_bytes`, человекочитаемо) + кнопка действия (стекло, §2.1 v2). Формат/роль читаются из данных, не хардкодятся.
- **Один primary сохраняется (readme §2):** «Скачать 3MF» остаётся единственным сплошным-зелёным (§3.4 v2); скачивания прочих артефактов (STL, G-code) — **нейтральное стекло**, не зелёные. Зелёный якорь страницы — один.
- **Честность (эпик §2 п.4):** портал НЕ обещает конвертацию/просмотр не-печатных форматов на MVP. G-code/DXF/Gerber хранятся и **скачиваются как есть** — кнопка «Скачать», без «Открыть во вьюере», без «Отправить на станок» (это вне эпика). Никаких обещаний конвейера, которого нет.

### 3.3 Мобильная адаптация блока файлов

Группы — вертикальный стек (одна колонка), каждая группа — заголовок + строки файлов на всю ширину, кнопки-действия ≥48px (тач-таргет, readme §5). Порядок = §3.2 (полезное сверху). Блок — под действиями/описанием в мобильном стеке (§2.3 v2).

## 4. Блок «Код»: вложения `code_archive` + задел под GitVerse (без анонса)

Отдельный подраздел блока «Файлы проекта» (§3) для ремесла `software`. **Решение Валерия зафиксировано** ([domain.model.md](../epics/domain.model.md) § Решённые вопросы п.3, эпик §2 п.5): **GitVerse-интеграция будет, но публично НЕ анонсируем и в схему не тянем.** На старте код-артефакты — вложения `code_archive`; блок проектируем так, чтобы позже принять линк на репозиторий **без перевёрстки**.

### 4.1 Что показываем сейчас (MVP)

- **Блок «Код»** появляется только когда у проекта есть файл роли `code_archive` (та же логика «структура включается от данных», §2.1/§3.2). У печатной модели без кода — блока нет.
- **Композиция** — как группа §3.2: `Eyebrow` «Код» + список вложений (архив/прошивка/конфиг: глиф `< >` + имя + размер + «Скачать»). Приглушённое стекло, скачивание как есть — тот же честный паттерн, что прочие артефакты (§3.2): портал хранит и отдаёт файл, не запускает и не собирает код.
- **Никакого упоминания GitVerse** нигде в UI (текст, тултип, иконка) — прямое требование Валерия. Для пользователя это просто «файлы кода к проекту».

### 4.2 Задел под будущий линк-репозиторий (место, не функция)

Ключевое требование эпика — «заложить место под будущий линк на репозиторий без перевёрстки». Проектирую **резерв композиции**, а не активный элемент:

- Блок «Код» устроен как **список источников кода**, где вложение (`code_archive`) — **один тип** источника. Второй тип (будущий линк на репозиторий) встанет **в тот же список той же строкой** — «глиф-репозиторий + имя репо + [Открыть]» вместо «[Скачать]». Раскладка группы (§3.2) уже это принимает: строка-источник + действие.
- Так добавление линка позже — это **новая строка в существующем списке**, не новый блок и не переверстка. Композиция §3.2 инвариантна к типу источника (файл vs линк).
- **Сейчас линк-строку НЕ рисуем** (нет интеграции, нет анонса). Только фиксирую: место для неё = ещё один элемент списка «Код», глиф+имя+действие. Ноль обещаний в UI до того, как Валерий откроет интеграцию.

**Итог:** блок «Код» на MVP = группа вложений `code_archive` (скачать как есть, без GitVerse-упоминаний); архитектурно = список источников кода, куда будущий репо-линк добавляется одной строкой. Требование «без перевёрстки» выполнено композиционно.

## 6. Инварианты (проверяются на приёмке Architect)

1. **Терминология:** UI держит «Модели» до второго живого ремесла; переключение — одномоментная смена словаря (§1.3), одна витрина (не два раздела §1.2). Мини-словарь форм — задел стадии 2 (значение = «модель»).
2. **Craft-бейдж скрыт при моно-ремесле** (§2.1): на MVP-печати бейджей нет нигде; появление второго `craft` «зажигает» их автоматически от данных, без перевёрстки. Тон — `dim` (различитель = глиф+метка, не цвет).
3. **Блок «Файлы проекта» дремлет при одной роли-группе** (§3.2): типичная печатная модель показывается как в v2 (primary «Скачать 3MF» + мета «Формат»); группы по ролям разворачиваются только у мульти-артефактного проекта.
4. **Честный UI (эпик §2 п.4):** не-печатные артефакты (G-code/DXF/Gerber/код) — «Скачать как есть», без «Открыть»/«На станок»/конвертации, которых нет.
5. **Блок «Код»** = вложения `code_archive` (скачать), **ноль упоминаний GitVerse** (§4.1); задел под репо-линк = ещё одна строка в списке источников кода (§4.2), сейчас не рисуется.
6. **Один зелёный primary на кадр сохранён** (readme §2): каталог → «Добавить»; страница модели → «Скачать 3MF» (единственный сплошной-зелёный, даже когда в блоке файлов много скачиваний — прочие нейтральное стекло).
7. **Не конфликтует с marketplace.v2 / model-preview / MF-464:** только дополняет; craft-бейдж — наложка поверх превью-стека, не правка пайплайна; craft-фильтр — новый блок сайдбара по образцу тегов.
8. **Всё от данных, не от флагов:** видимость бейджей/фильтра/групп определяется значениями `craft`/`role` в выборке (§2.1), а не ручным переключателем — портал «взрослеет» в проекты сам, когда появляется контент второго ремесла. Исключение — терминология (§1.3): её переключает Валерий явно.
