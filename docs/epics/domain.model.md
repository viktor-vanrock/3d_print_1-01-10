# EPIC: Доменная модель — расширяемое ядро БД

**Статус:** принято как архитектурный ориентир (Architect), открытые вопросы — Валерию
**Контекст:** поручение Валерия в MF-336 — «продумать все элементы в базе заранее». Стартуем с 3D-печати и принтеров, но растём в другие станки (ЧПУ, лазер, токарка, дерево/металл) и в Reddit-подобное DIY-комьюнити России (включая тех, кто пишет код). См. `docs/product/vision.md` («Три кита», п.3), `docs/product/features.md` (v2 «Расширение за пределы 3D-печати», «Клубы/комьюнити-механики»).

Этот документ — не «построить всё сейчас», а карта доменов + принципы, чтобы таблицы, которые мы заводим уже сегодня (MF-336 и далее), не пришлось ломать при росте.

## Принципы

1. **Ядро не знает про 3D-печать.** 3D-печать — первое значение справочника, а не зашитая ось системы. Никаких `print_*`/`stl_*`/`printer_*` имён в общих таблицах, колонках и модулях (исключение — уже живущая `user_printers`, см. ниже).
2. **Справочники и `text + check` вместо жёстких enum-типов** там, где таксономия будет расти: ремёсла, виды станков, виды материалов, роли файлов, форматы. `check`-констрейнт расширяется одной миграцией; Postgres-`enum` и колонки-зависимости — дороже.
3. **Три слоя, не смешивать:** предметка мастерской (станки, материалы), контент (модели, make'и, посты), социальный слой (комьюнити, комментарии, голоса, теги). Связи между слоями — явные FK/связки, а не «супер-таблица контента».
4. **Полиморфные связи — явной парой `(subject_type, subject_id)`** с `check` по списку типов: комментарии/голоса/теги должны уметь цепляться и к посту, и к модели, и к make'у, не плодя по таблице на комбинацию.
5. **`jsonb` — для видо-специфичных атрибутов** (спеки станка, свойства материала), реляционные колонки — только для того, по чему ищем/джойним/сортируем.
6. **Единые конвенции:** `id uuid default gen_random_uuid()`, `created_at`/`updated_at timestamptz`, `status text + check`, — как в `users` (`apps/api/src/db/schema.ts`).

### Ремёсла (`crafts`)

Ключевой справочник роста: `3d_printing`, `cnc`, `laser`, `woodworking`, `metalworking` (токарка), `electronics`, `software`. Поля: `slug`, `name`, `position`, `status`. На него будут ссылаться комьюнити, каталог станков, материалы, категории моделей. Заводить таблицу — при втором ремесле; до этого достаточно `craft text not null default '3d_printing'` (slug) в новых таблицах — миграция на FK тривиальна, пока значение одно.

### Станки: не «принтеры», а `machines`

- **Производители — отдельная сущность `vendors`** (`slug`, `name`, `verified`), не text-колонка: вендор — субъект авто-комьюнити («глобальный саб Creality», см. ниже) и точка агрегации каталога. `user_printers.brand text` позже мигрирует на `vendor_id`.
- **Каталог** (будущий MF-32): таблица `machines` — `craft`, `kind` (`fdm_printer` | `sla_printer` | `cnc_router` | `cnc_lathe` | `laser_cutter` | …), `vendor_id`, `model`, `specs jsonb` (характеристики), `status`. Каталог принтеров = первая заливка `machines`, НЕ отдельная таблица `printers`.
- **Класс подключаемости — свойство записи каталога** (решение Валерия, 2026-07-05). Станки делятся на три класса, это колонка `integration text + check`:
  - `live` — коннектор к сервису работает (принтеры с готовой интеграцией);
  - `in_development` — демон/коннектор пишется (принтеры и ЧПУ на подходе; для программируемых станков портал будет хранить их форматы файлов — покрыто расширяемостью `source_format`/`role`);
  - `none` — непрограммируемые станки (токарка и т.п.): живут в каталоге как справочная запись + комьюнити вокруг, добавляются вручную.
- **Происхождение записи каталога**: `source` (`official` | `community`) + `verified boolean` — непрограммируемые и редкие станки добавляет сообщество, модерация подтверждает. Тот же смысл, что `verified=false` в живой `user_printers` (сигнал спроса для MF-32).
- **Собственность** — «добавить в собственность» касается ЛЮБОГО станка, не только принтеров: целевая таблица `user_machines` (сейчас — live `user_printers`, остаётся как есть на MVP; её `printer_id uuid` получил FK на `machines.id` 2026-07-06, см. «Каталог станков (MF-32) — реализовано» ниже; переименование таблицы и заполнение `kind='fdm_printer'` для существующих строк — при втором виде станка). Новые printer-специфичные колонки в неё не добавлять — видовое уходит в `jsonb`-спеки.
- **Материалы**: `materials` — `craft`, `kind` (`filament` | `resin` | `plywood` | `aluminum` | …), `vendor_id`, `name`, `specs jsonb`. Филамент — частный случай, не корневая сущность. Профили «связка станок+материал» (наш кит №1) строятся поверх этих двух таблиц.

### Каталог станков (MF-32) — реализовано

Схема задеплоена 2026-07-06 (`apps/api/src/db/schema.ts`) — только каталожная часть эпика MF-32 (canonical-запись станка + провенанс + очередь дедупа + календарь релизов). Агенты-парсеры, вендор-коннекторы (Bambu LAN-MQTT/Prusa Connect) и бизнес-логика API-резолвера — вне зоны ответственности этой миграции, реализуются отдельно поверх готовой схемы.

- **`vendors`** — `slug`, `name`, `verified`. Как и описано выше: вендор не text-колонка, точка агрегации каталога и будущего авто-комьюнити.
- **`machines`** — каноническая запись. `craft`/`kind` — text+check (union уже включает `cnc_router`/`cnc_lathe`/`laser_cutter`, чтобы не трогать констрейнт при первом ЧПУ/лазере), `vendor_id`, `model`, `aliases text[]` (для RU/EN дедупа и ребрендов), `specs jsonb` (кинематика/объём печати/экструзия/термо/материалы/электроника/цена/медиа — полный список полей см. в описании MF-32 § «Схема данных принтера»; реляционных колонок под них не заводим, только то, по чему реально фильтруем: `vendor_id`/`craft`/`kind`/`integration`/`source`/`verified`/`status`), `schema_version` (версионирование канонической записи), `integration` (`live`/`in_development`/`none`, решение Валерия 2026-07-05), `source` (`official`/`community`) + `verified`, `field_provenance jsonb` (карта `{field: {source, source_url, ts, confidence}}` — провенанс без отдельной EAV-таблицы), `status` (`active`/`quarantined`/`archived` — карантин для записей, не прошедших plausibility-проверку). Индексы: `vendor_id`, `(craft, kind)`, частичный по `status='quarantined'` (очередь ревью), GIN по `aliases` (blocking-стадия дедупа) и GIN `jsonb_path_ops` по `specs` (фильтры резолвера «кинематика/объём/материалы/enclosed»). Уникальности по `(vendor_id, model)` нет намеренно — дедуп ребрендов/алиасов решает entity-resolution пайплайн (blocking→matching→merge), не DB-констрейнт.
- **`user_printers.printer_id`** получил FK на `machines.id`, добавленный как `NOT VALID` (additive, безопасно при автоприменении на старте сервера независимо от текущих данных в проде — существующие строки не проверяются, enforcement только для новых/изменённых). `VALIDATE CONSTRAINT` — отдельным шагом после того, как Ops подтвердит отсутствие «осиротевших» `printer_id` (протокол expand→migrate→contract).
- **`machine_candidates`** — сырые записи от источников (слайсер-профили/каталоги/вендор-сайты) до слияния в канон: `source`, `source_url`, `external_ref`, `raw jsonb`, `content_hash` (идемпотентный ре-ингест по расписанию), `matched_machine_id`, `confidence`, `status` (`pending`/`matched`/`merged`/`rejected`/`quarantined`). Одновременно это и очередь дедупа, и очередь ревью — `status='pending'` с низким `confidence` = спорное слияние на ручной аппрув. `unique (source, external_ref)`.
- **`release_events`** — календарь релизов: `machine_id` nullable (анонс может существовать до полной каноничной записи), `vendor_id`, `model_name` (текстовый дубль на случай, если матчинг ещё не проставил `machine_id`), `status` (`announced`/`preorder`/`shipping`/`eol`), даты (`announced_at`/`preorder_at`/`ship_at`/`eol_at`), `source_url`.

Проверено локально (docker compose Postgres 16): миграция идемпотентна (повторный прогон — чисто NOTICE/skip, без ошибок), FK `NOT VALID` пропускает существующие данные, но продолжает блокировать некорректные новые вставки (проверено вручную), GIN-индекс по `specs` и `aliases` корректно фильтрует по вложенным полям.

Не сделано этой миграцией (сознательно, вне территории Data): бутстрап-импорт ≥300 моделей из слайсер-профилей, агенты-парсеры на расписании, коннекторы Bambu/Prusa, публичный/внутренний API-резолвер, дашборд покрытия. Это Back/Fullstack-реализация поверх готовой схемы — следующий шаг для Lead: разбить оставшуюся часть MF-32 на карточки по направлениям (парсеры, резолвер, коннекторы, календарь-фид, дашборд).

### Агент-парсер свободного HTML (MF-649, декомпозиция MF-406) — реализовано

`apps/giga/src/giga/catalog` — LLM-экстрактор для источников без структурного JSON/таблицы (вендор-ньюсрумы: те же RSS-фиды, что уже гоняет `giga.calendar` под календарь релизов, — один текст статьи параллельно проверяется двумя промптами). Пишет НАПРЯМУЮ в `machine_candidates`/`ingest_runs` через psycopg (`db.py`), не через TS `runIngest` — `apps/api`/`apps/giga` интегрируются только общим `DATABASE_URL`, без HTTP между сервисами (тот же паттерн, что `generations`/`release_events`; см. `apps/api/src/generations/contract.ts`), тот же идемпотентный контракт (`unique(source, external_ref)` + `content_hash`, статус сбрасывается в `pending` при изменившемся контенте). `raw = {vendor, model, specs}` — та же форма, что структурные TS-адаптеры (`cura-definitions`/`sovol3d-store`), читается тем же TS-резолвером (`apps/api/src/modules/catalog/infrastructure/resolve/run.ts::parseRaw`) без доработок на стороне резолвера. `confidence` пишется в колонку (не только внутрь `raw`) — резолвер уже использует её как provenance-confidence при создании новой канонической записи и при разрешении конфликтов полей merge.

Устойчивость к галлюцинации (домен-принцип «вход враждебен» + «качество измеряется»): системный промпт требует опускать поле, если оно не названо в тексте явно (не гадать «типичное для класса» значение); числовые `specs`-поля дополнительно фильтруются на вменяемость теми же границами, что `apps/api/src/modules/catalog/infrastructure/resolve/plausibility.ts` (`0 < build_volume ≤ 2000мм`, `0 < nozzle_temp ≤ 500°C`, `0 < bed_temp ≤ 200°C`) — implausible-поле дропается точечно, кандидат (vendor+model) не выбрасывается целиком. Golden-set (`apps/giga/tests/golden/machine_candidate_extraction.py`) фиксирует регрессионный якорь на реальных статьях, включая мусорный кейс (страница не о конкретной модели → `is_machine_page=false`, `machines=[]`).

Известный побочный факт (не блокер этой карточки, для осведомлённости Lead/CTO): помимо этого пайплайна (`apps/api/src/modules/catalog/infrastructure/ingest`+`apps/api/src/modules/catalog/infrastructure/resolve`+теперь `apps/giga/src/giga/catalog`) в репо существует независимый `apps/scout` (MF-623/627/720) — свой резолвер (`apps/scout/src/scout/resolver`), свои источники (`vendor_whitelist`/`slicer_profiles`/`spoolman`), свой `raw`-словарь ключей (`vendor_slug`/`model_name` вместо `vendor`/`model`), тоже пишущий в `machine_candidates`. Обе линии совместно используют таблицу, но НЕ совместимы по форме `raw` между своими резолверами — `apps/scout`'s резолвер explicitly читает оба формата (generic dispatch, см. `apps/scout/src/scout/resolver/normalize.py`), а TS-резолвер (`apps/api/src/modules/catalog/infrastructure/resolve`) — только свой (`vendor`/`model`). Не разбирался глубже (вне скоупа MF-649) — вероятная параллельная реализация одного и того же эпика.

### Ownership contract `machine_candidates` v1 (MF-1513, решение)

`machine_candidates` остаётся **одной** очередью и одним сырым входом в
канон `machines`; второй канон, отдельная очередь или смена merge-алгоритма
этим решением не вводятся. Владелец схемы, миграций и DB-row-контракта —
**Data**. Логический владелец каждой строки — ровно один из `Catalog` или
`Scout`, вычисляемый по точному `source`. Логический `namespace` в v1 —
производное от `source`, а не новая колонка: это сохраняет
`unique(source, external_ref)` и обратную совместимость существующих строк.

Версия контракта: `machine_candidate_ownership.v1`. Изменение списка source
family, формы `raw` или разрешённых переходов требует аддитивной следующей
версии контракта и совместного изменения шва, а не fallback «попробовать
чужой резолвер».

| Namespace / source family | Логический владелец и формат `raw` | Допустимые состояния | Единственный predicate claim/filter |
|---|---|---|---|
| `catalog.v1`: `cura-definitions`, `sovol3d-store`, `giga-free-html` | `Catalog`; `raw={vendor, model, specs}`. `giga-free-html` принадлежит Catalog по форме и резолверу, хотя продюсер запущен в `apps/giga`. | На входе `pending`; штатный резолвер читает только `pending`, может оставить `pending` для review либо записать `merged`, `rejected` или `quarantined`. `matched` остаётся допустимым состоянием очереди для совместимости и ручного review, но не делает строку claimable. | `status = 'pending' AND source IN ('cura-definitions', 'sovol3d-store', 'giga-free-html')` |
| `scout.v1`: `vendor_whitelist`, `slicer_profile` | `Scout`; собственный словарь `raw` (`vendor_slug`/`model_name` и поддерживаемые Scout варианты). | На входе `pending`; Scout claim-ит только `pending` и завершает текущими ветками `merged`, `matched` либо `rejected`. `quarantined` допустим как состояние общей очереди, но не claimable без отдельного решения. | `status = 'pending' AND source IN ('vendor_whitelist', 'slicer_profile')` |

`source` вне этой матрицы не принадлежит ни одному резолверу: ни Catalog, ни
Scout не имеют права его claim-ить, менять `status`, `matched_machine_id` или
`machines`. Продюсер обязан отклонить такую запись до записи с
`source_owner_unmapped`; уже существующие неизвестные строки не переписываются
массово и остаются предметом отдельной сверки Data. Это намеренно строже, чем
определять владельца по удачному разбору `raw`: форма данных не является
разрешением обработать чужой namespace.

**Переходы и идемпотентность.** `pending → pending` допустим только для
сохранения review-контекста (неоднозначный match/конфликт полей); терминальные
переходы — в перечисленные в матрице состояния. Любой claim выполняется в
короткой транзакции с predicate выше и `FOR UPDATE SKIP LOCKED` либо
эквивалентным атомарным guard на `id + source + status`; lock не является
долгоживущим статусом. Повторный claim не меняет строку и возвращает
`claim_not_pending`/`claim_conflict`; повторный ingest с тем же
`(source, external_ref, content_hash)` — no-op и не сбрасывает результат
резолвера. Изменение содержимого сохраняет уже принятый source-specific
ingest-путь; эта карта не вводит единый reset или rewrite статусов.

**Граница, авторизация и ошибки.** Это внутренний DB-row/job-шов, публичного
HTTP API и межсервисного event bus в v1 не появляется. Data выдаёт сервисным
процессам права только на их source family; пользовательская сессия не даёт
права claim. Ручной API review обязан применять тот же namespace guard, что и
его резолвер. Стабильные причины отказа: `source_owner_unmapped`,
`ownership_mismatch`, `claim_not_pending`, `claim_conflict`,
`invalid_raw` и `candidate_not_found`; первые две никогда не меняют кандидата
или канон. `invalid_raw` и результат plausibility остаются семантикой
собственного резолвера, не поводом передать строку соседу.

**Audit и наблюдаемость.** Формат события фиксируется как
`machine_candidate.audit.v1`; transport в v1 — структурированный audit-log,
не новая шина. Обязательные виды: `ingested`, `claim_acquired`,
`claim_rejected`, `status_transition`, `released` и `error`. Поля:
`event_id`, `occurred_at`, `candidate_id`, `namespace`, `owner`, `source`,
`from_status`, `to_status`, `actor`, `reason`, `correlation_id` и
`idempotency_key`; для отсутствующего перехода статусы допускаются `null`.
Метрики имеют только низкокардинальные labels `owner`, `source_family` и
`outcome`: очередь `pending`, claim/reject/error и переходы. `candidate_id`
остаётся в логе, не в label. Доставку и одинаковую сериализацию audit берёт
отдельная карта MF-1518.

**Совместимость и rollout.** Контракт не меняет merge priority/точный
normalized-name merge и provenance из MF-650 и MF-720. Существующие
`cura-definitions`, `sovol3d-store`, `giga-free-html` продолжают Catalog
контур; результаты MF-623 (`vendor_whitelist`) и MF-627 (`slicer_profile`)
остаются Scout-контуром. Сначала добавляются schema/index или только
производный guard по результату MF-1514 и regression fixtures; затем Scout
ограничивает claim своей allowlist, Catalog — своей, после чего включается
audit. Такой порядок прекращает захват Catalog строк Scout без массовой
миграции. Rollback — откат кода/индекса, без переписывания `source`,
`external_ref`, `raw`, статусов или `machines`; версия mapping остаётся
зафиксирована в документе до следующего совместимого решения.

Контракт не связывает account с printer, не читает и не меняет
`config_fingerprint`/`slice_key` и не создаёт P2P-канал. Поэтому он сохраняет
account↔printer identity и возможность будущего P2P из
`docs/architecture/data.fragmentation.md`, не реализуя P2P в v1. Исполнение
границы разделено между владельцами шва: Catalog — MF-1515/MF-1516, Scout —
MF-1517; schema/index — MF-1514, единый audit — MF-1518.

### Планировщик боевых агентов (MF-652, декомпозиция MF-406) — реализовано

Собранный до этой карточки побочный факт оказался активным багом, не только архитектурной шероховатостью: TS-резолвер (`runEntityResolution`) в штатном (безаргументном, под расписание) режиме забирал ВСЮ очередь `status='pending'` без фильтра по `source` — значит, при одновременном расписании обеих линий он забирал бы себе и scout-кандидаты, не мог распарсить их `raw` (`parseRaw` понимает только `vendor`/`model`) и рубил их `status='rejected'` (см. `invalidCandidates`-ветку) ДО того, как их увидит `apps/scout`'s резолвер — тихая потеря чужой очереди при первом же совместном прогоне по расписанию. Пофикшено точечно (`apps/api/src/modules/catalog/infrastructure/resolve/run.ts`): штатный полноочередной прогон фильтрует `source = any(KNOWN_SOURCES)` (`cura-definitions`/`sovol3d-store`/`giga-free-html` — то, что этот резолвер реально умеет разобрать), точечный прогон по `ids` (тесты, ручной ре-прогон) фильтр не применяет — вызывающий код сам отвечает за выбор id. Тест-регрессия — `run.test.ts` § «full-queue run (no ids) leaves candidates from unknown sources... untouched».

Это устраняет только столкновение на уровне *claim из очереди*, НЕ более широкий факт двух несогласованных matching/similarity-алгоритмов поверх одного `machines`-канона (см. абзац выше) — та часть остаётся открытой для Lead/CTO, но перестала быть безопасной молчать: `apps/api/deploy/portal.catalog-{ingest,resolve}.{service,timer}` и `apps/giga/deploy/portal.giga-catalog.{service,timer}` теперь готовы к установке Ops, а `apps/scout` уже имеет свои юниты (`apps/scout/deploy/`) — обе линии реально могут оказаться на одном VDS-расписании одновременно, не только гипотетически.

### Контент

- **`models`** — цифровой дизайн-файл в общем смысле: сегодня STL/STEP/3MF, завтра DXF/SVG под ЧПУ/лазер. Требования к Фазе 1 — ниже. Решение Валерия (2026-07-05): **маркетплейс моделей — отдельная сущность от принтеров**, в будущем полноценная страница (поиск, покупка/продажа, обсуждение, **форки**). Мост к станкам — кнопка «отправить в печать»: выбираешь свой станок из собственности → задание уходит на него (будущая сущность «задание на печать»: модель + `user_machine`, поверх очереди из `docs/architecture/readme.md`). Форки — self-FK на исходный проект (родословная нужна для лицензий/атрибуции). Реализовано MF-514/MF-516 (`docs/epics/project.git.md` §10.1) под именем `models.forked_from`, не `parent_model_id` — базовый форк подтянут в v1 решением «проект = git» (server-side clone), рабочее имя из этого наброска не используется.
- **`makes`** — фото готового изделия: FK на модель + (опционально) станок юзера + материал. Имя — `makes`, не `prints`: make бывает и фрезерованный.
- **`posts`** (Reddit-слой, v2) — `kind` (`text` | `link` | `question` | `showcase`), тело, автор, `community_id nullable` (пост живёт в клубе или в профиле), опциональная связь с моделью (пост «несёт» модель). Артефакты «тех, кто пишет код» (конфиги Klipper, прошивки, скрипты) на старте — посты с вложениями, отдельную сущность заводим только по спросу.

### Комьюнити (v2, но форму фиксируем сейчас)

**Ключевое решение Валерия (2026-07-05): комьюнити привязаны к сущностям каталога** (саб модели станка, глобальный саб вендора, саб ремесла), а не только рукотворные клубы. **Вступление — opt-in, не автоматическое** (уточнение 2026-07-05): при добавлении станка в собственность юзеру задаётся вопрос «Хотите стать частью комьюнити?» с чекбоксами — саб вендора и саб модели (если на вендора уже подписан — показываем только модель). Не хочет — подписки нет. **Владение и членство — разные факты**: в глобальную статистику владельцев по модели/вендору юзер попадает независимо от подписки (см. «Статистика владения» ниже).

- **`communities`** — `slug`, `name`, `kind` (`machine` | `vendor` | `craft` | `custom`), привязка к предметке через `(subject_type, subject_id)` (→ `machines.id`, `vendors.id`, `crafts` — для `custom` пусто), `description`, `visibility`, `created_by nullable` (у каталожных сабов создателя нет).
  - Каталожный саб создаётся **лениво** — при первой подписке (не при первом владельце и не сидом на весь каталог: пустые сабы-призраки не нужны).
  - `unique (kind, subject_type, subject_id)` — один каталожный саб на сущность.
- **`community_members`** — `role` (`owner` | `moderator` | `member`) + `source` (`machine_prompt` | `manual`) — откуда пришла подписка: из вопроса при добавлении станка или руками. Выйти можно; продажа/удаление станка членство не рвёт. У каталожных сабов нет `owner`-юзера — модерация по общим правилам портала, пока не назначен модератор.
- **`comments`** — древовидные (`parent_id`), цепляются к `(subject_type, subject_id)`: пост, модель, make.
- **`votes`** — стрелки вверх/вниз как на Reddit (подтверждено 2026-07-05): `(user_id, subject_type, subject_id, value ±1)`, `unique(user_id, subject_type, subject_id)`. Карма — агрегат, не колонка-счётчик, который врёт; формула репутации (голоса + проверяемый опыт) — открытый вопрос, на схему `votes` не влияет.
- **`tags`** — глобальные, связка через `(tag_id, subject_type, subject_id)`.

### Статистика владения (отдельно от подписок)

Решение Валерия (2026-07-05): считаем владельцев по модели/вендору **двумя ярусами** — оба выводятся из `user_machines` (`user_printers`), отдельных таблиц не нужно:

1. **Заявленные владельцы** — все строки собственности (юзер отметил «у меня такой»).
2. **Подтверждённые владельцы** — станок физически подключён (по IP) и модель определена автоматически. Сигнал уже есть в живой схеме: `user_printers.link_source='connector'` + `verified=true`. Это и есть «реальные владельцы, а не просто галочкой отметили».

Агрегаты (сколько владельцев у K1, сколько у Creality всего) — считаются запросом/materialized view по `user_machines`, не колонками-счётчиками.

### Три типа подключения принтера (сверка CTO, MF-864, 2026-07-10) — явная градация

Видение оператора требует **явной** трёхступенчатой градации того, как принтер попадает в парк
пользователя — она уже реализована в схеме (`user_printers.link_source`), но была размыта по трём
разным подразделам ниже. Фиксирую как одну таблицу-канон, дальнейшие изменения `link_source`
обязаны укладываться в неё:

| # | Тип | `link_source` | Что физически происходит | Сигнал владения | Где реализовано |
|---|---|---|---|---|---|
| (а) | Заявить «у меня есть» | `manual` | Юзер вручную отмечает станок из каталога, сети нет вообще | «Заявленный владелец» (см. «Статистика владения» выше) | Базовый v1, `user_printers` |
| (б) | Подключить по IP/вендор-API + слать печать | `connector` | Юзер вводит ключ вендорского облачного API (сегодня — Prusa Connect); портал синкает флот через вендора, не напрямую по локальному IP | «Подтверждённый владелец» (`verified=true`) | MF-646, § «Коннектор Prusa Connect» ниже |
| (в) | Накатить нашего агента | `agent` | Юзер ставит наш агент-процесс (Docker/Pi/ПК) в своей сети, агент держит исходящий relay-канал к порталу — портал никогда не имеет прямого доступа к железу | «Подтверждённый владелец» + живая телеметрия/команды (pause/resume/cancel, статус) | MF-390/MF-26, § «Парк устройств и агент» ниже |

Грейд растёт слева направо: (а) — только факт, (б) — синк состояния через чужое облако, (в) —
полный контроль (мониторинг+команды) через нашу инфраструктуру. Разные вендоры лежат на разных
ступенях одновременно (Prusa сегодня — (б), Klipper/Moonraker — (в) уже в Фазе 1 MF-26, Bambu LAN
ожидается как будущий `provider` того же (б)) — это не последовательные версии одного и того же
коннектора, а параллельное меню способов подключения, каждый вендор идёт по своей ступени по мере
готовности его API. UI обязан показывать пользователю все три опции для его станка, а не молча
выбирать одну (открытый вопрос UI/Front, не блокирует схему).

### Коннектор Prusa Connect (MF-646, Фаза 3 эпика MF-32/MF-407) — реализовано

Схема добавлена 2026-07-09 (`db/migrations/20260709020000_printer_connector_prusa.sql`) — первый вендор-коннектор из «Подтверждённых владельцев» выше: пользователь вводит API-ключ своего аккаунта Prusa Connect, сервер читает флот принтеров и сопоставляет каждый с `machines`. Аддитивно (expand), деструктива нет; вердикт Data принят 09.07 после форвард/роллбэк/форвард на локальном Postgres.

- **`printer_connections`** — одна строка на `(user_id, provider)`: ключ Prusa Connect выдаётся на аккаунт целиком (не на конкретный принтер), поэтому один ключ покрывает весь флот юзера. `provider` — `text + check` с единственным значением `'prusa_connect'` пока (принцип «text+check вместо enum», расширяется без миграции-ремонта при следующем вендоре). `api_key_enc bytea not null` — AES-256-GCM (`encryptIdentity`/`decryptIdentity`, `apps/api/src/auth/crypto.ts`), не plaintext; ключ хранится в Postgres (не в S3 — S3-слой в этом репо best-effort/опциональный, критический путь синка на нём заводить не стоит). `status` (`active`/`error`) + `last_error`/`last_synced_at` — статус последнего синка для будущего UI коннектора.
- **`user_printers.connection_id`** (FK → `printer_connections`, `on delete cascade`) + **`external_ref`** (id принтера у вендора) + **`status`** (сырой статус от вендора: `IDLE`/`PRINTING`/…) — коннектор-привязанные принтеры остаются той же таблицей `user_printers`, не отдельной сущностью: `link_source='connector'` + `verified=true` (уже описанный выше сигнал «подтверждённый владелец») срабатывает и здесь. Уникальный partial-индекс `user_printers_connection_ref_idx (connection_id, external_ref) where connection_id is not null` — идемпотентный ре-синк (`ON CONFLICT`) обновляет существующую строку вместо дублей при каждом ручном/фоновом ре-синке. `on delete cascade` на `connection_id` — намеренно: отключение аккаунта убирает коннектор-принтеры вместе с подключением (источник правды пропал), ручные записи (`link_source` другой) не трогает.
- `printer_id` (матчинг с каталогом) заполняется best-effort по имени модели — если каталог не смэтчил, строка всё равно пишется с `printer_id=null`: сам факт привязки через вендорский API уже подтверждает владение, каталожный матчинг — не блокирующий бонус.

Проверено локально (docker Postgres 16, `dbmate`): миграция идемпотентна (повторный `up` чист), прогнана вперёд→назад→вперёд (`rollback` дропает `user_printers.connection_id/external_ref/status` + индекс + таблицу `printer_connections`, базовые таблицы целы; re-forward воссоздаёт схему один в один), `ON CONFLICT (connection_id, external_ref)` ре-синк обновляет строку без дублей, `on delete cascade` подтверждён (удаление `printer_connections` убирает связанные `user_printers`), `encryptIdentity`/`decryptIdentity` round-trip и коннектор-тесты (`prusaConnect.*.test.ts`, `auth/crypto.test.ts`) зелёные. Happy-path с реальным аккаунтом Prusa не проверен (нет тестового ключа у Back/Data) — висит на операторе/QA отдельно от вердикта по схеме.

### Форензик-журнал скачиваний (MF-735, шаг 2 фазы MF-424, эпик MF-39 «Антипиратство») — реализовано

Схема добавлена 2026-07-10 (`apps/api/db/migrations/20260710170000_model_download_log.sql`). Контекст и открытая проблема офлоада — `docs/epics/ids.policy.md` § «Открытая проблема: публичный offload файлов конфликтует с целью MF-39»: этот лог покрывает **API-опосредованные** скачивания (сегодня — единственный реальный путь, `models/download.ts` требует сессию до любой выдачи байт, включая offload-редирект), а не гипотетический прямой обход по угаданному S3-ключу — тот риск отдельный и уже задокументирован там, решение за Lead/CTO.

- **`model_download_log`** — append-only: `model_id → models`, `file_role` (`text+check`: `canonical_3mf` + as-is роли из `AS_IS_DOWNLOAD_ROLES`, `apps/api/src/models/download.ts` — не полный `model_files.role`, т.к. `preview`/`thumbnail`/`source`/`description_image` через этот путь не скачиваются), `user_id → users` (`not null` — скачивание уже требует сессии), `anon_id text` (тот же тип/значение, что `events.anon_id`/`ensureAnonId()`, `apps/api/src/analytics/anon.ts`), `ip_hash bytea` (nullable, псевдонимный — тот же паттерн, что `idea_vote_log.ip_hash`/`user_identities.identifier_hash`; сырой `inet` сознательно не взят — `user_id` уже деанонимизирует запись, хэш достаточен для «тот же источник, разные аккаунты»), `created_at`.
- Пишется **всегда**, независимо от 152-ФЗ консента на поведенческую аналитику (`events`/`consent_records`, `apps/api/src/analytics/events.ts` — fail-closed по консенту) — это security-обязанность (расследование утечки), не маркетинговая аналитика, поэтому отдельная таблица, не переиспользование `events`.
- Отдельного `fingerprint`-столбца нет — в коде нет request-fingerprint хелпера (черновик карточки ссылался на несуществующий `security/rateLimit.ts::requestFingerprint`); появится реальный источник — добавится аддитивной миграцией вместе с кодом, который его пишет.
- Retention: не чистим — объём ~1 строка/скачивание, тот же порядок, что `models.downloads_count`; TTL/архивация — отдельное решение, когда объём станет заметен.
- Индексы: `(model_id, created_at desc)` и `(user_id, created_at desc)` — обе стороны форензик-запроса («кто скачивал файл X» / «что скачивал юзер Y») одинаково частые; `(ip_hash, created_at desc) where ip_hash is not null` — ретроспектива по скоординированной выкачке с одного источника разными аккаунтами (partial, как `idea_vote_log_ip_idx`).
- Запись на стороне API (`download.ts`, после текущего инкремента `downloads_count`) — код Back, отдельная сабкарта [MF-424 stage 2] в backlog до этого мерджа.

Проверено локально (docker Postgres 16, `dbmate`-миграция прогнана внутри транзакции с явным `ROLLBACK` — `sandbox-db create` временно недоступен в этой среде, `CREATE DATABASE` для роли `portal_dev` вернул `permission denied to create database`, похоже на недавнее ужесточение прав со стороны Ops, не разбирался дальше — не блокер этой карточки): DDL идемпотентен (повторный прогон — `NOTICE ... already exists, skipping`), `check` на `file_role` отклоняет постороннюю роль (`preview`), `not null` на `user_id` отклоняет анонимную строку, `on delete cascade` на `model_id`/`user_id` подтверждён (удаление модели убирает её лог-строки), `EXPLAIN` показывает использование `model_download_log_model_idx` (Bitmap Index Scan) для запроса «лог по модели», `migrate:down` дропает таблицу чисто.

### Страница идей (MF-558 / MF-559) — реализовано

Схема добавлена 2026-07-08 (`apps/api/src/db/schema.ts`) под эпик «страница идей» — публичный канал предложений с голосами, статусами и обсуждением. Вердикт совета принят CTO 08.07. Аддитивно (expand), деструктива нет.

- **`idea_vote_log`** — append-only форензика накрутки: `event('cast'|'revoke')`, `user_id`, `idea_id`, `ip_hash bytea` (nullable, pseudonymous), `created_at`. Отдельно от состояния, потому что отзыв удаляет строку `idea_votes`, а событие терять нельзя. Rate-limit голосов и ценз возраста аккаунта выводятся из этого лога + `users.created_at` — «спящих» колонок под анти-абьюз не заводим.
- **`idea_comments`** — плоский тред: `idea_id`, `user_id`, `body` (md), `created_at`, `deleted_at` (soft-delete под модерацию).
- **`users.is_staff boolean default false`** — минимальный гейт под `PATCH /ideas/:id/status` (менять статус может только команда/модератор; в `users`/`SessionUser` роли не было — поднял Fullstack). Кто получает `is_staff=true` — операционное решение (Ops/CTO), самоназначения нет.

**Слияние дубликатов без переливки голосов.** «Дубликат B → каноник A» ставит `B.canonical_id = A.id`; голоса физически остаются на своих идеях. Отображаемый счётчик каноники = `count(distinct user_id)` по кластеру (A + все дубликаты) — двойного счёта нет by design (один юзер в distinct один раз, даже если голосовал и за оригинал, и за дубликат), обратимо (un-merge = обнулить `canonical_id`+статус), форензика цела. Для 99% не-слитых идей работает дешёвый денорм `vote_count`.

**Индексы (сняты `EXPLAIN`'ом на seed-объёмах v1, все выбираются планировщиком):** `ideas_popular_idx` partial `(vote_count desc, created_at desc) where status not in ('archived','duplicate')`; `ideas_created_at_idx` (новые + окно тренда); `ideas_filter_idx (category, status, vote_count desc)`; `ideas_archive_scan_idx (last_activity_at) where status<>'archived'`; `ideas_canonical_idx (canonical_id) where canonical_id is not null` (кластерный пересчёт каноники — без него `id=X OR canonical_id=X` даёт seq scan, просил Fullstack); `ideas_title_trgm_idx` GIN `gin_trgm_ops` (живой поиск похожих, `pg_trgm` уже стоит); `ideas_author_created_idx (author_id, created_at)` (лимит 3 идеи/сутки); на логе — `(user_id, created_at)` и partial `(ip_hash, created_at)`; на тред — `(idea_id, created_at)`. Тренд `votes/(age_hours+2)^1.5` не индексируется (зависит от `now()`) — считается в приложении на 30-дневном окне, окно покрывает `ideas_created_at_idx`.

Проверено локально (docker Postgres): миграция идемпотентна (повторный прогон чист), прогнана вперёд-назад (rollback дропает `idea_*`+`is_staff`, база users/models цела, re-forward воссоздаёт всё), все `check`-инварианты сработали на позитивных/негативных вставках, кластерный distinct-count не даёт двойного счёта. Применение на прод — заявкой Ops после merge (Data руками на прод не пишет).

## Обязательные ограничения для Фазы 1 (MF-336)

Схема `models`/`model_files` из описания MF-336 остаётся, но с поправками «на рост»:

1. `models.source_format` — `text + check ('stl','step','3mf')`, расширяемо (`dxf`, `svg`, `obj`…). Не Postgres-enum.
2. `models.craft` — `text not null default '3d_printing'` (slug будущего справочника `crafts`). Одна колонка сейчас — ноль миграционной боли потом.
3. `models.status` — `text + check ('uploaded','pending','processing','ready','failed')`, расширяемо.
4. `model_files.role` — `text + check ('source','canonical_3mf','preview')`; новые роли (`gcode`, `drawing`…) — одной миграцией.
5. Никаких принтер-специфичных колонок в `models` — принадлежность к станку/материалу появится через `makes` и профили совместимости, не в ядре модели.
6. `checksum` — sha256 `bytea`; `size_bytes bigint`; bbox — `jsonb` (у ЧПУ-заготовки тоже есть габариты — поле универсально).
7. Ключи S3 `models/{model_id}/{role}.{ext}` — нейтральны к ремеслу, оставить как в спеке.
8. Нейминг таблиц/колонок/модулей — без `print`/`stl` в именах общего назначения.

### Каталог филамента (MF-31) — конкретизация `vendors`/`materials`

Эпик MF-31 («Каталог филаментов + партнёры-поставщики») — первая реальная реализация
`vendors`/`materials`, набросанных выше пунктиром. Решения по схеме (Data-агент, 2026-07-06):

- **`vendors`** заводится как есть по наброску (`slug`, `name`, `verified`) — общая сущность
  для будущего каталога станков (MF-32) и каталога материалов, не дублируем под «бренд филамента».
- **Ось «материал» — две сущности, не одна** (наброска `materials.kind` было недостаточно для
  фильтра каталога из «Готово когда» эпика):
  - `materials.kind` (уже в наброске) — **форма** материала: `filament` | `resin` | `plywood` |
    `aluminum`… — на будущее для других ремёсел/форм, в MF-31 всегда `filament`.
  - `material_types` (новая таблица) — **вид полимера/сплава**: PLA, PETG, ABS, TPU, PA — растущий
    справочник (принцип 2: `text+check` дороже одной FK-таблицы, когда есть собственные атрибуты —
    default-температуры/плотность по ISO 1043/11469, см. «Готово когда» п.3 эпика). `materials`
    ссылается на него `material_type_id`.
  - Разделение отвечает и на будущий рост: у ЧПУ-дерева/металла тоже будет своя таксономия видов
    (порода дерева, сплав) поверх той же пары `kind`+`material_types`-подобного справочника.
- **`materials` = продукт/линейка бренда** (третий уровень из брифа «brand → material → product →
  variant»): `vendor_id` + `material_type_id` + `name`/`slug`, `specs jsonb` — филамент-специфичные
  атрибуты линейки (наполнитель, температуры/усадка/сушка конкретного продукта поверх дефолтов
  `material_types`), которые не участвуют в фильтре каталога (принцип 5).
- **`material_variants`** (новая таблица, SKU-уровень) — цвет/диаметр/навеска. Цвет и диаметр —
  реляционные колонки (по ним фильтрует каталог, «Готово когда» п.4 эпика), остальное
  SKU-специфичное — `specs jsonb`.
- **Слуги для необнаружимых путей**: PK везде `uuid` (как и всюду в схеме), человекочитаемый путь
  каталога — `vendors.slug` + `materials.slug` (уникален в рамках вендора), без автоинкремента —
  закрывает риск эпика «конкуренты посчитают объём базы по ID».
- **`source`+`confidence`** на `materials`/`material_variants` (`manual` | `import`, confidence
  0..1 у вариантов) — минимальный след для будущего парсер-агента (эпик, риск «качество данных»);
  стейджинг-таблица для diff-approve остаётся отложенной (принцип «не заводить впрок» — нет ни
  одного парсер-агента на момент этого решения). Профили печати — см. § «Профили печати и
  модификаторы (MF-402)» ниже, заведены отдельной миграцией.
- **`models.recommended_material_id`** — нового поля добавлено (nullable FK на `materials`) для
  связи проекта с рекомендованным филаментом («Готово когда» п.6 эпика); API/UI карточки проекта
  (MF-10) — вне зоны Data, реализуется отдельной карточкой.
- **Цены/наличие** — задел-заглушка заведён MF-402 (см. ниже); публичный слой reward-shop v3 —
  отдельная будущая карточка, здесь только схема.
- Импорт из Open Filament Database/SpoolmanDB, публичный read-API, парсер-агенты и заполнение
  RU-брендов данными — **вне зоны Data-агента** (владелец схемы, не бэкенд-эндпоинтов/агентов/
  контента); схема выше рассчитана как основа под них, реализация — отдельными карточками
  Back/Fullstack/контент.

### Профили печати и модификаторы (MF-402, фаза 1 эпика MF-31)

Фаза 1 эпика MF-31 явно поручает то, что решение выше сознательно откладывало «до появления
потребителя» — сейчас заведено отдельной миграцией (Data-агент, 2026-07-08):

- **Модификаторы/наполнители** (issue #32) — НЕ новые колонки/таблица: живут в уже существующем
  `materials.specs jsonb` (принцип 5 — не участвуют в фильтре каталога «Готово когда» п.4 эпика
  MF-31, который фильтрует по материалу/бренду/цвету, не по наполнителю). Канонический набор
  ключей `specs` для наполнителей задокументирован прямо в `schema.ts` рядом с миграцией (не
  дублируется здесь, чтобы не разъезжаться): `fill_type`/`fill_percent`/`fiber_length_mm`,
  `translucent`/`glow`/`finish`/`pattern`/`multi_color_direction`, `esd_conductive`/
  `flame_retardant`/`recycled_content_pct`/`scented`/`support_type`/`tpu_shore_hardness`.
  Добавлен GIN `jsonb_path_ops` индекс на `materials.specs` (тот же паттерн, что
  `machines_specs_gin_idx` MF-32) — под будущие фильтры без роста реляционных колонок.
- **`machine_material_profiles`** (новая таблица, вместо рабочего имени `print_profiles` из
  наброска выше — нейминг без `print_*` по принципу 1, растёт на другие ремёсла тем же путём, что
  `machines`/`materials`) — связка станок(`machine_id`)×материал(`material_id`), опционально
  `nozzle_diameter_mm` (доп. разрез под FDM-сопло). `overrides jsonb` — переопределения к дефолтам
  `material_types`/`materials`, схема полей не констрейнится в БД (потребитель — MF-16/экспорт в
  слайсер). Без уникальности по (`material_id`, `machine_id`, `nozzle_diameter_mm`) — для одной
  пары допустимо несколько именованных профилей («качество»/«скорость»), как и у `machines`.
  Привязка к `material_id` (линейке), не к `material_variants` (SKU) — настройки печати не
  зависят от цвета/навески одного и того же продукта.
- **`material_variant_offers`** — задел-заглушка цены/наличия под reward-shop v3 (`store_id` пока
  `text`, сущность «магазин» не спроектирована), привязана к `material_variants` (цена зависит от
  конкретного SKU, не от линейки). Таблица есть, эта миграция её не заполняет.

Проверено локально (docker, Postgres 16/pgvector-образ): миграция идемпотентна (двойной прогон
без ошибок), ручной откат (`drop table`/`drop index` в обратном порядке зависимостей) проверен и
после отката форвард-миграция переприменяется чисто, вставка тестовых REC PLA-данных с
наполнителем в `specs` + профиль печати + офер читается одним join через всю цепочку
`vendors → materials → material_types/material_variants/machine_material_profiles(→machines)/
material_variant_offers`. `pnpm lint`/`typecheck`/`test` в `apps/api` — зелёные (97 тестов).

Вне зоны этой миграции (сознательно, как и в MF-31/MF-32 выше): наполнение реальных профилей
из вики производителей, UI/API экспорта в слайсер (MF-16), реальные цены от партнёров
(reward-shop v3) — отдельные карточки Back/Fullstack/контент поверх готовой схемы.

### Импорт моделей с внешних площадок (MF-37, Фаза 1 — MF-417) — схема

Схема добавлена 2026-07-10 (`db/migrations/20260710010000_import_pipeline_foundation.sql`) —
только хранилище для «Готово когда» шагов 1 и 2 эпика: таблица привязок с дедуп-ключом и
очередь фоновых джобов. Коннектор-интерфейс/`normalize()`, сам GraphQL-коннектор Cults3D и
код гейта публикации — Back/Fullstack поверх этой схемы, отдельными карточками (MF-417 режется
на параллельные подзадачи, см. карточку).

- **`import_connections`** — один аккаунт-источник на `(user_id, source_platform)`, тот же
  паттерн, что `printer_connections` (коннектор Prusa Connect выше): `credential_enc bytea` —
  AES-256-GCM (`apps/api/src/auth/crypto.ts`), не plaintext. `source_platform` — `text+check`
  с единственным значением `'cults3d'` пока (принцип 2, расширяется без миграции-ремонта при
  следующем источнике — Printables/MakerWorld/Thangs).
- **Подтверждение владения — два режима, одна колонка `ownership_status`** (эпик MF-37 § 6):
  для коннекторов с официальным API-ключом (Cults3D) сам факт валидной авторизации уже
  доказывает владение аккаунтом (ключ на cults3d.com/en/api/keys выпускает только владелец) —
  коннектор ставит `'verified'` сразу после первого успешного запроса, без отдельного шага.
  Для будущих коннекторов без OAuth/ключа (публичный скрейп) — `challenge_token`/
  `challenge_target`: автор временно вставляет строку в bio/описание модели на источнике,
  коннектор её читает и переводит `'pending'` → `'verified'`. Решение — не заводить два разных
  механизма/таблицы под эти пути, а один набор колонок, которым по-разному пользуется код
  каждого коннектора.
- **`import_bindings`** — привязка импортированной модели к исходнику, `unique(source_platform,
  external_id)` — обязательный дедуп-ключ («повторный импорт не плодит дубль»); `unique(model_id)`
  — одна модель = максимум одна привязка. `ownership_status` здесь — **денормализованная копия**
  состояния `import_connections` на момент импорта/последней проверки (тот же паттерн, что
  `models.votes_up`/`vote_count` — консистентность на api-слое, не триггером): один раз
  подтверждённое владение остаётся подтверждённым, даже если автор потом отключит аккаунт
  (`connection_id` → null через `on delete set null`, факт владения уже доказан и не отзывается
  отключением ключа). Публикационный гейт («Готово когда» шага 4: неподтверждённый импортированный
  черновик нельзя опубликовать) читает `ownership_status` по `import_bindings.model_id` ОДНИМ
  запросом, без второго джойна до `import_connections` — на реализацию Back/Fullstack.
- **`import_jobs`/`import_job_items`** — очередь фоновых джобов (джоб = список `external_id` на
  вход), тот же дух, что `machine_candidates` (стейджинг+статус+дедуп-ключ) чуть выше: per-item
  обработка — частичный успех не роняет пачку, у каждого item свой `status`/`retryable`/
  `attempt_count`/`next_retry_at` под экспоненциальный бэкофф. `unique(job_id, external_id)` —
  идемпотентность повторного прогона ОДНОГО ЖЕ джоба (не путать с глобальным дедупом — тот на
  `import_bindings`). `total_count`/`done_count`/`failed_count` на `import_jobs` — денорм-прогресс
  для ЛК (MF-15), консистентность на api-слое.

Проверено локально (docker Postgres 16, `dbmate`): миграция идемпотентна (повторный `up` чист),
прогнана вперёд→назад→вперёд (`rollback` дропает все 4 таблицы+индексы, `users`/`models` целы,
re-forward воссоздаёт схему один в один), `unique(source_platform, external_id)` подтверждён
вручную (повторная вставка того же `external_id` падает с ожидаемым `duplicate key`), FK
`on delete cascade`/`on delete set null` расставлены по смыслу (см. комментарии в миграции).

Не сделано этой миграцией (сознательно, вне территории Data): TypeScript-интерфейс коннектора
и `normalize(meta)→draft`, сам коннектор Cults3D (GraphQL-клиент, rate-limit/бэкофф), воркер
очереди джобов, эндпоинты прогресса для ЛК, код гейта публикации по `ownership_status`. Это
Back/Fullstack-реализация поверх готовой схемы — разбито на параллельные подзадачи под MF-417.

### Движок совместимости — фундамент данных (MF-33 Фаза 1 / MF-408)

Фаза 1 эпика MF-33 (движок принтер×филамент×модель) поручила спроектировать нормализованные
`printers`/`materials`/`filaments` + M:N `printer_material_support` и колонку bbox на модели.
К моменту этой фазы каталог станков (MF-32) и каталог филамента (MF-31) уже спроектированы и
задеплоены под другими именами — решение Data ниже мапит формулировку карточки на живую схему,
а не дублирует её новыми таблицами.

**1. «printers»/«materials»/«filaments» — уже живые сущности, не новые таблицы.**
- «printers» = `vendors`+`machines` (MF-32) — конкретная модель станка, `craft='3d_printing'`.
- «materials» (линейка бренда) = `vendors`+`material_types`+`materials` (MF-31).
- «filaments» (конкретная катушка) = `material_variants` (MF-31, SKU-уровень: цвет/диаметр/навеска).
Заводить параллельные `printers`/`filaments` — прямое дублирование живых таблиц без причины;
никакой миграции под них в этой фазе нет.

**2. Контракт `machines.specs` для compat.check (документация ключей, не DDL).**
`specs` — jsonb по принципу 5 (машины обслуживают и будущие ЧПУ/лазер, 3D-печатные поля были бы
запрещённым принципом 1 `print_*` на общей таблице). Уже живые ключи (bootstrap-импорт MF-405):
`build_volume {x,y,z,shape:'rectangular'}` (мм), `kinematics`, `nozzle_diameters` (number[], мм).
Канонические ключи, которые нужно заполнять/читать движку совместимости (соглашение для
будущей реализации compat.check — Back/Fullstack, вне зоны Data этой фазой):
`nozzle_hardened` (bool — закалённая сталь/рубин, может абразив), `max_hotend_temp_c` (smallint),
`chamber` (`'none'|'passive'|'active'`), `chamber_max_temp_c` (smallint, только для `'active'`),
`bed_types` (text[] — `'glass'|'pei'|'magnetic'|…`), `filament_dia_mm` (numeric — сравнивается с
`material_variants.diameter_mm`), `extruder_count` (int), `filament_system`
(`'single'|'ams'|'idex'|'toolchanger'`). `materials_supported` (array слагов `material_types`,
заведён в `REQUIRED_SPEC_KEYS` `catalog/metrics.ts`, но ни один пайплайн его пока не пишет) —
необязательный ДОПОЛНИТЕЛЬНЫЙ сигнал (вендор явно заявил поддержку), не обязательное условие:
compat.check не должен требовать его наличия, основная логика — по геометрии/темпе/соплу/камере/
диаметру ниже.

**3. `material_types` — новые колонки под семейные требования к железу** (миграция
`20260710130000_compat_material_flags.sql`): `default_extruder_temp_c`/`default_bed_temp_c`
(типовые, не только min/max, уже были из MF-31) + `requires_chamber`/`requires_drying`/
`requires_direct_drive boolean not null default false`. Это СЕМЕЙНЫЕ атрибуты (ABS всегда любит
камеру вне зависимости от бренда) — в отличие от абразивности, которая уже атрибут конкретной
ЛИНЕЙКИ (`materials.specs.fill_type` в `('carbon','glass','wood','metal','glitter','ceramic')`,
заведено MF-402) — абразив→нужно `nozzle_hardened` компарит fill_type∈{carbon,glass}, не заводим
второй колонки под это. Бэкфилл best-effort по имени/слагу (word-boundary regex, идемпотентно —
`where <флаг> = false`, не переписывает то, что уже выставлено вручную/импортом): abs/asa/pc/nylon
→ chamber; pa/nylon/pc → drying; tpu/tpe/flex → direct-drive. Список — из золотых кейсов эпика,
не исчерпывающий; будущий парсер-агент/ручное редактирование уточняют по TDS точнее.

**4. Решение НЕ заводить M:N `printer_material_support` с флагами камера/сушка/сопло.**
Карточка MF-408 просила ровно эту таблицу — вето Data: сам эпик MF-33 явно требует, чтобы
совместимость была «детерминированной функцией над справочниками, а не хардкод-таблицей
принтер→список» (тот же принцип уже принят для геометрии bbox↔build_volume, п.5 ниже). Материал↔
железо ничем не отличается: abrasive→hardened nozzle, ABS/ASA/PC/PA→chamber, TPU→direct-drive,
temp≤max_hotend, diameter-match — все правила выводятся из атрибутов ОДНОЙ записи `machines`
(specs, п.2 выше) и ОДНОЙ записи `material_types`/`materials` (п.3 выше + `specs.fill_type`), без
переливки в M:N на каждую пару. Причина не только принципиальная: 320+ станков × N материалов не
масштабируется ручным вводом, а полное декартово покрытие в актуальном виде никто не будет
поддерживать — то же обоснование, по которому уже отклонена «хардкод-таблица принтер→список
моделей» для геометрии. Реализация самого `compat.check(...)` — Back/Fullstack (Направление 2
эпика MF-33), вне зоны Data этой фазой; здесь только фундамент данных под неё.

**5. Bounding-box модели — уже реализовано (MF-339/MF-480), контракт подтверждён этой фазой.**
Вторая часть фазы 1 («добавить bbox на модель») формально уже выполнена ДО этой карточки: у
`models` есть `bbox jsonb` (MF-336, легаси-агрегат), а после декомпозиции на мультимеш (MF-339,
`model_meshes.bbox jsonb`, см. § «Контент» выше) канонический per-мещ bbox живёт на
`model_meshes.bbox`, с идемпотентным backfill из `models.bbox` в baseline-миграции. Контракт «кто
пишет, кто читает» (запрошен эпиком): `apps/mesh` (конвертер STL/3MF, MF-22/MF-456) — ЕДИНСТВЕННЫЙ
писатель, на шаге конвертации (`worker.py::_finish_ready`), рантайм compat.check только ЧИТАЕТ,
никогда не считает bbox сам (уже прямое требование карточки MF-408). **Найден разрыв контракта**
(не Data-территория, apps/mesh — Fullstack/Mesh): `worker.py` сейчас пишет bbox ТОЛЬКО в легаси
`models.bbox`, не в `model_meshes.bbox` — новые модели, сконвертированные ПОСЛЕ миграции MF-339,
получат `model_meshes.bbox = null` (одноразовый backfill покрыл только строки на момент миграции).
Схема не виновата (колонка есть, контракт документирован), но writer не обновлён под новый
источник истины — заведена карточка Fullstack/Mesh на исправление (см. трекер 007).

### Лента (MF-420, Фаза 1 эпика MF-38 «Социальная лента и сообщества») — фундамент данных

Схема добавлена 2026-07-10 (`db/migrations/20260710000000_feed_foundation.sql`) — только шаг 1
Фазы 1 (модель данных + непоследовательные ID), плюс задел материализации (шаг 3) как таблицы

карточки — НЕ новые таблицы, а расширение полиморфизма уже живущей схемы MF-35 (`communities`/
`community_members`/`votes`/`comments`, §«Комьюнити» выше + `community.foundation.md`/
`marketplace_social_layer.sql`). Прецедент уже задан самой этой схемой (`model_tags`→`taggings`,
`model_votes`→`votes` — Data-вердикт `community.foundation.md`): второй/третий реальный
потребитель полиморфной связки переключает на неё, а не плодит узкую пару. Лента — именно такой
третий потребитель.

- **«Саб» = `communities`, «подписка» = `community_members`** — без изменений схемы. Саб ленты и

- **`votes.subject_type`** расширен `'post'|'thread'` → `+'feed_post'|'feed_comment'` (не
  заводим `feed_post_votes`/`feed_comment_votes`). `'post'` — это уже существующая сущность

  MF-420 закрывается без изменения структуры. Добавлены `comments.votes_up`/`votes_down` —

- **`taggings.subject_type`** расширен `'thread'` → `+'community'` — таксономия сабов через
  глобальные `tags` (карточка MF-420: «опереться на MF-11 как таксономию сабов через FK, не
  дублируя её»), третий потребитель после `model_tags`(legacy)/`threads`.
- **Новая сущность — только `feed_posts`.** Существующая `posts` (MF-35) — Discourse-ответ

  `community_id` nullable — «пост живёт в клубе или в профиле»). Совпадение имени с `posts`
  было бы путаницей, не переиспользованием — 3 типа по карточке (`model_link`/`media`/`text`,
  переименовано из `link`/`showcase`/`text` наброска под текст самой карточки MF-420),

  нужное поле непустым под свой `type`). `votes_up`/`votes_down`/`comments_count` — денорм,

- **`post_score`** — материализация Hot/Best/Controversial (`double precision`, по одному

  по `votes.created_at` в окне (данные уже есть, индекс — по факту запроса Фазы 2, не «на
  всякий случай»), New — сортировка по `feed_posts.created_at` напрямую

  20K строк — Hot/Best/Controversial-сортировка идёт Index Scan по соответствующему индексу
  `post_score`, New — Index Scan по `feed_posts_visible_created_idx`, ни разу seq scan/расчёт
  формулы на лету (карточка «Готово когда» п.3).
- **`feed_events`** — отдельная таблица implicit-сигналов (view/read_complete/model_click/

**Формулы ранжирования** — `apps/api/src/modules/feed/domain/ranking.ts`, чистые функции без обращения к БД
(`hotScore`/`bestScore`/`topScore`/`controversialScore`/`newScore`), покрыты юнит-тестами на
эталонные кейсы карточки (`ranking.test.ts`: 5:0 обгоняет 100:40 по Best, старый вирусный не
доминирует над свежим по Hot, сбалансированный большой объём выше по Controversial).

**Data-вердикт по формуле Hot (расхождение с буквальным текстом карточки):** карточка MF-420 и
эпик MF-38 дают формулу как `log10(max(1,|U−D|)) + sign(U−D)·(t−epoch)/45000` — знак у
временнóго члена. Канонический Reddit-алгоритм, на который сама карточка ссылается («формула
Reddit»), устроен иначе: `sign(U−D)·log10(max(1,|U−D|)) + (t−epoch)/45000` — знак у ПОРЯДКА,
временной член без знака (`reddit/r2/r2/lib/db/_sorts.py`). Буквальный текст карточки даёт
сильно заминусованным постам большой положительный вклад от order (лог модуля разницы голосов
без знака) — заминусованный контент лез бы в Hot наравне с популярным. Реализована каноническая
формула (знак у order), расхождение задокументировано в коде (`ranking.ts`) и здесь; эталонные
кейсы карточки проходят в обеих версиях (там нет кейса на заминусованный контент), решение не
блокирует «Готово когда». Правки — одна строка в `hotScore`, если понадобится буквальная версия.

**Эпоха Hot** — `HOT_EPOCH_SECONDS = 1782864000` (2026-07-01T00:00:00Z). Явной даты «запуска
портала» в доках нет — ближайшие зафиксированные вехи: первый коммит репозитория (2026-07-02),
перевод DNS 3mf.tech на cloud.ru (2026-07-03, `docs/issues/009.dns.cloudru.md`). Выбрана
округлённая дата непосредственно перед ними; как и у Reddit-эпохи, само число не несёт смысла —
только сдвигает шкалу так, чтобы `t−epoch` было небольшим положительным числом с первого дня
портала.

**Материализация — воркер, не API-хендлер** (карточка «Готово когда» п.3). `apps/api/src/feed/
scores.ts`: `recomputePostScore(postId)` (апсерт по одному посту) + `batchRecomputeVisible()`
(постраничный проход всей видимой выборки — двигает временной член Hot вперёд даже без новых
голосов). Канал «голос → пересчёт» — `pg_notify('post_score_recompute', postId)`
(`notifyPostScoreRecompute`, вызывается будущим vote-хендлером Фазы 2 сразу после записи голоса,
внутри той же транзакции — `pg_notify` не транзакционный побочный эффект, доставляется только
при `COMMIT`), не отдельная таблица-очередь — LISTEN/NOTIFY дешевле лишней записи+индекса под
чисто сигнальную задачу. Payload не durable (не переживает рестарт воркера) — периодический
батч в `scripts/feed-score-worker.ts` (systemd-сервис, заводит Ops) страхует пропущенные
уведомления, пересчитывая всю активную выборку по расписанию (`FEED_SCORE_BATCH_INTERVAL_MS`,
по умолчанию 5 мин).

Проверено локально (docker Postgres 16, `dbmate`): миграция идемпотентна (повторный `up` чист),
прогнана вперёд→назад→вперёд (`rollback` возвращает `votes`/`comments`/`taggings` check-
констрейнты к исходному виду, дропает `feed_posts`/`post_score`/`feed_events`+индексы,
`users`/`communities`/`votes`/`comments` целы), проверена совместно с миграциями, добавленными
параллельно другими агентами тем же днём (нет пересечения по таблицам, порядок применения не
важен). Check-констрейнты проверены прямыми вставками: `model_link`/`media` без обязательного
поля отклоняются, повторный голос того же юзера на тот же subject отклоняется (идемпотентность
по PK), обратная совместимость старых `subject_type` (`'post'`/`'thread'`/`'model'`/`'thread'`
у taggings) подтверждена. `pnpm lint`/`typecheck`/`test` в `apps/api` — зелёные (22 новых
теста: 16 `ranking.test.ts` + 6 `scores.test.ts`).

### Движок совместимости (MF-33 compat.check) — реализовано

Фаза 2 эпика MF-33 (MF-409, Data-агент, 2026-07-10) — поверх уже задеплоенной Фазы 1 (MF-408,
`0e2763a`, § «Движок совместимости — фундамент данных» выше). Реализация `compat.check` в этой
фазе НЕ территория Data по формулировке самой Фазы 1 («Реализация самого `compat.check(...)` —
Back/Fullstack... вне зоны Data этой фазой») — тем не менее карточка MF-409 явно назначает этот
пункт Data (следующая фаза того же эпика), сервис реализован здесь: расхождение зафиксировано
как замечание Lead/CTO, не блокер (никто другой этот сервис не начинал — `grep -r "compat"` по
`apps/api/src` до этой фазы не находил ни одного вхождения).

**Контракт `compat.check`** (`apps/api/src/compat/check.ts`) — чистая функция без обращения к БД:
`compatCheck(printer, filament?, model?) → {verdict: 'ok'|'warn'|'blocked', reasons[]}`. Контракт
входа — ПРЯМОЕ отражение уже задокументированных Фазой 1 ключей (не собственные family-эвристики
в TS: «ABS нужна камера» решается на уровне данных `material_types.requires_chamber`, функция
только читает уже разрешённый флаг):
- `machines.specs`: `nozzle_hardened` (bool), `max_hotend_temp_c`, `chamber`
  (`'none'|'passive'|'active'`), `filament_dia_mm` — все из списка Фазы 1. Плюс ОДНО расширение
  контракта этой фазой — `extruder_drive` (`'direct'|'bowden'`), которого не было в списке Фазы 1
  (нужен правилу TPU→директ-драйв, в исходном списке машинных ключей такого поля нет).
- `material_types`: `requires_chamber`/`requires_drying`/`requires_direct_drive`,
  `default_extruder_temp_c` — колонки Фазы 1 (`compat_material_flags` миграция), читаются как
  есть, override на уровне конкретного продукта (`materials.specs`) контрактом не предусмотрен.
- `materials.specs.fill_type` (MF-402) — абразив = `fill_type ∈ {carbon, glass}`, тот же критерий,
  что зафиксирован в решении Фазы 1 (п.3 выше).

Реализованные правила: геометрия (bbox модели ≤ build volume станка с отступом 5мм, допускается
разворот X/Y), абразив→сопло (`nozzle_hardened=false` → `blocked`; `undefined` → `warn`, не
`blocked` — недостаточно данных для гарантии), семейство→камера (`requires_chamber` и
`chamber∈{none,undefined}` → `warn`), гибкий материал→директ-драйв (`requires_direct_drive` и
`extruder_drive='bowden'` → `warn`), сушка (`requires_drying` → `warn`, безусловно — не зависит
от станка), макс. темп. хотэнда, диаметр прутка. `blocked` перевешивает `warn`. 17 golden-тестов
в `check.test.ts`, включая все 5 эталонных кейсов из «Готово когда» эпика.

Маппинг DB-строк (JOIN `machines`/`material_types`/`materials`/`material_variants` → вход
`compat.check`) — задача потребителя (Фаза 3, MF-410, UI/API-резолвер), здесь только контракт и
его реализация.

**Импортёр v0** (`apps/api/scripts/import-materials-bootstrap.ts` + уже живой
`import-machines-bootstrap.ts`/MF-405 закрывает требование «≥2 источника»). Оба импортёра при
создании НОВОЙ строки `material_types` выставляют `requires_chamber`/`requires_drying`/
`requires_direct_drive` той же word-boundary regex-эвристикой, что бэкфилл Фазы 1 — та миграция
сработала на пустой таблице (`material_types` до этой фазы не имела ни одной реальной строки),
поэтому её `UPDATE ... WHERE` был no-op; без повторения той же логики на `INSERT` в импортёрах
новые семейства молча остались бы с `requires_*=false`, и compat.check тихо потерял бы
ABS→камера/TPU→директ-драйв на всём импортированном каталоге:
- **SpoolmanDB** (github.com/Donkie/SpoolmanDB, MIT — проверено 2026-07-10 по LICENSE в
  репозитории) — 6957 SKU / 221 линейка филамента, группировка `(manufacturer, material)` →
  `materials`, каждый цвет → `material_variants`. Дедуп: `materials` через уже живой
  `unique(vendor_id, slug)` (MF-31), `material_variants` — новый
  `material_variants_dedup_uidx (material_id, color_name, diameter_mm)`
  (`db/migrations/20260710193000_material_variants_dedup.sql`). Прогнан на локальном Postgres
  дважды подряд — второй прогон не меняет количество строк (идемпотентно).
- **Open Filament Database** (github.com/OpenFilamentCollective/open-filament-database,
  api.openfilamentdatabase.org) — лицензия проверена 2026-07-10: репозиторий MIT (LICENSE-файл,
  © OpenFilamentCollective 2025), импорт разрешён контрактом лицензии так же, как SpoolmanDB.
  Импортёр под неё сознательно НЕ написан в этом прогоне: её 146 брендов/1982 филамента почти
  целиком пересекаются с уже импортированным SpoolmanDB по западным брендам и не содержат ни
  одного RU-бренда (сверено вручную по `brands/index.json` — REC/PICASO 3D/Bestfilament/
  Filamentarno!/FDplast отсутствуют), то есть добавление сейчас — в основном дубли, а не новый

- **RU-слой** (`apps/api/scripts/import-ru-vendors-bootstrap.ts`) — вручную сверенные (не
  live-скрейпинг) данные 2026-07-10 с офсайтов/вики брендов: REC (PLA/PETG-Relax/ABS/Flex,
  источник — rec3d.ru/rec-wiki, `quality: vendor_tds`), Bestfilament (PLA, bestfilament.ru,
  `vendor_tds`), FDplast (PLA, community-обзор 3dtoday.ru — офиц. TDS недоступен на момент
  прогона, помечено `quality: community_review` + `data_quality_note` в specs), PICASO 3D

  slicer-profiles-db, build volume/темп./камера с picaso-3d.ru). Filamentarno! заведён только
  как `vendors`-ряд (офиц. сайт на момент прогона отдавал 404/битую кодировку) — линейки не
  выдуманы, ждут будущего парсер-агента (MF-33/MF-409 явно выносит агентов-парсеров в отдельную
  карточку — здесь честно зафиксирован факт «не хватило источника», не заглушка с точностью
  «наугад» при материале, где ошибка стоит пользователю испорченной печати).

Проверено локально (`sbx_mf409`, throwaway Postgres): миграция `material_variants_dedup_uidx`
прогнана вперёд→назад→вперёд (индекс появляется/исчезает чисто, форвард переприменяется без
ошибок), оба импортёра (`import-materials-bootstrap`, `import-ru-vendors-bootstrap`) прогнаны по
два раза подряд — количество строк не растёт на повторе (идемпотентность подтверждена, не
предположение). `pnpm lint`/`typecheck`/`test` в `apps/api` — зелёные.

Вне зоны этого прогона (сознательно): HTTP-эндпоинт над `compat.check` и UI-бейджи/фильтр —
Фаза 3 эпика (MF-410); полноценные автономные агенты-парсеры RU-брендов + календарь выхода
принтеров — отдельная будущая data-карточка (явно вынесено текстом эпика MF-33).

**Найдено и починено при верификации на dev (Data, 2026-07-10, тот же прогон MF-409).**
`20260710130000_compat_material_flags.sql` (Фаза 1/MF-408) значилась применённой в
`schema_migrations`, но `requires_chamber`/`requires_drying`/`requires_direct_drive`/
`default_extruder_temp_c`/`default_bed_temp_c` на `material_types` на деле не было: до
фикса коллизии таймстемпов `0ab5f69` (MF-746 follow-up) под тем же номером `20260710130000`
существовал ещё один файл (`marketplace_metrics_views.sql`), и dbmate записал версию как
выполненную, не прогнав саму `compat_material_flags`. Симптом нашёлся не в CI (юнит-тесты
`compat.check` — чистая функция, БД не видят), а прямым `psql`-осмотром `material_types` на
dev. Почин — новая миграция `20260710260000_compat_material_flags_recover.sql`, тот же DDL/
бэкфилл под свежим таймстемпом (переиздать файл под старым номером бессмысленно — dbmate его
не тронет, версия уже "занята"). Проверено на одноразовом Postgres 16: форвард/бэк/форвард с
чистого состояния (миграция — no-op, раз 130000 сама отработала) и отдельно смоделированный
битый сценарий (колонки руками дропнуты + запись 260000 удалена из `schema_migrations`) —
восстанавливает колонки и бэкфилл идентично оригиналу. Задеплоено на dev, подтверждено live
(`\d material_types` показывает все 5 колонок, бэкфилл на реальных данных: abs/asa/pc→chamber,
pa/pc→drying, tpu→direct_drive). Смержено в `main` (`5d700a4`) тем же прогоном — на любой
среде, где случилась та же коллизия (включая прод, если деплой туда попал в то же окно),
тот же симптом чинится тем же способом.

Заодно — то, что «Проверено локально (`sbx_mf409`...)» выше означало прогон на ОДНОРАЗОВОЙ
песочнице, не на реальном dev: `portal_dev` до этого прогона содержал только 24 материала/
4 SKU/25 вендоров (ручной ввод MF-31, RU-слоя не было). Оба импортёра запущены по-настоящему
против dev (`DATABASE_URL` из `portal.api-dev.env`, дважды подряд — идемпотентность
подтверждена на реальных данных, не на песочнице): `vendors` 25→92, `materials` 24→253,
`material_variants` 4→4203, все 5 RU-вендоров (`rec`/`bestfilament`/`fdplast`/`picaso-3d`/
`filamentarno`) на месте — «Готово когда» эпика («в БД есть хотя бы часть RU-филаментов/
принтеров») закрыто фактическими строками, не тестом на пустой БД.

### Лента (MF-420, Фаза 1 эпика MF-38 «Социальная лента и сообщества») — фундамент данных

Схема добавлена 2026-07-10 (`db/migrations/20260710150000_feed_foundation.sql`) — шаг 1 Фазы 1
(модель данных) + задел материализации (шаг 3, таблицы без наполнения). API постов/голосов/
комментариев/подписок — Фаза 2 (MF-421), антинакрутка/персонализация/`feed_events`-эмиттер —
Фаза 3 (MF-422), обе поверх этой схемы.

**Data-вердикт по переиспользованию:** сабы/подписки/голоса/комментарии — НЕ новые таблицы, а
расширение полиморфизма уже живущей схемы MF-35 (`communities`/`community_members`/`votes`/
`comments`, §«Комьюнити» выше). Тот же прецедент, что `model_tags`→`taggings`/`model_votes`→
`votes` (`community.foundation.md`): второй/третий потребитель полиморфной связки переключает
на неё, а не плодит узкую пару.

- «Саб» = `communities`, «подписка» = `community_members` — без изменений схемы.
- `votes.subject_type`: `+'feed_post'|'feed_comment'` (не `feed_post_votes`/`feed_comment_votes`);
  `'post'` уже занят Discourse-ответом MF-35, новым сущностям — свои значения. Добавлена
  `votes.trust_snapshot numeric(4,3)` nullable — задел Фазы 3 MF-422, не заполняется здесь.
- `comments.subject_type`: `+'feed_post'` (не `feed_comments`) — дерево (`parent_id`, MF-467)
  уже поддерживает произвольную глубину. Добавлены `comments.votes_up`/`votes_down`.
- `taggings.subject_type`: `+'community'` — таксономия сабов через `tags` (MF-11), не дублируя.
- **Новая сущность — только `feed_posts`** (не `posts`, занято MF-35 Discourse-ответом): 3 типа
  `model_link`/`media`/`text` (домен `domain.model.md` §«Контент», Reddit-слой v2-наброска),
  `community_id` nullable, `model_id`/`media_s3_key` — цель типа под check-констрейнт.
  `votes_up`/`votes_down`/`comments_count` — денорм, тот же паттерн, что везде в схеме.
- `post_score` — материализация Hot/Best/Controversial (`double precision`, индекс на каждый
  desc). Top(окно)/New не материализуются: Top — запрос по `votes.created_at` в окне (Фаза 2),
  New — сортировка по `feed_posts.created_at` (`feed_posts_visible_created_idx`). `EXPLAIN` на
  20K строк подтверждает Index Scan по каждому из четырёх, ни разу seq scan/формула на лету.
- `feed_events` — implicit-сигналы (view/read_complete/model_click/download/favorite/
  time_on_post/vote/comment/remix), НЕ то же самое, что `events` (`analytics.events.md`) —
  разный consumer (ML-персонализация/MF-12 vs 152-ФЗ-consent-gated продуктовая воронка).

**Формулы** — `apps/api/src/modules/feed/domain/ranking.ts`, чистые функции без БД (`hotScore`/`bestScore`/
`topScore`/`controversialScore`/`newScore`), юнит-тесты на эталонные кейсы карточки. **Data-
вердикт по Hot:** карточка даёт формулу со знаком у временнóго члена
(`log10(max(1,|U−D|)) + sign(U−D)·(t−epoch)/45000`), что при down≫up даёт большой
ПОЛОЖИТЕЛЬНЫЙ вклад от order — заминусованный контент лез бы в Hot наравне с популярным.
Реализована каноническая формула Reddit (знак у order, `reddit/r2/r2/lib/db/_sorts.py`),
расхождение — в коде и здесь; эталонные кейсы карточки проходят в обеих версиях. Эпоха —
`HOT_EPOCH_SECONDS=1782864000` (2026-07-01T00:00:00Z, явной даты запуска портала в доках нет,
округлено перед первым коммитом репо 2026-07-02/переводом DNS 2026-07-03).

**Материализация — воркер, не API-хендлер.** `apps/api/src/modules/feed/infrastructure/scores.ts`:
`recomputePostScore`/`batchRecomputeVisible`. Канал «голос→пересчёт» — `pg_notify
('post_score_recompute', postId)` внутри транзакции голоса (Фаза 2 вызывает), не отдельная
таблица-очередь. `scripts/feed-score-worker.ts` — LISTEN + периодический батч (systemd-сервис,
заводит Ops), батч страхует пропущенные (не durable) уведомления и двигает time-decay Hot.

**Переименована `20260710000000_...`→`20260710150000_...`** (до промоушена): `dbmate` пишет
применённые версии по числовому префиксу файла, не по содержимому — конкурентный агент уже
занял версию `20260710000000` своей миграцией на dev-БД, из-за чего под тем же префиксом
`feed_foundation` молча пропускался бы `dbmate up` («уже применена») и не создал бы ни одной
из своих таблиц/колонок ни на dev, ни на проде. Обнаружено сверкой `schema_migrations` на
живой dev-БД (только SELECT). Новый префикс проверен форвардом на чистом Postgres.

Проверено локально (docker Postgres 16, `dbmate`): идемпотентна, прогнана вперёд→назад→вперёд
(`rollback` возвращает `votes`/`comments`/`taggings` check-констрейнты к исходному виду,
`users`/`communities`/`votes`/`comments` целы). Check-констрейнты проверены прямыми вставками:
`model_link`/`media` без обязательного поля отклоняются, повторный голос того же юзера на тот
же subject отклоняется (идемпотентность по PK). `pnpm lint`/`typecheck`/`test` в `apps/api` —
зелёные (22 новых теста: 16 `ranking.test.ts` + 6 `scores.test.ts`).

### Парк устройств и агент (MF-390, Фаза 1 эпика MF-26) — модель данных реализована

Схема добавлена 2026-07-10 (`db/migrations/20260710310000_device_fleet_foundation.sql`) — только
шаг «модель данных» Фазы 1 эпика MF-26 (привязка принтеров к пользователю и удалённое управление
парком через локального агента+relay). Relay (stateful WS-туннель, outbound-only) и enroll-флоу
(генерация/выдача кода, установка агента, обмен на креды, mTLS) — вне территории Data, следующий
шаг Back поверх этой схемы (см. трекер 007).

**Data-вердикт по переиспользованию (главное решение).** Карточка MF-390 просила отдельную
сущность `device`. Вето: это дублировало бы уже живую `user_printers` — та же декларативная
запись «у юзера есть такой-то принтер», что и ручной ввод (`link_source='manual'`) или синк
через Prusa Connect (`link_source='connector'`, см. «Коннектор Prusa Connect» выше). Агент+relay —
третий способ узнать о принтере, не новый факт владения, поэтому `user_printers` расширена (не
задублирована): `agent_id` (FK на новую `agents`, nullable), `firmware_class` (`text+check`
`klipper`/`octoprint`/`bambu`/`prusa`/`creality`, принцип 2), `last_seen_at`, `capabilities jsonb`
(живые возможности — камера/AMS/мультиэкструзия/белый список команд, принцип 5 — растёт с каждым
новым протоколом Ф2/Ф4, в отличие от статичного каталожного `machines.specs`), `fleet_id`/
`zone_id` (см. ниже), `link_source` получил третье значение `'agent'`.

- **`agents`** — процесс на стороне юзера (Docker/Pi/ПК), НЕ 1:1 с устройством: один агент
  мультиплексирует несколько принтеров в одном relay-канале (карточка явно требует мультиплекс).
  `owner_id`, `version`, `channel` (`stable`/`beta`), `status` (`online`/`offline` — связность
  самого агентского процесса, не печатный статус конкретного принтера), `last_seen_at`.
- **`fleets`/`zones`** — группировка, заведена как задел (карточка: «fleet/zone как задел»),
  минимальные таблицы без индексов (принцип «индексы по реальным запросам, не на всякий случай») —
  появятся с первым UI-фильтром по ферме/зоне.
- **`device_shares`** — шаринг устройства ролями `owner`/`operator`/`viewer`/`guest` (карточка +
  эпик MF-26 §5 «Безопасность и изоляция»: только owner/operator шлют команды). `device_id` →
  `user_printers.id`, `unique(device_id, user_id)`. Владелец получает свою же строку `'owner'` при
  создании устройства — вставляет API (консистентность на api-слое, тот же паттерн, что денорм-
  счётчики по всей схеме), в БД не триггерится.
- **`device_audit_log`** — append-only, `action text` БЕЗ `check` намеренно: таксономия действий
  (`device.created`/`access.revoked`/`command.pause`/…) растёт вместе с командным слоем, который
  пишет Back поверх этой таблицы — констрейнтить её здесь означало бы миграцию-ремонт на каждую
  новую команду вне территории Data. `actor_user_id` nullable — системные события (relay пометил
  offline по таймауту хартбита) без человека-инициатора.
- **`device_state`** — горячий перезаписываемый снэпшот (ОДНА строка на устройство, PK=`device_id`).
  `status`/`progress`/`job_id` — реляционные (реально фильтруются дашбордом «что сейчас печатает»),
  `nozzle`/`bed`/`chamber`/`z-offset` из наброска карточки — в `metrics jsonb` (принцип 5: набор
  полей разный у Klipper/Bambu/Prusa, реляционная колонка на каждый вариант не масштабируется).
  Printer-специфичные имена в наброске карточки — ГРАНДФАЗЕРЕННОЕ исключение принципа 1 (см.
  `user_printers` выше): Фаза 1 эпика — явно Klipper/Moonraker only, не общее ядро.
- **`device_telemetry`** — ОТДЕЛЬНЫЙ временной ряд (карточка требует явно: не перетирает
  `device_state`), тот же `metrics jsonb`, но неизменяемый снимок момента времени. Retention-
  политика (карточка требует «с retention-политикой») сознательно НЕ реализована TTL/партициями
  этой миграцией — писателя (агента, реально пушащего телеметрию) ещё нет, заводить чистку под
  объём, которого не существует, — преждевременно (тот же YAGNI, что у стейджинг-таблиц
  парсер-агентов в § «Каталог филамента»); заводится отдельной карточкой, когда Back поднимет
  реальный push и станет виден настоящий объём.
- **`device_jobs`** — история печатей. `model_id` → `models`, nullable + `on delete set null`
  (печать не обязательно из каталога портала — G-code может быть залит вручную) — история принтера
  не должна стираться удалением модели. `file_name` — то, что видит юзер, если модели в каталоге
  нет.
- **`device_enroll_codes`** — только хранилище одноразового кода (карточка: TTL ≤15 мин, повторное
  использование отклоняется). `code_hash bytea unique` — sha256 самого кода (plaintext нигде не
  лежит, тот же принцип, что `ip_hash`/`identifier_hash` по всей схеме); `used_at`/`expires_at` —
  проверка одноразовости и TTL на уровне приложения (`UPDATE ... WHERE used_at IS NULL RETURNING`
  закрывает гонку редимпшена, без отдельного лока). Генерацию кода, редимпшн-эндпоинт и
  однострочную команду установки агента пишет Back — вне территории Data.

Проверено локально (docker Postgres 16, `dbmate`): миграция идемпотентна (повторный `up` чист),
прогнана вперёд→назад→вперёд (`rollback` дропает все новые таблицы + добавленные колонки
`user_printers`, откатывает `link_source`-констрейнт к исходному union, базовые
`users`/`user_printers`/`models` целы; re-forward воссоздаёт схему один в один). Функциональная
проверка прямыми SQL-вставками: seed-устройство (`user_printers` с `link_source='agent'`,
`agent_id`, `firmware_class='klipper'`) создаётся и читается одним join через
`user_printers → device_state → agents` (то, что будет делать API-хендлер `/printer/:id`);
`device_shares` с ролями `owner`/`operator` читается отдельно. Негативные проверки: невалидный
`firmware_class`/`role` в `device_shares` отклонён `check`-констрейнтом, повторный
`(device_id, user_id)` в `device_shares` и повторный `code_hash` в `device_enroll_codes` отклонены
`unique`-констрейнтом. `EXPLAIN` на `device_telemetry`/`device_shares` подтверждает Index Scan по
`device_telemetry_device_recorded_idx`/`device_shares_user_idx`, не seq scan. `pnpm lint`/
`typecheck` в `apps/api` — зелёные.

Не сделано этой миграцией (сознательно, вне территории Data): relay (WS-туннель, мультиплекс,
хартбит/детерминированный offline, rate-limit/backpressure — выбор хостинга CF Durable Objects vs
VDS ещё не сделан), enroll-эндпоинты (генерация/редимпшн кода, установочный скрипт/Docker-образ,
mTLS/подписанный токен обмена на креды сессии), seed-запись устройства «через API» (эта миграция
доказывает схему прямыми SQL-вставками — HTTP-эндпоинт создания устройства ещё не написан). Это
Back-реализация поверх готовой схемы — заведены сабкарты под MF-390 (см. трекер 007).

### `printers` — канон, провенанс по листу, не по секции (MF-877, ревизия MF-878) — решено

Канон `printers` (`20260710430000_printers_canon_researcher.sql`, вердикт CTO MF-839 §1) уже
поднят и задокументирован в контексте следующей миграции (см. «Уровни поддержки» ниже) — здесь
фиксируется ревизия механизма провенанса, сделанная в рамках MF-877 (свод колонок/провенанса с
`docs/research/printer.schema.json`).

**Находка:** первая реализация (`apps/api/src/printers/research.route.ts`, MF-878) вела
`field_provenance`/конфликт-детект на уровне ЦЕЛОЙ секции схемы (`bed`, `hotend`, `price`, …:
`SPEC_SECTIONS` из `printers/contract.ts`), а не отдельного листового поля (`bed.max_temp_c`).
Живой прогон (`docker compose` + новый тест `printers/research.route.test.ts` — «keeps a sibling
leaf field from an earlier source…») показал: вендор-сейв `bed: {max_temp_c: 100}`, затем
ресёрчер-сейв `bed: {surface: "PEI"}` (не повторяя `max_temp_c`, — ожидаемая эргономика §8.3
«нашёл три поля из тридцати, должен уметь их отдать») **молча стирал `max_temp_c`**: секция
целиком заменялась телом второго запроса. Это прямое нарушение принципа «провенанс на поле» (§1)
и явного текста printers.research.md §8.4 («молчаливый overwrite запрещён»), а не гипотетический
край — сам контракт `field_sources` там же в §8.3 уже описан как `{"hotend.max_temp_c": 0}`
(дотнотация листа), то есть секционная гранулярность MF-878 была отклонением от уже
задокументированного контракта, а не альтернативным дизайном.

**Решение (Data, веб-вердикт по MF-877):** провенанс/конфликт-детект для секций-объектов
(`build_volume`, `hotend`, `bed`, `speed`, `multimaterial`, `connectivity`, `price`,
`dimensions_mm`, `media` — `LEAF_PROVENANCE_SECTIONS` в `contract.ts`) переведён на уровень
листа: `field_provenance` хранит записи по пути `"bed.max_temp_c"`, конфликт при параллельной
правке того же листа детектируется и подсвечивается отдельно от несвязанных листьев той же
секции (которые по-прежнему мержатся молча — ровно §8.4). Секции-массивы
(`toolhead_extras`/`materials_supported`/`unique_features`/`aliases`/`sources`) и скалярные
верхнеуровневые поля (`brand`/`model`/`status`/…) остаются как были — целиком-заменяемым
значением с провенансом на само поле: у списков нет естественного «листа» для точечного мержа,
переизобретать object-diff для них здесь не нужно (YAGNI, MF-877 просит закрыть именно
провал per-field провенанса схемы, не мигрировать всё на новую модель).

Проверено (sandbox-db, `sbx_data_mf877` — копия `portal_dev`): `pnpm test` в `apps/api` зелёный
(`printers/research.route.test.ts` — 9/9, `catalog/printers.test.ts` — 5/5, `tsc --noEmit`/`eslint
src/printers` чисто); новый тест воспроизводит находку до фикса (провалился на исходном коде,
проверено вручную) и проходит после. Существующие тесты MF-878 на конфликт/`resolve_conflicts`
обновлены под дотнотацию (`price` → `price.msrp_usd`) — семантика (конфликт не тонет молча,
несвязанные поля мержатся) не изменилась, изменилась только гранулярность «поля».

Не сделано этой правкой (сознательно, вне скоупа): миграция данных для старых `field_provenance`
записей — прод-таблица `printers` пуста/dev-only на момент правки (заливка MF-878/агент
Researcher-Creality ещё не запущена в проде), старые секционные ключи просто не появятся; ре-визит
`user_printers.printer_id` (FK на `machines`, найденный риск «раздвоенного канона» §9.4
printers.research.md — колонка уже занята коннектором Prusa Connect) — отдельный, более крупный
шаг expand→migrate→contract, не блокирует текущую схему `printers` и не входит в «Готово когда»
MF-877; решение по нему — следующая карточка Data, не эта правка.

### Демо-мастерская → прообраз БД (MF-23 Фаза 1 / MF-381) — черновая DDL, не мигрировано

Сверка кликабельного демо `3dmake` (`DEMO.md`/`app.js`/`data.js`, vanilla JS + мок) со связями

бо́льшая часть «не спроектированных» сущностей из тела эпика **уже реализована под другими
именами**. Ниже — сверка (что уже есть → не дублировать) и черновая DDL только для реально
недостающего (модель→печать, версионирование, коммерция). Всё это **прообраз для будущей
миграции**, не сама миграция — реализация уйдёт в Фазу 2/3 того же эпика (MF-382/383) отдельными
карточками, тут фиксируется решение и форма.

**Сверка «демо-сущность → прод-таблица» (не заводить второй раз):**

Не покрыто компат-движком: `bedOk` в демо требует ещё «материал ЗАРЯЖЕН в конкретный принтер
прямо сейчас», а `compat.check` сегодня работает на уровне каталога (эта модель принтера
совместима с этим материалом вообще), не на уровне «у ЭТОГО принтера ЭТОГО юзера сейчас заряжен
ЭТОТ цвет/остаток» — см. `spool`/`stock_lot` ниже, это и есть реальный пробел P0.

**1. `spool`/`stock_lot` → расширение `user_materials`, не новая таблица.**
`user_materials` (MF-626) уже моделирует ровно «катушка у юзера»: `user_id`+`material_id`+
`variant_id`(nullable)+`note`, без `unique` — юзер легитимно держит несколько катушек одного
варианта. Не хватает двух вещей, которые демо считает первоклассными (`whereLoaded`,
пуш-лента срочности `left < needGrams`): «в каком принтере эта катушка сейчас» и «сколько
осталось». Решение — добавить колонки, не новую сущность (та же катушка не мигрирует между
`user_materials` и гипотетическим `spools`):

```sql
-- прообраз, будет отдельной миграцией Фазы 2/3 MF-23, expand-only:
alter table user_materials add column if not exists printer_id uuid
  references user_printers(id) on delete set null; -- null = на складе/не заряжена никуда
alter table user_materials add column if not exists remaining_g int
  check (remaining_g is null or remaining_g >= 0); -- null = остаток неизвестен (нет датчика — деградация по DEMO.md §риски)
alter table user_materials add column if not exists loaded_at timestamptz; -- когда заряжена в printer_id
create index if not exists user_materials_printer_idx on user_materials (printer_id) where printer_id is not null;
```

`remaining_g` — оценка, не датчик (у большинства принтеров его нет, см. риск «телеметрия» в теле
MF-23) — источник заполнения (ручной ввод юзера vs пересчёт по времени печати) — вопрос Фазы 2/3
(API-контур MF-382), тут только колонка. `stock_lot` (агрегат склада мастерской: «сколько кг PLA
серого на полке A16» из демо-фермы) — это `sum(remaining_g) group by material_id/variant_id`
поверх `user_materials` того же `user_id`/будущего `fleet_id` (MF-390 уже завела `fleets`/`zones`),
а не отдельная таблица — считается на чтении, не денормализуется, пока нет замеров нагрузки.

**2. Версионирование модели / soft-delete — закрывает открытый вопрос issues/007.**
Решение: старая версия остаётся доступной тем, кто уже скачал/купил (демо это подразумевает,
Валерий не отменял) — модель добавляет `model_versions`, `model_files` привязывается к версии
номером (не переносится на новую FK-цепочку — `model_files.model_id` был бы избыточен, оставляем
как есть, версия — дополнительный тег на файле того же `model_id`):

```sql
-- прообраз, будущая миграция:
create table if not exists model_versions (
  id uuid primary key default gen_random_uuid(),
  model_id uuid not null references models(id) on delete cascade,
  version_number int not null check (version_number > 0),
  changelog text,
  created_at timestamptz not null default now(),
  unique (model_id, version_number)
);
alter table models add column if not exists current_version int not null default 1;
alter table model_files add column if not exists version_number int not null default 1;
-- скачивание уже логируется (model_download_log, MF-735) — довязать версию, чтобы «выдать файл,
-- который юзер реально купил», не последний:
alter table model_download_log add column if not exists version_number int;
```

Soft-delete — тот же паттерн, что `comments.deleted_at`/`idea_comments.deleted_at` (не
`status`-enum: `models.status` — конвейер загрузки/конвертации, удаление автором — другая ось,
смешивать нельзя, тот же вывод, что уже сделан для `comments` в MF-826):

```sql
alter table models add column if not exists deleted_at timestamptz; -- автор снял модель с публикации
```
Удалённая модель (`deleted_at is not null`) пропадает из каталога/поиска, но её файлы и
`model_versions` не трогаются — у купивших доступ остаётся (то же обоснование, что «право на
забвение vs уже выданный файл» ниже по 152-ФЗ треку в issues/007, только для авторского, не
персонального удаления).

**3. Коммерция — `order`/`order_stage`/`payout`/`ledger_entry` (P1, реально не начато).**
`make`-галерея уже есть (см. таблицу сверки) — здесь только оплачиваемые B2B-заказы и леджер.
`order_stage` — не отдельная таблица (сверка с демо: стадии — конечный список, меняется редко),
`status` text+check на `orders`, тот же паттерн, что везде в схеме (`models.status`,
`machines.status`) вместо отдельного справочника ради 5 значений:

```sql
-- прообраз P1, будущая миграция:
create table if not exists orders (
  id uuid primary key default gen_random_uuid(),
  seller_id uuid not null references users(id), -- владелец мастерской, тот же users, что models.owner_id
  client_id uuid not null references users(id), -- заказчик; гостевой заказ — вне MVP (риск демо «гость != владелец»)
  model_id uuid references models(id) on delete set null, -- печать по каталогу; null — кастомный заказ без модели портала
  status text not null default 'new' check (status in
    ('new', 'quoted', 'accepted', 'printing', 'ready', 'shipped', 'completed', 'cancelled')),
  material_cost_minor bigint, -- смета в минорных единицах (копейки) — не float для денег
  labor_cost_minor bigint,
  total_minor bigint,
  currency text not null default 'RUB',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create index if not exists orders_seller_idx on orders (seller_id, created_at desc);
create index if not exists orders_client_idx on orders (client_id, created_at desc);

-- Леджер, не изменяемое поле баланса (та же причина, что reputation_events — append-only,
-- баланс = agg на чтении, не денормализованное поле, которое можно рассинхронить update'ом):
create table if not exists ledger_entries (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references users(id) on delete restrict, -- restrict: денежная история не удаляется каскадом
  amount_minor bigint not null, -- знак: + начисление, - списание/выплата
  currency text not null default 'RUB',
  reason text not null check (reason in ('order_payout', 'order_refund', 'platform_fee', 'manual_adjustment')),
  order_id uuid references orders(id) on delete set null,
  created_at timestamptz not null default now()
);
create index if not exists ledger_entries_user_idx on ledger_entries (user_id, created_at desc);

-- payout — фиксация вывода со счёта (эквайринг/самозанятость/налоги РФ — вне эпика, здесь
-- только запись факта и статуса, не сам провайдер):
create table if not exists payouts (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references users(id) on delete restrict,
  amount_minor bigint not null check (amount_minor > 0),
  currency text not null default 'RUB',
  status text not null default 'pending' check (status in ('pending', 'processing', 'paid', 'failed')),
  ledger_entry_id uuid references ledger_entries(id) on delete set null,
  created_at timestamptz not null default now(),
  paid_at timestamptz
);
create index if not exists payouts_user_idx on payouts (user_id, created_at desc);
```

Баланс юзера = `sum(amount_minor) from ledger_entries where user_id = ...` на чтении — тот же
инвариант, что явно требует тело эпика («не изменяемое поле баланса»). `payouts.status` — не
дублирует `ledger_entries` (запись в леджере создаётся при факте выплаты, не при заявке — заявка
`pending` ещё не факт денежного движения).

**Не сделано этим прогоном (сознательно):** сами миграции (это ER/DDL-прообраз, не `db/migrations/
*.sql` — исполнение уйдёт в Фазу 2/3 MF-23 отдельной карточкой, когда экраны/API её действительно
запросят, YAGNI по тому же принципу, что уже применён к stage-таблицам парсер-агентов выше);
API/UI над `orders`/`ledger_entries`/`payouts` — Fullstack/Back; реальный алгоритм `remaining_g`
(ручной ввод vs расчёт по времени печати) — открытый вопрос для Фазы 2, экраны+API-контур+спека
`printerFit`/`bedOk`/`whereLoaded` — [mvp.chain.md](mvp.chain.md) (MF-382, 2026-07-19).

### Фундамент витрины мастера — сущность «мастер» и «заявка» (CTO-решение, MF-30, разбор блокера MF-992/995/996, 2026-07-11)

Fullstack (MF-995 `master_services`, MF-998 Data-вердикт) уже начал строить `master_services.master_id
→ users(id)` до того, как фаза 1 эпика MF-30 (MF-399, «завести сущность мастер») стартовала — обе
карточки MF-399 (фундамент: мастер+storefront+парк) и MF-996 («поток заявок») были ещё `todo`, когда
MF-401 (фаза 3: отзывы/галерея/подписки) уже нарезал MF-991/992/993 поверх несуществующего фундамента.
Решение ниже закрывает архитектурный вопрос, чтобы MF-995/996/992/991/993 не изобретали несовместимые
схемы параллельно; **порядок исполнения (не архитектура) — за Lead**, см. хвост секции.

**1. «Мастер» — роль поверх `users`, отдельной таблицы `masters` НЕ заводим.**
Основание: тот же вывод, что уже принят для `orders.seller_id`/`master_services.master_id` (оба —
`references users(id)`, не гипотетическая `masters(id)`) — «мастер» не отдельная личность, а профиль
существующего аккаунта (auth MF-14, ЛК MF-15 уже готовы). Один `user` либо мастер, либо нет; связка
многие-люди-одна-ферма — не в v2 (см. открытый вопрос MF-30 «один аккаунт — одна ферма или несколько»,
откладывается до появления первого запроса). Реализация роли — не новая таблица, а два поля:
```sql
-- прообраз MF-399, будущая миграция:
alter table users add column if not exists is_master boolean not null default false;
alter table users add column if not exists master_profile jsonb; -- {headline, description, city, slogan}
                                                                    -- шапка storefront — jsonb, не колонки:
                                                                    -- меняется чаще схемы, нет что фильтрует SQL
```
RBAC-роль `master` (MF-20) — читает `users.is_master`, не отдельный grant; необнаружимый публичный ID
storefront — тот же `users.id` (уже `gen_random_uuid()`, см. `ids.policy.md`, тот же вывод, что там уже
принят для моделей/принтеров: честный крипто-случайный PK и есть публичный ID, второй `public_id` не
нужен).

**2. «Заявка» (print request) — НЕ то же самое, что черновой `orders`/`ledger_entries` выше.**
`orders` (§ «Демо-мастерская», P1) — расчётный B2C-заказ по каталогу моделей с леджером/выплатами
(граница с MF-17, деньги). «Заявка» мастеру (MF-400/MF-996) — включает торг ДО денег (обсуждение цены,
без гарантии сделки) и живёт по своей воронке статусов из тела MF-400, которая не совпадает 1:1 со
статусами `orders`. Две разные сущности, разделяем явно, не перегружаем `orders.status`.

> **Обновление 2026-07-17 (Fullstack, разбор блокера MF-992):** черновик DDL ниже — то, что было
> спроектировано ДО реализации. Фактическую схему завизировал Data вердиктом «ок с правками» в
> [MF-999](mention://issue/d1f6106e-9c2b-4b15-920b-26472c8b19b4) (done 2026-07-16) — таблица называется
> **`print_requests`**, не `service_requests`, и расходится с черновиком по составу колонок/статусов
> (детали разошедшихся мест — под DDL). Секция ниже приведена к фактически одобренной схеме; DDL —
> живая миграция `apps/api/db/migrations/20260711180000_print_requests.sql` (MF-996), не прообраз.

```sql
-- фактическая схема (MF-996, вердикт MF-999, 2026-07-11/16):
create table if not exists print_requests (
  id uuid primary key default gen_random_uuid(),
  master_id uuid not null references users(id) on delete cascade,
  client_id uuid not null references users(id) on delete cascade,
  model_id uuid references models(id) on delete set null, -- печать по каталожной модели; null — свой файл/кастом
  model_file_id uuid references model_files(id) on delete set null, -- клиентская загрузка вне каталога
  material_id uuid references materials(id) on delete set null,
  material_variant_id uuid references material_variants(id) on delete set null,
  quantity int not null default 1 check (quantity > 0),
  due_date date,
  client_note text,
  master_note text,
  status text not null default 'new' check (status in
    ('new', 'discussion', 'in_work', 'done', 'rejected')), -- 'done' = «готово», гейт для отзыва
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create index if not exists print_requests_master_active_idx on print_requests (master_id, created_at desc)
  where status not in ('done', 'rejected');
create index if not exists print_requests_master_history_idx on print_requests (master_id, created_at desc)
  where status in ('done', 'rejected');
create index if not exists print_requests_client_idx on print_requests (client_id, created_at desc);
```
Разошлось с черновиком (зафиксировано вердиктом MF-999, не опечатка): `master_service_id` —
отсутствует, привязка к конкретной услуге каталога отложена (expand-only колонка+FK будущей миграцией,
когда MF-995 будет в проде — заявка пока привязана к мастеру напрямую, не к услуге); `material` (text) →
`material_id`/`material_variant_id` (FK на `materials`/`material_variants`, не свободный текст);

**3. Отзыв (MF-992) — FK на `print_requests`, не на `orders`.**
```sql
-- прообраз MF-992, будущая миграция (MF-992 ещё не начат, схема не завизирована отдельным вердиктом):
create table if not exists master_reviews (
  id uuid primary key default gen_random_uuid(),
  print_request_id uuid not null references print_requests(id) on delete cascade,
  author_id uuid not null references users(id), -- = print_requests.client_id на момент отзыва, проверяется в API, не FK-constraint'ом
  master_id uuid not null references users(id), -- денормализация ради индекса «рейтинг мастера» без join через print_requests на каждый read
  rating smallint not null check (rating between 1 and 5),
  body text,
  created_at timestamptz not null default now(),

create index if not exists master_reviews_master_idx on master_reviews (master_id, created_at desc);
```

### Каталог услуг мастера — `master_services` (MF-995/MF-400) — реализовано

### Биллинг: цена модели → покупка → баланс автора → выплата (MF-363, Фаза 1 эпика MF-17) — реализовано

Спроектировано и задеплоено локально (2026-07-11, MF-363, шаг 1 фазы). Миграция
`apps/api/db/migrations/20260711200000_billing_foundation.sql`, прогнана вперёд-назад на
песочнице-копии dev (`sandbox-db`), инвариант леджера («сумма проводок по покупке = цена»)
проверен вручную вставкой тестовой покупки — сходится.

**Сущности:**
- `models.price_minor`/`models.currency` — expand существующей таблицы (не новая), 0 = бесплатно
  (MVP-поведение не меняется), currency зафиксирована `'RUB'` text-колонкой, тот же приём, что у
  `status`-полей в схеме (мультивалютность вне скоупа v3).
- `purchases` — факт покупки, `seller_id`/`price_minor`/split — снэпшот на момент покупки (не
  плывёт при смене владельца модели или take-rate в конфиге). Частичный уникальный индекс
  `(buyer_id, model_id) where status='paid'` — БД сама не даёт задвоить оплаченную покупку гонкой
  параллельных запросов, гейт скачивания (MF-365) делает `EXISTS` по этой же таблице.
- `payouts` — заявка/факт выплаты, `requisites jsonb` (шифрование/маскирование — вне этой карточки,
  см. `SECURITY.md` перед реализацией API).
- `ledger_entries` — append-only леджер, тот же инвариант, что уже принят для
  `reputation_events`/чернового `orders`/`ledger_entries` (§ «Демо-мастерская» выше): баланс НЕ
  хранится изменяемым полем, агрегируется на чтении. Двойная запись на покупку:
  `account='seller_balance'` (доля автора) + `account='platform_revenue'` (доля платформы,
  `user_id null`). `available_at` — механизм холда без отдельной мутируемой таблицы-баланса:
  «доступно» = `sum(amount_minor) where account='seller_balance' and available_at <= now()`,
  «в холде» — тот же `sum` с `available_at > now()`. Срок холда — конфиг `apps/api`, не в БД.

**Решение (не буквально по тексту карточки):** карточка называла `author_balance` отдельной
таблицей «доступно/в холде» — вместо неё расширен `ledger_entries` колонкой `available_at`,
тот же принцип, что уже применён к балансу в § «Демо-мастерская» и к `reputation_score`: не
заводить мутируемый агрегат, который можно рассинхронить `UPDATE`'ом, когда агрегат на чтении
даёт тот же результат. Что переубедит: если агрегат на `ledger_entries` станет узким местом по
измеренной нагрузке — тогда денормализованное поле-кэш с пересчётом по триггеру, не раньше.

**Take-rate — не в БД.** Доля платформы вычисляется в `apps/api` из конфигурируемого коэффициента
(env/константа), в `purchases` сохраняется уже посчитанный на момент покупки split — исторические
продажи не должны задним числом менять сумму при смене коэффициента в конфиге.

### HTTP-слой эквайринга: создание платежа + вебхук (MF-1025, шаг 2 MF-364) — реализовано

`apps/api/src/billing/{provider,ledger,contract,routes}.ts`, 2026-07-17. `POST /purchases`
(auth-гейт, снэпшот цены/split в `purchases`, вызов ЮKassa Payments API `POST /v3/payments`,
`Idempotence-Key` = `purchases.id`) и `POST /billing/webhooks/yookassa` (открытый путь,
`OPEN_PATH_PREFIXES`, машинный вызов провайдера без `portal_session`).

- **Подпись вебхука.** ЮKassa не подписывает тело нотификации (нет HMAC/заголовка — только
  IP-allowlist их нотификатора в их доке). Вместо доверия телу вебхук использует его ТОЛЬКО
  чтобы узнать, какой `provider_payment_id` перепроверить, затем делает собственный
  аутентифицированный `GET /v3/payments/:id` (`provider.ts::fetchPayment`) — реальные
  `status`/`paid` берутся из этого ответа. Так подделать вебхук нельзя, не зная `secretKey`.
- **Идемпотентность.** `event_id` = `` `${event}:${object.id}` `` (у ЮKassa нет отдельного id
  самой нотификации) → `INSERT ... ON CONFLICT (provider, event_id) DO NOTHING` в
  `payment_webhook_events` до любой мутации; 0 вставленных строк = уже обработано, no-op.
  Дополнительная защита от гонки параллельных доставок — `UPDATE purchases ... WHERE status =
  'pending'`, 0 обновлённых строк = другая доставка уже увела статус, ledger не трогается.
- **Ledger/take-rate.** `ledger.ts::splitAmount` — платформенная доля из `BILLING_TAKE_RATE_BPS`
  (дефолт 20%, не зафиксировано оператором), `creditPurchaseLedger` — двойная запись
  seller_balance/platform_revenue в той же транзакции, что перевод `purchases` в `paid`.
  `holdAvailableAt` — холд `BILLING_HOLD_DAYS` (дефолт 14 дней).
- **Аналитика.** На успешный платёж эмитится `purchase` (`analytics/events.ts`) с
  `{model_id, seller_id, amount}` — контракт, ожидаемый `metrics.marketplace.md` § «Take-rate/
  GMV» (amount в рублях, не в минорных единицах БД); `marketplace_gmv_take_rate` перестаёт быть
  всегда-нулевой вьюхой без новой миграции.
- **Тесты.** `provider.test.ts` (мок `fetch`), `ledger.test.ts` (split/hold + реальный insert в
  sandbox-БД), `routes.test.ts` (мок `./provider.ts`, реальная БД): 401/400/404/422/409/502 на
  `POST /purchases`, и на вебхуке — успешный `paid` с корректным ledger, повторная доставка того
  же события не дублирует проводку (`fetchPayment` вызван ровно 1 раз), `canceled` не трогает
  ledger, неизвестный `provider_payment_id` — no-op, `waiting_for_capture` игнорируется.

**⚠️ Блокер на живую проверку (не на код).** Готово-критерий карточки — "тестовая оплата
переводит purchase в paid" — требует РЕАЛЬНОГО тестового платежа у ЮKassa. Секреты, выданные
Ops (MF-1024, `YOOKASSA_AGENT_ID`/`YOOKASSA_PAYOUTS_SECRET_KEY`), — это Payouts API (выплаты
авторам, MF-1027), НЕ Payments API (приём оплаты, нужный именно этой карточке) — два разных
продукта ЮKassa с разными кредами. `YOOKASSA_SHOP_ID` для Payments API не заведён. Код рабочий и
покрыт тестами с мок-провайдером; живой прогон на dev.3mf.tech до появления `YOOKASSA_SHOP_ID`/
корректного `YOOKASSA_SECRET_KEY` невозможен — см. `SECURITY.md` § «Секреты».

### Выплаты авторам: баланс, заявка на вывод, ручная обработка (MF-364 фаза 2 шаг 3) — реализовано

`apps/api/src/billing/{ledger,routes}.ts`, 2026-07-19. Закрывает и разрыв шага 2 (веб уже вызывал
`GET /purchases`/`GET /purchases/:id` из `purchases.tsx`, бэкенд их не отдавал) — оба роута
добавлены тем же проходом.

- **Баланс — по-прежнему agg на чтении** (`computeBalance`), не мутируемое поле: `available` =
  `sum(amount_minor) where account='seller_balance' and available_at <= now()`, `hold` — тот же
  agg с `available_at > now()`. `GET /me/balance` только читает.
- **`GET /sales`** — список оплаченных продаж автора (`seller_amount_minor`, не `price_minor` —
  доля автора после take-rate, тот же снэпшот-принцип, что у `purchases`).
- **Списание — при заявке, не при факте выплаты** (готово-критерий карточки: «баланс уменьшается
  на сумму+в холд» сразу при `POST /payouts`). `ledger_entries.reason='payout_debit'` уже был
  разрешён check-констрейнтом `billing_foundation` миграции — новой миграции под этот шаг не
  потребовалось. Гонка параллельных заявок одного автора закрыта
  `pg_advisory_xact_lock(hashtext(user_id))` внутри транзакции POST /payouts: без него два
  одновременных запроса могли бы оба пройти проверку баланса до своей вставки.
- **Ручная обработка на старте** (card допускает «либо Payouts API, либо ручная обработка»):
  `PATCH /payouts/:id` — гейт `requireStaff` (`users.is_staff`, тот же, что `/ideas/:id/status` и
  `/users/:id/ban`), переходы `pending → processing/failed`, `processing → paid/failed`.
  `failed` возвращает списанное на баланс — `reversePayoutLedger`, `reason='manual_adjustment'`
  (`payout_debit` зарезервирован за самим списанием заявки, реверс — не он). `paid` ledger не
  трогает — сумма уже списана в момент заявки. Автоматический вызов ЮKassa Payouts API — вне
  скоупа этого шага, `YOOKASSA_AGENT_ID`/`YOOKASSA_PAYOUTS_SECRET_KEY` заведены в `.env.example`
  как задел, но кодом пока не читаются (см. `SECURITY.md` § «Секреты»).
- **Веб (кабинет автора)** — `apps/web/src/market/payouts.tsx` (`PayoutsPanel`), в
  `profile.workshop.tsx` рядом с `PurchasesPanel`: доступно/в холде (`StatTile`), форма заявки
  (сумма + метод карта/СБП/счёт), список продаж, история заявок со статусом. Панель не рендерится,
  если у автора одновременно нулевой баланс, нет продаж и нет заявок — не занимает место в
  «Мастерской» до первой продажи.
- **Тесты.** `ledger.test.ts` — `computeBalance` (available/hold, чужие проводки не подмешиваются),
  `debitPayoutLedger`/`reversePayoutLedger` (баланс уменьшается/восстанавливается). `routes.test.ts`
  — 401/400/422 на `POST /payouts` (невалидная сумма/реквизиты/недостаточный баланс), 403/404/409
  на `PATCH /payouts/:id` (не staff/неизвестный payout/недопустимый переход), `failed` восстанавливает
  баланс, `paid` не трогает ledger повторно. `payouts.test.tsx` (web) — баланс/продажи/история
  рендерятся, панель скрыта при полностью пустом состоянии, заявка создаётся и список обновляется.

## Решённые вопросы (ответы Валерия, 2026-07-05)

### Кэш переиспользования слайс-результатов (MF-1073, вердикт Data к MF-1072/MF-1053) — вердикт, схема прогнана вперёд-назад

MVP-планка карточки: точный хэш-мэтч (без fuzzy-дедупа геометрий — это на будущее, v2/v3 по
`docs/architecture/data.fragmentation.md` §8). Схема реализует §1 того документа
(`slice_key = hash(model_hash · profile_hash · config_fingerprint)`) поверх уже существующей
`slice_jobs` (MF-958) и `slicer_profiles` (MF-411) — без новой дублирующей схемы bed/nozzle
профилей, как просила карточка: `bed_profile_id`/`nozzle_profile_id` из тела карточки — это
`slicer_profiles.id` (profile_class='machine'), уже связанного с `machines`, своей связки не
заводим.

Миграция `apps/api/db/migrations/20260711270000_slice_result_cache.sql`, прогнана
вперёд-назад на копии dev (docker `portalru-postgres-1`, throwaway DB), 2026-07-11.

- `slice_cache_entries(slice_key bytea PK, gcode_s3_key, ...)` — общий технический артефакт,
  ключ — sha256(`model_files.checksum` канонического 3mf · scale · `slicer_profiles.id`
  machine-класса · `slicer_profiles.id` filament-класса · `slicer_engine_version`). Сам хэш
  считает вызывающий код (apps/mesh, MF-1053), в БД не констрейнится (принцип 5 выше). Таблица
  **не хранит** `owner_id`/`model_id` — по кэш-хиту нельзя определить, чья модель слайсилась
  первой (требование приватности карточки).
- `slice_cache_hits(slice_key, user_id, model_id, created_at)` — отдельная приватная
  append-only запись «кто отправил печать по кэш-хиту», не участвует в дедупе (уникальность
  уже на `slice_cache_entries.slice_key`), только учёт/будущая аналитика «твой облачный кэш».
- `slice_jobs.slice_key` (nullable, addition) — линковка джобы к её ключу: дедуп-проверка кода
  — посчитать `slice_key` → найти в `slice_cache_entries` → есть → отдать `gcode_s3_key`,
  инкремент `hit_count`/`last_used_at`, слайсер не запускается; нет → слайсить как сейчас,
  после `ready` — upsert в кэш.
- TTL/эвикшн: `last_used_at` + партиальный индекс, конкретный TTL — операционный параметр
  джобы очистки (MF-1053/Ops), не структурное решение схемы — не фиксируется в DDL.
- Хранилище: g-code остаётся в S3 (`gcode_s3_key`, как у `slice_jobs`), метаданные/индекс — в
  Postgres — тот же паттерн, что весь остальной домен (3mf.storage.md), отдельного объектного
  хранилища под кэш не заводим.

**Не сделано этим шагом (территория MF-1053, Autofab/веб-слайсер):** сам вызов проверки кэша
перед слайсингом и запись после — код, не схема.

**⚠️ Открытое расхождение со scope-решением MF-1075 (зафиксировано вердиктом MF-1076, Data):**
`slice_cache_entries` контент-адресован ПО ГЕОМЕТРИИ (`model_files.checksum`) и ПРОФИЛЮ
(`slicer_profiles.id`), без `owner_id`/`config_fingerprint` в ключе — то есть кэш-хит уже сегодня
шарится МЕЖДУ аккаунтами с одинаковой моделью+профилем. Решение CTO MF-1075 п.1 явно ставит
"глобальный кэш «сток-принтер → общий слайс»" в v2/v3, требующим проверенного
`config_fingerprint` + модели доверия (`trust.md`), и разрешает в v1 только per-account кэш
("не пересчитывать свою же печать"). Это создаёт разрыв: реализованная в MF-1073 схема уже
даёт межаккаунтное переиспользование без trust-механизма. Возможные пути (решает Lead/CTO,
не мой единоличный вызов — трогает уже смерженный код Fullstack/MF-1053):
(a) добавить `config_fingerprint` в `slice_key` и на v1 требовать per-account partitioning в
коде (проверка `slice_cache_hits.user_id = текущий юзер` перед выдачей `gcode_s3_key`, кэш-таблица
остаётся общей, но выдача — нет) — минимальный аддитивный патч без ревёрта схемы;
(b) явно принять межаккаунтный дедуп для идентичных `model_files.checksum` как часть v1 (тогда
нужно отдельное решение CTO — оператор ссылался на "риски доверия чужого слайса" именно для
этого случая, тихо считать её принятой нельзя).
Колонки `config_fingerprint`/`canonical_config_fingerprint`, добавленные MF-1076, закладывают
фундамент для (a), но сама логика partitioning — не эта миграция (код, не схема, тот же принцип,
что выше).

### `user_api_keys` + `config_fingerprint` (MF-1076, вердикт Data к MF-1075 п.4) — вердикт, схема прогнана вперёд-назад

Миграция `apps/api/db/migrations/20260711290000_user_api_keys_config_fingerprint.sql`, прогнана
вперёд-назад на throwaway DB (`portalru-postgres-1`, отдельная БД `mf1076_test`), 2026-07-11.
Аддитивно, `printer_connections`/`user_printers`/`device_shares` не изменены разрушительно.

- `user_api_keys` — единая модель ключей на три scope (`slicing`/`printer`/`public_api`),
  обобщает `printer_connections.api_key_enc`. Держит ОБА паттерна секрета через CHECK:
  `secret_enc` (обратимо шифрованный чужой вендорский ключ, scope='printer', провайдер
  обязателен) vs `key_hash` (sha256 нашего минтед-ключа, scope in ('slicing','public_api'),
  provider запрещён) — юзер видит plaintext минтед-ключ один раз, как уже принято в
  `api_keys` (MF-888). Ротация — `rotated_from_id` цепочкой, старый ключ → `status='revoked'`,
  не удаляется. **Существующие `printer_connections` и `api_keys` (MF-888) этим шагом НЕ
  перенесены** — перенос трогает читающий код (`prusaConnect.sync.ts`, `device_commands.api_key_id`
  FK на `api_keys`), это отдельная карточка с планом двойной записи, не структурное решение
  здесь; схема заложена совместимой (тот же домен `provider`, что у `printer_connections`).
- Контрактное расширение 2026-07-13: миграция
  `apps/api/db/migrations/20260712230100_user_api_keys_public_contract.sql` добавила `scopes`,
  `expires_at`, `updated_at`, `revoked_reason`, проверки срока/отзыва/непустого `key_prefix` и
  индексы активных ключей. `rate_limit_per_min` остаётся nullable операционным параметром,
  а legacy-таблица `api_keys` и её чтение публичным v0 этим расширением не заменены.
- `printers.canonical_config_fingerprint` + `user_printers.config_fingerprint*` — слепок
  конфигурации: `source='agent'` (наш systemd-агент считает хэш из реального Klipper/Moonraker
  config) vs `source='declared'` (managed/connector без агента — `canonical_config_fingerprint`
  каталожной модели + `config_fingerprint_stock_declared` boolean, декларация юзера
  "сток/модифицирован"). **Явно зафиксировано:** `declared` — доверие уровня "заявлено", НЕ
  "проверено"; потребитель (будущий дедуп) обязан различать источники, не трактовать наравне.
  `canonical_config_fingerprint` — общий для всех идентичных стоковых машин по дизайну (нужен
  будущему дедупу v2/v3), сам расчёт — прикладной код (Scout/каталог), не констрейнится в БД.

**Не сделано этим шагом:** миграция `printer_connections`/`api_keys` в `user_api_keys` (код,
отдельная карточка); расчёт/заполнение `config_fingerprint` (агент-контур MF-879, каталог);
partitioning `slice_cache` по `config_fingerprint`/владельцу — см. предупреждение выше про
расхождение со scope MF-1075.
