# Доска + цикл карточки + отчёт о завершении (Autofab)

> Вынесено из сквад-промпта. Правило-суть — в промпте.

## Доска — структура и стейджи
- Заголовок читается без открытия, ≤60 симв, «тема: суть». Эпики — «эпик: …».
Обрубки («фиксы», «Фаза 2») запрещены.
- Дерево: эпик → 4–8 крупных delivery-подзадач в первой волне (`--parent`, уровней ровно два).
Шаги — чеклист в описании, не новые карточки. `--stage N` = волна
параллельности: ждёшь чужой результат — другой стейдж.
- **Размер карточки.** Объединяй 3–7 связанных шагов, когда у них один
  владелец, один контракт/экран и один независимо проверяемый результат.
  Реализация, её тесты, документация и live-evidence — одна карточка, а не
  четыре. Новая child-карточка нужна только при другом владельце, зависимости
  или stage, отдельном deploy/evidence либо реальном блокере. Карточки уровня
  одного файла, компонента, состояния или теста запрещены.
- Карточка не должна превращаться в скрытый эпик: её результат помещается в
  один полноценный агентный запуск и заканчивается commit → `origin/dev` →
  проверкой на `dev.3mf.tech` либо явно указанным неприменимым live-критерием.
- **Порядок слоёв при нарезке фичи (зависимости → стейджи).** Раскладывай подзадачи по слоям —
  каждый следующий слой ЗАВИСИТ от предыдущего, поэтому ждёт его через `--stage`:
  · **stage 1 — Данные/схема** (Data): таблицы, миграции, индексы. Фундамент — всё сверху зависит
    от схемы, поэтому первым.
  · **stage 2 — Бэкенд/API** (Back/Fullstack/Mesh/AI): эндпоинты и логика поверх схемы.
  · **stage 2 — Дизайн/UX** (UX→Design): сценарий+визуал не зависит от API — идёт ПАРАЛЛЕЛЬНО
    бэку (тот же stage 2).
  · **stage 3 — Фронт** (Front/Motion/Sound): вёрстка UI нужна и API (s2), и дизайн (s2) → s3.
  · **Тест** (Test/QA) — НЕ отдельный блокирующий стейдж (тормозил бы поток): Test пишет тесты
    параллельно, QA ситуативно (CI-первый флоу).
  Смысл: агент не берётся за фронт, пока нет API и дизайна; за API — пока нет схемы. Демон будит
  следующий stage, когда предыдущий закрыт → меньше «жду чужое» и переделок.
- **Приоритет в саб-карточке ВСЕГДА проставлен** (не none): наследует приоритет ЭПИКА (его версия-фокус).
  Порядок внутри фичи держит stage, а приоритет — фокус: v1-фокус (urgent) берут раньше, чем остальное.
- Паспорт (проект-направление по [board.projects.md](board.projects.md), лейбл версии `v1`…`v6`, приоритет, даты) заполняет создатель
карточки. priority=none = не оформлена (сигнал PM).
- Отдельной ветки на карточку НЕ заводи (см. «Git — ДВЕ ВЕТКИ»): работа
всегда в общем `portal.ru:dev`; фичу проверяешь ЖИВЬЁМ на dev.3mf.tech сам (webcheck), QA — ситуативно (CI-первый флоу). Исключение — device-runtime в `UltraPrint`: он публикуется только в `UltraPrint:dev` и подтверждается contract/simulator/hardware evidence; связанный portal seam остаётся отдельной карточкой в `portal.ru`.
- Эпик закрывает только CTO по критериям спеки docs/epics/&lt;name&gt;.md.
- Скиллы ставит/снимает только CTO. Болит повторяющееся — заявка ему
комментом: скилл, ссылка, какую боль лечит.

## Цикл карточки и живость (CI-первый)

todo → in_progress → GREEN-GATE → merge → done + report-done + ДОКЛАД направленцу.
GREEN-GATE — твой гейт качества (у каждого свой, поэтому не общее горлышко): локально прогнал
lint + typecheck + test + build ЗЕЛЁНО (pnpm; Python-зоны — uv run pytest) И проверил фичу
ЖИВЬЁМ на dev.3mf.tech (webcheck-скрин). Зелёно → МЕРЖИШЬ свою вертикаль сам (кросс-вертикальное —
Lead), затем report-done + доклад. CI на gitverse (ci.yaml) гоняется на push второй линией;
красный build ловит deploy-таймер (не катит + telegram-алерт).
QA — НЕ обязательный шаг на каждую карту (раньше был, стал горлышком). Зовёшь QA СИТУАТИВНО:
- твой build/тесты красные и сам не разобрался → тег QA на диагностику;
- критичная зона (auth, деньги/выплаты, миграции БД, генерация по тексту) → QA-сэмплинг ДО мержа;
- регресс-smoke раз в ~10 версий QA делает сам.
Обычная фича (UI, эндпоинт, контент, док) с зелёным green-gate + живым dev.3mf.tech → мерж БЕЗ QA.
Reviewer ловит дефекты АСИНХРОННО после мержа (философия: велосити > осторожности, фикс-вперёд).
Выкатка на прод — промоушен dev→main через Release, ТОЛЬКО по запросу оператора (НЕ непрерывно).

Каждая сессия кончается одним из трёх исходов, записанным в карточку:
1. ДОДЕЛАЛ — мерж + report-done + доклад вверх.
2. ПРОДОЛЖАЮ — что сделано, что дальше, когда следующий шаг.
3. ПЕРЕДАЮ — blocked + эстафета (что сделано / что осталось / грабли) + тег конкретного адресата.
   Адресат обязан ответить за один свой запуск — висящий blocked теперь его.
PM обходит доску: тишина >24ч, blocked без адресата, просрочки, бесхозные — пинг.
Два пинга без ответа → направленец забирает и переназначает. Наверх тащи только неразрешимое на твоём уровне.

**Test и QA — РАЗНЫЕ независимые роли (не путать, взаимный контроль):** **Test** владеет CI/CD и автотестами — настраивает пайплайн (ci.yaml/гейты), пишет тесты, следит за покрытием; его независимый вердикт — «покрыто» / «продукт НЕДОТЕСТИРОВАН». **QA** — ситуативный функциональный аудит продукта; его вердикт — «требуется доработка». QA НЕ трогает CI/тесты (иначе подгонял бы под себя), Test НЕ судит продукт функционально. «Всё ок с CI/CD» говорит Test, не QA. Нужна тест-инфра/покрытие → карта Test; продукт не работает → аудит QA.

## Отчёт о завершении — report-done (Telegram)
Довёл карточку до готового (фича РАБОТАЕТ на dev.3mf.tech, проверил webcheck-ом) — ОБЯЗАТЕЛЬНО
отчитайся в чат команды релиз-нотой, ТЕМ ЖЕ текстом, что кладёшь в коммит. Формат — как релиз на гите:
версия · заголовок · что добавил · ссылка на гит.
**ОБЯЗАТЕЛЬНО `--kind`** (оператор должен сразу понять, ГДЕ смотреть, а не искать в UI то, чего там нет):
- `--kind base` (или api/db) — бэкенд/база/миграции: в интерфейсе трогать НЕЧЕГО. Пиши прямо «база готова».
- `--kind web` + **`--path /маршрут`** — фронт/UI: даёт кликабельную ссылку dev.3mf.tech<path>, куда смотреть. Приложи `--photo` скрин.
- `--kind fullstack` (база+веб, с `--path`) · `--kind infra` (не в UI) · `--kind docs`.
Отчёт про API/схему без `--kind base` — оператор пойдёт искать в вебе и не найдёт. Не путай его: помечай тип честно.
  `report-done --version "vX.Y.Z" --title "коротко что" --body "что добавил, 1-3 предложения" --link "<url коммита/PR на gitverse>" --role <ТвояРоль> --card MF-N`
- **Версия** — из `version.json` / свежего тега (спроси Git-агента, если не уверен). Ссылка — на конкретный коммит/PR gitverse.
- **UI/дизайн-изменение → приложи СКРИНШОТ:** `--photo ~/webcheck-out/<...>/screen.png` (webcheck снимает его при проверке). Для Design/Front/Motion показать глазами — обязательно, «показал» ценнее «рассказал».
- **Один текст в двух местах:** коммит-сообщение (гит) И `report-done` (Telegram) — не расходись, это одна релиз-нота, зеркало.
- Отчёт = ФИНАЛЬНЫЙ шаг ПОСЛЕ проверки на сайте, не вместо неё и не вместо смены статуса/эстафеты. Отчитываемся о ЗАВЕРШЁННОЙ работающей фиче, промежуточные микро-коммиты в чат не спамим.
- HTML в теле разрешён по чуть-чуть (`<b>`, `<code>`, `<a>`) — хелпер экранирует остальное; не вставляй сырые `<` в текст, если это не тег.
