## 1. Раскладка каталога v2: поиск сверху, панель слева, сетка справа ⟵ заменяет §2.1–2.2 marketplace.full.md

Валерий: «справа — список моделей по 4 в ряд; слева — настройки сортировки; сверху — поиск». Это **меняет** решение базовой спеки (§2.1: панель управления горизонтальным рядом **над** сеткой) на **левый сайдбар + сетка справа**. Всё остальное в §2 базы (анатомия карточки §2.3, пустое/скелетоны §2.4, пагинация «Показать ещё» §2.5) — **остаётся в силе**, меняется только внешняя раскладка экрана и место панели.

Это **GAP-CSS §9 п.16**.

### 1.2 Поиск (строка сверху, НОВОЕ)

Архрешение эпика §1.2 зафиксировано: `GET /models?q=` с `ILIKE` по `title`/`description`; UI проектируется так, чтобы замена бэкенда на нейропоиск ничего не сломала (тот же инпут, тот же параметр `q`).

**Форма.** Одна широкая строка на всю ширину контента:
- Слева внутри — line-глиф лупы (не эмодзи, [components.md](components.md)).
- Поле — `.marketInput` (существующий класс полей маркета, §0 инвентаря базы), высота ≥48px (тач-таргет), плейсхолдер «Найти модель…».
- Справа — `IconButton` «×» очистки, **видна только когда поле не пусто**.
- «Строгий и удобный стиль» (Валерий): это **не** «призрачный» hero-инпут главной ([components.md](components.md), Kandinsky-паттерн) — тут именно строгое поле маркета (рамка `--border`, фон `--surface`), чтобы каталог читался как рабочий инструмент, а не как арт-заставка. Философия §2 readme соблюдена: поиск — вспомогательный контрол, не второй зелёный акцент.

**Поведение.**
- **Debounce ~300–400мс** после ввода → `GET /models?q=<term>` (не на каждый keystroke). При пустом `q` — обычный листинг.
- Результат заменяет содержимое **правой сетки**; сайдбар (сортировка/теги) остаётся и **применяется поверх поиска** (`?q=…&sort=…&tag=…` — комбинируются, все фильтры складываются на бэке).
- **Пусто по запросу** (`models.length === 0` при непустом `q`) — `EmptyState`: глиф лупы, «Ничего не нашлось по «{запрос}»», подпись «Попробуйте другое слово или сбросьте фильтры», action = `Chip`/secondary «Сбросить поиск» (чистит `q` + фильтры). Это **отдельное** пустое состояние от «моделей вообще нет» (§2.4 базы) — не путать «пусто в маркете» и «пусто по фильтру».
- **Загрузка результата** — тот же скелетон-паттерн правой сетки (§2.4 базы), не спиннер.
- **URL:** `q` живёт в хэше (`#/market?q=…`) — deep-link на поисковую выдачу шарится (хэш-роутер, §1 базы / GAP-NAV-2). Синхронизация инпут↔хэш двусторонняя.

**Замена на нейропоиск (задел).** Когда `q` уйдёт в pgvector/giga ([neural.search.md](../epics/neural.search.md)) — **меняется только бэкенд эндпоинта**, UI (инпут, дебаунс, выдача, пустое состояние) не трогается. Не закладывать в UI ничего специфичного для ILIKE (напр. подсветку точного совпадения) — чтобы смена движка была прозрачной.

### 1.3 Сайдбар управления (слева, ⟵ заменяет §2.2 базы)

Тот же **состав** контролов, что §2.2 базы (сортировка сегментом, фильтр тегов, primary «Добавить»), но **вертикальным сайдбаром слева**, а не горизонтальным рядом над сеткой. Сверху вниз внутри `.marketSidebar`:

1. **Сортировка** — заголовок-`Eyebrow` «СОРТИРОВКА», под ним **вертикальный** сегмент из 2 `Chip` (полная ширина сайдбара, `data-selected` = активная):
   - **«Новые»** (default, `created_at desc` — уже в API).
   - **«Популярные»** (по голосам/скачиваниям — GAP-API §9 базы; до появления метрик — `disabled` + приписка «скоро»).
   - Это **выбор, не действие** → не primary-CTA.
2. **Фильтр по тегам** — `Eyebrow` «ТЕГИ», под ним ряд/столбец `Chip` (мульти-выбор, выбранный = зелёный). Источник — `GET /tags` (GAP-API). **Пока тегов в БД нет — блок скрыт целиком** (не показываем пустой заголовок). При активных фильтрах — `Chip`/`IconButton` «Сбросить» внизу блока.
3. **Primary «Добавить модель»** — `ActionCard variant="primary"` (существующий `.marketAddAction`), **внизу сайдбара**, полная ширина сайдбара. **Единственный зелёный CTA каталога** (правило одного primary, §2 readme, сохраняется).

**Правило анти-перегруза (наследуется §2.2 базы):** сортировка/теги — приглушённое нейтральное стекло; primary — единственный зелёный. Порядок чтения на десктопе: заголовок → поиск (сверху) → «чем управляю» (сайдбар, тускло) → «что смотрю» (сетка справа, контент) → «что делаю» («Добавить», ярко, низ сайдбара).

### 1.4 Мобильная адаптация каталога v2 (сайдбар схлопывается) ⟵ дополняет §8 базы

На мобиле левого сайдбара нет места — он **схлопывается**. Решение (я выбираю, как разрешает карточка): **шит фильтров + строка-триггер**, не постоянный аккордеон.

- **Раскладка на мобиле** (одна колонка, сверху вниз): интро → заголовок → **поиск** (строка на всю ширину, остаётся сверху — Валерий про поиск не давал мобильных исключений) → **строка контролов** → сетка (2 колонки, `.homeGallery` уже 2 на телефоне) → «Показать ещё».
- **Строка контролов** (вместо сайдбара): горизонтальный ряд:
  - `Chip`/`IconButton` «**Фильтры**» (глиф-слайдеры) — тап открывает `sheet` (слой всплывашек, `overlay.sheet`) со **всем содержимым сайдбара** (сортировка + теги + сброс). Бейдж-счётчик активных фильтров на кнопке, если есть.
  - Быстрый сегмент сортировки «Новые/Популярные» можно вынести сюда же (частый переключатель), а полный набор тегов — в шите. Точное дробление — на реализацию.
  - **primary «Добавить»** — отдельной строкой на всю ширину под контролами (тач-таргет ≥48px), как в §8 базы.
- **Почему шит, а не аккордеон:** тач-первый принцип ([layout.md](layout.md)) — фильтры это «зашёл, настроил, вышел», не постоянно раскрытая панель, съедающая экран под сгибом. Шит = фокус на одной задаче (философия §2 readme «одна мысль на кадр»), закрылся — снова весь экран под модели. Аккордеон в потоке толкал бы сетку вниз при каждом раскрытии (прыжок раскладки). Применяется `overlay.sheet` — примитив уже спроектирован (MF-440).
- `prefers-reduced-motion` — шит появляется без пружины (стандартное поведение overlay-слоя).

## 2. «Парящая» страница модели ⟵ ревизия §5.1 marketplace.full.md

Валерий: «Здесь иначе: всё должно парить, никаких подложек. Слева — модель, которую можно крутить; справа — парящие заголовки, описание, кнопки с фоном и прозрачностью».

Это **самая существенная ревизия**. База §5.1 строит правую колонку из **стеклянных карточек-подложек** (`Card` `.uiCard`, blur 24 — §0 инвентаря базы). v2 **убирает подложки** из правой колонки: заголовки/описание/мета **парят прямо на фоне студии** (луч-прожектор + зерно, [palette.typography.md](palette.typography.md)), а **фон и прозрачность остаются только у интерактивных элементов** (кнопки, поле голоса) — «полупрозрачное стекло» как аффорданс кликабельности.

### 2.1 Философия «парения» и её границы (читаемость/контраст)

«Парение» — это **не** отказ от системы, а её частный режим: **контент-текст живёт на фоне без карточки, интерактив — на полупрозрачном стекле**. Границы (обязательны, иначе «парение» ломает читаемость на светлой теме и на ярком превью):

1. **Что парит (без подложки):** заголовок модели, «by @автор», описание, теги, тех.метаданные, заголовки блоков обсуждения/makes/статистики. Это **текст** — он читается за счёт типографики и контраста к фону студии, а не за счёт карточки-плашки.
2. **Читаемость парящего текста — на нас.** Фон студии тёмный (`--bg #0a1512`) — белый `--text` на нём контрастен. **Но** правая колонка может лечь поверх области, где виден край 3D-превью/прожектора (яркое пятно) → под парящим текстом обязателен **мягкий градиент-вуаль**: не карточка с рамкой, а `radial/linear` затемнение фона под текстовой колонкой (`--bg` → прозрачность, `backdrop` без border/radius-карточки). Это сохраняет контраст ≥ 4.5:1 (WCAG AA для body), не создавая «подложки-плашки», которую Валерий отвергает. На светлой теме — тот же приём инвертирован (светлая вуаль).
3. **Что имеет фон+прозрачность (стекло-интерактив):** кнопки «Скачать/Отправить в печать/Поделиться», контрол голоса ▲N▼. Валерий дословно: «кнопки с фоном и прозрачностью». Это **полупрозрачное стекло** — `background: color-mix(surface + прозрачность)` + лёгкий `backdrop-filter: blur`, но **без** толстой карточки-обёртки; форма кнопки, не панели.
4. **Один зелёный primary сохраняется** (§2 readme): на странице модели primary — «Скачать 3MF» (заливка `--accent`, единственная сплошная-зелёная). «Отправить в печать» — стекло+disabled (заглушка), «Поделиться» — нейтральное стекло, голоса — стекло с акцентом только на активной стрелке. Ни одна из них не конкурирует с зелёным «Скачать».
5. **`prefers-reduced-motion`/слабое устройство:** `backdrop-filter` blur — дорогой; на Save-Data/слабом GPU допустима деградация до полупрозрачного фона без blur (стекло → просто затемнение). Парение остаётся, «стеклянность» упрощается. Это **GAP-CSS §9 п.17** (утилита «floating-veil» + «glass-button без карточки»).

**Итог принципа:** «никаких подложек» = **нет карточек-плашек** под текстом и мета; но **есть** (а) невидимая вуаль-контраст под текстом ради читаемости и (б) явное полупрозрачное стекло у кнопок как аффорданс. Это честно согласуется с философией: яркость/фон = важность и кликабельность, приглушённое/парящее = информация.

**Шапка:** `HomeHeader` + круглая `IconButton` «←» слева (назад) — как §5.1 базы.

**Левая колонка — зона 3D-вьюера (герой):** **остаётся ровно как §12 базы** (постер псевдо-3D → «покрутить» → three.js GLTFLoader-орбита/зум/сброс, все состояния вьюера). v2 её не трогает — Валерий подтверждает «слева модель, которую можно крутить». Единственная поправка от «парения»: под вьюером **нет карточки-обёртки**, сцена/постер парят на фоне студии (что и так естественно для canvas).

**Правая колонка — парящая мета и действия** (⟵ заменяет §5.1 правую колонку, порядок сверху вниз):
1. `Eyebrow` — формат исходника («STL → 3MF») + статус-пилюля, если не `ready`. **Парит** (uppercase-трекинг на фоне).
2. **Название** — `Heading size="md"` (Unbounded), парит **без карточки**, под ним вуаль-контраст (§2.1 п.2).
3. **Автор** — «by ⦿ @username» с мини-аватаром (персонаж 36px, [avatar.md](avatar.md), без кольца) → ссылка в профиль (§7 базы). Парит.
4. **Ряд действий-стекла** (§3 этого файла): голос ▲N▼ + «Скачать 3MF» (primary) в одном визуальном ряду; ниже — «Отправить в печать» + «Поделиться». Все — **полупрозрачное стекло**, «Скачать» — единственная сплошная-зелёная.
5. **Описание** — многострочный текст, парит на фоне (переводы строк сохраняем; пусто → «Автор не добавил описание», приглушённо). Под ним вуаль-контраст.
6. **Теги** — ряд `Chip` (приглушённые, парят), тап → каталог с фильтром (`#/market?tag=…`). Пусто → скрыто.
7. **Тех.метаданные** (`.marketModelSpecs`, §5.1 базы п.8) — «ключ · значение» приглушённо, парят строками (не таблица-карточка): Формат / Габариты (bbox) / Размер файла / Загружено. Пустые поля — строку скрываем.
8. **Действия владельца** — своя модель: «Редактировать» (secondary-стекло) + «Удалить» (коралл) — §3.2/3.3 базы. Не-владельцу скрыты.

Всё, что ниже двух колонок (статистика §7, makes §6, обсуждение §4) — **полноширинные секции** под героем, тоже в «парящей» стилистике (заголовки блоков парят; карточки-подложки — только там, где элемент интерактивен или это отдельная единица контента вроде плитки make/аватара коммента, §6/§4).

### 2.3 Мобильная «парящая» страница ⟵ дополняет §8 базы

Две колонки → **одна** (стек), порядок = приоритету: вьюер (сверху, полная ширина, фикс-высота `min(70vw,60vh)` §12.4 базы) → Eyebrow+статус → название → автор → **ряд действий-стекла** (голос+Скачать на всю ширину, print/поделиться под ним) → описание → теги → спеки → действия владельца → статистика → makes → обсуждение. Вуаль-контраст под текстом на мобиле особенно важна (превью прямо над текстом — яркий фон). Тап-таргеты кнопок-стекла ≥48px.

## 3. Кнопки страницы модели ⟵ уточняет §5.2–5.3 marketplace.full.md

Валерий: «Кнопки: отправить в печать, поделиться, стрелочка вверх как лайк и вниз как дизлайк». Все — в «парящей» композиции §2, полупрозрачное стекло, primary «Скачать 3MF» — единственный сплошной-зелёный.

### 3.1 Голоса ▲/▼ (лайк/дизлайк) — вписать в парение ⟵ уточняет §5.2 базы

§5.2 базы (Reddit-стрелки, `POST /models/:id/vote {value: 1|-1|0}`, оптимистично, toggle) — **в силе**. v2 уточняет **форму под парение**:
- Пара стрелок ▲/▼ + число между ними — **вертикальный контрол на полупрозрачном стекле** (не голая иконка на фоне: тут нужен аффорданс кликабельности → стекло уместно, Валерий «кнопки с фоном»). Число голосов — сумма (`votes_up − votes_down`), Unbounded, приглушённое пока не проголосовал.
- Активный **мой up** — ▲ заливается `--accent` (зелёная); активный **мой down** — ▼ заливается `--accent-danger` (коралл, деструктивная семантика цвета уместна) — **без пульса** (это не срочность).
- Тап по активной стрелке — снятие (`value: 0`). Оптимистично, откат при ошибке API.
- Стоит в ряду рядом с «Скачать» (§2.2 п.4). **Не** primary (голос — не главное действие); зелёная заливка ▲ при моём up не нарушает «один primary» — это состояние контрола, не CTA.
- До появления `votes` в БД (заведётся стадией 3) — блок скрыт.

### 3.2 «Отправить в печать» — заглушка ⟵ НОВОЕ (реализует §1.9 эпика)

Архрешение эпика §1.9 зафиксировано: кнопка **заглушка** (реальная отправка требует коннективности принтеров, линия MF-26, вне эпика).
- **Форма:** полупрозрачное стекло-кнопка (§2.1 п.3), **`disabled`**, глиф-принтер (line, не эмодзи) + текст «Отправить в печать».
- **Состояние «скоро»:** приглушённая (opacity как у disabled), рядом/под — микроподпись «скоро» (`--text-dim`, как disabled-«Популярные» в §2.2 базы). Не кликается.
- **Почему видима, а не спрятана:** показать намерение продукта (принтеры будут), не обещая работу сейчас — тот же честный паттерн, что «Скачать» до Фазы 3 (§5.3 базы). Опционально тап по disabled → мягкий `toast info` «Отправка в печать появится позже» (как «Скачивание скоро появится» §5.3 базы). На усмотрение реализации, но текст — RU, без обмана.
- **НЕ primary** (стекло-приглушённая), не конкурирует со «Скачать».

### 3.3 «Поделиться» — Web Share / копия ссылки + тост ⟵ НОВОЕ (реализует §1.10 эпика)

Архрешение эпика §1.10: Web Share API, фолбэк «копировать ссылку» (+тост); никакого сервера — только deep-link маршрута `#/market/model/:id`.
- **Форма:** полупрозрачное стекло-кнопка, глиф-«поделиться» (line: узел-с-ветвями или стрелка-из-коробки) + текст «Поделиться». Нейтральное стекло (не зелёная).
- **Поведение:**
  - Если `navigator.share` доступен (мобильные/часть десктопа) → системный шит шаринга с `{ title: название, url: абсолютный линк на #/market/model/:id }`.
  - Фолбэк (нет Web Share) → копировать абсолютную ссылку в буфер (`navigator.clipboard.writeText`) → `toast({ severity: "success", title: "Ссылка скопирована" })`.
  - Ошибка/отказ пользователя от системного шита — **тихо** (share cancel — не ошибка, без тоста). Ошибка копирования (нет clipboard-доступа) → `toast info` «Скопируйте ссылку из адресной строки» как последний фолбэк.
- URL строится из текущего маршрута (хэш-роутер §1 базы) → абсолютный (origin + hash). Работает для любой `ready`/не-`ready` модели (шарят и «в очереди»).
- **НЕ primary.**

### 3.4 «Скачать 3MF» — primary, без изменений

§5.3 базы (единственный зелёный primary, все статусные состояния `ready`/`processing`/`failed`, «скоро» до Фазы 3) — **в силе как есть**. В «парящей» композиции это **единственная сплошная-зелёная** кнопка (не стекло — заливка `--accent`), визуальный якорь правой колонки.

## 4. Блок обсуждения (плоские комментарии) — НОВОЕ §5

Валерий: «обсуждать её». Архрешение эпика §1.7 зафиксировано: полиморфная таблица `comments (subject_type, subject_id, user_id, body, created_at)`; **MVP — плоский список, без веток/реакций/модерации**. Ветки — открытый вопрос §4 эпика (не в этой итерации).

### 4.1 Место и композиция

Полноширинная секция под героем страницы модели (порядок §2.2 — после makes или рядом; точный вертикальный порядок makes↔обсуждение — на реализацию, оба под статистикой владельца).

- **Заголовок секции** — `Eyebrow` «ОБСУЖДЕНИЕ» + счётчик «(N)» приглушённо. Парит (без карточки-обёртки секции).
- **Инпут комментария** (вверху блока, чтобы написать было первым делом):
  - `.marketTextarea` (существующее поле маркета, §0 инвентаря базы), плейсхолдер «Оставьте комментарий…», авто-рост высоты.
  - primary-в-контексте-блока «Отправить» (**не** зелёный primary страницы — чтобы не спорить со «Скачать»; secondary-стекло или приглушённая кнопка блока, активна только при непустом тексте). Обоснование: правило «один зелёный на экран» — зелёный уже у «Скачать»; отправка коммента — локальное действие блока.
  - Отправка — `POST /comments {subject_type:'model', subject_id, body}` (GAP-API §9 п.18). Оптимистично: коммент появляется сразу вверху ленты, откат при ошибке → `toast critical` «Не удалось отправить. Попробуйте снова.».
- **Лента комментариев** (плоская, новые сверху):
  - Единица — **компактная карточка коммента** (это отдельная единица контента → лёгкая подложка допустима, «парение» касается меты модели, а не списка отдельных сообщений; но подложка тонкая — стекло без тяжёлой рамки): мини-аватар автора (персонаж 32px, [avatar.md](avatar.md)) + «@username» (ссылка в профиль §7 базы) + относительная дата («2 часа назад») + тело коммента (многострочное, переводы строк сохраняем).
  - Свой коммент — тонкая мятная обводка/метка «вы» (как `data-mine` плитки каталога §2.3 базы). Удаление своего коммента — `IconButton` «⋯» → `confirm` (не деструктив-критично, но подтверждение) → `DELETE /comments/:id` (владелец коммента ИЛИ владелец модели — owner-check на бэке). MVP: удаление своего; модерация владельцем модели — опционально, помечаю как открытый вопрос реализации (не блокирует).
  - Пагинация ленты — та же «Показать ещё» (§2.5 базы), если комментов много.

### 4.2 Состояния блока обсуждения

- **Пусто** (нет комментов) — `EmptyState` компактный (не полноэкранный): глиф-реплика (line-«облако диалога»), «Пока нет комментариев», подпись «Будьте первым — поделитесь мнением о модели». CTA не нужен (инпут уже над лентой — призыв встроен). Это пассивный обучающий слой.
- **Загрузка** — скелетон 2–3 карточек коммента (тот же shimmer-паттерн, GAP-CSS §10 базы).
- **Ошибка загрузки** — приглушённая строка «Не удалось загрузить обсуждение» + `IconButton` «Повторить» (не пустой блок).
- **Гость (MF-831/MF-850 — публичное чтение, `AuthGate` снят с публичных роутов):** лента обсуждения читается как есть, без входа. Инпут комментария виден, но не принимает набор — фокус/тап на нём открывает overlay-промпт входа (тот же паттерн, что у гостевого голоса ленты — [feed.md §3](feed.md)); уже набранный текст, если был, сохраняется и уходит сам после логина, а не «войдите и начните заново».
- Все тексты — **RU**.

## 5. Блок makes «Я напечатал» — НОВОЕ §6

Валерий: «поделиться фоткой, что ты её напечатал». Архрешение эпика §1.8 зафиксировано: таблица `makes (model_id, user_id, фото в S3, подпись, created_at)`, `machine_id` — nullable-задел; это первый шаг make-галереи, **не** полная соцлента. ### 5.1 Место и композиция

Полноширинная секция под героем (рядом с обсуждением, §2.2).

- **Заголовок секции** — `Eyebrow` «Я НАПЕЧАТАЛ» + счётчик «(N)». Парит.
- **Лента/сетка фото** — плитки фотографий напечатанных экземпляров:
  - Раскладка — **сетка** плиток (переиспользуем адаптивную `.homeGallery`-логику или ленту-скролл; для MVP — сетка 3–4 в ряд десктоп, 2 мобайл, как каталог). Каждая плитка — фото make (обрезка `object-fit: cover`, крупный радиус карточки [components.md](components.md)) + оверлей внизу: мини-аватар автора + «@username» + подпись (`caption`, обрезка 1–2 строки).
  - Плитка — это **единица контента с фото** → карточка-подложка уместна (не «мета модели»); «парение» тут — у заголовка секции и флоу-кнопки, а сами фото-плитки предметны.
  - Тап по плитке — лайтбокс/увеличенное фото (`overlay.modal` с фото + полной подписью + автором). Простой просмотр, без каруселей-зумов в MVP (можно свайп между makes — опционально).
- **CTA «Поделиться фото»** (§5.2) — призыв добавить свой make.

### 5.2 Флоу «поделиться фоткой» (загрузка фото + подпись)

Точка входа — кнопка в шапке блока makes: `ActionCard`/кнопка «Поделиться фото» (глиф-камера, line). **Не** зелёный primary страницы (зелёный у «Скачать») — secondary-стекло, локальное действие блока. Открывает **модалку** (`overlay.modal`, слой MF-440):

1. **Заголовок** — `Heading size="md"` «Поделитесь, что напечатали».
2. **Дропзона фото** — тот же паттерн, что файловая дропзона `AddModelFlow` (§3.1 базы), но для **изображения** (jpg/png/heic, лимит ~10 МБ — на реализацию): выбор/дроп → превью-миниатюра выбранного фото. Один снимок в MVP (мульти — позже).
3. **Подпись** — `.marketTextarea`, необязательная, плейсхолдер «Как печаталось? Материал, настройки, впечатления…».
4. **primary «Опубликовать»** (зелёный — единственный акцент **внутри модалки**, правило «один primary на кадр» соблюдено локально) + secondary «Отмена».
5. **Отправка** — `POST /models/:id/makes` (multipart: фото + `caption`), GAP-API §9 п.19. Прогресс-бар загрузки фото (тот же `.uiChecklistBar`, как аплоад модели). Успех → `toast success` «Спасибо! Ваше фото добавлено», модалка закрывается, новый make появляется вверху ленты оптимистично.
6. **Ошибки** — тип/размер фото (inline, RU), сеть → `toast critical` + «Повторить», модалка держит выбранное.
- Модерация фото — **нет в MVP** (открытый вопрос §4 эпика, как теги; пересмотр до публичного запуска). Не проектируем модерацию, но флоу не мешает её добавить (статус `pending` у make позже).

### 5.3 Состояния блока makes

- **Пусто** (нет makes) — `EmptyState`-**призыв**: глиф-камера/принтер, «Напечатали эту модель?», подпись «Поделитесь фото — покажите, как получилось», action = та же «Поделиться фото» (открывает флоу §5.2). Это **активный** призыв (в отличие от пассивного пустого обсуждения) — makes растят вовлечённость.
- **Загрузка** — скелетон плиток фото (shimmer, GAP-CSS §10 базы).
- **Ошибка загрузки** — приглушённая строка «Не удалось загрузить фото» + «Повторить».
- Все тексты — **RU**.

## 6. Статистика владельца — НОВОЕ §7

### 6.1 Видимость и место

- **Только владельцу** своей модели (`owner.id === me`). Чужому — блок не показывается (публичные агрегаты — голоса/скачивания — и так видны в мете каталога §2.3 базы и в контроле голоса §3.1; отдельная «статистика» — приватная для автора).
- **Место** — полноширинная секция сразу под героем (первой из соцблоков — владельцу его метрики важнее чужих комментов). Заголовок — `Eyebrow` «ВАША СТАТИСТИКА». Парит.

### 6.2 Композиция и «яркость=важность»

Ряд компактных **метрик-плиток** (4 показателя), приглушённых по умолчанию — это **фон-информация, не действие**:

| Метрика | Источник | Глиф (line) | Подпись |
|---|---|---|---|
| Голоса | `votes_up − votes_down` (+ разбивка ▲/▼ мелко) | стрелка-вверх | «голосов» |
| Скачивания | `downloads_count` (агрегат, §9 п.8 базы) | стрелка-вниз | «скачали» |
| Комментарии | `count(comments)` | облако-диалог | «комментариев» |
| Makes | `count(makes)` | камера/куб | «напечатали» |

- **Приглушённо по умолчанию** (`--text-dim`, лёгкое стекло-плитка): повседневная метрика — не срочность. Число — Unbounded (крупные цифры читаются как line-art, [palette.typography.md](palette.typography.md)), подпись — мелкая uppercase-eyebrow.
- **«Яркость=важность» в действии:** плитка **разгорается** (акцентный тон), когда показатель «важен/растёт» — трактовка (я фиксирую дефолт, чтобы стадия 4 не изобретала): **свежая активность подсвечивается**. Например: появились новые комментарии/makes/голоса с последнего визита владельца → соответствующая плитка получает акцентную обводку/`StatusPill dim→ok` «+N новых». Без данных «с последнего визита» (нет трекинга прочтения) — деградирует до простого «яркость по абсолютной значимости»: 0 у метрики → плитка почти прозрачная («ещё нет»), большое число → плотнее/акцентнее. Точный порог — на реализацию; принцип: **пустое/нулевое — тускло, живое/растущее — ярче**.
- **Hero-панель метрики (разворот контраста, §palette-typography):** приём «одна залитая мятная карточка с тёмным числом» — **зарезервировать для одной ключевой метрики**, если Валерий захочет выделить главную (напр. скачивания как «пульс» модели). MVP: не заливаем (4 равных приглушённых плитки), но композиция допускает промоушен одной в hero-панель без переверстки. Помечаю как микро-решение реализации.
- **Просмотры** (`views_count`) — **не заводим** (открытый вопрос §4 эпика, трекинг, согласуется с эпиком аналитики MF-429..431). Плитку не рисуем, пока метрика не решена — не «—», а просто нет плитки.

### 6.3 Состояния

- **Всё по нулям** (свежая модель) — плитки видны, но приглушены до «ещё нет данных»: «0 голосов», «0 скачали» и т.д., тускло. Не прячем блок (владелец должен видеть, что метрики есть и будут). Подпись-подсказка под блоком: «Статистика появится, когда модель начнут смотреть и скачивать».
- **Загрузка** — скелетон 4 плиток.
- Данные — из `GET /models/:id` (агрегаты, §9 п.1 базы) + `count` комментов/makes (можно тем же эндпоинтом или отдельными — GAP-API §9 п.20). Обновление — тем же поллингом `/models/:id` (4с, §6 базы).

## 7. Пост-аплоад: редирект на страницу модели — сверка §11 marketplace.full.md

Валерий: «После добавления открывается страница карточки данной модели». Это **подтверждает и упрощает** §11 базы (пост-аплоад флоу). Сверяю и фиксирую окончательно.

**§11 базы** проектировал богатый флоу: загрузка → reveal карточки в модалке → шаг «Опубликовать» (утверждение полей) → переход на страницу модели. Дословный запрос Валерия v2 — короче: «после добавления **открывается страница карточки**». Разрешаю кажущееся расхождение:

- **Целевой инвариант обоих — един:** пользователь после загрузки **не высаживается в анонимную ленту**, а попадает **на свою страницу модели** (§13.2 инвариант 1 базы). Валерий это и просит.
- **Шаг «Опубликовать» (§11.2 базы) — сохраняем как есть**, он не противоречит «открывается карточка»: это тот же контекст «вот твоя модель» (raскрытие в модалке §11.1) + быстрая проверка названия/описания перед публичной лентой, **затем** переход на страницу модели. Валерий не отвергал шаг утверждения — он описал **итог** («открывается карточка»), а §11 описывает **как именно** к нему прийти (reveal → confirm → страница). Итог совпадает.
- **Окончательная фиксация пути** (без изменений к §11, только подтверждение):
  1. Загрузка завершилась → **reveal** карточки в модалке (§11.1 базы, `homeRise` ~0.4s, reduced-motion → кросс-фейд).
  2. Шаг «Опубликовать» (§11.2) — предзаполненные поля, primary «Опубликовать».
  3. «Опубликовать» → **переход на `#/market/model/:id`** (§11.3, section-fade), где файл может быть ещё `pending`/`processing` (статус-пилюля + поллинг 4с §6 базы). Это и есть «открывается страница карточки».
  4. На «парящей» странице (§2 этого файла) владелец сразу видит свою модель, статистику (§6), может редактировать (§3.2 базы) — ровно как просит Валерий («можно покрутить и всё изучить, и если твоя — отредактировать»).
- **Если Валерий позже захочет убрать шаг утверждения** (сразу загрузка → страница, без confirm-кадра) — это точечное упрощение §11.2, не переверстка; фиксирую как **микро-решение**, дефолт — **оставляем шаг утверждения** (обоснование §11.2 базы: метаданные = «лицо» модели, дать подтвердить дешевле, чем чинить). Не блокирую.

**Итог:** §11 базы остаётся в силе целиком; v2 подтверждает его итог и увязывает с «парящей» страницей §2. Пост-аплоад ведёт на страницу модели — инвариант соблюдён.

## 9.5 «Интерфейс скомкан — используй больше страниц» (запрос Валерия, 2026-07-05)

Валерий (MF-463): «Текущий интерфейс чутка скомканный… по возможности используй больше страниц». Это **IA-замечание**, разбираю его как дизайн-решение, а не как «настрогать роутов ради роутов». Философия readme §2 — «одна главная мысль на экран»; «скомканность» = на одном кадре конкурирует слишком много мыслей. Лекарство — не дробить механически, а **разнести конкурирующие задачи по маршрутам**, оставив на каждом одну доминанту.

**Принцип «страница = одна задача».** Отдельный маршрут заводим, когда блок (а) самодостаточен как задача, (б) шарится/линкуется, (в) утяжеляет герой-экран, если живёт инлайном. Инлайном оставляем то, что читается как продолжение текущей задачи.

**Что уже правильно разнесено** (`router.ts`): каталог, страница модели, `#/u/:username` (профиль). Deep-link на модель/профиль/поиск — уже отдельные адреса. Это база, её не ломаем.

**Что даёт «скомканность» и как разнести** (кандидаты, приоритет сверху):

1. **Флоу «Добавить модель» → свой маршрут.** Сейчас аплоад-флоу живёт модалкой поверх каталога — это самый тяжёлый «кадр в кадре» (дропзона + прогресс + reveal + шаг «Опубликовать»), он и создаёт ощущение скомканности над сеткой. Аплоад — самодостаточная задача, заслуживает полного экрана-страницы (сохраняя пост-аплоад-редирект §7 на страницу модели). Модалку оставить только как быстрый вход, но целевой UX — отдельная страница. **Это главный кандидат.**
2. **Соцблоки страницы модели (статистика §6 / makes §5 / обсуждение §4) — вкладки-секции, НЕ всё сразу простынёй.** Валерий сам просит «больше страниц» — но страница модели уже «парящая» и вертикально длинная. Решение: под героем — сегмент-табы («Обсуждение · Напечатали · Статистика»), каждая — deep-linkable под-маршрут, чтобы не сваливать три ленты в один скролл. Одна лента на кадр = «одна мысль». (Реализуется на стадии 4 вместе с соцслоем — фиксирую IA заранее, чтобы стадия 4 не собрала простыню.)
3. **Профиль автора (`#/u/:username`) — уже отдельная страница**, не инлайн-поповер. Правильно, сохраняем; при росте — свои вкладки (модели · makes) тем же приёмом.
4. **Поиск/фильтр — остаются в каталоге, НЕ отдельной страницей.** Это управление текущим списком, а не новая задача; выносить в маршрут — та самая «механическая» ошибка. Их «скомканность» лечится раскладкой §1 (сайдбар слева разгружает верх), а не роутом.

**Граница (чтобы не переусердствовать):** не заводим маршрут ради одного контрола или одного тоста. Дробим **задачи**, а не виджеты. Каждый новый маршрут — в тот же лёгкий роутер (`router.ts`), без тяжёлой зависимости (архрешение §1 эпика). Тач-навигация назад (`IconButton ←`) обязательна на каждом вложенном экране.

**GAP-NAV (продолжение) — реализовано в MF-476.** Кандидаты 1–2 добавлены в `Route`-тип `router.ts`. Синтаксис путей взял актуальную path-схему роутера (после миграции с хэша в MF-524, `#/market` больше не резолвится), не легаси-хэш, которым эта секция была написана изначально — IA-принцип тот же: `/project/add` (кандидат 1), `/project/:id/{comments,makes,stats}` (кандидат 2, `comments` — дефолт без суффикса). IA-приёмку см. в [MF-476](mention://issue/a8dd2364-b17b-42f7-9a30-54961174851b).

## 10. Инварианты ревизии (проверяются на приёмке)

1. **Каталог:** поиск — сверху; управление — слева сайдбаром; модели — справа 4-в-ряд (десктоп). Мобайл: поиск сверху, сайдбар → шит.
2. **Страница модели «парит»:** нет карточек-подложек под текстом/метой; парящий текст читаем (вуаль-контраст, обе темы); фон+прозрачность — только у интерактива (кнопки/голос = стекло).
3. **Один зелёный primary на кадр** сохранён: каталог → «Добавить»; страница модели → «Скачать 3MF»; модалка make → «Опубликовать»; блок коммента → «Отправить» (не зелёный страницы).
4. **Деструктив коралловый через `confirm`** (удаление модели §3.3 базы, ▼-дизлайк коралл, удаление коммента).
5. **Пост-аплоад → страница модели**, не лента (инвариант §13.2 базы сохранён).
6. **Все тексты RU;** `prefers-reduced-motion`/Save-Data уважается (парение-blur, reveal, шиммер деградируют); тач ≥48px.
7. **Архрешения эпика §1 не нарушены** (роутер, `?q=` ILIKE, GLB-вьюер, `comments`/`makes`, Web Share, print-заглушка) — v2 в их рамках.

## 11. Контракт к хранилищу для DB-агента (что UI требует сохранять/читать)

**Зачем этот раздел.** Стадия 3 эпика — «схема соцслоя» на **DB-агенте** (`comments`, `makes`, счётчики, строго по [domain.model.md](../epics/domain.model.md)). Чтобы DB не выводил требования к данным из UI-описания задним числом, здесь — **явный контракт со стороны дизайна**: какие поля читает/пишет каждый новый блок v2. Это **требования UI к данным, не схема** — конкретную DDL (типы, индексы, полиморфизм vs узкая пара) проектирует DB в своей карточке; я лишь фиксирую, что экрану нужно, и сверяю с уже живой схемой (MF-462), чтобы не задваивать.

### 11.1 Что УЖЕ в проде (MF-462 — не заводить заново)

Сверено по `apps/api/src/db/schema.ts` на `main`:
- `tags` + `model_tags` (узкая пара под маркет, **не** полиморфная — сознательно, MVP).
- `model_votes (model_id, user_id, value ∈ {−1,1})`, PK `(model_id, user_id)` — голоса ▲/▼ (§3.1) читают/пишут сюда.
- Денормализованные счётчики на `models`: `votes_up`, `votes_down`, `downloads_count` — консистентность **на слое API** (инкремент при голосе/скачивании), **без триггеров** (осознанный MVP-выбор MF-462).
- Индексы каталога: `models_created_at_idx` («новые»), `models_popularity_idx` («популярные»).

**Вывод для v2:** голоса, теги, скачивания, сортировки — **данные уже есть**, стадия 4 их только читает/пишет через API. Новое для соцслоя — **только `comments` и `makes`** (+ агрегаты для статистики владельца).

### 11.2 Комментарии (§4) — требования UI

| UI читает/пишет | Поле-источник (имя предлагаю, DB решает тип) |
|---|---|
| Аватар+@автор коммента | `user_id` → join `users` (username, display_name, avatar_url) |
| Тело коммента (многострочное) | `body text` |
| Относительная дата «2 часа назад» | `created_at timestamptz` |
| Привязка к модели | `(subject_type='model', subject_id=models.id)` — полиморфная пара по [domain.model.md](../epics/domain.model.md) §4/§57 |
| Лента новые-сверху + «Показать ещё» | сортировка `created_at desc`, пагинация `limit/offset` |
| «мой коммент» (метка, право удалить) | сравнение `user_id` с сессией; удаление — owner коммента ИЛИ owner модели |
| Счётчик «(N)» в заголовке + плитка статистики | `count(*) where subject=(model,:id)` |

### 11.3 Makes «я напечатал» (§5) — требования UI

| UI читает/пишет | Поле-источник |
|---|---|
| Фото напечатанного (плитка + лайтбокс) | ключ S3 фото (роль/бакет — по [3mf.storage.md](../epics/3mf.storage.md), нейтральный ключ) |
| Подпись | `caption text` (необязательная) |
| Аватар+@автор make | `user_id` → join `users` |
| Привязка к модели | `model_id` → `models.id` (прямой FK, make всегда про конкретную модель — не полиморфный) |
| Лента новые-сверху + пагинация | `created_at desc`, `limit/offset` |
| Задел «на каком станке» (не в MVP UI) | `machine_id nullable` — по эпику §1.8, UI пока не показывает |
| Счётчик «(N)» + плитка статистики | `count(*) where model_id=:id` |

### 11.4 Статистика владельца (§6) — требования UI

4 плитки владельцу читают **только агрегаты** (не сырые строки):
- голоса `votes_up − votes_down` — **уже есть** (счётчики MF-462);
- скачивания `downloads_count` — **уже есть**;
- комментарии `count(comments)` — из §11.2;
- makes `count(makes)` — из §11.3.

`GET /models/:id` (GAP-API §9 п.1 базы) для владельца должен вернуть `comments_count` и `makes_count` рядом с уже существующими `votes_up/down`, `downloads_count`. **Способ (два `count`-подзапроса vs денормализованные счётчики `comments_count`/`makes_count` на `models` по образцу голосов) — на решение DB.** Дизайну важен только сам факт агрегата в ответе; «яркость=важность» (§6.2) работает от числа, не от способа его получения. Просмотры (`views_count`) — **не заводить** (открытый вопрос эпика §4).

### 11.5 ⚠️ Противоречие, которое DB/Architect должны развести: плоские vs древовидные комментарии

Нашёл рассинхрон в принятых документах — **фиксирую явно, чтобы стадия 3 не выбрала молча:**
- **Эпик §1.7** и **эта ревизия §4** (и запрос Валерия «обсуждать») → **MVP плоский, без веток**.
- **[domain.model.md](../epics/domain.model.md) §57** → «`comments` — **древовидные** (`parent_id`)».

Это не конфликт схемы, а конфликт **того, что показывать в MVP**: `parent_id uuid nullable` можно завести в таблице сразу (родословная-задел, ноль стоимости), а **UI стадии 4 его игнорирует** (рисует плоско). Так обе бумаги примиряются: **схема готова к веткам (`parent_id` есть), UX MVP — плоский**.

**Моё предложение дизайна (не решение — решает Architect):** DB заводит `comments` с `parent_id uuid nullable references comments(id)` сразу (дёшево, снимает будущую миграцию), а UI v2 §4 остаётся плоским (не читает `parent_id`). Открытый вопрос эпика §4 п.3 («нужен ли 1 уровень ответов сразу?») — тогда чисто UX-переключатель поверх готовой схемы, без миграции. **Требуется явное «да/нет» от Architect/Валерия** — до этого дизайн держит плоский вид как дефолт.

### 11.6 Что DB НЕ трогает по этой карточке

Границы (чтобы стадия 3 не разрослась): `communities`/`posts`/`crafts`/`machines` — **не заводить** (пустые впрок, [domain.model.md](../epics/domain.model.md) «Чего НЕ делать сейчас»); модерация makes/комментов — вне MVP (статус-поле можно заложить nullable-заделом, но не строить флоу); полиморфизм `votes`/`tags` расширять **не требуется** (узкие пары под маркет живут, домен допускает оба). Соблюдать конвенции ядра: `id uuid default gen_random_uuid()`, `created_at/updated_at timestamptz`, `status text + check`, консистентность счётчиков на API-слое (без триггеров) — как в MF-462.
