# Фрагментация данных: слайс-дедуп, P2P-обмен, платформа-верификатор

**Техническая сторона философии** [../product/platform.md](../product/platform.md) §Фрагментация.
Принцип: **не вычислять и не гонять одно и то же дважды.** Слайсинг дорог (CPU), трафик дорог (гигабайты
G-code) — а печатают часто одно и то же (один Benchy на тысячах одинаковых Ender-3 V3 KE). Платформа —
**верификатор и координатор**, а не центральная вычислялка/склад.

## 1. Слайс — детерминированная функция → content-addressed кэш

Слайсинг детерминирован: `slice(model, profile, printer_config) → gcode`. Одинаковый вход → байт-в-байт
одинаковый выход. Значит результат **адресуется по содержимому входа**:

```
slice_key = hash( model_hash · profile_hash · config_fingerprint )
```

Посчитали `gcode` для `slice_key` один раз — храним/переиспользуем. Второй запрос с тем же ключом
считать НЕ надо: отдаём готовый. Мы индексируем `slice_key → {подпись, где лежит}`, а сам G-code может
жить где угодно (у юзера, на устройстве, у пира, в CDN) — мы гарантируем подлинность подписью.

**Layout-путь (MF-1986, `project-slice-request.v1`).** Плита слайсится целиком, не по одной
детали — g-code зависит от ВСЕЙ раскладки (позиции/повороты/масштаб всех инстансов, форма стола,
intent). Компонент `model_hash` заменяется на `layout_digest` — sha256 канонического JSON
`{bed_geometry, instances без instance_id, intent}` (`packages/contracts/jobs/slicer-plate.ts`,
`computeLayoutDigest`), сервер считает его сам, не доверяя клиентскому хэшу:

```
slice_key = hash( layout_digest · profile_hash · config_fingerprint )
```

Идемпотентность — на этом `slice_key`, не на client-side `layout_snapshot_id` (тот только
корреляция для reload). Плоский одномодельный путь (`model_id` без `layout`) остаётся как есть —
`model_hash`-формула выше по-прежнему в силе там, где раскладки нет.

## 2. Config fingerprint — когда слайс переиспользуем (критично для безопасности)

Слайс валиден ТОЛЬКО для той конфигурации, под которую посчитан. Отдать чужой слайс не той машине =
брак или опасность (неверные температуры/лимиты → поломка, в пределе — возгорание). Поэтому:

- **Стоковый принтер** (модель без модификаций: заводской хотэнд/стол/сопло/прошивка) → **канонический
  fingerprint модели** — общий для ВСЕХ таких же машин. Их слайсы взаимозаменяемы → дедуп работает.
- **Модифицированный** (сменил хотэнд/сопло 0.4→0.6/стол/прошивку/кинематику) → **индивидуальный
  fingerprint** → своя связка → свой слайс, чужой не отдаём.

Как узнаём конфигурацию: наш агент на принтере читает Klipper/Moonraker config → выводит fingerprint;
для managed — по модели из БД + декларация юзера «сток/модифицирован». **Верификация конфигурации — наша
роль:** общий слайс отдаём, только когда уверены, что машина действительно сток-идентична.

## 3. Учётка = верификатор + якорь связности

Аккаунт на платформе — твой identity и корень доверия:
- **Связывает твои устройства:** 2 принтера на одной учётке — один парк, общий доступ к твоим
  **локальным моделям** и слайс-кэшу.
- **Определяет доступ:** твои модели видны твоим принтерам через учётку (не публично).
- **Корень доверия для P2P:** пир доверяет данным, потому что подпись/учётка верифицированы платформой.

## 4. Поток «Запустить печать» (пример оператора, по шагам)

Юзер (учётка A) жмёт «печать» модели M с профилем P на принтере D:

1. Считаем `slice_key = hash(M, P, fingerprint(D))`.
2. **Ищем готовый G-code по slice_key, по возрастанию стоимости:**
   - **(a) Локально в твоём парке** — другой твой принтер (учётка A, та же LAN) уже имеет этот файл →
     **P2P по локальной сети**, мгновенно, без облачного трафика.
   - **(b) Твой облачный кэш** — ты уже печатал это → отдаём.
   - **(c) Глобальный content-addressed кэш** — кто-то с ИДЕНТИЧНОЙ связкой (сток-принтер той же модели,
     та же M+P) уже слайсил → отдаём его G-code, **верифицированный нашей подписью** (гарантия
     подлинности; юзер получает не «чужой файл», а проверенный платформой слайс для его связки).
   - **(d) Нет нигде** — слайсим на сервере (apps/mesh-воркер) → подписываем → кладём в кэш под
     slice_key → отдаём. Все будущие идентичные связки берут из кэша (посчитали один раз на всех).
3. **Другой бренд / нужен новый слайс** (D2 несовместим с готовым) → повторяем с `fingerprint(D2)`: сначала
   кэш (может кто-то на таком D2 уже слайсил M+P), иначе сервер → в кэш.
4. **Доставка:** файл у твоего пира в LAN → P2P локально; иначе с сервера/CDN. Принтер перед стартом
   **верифицирует подпись** у платформы: «это валидный слайс для slice_key» — иначе не печатает.

Итог механики оператора: *заслайсил один раз под принтер — у кого идентичный не слайсим повторно; твои
принтеры и цех обмениваются напрямую; сервер слайсит только НОВОЕ; платформа всё это верифицирует.*

## 5. Что храним МЫ vs что фрагментировано

| Мы (верификатор, O(1)) | Фрагментировано (устройства/юзеры/пиры, O(n)) |
|---|---|
| индекс `slice_key → подпись, метаданные` | сами G-code файлы (у юзеров, на устройствах, CDN) |
| config-fingerprint'ы (сток-канон + модифицированные) | передача файлов (P2P локально / между юзерами) |
| подписи/ключи доверия, identity учёток | вычисление слайса (наш сервер только для НОВОГО) |
| граф «учётка → устройства → парк» | локальные модели юзера (у него) |

## 6. Экономика и масштаб

- **Слайсинг:** популярная модель на стоковой машине слайсится **один раз на всех** — не N раз. Огромная
  экономия CPU (слайсинг — секунды-минуты вычислений).
- **Трафик:** файл между твоими принтерами / в цеху — по LAN (P2P), не через облако. Экономия CDN и
  задержки.
- **Наша нагрузка:** O(1) на связку (проверить хэш/подпись — микросекунды), а не O(n) на каждую печать
  (слайс+хранение+раздача). Платформа не пухнет от объёма — растёт граф доверия, не вычисления.

## 7. Безопасность / верификация

- Слайс для чужой машины опасен → общий слайс отдаём ТОЛЬКО при доказанной сток-идентичности (fingerprint).
- G-code подписан платформой; принтер проверяет подпись перед печатью (integrity + authenticity, не подмена).
- P2P между чужими юзерами — только верифицированные слайсы (подпись наша), не сырой обмен файлами.
- Приватность: локальные модели юзера не публичны; P2P в чужой парк — только с согласия/по кэш-ключу
  публичной модели.

## 8. Этапы (ложатся на версии)

**Обновлено 2026-07-16 (см. §9) — «v2» ниже устарело для глобального кэша, актуальная граница v1
зафиксирована в §9 и `../epics/v1.device.cloud.md`.**

- **v1:** account-scoped content-addressed слайс-кэш (dedup только внутри аккаунта) + подпись/
  верификация; фундамент (fingerprint, slice_key) под будущий P2P без переделки схемы. Глобальный
  кэш и P2P — НЕ в v1 (см. §9, MF-1075).
- **v3+ (после отдельного решения CTO, см. §9):** глобальный content-addressed слайс-кэш для
  стоковых связок (MF-902); P2P локальный обмен в парке/цеху (твои устройства одной учётки);
  config-fingerprint через агент.
- **v3+:** P2P между юзерами с верификацией; обмен в рамках цеха разных владельцев.

Связь: слайсинг — [../epics/slicer.profiles.md] (MF-34/408..413); серверный слой/агент —
[printer.server.md]; учётка/identity — auth.plag.space (PlagID).

## 9. Граница поставки v1 и следующий контур (2026-07-16)

v1 реализует только безопасный фундамент: account-scoped slice-cache, очередь серверного
слайсинга, `config_fingerprint` в схеме и проверку привязки результата к аккаунту/профилю/
конфигурации перед dispatch. Это контур [MF-1075](mention://issue/7c29c98a-04f5-43c0-8f6d-adbad265dfa2)
([MF-1076](mention://issue/925b9a0a-3844-4533-86ab-712212df2c4c),
[MF-1078](mention://issue/1536f33d-4c83-4e79-94f6-fbe9f860e844)); он намеренно не выдаёт
результат одного аккаунта другому и не включает P2P.

MF-902 — следующий v3+ workstream, а не дубликат v1-очереди. Переход к глобальному dedup
разрешён только после того, как `config_fingerprint_source=agent` доказан фактом, результат
подписан платформой, а trust-контур различает заявленный и проверенный fingerprint. До отдельного
решения CTO нельзя добавлять cross-account выдачу или P2P-доставку в production.
