# Карта сервисов, зон ответственности и швов (для параллельной распределённой команды)

**Цель.** Каждый агент пишет СВОЙ микросервис/домен в своей папке, никто никому не мешает, все
работают параллельно и **заранее знают ШВЫ** (где сервисы соединяются) — чтобы потом не
синхронизироваться долго. Один шов = один контракт-пакет; менять его = один PR, обе стороны
адаптируются независимо.

> **Диагноз коллизий (2026-07-11):** домены УЖЕ нарезаны (`apps/api/src/<domain>`, `apps/web/src/<domain>`),
> но трение шло на общих файлах: `server.ts` (187 регистраций роутов — все правят), `auth` (импортится
> 138× — общее ядро), `db/`, и на неявных контрактах web↔api и relay↔agent. Эта карта убирает трение
> владением + швами, НЕ переписывая существующий код.

---

## 1. Три золотых правила (снимают 90% коллизий)

1. **Одна папка — один владелец.** Никакие два агента не правят одну папку параллельно. Владелец —
   в [CODEOWNERS](../../CODEOWNERS). Нужна чужая папка → не лезь в неё, а попроси её владельца через
   карту-зависимость ИЛИ ходи через ШОВ (контракт), не через внутренности.
2. **Сервис импортит ТОЛЬКО свою папку + `packages/*`.** Запрещено `import` из `src` другого
   `apps/*`-сервиса и из внутренностей чужого домена. Исключение — общее ядро `auth` (сессия/юзер,
   **read-only**, меняет только Back). Всё межсервисное — через шов (§3): контракт-пакет, HTTP, очередь-
   таблица или БД-строка.
3. **Менять шов = один PR в `packages/contracts/*`.** Это ЕДИНСТВЕННАЯ точка синхронизации. Обе
   стороны шва адаптируются в своём темпе после мержа контракта. Пока контракт не тронут — пиши свой
   сервис сколько угодно параллельно, никого не блокируя.

Следствия: **никто не редактирует `server.ts` руками** (§4 авто-регистрация); **только владелец
таблицы пишет в неё** (остальные читают через API/контракт, миграции — Data); коммить только свою
папку.

## 3. ШВЫ — где сервисы соединяются (знать заранее, синкаться только тут)

Все швы живут в `packages/contracts/` (см. его README). Пять швов покрывают всё межсервисное:

1. **`http`** — web ↔ api. Типы запрос/ответ по домену (`http/<domain>.ts`). Продюсер — владелец
   api-домена; консюмер — web. Меняешь форму ответа → PR в `http/<domain>.ts`, web адаптируется. Убирает
   неявный fetch-контракт (сейчас web пишет запросы руками).
2. **`device-protocol/v1`** — relay ↔ device-agent. `schema.json`, generated types, runtime validators
   и valid/invalid fixtures являются единым authority; обе стороны импортируют этот пакет. Любое
   изменение контракта обновляет schema/generated artifacts/fixtures и проходит drift gate.
3. **`jobs`** — api ↔ воркеры (mesh/scout/giga/search). Схемы payload+result + **контракт таблицы-
   очереди** (api кладёт джобу в таблицу со статусом `pending`, воркер забирает, пишет результат).
   Продюсер — api-домен; консюмер — воркер. Развязывает их полностью: общаются через таблицу+схему,
   не через код.
4. **`printer-driver`** — контракт `PrinterDriver` (getState/telemetry/command/camera). Реализации —
   `moonraker-adapter` (и будущие bambu/prusa/octoprint). Владелец контракта — Bridge; новый бренд =
   новый адаптер-пакет, ядро не трогается.
5. **`db-rows`** — типы строк БД для кросс-доменного ЧТЕНИЯ. Пишет в таблицу только её владелец-домен;
   остальные читают типизированно через этот пакет, но не пишут. Миграции/схема — **Data**
   (dbmate, `apps/api/db/migrations`).

**Единственная синхронизация команды** — ревью PR в `packages/contracts/*`. Всё остальное параллельно.

## 4. Убрать файл-коллизию `server.ts` (конвенция авто-регистрации)

Сейчас 187 регистраций роутов в одном `server.ts` — каждый домен его правит → конфликты. Целевая
конвенция (миграция — карта на Back, не в этом документе):
- Каждый домен экспортирует свой Fastify-плагин `apps/api/src/<domain>/routes.ts` (`export default
  fp(async (app)=>{...})`).
- `server.ts` НЕ содержит доменных роутов — он **глобит** `src/*/routes.ts` и монтирует их под
  `/<domain>`. Добавляя эндпоинт, агент трогает ТОЛЬКО свой `routes.ts`, `server.ts` не открывает.
- До миграции: правь в `server.ts` только СВОЙ блок регистрации (одна строка), не переформатируй файл.

Аналогично `main.ts`/`db/` — общая инфра меняется через конвенцию/владельца (Back+Ops), не наскоком.

## 5. План физического выделения в отдельные сервисы (post-v1, чтобы не ломать in-flight)

Сейчас форум/идеи/каталог/совместимость живут модулями в `apps/api` (общий рантайм) — это ОК для v1
(FK на `users`, одна БД). Выделять в отдельные деплоймые сервисы — когда домен дозреет и нагрузка
потребует, по одному, через шов уже готовый:
- `apps/forum` ← `api/src/{community,feed,makes}` (Fullstack) — кандидат №1 (высокая нагрузка ленты).
- `apps/slicer` ← модуль слайсинга (Mesh) — уже отдельный воркер внутри `apps/mesh`, вынести при росте.
- `apps/catalog` ← `api/src/{catalog,printers,compat}` (Data) — при росте парсер-нагрузки.
Каждое выделение = перенос папки + подъём своего рантайма; швы (http/jobs/db-rows) уже развязали
зависимости, поэтому вынос механический, без переписывания потребителей.

## 6. Как это даёт параллельность без синка (итог)
- Взял карту → работаешь в СВОЕЙ папке (§2) → импортишь только своё + `packages/*` (§1) → эндпоинты в
  своём `routes.ts` (§4) → пишешь в свои таблицы, читаешь чужие через `db-rows`/API (§3).
- Пересекаешься с другим сервисом ТОЛЬКО на шве → правишь контракт в `packages/contracts` одним PR →
  дальше каждый в своём темпе. Долгой синхронизации нет by design.
- CODEOWNERS + эта карта — источник, кто чем владеет; CTO раздаёт карты, уважая границы папок.
