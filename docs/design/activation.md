# Активация: first-run/онбординг новичка (эпик MF-436/MF-437/MF-438)

← [docs/design/readme.md](readme.md)

Реверс-инжиниринг того, что реально работает в `dev` — не новая философия, а фиксация фактического
поведения `apps/api/src/profile/activation.ts` (профиль активации) и `apps/web/src/home/firstrun.tsx`
+ `apps/web/src/auth/onboarding.tsx` (сам wizard). Follow-up ревизии MF-486 (карточка MF-568,
вердикт Docs 18.07: design-контент авторствует Design, не Docs) — на момент написания design-спека
по MF-436 отсутствовала на 100%, хотя код в `dev` уже 5+ фаз (MF-436→438).

**Где это на экране** — уже канон в [home.scenario.md §6](home.scenario.md) и
[home.visual.md §1](home.visual.md): `FirstRunFlow` — мягкий инлайн-блок, третий и последний ребёнок
`.homeContent`, только на `state === "first_run"`, ниже hero-поиска и полок. Этот файл не повторяет то
решение — здесь только внутренняя механика самого wizard'а: state machine, шаги, персоны, чек-лист,
телеметрия, реальные (не документированные раньше) особенности поведения.

## 1. Три слоя активации — не путать

| Слой | Где живёт | Что решает |
|---|---|---|
| **Хендл** (`HandleOnboarding`) | `apps/web/src/auth/onboarding.tsx`, гейтится `AuthGate` (`auth/authgate.tsx`) | Блокирующий полноэкранный шаг ДО всего приложения: пока `session.user.handle_confirmed === false`, вместо любого маршрута показывается выбор `@логина`. Не часть `FirstRunFlow` и не пишет в `user_activation` — отдельный контракт (`PATCH /me` → `handle_confirmed = true` на бэке). |
| **Состояние активации** (`user_activation.state`) | `apps/api/src/profile/activation.ts` | `first_run` \| `returning` — переживает reload/устройства, единственный источник истины для «показывать ли `FirstRunFlow`». |
| **Шаг wizard'а** (`FirstRunFlow`) | `apps/web/src/home/firstrun.tsx` | Пока `state === "first_run"` — какую именно карточку показать (`computeFirstRunStep`, чистая функция от персистентных полей, никакого отдельного client-side стейта шага). |

Хендл всегда идёт первым (без него человек вообще не видит `HomeScreen`), активация — второй слой,
уже внутри дома.

## 2. `state`: first_run → returning — три реальных триггера, не четыре

Комментарий в `activation.ts` (строка над `RETURNING_AFTER_SESSIONS`) декларирует триггер «≥1
«ага»-действие (привязка принтера)» — **в коде такого перехода нет**. `has_printer=true` НЕ
переводит в `returning`. Реальных триггеров ровно три:

1. **Пропуск персоны на первом шаге.** `PersonaCard` → «Пропустить» вызывает
   `activation.patch({ first_run_completed: true })` немедленно (`firstrun.tsx`, обработчик
   `onClick` кнопки `.homeSkipLink`, событие `first_run_completed` с `trigger: "persona_skip"`).
   Это **не** пропуск одного шага — это выход из ВСЕГО wizard'а сразу. Отличается от «Пропустить»/
   «Позже» на всех остальных шагах (те дисмиссят только свой шаг и ведут дальше по цепочке —
   см. §4).
2. **Чек-лист закрыт полностью.** `ActivationChecklist` — когда все шаги персоны `done`,
   `useEffect` пишет `first_run_completed: true` (`trigger: "checklist_all_done"`,
   `checklist.tsx`).
3. **N сессий.** `RETURNING_AFTER_SESSIONS = 5` (`activation.ts`) — грубый счётчик: каждый
   `GET /me/activation` инкрементит `sessions_seen` (upsert), и на 5-й сессии сервер сам переводит
   `state` в `returning`, даже если человек ни разу не открывал `FirstRunFlow`/не отвечал ни на один
   шаг. Единственный триггер БЕЗ клиентского действия.

Других путей в `returning` нет. `PATCH /me/activation {state: "returning"}` напрямую тоже возможен
(эндпоинт принимает `state` как произвольное поле), но ни один живой клиент так не делает.

## 3. Персоны — 5 в схеме, 4 объявляемых тапом

`PERSONAS = ["novice", "maker", "author", "builder", "pro"]` (и БД-констрейнт, и `activation.ts`
`apps/web`), но `PersonaCard` (`firstrun.tsx`) рисует только **4 плитки**:

| Плитка | id | Подпись |
|---|---|---|
| «У меня есть принтер» | `novice` | Хочу печатать |
| «Выкладываю модели» | `author` | Я автор |
| «Собираю принтер» | `builder` | DIY / Voron |
| «Печатаю на заказ» | `pro` | Мастер / ферма |

**`maker` не объявляется тапом никогда** — это inference-only персона (`inferpersona.ts`,
`useInferredPersona`, живёт в `HomeScreen`, не в `FirstRunFlow`): достраивается молча по поведению,
когда `primary_persona` пуст или уже `inferred` (объявленную персону эта логика никогда не
перезаписывает — `shouldApplyInferredPersona`). Три сигнала по убыванию силы:

1. **3+ принтера в парке → `pro`** (сильный, однозначный).
2. **Загружена первая модель → `author`.**
3. **Есть принтер И открывал каталог (`catalog_visited`) → `maker`** — единственный путь получить
   эту персону, и он не тап, а побочный эффект чек-листа/навигации.

`persona_source`: `"declared"` (тап по плитке) vs `"inferred"` — поле опционально (`null` у строк
старее этого поля), хранится, чтобы decided-выбор пользователя был неприкасаем.

## 4. `computeFirstRunStep` — цепочка шагов

Единственный источник истины «на каком шаге сейчас» — чистая функция от персистентного `activation`
(`FirstRunStep = "persona" | "printer_question" | "picker" | "filament" | "soft_track" | "checklist"`,
`firstrun.tsx`). Рендерится **ровно один шаг за раз**, никогда два одновременно.

1. **`persona`** — пока нет `primary_persona`. Тап по плитке → `declared` → следующий шаг. Кнопка
   «Пропустить» — не следующий шаг, а сразу `returning` (§2.1), дальше цепочка не идёт.
2. **`printer_question`** — «У вас уже есть 3D-принтер?». Все три ответа (Да / Пока нет /
   Пропустить) пишут `home_dismissed_prompts.printer_answer` и терминальны — шаг не появится
   снова. Код различает только `answer === "yes"` от всего остального (`"no"` и `"skip"` дальше
   ведут по одной ветке).
   - **Ветка «Да»:**
     a. **`picker`** — пока `!has_printer && !dismissed.picker`. Привязка принтера ИЛИ «Позже»
        (`Button` с иконкой часов, не текстовая ссылка) — оба исхода отмечают `dismissed.picker`
        и ведут дальше; после «Позже» `has_printer` может остаться `false`.
     b. **`filament`** — пока `!dismissed.filament`, независимо от того, привязан ли принтер.
        Чипы популярных материалов + «Пропустить» в любой момент.
     c. **`checklist`** — терминальный шаг (§5).
   - **Ветка «Пока нет» / «Пропустить»:**
     a. **`soft_track`** — пока `!dismissed.soft_track`. Три двери (`SoftTrackDoors`): «Посмотреть,
        что печатают» (уходит на `/market`, отмечает `soft_track`), «Подобрать первый принтер»
        (переиспользует тот же `PrinterPicker`, но пишет `dismissed.soft_track`, а не
        `dismissed.picker` — независимый ключ от шага (a) ветки «Да»), «Продолжить без принтера»
        (просто отмечает `soft_track`).
     b. **`checklist`** — как только `soft_track` отмечен, сразу терминальный шаг; `filament` в
        этой ветке НЕ показывается (он есть только после «Да»).

Свойства цепочки, которые стоит держать в голове при правках:

- **`printer_question` не зависит от персоны.** Даже персона `author` (которой чек-лист вообще не
  задаёт вопросов про принтер/филамент — см. §5) всё равно проходит через
  «У вас уже есть принтер?» и его ветку (picker+filament при «Да», soft_track при «Нет»/
  «Пропустить»), прежде чем попасть на свой author-чек-лист. Это реальное поведение кода, не
  идеализация — возможный кандидат на упрощение (author вряд ли должен отвечать на вопрос про
  принтер), но НЕ трогать без отдельной карточки: сейчас это не баг, а недокументированная
  особенность, которую фиксирует этот файл.
- **Ответ на `printer_question` невозможно переспросить.** Любое из трёх значений
  (`"yes"|"no"|"skip"`) — терминальная запись; при следующей загрузке страницы шаг не появится
  снова, даже если `has_printer` всё ещё `false` после «Да».
- **`soft_track`-picker и терминальный `picker`-шаг — два разных места, один компонент.**
  `PrinterPicker` переиспользуется трижды в файле (top-level шаг `picker`, ветка `SoftTrackDoors`,
  и снова в `ActivationChecklist` — см. §5) с разной семантикой `onLinked/onSkip`, но каждый вызов
  пишет в СВОЙ ключ `home_dismissed_prompts` (`picker` либо `soft_track`) — они не путаются между
  собой, но и не синхронизированы: связать принтер через `soft_track`-дверь не отмечает
  `dismissed.picker` (неважно — до `soft_track` эта ветка уже не проверяет `picker`).
- **`filament` — только в ветке «Да».** Ветка «Пока нет»/«Пропустить» идёт `soft_track → checklist`
  напрямую, шаг филамента в ней не показывается вообще — это НЕ то же самое, что «филамент общий
  для обеих веток», как можно было бы предположить по аналогии с чек-листом (§5).

## 5. Чек-лист — терминальный шаг, персона решает состав

`ActivationChecklist` (`checklist.tsx`) — последний шаг цепочки для всех персон, но набор пунктов
ветвится ровно на два варианта:

**`persona === "author"`:**
1. Аккаунт создан (всегда `done`, не кликабелен — см. ниже).
2. Загрузите первую модель → `/models/add`, отмечает `activation_checklist.model_uploaded`.
3. Заполните профиль → `/u/<username>`, отмечает `profile_visited`.
4. Найдите вдохновение в каталоге → `/market`, отмечает `catalog_visited`.

**Все остальные персоны (`novice`/`builder`/`pro`, и по факту `maker` — но `maker` не может быть
активной персоной ДО завершения first_run, см. §3):**
1. Аккаунт создан.
2. Привяжите принтер (`builder`: «Привяжите вашу сборку») → открывает `PrinterPicker` в оверлее
   (`overlay.modal`), done = `activation.has_printer`.
3. Откройте модель для печати (`builder`: «Сравните станки в каталоге») → `/market`, тот же
   `catalog_visited`, что и у author-варианта.
4. Укажите филамент → открывает `FilamentStep` в оверлее, done = `filaments.length > 0`.

**Эффект Зейгарник умышленно встроен:** первый пункт («Аккаунт создан») всегда `done: true` и
`action: () => {}` — прогресс-бар стартует не с 0%, а с одного закрытого пункта из четырёх (~25%),
без единого клика пользователя.

Виджет скрывается («Пропустить» / `×`), если ЛИБО `home_dismissed_prompts.checklist === true`,
ЛИБО все шаги `done` — и в момент, когда все шаги стали `done`, это САМО по себе переводит
`state → returning` (§2.2), так что дисмисс по завершению и переход состояния — одно и то же
событие, не два.

## 6. Тексты и тон — что реально в коде

- **«Пропустить» видно на каждом шаге, где оно есть**, и всегда с одинаковым весом действия —
  текстовая ссылка `.homeSkipLink`, не приглушённая кнопка: пропуск не наказывается визуально
  (иначе это не равноправный выбор, а трюк). Единственное исключение по факту веса — `picker`
  top-level шаг зовёт кнопку «Позже» (`Button variant="secondary"`, с иконкой часов), а не
  текстовую ссылку — единственное расхождение стиля дисмисса в цепочке.
- **Вопросы короткие, без объяснения зачем.** «Что вас сюда привело? Настроим портал под вас» /
  «У вас уже есть 3D-принтер?» / «Каким пластиком печатаете?» — ни один шаг не сопровождается
  абзацем убеждения; логика «зачем» (тайлы под персону, фильтр совместимости) нигде не
  проговаривается пользователю — она просто следует бесшовно из выбора.
- **Пустых экранов после «Нет» нет.** `SoftTrackDoors` (нет-ветка `printer_question`) — три
  двери, ни одна не тупик: витрина, тот же picker принтера или явное «продолжить без принтера».
  Комментарий в коде называет это «soft-track», решение оператора от 2026-07-09 — picker как
  живая заглушка-витрина, не квиз-лайт (открытый вопрос эпика на момент записи).
- **Persona-тайлы отвечают на «зачем я тут», не «кто я».** Подписи — действие/цель («Хочу
  печатать», «Я автор»), не социальная роль-ярлык.

## 7. Персистентность — сервер, не `localStorage`

Все ответы, дисмиссы и прогресс чек-листа идут через `PATCH /me/activation` в
`activation_checklist`/`home_dismissed_prompts` (JSON-поля `user_activation`) — ни один шаг
`FirstRunFlow` не хранит состояние в `localStorage`. Это гарантирует критерий приёмки MF-437:
ни один вопрос/шаг не возвращается на reload или на следующий вход того же аккаунта, включая
устройство. (Контраст: коучмарка `search_or_generate` в `coachmarks.ts` — отдельный, не связанный
с активацией слой — для гостя действительно падает в `localStorage`, потому что у гостя ещё нет
`user_activation`; это не имеет отношения к `FirstRunFlow`, который вообще не рендерится гостю.)

## 8. Телеметрия воронки

`POST /me/activation/events` — единственный канал, allowlist `ACTIVATION_EVENT_NAMES`
(`apps/api/src/analytics/events.ts`) сужен относительно общей таксономии `events`. Реально
эмитятся из `FirstRunFlow`/`checklist.tsx` (`track.ts`, `trackActivation`):

| Событие | Когда |
|---|---|
| `persona_declared` | Тап по плитке персоны (`{ persona }`) |
| `printer_question_answered` | Любой из трёх ответов (`{ answer }`) |
| `printer_picker_open` | Открытие `PrinterPicker` (все три места вызова) |
| `printer_linked` | Успешная привязка (`{ link_source }`: `popular`/`search`/`manual`) |
| `printer_not_found_manual` | Переключение picker'а в ручной ввод |
| `soft_track_chosen` | Тап по одной из трёх дверей soft-track (`{ track }`) |
| `checklist_step_done` | Отметка шага чек-листа (`{ step }`) |
| `first_run_completed` | Один из двух клиентских переходов §2, с `{ trigger }` = `persona_skip` или `checklist_all_done` (третий триггер — N сессий — переход серверный, без клиентского события) |
| `home_view` / `first_run_start` / `state_changed` | Логируются из `HomeScreen`, не из `FirstRunFlow` — уровень дома видит смену `activation.state` целиком, сам wizard этого не видит |

`aha_reached` числится в `ACTIVATION_EVENT_NAMES`, но по факту его эмитит только
`ModelTileGridWithAha` в `apps/web/src/home/personahome.tsx` — компонент, не подключённый ни к
одному живому маршруту (см. `home.scenario.md §7`, `CompatModule` снят с главной). Событие в
таксономии есть, реального источника на сегодня нет — фиксирую как известный разрыв, не мой
контур чинить (Front/Data, при возврате `CompatModule` на «Принтеры»/карточку модели).

## 9. Известные разрывы код↔документация на момент записи

- Комментарий-триггер «≥1 «ага»-действие (привязка принтера)» в `activation.ts` не реализован
  (§2) — либо мёртвый комментарий, либо недоделанная Фаза; не мой контур менять код, фиксирую факт.
- `printer_question`/`picker`/`filament` не пропускаются для `author`, хотя author-чек-лист их не
  использует (§4) — задокументировано как факт, не как желаемое поведение.
- `aha_reached` — таксономия есть, источник не подключён (§8).
