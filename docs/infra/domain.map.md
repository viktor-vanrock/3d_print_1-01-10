# Карта доменов/поддоменов — зоны на сетевом уровне (зеркально dev ↔ prod)

**Цель.** Продолжить разделение зон [service.map.md](../architecture/service.map.md) на уровень DNS:
чтобы зоны жили НЕ только на `api`, у каждой значимой — свой поддомен со своим владельцем и правилами
коммуникации. Поддомен = **стабильная логическая зона** (публичный контракт), развязанная от того, на
каком VDS/сервисе она сейчас крутится. Реверс-прокси маршрутизирует поддомен → текущий бэкенд (сегодня
часто монолит `api`), при выделении сервиса меняется ТОЛЬКО цель прокси, не имя.

> **Проектирование — ассистент; СОЗДАНИЕ DNS-записей — Domain, реверс-прокси/vhosts — Ops.**
> Набор поддоменов согласует **CTO** (нужны ли ещё). Ассистент DNS сам не трогает.

## 1. Правила (законы этой карты)

1. **Зеркальность dev ↔ prod — обязательна.** Любая зона существует в ДВУХ идентичных именах:
   `<зона>.3mf.tech` (prod) и `<зона>.dev.3mf.tech` (dev). Набор поддоменов на обоих окружениях —
   ОДИНАКОВЫЙ. Заводятся парой, не по одному. (Корень: prod `3mf.tech` ↔ dev `dev.3mf.tech`.)
2. **Поддомен развязан от сервера.** Сейчас: dev → VDS `82.202.159.148`, prod → VDS `176.123.160.18`
   (2 машины, всё на них). При росте зона переезжает на свой VDS/LB — **имя не меняется**, меняется A/CNAME
   у Domain + upstream у Ops. Код и клиенты завязаны на имя, не на IP.
3. **Новый поддомен — только весьма аргументированно (гейт).** Завести новый поддомен можно ТОЛЬКО если
   выполнено ВСЁ: (a) отдельная граница доверия/безопасности (свой auth/CORS/экспозиция) ЛИБО отдельный
   профиль нагрузки (персистентный WS ≠ stateless REST ≠ тяжёлая статика) ЛИБО отдельный деплой другого
   сквада; (b) это НЕ решается путём под существующим поддоменом; (c) есть названный владелец; (d)
   зеркально dev+prod. Апрув — **CTO + Domain**. Иначе — путь `/<зона>` под существующим поддоменом.
4. **Межсервис — приватно.** Сервис-сервис (api↔воркеры, воркеры↔БД) ходит по приватной сети
   (Tailscale `100.x` / localhost), НЕ через публичные поддомены. Публичные поддомены — только для
   браузера/агента-устройства.
5. **Владелец поддомена = владелец зоны** из [service.map.md](../architecture/service.map.md)+CODEOWNERS.
   DNS-запись ведёт Domain, vhost/прокси — Ops, содержимое — владелец зоны.

проходит). При нужде во внутреннем health — имя в приватной зоне, не в публичной.

## 3. Правила коммуникации (кто с кем и как)
- **Браузер →** `3mf.tech` (web) · `api.3mf.tech` (REST) · `relay.3mf.tech` (WS live, если смотрит) ·
  `cdn.3mf.tech` (ассеты, публичное чтение) · `auth.plag.space` (вход). Больше публичных точек у браузера нет.
- **Агент-устройство →** `relay.3mf.tech` (исходящий WSS, mTLS/enroll). Только сюда.
- **web → api**, никогда напрямую в воркеры. **api → воркеры** через очередь-таблицу (шов `jobs`), не HTTP.
  **воркеры → S3/БД**. Всё сервис-сервис — приватно (§1.4).
- **CORS:** `api`/`relay` разрешают origin `3mf.tech` (prod) и `dev.3mf.tech` (dev) — симметрично. `cdn` —
  публичное чтение. Dev и prod НЕ ходят друг в друга (dev.web → dev.api, prod.web → prod.api).
- **TLS:** каждый публичный поддомен — свой серт (Cloudflare/Let's Encrypt), оба окружения.

## 4. Что просим создать (Domain + Ops), зеркально dev+prod
Итоговый набор — после апрува CTO (§2 кандидаты). Базово к заведению СЕЙЧАС (аргумент проходит гейт):
- **`relay.3mf.tech` + `relay.dev.3mf.tech`** — Domain: DNS (A/CNAME на соответствующий VDS); Ops: vhost
  → L4 TLS passthrough к compiled Nest relay gateway listener (dev :3011; prod — отдельный
  `RELAY_GATEWAY_PORT`, см. `apps/relay/deploy`). Observability port не публикуется. Перевести
  агентов на отдельный relay-поддомен; legacy API-host location не является target-конфигурацией.
- **`cdn.3mf.tech` + `cdn.dev.3mf.tech`** — Domain: DNS; Ops: vhost → S3/R2-бакет ассетов, публичное чтение,
  кэш-заголовки.
Кандидаты `search`/`status` — по решению CTO. Всё — парой dev+prod, не по одному (§1.1).

## 5. Как масштабируемся (2 VDS → больше)
Сегодня всё на 2 VDS (dev 82.202, prod 176.123). Поддомены уже нарезаны по зонам → при росте:
переносим зону (напр. `relay`) на отдельный VDS/LB, Domain меняет A-запись, Ops — upstream, имя и код
не трогаем. Зеркальность обязывает делать это парой на dev и prod. Так набор поддоменов = план
горизонтального масштабирования, готовый заранее.

## 6.9 Внутренняя схема (растущая инфра, НЕ публичный DNS)
Сервис-сервис (api↔воркеры mesh/scout/giga/search/slicer, relay↔api) — по **Tailscale MagicDNS**
(`<svc>.<tailnet>.ts.net`) или приватной зоне `*.internal.3mf.tech`. Публичного имени воркерам НЕ даём
(гейт §1.3 не проходит). При росте сервис получает внутреннее имя сразу, публичное — только пройдя гейт.
