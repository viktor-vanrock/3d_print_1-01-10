## 0. Что уже есть в коде — не строим вторую страницу

**Ключевой факт для этого сценария:** публичная страница `/u/:username` (`apps/web/src/market/profile.tsx`,
`ProfileScreen`) — это уже почти витрина. §7 `marketplace.full.md` описывал её минимальный вид (MF-463); с тех
пор код ушёл дальше без обновления того файла. Живьём на `/u/:username` уже есть:

- `Card.profileCard`: аватар, `display_name`/`@username`, бейджи (`profile.badges`, MF-993 — «Проверенный»/«Топ-ферма»/«Популярный»,
  уже посчитаны на бэкенде `makers/contract.ts`), `bio`, `website_url`+`contacts[]`, строка счётчиков
  (`models_count` · `followers_count`).
- Кнопка **«Подписаться»/«Вы подписаны»** (`followUser`/`unfollowUser`, MF-993) — **уже полностью работает**,
  видна только гостю (`!own`).
- `own` (владелец) вычисляется как `profile.username === user.username` (`profile.tsx:115`) — уже есть чёткое
  разделение владелец/гость, реиспользуем 1:1, второй флаг не заводим.
- Владельцу (`own`) уже показан `AccountEditor` — инлайн-секция редактирования (не модалка!) полей
  `display_name`/`bio`/`website_url`/`contacts` + отдельный кроп-флоу аватара. Смена ника — отдельная,
  более тяжёлая модалка (`home/profileedit.tsx`), не трогаем.
- `MyCatalogsSection` (`profile.catalogs.tsx`) — «Мои принтеры»/«Мои филаменты»: список из каталога
  (`PrinterPicker`/`MaterialPicker`, тап по строке чужого свободного текста программно невозможен — выбор
  только из справочника), тап по строке → редактирование (`PrinterEditForm`/`FilamentEditForm`), корзина →
  `overlay.confirm`. **Сейчас рендерится только при `own` — гость её не видит вообще.**

Это значит: URL, разделение владелец/гость, честный источник бейджей/подписки и даже механизм «выбор из
справочника, не текстом» для парка — **уже решены существующим кодом**, Фазе 1 нужно не изобретать их
заново, а (а) добавить мастер-специфичные поля в ту же шапку и (б) сделать парк видимым гостю. Ниже — что
именно.

**Не путать с `docs/design/park.md`.** Тот файл — `/park`, приватная страница управления СВОИМИ устройствами
(живой статус, команды принтеру). Здесь — публичная витрина парка на `/u/:username`: только факт владения
(модель/материал), без live-статуса печати. Разные поверхности, разные данные, не смешивать.

## 1. Условие рендера мастер-варианта

Всё ниже (§2–§4) показывается на `/u/:username` **только когда `profile.is_master === true`** (новое
булево поле ответа `GET /users/:username`, читает `users.is_master`, домен уже одобрен в `domain.model.md`).
Для обычного автора (`is_master === false`) страница остаётся как сегодня — ничего не меняется, ничего не
скрывается.

`is_master` не переключается на этой карточке (нет UI «стать мастером» — вне объёма MF-949/MF-399, тот флаг
проставляется отдельным флоу активации роли). Здесь мы проектируем только то, что видно, когда флаг уже
`true`.

## 2. Шапка (имя/лого/город/слоган)

Расширяем существующий `profileCard`, не создаём второй блок:

| Элемент | Источник | Что нового |
|---|---|---|
| Имя | `display_name` / `@username` — как сегодня | ничего |
| Лого | `avatar_url` — тот же механизм, что личный аватар (крoп-флоу `AccountEditor`) | **ничего нового технически**: для мастера это тот же файл/поле, просто смысл переименован в UI-копирайте на «Логотип» вместо «Аватар» (владелец загружает лого фермы туда же, где раньше — свою фотографию) |
| Город | `master_profile.city` (новое, jsonb) | новое поле, строка под именем, мелким `Eyebrow`-стилем (тот же токен, что `@username`) — например «Москва» |
| Слоган | `master_profile.slogan` (новое, jsonb) | новое поле, короткая строка под городом/описанием, курсивом/приглушённо — не более ~80 символов, одна строка, обрезка `text-overflow: ellipsis` при переполнении |

**Открытый вопрос к Back/Data:** черновая схема `domain.model.md` заводит `master_profile jsonb {headline,
description, city, slogan}` — в этой карточке `headline` не упомянут в требованиях (только имя/лого/город/
слоган), а `description` дублирует уже существующее поле `users.bio`. UX-рекомендация: **не заводить
`description` внутри `master_profile`, переиспользовать `bio`** (см. §3) — одно поле «описание», а не два
несинхронных источника правды. Что делать с `headline` (нет в требованиях этой карточки) — решает Back при
миграции: либо не включать в MVP-версию jsonb, либо оставить зарезервированным пустым полем под будущее
(например короткий профессиональный тэглайн, отдельный от `slogan`) — эта карточка не блокируется этим
выбором, полю всё равно нет UI-слота в Фазе 1.

### 2.1 Владелец — редактирование

`AccountEditor` (инлайн-секция, не модалка — тот же паттерн, что уже редактирует bio/website/контакты)
получает два новых поля **Город** и **Слоган** рядом с существующими `Input`. Сохранение — тем же `PATCH /me`
(добавить `city`/`slogan` в `ProfilePatch`), тот же тихий успех / `toast` при ошибке, что уже описан для
остальных полей формы. Лого — существующий кроп-флоу аватара, без изменений в механике, только копирайт
кнопки/подписи «Логотип» вместо «Фото профиля» при `is_master`.

### 2.2 Гость — только чтение

Город/слоган рендерятся как обычный текст (как `bio` сегодня для гостя) — без намёка на интерактивность, без
`:hover`/`cursor:pointer`.

## 3. Описание мастера

Переиспользуем **существующее** поле `bio` (`AccountEditor`, лимит 500 символов, уже есть в проде) как блок
описания мастера — отдельного поля не заводим (см. открытый вопрос §2). Владелец правит его той же секцией,
что уже правит bio; гость видит текст как сегодня (`profile.bio ? <div className="profileBio">…` — без
изменений).

Пустое состояние: если `bio` не заполнен — блок описания просто не рендерится (как сегодня, `profile.bio ?
… : null`), не показываем «Описания пока нет» — тот же принцип, что уже применён к этому полю (не плодим
пустые рамки там, где их сегодня нет).

---

## 4. Соц-хедер (рейтинг, число выполненных, «на портале с»)

Заменяем/дополняем существующую простую строку счётчиков (`profileCount`: «N проектов · M подписчиков») на
ряд `StatTile` (`ui/ui.tsx`, уже готовый примитив — значение + `Eyebrow`-подпись + опциональный `hint`,
переиспользуем как есть, второй такой компонент не создаём) **только для `is_master`**. Для обычного автора
строка счётчиков остаётся как сегодня — эта дельта не трогает не-мастеров.

| Плитка | Данные | Состояние в Фазе 1 |
|---|---|---|
| Рейтинг | агрегат `avg(rating)` из `master_reviews` (см. `domain.model.md`) | **Отзывов физически ещё нет** (MF-992 заблокирована на MF-996, вне объёма этой карточки) — честное состояние «Отзывов пока нет» вместо плитки с цифрой/выдуманной звездой. Как только `count(master_reviews) > 0`, показывается число — контракт на будущее, не реализуется здесь |
| Выполнено | `count(print_requests where status='done')` | Тот же принцип честности: для свежесозданного мастера это реальный `0` (не «нет данных») — но сама воронка заявок ещё не имеет фронта (MF-400 Фаза 2 в работе), поэтому в Фазе 1 плитка показывает **«Выполнено: 0»** для любого мастера (честный факт «пока не подключено» = ноль), не блокирует; когда Фаза 2 подключит поток заявок, число начнёт расти само — сегодняшняя вёрстка не меняется |
| На портале с | `users.created_at`, уже есть в БД | Готово к показу уже сейчас — не зависит ни от чьей будущей фазы, просто прокинуть поле в ответ `GET /users/:username` (`created_at` → `member_since`, формат «на портале с 2026») |

Соц-хедер — **read-only и для владельца, и для гостя**: это агрегаты чтения, не поля формы, не редактируются
никем напрямую (тот же инвариант, что уже описан в `domain.model.md` для рейтинга — «не денормализованное
поле, которое можно рассинхронить UPDATE'ом»).

## 5. Кнопки «Заказать» / «Написать» / «Подписаться»

Три кнопки в один ряд под соц-хедером, видны **только гостю** (`!own`) — владелец видит свою витрину, но не
кнопки действий над самим собой (тот же принцип, что уже верен для «Подписаться» сегодня).

| Кнопка | Статус в Фазе 1 | Поток клика |
|---|---|---|
| **Подписаться** | **Уже полностью реализована** (MF-993) — не трогаем логику, только визуально ставим в один ряд с двумя новыми | Тап → `followUser`/`unfollowUser`, текст переключается «Подписаться» ↔ «Вы подписаны», как сегодня |
| **Написать** | Заглушка навигации (эта карточка явно просит НЕ реализовывать целевой экран — чат появится в MF-400 Фазе 2) | Тап → `overlay.toast({ severity: "info", title: "Скоро", message: "Чат с мастером — раздел ещё не собран" })` — переиспользуем **уже существующий** паттерн честной заглушки (`home/personahome.tsx:40`, тот же приём, что там прокомментирован «показываем "скоро" тостом, а не мёртвую ссылку»), не заводим второй способ сказать «не готово» |
| **Заказать** | Заглушка навигации (заявка — MF-400/MF-996 Фаза 2, бэкенд `print_requests` уже в `in_review`, фронта нет) | Тап → тот же паттерн: `overlay.toast({ severity: "info", title: "Скоро", message: "Отправка заявки мастеру — раздел ещё не собран" })` |

Порядок и акцент: «Заказать» — `variant="primary"` (это целевое денежное действие площадки, тот же вес, что
у любого primary CTA каталога), «Написать» и «Подписаться» — `variant="secondary"`, то же соотношение
приоритета, что сегодня «Подписаться» уже имеет как единственная кнопка (была `primary`, когда одна — при
трёх кнопках подряд primary остаётся только за «Заказать», иначе ряд из трёх одинаково ярких CTA спорит сам
с собой, тот же принцип «одна дверь», что уже применён в `ux.md §1.2`).

Тач-цели ≥48px, `:active`-отклик как у любой `Button` в проекте — ничего нового не создаём, все три —
обычные `Button` из `ui/ui.tsx`.

## 6. Парк оборудования

### 6.1 Источник данных — тот же, что «Мои принтеры»/«Мои филаменты»

Оборудование мастера — это **те же строки** `user_printers`/`user_materials`(филаменты), что уже показывает
`MyCatalogsSection` владельцу в приватном режиме. **Не заводим вторую сущность «оборудование мастера»** —
одна и та же таблица, разница только в видимости: сегодня список виден только `own`, для мастера он должен
стать виден и гостю (read-only). Это прямое следствие принципа платформы «не строить второй код» и снимает
риск рассинхронизации («у меня в ЛК 3 принтера, а на витрине почему-то 2»).

Публикация — не выбор «эти принтеры публичные, эти нет» (не проектируем гранулярную видимость по записи в
Фазе 1 — не запрошено, YAGNI): весь список парка мастера виден на его витрине целиком, как есть.

### 6.2 Раскладка на витрине

Секция «Парк оборудования» — заголовок `Eyebrow` (как «Мои идеи»/«Мои принтеры» сегодня) + список строк в
том же визуальном языке, что уже задан `.ideaRow`/`.ideaList` в `profile.catalogs.tsx` (**не** тяжёлый
`ActionCard` из `/park` — та карточка несёт живой статус печати, здесь он не нужен и не тапабелен на живую
панель):

- Строка принтера: `printerLabel(printer)` (уже существующий хелпер, бренд+модель), мелкая eyebrow-подпись
  X×Y×Z мм если задано (`build_volume`), без бейджа `support_level`/`FlagshipBadge` (тот словарь — про
  устройство юзера в его личном парке живой связи, здесь мы показываем факт владения, не готовность к
  удалённому управлению).
- Строка материала: `materialLabel(filament)` (существующий хелпер) + чип цвета/варианта, если есть (тот же
  чип, что уже рисует `profile.catalogs.tsx §3`/`MaterialPicker`).
- Несколько единиц одной модели — **отдельные строки**, группировку «Bambu X1C ×3» не строим (в схеме нет
  поля количества — каждая физическая единица уже отдельная строка `user_printers`, ровно как сегодня в
  «Мои принтеры»; групповое отображение — кандидат на будущую итерацию, не требование этой карточки).
- Строка **не тапабельна** для гостя (не ведёт никуда — нет живой панели, которую можно было бы открыть
  постороннему).

### 6.3 Владелец — добавление и редактирование прямо на витрине

Кнопка «+ Добавить технику» / «+ Добавить материал» (secondary, тот же визуальный вес, что «+ Добавить
принтер» в `/park`) видна только `own`, открывает **уже существующие** модалки `PrinterPicker`/
`MaterialPicker` (`overlay.modal`, `size: "form"`) — тот же код, что сегодня вызывает `MyCatalogsSection`
внутри ЛК, только точка входа теперь прямо со страницы витрины, а не только из приватной секции.

Тап по строке (кроме корзины) владельцем → редактирование, тот же `PrinterEditForm`/`FilamentEditForm`, что
уже есть (`profile.catalogs.md §2–3`) — каталожная запись: бренд/модель нередактируемы, X/Y/Z/сопло/
кинематика редактируемы; ручная запись — редактируемо всё. Корзина → `overlay.confirm` на удаление, как
сегодня.

**Важно:** страница `/park` (приватный список с живым статусом печати, `park.md`) при этом **никуда не
девается** и не дублируется — это разные назначения одних и тех же данных (управление своим устройством vs
публичная витрина владения). Владелец может продолжать управлять принтерами через `/park`, а добавлять/
править состав парка теперь может и прямо со своей витрины — это один источник данных с двумя точками
входа в редактирование, не расхождение.

### 6.4 Состояния «пустой парк» / «есть техника»

| Состояние | Владелец | Гость |
|---|---|---|
| Есть ≥1 единица техники или материала | Список строк (§6.2) + кнопки «Добавить» сверху/снизу списка | Список строк (§6.2), без кнопок добавления |
| Пустой парк — принтеров и материалов нет вообще | `EmptyState` (`ui/ui.tsx`, тот же примитив, что везде): иконка принтера (`PrinterIcon`), заголовок «Добавьте свой первый принтер», primary-кнопка → открывает `PrinterPicker` | `EmptyState`: тот же `PrinterIcon`, заголовок **«У мастера пока нет оборудования»**, без action — гостю нечего нажимать (тот же принцип различия копирайта owner/guest, что уже применён к пустой галерее проектов в `profile.tsx:340-341`) |
| Есть принтеры, но нет материалов (или наоборот) | Каждая под-секция («Оборудование»/«Материалы») имеет свой независимый `EmptyState`/список — не блокируют друг друга, тот же паттерн, что «Мои принтеры»/«Мои филаменты» уже два независимых блока сегодня | То же, но без action-кнопок |

## 7. URL с необнаружимым ID

**Ничего не меняется и не проектируется заново.** Витрина мастера — это существующий маршрут `/u/:username`
(`router.ts:262`, `profilePath()`), тот же самый, что уже работает для любого автора. Требование эпика
«необнаружимый публичный ID, нельзя пересчитать число мастеров» уже выполнено этим же маршрутом сегодня:
`username` — произвольная выбранная строка, не инкрементный числовой ID, перебором соседних значений нельзя
перечислить пользователей (та же логика, что `ids.policy.md` уже зафиксировал для UUID-сущностей — здесь
роль «необнаружимого» идентификатора играет сам никнейм, second `public_id` не нужен, второй маршрут `/master/
:id` или похожий — тоже не нужен).

Явные требования по этому пункту:
- **Не добавлять** breadcrumb, счётчик «мастер N из M» или любую нумерацию мастеров на странице/в URL.
- **Не добавлять** отдельный публичный листинг «все мастера по порядку» в этой карточке (каталог мастеров —
  явно вынесен в Фазу 3, MF-401).
- Визуально страница мастера **не должна выглядеть иначе** с точки зрения структуры URL, чем страница любого
  обычного автора — разница только в контенте (шапка/парк/кнопки), не в адресной механике.

## 8. Матрица владелец vs гость (сводно)

| Элемент | Владелец (`own`) | Гость/аноним |
|---|---|---|
| Имя/лого/город/слоган | Видит + правит инлайн (`AccountEditor`, §2.1) | Видит, только чтение |
| Описание (`bio`) | Видит + правит (существующий `AccountEditor`) | Видит, только чтение |
| Соц-хедер (рейтинг/выполнено/на портале с) | Видит, не редактирует (агрегаты чтения) | Видит |
| Кнопки Заказать/Написать/Подписаться | **Не видит** (не показываем действия над собой) | Видит все три, см. §5 |
| Парк оборудования — список | Видит + «Добавить»/тап-редактирование/корзина | Видит список, без действий |
| Парк оборудования — пустое состояние | CTA «Добавить первый принтер» | Нейтральный текст, без CTA |
| Модели/проекты, идеи, печати (существующие секции ниже) | Без изменений — уже разделены `own` сегодня | Без изменений |

Аноним (не залогинен) технически не может открыть `/u/:username` вообще — экран целиком требует сессии
(`readSession`/`AuthGate`, см. `profile.ts:60-61` и обёртку `app.tsx`), это уже существующее поведение всего
сайта, не специфика этой карточки: гость в терминах этого документа = «залогиненный пользователь, не
владелец страницы», а не «неаутентифицированный визитор».

## 10. Готово когда (проверяемо, Front)

- [ ] `/u/:username` при `profile.is_master === true` показывает город/слоган в шапке; при `false` —
      страница визуально идентична сегодняшней (регресс не внесён).
- [ ] Владелец правит город/слоган через `AccountEditor` (те же `Input`, тот же `PATCH /me`, тот же
      тихий-успех/toast-ошибка паттерн, что уже верен для bio/website/контактов).
- [ ] Соц-хедер — три `StatTile`: рейтинг (честное «Отзывов пока нет» без данных), выполнено (реальный
      счётчик/ноль, не выдумка), «на портале с» (`created_at`, показывается уже в Фазе 1 без зависимости от
      будущих фаз).
- [ ] Ряд кнопок гостю: «Заказать» (primary) и «Написать» (secondary) кликают в честный `toast` «Скоро» (тот
      же паттерн, что `personahome.tsx`), не ведут на несуществующий/битый маршрут; «Подписаться» —
      без изменений в логике, встроена в тот же ряд визуально.
- [ ] Владелец не видит ряда кнопок Заказать/Написать/Подписаться на своей же странице.
- [ ] Парк оборудования виден гостю (сегодня скрыт полностью) — та же строка `printerLabel`/`materialLabel`,
      что уже рисует `MyCatalogsSection`, без live-статуса, без бейджей `support_level`/`FlagshipBadge`, без
      тапа для гостя.
- [ ] Владелец добавляет технику/материал прямо со страницы витрины через существующие `PrinterPicker`/
      `MaterialPicker` (выбор из справочника, свободный текст недоступен — уже гарантировано этими
      компонентами) и правит/удаляет строки тем же существующим флоу, что `profile.catalogs.md`.
- [ ] Пустой парк — `EmptyState` с разным текстом/action для владельца и гостя (§6.4), не общая заглушка.
- [ ] Никаких новых элементов, раскрывающих число мастеров на портале (без нумерации, без счётчика «N из
      M», без нового публичного листинга) — URL и структура страницы не отличаются от обычного профиля
      автора кроме контента.
