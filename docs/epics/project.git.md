## 1. Проблема / запрос

До сих пор «проект как git» был **метафорой**: файлы в S3/MinIO, описание в БД, git-анатомия — только в UI (projects.page.md Р4). Валерий пересмотрел: git — не метафора, а **субстрат**. Каждый проект — настоящий git-репозиторий: и для юзера (README, структура папок, форки), и для нас в хранении. Поверх git мы строим визуализаторы и свою логику работы. Это новый факт от владельца продукта — пере-решение Р4 легитимно.

Что это даёт стратегически: дублирование на GitVerse становится тривиальным (`git push mirror`, когда договорённость закрыта); версионирование и форки достаются от git бесплатно; «проект-самоделка» (3mf + плата + код + инструкция) естественно живёт файлами одного репозитория.

## 2. Ресёрч (что есть и что затрагивается)

1. **Сегодняшнее хранение:** файлы моделей — MinIO/S3 на VDS (loopback), выдача через API-прокси (marketplace.md §1.13); канонический формат — 3MF ([3mf.storage.md](3mf.storage.md)); derived-артефакты (GLB-превью, webp) генерит mesh-воркер.
2. **БД:** `models` + `model_files` (+ `model_meshes`) — вердикт MF-9 (вариант B), никаких `project_*`-таблиц. Каталог, поиск, счётчики, статусы конвейера — всё в Postgres.
3. **Markdown-описание = README-аналог** уже принято (MF-497 Р3); `repo_url` — задел внешней ссылки (MF-497 Р4).
4. **GitVerse:** публичный API узкий (21 эндпоинт Repositories, нет branch protection, нет issues — CONTRIBUTING.md, docs/infra); договорённости о хранении пользовательских файлов нет. Хранить у них сейчас — нельзя.
5. **Роадмап:** ремиксы/форки стояли в v2 (MF-19); решение владельца «полностью гит-логика сейчас» подтягивает базовый форк в v1 (границы версий пересматривает CTO при новых фактах — roadmap §Принцип; факт есть).
6. **Инфра:** VDS с диском под MinIO уже есть; git как CLI на сервере — нулевая новая зависимость.

## 3. Решение: bare-репозитории за API (вариант А)

**Каждый проект = bare git-репозиторий на нашей инфраструктуре. Единственный писатель в v1 — apps/api.** Юзер работает через портал (загрузка файла → API делает commit; редактирование описания → commit README.md). Прямого git-протокола (clone/push юзером) в v1 нет — «для юзера это git-проект» проявляется анатомией (README, дерево файлов, история, форк), не протоколом.

Рассмотренные варианты:

| Вариант | Суть | Почему нет/да |
|---|---|---|
| **А. Bare-репозитории + git-модуль в apps/api** ✅ | `git init --bare` на диске VDS; commit/read/fork через git CLI из API | Нулевые новые сервисы (принцип minimal dependencies); объём v1-операций мал (init, commit, read-tree, server-side clone для форка); полная совместимость с будущим mirror на GitVerse |
| Б. Self-hosted форж (Gitea/Forgejo) как git-бэкенд | Готовые repos/forks/LFS/API/webhooks | Целый сервис ради бэкенда без его UI: вторая система аккаунтов, ops-нагрузка, интеграционный слой всё равно писать; пересмотр-триггер — если понадобится git-протокол наружу и мультиюзерный push |
| В. Хранить сразу на GitVerse | «Как сказано, там же хранить» | Договорённости нет, API узкий, SLA чужой; сам Валерий: «пока тестово у нас». GitVerse = будущее зеркало, не хранилище v1 |

Архитектурные положения (фазы на них стоят):

1. **Разделение труда git ↔ Postgres.** Git-репозиторий — источник истины по **файлам и описанию** проекта (README.md = описание; markdown-сырец больше не «в БД», БД хранит копию-кэш для поиска/каталога). Postgres остаётся источником истины по **каталогу и операционке**: индекс проектов, поиск, счётчики, голоса, комментарии, статусы конвейера, featured. Вердикт MF-9 не отменяется: `project_*`-таблиц по-прежнему нет, `models` эволюционирует в индекс-карточку поверх репо (`models.repo_path`).
2. **Derived-артефакты НЕ в git.** GLB-превью, webp-миниатюры — перегенерируемые производные; остаются в S3/MinIO по текущей схеме. В git — только исходники юзера. (Иначе каждый прогон конвейера раздувает историю репо.)
3. **Структура репозитория проекта** — конвенция, а не схема БД: `README.md` (описание), папки по ремёслам/ролям (например `print/`, `pcb/`, `code/`, `docs/` — финальную конвенцию даёт Design+Data в фазе 1, согласованно с реестром ролей MF-482). `model_files.role` мапится на путь в репо; маппинг фиксирует Data.
4. **Форк (v1, базовый):** server-side `git clone` в репо нового владельца + строка-карточка в `models` с `forked_from`. Атрибуция-цепочки, ремикс-лента, диффы — остаётся в MF-19 (v2).
5. **Версии/история:** git даёт историю бесплатно; в UI v1 — максимум простой список коммитов проекта (решает Design в фазе 1 page-эпика; не критерий приёмки). Ветки юзеру не показываем.
6. **Лимиты:** размер файла и репо ограничиваем на API (дефолт: файл ≤100 МБ как сейчас, репо ≤1 ГБ — правим по факту). Git LFS в v1 не вводим — бинарники лежат в git как есть, объёмы v1 это позволяют; LFS — пересмотр-триггер при росте.
7. **Миграция существующих публикаций:** backfill-джоба — для каждой строки `models` создать репо, положить README.md (из description) и файлы-исходники из S3, проставить `repo_path`. Прод не останавливаем: до конца миграции API читает по флагу «репо есть/нет» (fallback на S3-пути). S3-исходники после верификации бэкфилла не удаляем до отдельного решения CTO (деструктив).
8. **Бэкап и диск** — зона Ops: каталог репозиториев на VDS входит в бэкап-контур, мониторинг места; квоты из п.6.
9. **GitVerse-зеркало** — НЕ здесь: отдельный эпик после договорённости (`git push --mirror` встанет поверх без переделки — это и есть «либо то, что храним у себя, будет дублироваться»).

## 7. Критерии приёмки (приёмка эпика — CTO)

1. Новый проект при создании получает bare-репо; загрузка файла и правка описания видны как коммиты (история непустая, README.md соответствует описанию).
2. Страница проекта показывает дерево файлов из репо и README; derived-превью работают как раньше.
3. Форк создаёт юзеру копию-репо и карточку с `forked_from`; исходный проект не затронут.
4. Все существующие публикации мигрированы (у каждой карточки `repo_path`, файлы совпадают по хэшам), S3-исходники не удалены.
5. Каталог/поиск/конвейер не деградировали (smoke: загрузка → конвертация → превью → каталог → страница).
6. Репозитории в бэкап-контуре; лимиты размера действуют; `project_*`-таблиц нет.

## 10. Data — стадия 1 (MF-516): маппинг схемы

Решения ниже — только зона Data (маппинг `models`/`model_files`, что кэш, что нет). DDL —
`apps/api/src/db/schema.ts`, проверено идемпотентно (двойной прогон, docker/локальный Postgres 16)
и на данных (fork-insert, unique-конфликт, `on delete set null`, планы `EXPLAIN` под оба partial-индекса).

### 10.1 `models.repo_path` / `models.forked_from`

- **`repo_path text unique`, nullable.** Путь к bare-репо проекта на VDS; конкретный base dir —
  зона Ops (MF-518). Значение одновременно и есть **флаг «репо есть/нет»** из §3.7/§7.1: `null` →
  API отдаёт со старых S3-путей (fallback, до бэкафилла или для новых строк, ещё не получивших
  репо), задан → из репо. Отдельную boolean-колонку не заводим — второе поле дублировало бы то же
  состояние и могло разойтись с `repo_path`. `unique` — bug-guard на уровне БД (на диске не может
  быть двух проектов с одним путём), не бизнес-правило; `null` допускается многократно.
  Партиальный индекс `models_repo_path_pending_idx (created_at) where repo_path is null` — под
  backfill-джобу стейджа 3 (MF-521): находит немигрированные строки без full scan (план подтверждён
  `EXPLAIN`, см. коммит).
- **`forked_from uuid references models(id) on delete set null`, nullable.** Self-FK на исходный
  проект базового форка (§3.4, server-side clone). Имя поля — git-терминология эпика; более раннее
  рабочее имя `parent_model_id` из `domain.model.md` § «Контент» (набросок до этого эпика) этим
  полем закрывается, отдельной колонки под старое имя не остаётся. `on delete set null` (не
  `cascade`, паттерн как у `models.recommended_material_id`): форк — независимая копия-репо после
  clone, удаление исходного проекта не должно ронять форк, только обнулять атрибуцию — проверено
  вставкой/удалением на локальной БД. Партиальный индекс `models_forked_from_idx (forked_from) where
  forked_from is not null` — под обратную выборку «все форки проекта X» (будущая лента форков).
- **Не FK `not valid`, как у `user_printers.printer_id`/MF-32** — там понадобился `not valid`,
  потому что колонка добавлялась поверх уже существующих «осиротевших» значений. Здесь обе колонки
  новые и по умолчанию `null` у всех существующих строк — нарушить FK/unique в момент добавления
  колонки нечем, обычный `alter table add column ... references ...` безопасен сразу.

### 10.2 `model_files.role` ↔ путь в репо (финал Data, MF-339-тред 2026-07-10)

Git — источник истины по **файлам** проекта (§3.1); путь в дереве репо вычисляется по конвенции
`{craft-папка}/{оригинальное_имя_файла}`, не хранится отдельной колонкой — `model_files.role`
(что это за файл) уже есть, `models.craft` (чей это репо) уже есть, третьего источника истины не
заводим. Исходное имя файла сохраняется как есть (не переименовываем в `role.ext`) — в отличие от
сегодняшнего S3-ключа `models/{model_id}/{role}.{ext}`, репо может держать несколько файлов одной
роли (мульти-меш `model_meshes`, несколько чертежей/G-code одного проекта, см. `projects.foundation.md`
§2.7) — уникальность внутри роли даёт не фиксированное имя, а факт, что это разные файлы дерева;
коллизии одинаковых имён при аплоаде — зона Back (дедуп/суффикс на уровне API, не DB).

Дефолт эпика (§3.3) — 4 верхнеуровневых папки `print/ pcb/ code/ docs/`. Данных ролей в реестре
(MF-482/MF-497) больше, чем печатных, — **craft-based** маппинг (папка = ремесло, не роль впрямую),
плюс одну папку сверх дефолта эпика для ЧПУ/лазера (роли `cnc_program`/`drawing` уже в реестре под
будущие ремёсла `cnc`/`laser`, но ни один из 4 дефолтных топ-уровней их не покрывает буквально —
`print/` про 3D-печать, не про фрезеровку/раскрой). Имя 5-й папки — **`cad/`** (финализировано
Data+Design, см. §10.2.1 ниже; Design предложил, Data подтвердил):

| `model_files.role` | Ремесло (`models.craft`) | Папка репо | Git или S3 |
|---|---|---|---|
| `source` | `3d_printing` (печатный исходник, вход конвейера mesh) | `print/` | **git** (источник истины) |
| `cnc_program` | `cnc` (будущее) | `cad/` | **git** |
| `drawing` | `cnc` / `laser` (будущее) | `cad/` | **git** |
| `gerber` | `electronics` (будущее) | `pcb/` | **git** |
| `code_archive` | `software` (будущее) | `code/` | **git** |
| `aux` | любое (generic-бакет «доп-файл как есть», сегодня — STEP, `model.card.editor.md`) | папка ремесла проекта (`models.craft` → таблица выше; для живого MVP всегда `print/`) | **git** |
| `description_image` | любое (картинки markdown-описания) | — не в репо | **S3** (исключение из git-контракта, обоснование — §10.2.2) |
| `canonical_3mf` | `3d_printing` (derived, выход mesh-конвейера) | — не в репо | **S3** (как сейчас) |

| `project_doc` | любое (крафт-нейтральный бакет — мета-документы проекта, не привязаны к ремеслу) | `docs/` | **git** (финал MF-826, §10.2.3) |

Пояснение по derived-строкам: §3.2 эпика называет примерами «GLB/webp», не называя `canonical_3mf`
буквально — но `canonical_3mf` тем же способом произведён mesh-конвейером из `source`, не загружен
юзером напрямую, значит подчиняется тому же принципу («иначе каждый прогон конвейера раздувает
историю репо») и остаётся в S3 по текущей схеме ключей `models/{model_id}/{role}.{ext}` без изменений.

`README.md` — не строка `model_files`, а прямое зеркало `models.description`, лежит в корне репо
(git-конвенция), не под `docs/`; `docs/` папка репо держит `project_doc` (§10.2.3) — `description_image`
её не заняла (§10.2.2 держит картинки в S3), так что `docs/` свободна и не смешивает мета-документы
с производными ассетами.

#### 10.2.1 Имя 5-й папки — `cad/` (финализировано Data+Design)

Развилка `cad/` (Design, MF-517 §9) vs `cnc/`+`laser/` (рабочее предложение Data) — **закрыта в
пользу одной папки `cad/`**. Финал за Data (владелец маппинга role↔путь), решение согласовано с
Design (он же предложил `cad/`):

- **Роль `drawing` спанит два ремесла сразу** (`cnc` И `laser` — DXF/SVG идёт и на фрезу, и на
  раскрой). `model_files.role='drawing'` сам по себе не различает cnc от laser, а `models.craft` —
  primary craft проекта, не per-file. Значит `cnc/`+`laser/` дали бы **неразрешимый** маппинг: у
  файла роли `drawing` нет однозначного признака, в какую из двух папок он ложится. Одна папка
  `cad/` эту неоднозначность снимает — все не-печатные фаб-артефакты (ЧПУ-программы + чертежи/
  раскрой) в один бакет.
- **Принцип domain.model.md «не дробить впрок»** — до второго живого ремесла с реальными данными
  на проде только `3d_printing`; заводить две пустые папки под теоретическую развилку cnc/laser
  преждевременно. Разъедутся при реальном спросе — одной правкой этого маппинга (`cad/` → `cnc/`+
  `laser/` или подпапки), UI-проекция «папка ≈ craft-группа» (Design §9) переживёт без перевёрстки.
- **Консистентность с уже принятой дизайн-дельтой** — Design смержил `cad/` в main (`projects.page.md`
  §9, коммит `eae7a5c`); держать в маппинге Data другое имя = ровно тот рассинхрон, от которого
  предостерегал Lead. `cad/` — единое имя в обоих доках.

Отклонено (`cnc/`+`laser/`): точнее семантически, но ценой неразрешимого маппинга роли `drawing`
и преждевременного дробления — обе причины перевешивают точность имени при нуле не-печатных данных.

#### 10.2.2 `description_image` остаётся в S3 (вердикт Data, MF-339-тред 2026-07-10)

Развилка (Fullstack, MF-339 коммент 10:24): §10.2 требовал git (`docs/images/`), но `descriptionimage.ts`
(MF-656, живёт на проде с MF-709) уже пишет и отдаёт картинки описания через S3. Вариант (а) — оставить
S3, поправить §10.2 задним числом; вариант (б) — мигрировать на git, backfill. **Решение — (а), закрыто
навсегда, не «временно до backfill»:**

- **Множественность файлов одной роли уже решена ключом, не именем.** `description_image` — единственная
  роль с N файлов на модель (до `MAX_DESCRIPTION_IMAGES=20`, `description.ts:6`) сегодня; S3-ключ
  адресует файл по `fileId` (`descriptionimageKey`), коллизий нет. Git-конвенция §10.2 «путь = папка
  ремесла + оригинальное имя файла» коллизирует ровно на этой роли — юзеры массово называют картинки
  `screenshot.png`/`photo.jpg`; перенос в git означал бы городить дедуп/суффикс на Back только ради этой
  одной роли, без продуктовой ценности (см. §10.2 «коллизии одинаковых имён — зона Back», сегодня не
  нужна нигде, кроме этой роли).
- **CDN-offload — живая продуктовая фича, не переносится бесплатно.** `GET .../description-images/:fileId`
  делает 302 на публичный URL cloud.ru (MF-709) — картинки описания рендерятся на каждой странице
  проекта, редирект снимает нагрузку с API и даёт CDN-кэш. Git-backed чтение (`git/repo.ts::readFileContent`
  существует, но это `git cat-file` через API-процесс на каждый запрос) — регресс латency/нагрузки без
  компенсирующей выгоды; строить offload-прокси поверх git ради паритета с уже работающим S3-редиректом —
  чистые затраты.
- **README.md не выигрывает от git-адресации картинок.** Markdown описания уже ссылается на картинки по
  API-URL (`descriptionImageUrl`, `/models/:id/description-images/:fileId`), не по относительному пути в
  дереве репо — источник истины README (§10.3) не меняется независимо от бэкенда хранения самих байтов
  картинки. Git-контракт §3.1 существует ради «репо = переносимая суть проекта» (форк, будущий mirror на
  GitVerse); для описания это уже даёт текст README, для картинок — нет добавленной переносимости,
  которая оправдала бы миграцию живых данных.
- **Backfill живых данных — риск без стратегической выгоды.** Раздел про derived-роли (canonical_3mf/
  preview/thumbnail) уже фиксирует принцип «не раздувать историю репо машинными байтами»; повторные
  правки описания в UI пере-заливают картинки похожим паттерном (юзер правит текст, перезаливает
  скриншот) — тот же профиль роста истории репозитория, что и у derived, просто по другой причине.
  Мигрировать протестированный, живущий на проде поток (MF-656/709) только ради формальной чистоты §10.2
  — именно «throwaway работа, которую придётся переделывать», от которой предостерегает описание MF-339
  для этого шага.

`model_files.s3_key` для `description_image` остаётся источником истины (как для derived-ролей §10.3),
не легаси-указателем. Схема `model_files` не меняется этим решением — `role` уже принимает
`description_image` (действующий constraint), новых колонок/миграций не требуется.

#### 10.2.3 Мета-файлы проекта (`LICENSE.md` и т.п.) — новая роль `project_doc` в `docs/` (финал Data, MF-826)

Запрос оператора: «возможность положить и другие .md файлы, как на гите, условно описывая лицензию».
Развилка карточки MF-826 — отдельная роль `model_files.role` с путём в корне репо, или существующая
`docs/`-папка. **Решение — новая роль `project_doc`, путь `docs/{оригинальное_имя_файла}`** (не корень
репо), git-backed, как прочие исходники (`model_files_role_check` расширен, миграция
`20260710390000_model_files_project_doc_role.sql`):

- **Путь внутри `docs/`, не в корне — рекомендация Design** (`model.card.visual.md` §5.1,
  координация этой же карточки): `buildRepoTree` (`apps/web/src/market/projectfiles.tsx:205-232`)
  сегодня собирает только `root.folders` — файлы прямо в корне репо молча теряются (кроме `README.md`,
  у которого отдельный спец-кейс). Заводить роль с путём в корне означало бы либо чинить `buildRepoTree`
  под новый тип узла (файл-в-корне), либо получить фичу, которая нигде не отображается. `docs/` уже
  существует как папка репо (§10.2) и уже умеет рендерить произвольные файлы (глиф+имя+размер) — ноль
  новой вёрстки.
- **`docs/` свободна.** §10.2.2 закрыла `description_image` в S3 (не в git) — единственный кандидат,
  который мог бы занять `docs/` до этого решения, туда не переехал. Коллизий с существующим содержимым
  нет.
- **Не отдельная сущность, не новая таблица.** Тот же вердикт MF-9 (`models`/`model_files` эволюционируют
  на месте) — `project_doc` это ещё одно значение `role`, не `project_*`-таблица.
- **Крафт-нейтральна.** В отличие от строки §10.2 «роль → craft-папка» (`source`→`print/` и т.д.),
  `project_doc` не ветвится по `models.craft` — лицензия/контрибьютинг-гайд не зависят от ремесла
  проекта, путь фиксированный `docs/` для любого craft.
- **Множественность — тот же паттерн, что у прочих git-backed ролей** (§10.2: путь = папка + оригинальное
  имя файла, не колонка). Несколько мета-файлов на проект (`LICENSE.md` + `CONTRIBUTING.md` + произвольный
  доп-док) укладываются без изменений схемы; коллизии одинаковых имён — дедуп/суффикс на Back, как и для
  прочих ролей.
- **GAP для Front (не в зоне Data, флагирую как есть в model.card.visual.md §6 GAP-DATA п.5):**
  `shouldShowProjectFiles`/эквивалент (`projectfiles.tsx:60-62`) сегодня «просыпает» блок «Файлы проекта»
  только при роли вне печатной базы (`source`/`canonical_3mf`) — чисто печатный проект (STL+3MF) с одним
  `LICENSE.md` в `docs/` сегодня спрячет весь блок, и файл нигде не будет виден. Front обязан учитывать
  файлы `project_doc`/`docs/` в этом инварианте при реализации — правка на стороне Front, не DB.

### 10.3 Колонки-кэши git-истины (что дублирует git, зачем — для Back стадии 2)

| Колонка | Кэш чего | Зачем кэш (а не читать git на каждый запрос) |
|---|---|---|
| `models.description` | Содержимое `README.md` репо — **источник истины теперь git**, не эта колонка (§3.1, разворот от `projects.multiformat.md` Р3, где `models.description` был sourse of truth) | Каталог/поиск/будущий нейропоиск (pgvector, `neural.search.md`) читают текст без обращения к git на каждый листинг; Back стадии 2 обязан переписывать эту колонку **при каждом commit README.md**, иначе кэш расходится с репо |
| `model_files.checksum` (`bytea`, sha256), `model_files.size_bytes` | Метаданные git-blob'а файла (для git-backed ролей из §10.2 — сегодня это метаданные S3-объекта, после миграции роли — метаданные того же файла в дереве репо) | Отдаём в API размер/для сверки хэшей backfill (MF-521 п.2) без `git cat-file`/обхода дерева на каждый запрос; Back стадии 2 пишет их при каждом commit файла |
| `model_files.s3_key` | Для git-backed ролей (§10.2) — **устаревает**: становится легаси-указателем на домиграционный S3-объект (не трогаем, не удаляем — S3-исходники не чистим, §3.7/§8.4), не источник истины после того, как у карточки появился `repo_path`. Для derived-ролей (`canonical_3mf`/`preview`/`thumbnail`) и для `description_image` (S3-исключение §10.2.2) — **не кэш, остаётся источником истины** (файл реально живёт только в S3, git его не видит) | Разграничение — Back стадии 2 при записи после commit: git-backed роли новых/смигрированных строк можно оставлять `s3_key` как есть (историческое значение) или не создавать новую S3-запись вовсе — точная реализация вне зоны Data, здесь фиксируется только различие «кэш vs источник» |

Не кэш (несмотря на прилагательное «git» в контексте эпика) — не трогать логику этих колонок:
`models.status`/`source_format`/`bbox` — состояние конвейера конвертации и детектируемые
геометрические/форматные атрибуты, вычисляются на этапе обработки, а не хранятся байтами в
дереве репо; `models.repo_url` (MF-497 Р4) — **другая сущность**, nullable-ссылка на ВНЕШНИЙ
git-хостинг (GitVerse и т.п.), которую юзер сам вписывает в редакторе, не путать с `repo_path`
(путь к НАШЕМУ внутреннему bare-репо); обе колонки сосуществуют независимо.

### 10.4 Соответствие MF-9

Подтверждено: `project_*`-таблиц не заводится — `models`/`model_files` эволюционируют на месте
(новые колонки/индексы, ни одной новой сущности верхнего уровня). Мульти-модель по-прежнему на
уровне `model_files`/будущей `model_meshes` (`model.card.editor.md`, вариант B) — маппинг роль↔путь
в §10.2 явно рассчитан на N файлов одной роли в одном репо, не переоткрывает вариант A (контейнер).

Миграции идемпотентны — тот же паттерн `alter table ... add column if not exists`/drop+add
constraint, что и во всех предыдущих ревизиях `schema.ts` (MF-453/462/482/32/31); повторный прогон
безопасен, что нужно и backfill-джобе стейджа 3 (MF-521).
