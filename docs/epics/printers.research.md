# Эпик: БД принтеров + команда Ресёрчеры

**Директива оператора (2026-07-10).** Флагман данных v1 (см. MF-32, [roadmap.md](../product/roadmap.md) §v1).
БД всех существующих принтеров — наш data-moat: чем полнее и структурнее, тем сильнее каталог, поиск,
совместимость и рекомендации. Заполняют **Ресёрчеры** (агенты + люди) через гибкий веб-интерфейс.

## Вердикт CTO (MF-839, 2026-07-10): один канон, не два

MF-32 (флагман-эпик «База принтеров + вендоры», фаза MF-405 «Фундамент данных: схема,
bootstrap-импорт, резолвер») уже проектирует каноническую запись принтера **в Postgres**, с
`canonical_id uuid` (наружу — та же UUID-конвенция всего портала, см. `ids.policy.md`:
`id uuid default gen_random_uuid()`, никаких serial/слагов в PK), провенансом на поле
(`{value, source, ts, confidence}`) и пайплайном дедупа/ревью (MF-406). Первая версия
`printers.research.md` (эта карточка/MF-839) описывала **отдельный бакет `printers-research` с
`card.json`/`index.json` как источником истины** — это де-факто вторая, параллельная база
принтеров, которая разойдётся с MF-405/406 (два канона, два ID, ручной и авто-пайплайны никогда
не встретятся). Решение: **MF-839 — это ПЕРВАЯ КОНКРЕТНАЯ РЕАЛИЗАЦИЯ схемы MF-405**, канал
ручного/агентского (Ресёрчеры) наполнения той же таблицы, что будут писать и автономные парсеры
MF-406, — не отдельная БД. Ниже — исправленная архитектура; MF-405/406 (Data/Fullstack) обязаны
свести колонки с полями [printer.schema.json](../research/printer.schema.json) при реализации.

## 1. Хранилище — Postgres канон + бакет только под медиа

- **Источник истины — та же Postgres-БД портала**, таблица `printers` (+ провенанс-таблица per-field),
  которую поднимает MF-405 (Data). Поля таблицы = набор [printer.schema.json](../research/printer.schema.json)
  (build_volume/hotend/bed/speed/multimaterial/toolhead_extras/connectivity/materials/price/media/
  unique_features) — это готовый, продуманный под фасетную фильтрацию набор колонок, Data берёт его
  как основу для миграции MF-405, а не изобретает заново.
- **`id` в `printer.schema.json` переименовывается по смыслу в `slug`** (человекочитаемый рабочий
  ключ ресёрчера и SEO-путь `/printers/<slug>` — карточки принтеров публичны и малочисленны
  (десятки тысяч максимум), скрывать их количество не требуется, см. MF-32 §6 «для каталога
  принтеров это менее критично»). Каноническая PK-идентичность — `id uuid default gen_random_uuid()`
  (портальная конвенция, `docs/epics/ids.policy.md`), `slug` — обычная уникальная колонка рядом.
- **Бакет cloud.ru S3 `printers-research`** — ТОЛЬКО медиа (фото), не карточки данных:
  `printers/<id>/media/hero.webp`, `printers/<id>/media/<n>.webp` (webp, оптимизированные).
  Отдельный от `3mf`/`auth`; провижн — Cloud.ru-агент, доступ на запись команде Ресёрчеры + сервис-ключ
  веб-интерфейса.
- **`index.json` не нужен** — каталог `/printers` читает БД напрямую через резолвер MF-405
  (`GET /printers` с фасетами), не плоский файл в бакете.
- **Провенанс обязателен**: каждое поле подтверждается `source` (URL) + `filled_by` + `confidence` —
  тот же shape, что MF-405/406 уже проектируют для автономных парсеров, чтобы ручные (Ресёрчеры) и
  авто-записи мержились в ОДНОЙ таблице по единому пайплайну дедупа MF-406, а не жили в двух базах.
  Неизвестное = `null` + запись в `_meta.gaps` (НЕ выдумывать характеристику).

## 2. Схема — сортируемая по всему

[printer.schema.json](../research/printer.schema.json) спроектирована под фасетную фильтрацию каталога:
стол (`build_volume`, `bed.max_temp_c`), хотэнд (`hotend.max_temp_c/max_flow`), скорость, **AMS**
(`multimaterial`), **уникальная голова** (`toolhead_extras` — лазер/ЧПУ/каттер), кинематика,
коннективность (важно для наших 3 типов коннектора), материалы, габариты, **цена оригинал + РУ-рынок**,
свободный `unique_features`. Каждая карточка — `_meta` с confidence/gaps/filled_by.

## 3. Команда Ресёрчеры (Multica)

Отдельный сквад **«Ресёрчеры»** — заполняют БД, НЕ трогают продуктовый код.
- **Старт: 1 агент `researcher-creality`** (claude-haiku — дёшево, объём монотонный) на мониторинг
  Creality. Инструкция: следить за анонсами бренда, заводить/актуализировать карточки принтеров по
  схеме, класть фото в бакет, честно помечать gaps.
- Масштаб: по агенту на бренд (Bambu, Prusa, Anycubic, Elegoo, Flashforge…) — все на haiku, тот же паттерн.
- **Аккаунт агента на сайте**: у каждого ресёрчера — сервис-юзер в portal_dev (роль `researcher`),
  которым он пишет через веб-интерфейс/API (не напрямую в бакет — через гейт валидации схемы).
  Для машинного пути используется тот же `POST /research/printers`, но Bearer-ключ из
  `user_api_keys` со строго одним scope `research` и правом `write`; plaintext ключа в БД нет.
- **Мониторинг анонсов**: таймер дёргает агента на проверку RSS/новостей бренда → новинка → карточка +
  запись в календарь новинок (MF-32).

## 4. Веб-интерфейс ресёрчера (гибкий, заполнять карточки)

- Роут `/research` (за гейтом роли `researcher`): список принтеров, форма по схеме (валидирует поля,
  подсказывает gaps), загрузка фото (в бакет медиа), кнопка «сохранить» → API → валидация → upsert в
  `printers` (Postgres) + провенанс-запись.
- API `POST /research/printers` (роль `researcher`): принимает JSON по [printer.schema.json](../research/printer.schema.json),
  валидирует, **upsert в каноническую таблицу MF-405** с провенансом на поле (переиспользует
  merge-без-молчаливого-overwrite из MF-406, а не пишет мимо него).

### Машинная авторизация `researcher-creality` (MF-1574)

`POST /research/printers` принимает один из двух вариантов авторизации:

- человек: `portal_session` и `users.role = 'researcher'`;
- агент: `Authorization: Bearer mf_research_…`, строка в `user_api_keys` с
  `scope = 'research'`, `scopes = ['write']`, активным статусом и владельцем с ролью
  `researcher`.

Сервисная учётная запись — `researcher-creality`; quota контура — одна такая учётная запись
и один research-ключ. В БД сохраняется versioned binary scrypt hash со случайной
16-byte солью (N=32768, r=8, p=3, digest=32 bytes); plaintext не сохраняется.
Формат: `mf_research_<public-id>.<secret>`, canonical base64url без padding:
public-id — 16 случайных байт, secret — 32 случайных байта из CSPRNG.
API ищет запись по публичному `research_<public-id>` и сравнивает scrypt digest
через timingSafeEqual. Параметры задаёт код, а не содержимое БД.
Проверки ограничены двумя параллельными запросами на процесс без очереди;
при перегрузке запрос отвергается. Это ограничение ресурсов, не замена внешнего rate limiting.
Оператор задаёт ключ только через окружение. Пример генерации в новый временный
каталог (секрет не печатается; целевой файл ещё не существует):

```bash
umask 077
research_key_dir=$(mktemp -d)
node --input-type=module -e 'import { randomBytes } from "node:crypto"; process.stdout.write(`RESEARCHER_API_KEY=mf_research_${randomBytes(16).toString("base64url")}.${randomBytes(32).toString("base64url")}\n`)' > "$research_key_dir/researcher-key.env"
```

Файл безопасно доставляется worker-consumer и используется как временный env
для запуска `pnpm run provision:researcher` на целевой БД. Команда выводит лишь
имя учётной записи, роль, право и публичный `key_prefix`; сам ключ повторно не
печатает. Старые ключи и SHA-256 hashes новый verifier не принимает.
Переход требует согласованного окна: остановить worker, развернуть новый API,
запустить обновлённый provisioning с новым ключом на явно согласованной БД,
установить тот же ключ worker и запустить его. Проверить успешную работу нового
ключа и отказ старому. До завершения возможен перерыв машинного доступа.
Откат API требует восстановления старого hash через соответствующий старый
provisioning; простого отката приложения недостаточно. Старый secret и временный
файл удалить после проверки и завершения согласованного окна отката.
Локальные тесты не подтверждают deployment или закрытие CodeQL findings:
для этого требуется повторный SAST scan и проверка DefectDojo.

- `GET /printers` (публичный read-API, тот же резолвер MF-405) — фасетные фильтры по столу/хотэнду/
  AMS/лазеру/цене поверх Postgres; каталог `/printers` на фронте читает этот API, не бакет.
- Заметный UI/сценарий (форма ресёрчера + публичный каталог с фасетами) — по процессу CTO идёт
  СНАЧАЛА через UX (карточка «UX: сценарий /research + /printers»), потом Design/Front.

## 5. Задачи (workstream'ы — режет и назначает Lead своим людям/директорам)

1. Cloud.ru (Lead): провижн бакета `printers-research` (только медиа) + сервис-ключ + доступ команде.
2. Data (владелец MF-405): свести колонки `printers`/провенанс с полями printer.schema.json,
   добавить недостающие (multimaterial/toolhead_extras/price.ru_rub и т.д.) в миграцию MF-405.
3. Fullstack → Back: API `POST /research/printers` (валидация схемы, upsert в канон, провенанс) +
   роль `researcher` в RBAC + `GET /printers` read-API с фасетами (расширение резолвера MF-405).
   **Событийный контракт — см. §6.1/§6.3** (`printer_card_upserted` из этой ручки; расширение
   `POST /me/printers` под `printer_id`/`link_source` из каталога).
4. UX → Design → Front: сценарий, затем визуал и реализация `/research` (форма) и `/printers`
   (публичный каталог с фасетами) — по цепочке UX→Design→Front, не напрямую Front.
   **Событийный контракт — см. §6.2** (`printer_catalog_view`/`printer_facet_apply`/
   `printer_card_view`/`printer_card_click_through`).
5. Ресёрчеры: агент `researcher-creality` + инструкция + мониторинг-таймер (уже создан, ждёт API/UI).

## 6. Метрика успеха (Growth, MF-853)

Три петли этой инфры — три разных ответа на «работает». Ниже — честная метрика на петлю (не
тщеславная), контракт событий для Back/Front (§5 п.3/4 выше уже на них ссылается) и как гасим
накрутку. Написано **до** реализации (карта заказана на старте эпика, не постфактум) — Back/Front
берут контракт как есть, когда Lead режет им workstream-карточки.

### 6.1 Наполнение (Ресёрчеры)

**Успех = `printers_facet_ready_share`** — доля активных карточек, где заполнены все поля,
нужные фасетному каталогу (`brand`, `model`, `kinematics`, `type`, `build_volume.{x,y,z}`,
`price.msrp_usd` ИЛИ `price.ru_rub`) И `_meta.confidence` ∈ `{high, medium}`. База — 0 (таблицы
ещё нет). Цель — держать ≥80% активных карточек facet-ready к моменту, когда `/printers`
включает фасеты в продакшене; точную цифру объёма (сколько карточек всего) ставит Data/Lead —
я слежу за долей, не за абсолютным числом.

`facet_ready_share = count(printers where <критичные поля not null> and confidence in ('high','medium')) / count(printers)`

Guardrail (доля высокая, но каталог не растёт — тоже «не работает»): `cards_created_per_week`
по агенту/бренду.

Диагностика/воронка (не success сама по себе, а где узко — по агенту/бренду):
`cards_total`, `confidence_high_share` / `confidence_medium_share` / `confidence_low_share`,
`field_provenance_coverage` (доля непустых полей, у которых есть подтверждающий URL в `sources[]`
— карточка без единого источника это красный флаг, не полнота), `median_field_age_days`
(медианный возраст `_meta.updated_at` — кто не актуализирует статус `announced→shipping→eol`).

**События** — эти поля читаем напрямую из `printers`/провенанса (канон Postgres), не из `events`
(тот же принцип, что `marketplace_liquidity_30d` читает `models.downloads_count`, не
`events.model_download`, см. [metrics.marketplace.md §1](../product/metrics.marketplace.md)).
Одно серверное событие нужно только для throughput-таймлайна:

| Событие | `props` | Когда |
|---|---|---|
| `printer_card_upserted` | `{printer_id, slug, brand, model, confidence, gaps_count, sources_count, filled_by, is_new}` | `POST /research/printers`, на каждый успешный upsert |

**Как смотрим:** недельный SQL-срез по `printers` (я), плюс `printer_card_upserted` для
временного ряда throughput. Добавление в таксономию — та же миграция-паттерн, что MF-823
(`analytics.events.md` §«Таксономия»): `alter table events ... check (event_name in (...))`.

**Абьюз:** агент может нафармить `facet_ready_share` пустыми, но формально заполненными
карточками. Гасим тем, что `confidence=high` и непустой `sources[]` — два независимых сигнала,
подделать оба труднее, чем просто нарастить `cards/week`. High-confidence карточка с
`sources=[]` — сигнал вранья, эскалирую Lead/сквад Ресёрчеров, не игнорирую как шум.

### 6.2 Каталог `/printers` (публичная сторона)

**Успех = `printers_facet_engagement_rate`** — доля визитов `/printers`, где юзер применил ≥1
фасетный фильтр (стол/AMS/лазер/цена/…). Просто открыл и ушёл — не использование справочника.

`facet_engagement_rate = sessions_with_facet_apply / sessions_with_catalog_view`

База — 0 (страницы нет). Целевое число ставлю после первого месяца живых данных, не постулирую
заранее (тот же честный подход, что MF-731/732 для молодого портала).

Воронка: `catalog_view` → `facet_apply` (какие фасеты реально кликают — топ-3 показывает, что
ценнее юзерам, дублирование низких — сигнал упростить UI) → `card_view` → `card_click_through`
(из карточки принтера — в проекты/комьюнити или «мои принтеры»).

**События** (клиентские, тонкий транспорт по аналогии с `POST /feed/events`):

| Событие | `props` |
|---|---|
| `printer_catalog_view` | `{facets_active: string[], sort, source: 'direct'\|'search'\|'internal_link'}` |
| `printer_facet_apply` | `{facet: 'build_volume'\|'hotend'\|'bed'\|'multimaterial'\|'toolhead_extras'\|'kinematics'\|'connectivity'\|'materials'\|'price', value}` |
| `printer_card_view` | `{printer_id, slug, source: 'catalog'\|'search'\|'calendar'\|'direct'}` |
| `printer_card_click_through` | `{printer_id, target: 'project'\|'community'\|'my_printers'}` |

`printer_card_view.source='search'` против `'catalog'` — прямой SEO-сигнал захода на
`/printers/<slug>`, минуя каталог (п.3 задачи карты): доля `search` в общих `card_view` =
насколько `/printers/<slug>` работает как самостоятельная SEO-страница, не только придаток
каталога.

**Как смотрим:** `events` для facet/card-специфичных сигналов + Umami (`autofab-analytics`
скилл) для page-level SEO-трафика/источников на `/printers/<slug>` — Umami не видит slug↔printer_id
и фасетный контекст, `events` не даёт referrer/канал бесплатно, нужны оба.

**Абьюз:** `facet_apply` можно накрутить ботом без реального юзера — гасит тот же слой, что
весь `events` (`consent` fail-closed, MF-429: без `granted`-согласия строка не пишется вообще).
Смотрю `facet_engagement_rate` вместе с `card_click_through` — расхождение (фильтры растут,
клики в карточку/переходы нет) само по себе сигнал накрутки или сломанного UI, не жду отдельного
детектора.

### 6.3 Downstream-эффект (MF-32, ЛК «мои принтеры» MF-14/15)

**Успех = `catalog_to_my_printers_rate`** — доля визитов `/printers`/`/printers/<slug>`, которые
в течение 7 дней заканчиваются `printer_linked` (уже существующее событие активации,
`apps/api/src/profile/activation.ts`, таксономия `ACTIVATION_EVENT_NAMES`) с `printer_id`,
заполненным ИЗ каталога (не `manual`). Это прямой ответ на «каталог используется как справочник
при выборе/покупке принтера, не только ресёрчерами» — юзер посмотрел карточку и реально привязал
именно этот принтер в ЛК, не просто листал.

`catalog_to_my_printers_rate = subjects_with_card_view_and_printer_linked_7d / subjects_with_card_view`

**Контракт — расширение существующей ручки, не новое событие:** `user_printers.printer_id uuid`
уже есть в схеме и сейчас всегда пишется `null` (`activation.ts:177`, канона-каталога ещё нет).
`POST /me/printers` должен заполнять `printer_id` = `printers.id`, когда юзер выбирает принтер
из `/printers`/`/printers/<slug>`, и `link_source` — новым/переиспользуемым значением, отличимым
от `'manual'` (сейчас `LINK_SOURCES = ["connector", "popular", "search", "manual"]`,
`activation.ts:13`; точное значение — решение Back при реализации, важно только, что в данных
это отличимо от ручного ввода). `activation.ts:192-195` уже логирует ручной ввод как "demand
signal for MF-32 catalog" — приёмник для этого сигнала наконец появляется вместе с каталогом.

Для нейропоиска/ассистента/совместимости самого MF-32 — метрику не завожу заранее: фичи ещё нет,
формула-заготовка (доля `printer_linked`-юзеров, которые используют будущий compat-API) будет
картой, когда появится ручка (тот же принцип, что `marketplace_gmv_take_rate` не строится до
ручки покупки, см. [metrics.marketplace.md §3](../product/metrics.marketplace.md)).

**Как смотрим:** join `printer_card_view` → `printer_linked` → `user_printers.printer_id is not
null`, тот же activation-cohort SQL-каркас, что
[analytics.events.md §«Метод эмпирической валидации через когорту»](analytics.events.md)
(подстановка `candidate_event`/`window_days`).

**Абьюз:** низкий риск — добавление принтера в свой профиль дороже подделать, чем просмотр
страницы. Единственная неопределённость — атрибуция окна 7 дней (юзер мог добавить принтер
`manual` без связи с просмотром каталога), тот же класс честного допущения, что окно 30 минут у
`marketplace_search_match_rate_30d` (см. [metrics.marketplace.md §2](../product/metrics.marketplace.md)) — не блокер, первое, что стоит проверить, если разрыв на дашборде неустойчив.

## 7. Сквозные решения (действуют на оба экрана)

Три правила, из которых выводится всё остальное. Они же — то, что легко нарушить в реализации.

**7.1 Один объект, один URL, вся жизнь принтера.** «Анонсирован» — не отдельная сущность календаря,
а `status: announced` на той же строке `printers` с почти пустыми полями. Ссылка `/printers/creality-k1c`,
пошаренная в феврале на анонсе, в сентябре открывает ту же карточку, уже со спеками и ценой. Отсюда:
календарь новинок — **представление** над каноном (фильтр `released_at` + `status`), не вторая таблица;
анонсированный принтер никогда не отдаёт 404 и никогда не «переезжает» на новый адрес при выходе.

**7.2 Пустое поле — не ноль, а три разных факта.** Схема даёт ровно три состояния, и пользователь
должен видеть разницу:

| Состояние | В данных | Что видит ресёрчер | Что видит посетитель |
|---|---|---|---|
| **Заполнено** | `value ≠ null` + источник | значение + ссылка на источник | значение, сноска на источник |
| **Искали, нет данных** | `value = null`, поле в `_meta.gaps` | «нет данных» (галка стоит) | «нет данных» в строке пробелов секции |
| **Не трогали** | `value = null`, поля нет в `gaps` | подсвечено как работа | ничего (строки просто нет) |

`_meta.gaps` **не печатается руками** — это галка «не нашёл» рядом с полем. Никогда не рисуем сетку
прочерков «—» × 20 (`nav.sections.md §3.3`): отсутствие строки честнее, чем двадцать «мы не знаем».

**7.3 Неизвестное не молчит.** Фасет применяется **только к известным значениям**. Принтер с
`multimaterial.supported = null` не тихо выпадает из фильтра «есть AMS» — он попадает в строку под
выдачей: «Ещё 14 принтеров, у которых это поле не заполнено — показать». Молчаливое отбрасывание
неизвестного над неполной БД делает каталог одновременно и врущим («вот все с AMS»), и маленьким.
Клик по строке для посетителя — показать их; для роли `researcher` — прямая ссылка на дозаполнение.
Так дыра в данных превращается во вход для вклада, а не в тихую ложь. Принцип переиспользуемый —
вынесен в [product/ux.md §5](../product/ux.md).

## 8. `/research` — рабочее место ресёрчера

Аудитория: агент (`researcher-creality`, программный клиент) и человек (веб-форма). **Один контракт
API на оба пути**: форма — тонкий клиент над `POST /research/printers`. Практическое следствие —
в форме не может быть поля, которого не принимает API, и API не может требовать того, что форма не
собирает. Различает их только `_meta.filled_by`. Агент пишет не глядя в UI — поэтому главная работа
экрана не «ввод», а **обзор того, что уже написали агенты, и починка дыр**.

### 8.1 Точки входа

| Откуда | Кто | Куда попадает |
|---|---|---|
| Прямая ссылка `/research` (в инструкции агента, в закладке человека) | ресёрчер | очередь работ |
| `/printers/<slug>` → тихая строка «Дозаполнить карточку →» (видна **только** роли `researcher`) | ресёрчер | форма этой карточки |
| Строка пробелов в секции спеки на публичной карточке | ресёрчер | форма, скролл к этой секции |
| «Не нашли свой принтер? Добавьте →» (пустая выдача каталога, `nav.sections.md §4`) | посетитель → кандидат в очередь<br>ресёрчер → `/research/new`, предзаполнено тем, что он искал | |
| «Сообщить о неточности» на карточке принтера (петля фидбека, [ux.md §1.1](../product/ux.md)) | посетитель поднимает флаг | флаг в очередь `/research?flag=<id>` |
| Календарь новинок: анонс без спек | ресёрчер | форма (карточка уже существует, §7.1) |
| ЛК: привязанный вручную принтер, которого нет в каталоге | владелец | кандидат в очередь |
| `POST /research/printers` | агент | — (тот же upsert, минуя UI) |

### 8.2 Путь: список → форма

**Экран списка — это очередь работ, а не витрина.** Ресёрчер приходит не «посмотреть каталог», он
приходит закрывать пробелы. Поэтому сортировка по умолчанию — «где больше всего не хватает», а не по
алфавиту. Сегменты (один орган управления, состояние в URL): `Мои · Мой бренд · С пробелами ·
Низкая уверенность · Помечено пользователями · Все`.

Строка списка: бренд · модель · `slug` · чип статуса (`announced`/`shipping`/`eol`) · **полнота**
(N из M ключевых полей) · `confidence` · `filled_by` (с агент-бейджем, если писал агент) · когда
обновлено. Полнота считается **не по всем 60 полям схемы** (100 % недостижимы и демотивируют), а по
короткому набору, который кормит фасеты каталога: `build_volume`, `hotend.max_temp_c`, `bed.max_temp_c`,
`kinematics`, `multimaterial.supported`, `price`, `media.hero`.

**Поиск — он же кнопка «создать».** Голой кнопки «Создать карточку» до поиска нет: это главный
источник дублей. Ресёрчер печатает «K1 Max» → живая выдача по бренду, модели, `aliases` и `slug`;
последней строкой выпадашки — «Создать карточку “Creality K1 Max”». Тот же паттерн мягкого дедупа,
что у идей («проголосовать вместо создания», `ux.md §1.4`): подсказка, не запрет — ревизии (K1 / K1C /
K1 Max) законно похожи, и запрет создания сломал бы работу.

### 8.3 Форма — логика полей

Порядок сверху вниз; секции схемы сворачиваемые, в заголовке каждой — «заполнено 4 из 7».

1. **Идентичность** (обязательное): `brand`, `model` → `slug` генерируется как `creality.k1-max`,
   правится руками, уникальность проверяется живьём. Плюс `aliases`, `status`, `released_at`.
   На blur `brand`+`model` — мягкая проверка дубля: «Похоже на существующую: Creality K1 Max — открыть?».
2. **Фото** — сразу после идентичности, до спек: принтер узнают по картинке, а пустой герой калечит
   плитку каталога. Один поток загрузки (drag-drop / выбор файла), не два: файлы уходят в бакет
   немедленно (presigned URL → ключ), превью — сразу, `hero` = звёздочка на любой из галереи, первая
   загруженная становится `hero` автоматически. Загрузка **до** сохранения — упавший сейв не теряет
   фото. Агент делает то же самое: PUT по presigned URL → передаёт ключи. Лимит галереи — 8; подпись
   в форме про источник фото (`media.official_url`), чужие водяные знаки не тащим.
3. **Спеки** — секции схемы (`build_volume`, `hotend`, `bed`, `speed`, `multimaterial`,
   `toolhead_extras`, `connectivity`, `materials_supported`, `dimensions_mm`, `price`,
   `unique_features`). У каждого поля — галка **«не нашёл»** (§7.2). Обязательных полей ровно четыре
   (`id/slug`, `brand`, `model`, `_meta`) — всё остальное опционально **и сохранение никогда не блокируется
   пробелами**: ресёрчер, нашедший три факта из тридцати, должен уметь их отдать.
4. **Источники** — закреплённая панель сбоку, а не поле в конце. Ресёрчер добавляет 2–5 URL, они
   получают номера `[1] [2] [3]`. У каждого заполненного поля — маленькая сноска-выбор источника.
   **Ключевая эргономика: последний использованный источник цепляется к полю автоматически** — человек,
   читающий одну страницу спек и вбивающий двадцать полей, делает одно действие, а не двадцать.
   Контракт API: `sources[]` (как в схеме) + опциональный `field_sources: {"hotend.max_temp_c": 0}`
   (индекс в `sources[]`). Агент, приславший только `sources[]`, валиден — все заполненные поля
   атрибутируются карточным провенансом. Так «провенанс на поле» (§1) переживает и человека, и агента.
5. **`_meta`**: `confidence` — три радиокнопки с человеческим смыслом («сверил с офсайтом» / «одна
   вторичная статья» / «слухи, ревизия неясна»), `filled_by` подставляется автоматически, `gaps` и
   `updated_at` считает сервер.

### 8.4 Сохранение — что видит ресёрчер

Одна primary-кнопка «Сохранить», липнет к низу формы. Автосейв черновика с момента, когда есть
`brand`+`model` (форма длинная — потерянный ввод убивает волонтёра).

| Исход | Что видит |
|---|---|
| **Успех, карточка публикуется** | «Сохранено · опубликовано» + «Открыть в каталоге →» |
| **Успех, но черновик** (нет ни одного источника) | «Сохранено. Чтобы опубликовать, добавьте хотя бы один источник» + прыжок в панель источников |
| **Ошибка валидации схемы** | ошибки **у полей**, скролл к первой, у кнопки — «3 поля не приняты». Никогда не сырой JSON-дамп |
| **Конфликт правок** | «Пока вы редактировали, `researcher-creality` обновил 2 поля» → по каждому конфликтному «оставить моё / взять их»; непересекающиеся поля мержатся молча |

Конфликт — это не редкий случай, а норма: агент переобходит бренд по таймеру, пока человек правит ту
же карточку. Молчаливый overwrite здесь запрещён тем же требованием, что и в MF-406 (§1).

**Три состояния карточки, ревью не блокирует публикацию:**
`черновик` (нет источника, видна только в `/research`) → `опубликована, verified=false` (бейдж
«уточняется» в каталоге, сортируется ниже) → `verified=true` (человек проставил `_meta.reviewed_by`).
Отдельной очереди ревью на входе нет — иначе агенты упрутся в человека и конвейер встанет; честный
бейдж дешевле модерации.

### 8.5 Состояния экрана

| Состояние | Что видит |
|---|---|
| Гость | промпт входа (переиспользуем логин-флоу) |
| Вошёл, но нет роли `researcher` | не 404 и не «доступ запрещён», а «Это рабочее место команды Ресёрчеров» + «Хочу заполнять каталог →». Гейт, который вербует |
| Первый раз, роль есть | очередь + одна строка «Начните с пробелов вашего бренда» |
| Очередь пуста | «Пробелов по вашему бренду нет» + «Проверить анонсы →» (календарь) |
| Грузится / ошибка сохранения | скелетоны; ошибка сети → «Не сохранилось, черновик цел, повторить» |

## 9. `/printers` — публичный каталог (дельта к `nav.sections.md §3`)

Без гейта. Рамка (`wide`, сайдбар слева / сетка справа, полоса «мой парк», сортировка `verified`
вперёд, `/printers/releases` как вкладка, `/printers/compare` как роут) — из `nav.sections.md §3`,
не переоткрываем. Здесь — **фасеты по богатой схеме, плитка vs страница, сортировки, связи.**

### 9.1 Фасеты — ранжированы по вопросу, который человек задаёт

Двадцать фильтров в столбик — не мощь, а стена. Всегда видны шесть, остальное — под «Ещё фильтры».

| Фасет | Как выглядит логически | Почему так |
|---|---|---|
| Поиск `q` | по бренду, модели, `aliases` | ищут именем, а не фильтром |
| **Бренд** | список с числами | самый частый первый вопрос |
| **Цена** | двойной ползунок + сегмент валюты `₽ РУ / $ MSRP` (один орган, `ux.md §3`), дефолт ₽ | у нас две цены и они несравнимы |
| **«Влезет деталь ___×___×___ мм»** | три поля + пресеты `≥220³`, `≥300³` | человек думает **деталью**, а не столом; это не фильтр по `build_volume`, это ответ на его вопрос |
| **Тип и кинематика** | `fdm / resin` + `corexy / cartesian / delta / idex` | |
| **Возможности** | чипы-тумблеры: `AMS`, `лазер/ЧПУ-голова`, `закрытая камера`, `автокалибровка`, `закалённый хотэнд (абразивы)`, `Moonraker`, `LAN-режим` | булевы вопросы — чипами, не выпадашками |
| *Ещё фильтры* | хотэнд ≥ °C, стол ≥ °C, поток, скорость, сменное сопло, материалы (AND: «умеет и TPU, и PA-CF»), коннективность, `status` | это вопросы второго круга |

- Состояние всех фасетов — **в URL** (`?brand=creality&ams=1&bed_min=100&sort=price_ru`): иначе выдачу
  нельзя ни пошарить, ни вернуть «назад» (`ux.md §2–3`).
- Опции, дающие ноль при текущих фильтрах, **гасятся с нулём, а не исчезают** — панель не должна прыгать.
- Фильтр по цене выкидывает карточки без цены → строка «+7 принтеров без цены — показать» (§7.3).
- Пустая выдача — не тупик: «Снять фильтр “лазер” (вернёт 12)» (предлагаем **самый узкий** из активных)
  + «Не нашли свой? Добавьте →» (→ §8.1).
- Устаревшая РУ-цена (`price.ru_updated_at` старше 90 дней) в фильтре участвует, но на плитке и карточке
  показана с датой: «34 900 ₽ · март 2026». Иначе каталог врёт ценой прошлого года.

### 9.2 Плитка vs страница

**Плитка отвечает на один вопрос — «это он? открывать?»**, а не показывает спеки: фото 16:9 (нет фото —
нейтральная заглушка с бренд-меткой, не битая картинка), бренд · модель, цена ₽ (или «цена уточняется»),
**максимум три чипа, и они контекстные**: если человек фильтрует по AMS — на плитке чип AMS; иначе
дефолт (объём стола, кинематика, лазер/AMS при наличии). Плюс чип статуса (`анонсирован`/`снят с
производства`) и «уточняется» при `verified=false`. Тап → `/printers/<slug>`. Долгий тап / наведение —
«＋ Сравнить» (набор копится в липкой нижней панели, 2–4 шт → «Сравнить (3)» → `/printers/compare?ids=`).

**Страница `/printers/<slug>`** — структура из `nav.sections.md §3.3` (шапка · спеки · провенанс ·
обсуждение из саба · «что на нём печатают»), с дельтой под схему:
- галерея (hero + фото), спеки — секциями схемы, **только заполненные поля**;
- у каждой секции внизу одна честная строка пробелов: «Не заполнено: поток хотэнда, покрытие стола» —
  и для роли `researcher` рядом «Дозаполнить →» (§8.1);
- провенанс: сноска у поля → список «Источники» внизу; агент-бейдж у `filled_by`;
- действия: «Это мой принтер» (тихое, → `user_printers.printer_id`), «Сравнить», «Сообщить о неточности».

**Сортировки** — один контрол справа над сеткой: `Рекомендуемые` (дефолт: `verified` → полнота →
владельцы), `Новые` (`released_at`), `Дешевле` / `Дороже` (по выбранной валюте), `Больше стол`.
При непустом `q` дефолт — релевантность. «Популярность» до появления сигналов — это число владельцев
из `user_printers`, а не выдуманный счётчик.

### 9.3 Связи

- **Каталог ⇄ мои принтеры (MF-14/15):** «Это мой принтер» → `user_printers.printer_id`; полоса «мой парк»
  вверху `/printers`. Обратный ход: принтер, привязанный руками (`link_source='manual'`) и не найденный
  в каноне, → «Вашего принтера ещё нет в каталоге — добавить?» → кандидат в очередь `/research` (§8.1).
- **Каталог ⇄ календарь новинок (MF-32):** одна сущность, `status` + `released_at` (§7.1). Календарь —
  вкладка `Каталог · Новинки`, не второй раздел. Действие на анонсе одно — «Уведомить о выходе».
- **Каталог ⇄ фидбек:** «Сообщить о неточности» → флаг на объекте → очередь ресёрчера → правка →
  автору возвращается уведомление с глубокой ссылкой (`ux.md §1.3`). Петля замыкается, иначе фидбек — кладбище.
- **Каталог ⇄ сообщество:** пара «карточка ↔ саб `kind='machine'`» обязательна в обе стороны (`nav.sections.md §3.2`).
- **Каталог ⇄ витрина моделей:** «что на нём печатают» → `/project?printer=<id>`; бейдж совместимости на карточке модели → `/printers/<slug>`.
- **`/research` ⇄ каталог:** ресёрчер живёт в публичном каталоге и чинит его изнутри — «Дозаполнить»
  видно только ему. Отдельного «админского каталога» нет и не будет.

### 9.4 Крайние случаи и где заабьюзят

- **Дубли-ревизии** (K1 / K1C / K1 Max; «Creality» vs «Creality 3D»): поиск матчит `aliases` и `slug`,
  форма мягко предупреждает (§8.2–8.3), но не запрещает. Жёсткий дедуп — пайплайн MF-406, не форма.
- **Накрутка полноты** галкой «не нашёл» на всех полях: гасится тем, что пробелы **публичны** на карточке
  и подписаны `filled_by`. Врать невыгодно — врёшь под своим именем.
- **Маркетинговые цифры вендора** (поток «32 мм³/с»): провенанс + `confidence` + бейдж «уточняется»;
  каталог не спорит с вендором, он показывает, **кто это сказал**.
- **Календарь как рекламная площадка** (`nav.sections.md §7`): без баннеров, цен «от» и кнопки «купить».
- **Гость** жмёт «Это мой принтер» / «Уведомить о выходе» → промпт входа, не молчаливый отказ. Набор
  сравнения гостю доступен — он живёт в URL.
- **Мобила:** сайдбар фасетов → нижний лист по кнопке «Фильтры (3)»; панель сравнения конфликтует с
  bottom-tab (`touch.nav.md §1`, «одна навигация на экран») — схлопывается в один чип над таббаром.
  Решение по виду — за Design, требование «не две панели снизу» — отсюда.
- ⚠️ **Блокер (унаследован из `nav.sections.md §4`):** read-API каталога сегодня отвечает `401` без сессии.
  `/printers` — публичный роут в закреплённом меню; выкатывать его за логин-стеной нельзя.
- ⚠️ **Риск раздвоенного канона.** Сегодня в проде живут `machines` + `vendors` (MF-32, `GET /machines`),
  а MF-839 объявляет каноном `printers` (MF-405). Если Front возьмёт `GET /machines` для `/printers/:id`,
  а ресёрчеры будут писать в `printers`, мы получим ровно те два канона, против которых вынесен вердикт
  CTO (§«Вердикт CTO»). Сценарий выше исходит из **одной** таблицы и адресации по `slug`
  (`/printers/<slug>`, не `/printers/<uuid>`). Свести `machines` → `printers` — работа Data в MF-405;
  до этого решения Front не должен реализовывать чтение каталога.

### 9.5 Как поймём, что стало удобнее

- `/research`: медиана «полноты» карточки и **доля карточек с ≥1 источником** (провенанс — не галочка,
  а привычка); сколько правок агента пережили конфликт-мерж без потери человеческого ввода.
- `/printers`: доля визитов, дошедших до карточки принтера; доля выдач с нулём результатов (фасеты не
  должны загонять в тупик); сколько раз нажали «показать принтеры без этого поля» (§7.3) — это прямой
  спрос на дозаполнение, готовый бэклог ресёрчеров.
- Петля: «сообщил о неточности → исправлено → уведомление» — время от флага до правки.

## Живое состояние 2026-07-21: агентский конвейер запущен (MF-2039 продолжение)

Машинный путь §3/§8 («агент `researcher-creality`, программный клиент») реализован и работает на
HYPERPC (тот же кластер, что news-конвейер MF-2028): `printer-drafter` (gemma-4-e4b, slot2) ищет
реальные характеристики модели через keyless DuckDuckGo webfetch → `printer-publisher`
(Qwen3.6-35B-A3B, slot1) собирает JSON по контракту `POST /research/printers` и публикует Bearer
research-ключом сервисного аккаунта `researcher-creality`.

**Провижининг** выполняется по инструкции §«Машинная авторизация
`researcher-creality`» выше: CSPRNG-generated ключ передаётся через environment
в `pnpm run provision:researcher` на dev-vm — аккаунт `researcher-creality`
(роль `researcher`) + один `research`-scope ключ (`scopes=['write']`).
Plaintext ключ живёт только в `~/.researcher-key.env` на `ocsearch`@worker (600, тот же паттерн,
что `.agent-content-key.env` у news-конвейера) — в БД только SHA-256.

**Список моделей** — `/home/plag/pipeline-printers.json` на worker, ровно те же 18 брендов+
флагманы, что в каталоге `vendors`/`machines` (MF-2039, `import-global-printer-vendors-bootstrap.ts`)
— единый список брендов на оба контура (сабы + карточки), не два расходящихся источника. Ротация
по кругу (`pipeline-printers-rotation.state`), не пропускает уже существующие карточки — повторный
проход безопасно дозаполняет пробелы благодаря conflict-safe merge на бэкенде (§8.4).

**Надёжность (тот же принцип, что news-конвейер после инцидента 2026-07-21 со Snapmaker)**: driver
не доверяет текстовому отчёту publisher — проверяет `printers.updated_at` ДО/ПОСЛЕ вызова (строго
возрос = реальный запрос дошёл и прошёл валидацию; сервер бампает `updated_at=now()` при любом
успешном upsert, даже если значения не изменились — надёжный сигнал независимо от insert/update).
**Живая поимка бага**: первый прогон на QIDI Tech Q2 — publisher вывел curl-команду ТЕКСТОМ в
markdown-блоке, ни разу не вызвав bash-инструмент по-настоящему; independent-check корректно не
подтвердил публикацию (`updated_at` не появился), driver упал с понятной ошибкой, ничего не
потерялось молча. Фикс — явное требование в промпте "вызови bash-инструмент, не просто напиши
команду текстом"; повторный прогон на том же бренде прошёл успешно и с тех пор 3/3 прогона чистые.

**Осознанно НЕ делаем (v1)**: фото (`media.hero`/`gallery`) — агент их не грузит, оставляет `null`.
Реальные фото принтеров — копирайтный материал вендора; массово хотлинковать/скачивать под
разбор без явного ОК оператора — плохая идея (см. §7.2 "пустое поле — честный факт, не ноль":
отсутствие фото так и остаётся видимым пробелом на карточке, не выдумкой и не тихой заглушкой).

**Расписание**: `printer-research-pipeline.timer` на worker, каждые 6ч (00/06/12/18 МСК), смещено
на 3ч от `creality-content-pipeline.timer` (news) — оба контура делят один HYPERPC, не конкурируют
за GPU одновременно.

**Проверено живьём**: 3 карточки (Creality K1, QIDI Tech Q2, Snapmaker U1) — реальные, правдоподобные
специи (build_volume/hotend/bed/speed/connectivity/materials), честные `_meta.gaps` там, где источник
не нашёлся (напр. `price.ru_rub` — не выдумана конвертация курса), `confidence=high` с реальными
source URL. `GET /printers?q=...` отдаёт их публично со всеми фасетами (build_volume_mm/kinematics/
capabilities) — подтверждено прямым запросом и живым скриншотом каталога.

## Живое состояние 2026-07-21 (продолжение): фронтенд никогда не читал GET /printers (MF-2042)

Найдено при разборе жалобы оператора «конвейер простаивает» (см. `agent.accounts.md` §MF-2041):
экран `/printers` (список/карточка/сравнение, `apps/web/src/printers/{printersscreen,
printerdetailscreen,comparescreen}.tsx`) с самого первого дня рисовался поверх статичной фикстуры
(`fixtures.ts`, ~7 брендов). Комментарий в коде утверждал блокер «`GET /printers` ещё не публичный
(MF-405 не сведён)» — устарел: `catalog/printers.ts` полностью реализован (фасетный фильтр,
курсор-пагинация, `serializePrinter`, публичный доступ через `ALWAYS_OPEN_GET_PATH_PATTERNS` в
`server.ts`) и давно задеплоен — просто фронтенд никогда не переключили. Итог: всё, что писал
`printer-drafter`/`printer-publisher` в `printers`, было физически невидимо на сайте.

**Фикс**:
- `catalog/printers.ts`: список отдаёт `serializePrinter()` (полная форма) вместо урезанной
  `serializePrinterSummary` — комментарий явно предполагал этот момент («до отдельного удаления
  после интеграции Front»).
- `research/api.ts`: новая `listPrinters()` — курсор-пагинированный фетч `GET /printers`, та же
  форма `PrinterRecord`, что фикстура отдавала синхронно.
- 3 экрана переключены на `listPrinters()`; `fixtures.ts` остался только источником тестовых
  данных (обновлены все 4 связанных `*.test.tsx`).

**Заодно вскрылось**: `printer-research-pipeline.sh` страдал ровно той же болезнью, что
news-конвейер до MF-2041 — 1 модель за системд-прогон. `printers` table была почти пустая (6 строк
из 18, всё — ручные тесты внутри этой же сессии). Применён тот же `BATCH_SIZE`-паттерн
(`process_model`, изоляция сбоя одной модели, `TimeoutStartSec` 600→3600). Полный батч
(`BATCH_SIZE=18`): 17/18 успешно, Anycubic Kobra 3 — честный отказ (тот же транзиентный класс,
что у news-конвейера).

**Фото принтеров** (`media.hero`) — секция выше явно фиксировала «осознанно НЕ делаем (v1)» из-за
копирайт-риска. Оператор пересмотрел и одобрил конкретную схему: **hotlink с официального сайта
вендора**, не AI-рендер, не скачивание/переразмещение на своём хостинге (`img src` = домен
вендора, тот же приём, что favicon-логотипы сообществ и карточки источников в постах).
- `printer-drafter.md`: новое поле `PHOTO_URL` — заполняется ТОЛЬКО когда `webfetch` бьёт по
  официальному сайту бренда (источник №1 по приоритету) и в ответе виден прямой URL картинки;
  честное "не нашёл", если webfetch не отдаёт разметку картинок вообще (агент не гадает).
- `printer-publisher.md`: `media.hero` включается в payload ТОЛЬКО если домен `PHOTO_URL`
  совпадает с доменом официального источника из `sources` черновика — иначе `media` не включается
  вовсе (пустое поле — честный факт, не выдуманная/подставная ссылка).
- **Живой тест подтверждён**: Bambu Lab X1 Carbon →
  `media.hero = https://portal.bblmw.com/x1/x1Series-main-bg-v1.png` (собственный CDN бренда, не
  сторонний хостинг).

**Открыто**: фото-инструкция проверена на 1 модели из 18 — полного бэкафилла фото по всему
каталогу ещё не было (conflict-safe merge на бэкенде §8.4 значит он органически дозаполнится
следующими плановыми прогонами `printer-research-pipeline.timer`, либо нужен отдельный ручной
батч). Карточка `MF-2042` — полный отчёт.
