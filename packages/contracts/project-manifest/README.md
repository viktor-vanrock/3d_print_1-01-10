# Шов `project-manifest` — `portal.project.yaml` v1 (MF-1967)

Первая волна эпика «Ввести project-as-code» (родитель MF-1963, `docs/epics/project.git.md`
как git-субстрат уже есть). Контракт манифеста поверх дерева файлов проекта — декларативная
схема для многокомпонентных самоделок (робо-рука и т.п.: несколько печатных деталей + плата +
код + сборка), которых одной структуры папок (§10.2 project.git.md) недостаточно.

## Файлы

- **`schema.v1.json`** — JSON Schema (draft-07) манифеста. Источник правды по форме файла.
  Правки — **только через PR, апрув CTO** (это шов, см. `packages/contracts/package.json`
  description). `additionalProperties: false` на каждом уровне — deny-by-default: неизвестное
  поле вне `x-*`-неймспейса отклоняется на схемном уровне, произвольный исполняемый код
  (`run`/`exec`/`script` и т.п.) структурно невозможен.
- **`index.ts`** — ручное зеркало схемы в TS-типах для `apps/api`. Меняется в том же PR, что
  и `schema.v1.json` (нет кодогенерации — сверка ручная, как `device-protocol/handshake.v1`).
- **`fixtures/`** — канонические примеры: `minimal.v1.yaml` (наименьший легальный манифест),
  `multi-component.v1.yaml` (полный пример — конфигурации/артефакты/компоненты/BOM/соединения/
  фазы, включая `x-*`-расширение).

## Кто чем владеет

Parser/resolver (YAML → `ProjectManifestV1` → resolved project graph), диагностические коды,
security-проверки и импорт трёх входов (STL-пачка/составной 3MF/git-репозиторий) —
`apps/api/src/models/projectManifest/` (зона Back). Здесь — только форма контракта, без
бизнес-логики.

## Версионирование

`schemaVersion` — целое, сейчас только `1` (`const`). Новая версия — новый файл
`schema.v2.json` + `ProjectManifestV2` в `index.ts`, аддитивно (v1-манифесты остаются валидными
для резолвера, который поддерживает обе версии до отдельного решения о выводе v1 из эксплуатации).
Breaking-правка существующего v1 (сужение типа, новое обязательное поле) — не делается никогда;
это и есть смысл фиксации версии в файле.

## Вырожденный случай

Одиночный STL/3MF **не обязан** содержать `portal.project.yaml` — резолвер (`apps/api`)
синтезирует вырожденный манифест (один артефакт, без компонентов/BOM/фаз) на лету. Схема здесь
описывает файл, когда он есть; отсутствие файла — не ошибка схемы, а решение резолвера до её
применения.

## Неизвестные расширения (`x-*`)

Любой объект схемы допускает дополнительные поля с префиксом `x-` (`patternProperties`).
Резолвер обязан пронести их в `resolved project graph` как непрозрачный бакет `extensions`,
не читая и не теряя — контракт форвард-совместимости для интеграций, которых схема v1 ещё
не описывает явно.

## Безопасность (граница ответственности схемы vs резолвера)

Схема ловит структурную форму (типы, обязательные поля, deny-by-default на неизвестных
ключах, синтаксис путей/id). Она **не** гарантирует семантическую безопасность значений —
это резолвер (`apps/api/src/models/projectManifest/security.ts`):

- Path traversal (`artifacts[].path` не выходит за пределы дерева проекта — `..`, абсолютные
  пути, symlink/submodule-эскейп при git-импорте).
- SSRF (`bom[].vendor.url` — резолвер никогда не делает fetch по значению; allowlist схемы
  `http`/`https`, отказ на приватные/метаданные-адреса при любом будущем разыменовании).
- YAML-бомбы (anchor/alias expansion), дублирующиеся ключи, ZIP-бомбы составного 3MF —
  на уровне парсинга/импорта, до применения этой схемы.

Полная таблица диагностических кодов — `apps/api/src/models/projectManifest/diagnostics.ts`.
