# Модерация сообщества и ограничения TL0

← [docs/design/readme.md](readme.md) · контур UX для MF-416, без продуктового кода

## Решение

Интерфейс не выносит вердикт и не вычисляет лимиты: сервер — единственный
источник правды для статуса флага, видимости контента, прав актёра и времени
снятия ограничения. UI быстро и честно показывает последствия действия:
отправленный флаг получает подтверждение, скрытый материал не выдаётся за
удалённый, а TL0 видит конкретно недоступное действие и время следующей
попытки. Модератор действует из очереди, всегда указывает причину и может
отменить обратимое решение.

Это дополняет, а не меняет контракты MF-1417 (flag/moderation/audit) и MF-1418
(TL0/anti-fraud). Числа лимитов, пороги авто-скрытия, время окна и состав
разрешений не зашиваются в web: Front использует значения и коды ответа этих
контрактов.

## Участники и обозначения

| Участник | Что видит и делает |
|---|---|
| Читатель | Читает доступный контент; может отправить флаг после входа. |
| Автор | Видит свой скрытый материал и причину; подаёт одну appeal до решения. |
| Модератор | Видит очередь и доказательства; выбирает действие с обязательной причиной. |
| Апеллятор | Повторно рассматривает решение, не заменяя исходный audit trail. |

На карточке/в очереди у агентского автора остаётся существующая честная метка
«ответ ассистента» или «обновлено агентом»; она не является причиной
модерации и не скрывается после флага.

`status`, `visibility`, `reason_code`, `can_appeal`, `restrictions[]`,
`remaining` и `reset_at` приходят из API. Если поле не пришло, UI не
догадывается о нём и показывает безопасное состояние ошибки/повторной загрузки.

## Путь 1. Флаг → скрытие → решение

### 1. Отправка флага

Точка входа — небольшая текстовая кнопка «Пожаловаться» в меню контента;
не красная primary-кнопка. Она открывает модалку с заголовком «Пожаловаться на
материал», именем типа материала и ссылкой «Правила сообщества».

Причина выбирается радиокнопками с понятным текстом: «Нарушение закона или
опасный контент», «Нарушение прав», «Спам или мошенничество», «Оскорбления или
травля», «Другое». Поле «Поясните, что произошло» необязательно для типовых
причин и обязательно для «Другое»; лимит/валидация отображаются по ответу API.
Нельзя обещать анонимность, если её нет в контракте.

| Состояние | Текст и действие |
|---|---|
| Готово | Primary «Отправить жалобу», secondary «Отмена». |
| Отправка | Кнопка занята, повторный submit невозможен; текст «Отправляем жалобу…». |
| Успех, видимость не изменилась | «Жалоба отправлена. Мы рассмотрим её.»; закрыть модалку, вернуть фокус в меню. |
| Успех, материал скрыт | «Жалоба отправлена. Материал временно скрыт на время проверки.»; на месте материала сразу рендерится плейсхолдер §2. |
| Дубликат | «Вы уже пожаловались на этот материал.»; кнопка отправки отсутствует. |
| Нет входа / нет права | «Войдите, чтобы пожаловаться на материал.» + «Войти». |
| Лимит / временный отказ | «Сейчас нельзя отправить ещё одну жалобу. Попробуйте позже.» + время, только если пришёл `reset_at`. |
| Сеть / 5xx | «Не удалось отправить жалобу. Материал не был скрыт с вашей стороны.» + «Повторить». |

Смена `visible → hidden` производится только после подтверждённого ответа API,
не оптимистично. Так автор не получает ложного сигнала, а читатель не видит
контент, который сервер уже признал временно скрытым.

### 2. Скрытый материал

Для обычного читателя и автора это один спокойный блок на месте материала,
а не пустой провал разметки. Заголовок: «Материал временно скрыт на время
проверки». Текст: «Он недоступен в общей ленте и поиске, пока модератор не
примет решение.»

- Для читателя: только текст и «Назад к обсуждениям».
- Для автора: также причина человеческим текстом, дата решения при наличии и
  «Оспорить решение», только если `can_appeal=true`.
- Для модератора: «Открыть в очереди»; исходный материал остаётся доступен в
  защищённом контексте очереди, но не через публичную ссылку.
- Если тред закрыт/заблокирован без скрытия, применяется уже принятая строка
  `Тред закрыт для новых ответов`; скрытие не подменяется этим статусом.

### 3. Очередь модератора

Роут и доступ определяет API. Экран имеет один primary-смысл — обработать
выбранный флаг; сортировку и фильтры не выдаём за решение по умолчанию.

```
Очередь модерации                         [Новые 12] [На проверке 3]
[поиск] [Тип материала] [Причина] [Сбросить]

Карточка: причина · время · автор (с меткой агента) · короткий фрагмент
          [Открыть] [Взять в работу]

Деталь: исходный материал | история флагов | audit-действия
          Причина решения [выбрать…]
          [Скрыть] [Вернуть видимость] [Закрыть тред] [Отклонить флаг]
```

В таблице/карточке есть статус, причина, возраст и число флагов, но не личные
данные жалобщика, если они не разрешены контрактом. Открытие детали не меняет
статус; «Взять в работу» меняет его только после ответа API.

Перед необратимо воспринимаемым действием открывается confirm-sheet: действие,
цель, обязательный селектор причины, краткое поле пояснения и предупреждение
«Действие попадёт в журнал модерации». По ответу API показывается тост с
«Отменить», когда `undo`/reversal разрешён; не придумывать локальную отмену.
Причина видна автору в его языке, внутреннее пояснение — только роли, которым
его разрешил сервер.

### 4. Appeal

Автор открывает sheet «Оспорить решение». В нём отображаются решение и его
публичная причина, одно обязательное поле «Почему решение стоит пересмотреть»
и кнопки «Отправить апелляцию» / «Отмена».

После успеха: «Апелляция отправлена. Материал останется скрытым до решения.»
Кнопка становится неактивной с подписью «Апелляция уже рассматривается».
После решения: «Решение пересмотрено: материал снова виден» либо «Решение
оставлено в силе: {причина}». История не исчезает и не редактируется клиентом.

## Путь 2. TL0: понятное ограничение без стыда

TL0 не является ошибкой пользователя и не называется «подозрительным». В
профиле/на странице сообщества показывается компактный нейтральный баннер:

> «Новый аккаунт: часть действий пока ограничена, чтобы защитить сообщество от
> спама. Ограничения снимутся автоматически по мере активности.»

«Подробнее» открывает список ограничений, который строится только из
`restrictions[]`. Для каждой строки: действие, доступный остаток при наличии,
и точное время следующей попытки при наличии `reset_at`. Не показывать
выдуманный прогресс до TL1 и не обещать конкретную дату повышения уровня.

| Место | Доступно | Блокировано/лимит | Текст |
|---|---|---|---|
| Личные сообщения | поле и кнопка | вместо композера информационный блок | «Личные сообщения станут доступны после снятия ограничений нового аккаунта.» |
| Тред/пост | композер | кнопка disabled с пояснением под ней | «Лимит публикаций исчерпан. Следующая попытка: {дата и время}.» |
| Ссылка/картинка | редактор | конкретное вложение/ссылка помечены инлайн | «Для нового аккаунта это действие пока ограничено.» |
| Редактирование | кнопка «Сохранить» | действие отклонено API | «Время редактирования истекло.» |
| Голос | обычный контрол | сохранённый выбор откатывается | «Голос не засчитан: действие временно ограничено.» |

Если `remaining=1`, пишем «Осталось 1 действие»; если ноль — «Лимит исчерпан».
При `reset_at` дата показывается в локали пользователя и полным временем в
доступном описании. Обратный отсчёт — только дополнение к абсолютному времени,
обновляется без анимации при `prefers-reduced-motion`; после нуля повторно
запрашивается состояние, а не разблокируется действие локально.

Повышение trust-level приходит как новое серверное состояние: баннер мягко
меняется на «Ограничения нового аккаунта сняты», без конфетти и без обещания
нового статуса, если API его не прислал.

## Матрица экранных состояний

| Экран | Загрузка | Пусто | Ошибка | Недостаточно прав |
|---|---|---|---|---|
| Очередь | 3–5 skeleton-карточек | «В очереди нет материалов для проверки.» | «Не удалось загрузить очередь.» + «Повторить» | «У вас нет доступа к очереди модерации.» |
| Деталь флага | skeleton текста и audit-строк | — | «Не удалось загрузить материал для проверки.» + «Повторить» | «Этот материал недоступен для проверки.» |
| Список appeal | skeleton строк | «Апелляций на рассмотрении нет.» | «Не удалось загрузить апелляции.» + «Повторить» | «У вас нет доступа к апелляциям.» |
| Ограничения TL0 | компактный skeleton баннера | баннер не рендерится при отсутствии ограничений | «Не удалось проверить ограничения. Попробуйте ещё раз.» | действие остаётся закрытым по ответу API с его пояснением |

`404` — «Материал не найден»; `403` не маскируется под `404`; `429` использует
текст лимита и `reset_at`; `5xx` не меняет локально видимость, лимит или выбор
голоса. Ошибку отличаем от пустого списка всегда.

## Доступность, адаптивность и motion

- Все действия доступны с клавиатуры; после закрытия sheet/modалок фокус
  возвращается в породившую кнопку. Ошибка получает `role=alert` и текст,
  а успешная смена статуса — ненавязчивый live-region.
- Причина, скрытие, блокировка и обратный отсчёт дублируются текстом: цвет,
  иконка и пульсация не являются единственным носителем смысла. Контраст и
  видимый `:focus-visible` обязательны.
- На mobile очередь — список карточек, фильтры — горизонтально прокручиваемые
  chips, detail открывается отдельным экраном. На desktop разрешён master-detail
  с читаемой шириной текста. Все интерактивные зоны ≥48px.
- Анимация допускается только как короткий переход статуса после подтверждения
  сервера; без `requestAnimationFrame`, с отключением/сокращением при
  `prefers-reduced-motion`. Во время отправки не менять порядок карточек
  неожиданно — сначала подтверждение, затем обновление списка.

## Handoff Design → Front (MF-1423)

**Файл-источник:** этот документ; API-поля и коды окончательно сверяются с
`docs/contracts/community-moderation*.md` (MF-1417) и контрактом TL0 MF-1418.

1. Реализовать один набор визуальных состояний для `flag`, hidden-placeholder,
   moderator-queue/detail, appeal и TL0-restriction; не копировать числовые
   лимиты в `apps/web`.
2. Рендерить серверные `reason_code` через центральный RU-маппинг; неизвестный
   код — «Причина указана модератором», без падения и без показа raw-кода.
3. Все mutation-кнопки блокировать на время запроса, обрабатывать повтор/ошибку
   по матрице выше; optimistic update разрешён только для локального pending,
   не для `hidden`, appeal или снятия лимита.
4. Проверить component/Playwright-сценариями: flag→hidden, пустая/ошибочная
   очередь, обязательная причина, allowed undo, appeal pending/решена,
   TL0 с остатком/`reset_at`, 403/429/5xx, клавиатура и mobile 48px.

Конфликтующие швы: `apps/web/src/community/**` (новый community UI), общий
`apps/web/src/**/api.ts` для нормализации ошибок, существующие primitives из
`ui/ui.tsx`/`docs/design/components.md`. Не менять публичные страницы треда
в обход API: их read-only и закрытый состояния уже описаны в
`docs/design/community.md`.

## Acceptance UX

- Все переходы `flag → hidden → moderation decision → appeal` имеют один
  источник состояния, RU-тексты, empty/loading/error/403/429 и возврат фокуса.
- Автор, читатель и модератор видят разный, минимально необходимый контекст;
  скрытие не удаляет audit-след и не раскрывает жалобщика.
- TL0 объясняет ограничение и время повтора без жёстко заданных в UI порогов;
  разблокирование происходит только после нового ответа API.
- Handoff выше достаточен для MF-1423 и не создаёт второго конкурирующего UI-
  контракта.
