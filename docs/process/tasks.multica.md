# Доска задач — Multica (`tasks.3mf.tech`)

Общее приватное пространство задач под проект 3mf на self-hosted [Multica](https://github.com/multica-ai/multica)
(open-source оркестратор задач для AI-агентов, Modified Apache 2.0 — внутреннее использование разрешено).
Живёт на нашем VDS, вход только через нашу авторизацию (PlagID). Публично недоступно.

> Как **агенту** оперировать доской программно (режим API/CLI vs режим демона-исполнителя) — `docs/process/multica.md`.

> **Секреты, IP, точные команды эксплуатации/переноса — не здесь, а на VDS** (`~/tasks.multica/MOVING.md`).
> Этот файл — про то, как доской *пользоваться*, а не как она развёрнута.

## Язык рабочих записей

Русский — основной язык карточек, описаний, комментариев, handoff, решений и
отчётов. Английский оставляем для кода, API, CLI, путей, имён файлов,
идентификаторов и неизбежных терминов; в обычном тексте рядом даём русское
пояснение. Полный стандарт, включая требования к lineage и шаблон handoff,
зафиксирован в [headquarters.documentation.md](headquarters.documentation.md).

## Зачем доска, если есть `issues/`

Два разных инструмента, не дублируются:

| | `issues/*.md` + `epics/*.md` (git) | Multica (`tasks.3mf.tech`) |
|---|---|---|
| Что | Спеки, эпики, крупные инициативы, решения | Живая операционная доска: что делается прямо сейчас |
| Ритм | Меняется через PR, ревьюится | Меняется на лету, статусы в реaltime |
| Кто ведёт | Люди в репо | **Ассистент (Claude) + люди** |
| Видимость | В коде/PR | В вебе всей команде |

Правило: **большие/архитектурные вещи → `epics/` + `issues/`** (версионируется, ревьюится);
**повседневная работа и то, что ассистент делает по поручению → доска Multica**.
Крупная задача с доски может ссылаться на `issues/<NNN>` и наоборот.

## Рабочая договорённость (важно)

**Задачи, которые Валерий поручает ассистенту, ассистент заводит на доске Multica и держит статус актуальным**
(`todo → in_progress → done`), чтобы команда видела, что и как делается. Распространяется и на будущие сессии.
То есть поручение в чате = карточка на доске, а не только действие «в тишине».

## Доступ

1. **Гейт PlagID (Telegram)** — кто вообще попадёт на `tasks.3mf.tech`. Заходишь на сайт → редирект на вход
   через Telegram (`auth.plag.space`). Список допущенных Telegram-ID ведётся на VDS.
2. **Учётка Multica** — внутренний аккаунт + членство в воркспейсе `3mf`. Вход по email + одноразовый код.
   Пока код фиксированный (внутренний, на VDS), позже — реальная отправка на почту (см. ниже).

Воркспейс один: **`3mf`**, префикс задач — **`MF`** (задачи нумеруются `MF-1`, `MF-2`, …).

## Как ассистент ведёт задачи

Ассистент управляет доской через `multica` CLI (локально на VDS мимо гейта, либо снаружи по PAT).
Логин CLI — **только по токену**: `multica login --token <PAT>` (PAT создаётся в вебе Settings → Tokens).
Браузерный `multica setup self-host` за PlagID-гейтом не проходит (редирект на Telegram теряет CLI-callback),
поэтому используем токен. Гейт пропускает запросы с заголовком `Authorization` (машины по PAT), а браузеры —
по cookie: то есть CLI работает и с внешнего адреса `https://tasks.3mf.tech`.
Основные команды:

```bash
multica issue create --title "…" --description "…" --priority high   # завести
multica issue list --limit 20 [--status in_progress]                 # посмотреть
multica issue update MF-12 --status in_progress                      # сменить статус
multica issue assign MF-12 --to "<агент/человек>"                    # назначить
multica issue view MF-12                                             # детали
```

## Как оформлять карточки

- **Заголовок** — коротко и по делу, с глагола («Прикрутить email-провайдер», не «email»).
- **Описание** — контекст, чтобы задача была понятна без чата: что, зачем, критерий готовности.
- **Приоритет** — `urgent` / `high` / `medium` / `low`. По умолчанию `medium`.
- **Статус** — `todo → in_progress → done` (плюс `blocked` с причиной в комментарии). Держать актуальным: взял в работу — `in_progress`, завершил — `done`.
- **Одна карточка = один результат.** Крупное разбивать; если это эпик/архитектура — завести `epics/`+`issues/` в репо и сослаться на них из описания.
- Ссылки на спеки/PR/файлы — прямо в описании.

**Шаблон описания** (что / зачем / готово когда):

```text
Что: <одно предложение — что делаем>
Зачем: <зачем это нужно, контекст>
Готово когда: <критерий приёмки, проверяемый>
Ссылки: <issues/NNN, epics/*, PR, файлы — если есть>
```

**Пример:**

```bash
multica issue create --priority high \
  --title "Прикрутить email-провайдер для OTP" \
  --description "Что: подключить Resend или SMTP для отправки кодов входа.
Зачем: сейчас код фиксированный (issues/002), реальным юзерам письма не уходят.
Готово когда: новый юзер получает 6-значный код на почту, APP_ENV=production, фикс-код убран.
Ссылки: docs/issues/002.auth.triple.md, docs/process/tasks.multica.md § «Email вместо фиксированного кода»."
```

## Как добавить нового пользователя

**Гейт (шаг 1) синхронизирован с доступом к 3mf.tech (2026-07-06):** если человеку уже выдан доступ к `3mf.tech` (через `auth.plag.space` → Drafts → проект `3mf` → «Дать доступ»), Telegram-гейт `tasks.3mf.tech` пускает его автоматически — прописывать отдельно не нужно. `ALLOWED_TG_IDS` (на VDS, `~/tasks.multica/.env`) остаётся как способ пустить на доску того, у кого доступа к 3mf.tech нет и не будет (подрядчик/агент без продуктового доступа) — тогда шаг 1 нужен вручную. Механизм: `auth.plag.space` кладёт флаг `has3mf` во внешний токен (тот же `draft_access`/slug `3mf`), `gate/server.js` на VDS пускает по `ALLOWED_TG_IDS ИЛИ has3mf`.

Дальше шаги (правки на VDS, делает ассистент/админ):
1. **Гейт:** Telegram-ID человека → список допущенных (**нужно, только если доступа к 3mf.tech ещё нет** — см. выше).
2. **Multica:** его email → список разрешённых.
3. **Инвайт** в воркспейс `3mf` (в вебе: Settings → Members → Invite).

Дальше он входит: Telegram-гейт → email + код. **С 2026-07-06 код уже НЕ общий фиксированный** — Multica переведена в `APP_ENV=production` + реальный SMTP (Timeweb, `auth@3mf.tech`, тот же ящик что у 3mf.tech), каждому приходит свой одноразовый код на почту.

## Как подключить своего агента

**Уже реализовано, не гипотетически:** сквад Autofab (CTO → Lead → {Design, Fullstack, Data, PM} → разрабы + пайплайн), агенты работают иерархично над portal.ru — полное описание, роли, UUID, правила доски и грабля с упоминаниями агентов (`@Имя` — no-op, нужна ссылка `mention://agent/<uuid>`) — **см. `docs/process/squad.multica.md`**.

Общий рецепт ниже — как завести ЕЩЁ одного агента (нового или для другого проекта):

1. На машине, где установлен и **авторизован** нужный агент-CLI (со своими ключами — напр. ключ Anthropic),
   поставить `multica` CLI.
2. `multica login --token <PAT>` (PAT создаётся в вебе: Settings → Tokens).
3. `multica daemon start` — демон обнаружит установленные агент-CLI и зарегистрируется как **Runtime**.
4. Назначаешь задачу на агента (`multica issue assign … --to <agent>`) — демон её подхватывает и выполняет,
   прогресс стримится на доску.

Важно: расход токенов/ключи агента — на той машине, где крутится демон. Поэтому автономного агента ставим осознанно,
на отдельном раннере, а не «по умолчанию».

## Email вместо фиксированного кода (позже)

Когда появятся реальные соучастники — подключаем провайдер писем (Resend API-ключ **или** наш SMTP),
переводим Multica в production-режим, убираем фиксированный код. Тогда каждый получает свой одноразовый код на почту.
Тот же провайдер закроет и хвост авторизации самого portal.ru (`issues/002` — там отправка писем тоже не подключена).
